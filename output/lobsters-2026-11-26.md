## 2. Ubuntu 安全漏洞响应速度迟缓引发批评

- 原始链接: <https://www.openwall.com/lists/oss-security/2026/11/25/9>
- 英文标题: Slow Ubuntu security response times

独立安全研究员 Hanno Böck 在 oss-security 邮件列表中发文，批评 Ubuntu 对严重安全漏洞的修复响应速度令人担忧。他列举了多个案例：11 月 16 日公开的 Linux 内核 TCP 栈远程内存损坏漏洞 NoisyTCP（CVE-2026-99288），九天后 Ubuntu 仍未发布补丁，而其他发行版在漏洞细节公布时已提供修复；11 月 18 日公开的 KVM 主机逃逸漏洞（CVE-2026-99312，影响 AMD 虚拟化）同样无修复；此前另一远程 TCP 损坏漏洞（CVE-2026-98432）修复耗时数周，且已有迹象表明该漏洞可能正在野外被利用。Böck 指出，远程内存损坏类内核漏洞的修复理应在数小时内完成，而非数天或数周。他还批评了 Ubuntu 的内核维护策略：Ubuntu LTS 系统内核版本为 7.0.0-44，表明其向旧内核回移补丁，而非采用 kernel.org 的长期支持版本；相比之下，Debian stable 使用 6.12.118+deb13，基于较新的长期支持内核。他建议所有 Linux 发行版应基于内核开发者维护的长期发布版本，而非自行回移补丁，以缩短修复周期、降低安全风险。

## 3. 优化 Rustc 的新一代特征求解器

- 原始链接: <https://donsz.nl/blog/optimizing-rustcs-next-trait-solver>
- 英文标题: Optimizing Rustc's next trait solver

本文是作者 2026 年 Eurorust 演讲的写稿，介绍 Rust 编译器新一代 trait solver（特征求解器）的性能优化工作，该求解器将随 Rust 1.102.0 稳定发布，性能是最后的阻塞问题。文章从零基础出发，解释 trait 是类型的属性，trait solver 负责在类型检查时验证 trait bound 是否成立，其机制与 Prolog 逻辑求解器高度相似。求解策略包括查找 impl 块、使用编译器内置规则、利用 where bound 作为假设。多步求解中，一个问题可派生多个子问题，形成候选树；关联类型进一步增加复杂度。性能瓶颈有两方面：一是调用频率极高（仅编译标准库，Sized 查询就达约 80 万次）；二是单次调用可执行任意计算（因 impl 块兼具输入与输出，使类型系统图灵完备），复杂度可能随程序规模指数增长。新旧 solver 内部假设不同，导致部分既有程序编译时间出现多项式甚至指数级变化。项目始于 2015 年 Chalk 实验，2022 年正式立项为「project zero」，目标是消除类型系统中的健全性缺陷。作者全职投入约一年，专注性能优化，工作由 Hexcat 与 RustNL 资助。

## 5. 废除锁中毒：Rust Mutex Poisoning 机制应当被移除

- 原始链接: <https://lucumr.pocoo.org/2026/11/25/poisoning/>
- 英文标题: Abolish Lock Poisoning

Armin Ronacher 在本文中强烈主张 Rust 标准库的 Mutex 锁中毒（poisoning）机制应被彻底移除或降级为可选特性。该机制规定：当持有 std::sync::Mutex 的代码发生 panic 时，锁被标记为 poisoned，后续 lock() 调用将返回 PoisonError。作者列举了多个实际危害：其一，PoisonError 内部持有 guard，导致错误包装或 if let 回退路径中锁被意外长期持有，引发死锁；其二，一次 panic 使锁永久失效，在 tokio 任务、线程池等场景中进程虽存活却彻底不可用，RLS、Neon safekeeper、cargo、deno、polars、rustc 等均曾因此遭受级联故障；其三，即便用 into_inner() 恢复，poison 标志仍保留，造成每次访问都触发昂贵副作用。作者指出，标准库自身（标准 I/O、backtrace、WASI 锁）早已忽略 poison 标志，Tokio、Wasmtime、crossbeam-channel 等主流生态也普遍绕过该机制，parking_lot 维护者称之为「反特性」。此外，作者质疑为何仅 Mutex 有中毒而 RefCell 没有，认为逻辑上不一致。他建议 Rust 团队稳定 nonpoison 变体并设为 Mutex 默认行为，需要中毒语义的用户通过独立的 Poison<T> 包装器显式 opting in，同时适用于 RefCell 等类型。作者警告最坏结果是让 lock() 直接 panic 而非返回 Result，那只会将「缓慢永久故障」固化为唯一选择。

## 10. 用决策模型在海量 crate 中揪出恶意软件：Rust 供应链安全扫描实验

- 原始链接: <https://rustfoundation.org/media/needles-haystacks-and-numbers-between-0-and-1/>
- 英文标题: Needles, Haystacks, and Numbers Between 0 and 1

Rust 基金会资助了一项探索性实验，利用决策模型（decision model）对 crates.io 上发布的 crate 进行自动扫描，标记疑似恶意包供人工审核。决策模型输出受限（给出 0 到 1 的恶意概率评分），相比 LLM 更快更廉价，适合全量扫描。项目不采取任何自动行动，仅将结果作为第三方报告交由 crates.io 团队和 RustSec 等按正常流程处理；扫描后不保留 crate 内容，仅存名称、版本、文件名列表和评分。截至发文，已扫描 11 月 11 日至 21 日共 135,548 个 crate 文件。阈值实验显示：0.35 阈值下 332 个 crate 被标记但仅 1% 为真阳性；0.7 阈值下 15 个 crate 中 27% 为真阳性、73% 为假阳性；0.9 阈值下 4 个 crate 全部命中。团队认为 0.7 附近是当前模型与提示词组合的合理平衡点。假阴性率难以自动量化，计划 1 月结合社区报告做回顾评估。已知局限包括模型缺乏推理能力、对嵌入大量非代码数据的 crate 易误判。未来方向包括优化提示词与模型、与 crate 来源数据及元分析等其他安全信号融合，并计划在 2027 年初寻求赞助以扩大实验规模，同时关注 crates.io 的 RFC 4016（注册表扣留机制）。

## 11. 一种提取π十六进制数字的更快算法

- 原始链接: <https://www.stylewarning.com/posts/faster-digit-extraction/>
- 英文标题: A faster algorithm for extracting hexadecimal digits of π

Robert Smith提出了一种新的π十六进制数字提取算法，无需计算前导数字即可直接定位目标位。该算法基于Euler 1779年的级数重新排列，核心优化有两点：一是按奇数分母收集级数项，使四个余数合并后仅做一次除法；二是将分母M与3M配对，用两次完整模幂运算同时服务两个分母。与Huvent八项公式相比，该算法减少约61%的除法和38%的完整模幂运算，每操作推进位数从1.50提升至约2.41（模幂）和3.86（除法）。作者以AVX-512 IFMA实现，在跳过百万至万亿个十六进制位的测试中，单线程加速约65%，多线程加速10%至62%，整体墙钟时间缩短近40%。实现细节包括Montgomery乘法中复用逆元、用向量绝对值替代符号修正等微优化。作者认为共享模算术是加速关键，类似技巧或可推广至其他BBP型级数。

## 12. 从形式化验证到CHERIoT缺陷发现

- 原始链接: <https://cheriot.org/verification/2026/11/24/griotte-verification-effort.html>
- 英文标题: From formal verification to bug-finding in CHERIoT

Cerise项目始于奥胡斯大学，旨在为能力机开发形式化验证方法，重点处理非单调域转换等复杂属性。其子项目Griotte将验证技术应用于CHERIoT切换器（switcher），在Rocq定理证明器的Iris分离逻辑框架上，构建了可复用的分离逻辑与逻辑关系，作为CHERIoT的「通用契约」，用以推理未知代码的行为。验证过程中，团队发现两个关键缺陷：其一，恶意调用者可利用栈高水位寄存器（SHWM）与异常处理器的交互，将SHWM移至栈基址以下，在切换器返回路径中触发故障，从而恢复被调用者未清除的栈帧及私有数据；其二，恶意调度器可重新调度已退出线程，因退出路径未清除保存区，导致线程持有过期的局部能力，违反无捕获（no-capture）保证。两个缺陷分别通过禁止调用者修改栈基址、在退出路径清除寄存器文件并将退出线程转为空闲线程等方式修复。修复后，团队将验证扩展至完整的cheriot-sail指令集，确认当前上游切换器与硬件共同实现了线程与隔间隔离及无捕获属性。未来计划验证加载器，并将该逻辑机制推广至CHERIoT应用层的安全验证。

## 13. 用 Haskell 构建回合制游戏 WebSocket 服务器

- 原始链接: <https://blog.gordo.life/2026/04/12/haskell-websockets.html>
- 英文标题: Writing a Turn Based Game Websocket Server in Haskell

文章介绍了在 Haskell 中构建多人回合制游戏 WebSocket 服务器的设计模式，以井字棋为例。核心思路是利用共享广播 TChan，让所有连接的 WebSocket 客户端同步接收游戏状态更新。作者基于 Yesod 框架，用 TVar 存储游戏映射表，并引入 stm-containers 库的 HAMT 结构替代普通 Map 以提升并发写入性能。游戏加载环节借助 STM 事务保证并发插入时所有线程共享同一 GameState 实例；为规避「惊群」问题，用 MVar 标记正在加载的游戏条目，其他线程阻塞等待加载完成后再读取缓存。缓存清理方面，借助 resourcet 包的 allocate 机制，通过引用计数跟踪当前连接数，计数归零时自动从缓存移除游戏条目，防止内存泄漏。WebSocket 处理器用 race_ 并发管理收发消息，连接断开时自动触发资源释放逻辑。作者最终将该模式抽象为 shared-resource-cache 开源库，适用于任何需要多线程共享动态加载资源引用的场景，与传统缓存的区别在于必须保证所有持有者引用同一实例，而非简单按策略淘汰。

## 14. mockitdown 示例：类 SwiftUI 的用户界面原型语言

## 15. 通过可变洞实现ANF的扁平化/非高阶构造

- 原始链接: <https://blueberrywren.dev/blog/anf-mutable/>
- 英文标题: Flat/non-higher-order construction of ANF via mutable holes

本文提出了一种从简单函数式语言构造ANF（A-正规形）的算法，核心思想是用「可变洞」（mutable hole）替代传统的高阶闭包方法。输入语言包含Let、Name、Int、Add、Print等构造器；输出为所有let置于顶层的扁平ANF形式。算法在ANF类型中引入Hole构造器（anf option ref），转换每个子表达式时返回三元组：已生成的ANF片段、绑定名、以及待填充的洞引用。转换过程中，先处理「头」部分并留下洞，再处理「体」部分，最后将体的结果填入头留下的洞中，从而避免使用闭包或间接跳转。作者指出，传统continuation方法存在两个缺陷：一是转换时分配约两倍于必要的内存（ANF本身加闭包），二是闭包分配与应用带来额外开销。新算法仅分配输出程序所需的内存，无多余闭包，预期性能优于等价的高阶版本。文章给出了完整的OCaml实现，并以嵌套let表达式为例演示了转换过程。不足之处是会产生较多冗余名称，可通过特判和折叠消除。作者还展望了将该方法推广到CPS转换的可能性。

## 1. CoW：面向 Wayland 的堆叠式窗口管理器

- 原始链接: <https://cow-wm.codeberg.page/cow/>
- 英文标题: CoW — a stacking window manager for Wayland

CoW（Compositor on Wayland）是一款基于 River 合成器的堆叠式窗口管理器，最新版本为 0.3（2026 年 9 月），下一版本 0.4 已合并 22 项变更。其设计目标是重现 90 年代 FVWM 与 MWM 的视觉风格，同时兼容更现代的界面风格。配置方面，CoW 支持通过命令直接操作，且这些命令同样可写入配置文件，从而允许外部应用以脚本方式驱动窗口管理。高级特性包括：IPC 脚本接口、可定制的服务端窗口装饰、多种命令控制窗口放置、原生菜单支持、通过规则触发脚本执行，以及内置领域特定语言（DSL）实现条件过滤。项目以 C 语言编写，代码托管于 Codeberg 平台。社区规模较小但氛围友好，主要交流渠道为 IRC（irc.libera.chat 的 #cow-wayland 频道），此外在 Mastodon 上也有相关讨论，并设有社区 Wiki 供查阅。项目鼓励外部贡献者参与开发，README 中附有开发指南，其他问题可在 IRC 中咨询。总体而言，CoW 定位为一款兼具复古美学与现代脚本化能力的轻量级 Wayland 窗口管理器，适合偏好堆叠式布局且希望高度自定义桌面体验的用户。

## 2. Rust 中 Arc 下转型的探索

- 原始链接: <https://wolfgirl.dev/blog/2026-09-29-pining-for-arc-downcasting-in-rust/>
- 英文标题: Pining for Arc Downcasting in Rust

文章讨论了在 Rust 并发缓存场景中，如何避免对大型 JSON 值进行昂贵的 clone 操作，同时解决 Arc<JSON> 无法直接下转型为 Arc<String> 的难题。作者首先将缓存值包装为 Arc<JSON>，使 clone 仅增加引用计数；但发现从 Arc<JSON> 中提取 Arc<String> 会因生命周期问题而失败。为此，作者设计了 PinRef<V, T> 结构体，内部持有 Pin<Arc<MustPin<V>>>（利用 Pin 保证地址稳定性）和一个 *const T 裸指针（指向 val 内部目标位置）。通过 project、filter_project 等方法，利用高阶函数签名「for<'a> FnOnce(&'a T) -> &'a U」约束下转型必须为固定偏移，从而在保持地址稳定的前提下安全完成类型投影。文章还解释了为何简单的 &'static T 方案会因值移动而失效，以及为何必须引入 PhantomPinned 防止 Unpin 破坏 pin 保证。作者承认该方案可能仍存在未发现的未定义行为，但展示了 Rust 类型系统中一种精巧的「拥有值却行为如引用」的实现思路。

## 3. Aho-Corasick 多模式串匹配算法

- 原始链接: <https://compiler.club/aho-corasick/>
- 英文标题: Aho-Corasick Algorithm

本文介绍 Aho-Corasick 算法，该算法基于前缀树（Trie）构建自动机，用于在输入序列中同时匹配多个模式串。文章首先说明 Trie 通过共享公共前缀减少冗余，随后重点阐述两种关键链接：后缀链接与输出链接。后缀链接在转移失败时将状态回退到当前节点字符串的最长后缀所对应的节点（该后缀须为某模式的前缀），从而避免从头重新匹配；其构建采用广度优先遍历，逐层从父节点的后缀链接向上查找。输出链接则处理模式间的包含关系——当某模式结尾节点的后缀本身也是另一模式时，需同时输出。文章给出了完整的伪代码，并说明最终通过一次 BFS 将所有转移静态解析为确定性有限自动机（DFA），使每次转移为常数时间。文中以「suit」「item」「cadence」「facade」「spin」「pin」「in」「he」「she」「her」等多组示例直观展示了链接构建与 DFA 生成的过程，并提供了在线演示工具。

## 4. 为单页应用编写自动化测试的实践经验

- 原始链接: <https://reecoute.fr/tech_blog/2026-09-28_my-experience-writing-automated-tests-for-a-spa>
- 英文标题: My experience writing automated tests for a SPA

作者分享了为音频播放器SPA应用Réécoute构建Playwright测试套件的完整经验。测试在真实浏览器中运行，涵盖约20个文件、每个1至4个用例，偏好编写覆盖完整用户旅程的长测试而非细粒度小测试。数据隔离方面，作者选择让每个测试自行创建数据、不依赖也不清理已有数据，数据自然累积，适用于非公开应用。外部服务（S3、Stripe、Twilio等）使用全局mock，复杂场景通过测试专用HTTP参数启用替代代码路径。速度上，启用Playwright全并行并仅跑Chromium，整套测试在M3 MacBook Air上约20秒完成。可靠性是浏览器测试的主要挑战，作者通过设置CI重试2次缓解偶发失败，并解决了SSR与客户端水合（hydration）冲突问题：输入框默认禁用，React组件就绪后再启用，Playwright会等待启用后再填充。CI中利用Playwright自带的HTML报告（含截图、网络日志、控制台输出）便于排查。此外还介绍了用Playwright的request()写API测试、通过测试专用路由获取邮件内容、模拟鼠标拖拽等技巧。作者坦言尚未测量覆盖率，也希望将重试次数降为零，但暂未投入精力。

## 5. Shell 与邮件：多 Agent 协作的异步界面

- 原始链接: <https://www.machtiani.chat/blogs/the-shell>
- 英文标题: The Shell & Email

David Szigeti 在本文中探讨了 Shell/终端与邮件在 AI Agent 工作流中的角色。他认为，Shell 赋予 LLM 最大的实用性，终端是操作 Agent 最贴近底层的方式，使开发者无需依赖某一家公司的 iPhone 应用或云端 Web 应用即可高效使用计算机。然而，当需要同时管理多个 Agent 时，终端体验会令人眩晕，因为人们往往需要异步、分布式地工作：暂停一个任务、去做别的事、稍后再回来检查进度。邮件天然解决了这一异步协作问题——每个邮件线程即一个会话，支持群聊，且不绑定特定平台，在弱网络环境下依然可用。基于这一思路，作者将邮件作为与多个 Agent 及人类协作者共同工作的界面。他一年前发布了项目 Machtiani，近期加入了「迭代指令循环」机制：将 Agent 的回复反馈为下一步指令，由一个轻量级 Supervisor 驱动，该 Supervisor 可调用电脑上已安装的任何 Agent。项目已在 GitHub 开源。文章核心观点是：LLM 理解 Shell 与邮件的范式，正如它们理解人类异步协作的方式，邮件是同时驾驭多 Agent 时最自然、最自由的交互层。

## 9. 从普通应用获取 OnePlus 15 的 root 权限：两个漏洞的链式利用

- 原始链接: <https://blog.nns.ee/2026/09/24/oneplus-root/>
- 英文标题: Getting root on OnePlus 15 from an untrusted app

作者发现 OxygenOS 16 中存在两个可链式利用的漏洞，使任意普通安装 APK（无需特殊权限）从 untrusted_app 域提升至 uid 0 并获得全部 Linux capabilities。第一个漏洞位于 OxygenOS 自有的 AtlasService：其 setEvent 方法无调用者权限校验，特定事件名会触发 audiodumpinfo 服务，该服务将用户可控的 property 值未经转义直接传入 system() 调用，形成命令注入，使攻击者以 dumpstate 域（uid 0）执行命令。第二个漏洞位于 vendor HAL olc2 的 doShell 方法：仅校验 getCallingUid()==0 即 fork/exec 任意 shell 命令，子进程落入 vendor_qti_init_shell 域，拥有 CapBnd 全部能力。两者衔接后，攻击路径为：untrusted_app 调用 AtlasService 注入命令→以 dumpstate 域运行→调用 olc2 doShell→获得不受限 shell。PoC 为普通 APK，利用 app_process 加载 dex 完成 binder 调用。OnePlus 确认漏洞影响多款 OnePlus 与 OPPO 设备，截至 2026 年 9 月 151 款已修复、18 款待发布，OnePlus 15 修复版本为 16.0.10.500(EX01)。作者于 2026 年 4 月报告，经历约五个月协调后于 9 月公开。

## 10. 没有AI本身即是一项功能：LibreOffice 26.8的立场与原则

- 原始链接: <https://blog.documentfoundation.org/blog/2026/09/03/yes-no-ai-is-now-a-feature/>
- 英文标题: Yes, no AI is now a feature

LibreOffice 26.8发布后，有用户调侃「没有AI算不算一个功能？」项目方借此回应，阐明其不将AI纳入默认配置的原因。LibreOffice并非拒绝AI，而是为服务学校、医院、公共机构等数千万用户，提出六项硬性条件：推理位置须由用户自选；文档内容未经授权不得离开本机；不收集任何遥测数据；不绑定单一供应商API；生成内容必须为ODF开放格式；AI功能须完全可选、可卸载、对管理员部署无强制影响。项目方评估认为，当前没有任何集成方案能同时满足上述全部要求，因此默认安装中不含任何AI功能。与此同时，用户可通过第三方扩展（如连接Ollama、LM Studio等本地模型）自行启用AI能力，这些扩展由社区维护，与核心项目解耦。文章还指出，商业办公套件将AI与订阅涨价、数据锁定绑定，而The Document Foundation作为非营利组织，无季度业绩压力，可从容评估技术是否真正惠及用户。项目方强调，若未来本地推理与开放模型发展能满足全部条件，将认真纳入评估；在此之前，默认安装保持无AI，扩展机制为有需求的用户提供选择。

## 11. 两种SQL查询构建器

- 原始链接: <https://mechanicalrabbit.github.io/FunSQL.jl/stable/two-kinds-of-sql-query-builders/#Two-Kinds-of-SQL-Query-Builders>
- 英文标题: Two Kinds of SQL Query Builders

文章揭示SQL查询构建器存在两种本质不同的类型。尽管FunSQL、Active Record、Laravel、EF/LINQ、dbplyr等库的接口几乎一致，内部机制却截然不同。语法导向构建器（Active Record、Laravel）采用builder模式，将管道节点填入SQL语法树的固定槽位，节点顺序不影响结果，实现简单且能覆盖全部SQL特性，但继承了SQL刚性子句顺序等缺陷，难以组装复杂数据处理管道。数据导向构建器（FunSQL、EF/LINQ、dbplyr）将管道视为数据处理流程，节点顺序改变会改变语义，更直观易用，但需通过SQL下推将管道转换为SQL。EF/LINQ和dbplyr分别改编自LINQ和dplyr，受原框架能力限制，无法覆盖SQL自1974年积累的全部特性，如相关子查询、递归查询、窗口函数等。FunSQL是唯一从零设计、完整匹配SQL表达力的数据导向构建器，支持相关子查询、lateral join、窗口函数、递归查询等，且每个节点均有明确的数据处理语义，理论上可发展为完整查询框架，为用更连贯、更富表达力的语言替代SQL提供了可能。

本文系统介绍了 Unix/Linux/POSIX 系统的文件与目录权限机制。每个文件归属一个用户和一个组，访问者被归为所有者、组内成员、其他用户三类，每类可授予读、写、执行三种权限，共 12 个权限位（4096 种组合），信息存于 inode 中。权限不继承，目录权限不会传递给其内文件。权限控制的是系统调用（如 read()、write()、exec()）而非具体命令。目录权限有特殊含义：读权限用于列出文件名，写权限用于增删改名文件，执行权限（即搜索权限）用于访问文件 inode，因此访问任何文件需对其所有祖先目录具备搜索权限。文章还详述了 SUID、SGID 和 sticky 三个特殊属性位：SUID 使进程以文件所有者身份运行，SGID 以文件组身份运行，二者在脚本上存在严重安全隐患；sticky 位在现代系统中已无实际效果。脚本文件需同时具备读和执行权限才能运行，而编译程序仅需执行权限。

## 15. Lisp 为何难以阅读：括号位置与认知科学

- 原始链接: <https://paultm.nl/paren-thesis>

## 16. 文本到猫叫声模型：用表达范围图探索AI生成猫鸣的多样性

- 原始链接: <https://www.kmjn.org/notes/text_to_meowdio_models.html>
- 英文标题: Text-to-meowdio models

本文以猫叫声为切入点，将程序化内容生成（PCG）社区中的「表达范围图」方法应用于文本到音频模型，分析其生成多样性。作者用三个模型（Stable Audio Open 1.0、EzAudio、TangoFlux）配合七个提示词，共生成2100段猫鸣音频，并以音色、音高、响度三项声学特征经PCA降维后在二维平面上可视化。关键发现包括：EzAudio因训练数据中猫常无声出现，在「cat」或「sound of cat」等提示下频繁输出静音或背景噪音，但明确加入「meowing」后生成率显著提升；TangoFlux和Stable Audio Open对三种提示均能产出猫叫，但指定动作后音色范围明显收窄。在描述性修饰词实验中，各模型对「tiny kitten」「angry cat」「plaintive」「purring」等修饰的反应差异显著：TangoFlux在音色空间上质心偏移最大，而音高空间上各模型方向较为一致。对「plaintive」的跨模型比较显示，该词在音高空间使各模型输出趋同，在音色空间反而更分散，说明其并无统一的声学含义。作者强调，声学特征分布不能替代听感质量评估，嘶嘶声常退化为磁带噪声，呼噜声也常失真，表达范围图的价值在于直观揭示生成空间的切片结构，而非替代FAD、CLAP等指标。

## 18. Deser：重新思考 Rust 序列化

- 原始链接: <https://lucumr.pocoo.org/2026/9/29/deser/>
- 英文标题: Deser: Rethinking Rust Serialization

Armin Ronacher 在博客中介绍了他于 2022 年启动、近日重新推进的 Rust 序列化库 Deser。文章首先列举了 Serde 三个由设计导致的棘手问题：内部标签枚举与 serde_json 的 arbitrary_precision 特性冲突、flatten 后整数键退化为字符串、以及自定义适配器无法组合到 Option 或 Vec 内部。这些问题源于 Serde 的三大设计决策——一套 trait 服务所有格式、固定数据模型在缓冲时丢失信息、以及递归调用栈处理嵌套——且受稳定性保证约束难以修复。Deser 的核心思路是将控制权反转：由格式向 sink 推送事件，嵌套状态全部置于堆上的 arena，从而消除栈溢出、支持可挂起的流式解析与跨线程使用，并提供可扩展数据模型（扩展值替代魔法键）、无损缓冲、Layers 中间件、原生 flatten、可组合适配器、带路径的精确报错、XML 命名空间匹配及格式特定扩展类型（如 TOML 日期）等能力。代价方面，Deser 的 JSON 读取平均慢约 10%、写入基本持平，二进制体积约为 Serde 的 2.3 倍，内部依赖 unsafe，且最大障碍在于它并非 Serde，无法借助孤儿规则融入现有生态。作者认为 Deser 已具备作为「即插即用」替代品的潜力，至少值得社区关注其设计思路。

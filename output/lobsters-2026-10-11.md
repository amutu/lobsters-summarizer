## 1. 标准C中无法可移植地检测字符串转浮点数的转换错误

- 原始链接: <https://sebsite.pw/w/20261009-strtod.html>
- 英文标题: oh, apparently it's not possible to portably check for string-to-float conversion errors in standard c

文章指出，标准C中字符串转浮点数函数（strtod、strtof等）的错误检测存在严重的可移植性问题。这些函数虽不在math.h中，却受math_errhandling宏控制：若该宏未声明支持MATH_ERRNO（如musl），溢出或下溢时不会设置errno；下溢时甚至不要求报告任何错误。作者给出了依据math_errhandling条件判断errno或浮点异常的可移植检测方案，但下溢检测仍无法保证。POSIX规范则强制要求始终设置errno，与标准C存在冲突，且man page未注明这是扩展。对于无效输入，标准C仅通过endptr参数（endptr等于nptr）判断，不设置errno；POSIX允许设置errno为EINVAL，但glibc不设置、musl设置，行为不一致且man page未记录。文章最后逐一列举了溢出、下溢、无效输入三种情况各自的「正确」检测方式，结论是标准C在此处的措辞需要更清晰的规范，而POSIX与标准C的兼容性也存疑。

## 2. AI 远非「不可避免」

- 原始链接: <https://deadsimpletech.com/blog/llms-arent-inevitable>
- 英文标题: There's little that's "inevitable" about AI

作者 Iris Meredith 反驳「AI 是不可避免的，我们只能接受」这一流行论调，认为这不过是一种思想终止性陈词。她提出判定一项技术是否「不可避免」的四条标准：能完成与替代方案不相上下的任务；该任务社会价值高且劳动力稀缺；技术对替代方案具有压倒性优势而非适度改进；不使用方无法通过行为调整来中和其影响。以火炮为例，它满足全部条件，故属真正不可避免；磁罗盘虽有用但可被规避，故不算。将 LLM 逐条对照：它仅勉强通过第一条（多数人类知识工作质量平庸，LLM 可替代），第二条结果混合（只能替代最低价值环节），第三、四条明确不通过——目前没有任何公司因 LLM 实现五到十倍产能碾压，且社会对 LLM 产出的强烈抵制构成有效中和手段。作者进一步以化学武器类比：看似致命，但在现代机动战争中反而无用，防护成本极低，只有弱者对弱者时才有意义。LLM 处境类似——二流软件公司可能长期依赖它追求产量，但真正严肃的从业者几乎无需使用。结论是，LLM 属于「偶然性」技术而非「不可避免」技术，其广泛采用并非历史必然，而是取决于具体社会与文化语境。

## 3. Chrome 154 让 iframe 终于能自动适配内容高度

- 原始链接: <https://alfy.blog/2026/10/09/iframe-that-finally-fit-their-content.html>
- 英文标题: Iframes that finally fit their content

Chrome 154 新增 CSS 属性 frame-sizing: content-height，使 iframe 可一行代码自动匹配内容高度，无需 postMessage 通信或 resize 脚本。作者长期构建结账页面，支付表单嵌在第三方 iframe 中，固定高度要么留白要么出现嵌套滚动条，旧方案需父子页面通过 JavaScript 互相测量与传递高度，存在宽度变化、字体图片延迟加载、动态内容、多 iframe 区分、双方必须配合等痛点。新方案中，父页面只需设置 frame-sizing，iframe 内通过 meta 标签「responsive-embedded-sizing」声明允许的来源域名，内容变化时调用 window.requestResize() 即可。该特性还支持 content-width、content-inline-size 等变体，可与 max-height 组合。文章指出最关键的约束未消失：嵌入方必须主动配合，支付网关、评论服务等第三方需自行添加 meta 标签并调用 requestResize，否则宿主页面无法单方面启用。适用场景包括支付表单、第三方组件、多步问卷及 srcdoc 自渲染内容。上线前需注意：目前仅 Chromium 内核支持，应保留固定高度作为降级；iframe 加载后撑开可能导致布局偏移，建议设 min-height；allow-origins 不应设为通配符，以免泄露登录状态等敏感信息。浏览器端已就绪，真正落地取决于嵌入页面的构建者是否跟进。

## 5. 火星探路者号优先级反转故障：事件始末

- 原始链接: <https://nerdyelectronics.com/mars-pathfinder-what-really-happened/>
- 英文标题: Mars Pathfinder Priority Inversion Bug: What Really Happened

1997年7月，NASA火星探路者号着陆火星后数天，系统因反复完全重启而中断数据传输。根本原因是VxWorks实时操作系统中的优先级反转：低优先级的气象数据采集任务持有共享信号量，高优先级的总线管理任务需等待该信号量，但一个中等优先级的通信任务恰好阻塞了低优先级任务，使高优先级任务被间接延迟。看门狗定时器检测到总线管理任务超时未执行，遂触发系统重置。工程师在实验室复现环境中定位到该问题，解决方案是启用信号量的优先级继承机制——持有信号量的低优先级任务在等待者请求时继承高优先级，从而可抢占中等优先级任务。修复方式极为巧妙：利用VxWorks内置的C语言解释器，向航天器上传一段简短C代码，将相关全局标志从FALSE改为TRUE，即消除了重启。文章总结了三点教训：一是必须依赖详细的系统行为追踪而非黑盒诊断；二是系统内嵌的调试与远程修改能力不可或缺；三是在测试阶段就应验证优先级继承配置，即便带来少量性能开销也值得。此外，该问题早在1990年Sha、Rajkumar和Lehoczky的论文中已被提出并给出方案，但工程实践中仍被忽视。

## 6. 为何「外部化」的循环 trait 实现证明行不通

- 原始链接: <https://smallcultfollowing.com/babysteps/blog/2026/10/10/modular-vs-external-proofs/>
- 英文标题: Why 'externalized' proofs of cyclic trait impls does not work

本文是「循环 trait 实现」系列的一部分，探讨 Rust 中处理 supertrait 义务的两种证明策略：模块化证明与外部证明。模块化证明要求 impl 本身证明所有 supertrait 成立，调用方可直接信任该 impl，类似函数契约——调用者无需验证被调函数体是否匹配签名。外部证明则相反：impl 仅建立「浅层」实现（Shallow），调用者还需额外证明 supertrait 成立，impl 本身合法但不可直接使用。作者指出外部证明虽能避免循环依赖问题，但与 Rust 的 unsafe trait 机制根本矛盾：unsafe impl 要求 impl 自身证明 unsafe 条件成立，调用者信任 impl；若同时要求调用者证明 supertrait，则 impl 对 unsafe 条件可被信任、对 supertrait 却不可被信任，逻辑不一致。以 unsafe trait NullWord 为例，若 impl 无法证明 supertrait，则无法保证 unsafe 语义的健全性。作者最终得出结论：外部证明与 Rust 的设计不兼容，模块化证明是唯一可行路径，并预告后续将讨论共归纳模块化证明的具体方案。

## 8. culpert：面向 Rust 的 Span 感知堆分析器与回归检测工具

- 原始链接: <https://github.com/rupert648/culpert>
- 英文标题: culpert - rust heap profiling with span awareness and regression tooling

culpert 是一个仍处于实验阶段的 Rust 采样式堆分配分析器，核心能力是将每次被采样的分配归因到其所在的 span，并导出 pprof 兼容的 .pb.gz 文件，从而兼容 pprof、Speedscope、Pyroscope 等现有工具生态。它提供三种集成路径：对接 Cloudflare Foundations（零改动，复用已有 #[span_fn] 注解）、对接 tracing crate（通过 Layer 组合，复用 #[tracing::instrument] 注解）、以及完全独立的 #[culpert::span_fn] 宏（无需外部追踪器）。采样采用几何采样配合 Bernstein 校正，在保持低开销的同时给出无偏的字节分配估计。配套 CLI 提供 report（树形/扁平报告、按 span 下钻、未归因桶分析）和 diff（按绝对字节与百分比阈值检测回归，支持 Markdown 输出直入 GitHub Step Summary）两个子命令。CI 场景下，可借助 culpert-archive（一个 Cloudflare Worker）按 commit SHA 存储历史 profile，实现跨构建基线对比；仓库还附带可复用的 composite action 一键完成拉取基线、生成 diff、上传新基线的完整流程。文章指出 culpert 已在 Cloudflare 内部捕获过包括内存泄漏在内的多个真实分配回归。项目以 MIT 或 Apache-2.0 双许可发布。

## 11. Android中一键MMI代码执行漏洞

- 原始链接: <https://karansaini.com/mmi-android/>
- 英文标题: 1-click MMI execution in Android

文章披露了Android平台中利用CALL_PHONE权限实现一键MMI/USSD代码执行的攻击链。作者指出，持有CALL_PHONE权限的应用可静默执行任意USSD/MMI代码（如呼叫转移「**21*号码#」），但权限描述未提及此能力，执行时亦无用户确认，且MMI执行不写入通话记录。攻击前提为应用同时持有CALL_PHONE权限并暴露浏览器可达的自动拨号deeplink。作者扫描88个拨号及VoIP应用，发现54个存在浏览器可达拨号入口。以安装量超500万的ACR Phone为例，通过Chrome的intent: URI语法触发CALL_BUTTON action，单次点击即可注册无条件呼叫转移，将受害者来电（含语音OTP、银行验证回拨）转至攻击者控制号码。由于转移注册存储在运营商侧，重启、卸载应用或恢复出厂设置均无法取消。此外，Android 17将Telecom移入mainline模块后，调用方身份在传递中丢失，使仅持有CALL_PHONE的普通应用无需漏洞deeplink即可通过ACTION_CALL执行MMI。作者于2026年9月向Google报告，但被标记为Won't Fix，Google认为属第三方应用deeplink处理问题而非平台漏洞。作者建议将MMI执行权限与CALL_PHONE解耦，或在非默认拨号应用触发时添加确认提示。

## 12. 将 Go 的 defer 语句引入 TypeScript 编译器的尝试与反思

- 原始链接: <https://healeycodes.com/adding-defer-to-the-typescript-compiler>
- 英文标题: Adding Go's defer to the TypeScript Compiler

作者尝试在 TypeScript 编译器（tsc）中实现 Go 语言的 defer 语句，以解决资源获取与释放配对的代码可读性问题。实现思路是利用 tsc 已有的 AST 到 AST 转换机制，将 defer 语句改写为 try/finally 加闭包栈的形式：每个包含 defer 的函数维护一个栈，执行到 defer 时压入一个捕获了调用者、接收者和参数值的闭包，函数退出时按 LIFO 顺序依次执行清理。语义上，注册时机为执行到达 defer 语句时（而非函数入口），循环中每轮注册一次；不支持 defer await，直接报错。错误处理方面，所有清理调用均会执行，原始错误被保留，多个异常通过 AggregateError 聚合。然而，作者在实现过程中逐渐意识到 defer 并不适合 TypeScript：Go 中错误是值，defer 返回的错误无需特殊处理；而 JavaScript 中异常是控制流，一旦清理代码可能抛出或拒绝，就必须定义聚合策略、优先级和异步执行顺序等 Go 中不存在的规则。文章最终推荐 ECMAScript 显式资源管理提案（using 语句配合 Disposable 接口）作为更自然的替代方案，并指出理想语法 using await acquirePermit(sema) 尚未被支持。作者的 MVP 实现已发布在其 TypeScript 分支上。

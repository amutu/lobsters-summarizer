## 4. mold：一种大规模并行链接器

- 原始链接: <https://arxiv.org/abs/2608.23228>
- 英文标题: mold: A Massively Parallel Linker

本文介绍了mold，一款面向Unix/Linux系统的大规模并行链接器，由Rui Ueyama提出，已被ASPLOS 2027接收。链接是将编译后的目标文件合并为可执行文件或共享库的关键步骤，长期以来是大C++程序「编辑-编译-调试」循环中的显著瓶颈。现有链接器（如GNU ld、lld）仅利用有限并行度，链接时大量CPU核心处于闲置状态。mold的核心思路是在整个链接流水线中系统性地引入数据并行：作者首先剖析了阻碍现有链接器扩展的架构约束，尤其是符号解析与归档处理之间的耦合纠缠，随后通过全新设计将二者解耦，从而突破扩展性瓶颈。在大型真实程序上，mold可在数秒内（通常不到一秒）完成多GB调试二进制的链接，比当前最先进的lld快2.4至16.1倍，比传统GNU ld快最高达112倍。消融实验进一步表明，性能提升并非来自某一项单一优化，而是将各阶段全部并行化后产生的累积效果。该工作为构建工具链的并行化设计提供了系统性参考，对缩短大型C++项目的迭代周期具有实际意义。

## 6. 从 API 到 Hash Trie：深入理解 Go 的 sync.Map

- 原始链接: <https://victoriametrics.com/blog/go-sync-map-hash-trie/>
- 英文标题: Understanding Go's sync.Map from API to Hash Trie

本文由 VictoriaMetrics 团队撰写，系统剖析了 Go 标准库 sync.Map 从公开 API 到内部数据结构的完整实现。文章首先梳理了 sync.Map 的六个核心方法（Load、Store、Delete、LoadOrStore、CompareAndSwap、Range），指出其设计目标是针对「读多写少」且 key 集合相对稳定的场景提供比「Mutex + map」更低的锁竞争。随后深入内部结构：read 字段以 atomic.Value 持有 readOnly 结构体（内含 amap 普通 map 与 readOnly 标志位），dirty 为普通 map[interface{}]entry，配合 misses 计数器触发 read→dirty 的惰性拷贝；entry 内部用 atomic.Pointer 与 expunged 标志实现无锁删除。文章重点讲解了 Hash Trie 这一关键优化：当 key 的哈希值发生冲突时，sync.Map 不再简单依赖底层 map 的链式探测，而是借助 trie 结构将冲突 key 分层存储，从而在高基数、高冲突场景下避免性能退化。此外，文章还讨论了 sync.Map 与「Mutex + 普通 map」在 benchmark 中的对比，给出选型建议：若 key 集合频繁变化或写比例高，仍应使用 Mutex + map；若读远多于写且 key 基本不变，sync.Map 可显著降低锁开销。全文配有源码级注释与图示，适合希望理解 Go 并发容器底层机制的开发者阅读。

## 7. Google 为何将数十亿行代码存放在单一仓库中

- 原始链接: <https://dl.acm.org/doi/fullHtml/10.1145/2854146>
- 英文标题: Why Google stores billions of lines of code in a single repository (2016)

本文是 Google 工程团队于 2016 年发表的技术文章，系统介绍了 Google 将全部产品代码（涵盖 Android、Chrome、Gmail、Search 等）统一存放在一个单一大型代码仓库（monorepo）中的架构设计与工程实践。仓库规模达数十亿行代码、数万个项目，由数万名工程师共同维护。文章指出，Google 当时采用 Perforce 作为版本控制系统，并配合自研的 Bazel 构建工具（后开源）实现高效构建。核心技术亮点包括：稀疏检出（sparse checkout），使开发者仅拉取与自身工作相关的子集，避免下载整个仓库；基于路径的细粒度权限模型，保障各团队代码的安全隔离；分布式索引与搜索基础设施，支撑在海量代码中快速定位。文章总结了 monorepo 的主要优势：跨项目代码复用门槛低、全局重构与依赖变更可一次完成、构建与测试环境高度统一、减少版本碎片化。同时也坦承其挑战：对基础设施要求极高，初始配置复杂，权限与审计体系庞大，对中小团队并不适用。文章最后强调，monorepo 并非唯一正确选择，但其背后的理念——统一视图、降低集成成本、促进代码共享——对各类规模的团队均有参考价值。

## 11. ReaderT 设计模式

- 原始链接: <https://academy.fpblock.com/blog/2017/06/readert-design-pattern/>
- 英文标题: The ReaderT Design Pattern (2017)

Michael Snoyman 于2017年提出一种 Haskell 应用架构模式，核心是将应用代码置于 ReaderT Env IO 中。Env 为集中存放运行时配置、日志函数、数据库连接等全局依赖的数据类型；若需可变状态，则用 IORef 或 TVar 放入 Env。作者反对条件编译和 unsafePerformIO 等全局变量方案，认为它们带来构建组合爆炸和非确定性。他同时论证了为何避免 WriterT、StateT 和 ExceptT：前者在异常时丢失状态、并发下语义模糊、存在空间泄漏；后者与 IO 的异常契约冲突，无法真正文档化可能的异常。ReaderT 本身无可变状态，天然支持并发安全，且单层 transformer 更利于 GHC 优化。为降低耦合，作者推荐用 Has 类型类（或 lens）将 Env 字段拆分为独立约束，使函数签名精确表达依赖，便于单元测试。该模式是 Yesod 框架 Handler 类型和 Stack 代码库的设计基础，但作者强调这只是个人及 FP Complete 的最佳实践建议，并非 Haskell 社区共识。

## 12. 不用 JavaScript 构建 textlog：让 React 留在服务端

- 原始链接: <https://gist.github.com/stagas/09ad937b493bf8cd3285917279de2488>
- 英文标题: Building textlog without JavaScript

作者介绍其项目 textlog 的核心约束：浏览器端零 JavaScript。textlog 本质仍是 React 应用，但 React 仅运行于服务端完成渲染，浏览器只接收最终 HTML，无 hydration、无客户端运行时。作者发现，放弃 JS 后必须重新审视 HTML 本身的能力：链接导航、表单提交、URL 承载状态、radio 按钮、details 标签、CSS 状态响应等，足以覆盖投票、筛选、分页、关注、编辑等常见交互。关键思维转变在于，不再问「如何不用 JS 复刻 SPA 交互」，而是问「这个交互的网页版本长什么样」——提交表单、跳转、重新渲染即可。好处包括：URL 可复制、可收藏、可在新标签打开；服务端逻辑直白，无需通过 API 向浏览器端重建状态；无 bundle 下载与解析，页面体积极小，性能问题自然消解。当然存在边界，如推送通知必须依赖 JS 注册 service worker，作者的做法是仅在真正需要的页面加载 JS，而非将「零 JS」教条化。意外收获是技术约束塑造了产品气质：textlog 定位为安静的纯文本空间，无点赞、无即时通知，每增加一个交互都要多问一句「是否真的需要」。作者总结，我们或许太急于在浏览器中塞入应用运行时，而大量场景仍是阅读、点击链接、填表单、改服务端状态，HTML 本就擅长这些。

## 13. 标签名里藏着 JavaScript：利用 HTML 标签名特性实现 XSS 与 WAF 绕过

- 原始链接: <https://portswigger.net/research/whats-in-a-tag-name-javascript-apparently>
- 英文标题: What's in a tag name? JavaScript, apparently

研究员 Gareth Heyes 发现，HTML 标签名虽会被浏览器统一转为大写，但元素的 localName 属性始终保留小写原始值。他利用这一差异，将 JavaScript 代码（如 alert(1)）直接写入标签名，再通过 tabindex、autofocus 与 onfocus 事件链，将 localName 的内容经 new Function() 或 eval() 执行，从而在任意浏览器中触发 XSS。文章进一步展示了多种绕过技巧：用大写形式（如 JAVASCRIPT:ALERT(1)）绕过关键字检测；利用换行符和段落分隔符不被转换的特性构造多行 payload；将开括号「<」纳入标签名拼接出完整 HTML 片段；借助 part 属性将空格分隔值转为数组，提取 onfocus(event) 中的 event 部分并覆写为 Function 构造器；用 classList 替代 part 实现类似效果；用 contenteditable 替代 tabindex；以及 getAttributeNode、setHTMLUnsafe 等替代路径。作者还借助 AI 工具 Sol 5.6 发现了更多变体。核心结论是：浏览器对标签名及 localName、part、classList 等「看似无害」属性的处理远比预期宽松，攻击者可借此隐藏 payload、绕过黑名单与 WAF 签名，对前端安全防御构成新威胁。

## 16. WebSockets 与 SSE 之争：核心在于事件顺序与正确性

- 原始链接: <https://dashbit.co/blog/websockets-vs-sse>
- 英文标题: WebSockets vs. SSE should be about ordering and correctness

Elixir/Phoenix 作者 José Valim 针对「大多数应用应使用 SSE+Fetch 而非 WebSocket」的观点进行反驳。他指出，Fetch 虽复用 TCP 连接，但每次请求仍需解密会话、查询数据库，而 WebSocket 一次认证后数据常驻内存；Phoenix LiveView 还通过发送 diff 而非完整 HTML 大幅缩减载荷。但作者认为这些只是次要优势，真正关键的问题是事件顺序与正确性。他以文章标签的并发增删为例说明：当数据经由 SSE 和 Fetch 两条独立流传递时，网络、GC、代理等因素可能导致事件乱序，使 UI 短暂显示错误数据且无法自愈，这并非「最终一致性」所能覆盖。根本原因在于多流并发缺乏因果排序。WebSocket 的双向特性天然适合在同一连接上处理读写，保证用户操作与响应的因果顺序；而 SSE+Fetch 方案要么引入队列增加延迟，要么让客户端轮询刷新增加服务器负载，要么在客户端做复杂排序（需借助 Electric 等专门平台）。作者结论：选择传输协议时，首要考量应是如何保证事件按正确顺序送达、避免用户看到过期或错误数据；WebSocket 提供了最简洁的因果排序基础，而 Phoenix 借助 Elixir 与分布式 Erlang 还能进一步简化架构、降低延迟。

## 19. 代码检查器并发自动修复引发的冲突问题

- 原始链接: <https://jfmengels.net/concurrent-linter-fixes/>
- 英文标题: Problem with concurrent linter fixes

本文以 ESLint 为例，讨论了代码检查器（linter）同时应用多条自动修复规则时可能产生错误代码的问题。作者用一个简单示例说明：若一条规则将手动计算平均值替换为调用已有的 average 函数，另一条规则同时删除「未使用」的 average 函数，两条修复各自正确，但并发应用后代码将引用一个已被删除的函数，导致编译失败。作者指出，ESLint 的策略是批量收集所有修复、一次性应用后再重新分析，而作者自研的 Elm 语言检查器 elm-review 则采用更保守的策略：每次仅应用一条修复，随后立即重新分析代码，循环直到无修复可用。后者虽增加分析次数、带来性能开销，但能保证每一步修复都基于当前代码状态，避免跨规则冲突。作者认为，当 linter 未来支持更激进的自动修复（如自动删除未使用变量、重命名、移动语句等）时，此类冲突将成为阻碍。对于支持自定义规则的工具，由于维护者无法预知所有规则间的交互，逐条修复是更稳妥的方案；而不支持自定义规则的工具则可通过优先级排序等机制提前规避冲突。作者总结称，逐条修复虽慢，但让规则开发者无需担心自身修复与其他规则产生语义冲突，显著降低了调试成本。

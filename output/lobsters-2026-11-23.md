## 1. 程序员对 ATProto 的常见误解

- 原始链接: <https://reiver.link/atproto/falsehoods-programmers-believe/>
- 英文标题: Falsehoods Programmers Believe About ATProto

本文延续「Falsehoods Programmers Believe」系列，系统列举了开发者对 ATProto（Bluesky 底层去中心化协议）的常见错误假设，每条均引用规范或实际服务器验证。内容涵盖五大方面：句柄方面，句柄可随时变更、可指向任意域名、不区分大小写，真正永久的标识是 DID；DID 方面，除 did:plc 外还支持 did:web，DID 文档内容（句柄、PDS、签名密钥）可被更新，且存在 72 小时历史重写窗口；PDS 方面，单台 PDS 可托管多用户，时间线由 AppView 而非 PDS 构建，自托管 PDS 无需索引全网；记录方面，仓库可存储任意 lexicon 类型记录，记录键有 tid、literal、nsid、any 四种形式，TID 不可作可信时间戳，createdAt 仅为客户端声明值；数据模型方面，ATProto JSON 禁止浮点数、使用 $link 和 $bytes 等特殊语法，需经 DRISL-CBOR 编码后哈希签名。文章核心建议：以 DID 为唯一键，定期重新解析句柄与 DID 文档，妥善处理无句柄及无效句柄的边界情况。

## 2. GitHub Actions 接受非法 YAML 语法

- 原始链接: <https://yossarian.net/til/post/github-actions-accepts-invalid-yaml/>
- 英文标题: GitHub Actions accepts invalid YAML

作者发现 GitHub Actions 会接受若干不符合 YAML 1.2.2 规范的语法，导致使用标准 YAML 解析器无法解析部分真实的 workflow 定义。具体案例中，一个 workflow 步骤的 with 字段下使用了单引号包裹的多行 flow-style 字符串（JSON 内容），但右花括号 } 的缩进未比父级 block 映射多出一个空格，违反了 § 8.2.3 关于 flow 节点缩进的规定。正确写法仅需将 } 多缩进一个空格，差异极小却使整段 YAML 非法。作者此前误以为是 tree-sitter-yaml 解析器的问题并提交了修复 PR，后意识到根源在 GitHub Actions 本身，遂撤销该修复。GitHub Actions 底层疑似使用 YamlDotNet 解析器，但即便升级到最新版 18.1.0 该缺陷仍未修复。作者推测 2020 年 YamlDotNet 的一个补丁仅修复了双引号形式，而 YAML 官方测试套件也只覆盖了双引号场景，尽管规范对单、双引号均适用。此问题与 zizmor 项目 issue #1116 相关，已困扰作者一年半。文章核心结论是：GitHub Actions 的 YAML 解析存在规范偏差，工具链开发者需对此类「宽松解析」做兼容处理。

## 3. 在知合计算 A210 RISC-V 开发板上引导 NixOS

- 原始链接: <https://feyor.sh/blog/nixos-bringup-on-an-alibaba-riscv-board/>
- 英文标题: NixOS bring-up on an Alibaba RISC-V board

作者本欲购买阿里巴巴 Versal 开发板，却意外收到一块知合计算 A210 RISC-V SoC 板（8 核 1.9 GHz），遂将其作为 NixOS 构建服务器，借此学习 RISC-V 支持现状与 Linux 引导流程。借助 Nix 的交叉编译能力，作者从 x86_64 编译了上千个 RISC-V 包，仅遇 rust-bindgen 和 ministream 两个非 RISC-V 特有问题；编译 Clang、GFortran 时出现单进程超 9 GB 内存占用，通过降低并行度绕过。启动链为 U-Boot FSBL→OpenSBI→U-Boot SSBL→Linux→NixOS，期间排除了 macOS 无法识别 Fastboot 设备、串口 vRef 悬空、OpenSBI 因 mstatus 向量上下文未置位而触发非法指令异常、以及未用时钟被禁用导致 initrd 中断等问题。GPU 方面，厂商仅提供闭源内核模块，作者将上游 Linux 6.18 的 PowerVR 驱动移植至 6.6 内核，借助 Ghidra MCP 服务器与 Codex 在数分钟内定位差异，最终成功运行 Vulkan 与 OpenGL ES，vkmark 得分 244。文章还讨论了内核模块 ABI 兼容性难题，并感叹 NixOS 在 SoC 厂商中仍被忽视，期待其未来取代 Yocto/Buildroot。

## 4. Gliver：补全 Guix 桌面的最后一块拼图

- 原始链接: <https://dustycloud.org/blog/gliver-completes-the-guix-desktop/>
- 英文标题: Gliver completes the Guix desktop

Christine Lemmer-Webber 撰文介绍 Gliver——一款基于 Guile Scheme 的 Wayland 平铺窗口管理器，风格承袭 StumpWM 与 Emacs。Gliver 尚未正式纳入 Guix，但已有合并请求在等待其 0.0.5 版本发布。作者强调 Gliver 的核心价值在于「可理解性」与「参与性」：代码库鼓励用户探索，默认开启 Unix 域套接字 REPL，可借助 Geiser 实时查看命令定义、修改配置并即时生效，无需重启。它采用 River 作为 Wayland 合成器基础，GUI 层仅依赖 Cairo 与 Pango 的 FFI 绑定，保持极简。作者因长期受 GNOME 家长式设计哲学困扰而转向 Gliver，认为其以 Guile（与 Guix 同语言）构建，让非程序员也能通过定制逐步成长为 Scheme 使用者。当前版本仍存在明显缺陷，如交互式提示（#:interactive）尚未实现，创建工作区等操作只能在 REPL 中完成；开发者正参照 Flutter 思路重构 GUI 系统，预计 0.0.5 将修复大量问题。作者目前以 git 检出方式运行 Gliver，用 Cow 窗口管理器作启动器。她认为 Gliver 虽仍处早期，却代表了可理解、可参与软件的未来愿景，一旦正式打包进 Guix，很可能吸引整个 Guix 社区迁移。

## 5. 计算城市Mesh网络的无线链路布局与节点数量

- 原始链接: <https://meshcoveragecalculator.lalala.ing/>
- 英文标题: Calculate radio link placement and node amount for your city's mesh network

本文介绍了一款用于城市Mesh网络规划的交互式工具，核心功能是计算无线链路的放置位置及所需节点数量。工具界面以地图为基础，用户可通过点击Mesh链路或启用选择模式后在地图上选取两个位置，生成链路剖面图（Link Profile），从而评估两点之间的无线通信条件。工具将信号强度划分为三档：≥20 dB、10–20 dB、0–10 dB，并区分室内（Indoor）与室外场景。每个节点（Node）可显示其覆盖范围（Node Coverage）、地面/天线海拔高度（Ground / Antenna AMSL）、已连接的邻居节点数（Connected Neighbors）等关键参数。用户还可从任意节点视角查看地形剖面（Profile from this node），辅助判断遮挡与视距条件。整体而言，该工具面向城市级Mesh网络部署，帮助规划者在实际地形与建筑环境中合理确定节点数量与链路走向，降低部署成本并提升网络连通性。由于原文正文主要为界面元素与操作提示，未包含具体算法细节或实测数据，上述内容基于已有信息如实概括。

## 6. 假如网景用 HTTP 方式实现 SSL 会怎样

- 原始链接: <https://owl.billpg.com/what-if-netscape-did-ssl-the-http-way/>
- 英文标题: What If Netscape Did SSL the HTTP Way?

本文设想了一个平行宇宙：1995年网景发布SSL时，没有另起443端口和https://协议，而是将TLS作为HTTP的Upgrade升级来实现。具体流程是：浏览器先以明文HTTP请求服务器证书（GET /.well-known/tls-cert），验证后用Upgrade头协商切换加密，握手全程在HTTP层完成。这一设计带来多重好处：Host头天然解决虚拟主机问题，无需后来2003年才标准化的SNI；TLS握手不再是封闭黑盒，浏览器和服务器可独立更新，新CA可通过内容协商逐步推广；SSH与TLS可共享同一加密核心，避免重复造轮子；甚至可通过HTTP Upgrade直接承载SSH会话，省去端口22和「首次连接信任」的麻烦。文章也指出主要缺陷：机会性加密易遭stripping攻击，攻击者只需阻止握手即可降级为明文，浏览器无法区分服务器真未配置证书还是中间人拦截。作者认为该宇宙最终仍会引入类似HSTS的强制加密机制，甚至可能重新发明https://，但含义变为「在80端口做HTTP，若无法协商加密则停止」。文章最后以QUIC复用TLS 1.3握手、SSH3项目等现实进展佐证，这一思路并非空想，只是真实世界走了更长的弯路。

## 7. 面向未来百个 Rust GUI 项目的建议

- 原始链接: <https://linebender.org/blog/next-100-guis/>
- 英文标题: Advice for the next 100 Rust GUIs

Raph Levien 在 2022 年「面向未来十二个 Rust GUI」一文基础上，于 2026 年发布续篇，回顾 Rust GUI 生态四年半的进展并给出新建议。文章指出，Rust GUI 在性能、内存占用和跨平台方面仍具显著优势，而 AI 编程的兴起正在消除 Rust 开发门槛高的障碍——LLM 生成 Rust 代码的成本与其他语言相当，且 Rust 类型系统在大代码库中更利于维护，使其成为 AI 驱动重写的热门选择。Zed 编辑器的 GPUI 框架已证明 Rust UI 可落地，Discord 等也在采用。作者认为移动端最务实的路径是原生 UI 搭配 Rust 业务逻辑，因 Liquid Glass 等原生细节难以跨平台复现。文本布局（Parley、Cosmic Text）和无障碍（AccessKit）已基本解决，但系统合成器集成仍是未解难题，subduction 库有初步进展。在架构上，作者认为即时模式适合游戏开发但难以支撑生产级应用，建议将设计层与执行层分离，借鉴 Web 标准（如 CSS 选择器、WPT 测试）但做轻量化适配，避免 DOM 和完整 CSS 的开销。Blitz 模块化浏览器引擎和 Xilem/Masonry 的拆分被视为良好范例。最终建议：大胆尝试、基于成熟规格构建、与上游开源社区协作。

## 8. scriptura：你的脚本专属小角落

- 原始链接: <https://alanpearce.eu/post/scriptura/>
- 英文标题: scriptura: a cozy corner for your scripts

作者基于 sd 的理念，为 fish shell 用户开发了 scriptura 工具，用于在目录树中运行和管理脚本。用户通过设置 SCRIPTURA_ROOT 环境变量，以层级路径调用脚本（如 scriptura run os update linde），并享受逐层 tab 补全；脚本解析完成后自动插入 -- 分隔符，再衔接默认文件名补全。工具提供 run、new、edit、which、cat、cmd 等子命令，还支持将 scriptura 子目录下的脚本注册为自定义子命令，降低调用门槛。文档方面，支持 .help 文件、脚本内 # 注释及文件夹级 help 文件，信息在补全和 help 子命令中统一呈现。脚本语言不限 fish，shebang 可自由修改。作者开发此工具的动机有二：sd 名称与系统中已有的 sed 替代工具冲突，且缺少 fish 补全支持。相比 sd，scriptura 采用子命令风格而非 flag 风格，并新增了 new 后补全、cmd 在根目录执行命令等特性。项目提供 home-manager 模块，代码托管于 git.alin.ovh、codeberg 和 sr.ht。

## 9. 为Mojang做端口扫描：一个业余项目如何沦为封禁私人服务器的数据源

- 原始链接: <https://sipacid.com/blog/port-scanning-for-mojang/>
- 英文标题: port scanning for mojang

作者开发了名为slowstack的Minecraft服务器端口扫描器，最初仅用于寻找CTF靶机。运行数月后，发现Mojang（《我的世界》开发商）以官方邮箱注册并使用其API，且同时依赖mcscans等第三方扫描服务。作者起初感到荣幸，但随后在Reddit上看到多起私人服务器因「违反Mojang准则」被ISP转达封禁通知的案例，且时间线与Mojang注册账号吻合。作者核查日志，确认Mojang确实在搜索含不当词汇的服务器描述；交叉比对Mojang公布的封禁IP哈希列表后，发现被封服务器包括描述仅为「faggot」或仅引用Lil Wayne歌词的私人服务器。为排除其他违规可能，作者让朋友架设带轻微不当描述的白名单服务器，一周内同样被封。作者质疑：Mojang作为微软旗下公司，完全可通过遥测或自行扫描获取数据，却选择免费利用业余爱好者的项目。两个月前Mojang再次联系作者，要求扩展扫描Bedrock版服务器。作者因处理大量滥用投诉邮件而关闭项目，Mojang随即索要数据导出与源代码，被作者拒绝。文章核心观点是：一家大型公司依赖第三方免费扫描数据来封禁私人服务器，而被封者仅收到ISP转来的恐吓邮件，这一做法既荒谬也缺乏透明度。

## 10. 绕过 Google Feedburner 订阅源问题及半生效的缓存机制

- 原始链接: <https://joshua.hu/fixing-google-feedburner-cache-problem-atom-rss>
- 英文标题: Fixing Google’s Feedburner problem, and caching that half works

作者此前发现 Google Chrome Releases 博客的 Atom 订阅源（经 Feedburner 分发）长期滞后数天，而 RSS 源又重定向至该过期源，导致其 CCBot 无法及时获取 Chromium 漏洞修复信息。本文记录了两个关键发现：第一，在 blogger.com 的 feed 地址后追加「?redirect=false」参数即可绕过重定向，直接获取最新内容；第二，该绕过路径的缓存行为「半生效」——Feedburner 本身仍不返回 ETag、忽略 If-Modified-Since 并强制 no-cache，但 redirect=false 路径下，前置缓存层（max-age=1 秒）会在同一秒内对后续请求返回 304，一旦缓存过期则后端 blogger-renderd 完全忽略 If-Modified-Since。不过 If-None-Match 可稳定返回 304，前提是请求时携带 Accept-Encoding: gzip 以获取 ETag（不压缩则无 ETag）。此外，所有 feed 重定向目标均为 http 而非 https，存在中间人篡改安全公告的风险。作者最终建议：轮询 Blogger 订阅源时使用 redirect=false、请求 gzip、保存 ETag 并以 If-None-Match 回传，Python requests 库默认已请求 gzip，只需额外处理 ETag 即可。CCBot 1.1.2 已发布。

## 11. Ghostscript CVE-2026-125396「Upload2Shell」：字体加载器释放后使用漏洞与沙箱绕过

- 原始链接: <https://pwn.ai/upload2shell/research.html>
- 英文标题: GhostScript CVE 2026-125396: "Upload2Shell"

pwn.ai团队于2026年11月披露Ghostscript中CVE-2026-125396「Upload2Shell」漏洞，系Type 1字体加载器的释放后使用缺陷。漏洞位于gs_fonts.ps的.putgstringcopy函数，.forceput操作前缺少操作数类型校验。攻击者注册恶意字体触发typecheck错误，借PostScript错误处理器劫持执行流至.forceput，在systemdict中写入本地对象引用；save/restore后该引用悬空，内存复用即指向活跃解释器数据，形成write-what-where原语。借此覆盖path_control_active等字段并修改PermitFileWriting、LockFilePermissions，可在-dSAFER仍启用时绕过沙箱实现任意命令执行。攻击入口极为隐蔽：应用无需直接调用gs，经ImageMagick、Pillow、libvips、Qt KImageFormats等常见图像库处理EPS或PDF内容即可间接触发Ghostscript。Roundcube邮件预览、WordPress PDF预览、InvokeAI、AUTOMATIC1111、ComfyUI等应用均受影响，命令以渲染进程账户（如www-data、lp）执行，无需攻击者持有目标账户。

## 1. Shell 感叹号不是用来喊叫的：善用历史扩展，做个懒人

- 原始链接: <https://refp.se/articles/your-shell-and-the-lazy-exclamation-mark>
- 英文标题: A shell exclamation mark is not for yelling. Be lazy

本文介绍了 shell（尤其是 bash、csh、tcsh、zsh）中的事件指示符（event designators），即用感叹号引用历史命令的机制。作者认为程序员都是懒人，而命令行重复劳动完全可以通过这些技巧简化。文章用大量示例展示了如何用 !! 重复上一条命令、用 sudo !! 以管理员权限重跑、用 !$ 取上一条命令的最后一个参数、用 !$:h 提取目录部分、用 !$:t 提取文件名，以及使用 :r、:e、:s/old/new/ 等修饰符对参数进行替换和裁剪。事件指示符的整体语法为 ![事件][:单词][:修饰符]，事件部分可指定行号、命令前缀、包含字符串等，单词部分可指定第几个参数或范围。文章还重点介绍了 POSIX 的 fc 命令，它不仅能重复命令，还能在 $FCEDIT 指定的编辑器中编辑历史命令，甚至通过 sed 等批量替换后重跑多条命令。作者认为掌握最常用的四个指示符（!$、!:0、!$:h、!$:t）就能大幅减少按键次数。FAQ 部分回应了为何不用 ctrl-r 或 alt-. 的疑问，并说明如何在 bash（set +H）和 zsh（setopt nobanghist）中关闭该功能，或通过 histchars 改用其他触发字符。文章强调这些技巧仅适用于交互式 shell，不应用在脚本中。

## 5. Zig 的 std.Io.Threaded：用线程实现可取消的阻塞 I/O

- 原始链接: <https://matklad.github.io/2026/08/06/neat-io-threaded.html>
- 英文标题: Zig's Io.Threaded is Neat

本文介绍了 Zig 新 I/O 接口的一种实现——std.Io.Threaded。它基于普通操作系统线程和阻塞系统调用，却完整支持取消操作。作者首先区分了并发与并行：并行是确定性的、声明式的，而并发必然涉及取消——当一个异步计算不再需要另一个计算时，必须主动取消后者，而不能干等其完成。传统“直接用线程”方案的主要问题在于：线程阻塞在内核系统调用中时，语言层 API 通常无法将其唤醒，因此无法可靠取消。Zig 的 Io.Threaded 在 POSIX 上利用信号机制实现取消——取消方在共享内存中设置标志并向目标线程发送信号，目标线程被阻塞的系统调用会返回 EINTR，随后检查标志并决定重试或确认取消并展开错误处理。用户侧取消表现为 error.Canceled。在 Windows 上则使用更直接的 NtCancelSynchronousIoFile。与 Java 的线程中断机制（无法中断 I/O）和 pthread_cancel（不集成语言级 try/defer 清理、销毁线程代价高等）相比，Zig 在接口层面区分了“可以并发”与“必须并发”（io.async 与 io.concurrent），使得实现更精确：concurrent 总是可失败的，async 则不会。concurrent 由线程池支持，池满时才退化为新建线程。

## 9. 设备如何自行发现加密DNS：DDR机制解析

- 原始链接: <https://blog.dundns.eu/posts/ddr-encrypted-dns-discovery/>
- 英文标题: How a device finds encrypted DNS by itself

本文介绍了“指定解析器发现”（DDR）机制，它让设备在仅配置了普通DNS解析器IP地址的情况下，自动发现并升级到加密DNS。普通DNS只需IP地址即可连接，但加密DNS还需要主机名、端口和协议信息，这些无法从现有地址推断。DDR通过查询保留名称“_dns.resolver.arpa”向当前使用的解析器询问是否存在加密版本及其位置。支持DDR的解析器会返回加密端点的主机名、端口、协议及优先级，设备按自身支持的协议选择端点；如果解析器没有加密端点，也会明确说明。查询结果可能因解析器的配置而异：对所有用户统一过滤的解析器返回相同答案，而支持按配置文件设置的解析器可返回与查询来源对应的配置，使过滤规则等从首个加密查询起生效。回复中还会包含端点的IP地址，避免设备再次通过不安全的明文连接解析主机名。DDR最适用于两类场景：一是已使用加密DNS的设备，可通过该机制发现更高版本协议；二是只能配置IP地址的电视、游戏机等设备，无需额外配置即可升级。但文章也指出，从明文DNS开始的升级过程本身可被网络拦截或篡改，客户端仅将其视为机会性升级；若失败则继续使用明文DNS。相比之下，直接在设备上配置加密解析器仍是最强选项，DDR只是覆盖了那些无法手动配置的设备。

## 10. Web服务器部署模型在业余规模下崩溃

- 原始链接: <https://w.on-t.work/web-deployment-model>
- 英文标题: the web server deployment model breaks at hobby scale

文章讨论了一个常见困境：如果你开发的是让其他人在自己服务器上托管的Web应用，那么你在部署层面会遇到一系列在“业余规模”（hobby scale）下难以绕开的问题。作者逐一列举了静态文件、未认证缓存、已认证缓存、前端SPA、数据库扩展等场景。静态文件若交给反向代理，容器化会让配置变得复杂，最终只能让应用自己服务文件，导致效率低下。缓存方面，由于无法依赖外部专用缓存如Varnish，只能靠应用层设置Cache-Control等头，但内置中间件能力有限，不同管理员使用的缓存配置五花八门，反而造成资源浪费和错误。已认证缓存更复杂，支持外部缓存需要写插件或自定义反向代理，为了降低部署门槛，作者只能把缓存和认证都移进应用内部，牺牲性能。前端若需要服务端渲染，非JavaScript后端难以集成Node进程，最终只能将前端拆成独立应用，让管理员配置更复杂的反向代理规则。数据库方面，日语搜索等需求可能需要pgroonga这类扩展，但在共享Postgres上安装扩展对业余管理员而言负担极重。最后作者得出结论：为了让普通人能够部署，他放弃了原有的“简单部署”目标，将所有组件打包进一个Docker镜像，管理员只需将现有反向代理指向容器即可。文章以对一个实际请求的讽刺描写结尾：这个请求经过了两层反向代理、缓存，最终发现它只是一个爬虫在抓取历史页面。

## 11. 超级马里奥派生：用 Nix 属性路径玩《超级马里奥兄弟3》

- 原始链接: <https://fzakaria.com/2026/08/05/super-mario-derivations>
- 英文标题: Super Mario Derivations

本文探讨了 Nix 语言的惰性求值特性如何催生一种创意玩法：把属性路径当作《超级马里奥兄弟3》的按钮序列。作者指出，Nix 的属性集可以是无限递归的，访问哪一层才求值哪一层，因此属性路径本质上是一个惰性生成的树。他利用这一特性，将每个游戏帧表示为一个派生（derivation），每次按键作为从一个帧到下一个帧的转换，从而让 Nix 存储成为模拟器的存档历史。例如，`.#level1.rightb.rightb.rightab` 会生成对应按钮操作后游戏画面的 PNG。项目代码位于 fzakaria/nes-nix，ROM 作为 flake 输入，可泛化到其他游戏。每个派生只依赖前一帧的存档状态，不会重复模拟祖先帧；因此分支或追加操作通常只新增一个派生。文章还测量了扩展性：默认最大调用深度约 2400 次按键，调高后可支持 20000 次，每次求值约 0.7 毫秒；但单参数大小限制在 21845 次按键（每个按键 6 字节）。可通过从文件读取输入序列绕过该限制，且生成的派生与属性路径完全一致。构建时间也随按键数线性增长，每按键约 1.27 秒（启用替换）或 0.28 秒（禁用）。作者总结，Nix 属性路径不仅是名称，而是一个程序，Nix 存储则是可复现状态机的持久层，这让“包管理器”也能用来玩马里奥。

## 16. Nix评估即调度问题：Evix引擎的架构与实践

- 原始链接: <https://notashelf.dev/posts/evix>
- 英文标题: Nix Evaluation Is a Scheduling Problem

文章围绕作者开发的Evix引擎，阐述了将Nix评估视为调度问题的核心观点。作者认为，Nix评估并非一次性成本，而是内循环中的高频操作；传统CLI管道每次调用都重新评估并丢弃图结构，效率低下。Evix是一个库优先的异步Nix评估引擎，通过Nix C API评估flake、文件或内联表达式，并以类型化事件流报告派生。其核心模型是：每个worker只评估一个属性路径并返回一个事件，队列驱动遍历，派生结果按属性路径组织成图，事件顺序不影响最终图。worker采用子进程而非线程，支持RSS内存检查与超限重启，图保存在父进程以保证稳定性。Session是产品核心，支持长期驻留、流式首评、查询、diff和文件监听；daemon通过Unix socket共享会话，便于多命令复用。远程worker通过Cap'n Proto协议实现分布式评估，使本地进程可退化为纯调度器。基准测试显示，同等测试下Evix四worker约198ms，优于nix-eval-jobs的359ms。Evix专为Circus CI设计，目标是让后续查询变为普通程序操作，而非重新评估。

## 17. celld：自托管的 Durable Objects

- 原始链接: <https://celld.dev/>
- 英文标题: celld — Durable Objects, self-hosted

celld 是一个自托管 Cloudflare Durable Objects 模型的实现，允许把该编程模型运行在自己选择的基础设施上。其核心机制是用 S3 bucket 作为协调者：没有成员协议、故障检测器或共识，cell 的所有权是 bucket 中的记录，通过一次原子写（compare-and-swap）获取；celld 内置复制器把每个 cell 的 SQLite 状态以 LTX 段持续复制到 bucket。文章从可靠性角度对比了自托管与托管：在放置上，cell 身份不再绑定特定机器，节点丢失后其他节点可获取租约并在几秒内恢复；在爆炸半径上，消除了共享的调度/放置层，避免与其他租户的工作负载相互耦合；在可读性上，故障证据（所有权记录、SQLite/LTX 文件、日志）都在自己的磁盘上，可用 sqlite3 和 grep 调查，而不用依赖语焉不详的状态页。作者也明确自托管并不自动更可靠，只是让故障域更明确、可检查。最后，文章表达了对 Cloudflare 和 Kenton Varda 的敬意，称 Durable Objects 是一个值得在任何地方运行的原语，celld 由 V8、SQLite 和 LTX 构成，是一个完全依托 S3 的有状态分布式系统。

- 英文标题: Setup a simple web server with bozohttpd on NetBSD

## 20. 深入理解 C++ ABI

- 原始链接: <https://www.ykiko.me/en/articles/692886292/>
- 英文标题: Thoroughly Understanding C++ ABI

文章从实践层面剖析C++ ABI，说明ABI是二进制程序模块间的接口，其稳定性受CPU、操作系统、编译器和C++标准共同影响。以x64平台为例，主流ABI分为Windows x64 ABI和x86-64 System V ABI，二者在目标文件格式（PE32+ 与 ELF）、数据表示（如long的位宽不同）及函数调用约定（寄存器传参规则、栈清理责任等）上都有差异。文中通过反汇编示例展示：在System V ABI下，小于16字节的结构体可以按值放入寄存器，比引用传递更高效；而Windows x64 ABI对大于8字节的结构体按值传递时，生成的代码与引用传递完全相同。文章还指出，unique_ptr因用户定义的拷贝构造只能按引用传递，与裸指针的效率并非完全一样；平凡类型对象才能用寄存器传递。C++标准本身不规定完整ABI，但保证结构体成员按声明顺序排列、标准布局等要求；同时C++17将noexcept纳入函数类型会影响名称修饰，C++20的no_unique_address可能造成ABI破坏。最后介绍了C++23的显式对象参数，允许明确定义this的传参方式，甚至可按值传递，便于成员函数作为回调使用。

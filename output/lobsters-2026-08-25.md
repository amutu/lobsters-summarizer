## 1. 无法摆脱过劳的困境

- 原始链接: <https://lobste.rs/s/0typpq/i_cannot_survive_from_burnout>
- 英文标题: I cannot survive from burnout

作者自述两年前经历严重过劳，随后离婚、搬到新城市，如今独居并照顾七只猫。尽管尝试强制自律、制定详细计划、不断重新开始，仍背负大量债务。核心问题在于：能持续投入自己的副业项目，却难以花时间在付费客户工作上，每周只能勉强工作五六个小时；虽然能凭借经验找到客户，却因产出低而流失。他试过常见的过劳建议均无效果，开始怀疑过劳已经变成习惯、借口或自我破坏。社区评论给出多种回应：多人建议寻求专业心理医生或精神科医生诊断，特别指出类似症状可能与ADHD有关，并分享自己通过诊断和药物治疗（如利他林、佐洛复）恢复能力的经历；也有人建议改变工作环境（如回到办公室）、重建人际联系、减少冗余负担，甚至彻底转行。总体结论是：过劳恢复过程漫长且非线性，仅靠意志力难以突破，专业诊断、药物支持和生活结构调整是关键；同时提醒网络建议不能替代医学诊断，若条件允许应尽快寻求正规医疗帮助。

## 3. 博客文章可以手写吗？

- 原始链接: <https://diggingforfire.blog/posts/can-a-blog-post-be-handwritten/>
- 英文标题: Can a blog post be handwritten?

这篇文章探讨了一个新颖的博客写作方式：是否可以完全手写博客内容？作者设想使用Supernote电子墨水设备进行手写，然后将内容导出为WebP图片格式。由于WebP支持XMP元数据，作者相信可以通过JavaScript读取其中的信息。具体实现路径是：把手写稿作为图片嵌入博客，同时将OCR识别并人工编辑后的文字存于元数据中，再编写脚本让读者在原始笔迹和规范文本之间自由切换。作者认为这个想法值得进行实验，并对自己手写的可读性表示好奇。全文没有任何实验数据或结论，本质上是一个创意技术随笔，亮点在于利用现有开放格式（WebP+XMP）将手写体验带上网页，兼顾了个人表达与数字内容的可检索性。文章最后附带一个键盘符号，或许暗示这仍是键盘时代的一次非主流尝试。

## 4. Firefox 宣布即将支持 JPEG XL：Rust 解码器与渐进式渲染

- 原始链接: <https://hacks.mozilla.org/2026/08/intent-to-ship-jpeg-xl/>
- 英文标题: Intent to Ship: JPEG XL

Firefox 在 2021 年发布 AVIF 后，近日宣布计划正式支持 JPEG XL；Chrome 也将跟进，加上 Safari 已有部分实现，该格式有望年底前获得跨浏览器支持。由于担心早期实验版依赖的 10 万行多线程 C++ 代码扩大攻击面，Firefox 要求谷歌研究院用 Rust 重写解码器；谷歌团队以 jxl-rs 完成挑战，它已成为 Firefox JPEG XL 支持的核心。文章重点介绍渐进式渲染：图片可在下载过程中逐步显示，用户仅需下载少量数据即可辨认图像主题。文章还对比 JPEG XL 与 AVIF：AVIF 在常见网络图片上文件更小，但 JPEG XL 在无损压缩、渐进式渲染和对既有 JPEG 的无损再压缩上更优，例如同一照片无损时 JPEG XL 为 1.45 MB，优于 AVIF 的 1.76 MB。作者建议开发者按站点代表性图片测试后选择。

## 5. Perspec 1.0：用于文档照片透视校正的 Haskell 桌面应用

- 原始链接: <https://adriansieber.com/announcing-perspec-1-0/>
- 英文标题: Perspec 1.0: A Haskell desktop app for perspective correction of document photos

Perspec 是一款专为文档和收据照片设计的桌面应用，用于校正透视变形，现已发布 1.0 版本。作者耗时九年，初衷是替代手机扫描应用，在电脑上处理照片，并避免 JPEG 压缩伪影和无效的实时预览。核心创新在于采用角点检测而非传统边缘检测：通过灰度化、模糊、Sobel 滤波、分水岭分割、Förstner 角点检测等步骤，能更准确处理褶皱或弯曲的文档边缘，并允许手动拖拽修正。软件还提供两种黑白导出算法：常规方法通过减去模糊副本去除阴影再应用 Otsu 阈值；新增的 Save BW Smooth 使用双阈值产生抗锯齿边缘，更小文件且更清晰。1.0 还新增了 Windows 支持、可拖动多边形边、拖放文件、EXIF 旋转处理等。应用基于自研 C 库 FlatCV 和 Haskell 构建，提供 macOS、Windows、Linux 预编译版本，需购买许可证去除升级提示。计划未来支持固定输出尺寸和二维码检测。作者希望用户试用并反馈问题。

- 英文标题: Everything I own, owned

## 8. 动态命名服务器：自建本地DNS的尝试

- 原始链接: <https://arch.dog/bark/dynamically-naming-servers>
- 英文标题: Dynamically Naming Servers

作者在自托管环境中遇到DHCP分配IP不稳定、静态IP管理繁琐的问题，决定自建一套本地动态DNS系统。他首先排除了使用Tailscale统一管理所有机器的方案，因为对家庭实验室而言成本高、存在锁定风险，且家人不便常开。他注意到现有动态DNS服务多面向公网，缺少纯本地、自动更新的方案，于是开发了名为“treens”的DNS服务器。该系统采用ed25519消息签名实现客户端自主注册主机名和更新IP，无需预共享API密钥；服务端用SQLite存储记录，通过TCP/UDP处理DNS查询，并提供HTTP接口管理主机。记录默认不对外服务，需审批或按子网自动批准。作者将Unbound配置为指向该服务器，使用.lan.gmem.ca子域，目前运行稳定。文中还提到原本计划引入Merkle树验证记录，但初期实现中觉得冗余而暂缓。作者认为该项目相对通用，可能推荐他人自部署。

## 10. 在其他论坛复刻 Reddit 的最佳功能

- 原始链接: <https://xavd.id/blog/post/highlighting-users/>
- 英文标题: Replicating Reddit's best feature on other forums

本文作者认为 Reddit 最被低估的功能是“好友（friend）”标记：无需对方批准或通知，一键标记后，该用户的帖子或评论就会以高亮显示，让社区更像熟人聚会而非匿名喊话。作者惊讶于 Lobsters、Tildes 等社区没有类似功能，加上 Tildes 已进入维护模式，他决定自己动手。他利用 Stylus 这类自定义 CSS 的浏览器扩展，针对用户个人页链接编写高亮样式，并开发了一个 CLI 工具 rolodex：它读取 TOML 文件中的用户名列表，自动生成对应的 CSS 规则，用户粘贴到 Stylus 中即可在浏览时高亮关注对象。目前该工具支持 Tildes 和 Lobsters，未来可能加入 Hacker News。作者还提供了模板仓库，方便他人定制自己的用户列表。但他也承认，这种方案有局限：增删关注用户需要编辑本地文件、运行脚本再上传，过程繁琐；同步选项有限；移动端支持不佳；也无法像 Reddit 那样自动聚合所关注用户的动态。因此作者最后呼吁，任何社交网络运营者或维护者应原生加入“关注”功能，才能提供真正无缝的社区体验。

## 13. kudu - 在Linux上轻松管理虚拟机

- 原始链接: <https://github.com/pythops/kudu>
- 英文标题: kudu - easily manage VMs on Linux

kudu 是一个用于在 Linux 上创建和管理虚拟机的 TUI（终端用户界面）工具，可作为 virt-manager 或 GNOME Boxes 等图形界面的替代方案，且不依赖 libvirt。它基于 QEMU 运行，支持 x86_64、aarch64 和 riscv64 架构。使用前需要安装相应的 QEMU 系统模拟器、xorriso（用于 cloud-init）、passt，以及可选的 UEFI 固件包。用户可通过预编译二进制或从源码构建（Cargo）安装，Arch Linux 用户可直接用 pacman 安装。基本用法是直接运行 `kudu` 命令。常见问题方面，如果 KVM 显示禁用或不可用，需确保内核模块已加载，普通用户需加入 kvm 组或使用 sudo；即使没有 KVM，kudu 也能正常运行。项目欢迎贡献，但明确要求不接受 LLM 生成的提交，贡献前需先提出 issue 或讨论，且保持 PR 小而专注。软件以 GPLv3 许可证发布。

## 14. 动手构建前的三条约束

- 原始链接: <https://jordanlord.co.uk/blog/3-constraints/>
- 英文标题: 3 constraints before I build anything

作者认为约束是创造力的催化剂，能压缩搜索空间、逼出创新方案。他在10年产品经历中，因复杂而无特色失败多次，最终沉淀出三条先决约束。第一，一页纸原则：所有想法必须先写成一份非协商、精确、精简的一页纸，作为北极星文档；它既是沟通工具，也是自我梳理方式。若写不满一页，说明尚未准备就绪；若超过一页，则过于复杂，不建。第二，核心技术与产品可分离：必须发展出一项独立于产品存活的核心技术（方法、库、工具等），像Git之于Linux、HCL之于HashiCorp、Kubernetes之于Google。产品可转向，但核心科技能复利增长，是长期承诺。第三，一个定义性约束塑造产品：此约束必须一览无遗、始终出现在用户交互中，成为产品身份，如Minecraft的方块、IKEA的平板包装。它抑制功能蔓延，缩小决策范围，让设计“流”出来。最终规则：只要违反任何一条，就不该建。三条约束共同筛选出足够精简、有杠杆、有辨识度的产品。

- 英文标题: The text mode lie: why modern TUIs are a nightmare for accessibility

本文指出，许多视力正常的开发者误以为终端应用因纯文本而天然无障碍，但现代文本用户界面（TUI）框架（如Ink、Bubble Tea、tcell）实际上比图形界面更不利于屏幕阅读器。命令行本质上是线性数据流，新数据在底部，向上回溯，屏幕阅读器可以轻松处理；而现代TUI采用二维网格布局，将每个字符单元视为像素，抛弃了时间流，改用空间布局，导致光标每次刷新都在乱跳，屏幕阅读器无法理解。相比之下，以Irssi为代表的老式TUI使用VT100滚动区域而非整体重绘，设计更贴近终端特性，因此对屏幕阅读器更友好。作者认为，问题并非TUI天生无障碍性差，而是现代框架没有利用终端的核心功能。他呼吁开发者正视这一缺陷，重视无障碍体验。

## 16. GNU Emacs Canvas 入门

- 原始链接: <https://monadicsheep.org/blog/an-introduction-to-canvas-in-emacs.html>
- 英文标题: An Introduction to Canvas in GNU Emacs

本文介绍 Emacs 新引入的 Canvas 图像类型，该功能已被合并到上游 GNU Emacs，并将在 Emacs 32 中发布。作者澄清 Canvas 与 HTML5 Canvas 无关，它是一种通过动态模块 API 暴露 ARGB32 像素缓冲区的图像类型，允许从 Emacs Lisp 或 C 动态模块直接操作像素数据。与 SVG 等传统图像格式不同，Canvas 的数据只是原始像素数组，且可通过 canvas-refresh 函数只刷新画布相关字形，避免触发全量 redisplay，从而显著提升高频率图像更新的效率。文章详细说明了如何在纯 Emacs Lisp 中创建和显示 Canvas，以及如何通过动态模块访问底层像素缓冲区，并演示了两个示例：弹球动画和混沌双摆模拟。作者还回应了常见疑问，指出 Canvas 无需硬件加速即可流畅运行，并建议在外部完成 GPU 计算后再将像素写入 Canvas。文章适合对 Emacs 图像处理和动态扩展感兴趣的开发者阅读。

这篇文章源自作者与Heidi Howard的对话，讨论TLA⁺等有限状态模型检查在研究与工业中的角色变化。过去用户面临经典取舍：花20%精力做模型检查，获得约80%信心；或花大力气做形式化证明。但2026年夏自动定理证明进展显著，出现了“花钱购买自动生成证明”的新选项。作者认为，有限状态模型检查虽技术上早已被符号模型检查超越，却因可理解性仍在使用——普通工程师也能自写检查器，而符号方法晦涩、存在性能悬崖。展望未来，可理解性只是利基；更重要的应用在测试：模型驱动测试与痕迹验证，但实现困难。作者唯一看好的是确定性模拟测试（如Antithesis），这需要指定动作、不变量、可控状态探索、快照恢复和不修改被测系统的抽象；实现途径有确定性CPU模拟与确定性hypervisor。文章列举了rr、hermit、deterministic-vmm、Bedrock、dhyve等项目及局限，预测80/20的舒适区正在消失，未来将分化为形式证明与确定性模拟测试，以确保规范与代码一致。

## 19. 控制与复杂性：系统设计中的张力

- 原始链接: <https://ferd.ca/control-and-complexity-tension-in-systems-design.html>
- 英文标题: Control and complexity: tension in systems design

文章探讨系统设计中控制与复杂性的张力，尤其在大语言模型改变软件开发实践背景下。作者对比两类思路：一是分析式分解/控制，源自经典科学与工程，主张将整体拆分为部件、理解因果、限定变量，以实现可预测、可验证的结果；二是复杂性/涌现视角，认为复杂系统高度互联、动态开放、受历史影响，难以分解和预测，只能小步干预、增强适应能力，追求影响而非控制。文章指出系统扩大后，控制类干预回报递减、意外增多；常见对策是更用力地分析和自动化，但可能让故障更少却更大。作者用表格对比两者在培训、安全、正确性、可靠性、事件处理、功能开发、标准制定上的典型差异，并说明代码审查、SLO、重构、混沌工程、平台等实践可同时服务两种目的，关键取决于参与者的立场和预期。最后提醒，仅选一种视角可能让控制活动被实践者暗中改造，或涌现活动沦为形式化忙碌；应留意变化所偏向的视角，并借用Box的话：所有模型都是错的，要警惕错在哪里。

## 20. Atkinson Hyperlegible 在相同字号下看起来比某些字体略小

- 原始链接: <https://twotwos.nekoweb.org/posts/hyperlegible.html>
- 英文标题: Atkinson Hyperlegible appears a little smaller than some other fonts at the same font size

文章讨论了 Atkinson Hyperlegible 字体在替换现有字体时可能遇到的问题：在相同字号下，它看起来比其他一些字体（如 Verdana）更小，从而可能降低可读性。作者通过对比 10pt 下的 Arial、Atkinson Hyperlegible 和 Verdana 的示例，指出字体实际显示大小受 x-height（小写字母如 x 的高度）影响，不同字体在同一字号下视觉尺寸差异明显。为了在网页中自动调整，作者介绍了 CSS 的 font-size-adjust 属性，并尝试设置 `font-size-adjust:0.545` 来匹配 Verdana，但效果不理想：有时 Atkinson 变得过大，有时仍显小，尤其在 11pt 时依然存在问题，推测是字号取整所致。作者还提到该问题可能仅出现在 Firefox 中。此外，MDN 文档给出的确定 font-size-adjust 值的方法较为繁琐，作者认为浏览器应能自动计算，但未找到便捷途径。最后，作者感谢 pebble 在 critter.cafe 网站中改用该字体并启发了这次探索。核心结论是：小字号下不同字体的显示差异显著，替换字体时需适当增大字号或使用 font-size-adjust 调整，但该属性并非总能可靠工作。

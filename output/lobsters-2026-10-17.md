## 1. NIST椭圆曲线种子生成之谜揭晓，悬赏已被领取

- 原始链接: <https://words.filippo.io/seeds-solved/>
- 英文标题: The NIST Elliptic Curves Seeds Bounty Has Been Claimed

2026年10月，Anthropic团队破解了NIST椭圆曲线（P-192至P-521）种子生成方式的长期谜题，领取了作者三年前设立的36,864美元悬赏并捐予运营Let's Encrypt的非营利组织ISRG。此前流传的说法是已故数学家Jerry Solinas于1997年用SHA-1哈希某些英文句子生成种子，但实际方法是使用POSIX标准drand48随机数生成器，以当时UNIX时间戳为种子，逐字节输出后按ANSI X9.62标准筛选有效曲线。团队还发现两个未文档化的额外筛选条件，其中一个仍未完全解释。安全层面，这一发现彻底排除了Bernstein和Lange于2017年描述的利用70比特自由度攻击假设性弱曲线的方法——即便假设NSA可自由选择1997至1998年间任意时间戳及前16个候选，其自由度也仅约30比特，不足以植入任何后门。作者认为这完成了NIST椭圆曲线密码学的「康复弧线」，如今个人推荐NIST曲线优于Curve25519/Ed25519/X25519，尽管它们即将被后量子签名方案取代。

## 2. iroh 1.0 之路：四年演进与关键取舍

- 原始链接: <https://www.iroh.computer/blog/the-road-to-iroh-1-0>
- 英文标题: The road to iroh 1.0

本文回顾了开源 P2P 网络库 iroh 从 2020 年启动到 1.0 发布的四年历程。iroh 最初是 IPFS 的 Rust 实现，面向轻量设备；在开发 krakensync 同步库时引入 QUIC（quinn），随后因 deltachat 聊天备份传输这一真实用例发现 IPFS 方案依赖过重、性能不佳，遂果断放弃 IPFS 兼容性，改用 Ed25519 公钥标识端点、BLAKE3 内容寻址、单一 QUIC 传输。此后逐步加入 TLS 原始公钥认证、参考 Tailscale 的打洞机制、ALPN 协议协商、pkarr 地址查找等能力。团队一度将 iroh 扩展为「开箱即用」的 P2P 应用工具包，但为保证质量最终收窄范围，1.0 仅聚焦「按端点 ID 建立可靠直连」，其余功能拆分为独立 crate。为支持多路径无缝迁移，团队 fork quinn 并维护自研 QUIC 实现 noq。文章还列出了未纳入 1.0 的议题：可配置密钥算法、后量子签名、加密 ClientHello 等。最终 iroh 1.0 以极简 API 和稳定线格式交付，已在数十万设备上运行，作者强调 1.0 仅意味着接口稳定，底层仍在持续演进。

## 3. 退相干陷阱：AI垃圾内容如何淹没无尽噪声中的信号

- 原始链接: <https://maevyn.codes/decoherence>
- 英文标题: The Decoherence Trap: When AI slop drowns out the signal in an endless sea of noise

本文提出「退相干」概念：系统中局部有效但彼此不兼容或冗余的模型不断积累，使变更成本被模型间翻译与防止副作用所主导，且退相干程度越高、增长越快，呈指数级失控。作者以管道维修和忒修斯之船作类比：逐步替换零件看似平滑，但中间状态需要同时理解新旧两套体系，复杂度远超任一单一系统；在软件领域，代码库如同迷宫，多套范式叠加后复杂度呈组合爆炸。通过图结构模拟，作者展示了「甜蜜点」曲线：相干性适中时开发效率最高，低于该点则特性交付时间急剧膨胀。关键洞见在于，退相干不随时间增长，只随变更增长，因此AI agent若以极快速度持续修改系统，即便每次引入的退相干极微，也可能在无人察觉时螺旋失控。好消息是，退相干同时阻止了AI在封闭环境中自我改进，也限制了其外部改进速率，从而排除了「智能爆炸」的幽灵；坏消息是，人类正滑向另一种灾难——「退相干崩溃」。作者指出，目前尚无证据表明AI agent比平均工程文化更擅长维持系统相干性，而大多数公司长期在甜蜜点以下循环往复，AI的大规模使用正以不可持续的速度制造退相干。

## 5. 用 ImageMagick 制作 88×31 像素《白鲸记》动画按钮

- 原始链接: <https://k.sosnierz.me/08-11-24/>
- 英文标题: Making a 88x31 button book using ImageMagick

本文介绍如何在 POSIX 系统上利用 ImageMagick 将整本《白鲸记》渲染为 88×31 像素的 GIF 动画按钮（book button）。作者指出，88×31 是早期网络（尤其 Small Web）中常见的按钮尺寸，多数动画仅用于吸引眼球，而他想尝试将一整本书塞进去。受限于极小画布，作者选用专为低分辨率设计的 TomThumb 字体（6×4 像素），每帧可排 5 行、每行 22 字符。文本处理阶段，先用 cat、tr、fold 三个 POSIX 工具将纯文本折成 22 字符宽的多行文件，再用 sed 清除非 ASCII 字符（如弯引号），并用 sed 在章节间插入空行。生成 GIF 时，通过 convert 命令将文本逐帧绘制为 88×39 的图像，再裁剪掉底部多余 8 像素，设置 6 秒帧延迟。作者还附了一段 Python 脚本，为每行文本计算前导空格以实现居中显示。最终成品为 4.2 MB 的 GIF，完整播放时长超过 19 小时，将整部小说以逐帧滚动的方式呈现在一个极小的按钮区域内。

## 6. Mull：基于语言服务器与 VS Code 扩展的纯文本 Wiki 笔记工具

- 原始链接: <https://github.com/stepchowfun/mull>
- 英文标题: Mull: note-taking with a language server / vscode extension

Mull 是一款以纯文本文件（.mull 扩展名）管理 Wiki 的工具，配套 Visual Studio Code / Cursor 扩展，提供语法高亮、悬停预览、自动补全、诊断、格式化与重构等能力。核心设计为：所有页面存于同一文件，以「# 标题」分隔，通过方括号链接互相关联；每个 Wiki 以 Home 页为起点，要求所有页面均可从 Home 到达，以此替代传统目录层级。外部文件与目录链接存放于同名 _files 目录，Mull 会校验链接有效性并支持预览。Portal 机制允许将某页内容嵌入另一页并自动同步编辑。用户还可编写 shell 脚本（如排序）嵌入特定代码块，格式化时自动执行。工具支持转义、反引号原文及围栏代码块。命令行提供 check、format、page、language-server 等子命令，便于 CI 集成。安装方面，macOS 与 Linux 可用一行 curl 脚本完成二进制与扩展安装，Windows 需手动下载并配置 PATH，Rust 用户也可通过 cargo install mull 获取。整体定位是轻量、无层级、以链接为唯一组织方式的个人知识管理方案。

## 10. Epic EAC2 v2 反作弊机制在 Linux 上存在较易绕过的缺陷

- 原始链接: <https://codon.org.uk/~mjg59/blog/p/epics-eac2-v2-seems-fairly-easily-bypassable/>
- 英文标题: Epic's EAC2 v2 seems fairly easily bypassable

Epic 宣布其 Linux 版 Easy Anti-Cheat 2.0（EAC2）将基于 eBPF 安全模块监控进程，并通过安全启动、度量启动和远程证明（remote attestation）三重机制防止绕过。核心思路是要求启用安全启动，用度量启动验证密钥，再由 TPM 生成签名的启动度量值提交服务器校验。文章指出该方案在技术上存在明显漏洞：其一，许多桌面主板的 TPM 为可插拔模块，带有标准 reset 引脚，作弊者只需短暂短接即可将 TPM 恢复初始状态，随后在用户态写入伪造的度量值，再配合修改过的内核向 eBPF 代码谎报正常启动日志，即可通过校验；其二，即使 TPM 焊死在主板上，也可通过约 20 美元的 USB 转 SPI 桥接器外接一个独立 TPM 模块，让内核将 /dev/tpmrm0 指向该外部设备并预置合法度量值，同样能骗过验证。文章总结认为，远程证明在无法将特定 TPM 与特定物理系统绑定的消费级环境中先天不足，仅在企业级部署中才可靠。从实用角度看，作弊者需额外购买硬件且每次被服务器封禁后需更换 TPM，可能足以形成一定威慑；但从技术严谨性而言，该方案远未达到真正防篡改的水平。

## 12. Rust 1.99.1 点发布

- 原始链接: <https://blog.rust-lang.org/2026/10/15/Rust-1.99.1/>
- 英文标题: Announcing Rust 1.99.1

2026年10月15日，Rust发布团队推出1.99.1点版本，修复了此前版本中的三处回归问题。第一，部分目标平台（尤其是UEFI）因LLVM的「loop-idiom-wcslen」优化pass引入对「wcslen」函数的调用，而该函数在libc中不可用，导致链接错误；修复方案是在编译器内置库中提供该函数的回退实现。第二，x86_64架构下，通过FFI返回「bool」类型的Rust函数可能未将返回寄存器的第1至7位清零，导致调用方读到非0或1的原始值；现已恢复ABI要求的零扩展行为。第三，macOS上「rust-lld」链接器在未通过rustup代理调用编译器时，因缺少库搜索路径配置而无法加载「libLLVM.dylib」；修复方式为在构建时添加对应的rpath条目。用户可通过「rustup update stable」一键升级。团队同时呼吁社区使用beta和nightly频道参与测试并反馈问题。

## 15. 智能体时代下 Rust 的机遇与演进方向

- 原始链接: <https://smallcultfollowing.com/babysteps/blog/2026/10/14/agentic-dev-and-rust/>
- 英文标题: What agents mean for Rust (and vice versa)

本文作者身为编程语言设计者，探讨了 LLM 智能体对编程及语言设计的影响，并论证 Rust 为何天然契合智能体开发。文章指出，Rust 当前增长迅猛，部分原因在于智能体降低了尝试新语言的门槛，而 Rust 的默认高性能与「能编译即正确」的类型系统护栏使智能体不易跑偏。作者将软件生产分为设计、构建、优化三支柱，认为智能体已擅长性能微调（如密码学算法的汇编优化、异步性能诊断），但设计环节仍是开放问题。在可靠性方面，作者强调类型系统虽能排除错误却无法保证正确性，需引入 Verus、Kani 等证明工具；而证明反过来也能释放 unsafe 代码的性能潜力。作者提出 Rust 的「北极星」目标：通过形式化证明让所有 unsafe 代码可验证安全，从而逐步消除未定义行为风险。改进建议包括：增强类型系统表达力、推动可扩展编译器以集成定理证明器、暴露性能调优旋钮同时保持代码意图清晰。最终，作者认为人类角色将转向高层设计与架构建模，智能体负责将设计翻译为 Rust 代码，语言设计的权衡重心也随之改变。

## 16. gopls 中的交互式重构

- 原始链接: <https://go.dev/blog/interactive-refactoring>
- 英文标题: Interactive refactoring in gopls

Go 官方博客介绍了 gopls 新增的交互式重构功能，该功能基于语言服务器协议（LSP）的一项新提案，由 Go 团队与 Dart 团队合作设计，旨在为所有语言和编辑器生态提供开放标准。传统 LSP 重构操作类似无参函数，服务器仅凭光标位置和语法树推断意图，无法向用户提问，导致许多重构只能给出固定默认值或干脆不提供。交互式重构在 LSP 层面建立了标准机制，允许语言服务器在生成编辑前通过多步对话框收集用户输入。具体功能包括：添加/移除 struct tags 时可自定义标签组合与命名风格；实现接口时支持动态符号搜索与泛型参数填写；移动声明时可跨文件、跨包选择目标位置并自动处理依赖与导入清理。该功能已在 gopls v0.24.0 和 VS Code Go 扩展 v0.56.0 中可用，Neovim 与 Emacs 也有概念验证集成。未来路线图涵盖函数签名变更、命名冲突的交互式解决，以及将交互性扩展到测试配置等非编辑操作。完整技术规格见 LSP 设计文档及 microsoft/language-server-protocol#1164 提案。

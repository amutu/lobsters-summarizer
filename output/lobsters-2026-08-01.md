## 2. 为什么我分叉了rand：构建urandom随机数库

- 原始链接: <https://casualhacks.net/blog/2026-07-27-why-i-forked-rand.html>
- 英文标题: Why I forked rand

作者因对Rust生态中广泛使用的`rand` crate感到不满，开发了分叉库`urandom`。主要痛点是`rand`的日常操作难以发现：有用方法分散在多个trait中（如`RngExt`、`IndexedRandom`、`SliceRandom`），需要用户额外导入并了解扩展方法适用于哪些类型，IDE补全帮助有限。`urandom`将高级API统一放在一个`Random`包装结构上，所有常用操作（如`uniform`、`choose`、`shuffle`）都是固有方法，无需导入trait。此外，`urandom`将低级`Rng` trait设为密封，不支持外部自定义生成器，但允许在内部针对特定生成器（如Xoshiro256）做优化，例如为`u32`和浮点数提供专门的`next_f32`/`next_f64`方法，从而在浮点生成上比`rand`快约24%。对于均匀整数采样，`urandom`采用延迟计算阈值的方式，统一使用无偏的multiply-and-reject算法，避免了`rand`中`UniformSampler`与一次性采样路径的割裂以及潜在的偏差。在可复现性方面，`urandom`保证在给定显式种子和低层调用序列时，确定性生成器的原始输出在支持架构和SemVer兼容版本间保持稳定（因此牺牲了32位架构的性能），这比`rand`的承诺更强。作者总结，`urandom`适合追求易用性、无偏性能和确定性可复现性的项目，但需要`rand`生态中更丰富分布和第三方集成的场景仍应使用`rand`。

## 3. Guix shell 现已集成到 Emacs 中

- 原始链接: <https://tusharhero.codeberg.page/guix-shell-in-emacs.html>
- 英文标题: Guix shell now inside Emacs

本文是作者为 Emacs Carnival 2026 提交的一篇技术文章，介绍了 GNU Guix 及一项新集成：在 Emacs 内部直接使用 guix shell。GNU Guix 是一个受 Nix 启发的高级包管理器，也是 GNU 操作系统的一个发行版，使用 GNU Guile 定义包，并用 GNU Shepherd 替代 systemd。guix shell 是作者最常用的功能之一，可快速创建包含指定包的软件环境，也可通过 manifest.scm 文件管理项目开发依赖。作者向 emacs-guix 包贡献了 M-x guix-shell 命令，使用户无需为每个项目单独启动终端运行 guix shell，再打开 Emacs。文章展示了在 Emacs 中调用 guix shell 的几种方式：指定单个包（如 python）、指定多个包（如 python 和 python-numpy）、以及生成 manifest.scm 文件。作者认为该界面仍有改进空间，目前未完全覆盖 guix shell 的全部功能，未来可能需要基于 transient 菜单（如 magit 所用）来增强体验，并推荐了 ben.el 等类似包。

## 4. 接受混乱的 Git 历史

- 原始链接: <https://beza1e1.tuxen.de/git_two_users.html>
- 英文标题: Accepting a messy git history

文章以 GitHub 推出 stacked pull requests 为引子，揭示了 Git 用户中的两种对立风格：一种是经常提交、不假思索的“频繁提交派”，另一种是精心 rebase、追求整洁历史的“rebase 派”。频繁提交派认为 rebase 是在浪费时间，细粒度的提交历史恰好反映了开发的实际过程；而 rebase 派认为频繁提交者懒惰粗心，只有整洁的历史才能让人理解每次变更的意图。在合并 PR 到主分支时，同样存在争论：rebase 派讨厌 squash merge 毁掉自己精心整理的历史，希望保留每个提交；频繁提交派则喜欢 squash merge，因为那让主分支历史更干净易读。作者承认自己更偏向 rebase，但这需要严格纪律，在大型组织中很难维持。如果不严格保持整洁，Git 历史很快就会变成一团乱麻，基于破窗效应会越来越糟，最终整个团队会放弃 rebase。因此，频繁提交似乎是更具韧性的做法，抵抗这种趋势没有意义。除非你拥有 Git 仓库的完全控制权，否则不如坦然接受混乱的历史。

## 5. 2026年7月Rust编译器性能优化进展

- 原始链接: <https://nnethercote.github.io/2026/07/31/how-to-speed-up-the-rust-compiler-in-july-2026.html>
- 英文标题: How to speed up the Rust compiler in July 2026

本文总结了2025年12月至2026年7月期间Rust编译器性能的改进。整体平均墙钟时间降低了5.59%，其中rustdoc贡献巨大，平均降低37.92%；剔除rustdoc后平均降低2.90%。主要改进包括：Noah Lev通过多个PR大幅减少处理impl时的工作量，使rustdoc性能提升；Jakub Beránek将rustdoc基准加入PGO训练集，带来平均2.85%的加速；作者本人优化了rustdoc的impl排序方式，减少指令数。Clippy方面，xmakro通过合并pass避免调用大量空的check_foo方法，实现10-30%的运行时减少；作者也独立发现类似问题但未合并。增量编译有多项小改进，例如Zalathar和xmakro的优化。新trait solver基准从27秒降至不到1秒，作者还修复了一个因136字节类型导致memcpy开销的问题。新贡献者xmakro和arya dradjica（Krabby编译器作者）受到关注。作者还缩小了AST节点大小，将表达式节点从72字节减至64字节，减少了缓存未命中。文章最后感谢了性能分类团队的成员，并提到作者已离职，正寻求回归Rust编译器开发工作。

## 6. 我们不断重新发明的轮子

- 原始链接: <https://blainsmith.com/articles/reinventing-the-wheel/>
- 英文标题: The Wheels We Keep Reinventing

技术行业存在一种怪圈：已被解决的问题被反复重新发明。作者以Heroku为例，其早于十多年前就提供了滚动部署、蓝绿发布和健康检查回滚，而如今许多Kubernetes团队仍在用探针、部署策略等原语重新搭建同一套机制。文章列举了常见案例：认证、后台任务、重试、限流、幂等键、特性开关、缓存、配置、搜索、工作流、多租户隔离等，均有成熟方案，但团队仍倾向自建，往往带来安全漏洞和维护负担。背后的原因包括：抽象泄漏、与问题不匹配、以及不愿将系统的一部分交给外部托管服务。作者主张：保持简单，但不能简单到把自己困在盒子里；用OIDC等标准协议和可自托管的子系统（如Keycloak、Postgres、Redis）在“完全自建”和“托管服务”之间取中间路线；同时呼吁撰写类似Stripe幂等键文档那样的规范，让常见组件的正确实现可复用。最后提醒团队关注投入精力比例：如果自建基础设施的耗时超过核心产品，就说明在重新发明轮子。动手前应先确认问题是否真的未解决，多数情况下已有答案，直接运行成熟版本即可。

## 8. 计费不必纠缠业务逻辑：用可计费事实简化架构

- 原始链接: <https://blog.exe.dev/billable-facts>
- 英文标题: Stripe Just Wants a Number

作者在 exe 公司负责计费系统，指出传统计费方式容易把计费逻辑与业务逻辑纠缠在一起，导致代码遍布热点路径、定价结构僵化，初创公司难以承受重写计费的代价。他提出“可计费事实”（billable facts）的概念：产品事件只需告诉计费系统“某事发生了变化，你可能需要为此收费”，而具体如何计算费用则由独立的对账流程完成。文章以团队新增成员为例，对比了旧方式（在事务中直接调用计费 API）和新方式（将席位状态标记为 dirty，由后台 worker 计算席位增量并同步 Stripe 订阅数量）。新架构让新成员入组不再依赖计费代码，也便于调整计费规则。该模式已扩展到计量计费（如磁盘用量）和 iOS 应用内购买等场景，系统只需记录事实，后续再与计费提供商对账。作者强调，计费系统最终要满足的只是“Stripe 想要一个数字”，关键在于如何可靠地算出这个数字。这种设计让团队其他成员也能安全地改动计费相关代码，降低了单点维护风险。

## 9. 何为双重fork（double-fork）？

- 原始链接: <https://bower.sh/what-the-double-fork>
- 英文标题: what the double-fork?

本文作者在构建zmx（一个用Zig编写的终端复用工具）时，深入研究了守护进程（daemon）的创建方法，并从abduco的实现中发现了double-fork技巧。文章首先解释了守护进程的概念：它属于没有控制终端的会话，因此不会因终端关闭而收到SIGHUP或SIGINT等信号。接着介绍了fork(2)的行为——进程在调用处克隆自身，父子进程各自独立运行；以及会话（session）和进程组的概念：会话是进程组的容器，只有一个前台进程组能与终端交互。作者解释为何需要双重fork：第一次fork后，子进程通过setsid()创建新会话并脱离控制终端，但此时子进程成为会话领导者，按POSIX规则，会话领导者仍有可能通过打开终端设备重新获得控制终端；第二次fork产生的孙进程不是会话领导者，从而永久杜绝了获取控制终端的可能，这是可移植的保证。文章还描述了double-fork之后的清理步骤：将stdin/stdout/stderr重定向到/dev/null，关闭继承的文件描述符（3至64），并说明了zmx不调用chdir和umask的理由。最后提到，理想情况应由systemd等监督进程管理守护进程，但zmx为了跨平台和自动daemon化，采用了此方法。

## 14. 嵌套数据并行的完全扁平化

- 原始链接: <https://futhark-lang.org/blog/2026-07-31-full-flattening.html>
- 英文标题: Full flattening of nested data parallelism

本文介绍了Futhark编程语言编译器在实现完全扁平化（full flattening）方面的突破性进展。由于GPU等硬件不支持嵌套并行，Futhark长期以来只能编译规则嵌套并行程序，而无法处理不规则嵌套。经过多年努力，特别是学生们的主要贡献，如今已能接近将任意Futhark程序编译为并行GPU代码。文章首先阐述了扁平化的基本思想：通过循环分布（fission）将复杂的map操作分解为一系列简单操作，并引入分段数组（segmented array）来表示不规则数组，用数据向量和标志向量编码，配合分段扫描（segmented scan）等原语，在保持扁平并行性的同时表达嵌套结构。针对控制流，文章介绍了分支打包（branch packing）方法，将map中条件不同的迭代分组执行；循环则采用类似思路。文章强调，新的扁平化转换旨在不降低原有程序性能，而对新支持的不规则程序性能优化则是后续目标。作者以直觉化的方式解释了这一复杂编译技术，并指出该工作基于Blelloch等前人的学术成果，但采用了更系统、可维护的实现方案。

## 17. .env 错在哪里

- 英文标题: Where .env Went Wrong

文章指出，.env 从一个只需几条 export 命令的便捷机制，演变成了项目的配置模式、秘密存储、环境模型和部署格式，但环境变量本身只负责向进程传字符串，无法表达值是否必需、是否秘密、类型、作用域等关键信息，导致需求只能散落在验证代码、README 或团队成员记忆中。.env 的解析器也缺乏统一规范，不同工具在变量展开、引号注释、优先级和加载时序上各有偏差，让同名配置在不同环境下产生不同结果。此外，.gitignore 并不能带来加密、访问控制、审计或撤销能力，秘密以明文存在本机反而扩大泄露面。作者建议让 .env 回归“本地普通设置”的小工具角色，并引入 SecretSpec：用可提交的 secretspec.toml 声明应用所需的秘密及其描述、默认值，通过 provider 管理实际值，用 SDK 直接解析，从而避免秘密进入全局环境变量；支持 scopes、临时文件，并能用 secretspec init --from dotenv:.env 从现有 .env 渐进迁移。核心是把声明、存储、交付三件事拆开。

## 22. 关联随机数生成器：问题与解法

- 原始链接: <https://knivesforcats.online/correlated-rng/>
- 英文标题: Correlated RNG

文章讨论游戏开发中程序化生成使用随机数生成器（RNG）时遇到的“关联RNG”问题。若整个项目共享一个RNG，各系统输出会相互干扰，例如新增一次道具抽取会改变后续地图生成结果。常见的多RNG方案虽然让各系统独立，但若都用同一初始种子，则所有生成器会产生相同序列，玩家可通过一个系统的结果推断另一系统的随机选择，破坏游戏体验或产生可被利用的规律。作者列举了三种解决方案：一是给每个生成器设不同偏移量，这仅是掩盖问题，且偏移量需足够大、部分RNG不支持跳转，较麻烦；二是用专用RNG为其他生成器生成种子，有效但依赖创建顺序，移除一个生成器会影响后续所有生成器；三是基于哈希的种子，将共享种子与每个RNG的唯一标识符一起哈希，得到完全独立且可复现的序列，作者认为这是最佳方案。文章更新提到，Slay the Spire 2开发者几乎用了相同方法，但其问题在于C#的System.Random对线性递增种子会产生相关输出，改用xoshiro256**异或移位算法可解决。作者个人使用Squirrel3算法，因其简单、可序列化、支持快速跳转且保证不重复。总之，核心在于避免相同种子序列，哈希标识符是高效且彻底的解决方式。

## 23. ST推出Rust传感器驱动：安全性、实用性与社区驱动

- 原始链接: <https://blog.st.com/rust-mems-drivers/>
- 英文标题: ST Rust drivers

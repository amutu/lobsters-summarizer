## 1. 钓鱼攻击之殇：错不在用户，也不在DNS

- 原始链接: <https://maurycyz.com/misc/domains/>
- 英文标题: A rant about phishing: It's not the user's fault (and not DNS either)

本文以一次情绪化的技术吐槽，指出当前钓鱼攻击频发的根源并非用户缺乏安全意识，也非DNS机制缺陷，而是组织自身在登录与链接设计上「主动制造了与钓鱼网站无法区分的体验」。作者举例说明，许多企业的登录流程会经过多个第三方域名跳转（如认证服务、OAuth、2FA等），用户名、密码和验证码输入框均不在企业自有域名下，再叠加token过期后弹出的随机认证窗口，用户已无法分辨真假。作者进一步指出URL结构对非技术用户极不友好——最重要的二级域名位于URL中部，而协议、路径等部分阅读方向相反，仅靠「别点可疑链接」的提醒毫无意义。因此作者以RFC 2119的强制语气提出：组织必须使用单一可识别的根域名，内部服务必须置于其子域名下，严禁使用形如「公司名-auth.com」或「他人域名/公司名」的URL；邮件和短信中的链接也必须落在可识别域名下，必要时用本地重定向；联系电话同样不得直接写入消息，须通过网页提供。作者强调，DNS作为四十余年未变的层级体系本身清晰可靠，问题在于合法站点刻意让自己与钓鱼页面外观一致，这才是用户被骗的真正原因。

## 2. Xteink X4 Pro 电子阅读器评测

- 原始链接: <https://abstractnonsense.xyz/microblog/2026-09-07-xteink-x4-pro-review/>
- 英文标题: Xteink X4 Pro review

本文评测了 Xteink X4 Pro 电子阅读器，这是一款通过 MagSafe 吸附在手机背面的 E Ink 阅读设备。硬件方面，触摸屏响应灵敏、前光灯支持亮度与色温精细调节、翻页按钮单手操作便捷、机身极轻可长时间握持，E Ink 屏幕仅在翻页时耗电，续航极为持久；不足之处是分辨率偏低导致字体略显粗糙，且缺少 USB-C 接口，需搭配一个做工一般的 pogo-pin 转接头，作者认为这是唯一槽点。固件方面，原生系统体验一般，但设备已解锁，可通过浏览器 Web Serial API 轻松刷入 CrossPoint 固件，后者拥有活跃的插件生态。设备基于 ESP32 芯片，仅用几百 KB 内存即可运行，体现了嵌入式计算的精巧。得益于 WiFi 支持，传书方式丰富，包括 USB-C、局域网、WiFi 热点及 Calibre 插件，甚至可对接 Libby 借阅图书馆 DRM 电子书。作者最终表示，若设备损坏会毫不犹豫地再买一台，整体体验令人满意。

## 3. 「挪威问题」并非YAML规范之过

- 原始链接: <https://slugcat.systems/post/26-09-10-yaml-spec/>
- 英文标题: It's not the YAML spec's fault, but

作者针对网络上反复批评YAML「挪威问题」（即「no」被隐式解析为布尔false而非字符串）的文章，进行了深入考证。他首先分享自身经验：在Space Station 14项目中，团队始终自行编写反序列化逻辑，按字段模型解析YAML节点，从而完全规避了隐式类型歧义。随后他逐条查阅YAML 1.0、1.1、1.2规范，发现规范对隐式类型解析的措辞均为「may」和「取决于应用」，1.2的Core Schema更已移除yes/no布尔值，因此「挪威问题」并非规范强制行为。为追溯设计意图，作者用脚本爬取了SourceForge上YAML早期邮件列表数千封邮件，还原了隐式类型规则从「强类型默认」到「默认全部当字符串」的演变过程，确认规范作者本意是「默认字符串、类型由加载器决定」。作者最终结论：问题出在PyYAML等库将不安全加载设为默认选项，属于实现层面的设计缺陷，而非规范本身；动态语言中「对象序列化/反序列化」的固有难题才是更深层原因。此外，作者还解释了YAML规范之所以庞杂，源于其诞生于XML热潮期、试图覆盖XML全部用例的野心，而多数雄心勃勃的子项目最终并未落地。

## 4. Bevy 六周年：AI 政策如何撕裂社区

- 原始链接: <https://blog.fallible.net/it-breaks-a-village/>
- 英文标题: It Breaks a Village: Bevy's 6th Birthday

Bevy 核心贡献者在引擎六周年之际发表长文，反思社区因 AI/LLM 政策变化而陷入的信任危机。文章指出，0.19 版本带来 BSN 宏合并、UI 可用等技术突破，但新「AI 政策」的制定过程——先在小圈子内决定、再开放有限讨论、反对意见被边缘化——严重损害了社区凝聚力。作者认为，游戏引擎作为创意工具，其社区文化与 LLM 推手的浅层参与存在根本冲突；Showcase 频道被低质量 AI 项目占据，批评性表达被规则压制，原有成员感到不被倾听而流失。作者以「纳粹酒吧问题」类比，描述敌对行为如何逐步将社区规范扭转为自身标准，并强调 AI 推手背后有巨额资本与机构支持，并非弱势群体。文章还指出公众对 AI 产出的普遍不信任，以及将复杂创作简化为「输入-输出」的思维对社区成员的贬损。作者坦言已无法继续贡献，但仍希望 Bevy 能恢复为可信赖的协作空间。

## 5. 通过浏览器启动构建产物来审查 Pull Request

- 原始链接: <https://fzakaria.com/2026/09/09/review-a-pull-request-by-booting-it>
- 英文标题: Review a pull request by booting it

本文介绍了 trynix-preview，一个 GitHub Action，它能在 Pull Request 上自动评论一个链接，审查者点击后即可在浏览器中启动该 PR 的构建产物，无需克隆仓库、无需本地构建，也无需服务器、SSH、Docker 或虚拟机。其底层依赖 trynix.dev，可在浏览器中启动任意 /nix/store 路径。作者以 sqlelf 项目的 PR#31 为示例，展示了一个来自 fork 的 PR 如何在浏览器中启动带 sqlelf 的 Linux 环境。配置上，只需在 workflow 中加入几行 YAML：先用 Cachix 等缓存服务构建并推送产物，再调用 trynix action 指定缓存地址、公钥和要启动的 attr 路径。action 本身不执行构建，仅通过 nix eval 获取 store 路径并将缓存信息交给浏览器。安全方面，因 workflow 运行在默认分支上、fork 无法篡改构建流程，但需开启 allow-unsafe-pr-checkout，作者建议使用独立私有缓存隔离 PR 构建。性能是当前主要短板：大二进制文件启动仍需 1–2 分钟，作者已提供基准测试页面（trynix.dev/bench/），目前该方案更适合中小规模二进制。作者认为尽管尚未颠覆 CI 产品，但这一工作流充分展现了 Nix 生态的潜力。

## 6. Git 之后是什么：ERSC 的下一代版本控制构想

- 原始链接: <https://ersc.io/blog/what-comes-after-git>
- 英文标题: What comes after git

East River Source Control（ERSC）分享了其对版本控制未来的思考。文章指出，AI agent 的兴起使代码产出速度、仓库规模、分支数量和合并冲突急剧增加，将过去仅大型组织面临的问题带给所有团队，对现有版本控制系统构成巨大压力。ERSC 认为 Git 虽服务开发者多年，但其设计基于 2005 年 Linux 内核的约束，难以满足当今及未来企业级需求，且深度嵌入工具链使其难以被替代。ERSC 的解决方案是：客户端仍使用标准 Git 协议，服务端则采用自定义的非 Git 存储引擎，实现水平扩展且各部署相互隔离，兼顾可靠性与可控性。为渐进式过渡，他们计划未来支持 Jujutsu（jj）的原生协议，使开发者可按自身节奏逐步迁移，而服务端对 Git 协议用户透明无感。产品理念上，ERSC 不做一体化 forge，而是提供可组合的构建块，存储层先行，后续将覆盖代码审查、CI、issue 追踪等环节，同时兼容用户自有工具链。目前产品尚未发布，团队将在 JJ Con 上进一步交流。

## 7. 我的 HTML 基础模板

- 原始链接: <https://vale.rocks/posts/html-boilerplate>
- 英文标题: My HTML Boilerplate

作者回顾 HTML 从早期极简文档到 HTML 2.0 正式标准结构的演变，指出「不要破坏网页」的兼容性原则催生了大量跨站点重复的 boilerplate 代码。文章核心是作者公开并逐段解析自己维护的 HTML boilerplate 模板，涵盖 doctype 声明、lang 属性、UTF-8 编码、viewport 设置、text-scale 文本缩放、页面标题、样式表引入、WOFF2 字体预加载、Open Graph 社交嵌入元数据（og:title、og:description、og:image 等）、favicon（采用 SVG 格式）、canonical 链接、color-scheme 与 theme-color 明暗主题适配、RSS 与 JSON Feed 自动发现、OpenSearch 搜索集成、PWA manifest 声明，以及 header/main/footer 的 body 骨架结构。作者强调 head 中元素顺序对性能有显著影响，推荐用 Capo.js 工具评估。关键观点包括：viewport 无需添加 initial-scale，minimum-scale、maximum-scale、user-scalable 严重损害可访问性应尽量避免；og:image 推荐 1200×630 的 WebP 格式；color-scheme 声明可防止暗色模式下的 FOUC。作者指出该模板仅为通用基础，学术引用、文章、音视频等不同内容类型需追加相应元数据，并推荐 Manuel Matuzović 的 2026 版 HTML boilerplate 文章作为扩展参考。

## 10. Windows 11 记事本菜单栏的诸多回归缺陷

- 英文标题: The terrible menu bar in the Windows 11 Notepad

作者抱怨 Windows 11 新版记事本的菜单栏相比旧版 Win32 记事本存在大量功能退化。主要问题包括：无法按住鼠标左键在展开的菜单中移动并释放以选择项目（作者最常用的操作方式）；无法按住鼠标在顶层菜单项间切换；左右方向键导航时会在含子菜单的项上卡住；F10 聚焦菜单栏快捷键完全无效；访问键（access keys）改用新样式显示，且用方向键导航时消失；菜单栏项异常响应右键点击，多次操作后禁用项竟变为启用。作者指出，这些问题并非记事本独有，WinUI 3 组件库中的 MenuBar 控件同样存在。相关缺陷早在 2019 年（WinUI 2 时期）即被报告，五年后却被以「功能请求」而非 bug 为由关闭，而实际上这是相对于 Win32 菜单的明确回归。作者提到自己二十多年前在自有软件中实现菜单工具栏时，上述交互均已正常工作，感叹 2026 年的微软竟难以解决这些基础问题。文章语气带有明显不满，但问题描述具体且有视频佐证。

## 11. JJ 使用手记：与 Git 并行半年的得与失

- 原始链接: <https://laurmaedje.github.io/posts/jj/>
- 英文标题: Conversations with JJ

作者分享了自己使用版本控制工具 jj 约半年的体验。他并未完全弃用 Git，而是将 jj 作为 PR 历史清理的辅助工具与 Git 并行使用。他欣赏 jj 的几点：编辑提交历史非常流畅（配合 jjui 图形工具）、拥有更细粒度的命令（如 jj split）、强大的撤销功能，以及整体友好的 CLI 交互。但 jj 也带来若干困扰：在大型仓库中 jj log 输出冗杂、在 Git 与 jj 间切换时容易进入 detached HEAD 状态、自动快照机制可能意外将 node_modules 等目录写入历史、以及「相同变更合并」行为在撤销后仍会吞掉变更，他最终通过配置 same-change 为 keep 来规避。作者坦言，阻碍他全面转向 jj 的最大原因是缺乏一个精美的原生 GUI 来查看和拆分 diff——他习惯反复阅读 diff 以发现重构机会和潜在 bug，而终端中的 git diff 输出远不能满足这一需求。他总结道，若能出现一个体验优秀的 jj 图形客户端，他愿意付费。

## 13. 糟糕氛围下的编程：对生成式AI的悲愤与反思

本文是作者对生成式AI在编程与开发领域应用的强烈批评，情绪从愤怒转为悲伤。作者认为AI在环境（数据中心过度扩张）、版权（长期抄袭与侵权）、伦理（模型被少数巨头控制）等多层面均造成严重伤害，且「民主化」的说法完全站不住脚——真正的民主化是开放工具、教育激励与分发平台，而非依赖OpenAI、Anthropic、Google等公司。文章以Playdate游戏开发社区为例，指出部分开发者用AI生成代码来「提高效率」，作者认为这终将导致平台充斥低质内容、独立开发者被挤压，重蹈iOS应用商店和Steam的覆辙。作者驳斥了「AI只是像代码补全」「只是处理繁琐部分」等辩护，强调LLM在云端运行是最低效的方案，且不可靠系统无法验证可靠性。文章最核心的情感落点在于：编程过程本身的价值不可替代——亲手写出一个弹球程序并一次运行成功，那种「我确实学会了」的纯粹满足感，是AI代劳无法给予的。作者最终感叹：这一切本不必发生，我们完全可以选择不用。

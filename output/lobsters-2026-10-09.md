## 1. 托举互联网的人：关键开源项目背后的少数维护者

- 原始链接: <https://sheets.works/data-viz/holding-up-the-internet>
- 英文标题: The people holding up the internet

本文下载了23个关键开源项目的完整提交历史，统计2025至2026年间每位贡献者的修改次数，揭示了一个令人不安的事实：23个项目中11个由一到两人承担日常维护。这些项目涵盖时区数据库（Paul Eggert一人维护，服务超40亿部手机）、xz压缩工具（Lasse Collin，2024年遭匿名者Jia Tan植入后门）、core-js（Denis Pushkarev，曾因交通事故入狱）、sudo（Todd Miller，十年间5409次修改中5408次出自他手）、SQLite（仅4人团队，使用量超万亿）、zlib（Mark Adler，无公开资助）等。文章还对比了资金注入与安全事件的关系：OpenSSL在Heartbleed后迅速获540万美元，而xz后门事件后未见类似跟进。德国主权技术机构、Alpha-Omega基金等虽资助了部分项目，但时区数据库、SQLite、zlib等核心组件仍无公开资助。文章结论指出，现代数字基础设施高度依赖少数无偿或低薪个体维护者，其脆弱性触目惊心。

## 2. 我成功从 Google 索引中移除了自己的网站

- 原始链接: <https://kennyqin.com/deindexed-by-google/>
- 英文标题: I've Been Deindexed by Google

作者于2026年10月分享了自己将博客从 Google 搜索索引中彻底移除的经历。起因是 AI 爬虫对互联网的无节制抓取令其不堪其扰，尽管公开可访问的页面无法完全阻止抓取，但作者希望至少让搜索引擎不再收录。整个过程历经数月、分多步完成：第一步，在 robots.txt 中设置全局 Disallow 规则，但数周后检查发现无效；第二步，在页面中添加 noindex、nofollow 的 meta 标签，却忽略了关键一点——必须允许执行去索引操作的爬虫（如 Googlebot）访问页面，它才能读到该 meta 标签；第三步，调整 robots.txt，对 Googlebot 单独设置 Allow，对其余爬虫保持 Disallow，并对其他常见爬虫逐一做同样处理，一旦确认某爬虫已不再收录便将其从规则中移除。经过至少三个月的等待与反复检查，作者确认网站已完全脱离 Google 索引，对此表示庆祝。文章以「#degoogle」为标签，反映了当前创作者对 AI 抓取与搜索引擎依赖的普遍焦虑，也提醒读者：去索引操作本身需要让爬虫能访问到指令，否则规则形同虚设。

## 4. Rust 错误处理中缺失的一环：用错误集实现精确与便捷的统一

- 原始链接: <https://mcmah309.github.io/posts/the-missing-piece-in-rust-error-handling/>
- 英文标题: The Missing Piece in Rust Error Handling

文章指出 Rust 错误处理的核心矛盾：精确的 enum 错误类型需要大量样板代码，而 anyhow 等不透明类型则隐藏了可能的错误种类，编译器无法追踪是否已处理所有分支。作者 Dillon McMahon 提出 eros 库，以「错误集」概念解决这一问题：用元组（如 (io::Error, ParseIntError)）直接描述函数可能返回的错误类型，无需声明新 enum。eros::Result 是 Result<T, ErrorUnion<E>> 的别名，.union() 将普通 Result 错误纳入集合，.widen() 在组合多个函数时自动扩展错误集，.recover() 处理特定错误后将其从返回类型中移除，使签名精确反映恢复后仍可能发生的错误。不指定元组时退化为 AnyError，兼顾传播场景。此外，eros 提供 #[context] 宏和 .context() 方法，让错误在传递过程中携带操作路径信息，最终报告时按层级列出上下文。文章还类比了 Zig 的 error sets 机制，指出 Rust 版本的优势在于可携带实际数据载荷。结论是 Rust 现有的 Result、? 传播和值语义已接近完备，缺少的只是让错误类型像函数一样自由组合与缩减的构造，eros 正是补上这一环。

## 6. 超越「&」：让 Rust 智能指针获得与内置引用同等的灵活性

- 原始链接: <https://lwn.net/SubscriberLink/1096028/7524dbcae1be7205/>
- 英文标题: Beyond the &

RustConf 2026 上，Rust 语言团队负责人 Tyler Mandry 介绍了名为「Beyond the &」的项目。该项目旨在解决用户自定义智能指针（如 MutexGuard）无法像内置引用（&、&mut）那样灵活使用的问题。文章以一个带缓存的页面渲染函数为例：使用 &mut 时借用检查器能区分结构体不同字段的独立访问，但引入 Mutex 后，借用检查器只能看到不透明的 MutexGuard 访问，导致编译失败。语言团队基于 Nadrieril 和 Benno Lossin 的工作，提出将编译器内部的「place」（类似 C 的左值）概念暴露给用户代码，为每种智能指针创建对应的 handle 类型，并通过 WritePlace、ReadPlace、ProjectPlace、BorrowPlace、VariantPlace 等新 trait 让借用检查器理解智能指针的读写、字段投影和借用语义。该设计使内置引用行为也可用同一机制描述，并支持在智能指针后直接进行模式匹配。目前设计仍为原型阶段，错误诊断、语法选择（如是否用 @ 替代 &）及枚举支持等问题尚待完善。Mandry 邀请社区审阅设计文档并补充边界用例，期望该机制能让库作者将自定义抽象更深地融入语言，降低 Rust 的学习曲线。

## 8. specialArgs 有害论：NixOS 模块参数注入的陷阱与替代方案

- 原始链接: <https://ysun.co/special/>
- 英文标题: `specialArgs` considered harmful

本文作者（NixCon 2026 闪电演讲的书面补充）指出，NixOS 配置中普遍通过 specialArgs 将 inputs 等值注入模块评估上下文，但随着配置仓库规模增长，specialArgs 还被塞入辅助函数、静态数据等，导致模块无法跨项目复用。核心问题是不可移植性：模块在函数签名中声明 inputs 参数后，若下游调用者未通过 specialArgs 提供该值，评估即报错。作者提出「柯里化模块」方案：将模块写成两层 lambda，外层接收特殊参数，内层接收标准模块参数，在 lib.evalModules 消费前完成参数注入。具体实现包括直接柯里化、lib.modules.importApply（保留文件位置以改善报错信息），以及作者自研的 importApplyWithArgs（自动扫描模块目录、按参数模式匹配注入，对普通模块透明）。文章还讨论了模块去重机制：路径导入以路径为 key 可安全去重，而柯里化后的匿名模块需手动指定 key，否则同一文件导入两次会被视为两个模块。最后补充了 _module.args 替代方案的局限：在 imports 中引用 config 会导致无限递归，且多模块设置相同 _module.args.inputs 会因 lazyAttrsOf raw 类型产生冲突。

## 9. Hetzner Cloud 网络栈的演进历史与技术架构

- 原始链接: <https://www.hetzner.com/blog/the-hetzner-cloud-network-stack-history-and-technical-overview/>
- 英文标题: The history of the Hetzner Cloud network stack

本文是 Hetzner 工程团队系列文章的第一篇，系统回顾了 Hetzner Cloud 网络栈从 2011 年至今的演进历程，并详细介绍了当前基于 Open vSwitch（OVS）的数据面架构。Hetzner 一贯坚持「将网络功能放在主机侧而非物理网络」的设计理念，以获得更高的灵活性和故障隔离能力。历史上，其网络方案经历了三个阶段：2011 年 vServer 采用 Linux 网桥与静态路由；2015 年转向 Ceph 超融合架构并引入 BGP 动态路由和 1:1 NAT；2018 年 Hetzner Cloud 上线后取消 NAT 改为直接 IPv4 路由，2019 年引入 OVS 并支持基于 VXLAN 的私有网络，2021 年推出基于 OVS 流表和 netfilter 的有状态云防火墙。在 OVS 编排层面，Hetzner 未采用 OVN，而是自研了名为「Flusskrebs」（意为「流蟹」）的 Python 控制器，通过 REST API 为每台虚拟机和负载均衡器配置 OpenFlow 流规则，同时充当私有网络的集中式 DHCP 服务器。每台 VM 主机还运行本地 DHCP、metadata 服务（169.254.169.254）以及内部监控组件。有状态防火墙依赖 Linux netfilter 连接跟踪，并通过内部项目 ctcount 将每服务器并发连接数限制在 8 万条。目前该 OVS 数据面已支撑超过一百万台云服务器，但团队正着手构建更专用、更易扩展的新一代网络栈，以支持私有网络 IPv6 等新特性，后续文章将详细介绍。

## 12. 读多写少工作负载中 RwLock 的性能开销

- 原始链接: <https://pranitha.dev/posts/rwlock-vs-lockfree/>
- 英文标题: The Performance Cost of RwLock in Our Read-Heavy Workload

本文以一个读多写少的实际服务为例，对比了 RwLock 与无锁原子指针（Crossbeam Atomic）在高频遍历场景下的性能差异。数据模型中，读请求需遍历含 16,384 个元素的 Block 并做聚合计算，单写线程以 500 次/秒更新。基准测试显示，RwLock 读吞吐仅 15.93k reads/s，Crossbeam 方案达 229.07k reads/s，p50 延迟从 441µs 降至 22µs。关键发现是：关闭写者后 RwLock 性能几乎不变，说明瓶颈并非读写竞争，而是每次遍历中 16,384 次读锁获取与释放带来的原子操作开销（每秒约 5.24 亿次 CAS 与原子减）。Crossbeam 方案通过在整个 Block 遍历开始时 pin 一次 epoch，将每个元素的同步降为一次原子指针加载，大幅削减开销。文章还讨论了 ArcSwap（仍有逐元素开销）、left-right（内存翻倍）等替代方案，并指出对低频插入的 Block 本身用 RwLock 包裹即可满足需求。结论强调：无锁并非万能，同步点的位置与频率同样决定性能。

## 13. DNS根密钥轮换进展更新（2026年10月）

- 原始链接: <https://ispcol.potaroo.net/2026-10/kskroll.html>
- 英文标题: Rolling the Root Key (Update)

APNIC首席科学家Geoff Huston发布此文，更新DNS根密钥（KSK）轮换的最新状态。根密钥无父密钥，新KSK由旧KSK签名认证，需经历30天「hold-down」期供验证型解析器自动加载。2026年10月11日将完成KSK-2024（2024年生成）的正式轮换，仅更换密钥对而非算法。文章介绍两种测量手段：RFC 8145通过在查询中嵌入信任密钥标签供根服务器观测；RFC 8509「Root Key Trust Anchor Sentinel」则通过特定查询名让解析器返回SERVFAIL或正常应答，从而判断其是否已加载新密钥。APNIC利用广告式测量系统每日发起约1600万次测试，结果显示约70%的测试点支持RFC 8509并确认已加载KSK-2024，但仍有相当比例未加载。RIPE Atlas小规模测试（2900个AS）中失败率约3.7%。文章重点列出了50个KSK-2024接受率最低的ISP网络，涵盖菲律宾Globe Telecom、印度Reliance Jio、伊拉克HulumTele、荷兰Vodafone Libertel等，建议相关运营商尽快核查DNS解析器配置，以免密钥轮换后出现解析故障。

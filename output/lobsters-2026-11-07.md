## 1. 让 musl 与 NVIDIA 专有驱动协同工作

- 原始链接: <https://chimera-linux.org/news/2026/11/musl-nvidia.html>
- 英文标题: Making musl and proprietary NVIDIA drivers work together

本文记录了作者在基于 musl libc 的 Linux 发行版上运行 NVIDIA 专有 GPU 驱动的技术探索。由于 NVIDIA 驱动针对 glibc 编译，musl 发行版无法直接使用。文章按 GPU 代数梳理了现状：RTX 2000 及以上可用开源驱动但性能损失 40-80%；GTX 700 至 GTX 1000 系列必须依赖专有驱动；更老的卡可能完全无法使用。解决路径涉及多重技术难点：需先切换到 GLVND 架构；借助 gcompat 兼容层（须用最新 Git 版本）补齐 glibc 符号；用 patchelf 清理驱动库中的 glibc 依赖并注入 gcompat；处理 musl 不支持的 ifunc 重定位（类型 37），从 Alpaquita Linux 的 musl-perf 项目移植补丁；解决 NVIDIA 驱动采用的 STATIC_TLS/initial-exec 线程局部存储模型与 musl 动态加载机制的冲突，通过补丁动态链接器在 dlopen 时预留静态 TLS 空间；最后处理 glibc 特有的静态递归互斥锁初始化器，通过 shim 库模拟其内存布局。目前 580 与 620 分支的 pull request 已提交，支持 x86_64 和 aarch64，作者以 GTX 980 Ti 完成了初步测试。

## 2. Go 测试中的 MustCreate 泛型模式

- 原始链接: <https://mtlynch.io/notes/go-must-create-pattern/>
- 英文标题: The MustCreate Pattern for Go Tests

本文介绍了 Go 测试中一种名为 MustCreate 的辅助模式，旨在消除测试代码中冗余的 error 检查。问题背景是：当测试需要调用可能返回 error 的构造函数（如 NewUsername）时，即使测试者确信输入合法，仍须编写 if err != nil 等样板代码，使测试冗长且可读性差。作者早期的做法是为每个类型单独编写 MustCreateXxx 辅助函数，将 error 检查封装其中，但该方案扩展性差，代码库中会充斥着大量 MustCreateFoo、MustCreateBar 等函数。Go 1.18 引入泛型后，作者意识到可用一个通用泛型函数 MustCreate[RawInput, CreatedValue] 统一解决所有类型的问题：该函数接收 testing.TB、构造函数和原始输入，内部调用构造函数并在出错时调用 t.Fatalf，测试调用形如 testutil.MustCreate(t, NewUsername, 「joe123」)。对于多参数构造函数，作者还扩展了 MustCreate2 等变体，增加对应泛型参数即可。作者总结称，该模式虽不具革命性，但切实提升了测试可读性，减少了开发中的无意义重复劳动。

## 4. NetBSD 11.0 升级至 11.1 实战记录

- 原始链接: <https://www.dwarmstrong.org/netbsd-upgrade/>
- 英文标题: Upgrading NetBSD from 11.0 to 11.1

作者记录了首次将 NetBSD amd64 系统从 11.0 原地升级至 11.1 的完整过程。NetBSD 官方指南提供两种升级方式：通过安装介质启动并使用 sysinst(8)，或使用 sysupgrade(8) 进行原地升级。作者认为主版本跨越（如 10.1 到 11.1）推荐 sysinst，小版本升级则用 sysupgrade 更便捷，因此选择了后者。具体步骤为：先执行 pkgin update 并安装 sysupgrade 包，再运行 sysupgrade auto 命令指定 11.1 的 CDN 地址，系统自动下载内核与 sets、解包后提示用户审查并合并配置变更。作者对 NetBSD 展示新旧文件 diff 及合并差异的处理方式表示满意，仅 passwd 和 sshd_config 等少数文件需手动编辑。升级过程中遇到一个 postinstall 检查失败（opensslcertsrehash），解决方法是删除 /etc/openssl/certs/ 下的旧缓存，用 certctl rehash 重新生成证书哈希，再通过 sysupgrade postinstall fix 确认修复。此外还需手动编辑 /usr/pkg/etc/pkgin/repositories.conf，将 pkgin 指向 11.1 的软件仓库。最终重启后升级顺利完成，作者对整体体验表示满意。

## 5. Clojure 核心概念精要

- 原始链接: <https://yogthos.net/ClojureDistilled.html>
- 英文标题: Clojure Distilled

本文是Clojure语言的核心概念入门指南。作者指出，学习Clojure的难点并非其极简的Lisp语法，而在于掌握函数式编程的全新思维方式。文章从三大优势展开：不可变性使开发者无需手动管理数据引用，纯函数天然具备引用透明性，便于隔离推理；逻辑与数据分离让函数成为核心可复用组件，通过组合高阶函数即可声明式地解决复杂问题；不可变数据结构与纯函数特性使并行计算和并发编程更为安全，Clojure的STM机制进一步简化了共享状态管理。在实践部分，文章依次介绍了Clojure的数据类型（列表、向量、映射、集合）、特殊形式、前缀表示法的函数调用、匿名函数与命名函数（defn）、高阶函数（map、filter）及闭包等核心语法，并以地址格式化等实例展示如何仅通过组合标准库函数完成数据转换，无需显式循环或递归。文章强调「代码即数据」的元编程特性，以及Clojure标准库的丰富性使多数问题可通过函数组合优雅解决，鼓励读者将数据变换映射到对应函数上，以声明式风格编写简洁、可测试、可并行的代码。

## 6. Futhark 语言中的非确定性

- 原始链接: <https://futhark-lang.org/blog/2026-11-04-nondeterminism.html>
- 英文标题: Nondeterminism in Futhark

作者在参加 IFL2026 会议后，受 Michael Haddon 关于浮点可复现性类型系统「The Replay Lattice」的启发，系统分析了 Futhark 这一纯函数数据并行语言中实际存在的非确定性。文章借用 Haddon 的三级分类：Exact（每次结果完全一致）、Replay（同一调度下可复现）、Approx（可能不同），指出 Futhark 的非确定性并非传统并发竞态，而主要源于浮点舍入误差。语言层面存在三处隐患：使用 #[unsafe] 属性绕过安全检查；scatter 构造要求索引无重复但不做动态校验，违反后写入结果不可预测；reduce 要求操作符满足结合律但无法静态检查，新程序员常误用非结合操作符。在浮点求和场景中，C 后端按左到右顺序执行，GPU 后端则按硬件拓扑分块并行，导致跨机器结果不同（Replay 级）。作者展示了用树形归约可实现 Exact 级确定性，但在 MI100 GPU 上比内置 reduce 慢近 3 倍；scan 和 reduce_by_index 的确定性替代方案性能差距更大。文章最后提出设想：编写一个以确定性实现替换所有 SOAC 的 Futhark 库，并评估其性能代价，留待后续讨论。

## 7. getaddrinfo 的极限：IPv4 地址解析的 Unicode 绕过与感知欺骗

- 原始链接: <https://acid.vegas/blog/pushing-the-limits-with-getaddrinfo/>
- 英文标题: Pushing the Limits with getaddrinfo

本文系统展示了 glibc 中 getaddrinfo() 解析 IPv4 地址时的多种绕过手法。核心原理：IPv4 地址本质是 32 位整数，inet_aton() 接受十进制、十六进制、八进制、混合进制及不同分段形式；当调用者传入 AI_IDN 标志时，glibc 先经 libidn2 执行 UTS #46 映射，将全角数字、上/下标、圈号数字、LCD 段码、数学粗体、罗马数字、修饰字母等 Unicode 字符折叠为 ASCII，再交给数值解析器，因此「⁰𝑋⁴5．🯰３₆。⁵₂₈𝟲🯶」等看似乱码的字符串可被解析为 69.30.206.130。UTS #46 的 ignored 类还允许插入软连字符、零宽空格等不可见字符而不影响解析。作者进一步演示了 URL 感知欺骗：利用 user:pass@ 前缀与路径后缀将真实主机（如 0xcdb97a5a）伪装成可信域名，以及 wget 将整数当作位置参数、URL 当作选项值的混淆。所有示例均在 Ubuntu 24.04 / glibc 2.39 上实测通过 ping 和 curl。文章指出，SSRF 过滤器、黑名单、日志检索等基于正则或字符串比较的防护均易被绕过，2022 年 Emotet 邮件已使用十六进制/八进制 IP 规避模式匹配。防御建议：永远先调用解析器获取实际地址，再对该地址做判断，切勿对原始字符串做匹配。

## 8. X-87：256字节DOS程序化图形

- 原始链接: <https://www.onirom.fr/wiki/codegolf/x-87/>
- 英文标题: X-87 - DOS 256 bytes

本文介绍了一个仅256字节的x86/x87（386+）DOS实模式程序，在VESA 2模式（640×400、32bpp）下用振荡器算法绘制风格化荒凉景观。项目始于2021年的p5.js草图，2024年重启，2025年正式着手压缩。开发路径为：p5.js→Gforth（利用x87栈式架构与Forth的天然契合）→约320字节灰度DOS移植→多轮优化→最终256字节。关键优化包括：重叠/截断浮点常量、打包颜色增量、减少FPU指令、将两个主循环合并为单循环并用ECX高低半部分别作帧计数器与振荡器索引，同时避免fcomi以兼容386。兼容性修复涉及fninit缺失、未初始化内存、段初始化及VESA分页/银行切换等问题，最终在Bochs+Freedos（10 MIPS）下亦能运行。性能方面，DOSBox默认3000 cycles渲染约13分钟，20000 cycles约2分30秒；Bochs 10 MIPS约6分10秒。作者对最终效果满意，认为接近原型，但质疑32bpp是否必要，推测256色或可更小实现；图像可缩放至任意分辨率，但中等分辨率下收敛更快、伪影更少。

## 9. Datadog 如何用 FETCh 在生产环境持续验证形式化规格

- 原始链接: <https://www.datadoghq.com/blog/engineering/continuous-formal-spec-validation/>
- 英文标题: How we continuously validate formal specifications in production

Datadog 工程师 Nicolas Couvrat 介绍了 FETCh（Formal Execution Trace Checker）系统，用于将 TLA+ 形式化规格持续转化为 Rust 运行时监控器，在生产环境中检测系统行为与规格之间的偏差。背景是 Datadog 事件数据库 Husky 的路由系统虽已有形式化模型，但随代码演进，一处 placement 逻辑变更使冲突 placement 在生产中存续约一年，传统测试未能发现。文章指出，可观测规格（描述「什么可以发生」）与可模型检查规格（需有界输入）之间存在固有矛盾，仅验证不变量不足以证明规格仍有效。FETCh 借助 TLA+ 的 refinement 机制，用可观测规格 A 描述真实行为，用可模型检查规格 B 精化 A，从而在单一形式化基础上同时支持模型检查、运行时验证与定理证明。针对 Husky 路由系统，团队将验证拆分为 Router.tla 与 PlacementStorage.tla 两个抽象规格，并将事件级状态下沉到各 sidecar 进程，避免在万亿级事件规模下维护全局状态。最终 FETCh 成功定位了常规测试无法暴露的微妙缺陷，验证了「规格即活文档」的持续对齐思路。

## 10. Linux 树外安全缓解措施实践指南

- 原始链接: <https://clehaxze.tw/gemlog/2026/11-04-practical-guide-on-out-of-tree-mitigations-on-linux.gmi>
- 英文标题: Practical guide on out of tree mitigations on Linux

本文以 systemd 为服务管理基础，按实施难度与防护效果之比，系统介绍了 Linux 上多种「树外」安全缓解措施。核心原则是「最小权限、最大干扰」：假设程序已被攻破，从外部限制其能触达的资源。文章依次覆盖：（1）硬化分配器（hardened_malloc、mimalloc、scudo），通过 LD_PRELOAD 替换默认分配器，使堆溢出和 use-after-free 在 free() 时即崩溃，是作者认为最重要的单一措施；（2）禁止系统调用，利用 SystemCallFilter 屏蔽 fork、execve、io_uring、bpf 等，阻止攻击者生成 shell 或安装后门；（3）禁止/正向列出文件路径，用 ProtectSystem、PrivateTmp、NoExecPaths/ExecPaths 等将进程可读写范围缩至最小；（4）按用户设置 iptables 防火墙规则，限制应用仅能访问本地回环地址；（5）其他 systemd 安全标志，如 NoNewPrivileges 防止提权、MemoryDenyWriteExecute 禁止内存同时可写可执行（但 JIT 语言如 Node.js、.NET、Java 等不适用）。文章强调安全是多层防御，不同攻击面（缓冲区溢出、认证缺失、路径遍历等）需不同缓解手段配合，并给出了大量可直接套用的配置示例。

## 11. 寻找 Bug 是否有害？——测试研究在 AI 时代的反思

- 原始链接: <https://alperenkeles.com/posts/bug-finding-considered-harmful/>
- 英文标题: Bug Finding Considered Harmful?

作者是一名从事基于属性测试（PBT）的研究者，在开发新 PBT 工具期间提出一个尖锐问题：在 AI 时代，大规模 bug 发现是否反而有害？文章首先回顾 PBT 的核心思想——用「属性」（如任意输入不应导致崩溃、加法满足交换律）替代逐例测试，通过随机采样输入空间验证系统。作者坦言一个月内提交了 500 余个 bug 报告，虽引以为豪，却意识到若数十亿用户从未触发这些缺陷，其实际价值存疑，甚至可能拖慢 Postgres 19 等项目的发布。文章指出测试研究的核心张力在于测试者与维护者的分离：测试者从外部审视系统，既不如维护者了解内部，也缺乏修复的激励。作者进一步论证了 bug 发现与修复之间的根本不对称——bug 易于验证，但修复方案多样、复杂且难以验证，贪心地逐一修补可能导致无穷无尽的修复工作。其结论是：事后测试（in vitro）对安全漏洞和静默故障仍有价值，但应选择性报告和修复；真正高价值的是与开发同步进行的「活体测试」（in vivo），将验证能力嵌入开发流程以加速而非拖慢迭代。在 AI 使 bug 发现能力指数级提升的背景下，正确性成为永无止境的追求，测试研究需重新定位自身价值。

## 12. Go 汇编器快速指南

- 原始链接: <https://go.dev/doc/asm>
- 英文标题: A Quick Guide to Go's Assembler

本文是 Go gc 编译器汇编器的速查文档，核心要点如下。Go 汇编器操作的是半抽象指令集而非直接机器指令，因此 MOV 等指令的实际映射可能因架构而异，机器特定操作通常原样出现，而内存移动、子程序调用等通用概念则较为抽象。汇编器借鉴 Plan 9 风格但存在差异：常量按 Go 运算符优先级解析（如 3&1<<2 结果为 4），且始终视为 64 位无符号整数。系统定义四个伪寄存器：FP（帧指针）、PC（程序计数器）、SB（静态基址）、SP（栈指针），用户符号以 SB 或 FP 偏移表示，包路径在汇编源文件中用中点（U+00B7）和除号（U+2215）替代点号与斜杠。TEXT 指令声明函数体，DATA 与 GLOBL 指令定义全局数据，配合 NOSPLIT、NOPTR、RODATA、NOFRAME 等标志控制函数与数据行为。与 Go 类型交互时，编译器自动生成 go_asm.h 头文件，提供结构体字段偏移和常量宏，避免硬编码布局假设。GC 协调方面，含指针的符号必须在 Go 源码中定义，汇编函数需通过 FUNCDATA 与 PCDATA 伪指令标注活指针位置，无指针结果且无局部帧的简单函数只需在 Go 源码中声明原型即可。

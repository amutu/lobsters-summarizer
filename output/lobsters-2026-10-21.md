## 3. 在 macOS 上利用 Touch ID 与 Secure Enclave 设置 SSH 密钥

- 原始链接: <https://nmattia.com/posts/2026-10-19-setting-up-ssh-keys-touch-id/>
- 英文标题: Setting up SSH keys on macOS with Touch ID

本文介绍在 macOS 上借助 Secure Enclave 和 Touch ID 创建 SSH 密钥的完整方案，分为快速上手与原理剖析两部分。快速设置仅需三步：用 sc_auth create-ctk-identity 在 Secure Enclave 中创建不可提取的 CTK 身份（密钥类型 p-256-ne，保护方式 bio）；用 ssh-add -K -S /usr/lib/ssh-keychain.dylib 将该身份注册到 SSH agent；用 ssh-add -L 导出公钥并添加到 GitHub 等服务器。此后每次 git push 等 SSH 操作都会触发 Touch ID 验证。相比传统密钥文件，该方案的核心优势在于：私钥材料永远无法被提取或窃取，每次使用均需生物识别确认，且不在文件系统中留下密钥文件。文章进一步解释了底层机制：ssh-keychain.dylib 充当 FIDO 风格认证器的翻译层，通过 _sk_load_resident_keys 向 SSH agent 提供公钥列表，通过 _sk_sign 将签名请求转发至 Secure Enclave 完成运算。作者也提醒了若干注意事项：重启后需重新执行 ssh-add 注册；若 Mac 硬件损坏，身份将永久丢失且无法恢复；注册时出现的 PIN 提示可直接回车跳过，因为实际安全由 Touch ID 保障而非 PIN。此外，作者指出相关接口文档极为匮乏，部分内容依赖社区逆向与实验得出。

## 5. OpenBSD 8.0 发布说明

- 英文标题: OpenBSD 8.0

OpenBSD 8.0 于 2026 年 10 月 20 日发布，为第 61 个正式版本。多平台改进方面：amd64 内核虚拟地址空间从 4G 提升至 512G，swap 加密改用 AES 指令加速；arm64 新增休眠支持与弹跳缓冲区；riscv64 加入 V 向量扩展、高级中断架构（imsic/aplic）及 Sstc 定时器扩展；sparc64 切换至 LLVM 工具链；loongson 架构因不兼容 Clang 22 被退役。内核改进了页面回收启发式算法并新增 getexecpath(3)；挂起/休眠支持扩展至更多设备。图形驱动 drm(4) 更新至 Linux 6.18.53，新增 Intel Arc A 系列支持。VMM 虚拟化支持每客户机最多 64 个 VCPU，新增 x2apic 模式及 MSI/MSI-X 中断。用户空间方面，httpd(8) 新增自定义 HTTP 头与 Lua 模式匹配等特性；qwx(4) 无线驱动完成大量稳定性修复并加入 802.11n 支持。安全方面修复了涉及 perl、libexpat、nsd、Xserver 等多个 CVE，加固了 pledge/unveil 策略，修复了 pf 防火墙的越界读取与竞态问题，并强化了 smtpd、iked 等守护进程的权限分离机制。

## 6. Jepsen 测试 Orkes Conductor 5.3.2：工作流编排系统的可靠性缺陷

- 原始链接: <https://jepsen.io/analyses/orkes-conductor-5.3.2>
- 英文标题: Jepsen: Orkes Conductor 5.3.2

本文是 Jepsen 对 Orkes Conductor（Netflix 开源的工作流编排系统，现由 Orkes 维护）5.3.2 及后续版本的可靠性测试报告。测试基于 Jepsen 框架和 Conductor Java SDK，在十台 Debian 节点上模拟生产部署（Postgres 数据库、Redis 队列、Conductor 服务器与自定义 Worker），通过注入进程暂停、网络分区等故障，验证「至少一次投递」和「工作流最终终止」等保证。测试发现多项问题：（1）即使健康集群中，同一任务也可能在两个 Worker 上并发执行，分布式锁仅能降低频率而无法消除；（2）Postgres 加 Redis 架构下，故障可导致工作流在任务执行前停滞长达一小时（默认响应超时）；（3）startWorkflow 偶尔返回 null 或语法错误（分区轮转竞态）；（4）看似连接失败的调用实际已成功创建工作流，客户端重试逻辑掩盖了真实状态；（5）部分写入（Postgres 成功但队列缺失）导致工作流被永久放弃，sweeper 仅依赖队列而非数据库；（6）网络分区可致已可见的工作流被遗忘；（7）5.5.0-rc1 的重试机制引入重复键错误。多数问题在 5.5.6 中修复，Orkes 对部分行为（如任务停滞）选择不修改。

## 13. 为何需要 ud2 指令而非直接用 int 6

- 原始链接: <https://devblogs.microsoft.com/oldnewthing/20261019-00/?p=112781/>
- 英文标题: Why do we need ud2 when int 6 is right there?

本文解释了为何不能以 int 6 替代 ud2 来触发未定义指令异常（#UD）。表面上看，int 6 与 ud2 同为两字节指令，且中断向量 6 正是无效操作码向量，似乎可以手动调用。但架构层面存在关键区别：无效操作码属于 fault（故障），异常处理时报告的是出错指令本身的地址；而 int 6 属于 trap（陷阱），报告的是该指令之后一条指令的地址。fault 表示内核可尝试修复并重试的错误（如缺页），trap 则表示操作已完成、处理完毕后继续执行下一条。若用 int 6 模拟 #UD，异常处理程序会误以为 IP 指向的指令就是那条未定义指令，结果看到的却是一条合法指令（如 xor eax, eax），从而产生困惑。此外，在保护模式下，int 6 的调用需要相应权限，操作系统通常禁止用户态触发 int 6，以避免用户程序伪造 #UD 故障混淆处理器。因此，要真正触发 #UD 未定义指令故障，唯一途径是执行一条真正的未定义指令，如 ud2。

## 14. 为修复 0.000000000000000000542% 的除法边界缺陷而让所有除法变慢

- 原始链接: <https://futhark-lang.org/blog/2026-10-14-defining-division.html>
- 英文标题: Making all divisions slower to fix a bug in 0.000000000000000000542% of cases

Futhark 编译器团队记录了一次因 C 语言未定义行为引发的修复。现代机器用补码表示整数，最负值（如 32 位 int 的 -2^31）取负后无法用同类型有符号整数表示，因此 x / -1 在 x 为最负值时触发有符号溢出，而 C 标准将其视为未定义行为，x86 上甚至会引发 CPU 异常。Futhark 用无符号 C 类型承载所有整数运算以规避溢出问题，但除法必须保留符号，故生成有符号除法，从而暴露该缺陷。修复方式是在运行时的 squot32 函数中判断除数是否为 -1，若是则通过无符号取负得到正确结果，否则执行普通除法，代价是每次除法多一个分支。性能实测显示：在 CPU（c 后端）上分支极易预测，无可测量差异；在常规 GPU 基准测试中，有符号除法罕见且内存延迟掩盖了开销，同样无影响；但在刻意构造的除法密集程序上，CUDA 后端因分支阻止了指令展开，耗时从约 5.5 ms 升至约 12.6 ms，接近 2.3 倍；AMD GPU 上也有类似但稍小的退化。作者认为正确性不可妥协，该修复是 Futhark 生成 C 代码中最后一个已知的未定义行为实例，但仍有至少一处实现定义行为（移位量超过位宽）尚未处理。

## 16. 单哈希布隆过滤器：从原理到工程实践

- 原始链接: <https://www.calabro.io/ohbf>
- 英文标题: One Hash Bloom Filters

本文由Jim Calabro撰写，系统介绍了布隆过滤器从传统多哈希到单哈希的演进，并结合Bluesky后端的实际工程经验。布隆过滤器是一种概率型数据结构，以极少内存快速判断键是否存在于集合中，在Bluesky中可拦截约99%的数据库查询（如拉黑、静音检查）。传统方案需k个独立哈希，2008年Kirsch与Mitzenmacher提出双哈希技巧，用两个哈希模拟k个，大幅降低计算开销。Bluesky早期使用bits-and-blooms库，但因非线程安全需加互斥锁，导致部署耗时90分钟；同事改用原子指令后降至15分钟。进一步地，Lu等人证明可将位数组划分为k个两两互素大小的分区，仅用一次哈希即可得到k个位位置，作者据此实现Go库gloom，已在Bluesky后端及jetstream同步服务运行九个月。性能优化方面，gloom将过滤器切分为64字节块以匹配CPU缓存行，通过unsafe确保缓存对齐，最坏情况仅一次缓存未命中；同时用MUL指令替代取模运算，并提供ShardedAtomicFilter将写入分散到多个分片以减少多核争用。文章强调布隆过滤器与roaring bitmaps在高性能数据系统中的核心地位。

## 1. 我讨厌为 Linux 打包我的软件

- 原始链接: <https://getfresh.dev/docs/blog/packaging-for-linux/>
- 英文标题: I hate packaging my software for Linux

作者吐槽为 Linux 打包软件的糟糕体验。为了让自己的终端工具 Fresh 易于安装，他先后支持了 npm、cargo、AppImage、Flatpak、deb、rpm、AUR、Nix、mise、Homebrew 等几乎所有渠道，但每个渠道都只适用于部分用户，且各有缺陷：npm 存在安全隐患且并非人人安装；Flatpak 的沙箱机制与终端应用不匹配，需要传递危险标志；AppImage 因 FUSE 挂载导致启动极慢，且二进制仍受 libc 版本限制；deb/rpm 因未能进入官方源而无法获得自动更新，进入官方源又要求所有 Rust 依赖都打包成 Debian 包，工作量巨大且难以长期维护；AUR 因安全事件进入只读模式，导致无法发布新版本；mise 则因 GitHub 证书轮换而意外失效。作者感慨，随着发行版和变种增多，为每个发行版维护包几乎不可能。因此他决定转向静态链接的 musl 二进制，并内置自更新机制，作为 Linux 上的主要发布方式，同时暂时保留现有包渠道。

## 2. 避免搞砸二维码的指南

- 原始链接: <https://infosec.exchange/@rebane2001/117078420917152774>
- 英文标题: Guide to (not) fucking up QR codes

本文是Mastodon上的一篇帖子，作者以幽默和反讽的口吻分享了一份关于“如何避免搞砸二维码”的实用指南。文章指出，二维码虽然普及，但许多人在设计和使用时容易犯下各种错误，导致二维码无法被扫描或扫描后体验糟糕。作者列举了常见问题，例如：在二维码上叠加半透明图片或遮挡关键区域、使用过低的对比度导致扫描器无法识别、将二维码打印在弯曲或扭曲的表面上、在二维码周围留的留白不足、使用损坏或过期的URL链接、动态二维码失效等。文章强调，正确的做法是确保二维码有足够的静区（quiet zone）、保持色彩对比鲜明、不要在二维码上随意放置图案或文字、测试所有设备上的扫描效果、尽量使用静态链接而非短链或动态链接以避免失效。作者还提醒，二维码不是设计元素，而是功能工具，美观应让位于可用性。整体上，这是一篇轻松但信息量大的实用指南，适合需要生成或设计二维码的人群阅读，避免因小失大，导致二维码无法正常使用。

## 3. Tailscale 如何协助定位 SQLite WAL-Reset 漏洞

- 原始链接: <https://tailscale.com/blog/sqlite-wal-reset-bug>
- 英文标题: How Tailscale helped find the SQLite WAL-Reset bug

本文讲述了 Tailscale 团队持续数月排查数据库损坏问题，最终协助发现并修复了一个潜伏在 SQLite 中长达 16 年的罕见竞态条件漏洞。Tailscale 的控制平面按分片使用 SQLite，并以单写者模式运行。自 2023 年起，其备份流程定期将完整数据库快照上传至 S3；但 2024 年 8 月起，多个数据库出现偶发损坏，导致部分分片停机，影响 tailnet 的配置同步和管理面可用性。团队尝试通过代码审查、共性分析等手段均未找到触发条件，后来借助 SQLite 专业支持团队开发的 tmstmpvfs 诊断工具，在真实环境中捕获了错误日志，最终定位为 checkpoint 与写事务之间发生的数据竞争：在特定时刻写入时，checkpoint 进程误以为已将 WAL 中的页面复制到主数据库文件，实际却未写入，导致数据永久丢失和文件损坏。SQLite 团队将其命名为 WAL-Reset bug，并在 3.51.3 中修复。Tailscale 通过增加重叠操作告警确认了该条件确实存在，修复后恢复稳定。文章强调，以非标准方式运行“无聊技术”也会引入风险，同时展示了开源协作在深层问题排查中的价值。

## 5. 有意识编码：目的与意图

- 原始链接: <https://var0.xyz/posts/mindful-coding-purpose-and-intention.html>
- 英文标题: Mindful coding: Purpose and intention

作者所说的“有意识编码”（mindful coding）并非关注呼吸或手指动作，而是时刻留意代码背后的意图。编程语言擅长描述操作本身，但更关键的问题是“为什么”。好的代码通过命名、抽象边界、提交信息和注释来传达意图。命名不只是贴标签，取名困难往往暴露抽象本身的问题：如果没有一个有意义的概念可命名，或许就不该在那里划分边界。提交信息不应复述diff，而应记录变更的原因，比如发现了什么bug或用户的真实困扰。注释也不应重复代码，而应解释代码无法体现的背景，例如某个看似多余的操作为何不能删除，或引用相关issue。作者强调，意图本身就是信息；有意识地编写代码意味着让“为什么”清晰可见，有时最有意向的做法是不添加多余抽象或注释。当命名感到困难时，应反思该概念是否本就不该存在。

## 6. 我的家庭实验室被黑：事后分析

- 原始链接: <https://phunky.cafe/my-homelab-got-hacked/>
- 英文标题: My Homelab Got Hacked - A Postmortem

作者的家庭实验室遭遇黑客攻击，其自托管的Forgejo代码托管服务被利用CVE-2026-60004漏洞实现远程代码执行。攻击者趁开放注册功能未关闭，创建恶意账户并上传含恶意Git hook的仓库，通过diffpatch端点漏洞触发攻击。作者发现CPU异常后展开调查，确认攻击利用了已停止维护的Forgejo v13版本（未及时更新至已修复的LTS或v16）。恶意脚本会下载并运行加密货币矿工二进制文件，经VirusTotal验证为已知矿工。攻击者IP来自VPN，日志显示攻击过程高度自动化，包括扫描、注册、上传和多次触发漏洞。作者随后采取补救措施：回滚到预攻击备份、升级至v16、关闭开放注册和本地认证，并计划进一步限制容器对LAN/WAN的访问。文章总结教训：坚持3-2-1备份、及时打补丁、谨慎暴露服务，并提醒认为自身不会遭黑客是错误的想法。

## 7. fearless_simd v0.7：64位整数、改进泛型、SSE2与v1.0前瞻

- 原始链接: <https://linebender.org/blog/fearless-simd-0-7/>
- 英文标题: fearless_simd v0.7: 64-bit integers, improved generics, SSE2, and upcoming v1.0

fearless_simd 是一个零依赖、构建时间短、公开 API 安全的 Rust SIMD 库，旨在消除 SIMD 编程中的 unsafe 代码。v0.7 版本新增了 u64 和 i64 向量类型支持，填补了完整类型覆盖的最后空缺；此前版本受限于硬件支持不均，如今编译器已能自动跟踪指令集特性，大幅减少了 unsafe 块。新版本还补充了更多操作：swizzle_dyn 支持任意字节洗牌，可对越界索引清零或返回实现定义但内存安全的结果；所有类型支持拓宽与窄化转换，且可灵活选择回绕、饱和或平台最廉价方式；还新增了 shift/rotate_elements 等便捷函数以兼容 std::simd API。泛型编程能力显著提升：SimdBase trait 统一抽象整数与浮点向量，Bytes trait 支持泛型位转换，所有操作均通过 trait 暴露，关联类型也携带泛型约束，使编写跨向量类型的通用算法更加方便。显式新增 Sse2 指令集级别，在不支持 SSE4.2 的旧 x86 系统上使用核心 SSE2 指令而非标量回退，改善性能并降低二进制体积。尽管新增大量功能，依赖编译时间仍保持在 x86 上 2 秒、Aarch64 上 1 秒。此外，v0.7 清理了部分 API（如将 reinterpret_* 统一为 bitcast，重命名 load_four_interleaved）。作者表示 API 已稳定近一年，社区无异议的话将在 9 月初发布 v1.0。

## 10. 为何Chrome中微小JPEG显示不同

- 原始链接: <https://guillaumetech.github.io/posts/jpg-scaling-chrome/>
- 英文标题: Why tiny JPEGs look different in Chrome

作者发现同事电脑上的15px JPEG图标显示更细、更接近原图，而Chrome中则显得更粗。调查后得知，这并非渲染缺陷，而是Chrome的一项JPEG解码优化。JPEG压缩将图像分为8×8块，通过离散余弦变换（DCT）转为频率系数，其中高频系数代表细节，低频代表大致形状。当目标显示尺寸很小时（如1/8比例），Chrome通过Skia调用libjpeg-turbo的partial IDCT scaling技术，只解码低频系数，跳过高频细节，再进一步缩放至目标尺寸。这样做减少了内存占用和计算量，但会导致小尺寸JPEG看起来更模糊或更粗。该优化适合照片，因为照片感知主要依赖低频信息；但对图标等需要清晰边缘的场景并不友好。作者建议，图标类图片应使用SVG等矢量格式，而非JPEG。

## 13. C++26 新特性：std::indirect

- 原始链接: <https://www.sandordargo.com/blog/2026/08/12/cpp26-indirect>
- 英文标题: C++26: std::indirect

本文介绍了 C++26 标准库新增的 vocabulary 类型 std::indirect（来自 P3019R14 提案）。它解决了 std::unique_ptr 作为类成员时的两个根本问题：一是 const 传播被破坏，unique_ptr 的 operator* const 返回非 const 引用，导致 const 对象也能修改间接持有的内容；二是它会删除拷贝操作，迫使开发者手写 Rule of Five 样板代码。std::indirect<T> 为动态分配的 T 对象提供值语义：拷贝时深拷贝所拥有的对象，const 路径上访问时会将 const 正确传播到所拥有对象，因此 const 成员函数中无法修改内部状态；它还支持基于所拥有对象的比较和哈希，并且类无需手写特殊成员函数即可获得正确的拷贝、移动、析构行为。indirect 没有空状态，被移动后处于 valueless_after_move() 状态，访问该状态是未定义行为；若需要可空间接引用，应使用 optional<indirect<T>>。它适用于 PIMPL、递归类型以及为缩小类体积而将大成员移到堆上的场景。文中也提到同源提案中的 std::polymorphic 将另行介绍。

## 17. Rust中的尾调用解释器

- 原始链接: <https://lordgoati.us/blog/tail-call/>
- 英文标题: Tail-Call Interpreters in Rust

这篇文章介绍了在Rust中实现尾调用解释器（tail-call interpreter）的多种虚拟机指令分发技术。作者受一篇Scala VM dispatch文章启发，为自己的ternary项目寻找性能改进方案，决定在Rust中复现并对比这些技术。文章首先解释了尾调用解释原理：通过编译器优化将递归转化为跳转，避免栈帧分配；Rust在高度优化下也会执行，并可通过不稳定的explicit_tail_calls特性直接控制。随后作者用一个5指令的栈机实现了四种分发方式：switch dispatch（递归match）、subroutine threading（利用Fn trait进行动态分发）、indirect threading（操作内递归调用dispatch）、direct dispatch（每个操作直接调用下一个操作）。基准测试结果显示，在作者机器上direct dispatch最快（约24.59 ns/iter），indirect（55.32）、switch（59.39）和subroutine（79.93）较慢。最后，作者把这些方法移植到一个更贴近真实硬件的16位寄存器机，加入寄存器、立即数和跳转指令，并讨论了switch和subroutine dispatch的实现。文章强调这些实验数据很小，需谨慎对待编译器优化，但技术间的关系符合预期。

## 1. 遭遇定向攻击：通过 Git post-checkout 钩子窃取凭据

- 原始链接: <https://frankwiles.com/posts/i-got-targeted/>
- 英文标题: I got targeted: Trying to get your credentials via a git post-checkout hook

REVSYS 创始人 Frank Wiles 披露了一次针对他的定向社会工程攻击。攻击者伪装成教育科技领域的潜在客户，以项目咨询为由联系他，随后通过 Dropbox 分享了一个包含 Markdown 项目文档的文件夹，并要求他切换到所谓的「NDA 分支」签署保密协议。Wiles 在查找 NDA 文件时发现该文件夹内含 .git 目录，进一步检查 .git/hooks 后发现一个真实的 post-checkout 钩子脚本。该脚本利用 Vercel 应用作为命令与控制（C2）服务器，下载与操作系统匹配的二进制文件、赋予执行权限、运行后自删除，目的是在受害者机器上执行任意代码，进而窃取其 GitHub 账户及大量 REVSYS 客户相关凭据。Wiles 因对 Git 工作流足够熟悉而及时识破，未造成损失，并立即通知了 Dropbox 和 Vercel 安全团队。文章强调，攻击者同时伪装成一家开发公司，利用开发者日常使用 Git 的习惯，通过几乎无人实际使用的 post-checkout 钩子实施攻击，极具隐蔽性。他提醒同行保持警惕，严密守护自身凭据。

- 英文标题: The Era of Software Quality, or the Era of Ostriches?

本文是GNOME安全维护者对2026年软件安全形势的深刻反思。作者指出，GNOME以C、C++、Vala等不安全语言编写，人类几乎不可能写出完全安全的代码，而AI漏洞扫描已成为2026年维持软件质量的唯一可行手段。数据显示，GNOME的CVE数量从2023年的13条激增至2026年前三季度的141条；WebKitGTK同期更达305条（主要源于Skia和ANGLE）。作者强烈反对以「AI生成」为由拒绝漏洞报告，认为此举等同于拒绝所有安全报告。文章回顾了GNOME漏洞赏金计划的兴衰：2024年启动，仅覆盖GLib、glib-networking和libsoup，两年内收到298份报告、接受71份，发放奖金18.39万欧元，最终因报告量过大而于2026年2月关闭。Red Hat委托AISLE Research对GLib进行AI扫描，发现118个漏洞（含40%误报），GLib因公开API众多而成为重灾区。作者同时强调，人类安全审计（如Codean Labs对Flatpak沙箱逃逸的发现）仍不可替代，AI无法覆盖所有复杂场景。文章呼吁维护者接受AI报告、调整编译警告标志（如-Wconversion、-Wsign-compare），并建议未来赏金计划仅针对可复现的功能性利用，而非所有AI可发现的漏洞。

## 3. 利用C2PA排除机制篡改时间戳：一次「时间黑客」演示

- 原始链接: <https://www.da.vidbuchanan.co.uk/blog/hacking-time.html>
- 英文标题: How to Hack Time, With C2PA

安全研究者David Buchanan（retr0id）于2026年10月发布文章，演示了如何利用C2PA内容认证规范中的「排除」（exclusions）机制，在保留有效签名和时间戳证明的前提下任意篡改图像内容。C2PA元数据通常包含两个签名：设备端的claim签名和远程时间戳权威（TSA）签发的时间戳签名，后者通过RFC 3161协议证明数据在指定时间之前已存在。作者并未攻击TSA，而是利用规范允许将文件字节范围排除在签名计算之外的设计，将整个文件排除，使签名实际覆盖的是空字符串（SHA-256哈希为47DEQpj8...），从而在彩票开奖后对图像进行PS而不使任何签名失效。该漏洞早在2025年6月Neal Krawetz的C2PA缺陷列表中已被指出，但至今无人修复。作者指出修复并非简单：排除机制对PNG等格式中CRC32校验和的更新是必要的，完全移除会破坏兼容性。其建议是为每种受支持的文件格式明确限定允许排除的字节范围，并要求验证器强制执行这些约束，而非仅检测「整文件排除」这一极端情况。

## 4. 双栈滑动窗口聚合算法

- 原始链接: <https://orlp.net/blog/two-stack-sliding-window-aggregation/>
- 英文标题: Two-Stack Sliding-Window Aggregation

本文介绍了一种用于滑动窗口聚合的双栈算法，适用于最小值、分位数、HyperLogLog近似去重计数等无逆运算的聚合场景。对于有逆运算的聚合（如整数求和），双端队列即可解决；但大多数有意义的聚合（浮点求和、最小值等）缺乏逆运算，朴素滚动方案会因NaN或浮点误差导致结果永久污染。双栈算法的核心思想是维护两个栈：values栈存放当前窗口元素及其聚合值values_agg，cum_aggs栈存放已移出values但仍在窗口内的元素的累积聚合。每次eval()时，将cum_aggs栈顶与values_agg结合即可在常数时间得到窗口聚合。算法通过泛化四个函数（empty、unit、combine、finalize）支持任意结合性聚合，每w次弹出操作排空一次values栈，实现摊销O(1)时间复杂度，空间为O(w)。该算法可追溯至2001年Sleator关于双栈实现FIFO队列的讲义，后经2011年Stack Overflow用户「adamax」推广，并被Tangwongsan等人的低延迟滑动窗口聚合论文引用。文章还指出，尽管浮点加法不严格满足结合律，该算法仍具实用价值：每个聚合仅依赖窗口内元素，不会将NaN或异常值传播到窗口之外，从根本上避免了长期误差累积。

## 5. gVisor 正式捐赠给 CNCF，开启社区化治理新篇章

- 原始链接: <https://gvisor.dev/blog/2026/10/02/gvisor-cncf/>
- 英文标题: gVisor is being donated to CNCF

2026年10月，Google 宣布将 gVisor（2018年开源的用户态 Linux 实现，被视为继 Linux 内核之后最成熟的第二套 Linux 实现）连同名称与商标捐赠给云原生计算基金会（CNCF）。捐赠申请于9月7日提交、9月28日获批。短期内项目将进入 CNCF「Sandbox」状态，构建与测试基础设施迁移至 GitHub Actions 和 Buildkite，治理模式转为维护者制，并引入非 Google 维护者；数月后将推进至「Incubation」状态，GitHub 仓库迁出 google 组织，最终采用基于组织的投票机制以防止单一公司主导。捐赠动机包括：gVisor 处于容器与虚拟机的中间地带，常被安全审计者误解；I/O 密集型负载的性能感知不佳；作为 Google 全资项目难以将性能补丁推入 Linux 内核上游；以及桌面沙箱、macOS 运行 Linux 等非商业场景缺乏推动力。Ant Group、Modal、Tines 已承诺长期参与维护，OpenAI、腾讯、NVIDIA 等继续贡献。Google 强调不会退出开发，此举旨在加速 gVisor 在更广泛用户中的采用，类似当年 Kubernetes 捐赠 CNCF 后的生态爆发。

- 英文标题: Rust for CPython (Python Language Summit 2026)

David Hewitt 作为 Rust for CPython 项目团队的「大使」，在 Python 语言峰会 2026 上向核心开发者征求对 Rust 引入 CPython 的意见。该项目由 Kirill Podoprigora 和 Emma Smith 领导，团队约 60 人，含数名 Python 核心开发者及 Rust 项目代表。选择 Rust 的动因包括 CPython 中 type-crash 类问题持续上升，以及新解析器、JIT、free-threading 等大型特性带来的复杂性。团队提出分阶段路线图：2026 年夏完成 Rust API 概念验证，年末发布定义成功标准的 PEP；Python 3.16（2027 年 10 月）引入 zlib 模块的可选 Rust 后端（基于 zlib-rs，可加速几乎所有 pip install）；3.17（2028 年）扩展至 io、json、xml 等模块；3.18（2029 年）起 Rust 成为必需构建组件并发布公共 API。成功标准包括多数活跃核心开发者对 Rust API 持开放态度、性能基准无明显回退、所有分层平台均获支持。讨论中，Larry Hastings 质疑是否应做完整重写，David 回应 CPython 将长期保持 C/Rust 双语言；Pablo Galindo 担忧从 Cargo 获取外部依赖将成为「巨大问题」，David 表示将尽量精简依赖并采用 vendored 源码，构建 CPython 无需 Cargo。

## 8. Cyclone Scheme 编译器的设计与实现（2017）

- 原始链接: <https://justinethier.github.io/cyclone/docs/Writing-the-Cyclone-Scheme-Compiler-Revised-2017>
- 英文标题: Writing the Cyclone Scheme Compiler (2017)

本文为 Justin Ethier 撰写的 Cyclone Scheme 编译器技术文档（2017 年修订版），系统介绍了编译器的各组件及其实现思路。编译器整体架构为：解析 Scheme 源码生成 AST，经多轮源到源转换（宏展开、CPS 转换、闭包转换等）后输出 C 代码，再由 C 编译器生成可执行文件。设计灵感来自 Marc Feeley 的「90 分钟 Scheme 到 C 编译器」，但针对生产需求做了扩展。转换阶段采用「多小 pass」策略，每个变换独立成 pass 以降低耦合；CPS 转换后通过原语内联、lambda 收缩、常量折叠等优化减少冗余代码，并借助哈希表分析数据库辅助优化。闭包转换使用扁平闭包（函数指针加自由变量向量）以提高查找效率。垃圾回收器是本文重点：小代回收沿用 Henry Baker 的「Cheney on the MTA」复制式算法，将 C 栈视为最年轻代；大代回收改用 Doligez-Leroy-Gonthier 三色标记算法，堆对象不移动，从而支持原生多线程，且大代回收在独立线程上异步执行。堆按页分配，页大小按 Fibonacci 序列递增，小对象使用固定大小堆以减少碎片。C 运行时提供原语函数、调用历史、异常处理及 GC 支持。文章还提及 SRFI 18 多线程支持、基准测试及未来计划，并致谢 Scheme 社区资源（如 Chibi Scheme）对项目的贡献。

## 9. 为何开发者不愿「使用平台」？

- 原始链接: <https://nolanlawson.com/2026/10/03/why-dont-more-developers-use-the-platform/>
- 英文标题: Why don’t more developers "use the platform"?

文章从多个角度剖析了开发者倾向于自行用 JavaScript 实现功能、而非调用浏览器或平台原生 API 的原因。历史层面，浏览器长期落后于上层生态，jQuery 等库填补了关键 API 空白，IE6 等旧浏览器更拖慢了采用进度；习惯层面，开发者已习惯在 npm 上搜索现成方案；文档层面，第三方库常配有详尽教程与示例，而平台文档曾分散且不够友好。作者还指出「宜家效应」：自己搭建更有趣、更易理解，许多如今力推「使用平台」的专家也曾是造轮子的人。当然，有时也源于对 CSS 等平台特性的认知不足，作者以 ClickHouse 的压缩机制为例说明该现象不限于 Web 领域。最后，作者探讨了 AI 编程的双重影响：乐观地看，大模型能精准选择平台 API；悲观地看，模型倾向于重复造轮子、过度工程化。作者认为「使用平台」作为口号简洁有力，但理解开发者的处境同样重要，这一呼吁将长期存在。

## 10. 现代桌面操作系统的困境与出路：让 tmux 成为操作系统

- 原始链接: <https://matduggan.com/what-does-my-dream-os-ui-look-like/>
- 英文标题: Problems and solutions to the modern desktop (Make tmux the OS)

作者受Scott Jenson演讲启发，梳理了当代桌面窗口管理的核心痛点：屏幕空间随多显示器与笔记本/台式机切换频繁变化；用户分为最大化、近最大化、协调三类，但现有OS仅优化第一类；浏览器已成事实上的迷你操作系统，标签与工作流关联混乱；文件系统统一抽象失效，数据散落各应用内部。作者强调这些问题并非新发现，2001至2004年的研究已识别相同模式，但Windows Timeline、macOS Stage Manager、KDE Activities等方案因非默认、需手动配置或妥协于平板逻辑而未能普及。其核心愿景是将tmux的可滚动、会话持久、可分离、任务导向体验普及给普通用户：以无限画布为基底，物理显示器作为视口；切换时布局确定性重排而非重置；通过焦点遥测自动识别主辅显示器；浏览器标签脱离浏览器成为OS一等公民，按任务而非按应用组织；隐私作为一等标志。作者认为本地LLM或可辅助任务归类，但关键在于方案须作为默认行为在OS层统一实现，而非依赖用户手动配置。

## 11. 编程语言探索时代已至

本文发表于2026年10月，作者是一名编程语言（PL）研究员，针对TYPES邮件列表中关于AI工具冲击PL研究的悲观讨论，提出了截然不同的乐观立场。作者指出，多数研究者因AI编程能力而陷入类似疫情时期的焦虑与士气低落，但作者认为PL研究并未死亡，而是进入了全新的「探索时代」。其核心论点是：即便人类不再亲手写代码，PL领域在理论之美、形式化洞察方面的价值依然完整；况且绝大多数编程语言本就没有实际用户，研究者无需执着于应用落地。更重要的是，大语言模型（LLM）让研究者得以以前所未有的速度验证反事实假设、生成形式化语义、迭代类型系统设计。作者列举了三个实践方向：自动为解释型语言生成并验证语义、与Amazon合作开发面向AI智能体的验证工具接口、以及为动态系统新语言dynestyx自动构建大步骤语义。作者坦言，过去手工编写数十万行代码的「匠人自豪感」正在消退，但那更多是自我认同而非真正的智识好奇心。文章最终呼吁年轻PL研究者放下ego，拥抱LLM带来的探索自由，将研究回归其本质——拓展人类知识边界的探索与好奇。

## 12. 2026年Android系统级广告拦截

- 原始链接: <https://kevinboone.me/adblock.html>
- 英文标题: System-level ad-blocking in Android

本文介绍2026年Android平台上系统级广告拦截的原理与四种主要方法。核心原理是通过覆盖DNS解析，将已知广告域名映射到虚假IP（如127.0.0.1），从而阻止广告加载。四种方法依次为：使用商业DNS广告拦截服务、订阅带广告拦截功能的商业VPN、安装无需root的本地VPN类拦截应用（如AdAway，可从F-Droid获取）、以及root后直接修改hosts文件（可通过Magisk模块实现）。文章指出，Google正逐步收紧对非root应用和第三方软件安装的限制，但root方案仍是最有效、最轻量且免费的选择。作者同时提醒安全风险：不透明的DNS或VPN服务商可能窃取用户数据，非开源拦截应用同样存在隐患。此外，系统级拦截并非万能：部分应用内置广告无法被拦截，少数开发者已采用IP直连绕过DNS，且Android的DNS缓存可能导致规则更新后需重启才能生效。若用户主要困扰来自网页广告，安装带拦截功能的浏览器即可，无需动用系统级方案。

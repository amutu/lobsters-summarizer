## 1. curl维护者谈Rust重写：代码转换易，持续演进难

- 原始链接: <https://daniel.haxx.se/blog/2026/11/17/actual-curl-rewrites-in-rust/>
- 英文标题: Actual curl rewrites in rust

curl项目维护者Daniel Stenberg就近期出现的两个Rust重写项目（urlx与一个直接命名为「curl, rewritten in Rust」的项目，后者声称花费8600美元）发表看法。他指出，AI能在数周内将18.5万行C代码转为34万行Rust代码，并非技术奇迹，而是因为curl文档完善、测试用例丰富，AI只需转换并跑通测试。然而，在这三周多时间里，curl本身上游已合并300余个提交、修复200多个bug及若干漏洞，这些修复在重写项目中并不存在。作者强调，curl的真正价值来自数十年积累的用户反馈、社区协作与持续迭代，而非实现语言；仅凭一次快照式重写无法复制这种生命力。关于安全性，2026年curl已确认的81个漏洞中仅14个（17.3%）可能因使用内存安全语言而避免，其余67个与语言无关。作者明确表示不认同任何语言重写，主张持续打磨与重构。他与重写项目团队无接触，不知其后续走向，仅表示「被逗乐、略感困惑、颇为好奇」，并引用一句老话：模仿是平庸对伟大最真诚的赞美。

## 2. Redict 正式弃用，最终版本为 7.3.6

- 原始链接: <https://redict.io/posts/2026-11-17-redict-deprecated/>
- 英文标题: Redict is deprecated

2026年11月17日，Redict 作者 Drew DeVault 宣布 Redict 项目正式弃用，7.3.6 为最终发布版本。Redict 最初是 Redis 的一个 copyleft 分支，旨在为 Redis 社区提供保护，防止未来出现许可证「rug-pull」（突然收回开源）事件。然而，随着 Valkey 项目的成功以及 Redis 重新回归 copyleft 许可证，Redict 未能建立起可持续的社区，因此选择终止维护。作者建议 Redict 用户迁移至 Valkey：Valkey 采用宽松许可证，长期前景更为乐观。同时，作者明确不建议用户转回 Redis——尽管 Redis 已重新开源并采用 copyleft 协议，但其贡献者许可协议（CLA）可能在 Redis 遭遇财务困难时再次成为「rug-pull」的工具。迁移操作十分简便：通过包管理器安装 valkey 后，将 /etc/redict.conf 重命名为 /etc/valkey.conf 即可；若使用容器，则拉取 valkey 镜像并挂载相应配置文件。作者感谢了所有为 Redict 做出贡献、背书及切换的用户，表示「我们有一段不错的旅程」。

## 3. 绕过 Rust 孤儿规则：为 Trait 预留泛型扩展槽

- 原始链接: <https://edvong.com/bypass-orphan-rule/>
- 英文标题: How to Bypass Rust's Orphan Rule

本文系统讲解了如何优雅地绕过 Rust 孤儿规则（Orphan Rule）。孤儿规则要求「类型或 trait 至少有一个属于当前 crate」，目的是防止全局实现冲突。作者指出两种常见绕行方案均有明显缺陷：库内通过 feature flag 内置支持会导致版本锁定和行为硬编码；用 NewType 包装第三方类型则在复杂领域模型中造成大量冗余。核心方案是利用 RFC 2451 的细节——trait 自身的泛型参数也参与孤儿规则检查。库作者只需在 trait 上预留一个带默认值的泛型槽（如 Ctx = ()），用户即可在本地定义一个空标记结构体（如 MyApp），然后为任意第三方类型写出 impl ToJson<MyApp> for uuid::Uuid，编译器因检测到本地类型而放行。文章还强调了本地类型在泛型参数列表中的位置约束：裸泛型参数不能出现在本地类型之前。在架构层面，该机制让独立 models crate 无需引入序列化库即可编译，实际转换延迟到下游服务 crate 完成，保持依赖边界清晰。作者以自研 ORM Kova 为例，展示 Encode/Decode trait 及 CanString、Compatible 等能力 trait 均采用此模式，用户通过 AppCodec 标记类型即可让第三方类型无缝融入 ORM 的 DSL，且切换上下文仅替换 PhantomData，零运行时开销。

## 5. GitHub 仓库页面重设计（2019）

- 原始链接: <https://tonsky.me/blog/github-redesign/>
- 英文标题: Github Redesign (2019)

本文作者对 2019 年 GitHub 仓库页面提出系统性重设计方案，逐一指出 11 个 UI 问题并给出改进建议。核心问题包括：嵌套标签页造成信息层级混乱，应扁平化为单层导航；标签图标在抽象领域（如 commit、release）中无法有效传达语义，属于纯装饰，移除后可释放水平空间；虚荣指标（watch、fork）应精简，仅保留 star 并左移以突出；Watch 按钮存在「按钮还是状态」的歧义，应改用下拉菜单同时展示状态与操作；仓库描述应上移至标签页上方，话题标签紧邻仓库名以节省垂直空间；文件列表中右侧的最近提交信息实用性低且易与文件描述混淆，可移除；建议新增「概览」页，整合最近提交、贡献者头像、项目活跃度与语言统计；文件操作按钮应紧邻文件列表；clone 链接应恢复为完整可见形式；整体视觉可去除渐变与脏色，增加留白。作者强调，在相同垂直空间内，新方案在不丢失任何信息的前提下，额外容纳了约 4 个文件、6 条提交、3 个分支、10 位贡献者及活动与语言统计等内容，显著提升了信息密度与日常使用效率。

## 7. Java4Shell：一次编写，处处RCE

- 原始链接: <https://calif.io/java4shell/>
- 英文标题: Java4Shell: Write once, RCE everywhere

Calif团队披露了OpenJDK Base64解码器中的内存损坏漏洞Java4Shell（CVE-2026-114938），CVSS 4.0评分9.2（严重）。漏洞源于OpenJDK为加速解码而引入的AVX-512 VBMI指令优化路径：处理末尾字符时，64个「A」后跟一个「=」即可触发负数输出长度，被解释为64字节写入，越界覆盖相邻内存对象；旧版OpenJDK 17需128个「A」。该缺陷可导致敏感内存泄露或远程代码执行。团队在Keycloak、Jira、Confluence、Artifactory、Jenkins、PingFederate中验证了预认证RCE，在Kafka、Solr、Elasticsearch、Gerrit、Spinnaker中验证了后认证RCE，Struts与Spring Boot框架亦受影响，且客户端TLS连接场景同样可被利用。漏洞由AI辅助发现，研究者Quang Luong仅用一小时定位、两小时完成首个利用，总token成本不足200美元。文章提出「半人马黑客」理念，强调人与AI协同；并倡导「vibe-uncoding」——借助AI识别并删除系统中不需要的代码与优化，从源头缩小攻击面，呼吁安全领域从「能构建什么」转向「能删除什么」。

## 9. 程序即权重：面向模糊函数的编程范式

- 原始链接: <https://arxiv.org/abs/2607.02512>
- 英文标题: Program-as-Weights: A Programming Paradigm for Fuzzy Functions

本文提出「模糊函数编程」(fuzzy-function programming)范式，旨在解决日志告警、JSON修复、搜索排序等难以用清晰规则实现、却常被外包给大语言模型API的日常编程任务，从而在局部性、可复现性和成本之间取得平衡。其核心思路是将自然语言规格编译为一个紧凑的、可本地执行的神经制品。具体实例为「程序即权重」(Program-as-Weights, PAW)：一个4B参数的编译器在作者发布的FuzzyBench数据集（1000万样本）上训练，为冻结的轻量解释器生成参数高效适配器。实验表明，0.6B的Qwen3解释器执行PAW程序即可匹配直接提示Qwen3-32B的性能，而推理内存仅约为后者的五十分之一，在MacBook M3上可达30 tokens/s的推理速度。PAW将基础模型的角色从「逐输入问题求解器」重新定义为「工具构建器」：每次函数定义仅调用一次大模型，产出一个小型可复用制品，后续每次函数调用均廉价且可离线完成。该论文为NeurIPS 2026录用版本，作者包括Wentao Zhang、Liliana Hotsko、Woojeong Kim、Pengyu Nie、Stuart Shieber和Yuntian Deng。

## 10. 用 C 语言指定初始化器实现命名参数

- 原始链接: <https://quuxplusone.github.io/blog/2026/11/16/named-arguments-in-c/>
- 英文标题: C’s designated initializers give us named arguments

本文介绍了一种利用 C 语言指定初始化器（designated initializers）模拟命名参数的宏技巧，最早见于 Ben Klemens 的《21st Century C》。核心做法是：定义一个 Args 结构体，在宏中用指定初始化器填入默认值，调用者通过 .字段=值 语法覆盖任意参数，从而获得类似 ideal_volume(.kelvin=373.15, .moles=2) 的调用体验。该模式依赖 C 的两个 C++20 未采纳的特性：初始化器可任意顺序书写，且同一字段可重复出现、以最后一次为准（后者会触发 Clang 的 -Winitializer-overrides 警告）。重要优势在于：向 Args 结构体新增字段不会构成 API 破坏，旧调用点无需改写，但需重新编译（即 ABI 破坏）。此外，一族相关函数可共享同一个 Args 结构体，也可在命名参数前拼接普通参数。文章列举了 GitHub 上的真实用例，包括 EpicGames/raddebugger 中的 UI 动画参数传递。作者同时提醒，该模式偏「花哨」且开销较大，普通场景下普通函数签名通常已足够，不宜盲目替换。

## 11. 基于 E-Graphs 的编译器正确性自动验证

- 原始链接: <https://stng.substack.com/p/automatic-checking-of-compiler-correctness>
- 英文标题: Automatic Checking of Compiler Correctness with E-Graphs

MIT 的 Adam Chlipala 介绍了一项即将发表于 POPL 2027 的研究（第一作者 Dustin Jamner），该研究利用 e-graphs 数据结构与相关算法，实现了对编译器正确性的全自动形式化验证。研究建立在 Pyrosome 框架之上，该框架允许以模块化方式定义编程语言特性及其对应编译器代码，每个模块可独立验证，链接后自动获得整体正确性定理。编译器属于函数式语言传统（源自「From System F to Typed Assembly Language」），编译过程包含 CPS 转换、闭包转换等阶段，每阶段中间形式均受健全类型系统约束。核心难点在于：原贪心重写策略无法处理需要展开（如 eta 律）的证明义务，易陷入局部最优。解决方案是引入受 egglog 启发的 e-graph 引擎，在 Rocq 证明器中以纯函数式语言重新实现，从而可证明引擎本身的声音性。引擎支持从一般 e-graph 中提取最短项，用于在验证失败时给出简洁反馈。实验表明，在排除多态的设定下，引擎可自动完成所有编译义务；含多态的完整案例中，约 200 个义务仅余约 5 个需手动证明。作者指出当前引擎为顺序实现，面对复杂目标可能超时或耗尽内存，未来需转向并行、高性能的 Datalog 实现，并设想 AI 编码代理通过工具调用该验证器来生成经验证的编译器。

## 12. 修复 Wii U Wii 模式的画面裁剪与色彩溢出问题

- 原始链接: <https://garyodernichts.blogspot.com/2026/11/improving-wii-us-wii-mode.html>
- 英文标题: Improving the Wii U's Wii Mode

Wii U 的 Wii 模式（vWii）通过 DMCU（显示微控制器单元，一颗 68HC11 兼容的 8 位 CPU）模拟 GameCube/Wii 的 VI 视频接口，但存在两个长期未修复的问题：强制裁剪（模拟过扫描裁掉最多 16 像素）和色彩溢出（角色边缘出现绿色偏色）。作者对 DMCU 固件进行了逆向工程，发现该芯片并非 Wii U 独有，AMD 的 Raven、Navi 12 等 GPU 中同样存在基于 M68HC11 的 DMCU。作者使用 2006 年版的 GCC 3.3.6 工具链将固件完整反编译为 C 代码，发布为 OpenDMCUFirm 项目。色彩溢出的根因是 IRQ 处理函数中一处笔误：本应检查 eventFlags 中的事件活跃位，却错误地读取了硬件寄存器 irqStatus，导致事件 2 和 3 被永久卡在「重触发」状态而不再执行。事件 2 负责根据图像水平原点设置 CBCR_SWAP 位，其逻辑也曾被任天堂在后续固件中反向修正以掩盖问题。作者将两处笔误修正后，裁剪问题可通过直接修补固件中视口寄存器值解决，色彩溢出则通过修正 IRQ 判断和 CBCR_SWAP 条件消除。修复版已集成于 OpenDMCUFirm 的自定义分支，可配合 evWii 加载使用。

## 13. 用 Go 语言构建游戏：实体组件系统（ECS）

- 原始链接: <https://threedots.tech/post/making-games-in-go-ecs/>
- 英文标题: Making Games in Go: Entity Component System (ECS)

本文是 Miłosz Smółka 用 Go 语言做游戏开发的系列文章，重点介绍实体组件系统（ECS）架构。作者先指出传统面向对象的写法（每个游戏对象自带 Update 和 Draw 方法）在复杂度上升后难以维护，继承模型也无法灵活应对「NPC 变敌对」「临时接管敌人」等需求。ECS 将游戏拆为三部分：实体（仅一个 ID，无行为）、组件（纯数据结构，如位置、颜色、速度）、系统（遍历特定组件组合并执行逻辑）。作者选用 Donburi 库配合 Ebitengine 引擎，通过一个彩色方块示例演示完整流程：注册组件类型、在 World 中创建实体、用 Query 和 filter.Contains 筛选实体、在渲染系统中遍历并绘制方块；随后加入 Velocity、Rotation 组件和 Clickable 标签，实现点击方块使其随机旋转下落的效果。作者强调 ECS 的最大价值不仅是性能（同类组件内存连续），更是思维模型的转变——系统只关心组件组合而非具体实体类型，组件可动态增删，比继承更灵活。文章还提到，即便 AI 能一键生成游戏，亲手搭建脚手架仍有助于理解软件概念、保持清晰的思维模型。文末预告了一个更完整的水族箱模拟游戏，但正文在此处截断。

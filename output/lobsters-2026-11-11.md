## 1. 用 Astro 与 Typst 在构建时自动生成 Open Graph 社交卡片

- 原始链接: <https://eaj.no/posts/open-graph-images-with-typst/>
- 英文标题: Open Graph images with Astro and Typst

作者介绍了一套在 Astro 静态站点构建阶段自动生成 Open Graph 图片的流程，替代了此前手动从 unspash.com 挑选配图的低效方式。核心工具是 Typst——一个兼具 LaTeX 排版质量与 Markdown 易用性的文档引擎，可通过 CLI 将模板渲染为 1200×630 的 PNG 图片，并借助 --input 参数将文章标题注入模板。在 Astro 侧，文章以 Markdown 编写并通过 Content Collection 管理元数据；作者利用 Astro 的 API 路由机制，在 src/pages/posts/[id]/og.png.ts 中定义一个构建时端点：通过 getStaticPaths 遍历所有文章，在 GET 处理器中调用 execFile 执行 typst compile 命令，将标题作为输入生成 PNG 并以 image/png 的 content-type 返回。此外，作者还实现了缓存破坏策略：对 Typst 模板文件与文章标题做 SHA256 哈希，取前 10 位十六进制字符作为 URL 查询参数，确保仅当模板或标题实际变化时才使社交平台缓存失效，避免品牌更新后旧图仍被显示。整套方案无需运行时依赖，所有图片在构建时一次性生成，兼顾了自动化与性能。

## 2. .NET 11 正式发布

- 原始链接: <https://devblogs.microsoft.com/dotnet/announcing-dotnet-11/>
- 英文标题: Announcing .NET 11

.NET 11 作为标准支持周期（STS）版本发布，提供两年支持，覆盖 C# 15、ASP.NET Core、.NET MAUI 及 Windows 开发。语言方面，C# 15 引入联合类型与封闭层次结构，支持编译器检查的模式匹配；F# 11 优化编译器内存使用。SDK 默认启用 Native AOT CLI 主机和常驻 MSBuild 服务器，减少日常开发等待。运行时层面，JIT 移除更多冗余边界检查，Native AOT 接口分发提升吞吐量，Runtime Async 将异步挂起与恢复移入运行时（仍为预览）。AI 生态方面，SDK 内置 MCP 服务器模板，Microsoft.Extensions.AI 提供模型访问抽象，Microsoft Agent Framework 支持智能体与工作流编排。库层面新增 Zstandard 压缩、内存流适配器、LINQ FullJoin 等能力。EF Core 11 优化查询翻译并实验性支持向量搜索。ASP.NET Core 支持联合类型序列化、异步验证、OpenAPI 3.2 及 Blazor AI 组件（实验性）。.NET MAUI 默认采用 CoreCLR 运行时。此外，.NET Skills、MAUI DevFlow 和 Upgrade 画布等工具将 AI 智能体能力引入日常开发流程。

## 3. 奇怪的许可证与开源的未来

- 原始链接: <https://dustri.org/b/weird-licenses-and-the-new-open-source.html>
- 英文标题: Weird licenses and the new open source

文章从IRC频道上关于「脏手许可证」（FHH）和Reticulum许可证的讨论切入，回顾自由软件四大自由与copyleft之争。作者指出，自由软件虽在技术上全面胜利——几乎所有公司都依赖它——但企业几乎不回馈社区，AI时代更使维护者被低质量PR和bug报告淹没。Copyleft虽能部分约束企业，但存在多种绕过手段，如Android的强边界隔离、云租赁模式等。作者认为第0自由（为任何目的运行程序）可能是核心问题所在。Reticulum许可证禁止软件用于伤害人类的系统，FHH许可证则禁止50人以上组织使用及任何促进偏见的用途。这些条款法律上难以执行，但作者认为这恰是设计意图：有法务部门的机构不会采用，从而天然排除资本与威权力量。作者呼吁在Linux发行版中设立「奇怪许可证」仓库，容纳小社区、手工制作的软件，认为在当前世界局势下，不愿代码流入战争机器比40年前自由软件的初衷更为温和。

## 4. 更快的复活节日期计算函数

- 原始链接: <https://www.benjoffe.com/fast-easter>
- 英文标题: A faster Easter date function

本文介绍了一个极快的格里高利复活节日期计算算法（computus），精度覆盖约±1000万年，速度约为典型日期库中easter函数的两倍，且仅使用5次乘法（传统算法需10次以上）。作者通过五个核心技巧实现优化：（1）激进常量折叠——通过添加SHIFT将年份平移至正域，消除算法中的常数项；（2）避免计算year mod 19——利用64位定点乘法将梅冬周期相关项合并为一次乘法；（3）用6/7的定点乘法替代取反，使最终加法适配x86的LEA单指令；（4）采用mod-pad技术将MOD 30转化为按位与操作（&31）；（5）利用3月31天的特性，通过%32截断和右移处理月份溢出，以纯位运算提取月日。文章还提到，该灵感源于Twitter用户用ChatGPT生成的复活节函数（精度1498–14544年），作者将其范围扩展至±1000万年，吞吐量提升5%–15%。此外，借助Z3定理求解器还找到了一个仅覆盖1894–2199年但再快15%–20%的微范围版本。基准测试在Apple M4 Pro和AMD Ryzen 9 9950X3D上验证了新函数相较传统算法约2倍的加速比。

## 5. 基准测试过拟合的下一个层级：GenDB-V 的争议

- 原始链接: <http://databasearchitects.blogspot.com/2026/11/next-level-benchmarking-overfitting.html>
- 英文标题: Next-Level Benchmarking Overfitting

Thomas Neumann 在博客中批评 GenDB-V 系统声称在 TPC-H 上比 Umbra 和 DuckDB 快 22 至 61 倍，认为这是 AI 代理针对基准测试的极端过拟合。他指出，在 SF10 规模下，仅内存带宽（54GB/s）就决定了 540ms 的物理下限，22 倍加速在传统查询处理中不可行。GenDB-V 的加速主要来自两类手段：一是在加载时为每条查询预构建专用辅助结构（如按 s_acctbal 降序排列的供应商列表），使部分查询在 SF100 下近乎常数时间完成；二是直接硬编码数据生成器 dbgen 的布局规律（如客户 k 位于第 k-1 行、订单编号公式），使连接操作变得极廉价。Neumann 强调，形式化验证仅保证结果正确性，与性能无关；一旦数据发生微小变动，专用路径即失效并回退到极慢的通用实现，这在生产环境中不可接受。GenDB-V 作者 Jiale Lao 在评论区回应，承认性能声明过度，澄清该系统定位为面向特定客户的专用引擎而非通用引擎替代品，并承诺以更严格设置重新实验。其他评论者进一步质疑：形式化验证无法约束性能，且现有引擎已具备物理设计、物化视图等专用化能力，独立合成引擎的增量价值尚不明确。文章核心结论是：让 AI 代理针对已知基准测试优化会使该测试失去意义，未来需要未知且动态变化的工作负载来对抗过拟合。

## 6. 构建网络交换机ASIC全芯片：从设计到流片

- 原始链接: <https://essenceia.github.io/projects/expresso/>
- 英文标题: Building a networking switch ASIC chip

作者正在推进一套开源网络设备项目，最终目标是完整路由器，其中网络交换机是关键中间环节。此前他通过Tiny Tapeout完成了三端口交换机的流片，随后获得wafer.space提供的免费全芯片流片机会，但仅有96小时完成全部设计。文章系统介绍了全芯片流片的工程要点：wafer.space由前Google工程师Tim Ansell创立，提供GlobalFoundries 180nm工艺制造服务，按芯片面积（mm²）计费，面积越大良率越低、成本越高，但gf180作为成熟工艺良率优异。晶圆制造后需经切割（dicing）和封装（packaging）才能成为可用芯片；作者选择了CoB（chip-on-board）封装，用透明环氧树脂覆盖芯片，兼具成本与美观。与Tiny Tapeout共享基础设施不同，全芯片需自行处理IO引脚、电源分配和时钟网络。本设计最多可用46个引脚，每个以太网端口通过RMII接口占用7个引脚，引脚环绕核心区域形成padring以隔离噪声并共享电源。IO与核心电源可独立供电，但本设计因gf180标准单元库耐压范围宽（1.62至5.5V），统一采用5V供电。文章末尾附有静态时序分析结果，显示在部分工艺角下存在setup违例，表明设计仍在迭代中。

## 8. 钝锤式封禁：用简单蜜罐拦截基础爬虫机器人

- 原始链接: <https://shkspr.mobi/blog/2026/11/blunt-banhammer-blocks-basic-bots-ballistically/>
- 英文标题: Blunt Banhammer Blocks Basic Bots Ballistically

作者为个人网站 OpenBenches.org 遭遇大量 AI 爬虫（月流量超 2.5TB）的问题，自研了一款名为 B6 的蜜罐封禁工具，一周内封禁逾 400 个 IP，日数据传输量从 216GB 降至约 25GB，降幅超 80%。B6 的核心思路极为朴素：在站点创建 /honeypot/ 目录并在 robots.txt 中声明 Disallow，同时在每页嵌入一个对正常用户不可见（CSS 隐藏、零宽字符、aria-hidden）的链接指向该目录；一旦有访问者触发蜜罐，PHP 脚本即把其 IP 与 User-Agent 写入 .htaccess 的 BLOCKED IPs 区块，服务器随后对该 IP 返回 402 永久拒绝。文章给出了完整的 .htaccess 改写、PHP 脚本及 HTML/CSS 隐藏链接代码，并讨论了潜在问题：误封人类用户、被劫持 IP 殃及无辜、机器人轮换 IP 导致重复封禁、智能爬虫可能识别 /honeypot/ 路径或拒绝点击隐藏链接等。作者强调 B6 是「钝锤」，不区分 User-Agent、国家等信号，触发即封、无警告无申诉，但正因如此对正常用户零干扰、无需特定托管环境。文章以 AGPL v3 协议开源，并建议未来加入地理定位记录与过期自动解封机制。

## 9. Rust 标准库中的内存安全缺陷

- 原始链接: <https://forge-blog.github.io/posts/rust-std-memory-safety/>
- 英文标题: Memory Safety Bugs in Rust Standard Library

微软 FORGE Lab 借助 AI 驱动漏洞扫描工具 Hyenas（代号 MDASH 的研究版），在 Rust 标准库 std 与 core 中发现多起内存安全缺陷，其中部分缺陷仅用纯 safe Rust 即可触发未定义行为。文章归纳出三类「错误信任」模式：一是信任代码不会 panic——例如 MapWindows::clone 在克隆过程中若用户实现 panic，析构器将访问未初始化内存；新稳定的 Allocator API 最终要求实现者绝不 unwind，因「从分配相关方法中 unwind 是普遍的不健全来源」。二是信任用户提供的 trait 实现正确——如 str::replace 的快路径假设单字节 StringPattern 必为 ASCII，但自定义 Pattern 可返回 0x80 等非法字节，导致生成非 UTF-8 的 String；join 函数也曾因 Borrow 返回值不一致而两次修复。三是信任底层系统状态——子线程调用 process::exit 会拆除主线程的备用信号栈，若主线程随后栈溢出将直接段错误而非打印 Rust 的友好提示。文章强调，Rust 正被 GitHub Copilot、Bun、Android、Linux 内核、Cloudflare 等关键项目采用，标准库的不健全缺陷影响远超其自身。修复思路包括用 ManuallyDrop 保护半构建状态、将类型约束编码进签名、避免跨线程清理全局资源等。

## 10. 单进程多应用：用共享资源消除部署开销

- 原始链接: <https://andersmurphy.com/2026/11/09/two-apps-one-process.html>
- 英文标题: Two apps one process

作者 Anders Murphy 提出一种极简架构思路：将多个应用运行在同一个 JVM 进程中，而非各自独立部署。他指出，绝大多数应用的并发用户仅 10 到 20 个，追求单核万级并发对实际项目意义有限；真正有价值的是把性能余量转化为「在单进程内塞入任意数量应用」的能力。独立进程各自维护堆、JIT、GC、线程池、HTTP 服务器、渲染引擎等，固定成本随应用数线性增长（公式 X×n，500MB 固定成本下 4 个应用即多出 1.5GB）。单进程方案则让所有应用共享一个 JVM、一个 HTTP 服务器、一个框架引擎、一套 HTTPS 证书管理（通过纯 Clojure 实现的 Clave 库对接 Let's Encrypt ACME），从而消除线程竞争与资源重复。应用本身被简化为「域名 + 数据库 + 路由」的声明式配置；打包时将各应用作为依赖引入一个启动项目，构建 uberjar 后 scp 到服务器即可。作者展示了三个应用（billion-cells、billion-checkboxes、game-of-life）同时运行在同一台 10 美元 VPS 的同一 JVM 上，部署过程等同于一次网络抖动，将新增应用的边际成本压到接近零。

## 11. 《星球大战：幽灵威胁》赛车游戏中的远程代码执行漏洞研究

- 原始链接: <https://synacktiv.com/en/publications/star-wars-episode-i-racer>
- 英文标题: Finding a vulnerability in Star Wars Episode I: Racer

本文由Thomas Dubier撰写，针对1999年LucasArts发行的赛车游戏《星球大战：幽灵威胁》（GOG版1.0，Windows平台）的局域网多人模式协议进行逆向分析，并揭示了一个允许远程代码执行（RCE）的漏洞。研究首先通过Wireshark抓包发现游戏在UDP 54792端口上以广播方式发送游戏发现包，初步判断其使用DirectPlay协议，但因「play」标识偏移量不符而未被Wireshark自动识别。随后通过IDA静态分析定位DirectPlay的CLSID，确认游戏调用IDirectPlay4接口，并明确选择IPX网络服务提供者。进一步分析发现，游戏通过ipxwrapper项目将IPX报文封装进UDP数据报，作者据此编写了自定义Wireshark dissector（packet-ipxwrapper.c），实现了对IPXwrapper头部及内嵌DirectPlay报文的完整解析，并修复了DirectPlay dissector对缺少可选头部字段的兼容问题。在应用层消息处理方面，作者追踪了IDirectPlay4A的Receive调用链，梳理了系统消息（如DPSYS_CREATEPLAYERORGROUP、DPSYS_HOST等）与用户消息（类型0x21、0x22、0x28、0x20）的分发逻辑，指出游戏在DirectPlay API之上还维护了独立的玩家状态管理。文章最终指向一个可触发远程代码执行的漏洞，但正文在消息处理细节处截断，未完整展示漏洞利用过程。

## 1. 自托管邮件服务器：大家在用什么方案？

- 原始链接: <https://lobste.rs/s/rwloew/email_self_hosters_what_are_you_using>
- 英文标题: Email Self Hosters - what are you using?

这是一篇论坛讨论帖，发起者使用 maddy 为多个域名自托管邮件，主要痛点是 iOS 原生邮件客户端连接和下载速度慢，影响 OTP 验证码接收。帖子引发 67 条回复，参与者分享了各自的邮件栈：经典组合 Postfix + Cyrus IMAPD 仍有大量用户坚守（有人已运行 27 年）；OpenBSD + OpenSMTPD + Rspamd + Dovecot 因配置简洁备受青睐；NixOS Mailserver 配合 SMTP2GO 中继解决 IP 声誉问题；轻量级方案 Mox 以零 Docker、零外部数据库吸引新手；Stalwart 因内置 JMAP 和 DAV 被部分用户从 Postfix 迁移过来，但文档和外部目录认证仍是短板；mailcow、docker-mailserver 等容器化方案适合非技术用户。讨论中反复出现的痛点包括：住宅 IP 声誉差导致被 Gmail 等拒收、Rspamd 配置复杂、灰色列表延迟 MFA 邮件、备用 MX 难以同步反垃圾状态、DMARC 强制要求等。也有用户表示每月几美元托管（如 Migadu）比自托管更省心。整体结论是：邮件自托管在 2026 年仍可行但维护成本上升，IP 声誉和垃圾邮件过滤是最大挑战，新工具在简化配置方面有所进步但成熟度不足。

## 2. Brut：面向 Unix 工具的极简命令路由器

- 原始链接: <https://brut.sh>
- 英文标题: Brut, the Brutal Router for Unix Tools

Brut 是由 Sam Stephenson 编写的一个纯 POSIX shell 脚本，定位为「粗暴而极简」的 Unix 工具命令路由器（router），项目地址为 brut.sh。其核心思想是：将主程序与子命令拆分为独立可执行文件，通过 PATH 中的符号链接（命名约定如 brut-xxx）实现子命令分发，无需任何外部依赖。脚本启动时先建立 LIB、LIBEXEC、SHARE、VENDOR 等目录结构并扩展 PATH，随后定义了一组辅助函数：namespaces 通过扫描符号链接识别命名空间，executables 在 PATH 中按命名规则查找可执行文件，resolve 将用户输入的命令名匹配到具体路径，invocation 则拼接完整的调用前缀。参数解析阶段，脚本遍历参数列表提取首个非选项参数作为命令名，若匹配成功则 exec 对应可执行文件；若未匹配则尝试加载 _unhandled.sh 钩子，最终回退到用法提示。此外，脚本还支持以「---」前缀直接透传执行任意命令、将「--version」重写为内部子命令、以及加载 _init.sh 进行初始化。整体设计体现了 Unix 哲学中「小工具组合」的精神，代码量极小却覆盖了路由、命名空间隔离、钩子扩展等完整能力，采用 MIT 许可证发布。

## 3. Montray：面向 systemd 服务健康监控的轻量托盘图标工具

- 原始链接: <https://github.com/dimonomid/montray/>
- 英文标题: Montray - a tray icon for systemd service health

Montray 是一款轻量级系统托盘监控工具，旨在解决 Linux 下 systemd 服务故障时缺乏醒目提醒的问题。项目源于作者 2021 年 Syncthing 服务静默宕机数周才被发现的经历。Montray 由两部分组成：montray-server（Go 编写）运行在被监控机器上，通过只读 WebSocket API 上报事件；montray-ui（Rust + Slint 编写）作为桌面客户端，连接一个或多个 server，在托盘显示状态图标并发送桌面通知。托盘图标以颜色区分状态：绿色表示正常，黄色闪烁表示警告，红色闪烁表示错误，品红闪烁表示 UI 自身连接异常。监控范围不仅限于 systemd 服务，还支持任意命令行检查（如磁盘空间、RAID 健康）。远程监控通过 SSH 隧道实现，UI 端配置即可自动分配本地端口。默认配置将 systemd 服务失败视为警告、根分区剩余空间不足 100 MiB 视为错误。客户端理论上可在 Windows 和 macOS 运行以监控远程 Linux 服务器，但服务端在非 Linux 平台意义有限。开发需 Go 1.26 与 Rust 1.92，提供 Makefile 构建与测试流程。

## 5. 什么是 Codemode：Pi 1.0 中的 MCP 编排机制

- 原始链接: <https://lucumr.pocoo.org/2026/10/6/codemode/>
- 英文标题: What is Codemode

Armin Ronacher 在 Pi 1.0 发布后撰文解释 Codemode 的定位与意义。他此前主张「代码即一切」，反对向上下文加载自定义工具或 MCP 服务器，如今 Pi 通过 Codemode 正式支持 MCP，看似矛盾实则一脉相承。文章首先厘清架构：harness（大脑）与执行环境（手）分离，前者可信、后者可沙箱化；bash 擅长组合可执行程序，但图像读取、子代理等原生操作无法用 bash 表达。Codemode 正是让 LLM 在 harness 侧以 JavaScript（运行于 QuickJS/WASM 沙箱，无网络、无文件系统、有限内存）编排工具调用的机制，支持并发、状态暂存（store）及跨调用复用。作者给出多个真实会话示例：调用图像生成 API、用分类器 Jev 批量分析 GitHub issue 情感、驱动坦克游戏引擎进行 30 步调试循环、以及通过渐进式发现调用 Sentry 等 MCP 服务器。同时他坦承 MCP 生态尚未适配 Codemode，存在结构化输出缺失、结果不一致、大二进制数据不支持、多服务器工具搜索不可组合等问题，Cloudflare 的「Codemode 套 Codemode」方案导致双重 JSON 转义，体验不佳。未来方向包括引入持久化工作流引擎、考虑用确定性语言 Starlark 替代 JavaScript、完善图像与二进制数据支持。总体而言，Codemode 并非对 CLI 路线的否定，而是将其扩展为 harness 内部更自由的编排层。

## 6. 我们所知的开源已死

- 原始链接: <https://jross.me/open-source-as-we-know-it-is-dead/>
- 英文标题: Open Source as We Know It Is Dead

作者是一位游戏服务器开发者，2011年注册GitHub，从早期开源社区中受益至深。文章核心论点是：AI正在杀死传统意义上的开源协作。过去，一个陌生人提交PR、维护者耐心合并，这种「看见你、一起做事」的互动构建了互联网基础设施；如今，AI让生成PR的成本趋近于零，但审查成本未降反升，大量低质量、幻觉式、批量刷量的AI垃圾PR涌入，维护者不堪重负。作者列举了大量项目关闭外部贡献的案例：curl终止赏金计划（真实报告不足5%）、tldraw自动关闭外部PR、OpenJDK禁止LLM贡献、Ladybird停止接受公共PR、Godot要求代码由人类编写、Sindre Sorhus关闭全部仓库外部PR、Hono也关闭了外部PR通道。GitHub自身亦于2025年2月发文称「开源的永恒九月」已至，并陆续推出关闭PR、限制提交者等功能。作者承认自己日常使用AI，但指出成本只是从贡献者转移到了本已超负荷的志愿者维护者身上。他不知道解法，但深感哀伤：当所有维护者都做出「关门」这一理性选择时，开源便不再是那个让陌生人愿意走进去的地方。

- 英文标题: Pared - remove unwanted Apple Intelligence models without disabling SIP

Pared 是一款面向 Apple Silicon 及 macOS 27 及以上系统的 macOS 工具，允许用户在不禁用系统完整性保护（SIP）的情况下，选择性地移除不再需要的 Apple Intelligence 模型。该工具提供原生应用、终端安装向导以及 Nix 模块三种使用方式，无需 Xcode 或 Homebrew 即可完成安装。用户可逐项将写作工具、Genmoji 等功能设为「开启」「关闭」或「应用默认」，新策略默认全部关闭，保存前需审查确认。配置流程分为三步：选择功能、在系统设置中安装 Pared 生成的配置描述文件以阻止后续模型下载、确认移除哪些模型。功能设置与模型移除为两个独立操作；若需恢复某功能，重新开启并安装更新后的描述文件，再通过 Pared 或对应 Apple 应用请求下载模型。Pared 会保留用户仍在使用或未管理功能所依赖的共享模型。此外，Pared 支持通过 nix-darwin 或 Home Manager 模块以声明式方式管理配置，默认在激活时清理模型，可通过设置 cleanupOnActivation = false 关闭该行为。源码构建需 Xcode 27 及以上版本。其底层机制依赖 Apple 的 asset service 完成模型移除，具体实现与兼容性限制详见官方文档。

## 9. 为何应当进行依赖注入

- 原始链接: <https://gist.github.com/alassek/1a185a8cdae20ddd991a8cd3cd90d347>
- 英文标题: Why We Should Inject Dependencies

本文论证了在 Ruby 中采用依赖注入（DI）的必要性，反驳了 Ruby 社区传统上视 DI 为不必要复杂性的观点。文章首先区分「依赖」与「参数」：依赖是对象生命周期内可复用的外部接口引用（如 EmailValidator、UserRepository），参数则是单次请求的输入值（如 email、password）。作者建议将所有依赖通过 initialize 显式声明，使类的依赖关系一目了然，并便于在测试中以替身替换，避免 stub 全局 API。针对依赖过多导致 initialize 冗长的问题，文章引入 Dry::Initializer 的 option DSL，消除重复的 kwargs 定义与实例变量赋值。进一步地，当需根据特性开关动态选择实现时，作者借助 Dry::Core::Container 注册命名键，配合 Dry::AutoInject 的 include Deps 语法，将对象构造细节从调用方中剥离。最终结论是：类的职责是定义依赖关系与公共接口，实例的职责是执行业务逻辑，二者应作为独立关注点分离；Ruby 的灵活性使 DI 可以比 Java 中更轻量地实现。

## 10. 用 Zig 扩展 Lua（一）：Hello World

- 原始链接: <https://www.robbielyman.com/blog/extend-lua-with-zig-1/>
- 英文标题: Extend Lua with Zig 1: Hello World

本文为 Robbie Lyman 撰写的系列教程首篇，面向熟悉 Lua 但零基础 Zig 的读者，目标是逐步实现从 Lua 调用自定义 Zig 函数。文章首先给出 Zig 的 Hello World 示例，讲解 @import() 编译器内建函数与 comptime 即时执行机制，并将其与 Lua 的 require 和脚本加载进行类比。作者指出 Zig 顶层作用域默认即 comptime 上下文，但过程式代码须放入命名 block 中执行；函数必须命名，不能像 Lua 那样匿名赋值；容器作用域声明默认私有，需加 pub 修饰方可被外部（如标准库 start.zig）调用。此外，所有 Zig 函数原则上均为泛型，std.debug.print 的 fmt 参数标记为 comptime 以便编译期校验。文章随后引入 Zig 构建系统：编写 build.zig 脚本，通过 b.addModule 将源文件注册为模块，用 b.addExecutable 编译为可执行文件，再通过 b.step 与 b.addRunArtifact 定义「run」步骤，使 zig build run 可编译并运行产物。作者还提及 @import() 的相对路径限制、zig fmt 自动格式化行为，以及 std.debug.print 实际输出到 stderr 而非 stdout 等细节。代码兼容 Zig 0.17 稳定版与 master 分支。

## 11. OSC 7501：面向程序状态的终端协议

- 原始链接: <https://mitchellh.com/writing/program-status-osc7501>
- 英文标题: A Terminal Protocol for Program Status (OSC 7501)

Mitchell Hashimoto 于 2026 年 10 月发布了一项名为 OSC 7501 的终端转义序列规范，即「程序状态协议」。该协议允许任何程序通过 pty 向终端报告自身状态，包括空闲、工作中、等待用户、完成和失败五种基本状态，并可附带原因、进度百分比及层级任务树。文章指出，终端中长时间运行的任务（构建、部署、编码代理等）日益普遍，用户需要及时了解任务进展或介入请求，但现有方案——如终端监控前台进程切换、等待输出静默期——缺乏统一性；而针对 AI 代理的「代理收件箱」工具则依赖启发式屏幕匹配或带外 socket API，维护成本高且无法跨 SSH 或容器使用。OSC 7501 以纯终端原生方式解决这一问题：序列体为以冒号分隔的 key=value 对，唯一必需键为 state，可选键包括 app（机器可读名称）和 msg（base64 编码的人类可读消息）。协议设计完全通用，不偏向任何 GUI 或特定工作负载，用 POSIX shell 脚本即可集成，无需 SDK、socket 或 JSON。Hashimoto 已在 libghostty、Rex 及 Terraform、Claude Code、Codex、Homebrew 中完成原型实现，每次仅需十余行代码。规范还涵盖记录生命周期、特性检测、terminfo 兼容、大小限制与安全等内容，篇幅简短，作者呼吁终端与程序开发者共同采用，终结靠读取屏幕或进程树猜测程序状态的时代。

## 12. Chrome 应对近期 ccTLD 注册机构劫持事件

- 原始链接: <https://blog.google/security/chromes-response-to-recent-cctld-registry-hijacks/>
- 英文标题: Chrome's Response to Recent ccTLD Registry Hijacks

2026年10月，.gh（加纳）、.sl（塞拉利昂）、.as（美属萨摩亚）三个国家代码顶级域名遭遇注册机构劫持。攻击者入侵第三方 ccTLD 注册机构，篡改权威 DNS 记录并获取了覆盖 Google 及多家组织域名的未授权 HTTPS 证书，签发 CA 本身并无过错。Chrome 安全团队随即通过 CRLSets 在浏览器端阻断相关证书，并协同 CA 完成吊销。证书透明度（CT）日志进一步显示更多全球品牌和服务受影响，Chrome 主动扩展阻断范围并通知相关方。Chrome 用户无需任何操作即可获保护。文章建议域名所有者采取两项防御措施：一是持续监控全部域名的 CT 日志（含停放或区域性 ccTLD 属性），以近乎实时方式发现异常证书签发；二是发布限制性 CAA 记录并绑定 ACME 账户，防止攻击者在 DNS 恢复后利用缓存的域名控制验证（DCV）状态签发新证书。Chrome 还承诺通过 Chrome Root Program 及抗量子根证书计划，推动缩短证书有效期、减少 DCV 复用等长期 HTTPS 生态改进。

## 13. 紧急漏洞修复：补丁交付的挑战与应对策略

- 原始链接: <https://projectzero.google/2026/10/emergency-patching.html>
- 英文标题: How to fix a bug in a fix

本文由Project Zero发布，面向软件供应商，探讨在补丁交付系统受限的情况下如何快速修复正在被利用的漏洞。文章首先梳理了补丁的完整流程——分诊、开发、测试、合作伙伴审查、交付与激活，指出紧急补丁的瓶颈通常不在分诊和开发，而在测试与交付环节：测试不足可能导致设备变砖或数据损坏，而交付受限于更新探测间隔、用户行为、重启需求等因素。文章随后介绍了四类紧急修复手段：一是功能开关（Feature Flags），如Apple 2019年FaceTime事件及Meta的「双栈」库方案，优势是测试可提前完成、下发数据量极小；二是过滤（Filtering），如Android Intent Firewall和Microsoft Defender，通过动态规则拦截特定输入，灵活性高于功能开关但需关注性能开销；三是替代更新通道（Alternate Channels），如Android APEX和动态库热加载，可绕过常规更新周期，但须确保来源验证；四是热补丁（Hotpatching），如Linux Livepatch和Windows hotpatch，可在运行进程中直接替换函数，无需重启，但存在绕过缓解机制的安全风险。文章最后强调，在大模型加速漏洞发现与利用的当下，供应商应提前盘点现有更新机制、填补快速修复能力的空白，以应对大规模活跃利用的极端场景。

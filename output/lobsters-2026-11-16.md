## 1. 40个主流C项目内存管理策略调查

- 原始链接: <https://theconsensus.dev/p/2026/11/08/c-memory-management-survey.html>
- 英文标题: Memory management in 40 major C projects, a survey

The Consensus 的 Phil Eaton 对 40 个主流 C 项目（涵盖 Web 服务器、数据库、操作系统、压缩库、开发工具等）的内存分配策略进行了系统调查，排除测试代码和第三方代码后，按分配调用点统计各策略占比。核心发现：仅 8 个项目（如 SQLite、zlib、LZ4、brotli 等）完全依赖 malloc/free；仅 2 个项目完全不用 malloc/free；15 个项目在某种程度上使用区域（region）分配，其中 pgvector、TimescaleDB、Citus、nginx 等 7 个项目以区域分配为主；5 个项目（Ruby、Julia、Emacs、OCaml、Lua）以垃圾回收为主；3 个项目（CPython、PHP、Perl）以引用计数为主。值得注意的是，以正确性著称的 SQLite 仍 100% 手动分配，cURL 和 Redis 也分别有 94% 和 79% 的手动分配。另一亮点是 Linux 和 QEMU 近年开始引入基于编译器扩展的作用域自动清理机制（如 Linux 的 __free(kfree) 和 QEMU 的 g_autofree）。seL4 作为微内核无堆分配，是特例。文章表明，C 生态中高层内存管理原语（区域、引用计数、垃圾回收、作用域清理）的使用远比通常认知广泛，纯手动管理并非唯一选择。

## 3. 按钮上的 cursor: pointer 终于被 CSSWG 采纳

- 原始链接: <https://blog.kizu.dev/cursors/>
- 英文标题: cursor:pointer on buttons

2026年11月，CSS工作小组（CSSWG）在会议上正式决议：为 button、select、option、checkbox、radio 等交互元素在 appearance: base-* 模式下默认应用 cursor: pointer。该规则并非修改浏览器默认样式，且未使用 !important，开发者可自由覆盖为 default 或其他值。作者自2013年发表「Correct Cursor on Active Elements」一文起便倡导此观点，2017年提交首个 CSSWG issue 推动规范变更。文章回应了「操作系统不这样做」这一常见反对意见，指出 Discord、Slack、VS Code 等主流非原生应用早已在交互元素上使用 pointer 光标，而默认光标仅能指向像素，无法传达「可点击」的语义。作者同时认同按钮与链接应有不同光标、新标签页链接也需区分，认为需要更多光标类型；但若仅两种光标分配给空白区域、按钮和链接，按钮显然应与链接归为一类，而非与空白区域。整体而言，这是一篇立场鲜明的观点文，庆祝 CSSWG 对交互元素光标规范的推进。

## 4. FreeBSD bhyve 虚拟机热迁移：跨主机迁移原型实现

- 原始链接: <https://gyptazy.com/blog/freebsd-bhyve-live-migration-support-rfc/>
- 英文标题: FreeBSD bhyve Live Migration: Moving VMs Between Hosts

本文介绍了 FreeBSD 15.1 上 bhyve 虚拟机热迁移的首个可工作原型（WIP RFC）。该实现基于 bhyve 实验性快照支持，在 vmm 内核模块中新增脏页跟踪，并在 bhyve 与 bhyvectl 中构建迁移协议。迁移流程采用预复制阶段（反复传输脏页位图）加最终停机拷贝阶段，支持多 vCPU 暂停与恢复、内存一致性校验、磁盘 fsync 写入验证及迁移失败回滚。当前仅支持 amd64 架构，依赖 BHYVE_SNAPSHOT，不支持 PCI 直通。测试中 512 MiB guest 停机时间约 138–171 ms，快速脏页 guest 可回退至 stop-and-copy 模式。作者强调该能力对 Sylve（类 Proxmox 虚拟化方案）和 BoxyBSD（免费 BSD VPS）项目至关重要。上游化前仍需解决：脏日志并发正确性证明、完整兼容性契约（CPU 能力、设备拓扑、共享存储身份）、传输层认证与加密、提交点设备副作用边界、存储与网络交接规范、自动化回归测试及补丁拆分。作者已将代码发布至 git.gyptazy.com 与 GitHub，邀请社区测试与反馈，后续将推进压缩、零页省略、更广设备覆盖及性能调优。

## 5. 面向FIRST机器人竞赛的周期性导向编程

- 原始链接: <https://bvisness.me/periodic-oriented-programming/>
- 英文标题: Periodic-Oriented Programming for FIRST Robotics

一位拥有17年FIRST机器人竞赛（FRC）编程经验的作者，在离开竞赛后提出「周期性导向编程」（POP）理念，批评FRC社区长期过度工程化的编程实践。POP的核心是：将逻辑集中在每秒调用50次的periodic函数中，减少抽象，以直线式代码表达控制。作者提出四条原则：一是硬件封装在子系统中，仅通过periodic方法访问，确保每周期只写入一次；二是以「追求期望状态」为框架，从执行器到整机统一采用目标导向控制；三是最小化程序状态，避免模式切换、定时器和冗余变量；四是坚决摒弃WPILib命令式编程，认为其状态不可预测、逻辑分散、调试困难。作者展示2025年赛季实际代码，仅25行完成全部遥操作驱动逻辑，而命令式方案需100至200行。他承认这种风格看似过于简单，但认为适用于95%以上的FRC团队，能避免命令冲突与执行顺序混乱，在竞赛现场快速修改代码时尤为可靠。

## 6. 拟人化软件：当程序学会「说话」

- 原始链接: <https://aspiz.uk/wiki/AnthropomorphicSoftware>
- 英文标题: Anthropomorphic Software

作者提出「拟人化软件」这一概念，指那些在提示信息中采用第一人称、人格化语气的程序，并强调这与 LLM 等对话式 AI 不同。文章列举了大量经典案例：Git 在首次提交时问「请告诉我你是谁」，在 bisect 失败时喊「我们不能再二分查找了！」；patch 命令说「嗯……我好像找不到补丁」；GNU tar 拒绝创建空归档时自称「胆小地拒绝」；Elm 语言编译器以极端拟人方式解释语法错误，甚至手把手教用户删逗号；sudo 开启 insults 选项后，输错密码会遭到程序「辱骂」；Bash 在无名称时喊「我没有名字！」；Nmap 在 9 月 1 日给自己祝 29 岁生日快乐，12 月 25 日祝用户圣诞快乐。作者认为这类设计主要出于趣味性（whimsy），并非真正改善用户体验，并引用 Apple 界面指南指出应避免「oops」类措辞。文章最后指出，LLM 代理是拟人化软件的终极形态，但作者出于个人 sanity 强制代理不以人类口吻说话，并担忧未来代理成为默认交互范式后，这种恰到好处的拟人趣味将消失。

## 7. NetBSD 磁盘加密实现数据保密

- 原始链接: <https://netbsd.org/~nia/disk-encrypt/>
- 英文标题: Disk encryption on NetBSD achieving secrecy

本文介绍在 NetBSD 上以「小未加密根分区 + 大加密分区」的折中方案实现磁盘加密，兼顾启动可行性与数据保密。文章先明确设备丢失与设备篡改两种威胁模型，聚焦前者。作者将数据分为开源系统文件与用户修改文件，指出 /home、/var、/usr、/etc 等目录最需保护，其中 /etc 因含启动必需文件处理较复杂。安装时先建约 4 GB 未加密根分区，剩余空间划为 cgd 加密分区。配置时使用 argon2id 密钥派生，加密算法可选 adiantum（无硬件加速场景）或 aes-cbc；通过在加密分区内嵌入 disklabel 或 GPT 表来验证密码正确性。文章分别给出 disklabel（sparc64）与 disk wedges（GPT/UEFI）两套完整操作路径。最终将 /home、/var、/usr 迁移至加密分区并以符号链接替换，在 rc.conf 中设置早期挂载。需注意：此方案下安装程序不感知加密分区，系统升级须使用 sysupgrade 等在线工具，不可用离线安装介质。

## 8. 在 BQN 中解析嵌套列表的三种方法

- 原始链接: <https://saltysylvi.github.io/blog/parsing-nested-lists-in-bqn.html>
- 英文标题: Parsing nested lists in BQN

本文以 Advent of Code 2022 第 13 题（解析嵌套列表）为背景，展示了在 BQN 语言中实现嵌套列表解析的三种方案并进行基准测试。第一种是「取巧」法：将方括号替换为尖括号后调用 BQN 的系统函数 •BQN 直接求值，实现最简但对大输入会触发段错误，且 100 次运行约需 0.74 秒，速度最慢。第二种是经典递归下降解析器，采用先分词再解析的两阶段流程，分词器利用数组掩码和求和扫描将字符串切分为方括号与数字标记，解析器按文法 Value→List|Number 递归构建结果；100 次运行仅约 0.007 秒，比第一种快约 10 倍。第三种是数组风格解析器，核心思想是按嵌套深度对标记重排，再用右折叠自底向上将子列表「插入」到对应闭合括号位置，初始版本约 0.015 秒，虽慢于递归下降，但展示了仅用算术和原语（如 ⊔、折叠）处理递归数据结构的巧妙思路。作者进一步提出将分词器输出改为扁平字符串加数字列表以消除逐元素比较的开销，文章在优化过程中截断。总体而言，递归下降法在 BQN 中兼具正确性与速度，而数组风格法在概念上颇具启发性。

## 9. 重新介绍 Spaces：atproto 的新社交原语

- 原始链接: <https://dholms.leaflet.pub/3mu3p3ldwrc26>
- 英文标题: Reintroducing Spaces

atproto 协议栈推出了新原语 Spaces（空间），目前已发布 alpha 版本。Spaces 旨在为多用户社交场景（如十万级论坛）提供非公开数据的共享机制，同时保持 atproto 的核心直觉：记录由用户发布并存储于其 PDS，权限归于作者 DID，应用通过爬取和同步构建视图。设计目标还包括「氛围感」——同一数据可在不同应用中以不同形式呈现，以及安全且用户可理解。每个空间代表一个共享社交上下文，记录「在」且仅在「一个」空间中，空间绑定特定模态并由单一实体拥有，可类比为「迷你 atproto」，使审核、账户迁移等难题可直接沿用现有方案。文章将 Spaces 与 Google+ 式的「圈子（Circles）」方案对比：圈子以内容为中心、受众为附加属性，在跨应用、跨 PDS、跨模态的复杂网络中会产生认知负担和权限混乱；而 Spaces 以空间为中心，内容发布进空间后所有访问者获得一致视图。作者提出「Daniel 的圈子公理」：只有同一实体创建且同一模态的两个圈子才能安全共享记录。文章承认 Spaces 对「每条记录面向不同受众」的场景并非最优，但可通过将内容放入空间后由应用管理访问逻辑来应对。作者呼吁社区参与 alpha 测试并提供反馈。

## 10. clice v1.0 发布：拥抱现代 C++

- 原始链接: <https://www.ykiko.me/en/articles/2105384023094834022/>
- 英文标题: clice v1.0 Released: Welcome to Modern C++

clice 是一个用 C++23 编写的 C/C++ 语言服务器，基于 LLVM/Clang 但完全重新设计架构，于 2026 年 10 月发布首个稳定版 v1.0。项目历时两年半、约 3000 小时，由独立开发者完成。核心亮点包括：采用浏览器式多进程编译池隔离编译器崩溃风险；完整支持 C++20 命名模块及跨会话 PCH/PCM 缓存；支持非自包含文件的编译上下文自动检测；通过 DFS 伪实例化改善模板导航；内置 50+ 工具链探测实现开箱即用。技术上全面使用 C++20 协程、命名模块与 import std、基于模板和 concepts 的静态反射、数据导向设计，并以 Bazel 和 xclang 工具链实现可复现构建。除语言服务器外，clice 还提供 index、lint、refactor、modularize 等命令行子命令，可直接操作持久化索引完成重命名、模块拆分等操作。作者解释不改进 clangd 的原因：clangd 自 2024 年起基本失去维护，架构改动量等同于重写，LLVM 仓库的自包含约束也阻碍引入第三方库。开发后期借助 AI 编码代理大幅加速，作者也由此思考语言服务器在 AI 时代的定位，主动转向 CLI 功能设计。

## 11. Strata：将内存视为显式 I/O

- 原始链接: <https://yrashk.com/strata/>
- 英文标题: Strata — memory is explicit I/O

本文介绍了 Strata 架构中一种激进的内存模型设计：将内存访问完全当作显式 I/O 操作，以「本地存储（Local Store）」取代传统硬件缓存。在该设计中，每个核心配备 64 KiB 的数据本地存储和 64 KiB 的指令本地存储；访存指令（load/store）只能触及寄存器与该核心的数据本地存储，指令取指也只能来自指令本地存储。L1 不再承担自动缓存的职责，而是被重新定位为架构级暂存区（architectural scratchpad），其中存放什么内容完全由软件决定，而非由硬件替换策略自动管理。这一设计将缓存管理的控制权从硬件转移到软件，使程序员或编译器能够显式控制数据在本地存储中的驻留与迁移，从而获得更高的确定性和可预测性。原文篇幅较短，仅给出了上述核心设计要点，未展开讨论性能数据、具体指令集细节或与现有架构的对比。

## 12. Rust 声明式宏：组织方式、作用域规则与常见用例

- 原始链接: <https://sigseis.dev/articles/2026/11/10>
- 英文标题: Rust Declarative Macros: Organization, Scoping, and Common Use-Cases

本文基于 Rust 2024 版，系统讲解如何将声明式宏集成到 crate 中。作者将宏分为 crate-local（仅 crate 内部使用）和 crate-exported（对外导出）两类，并强烈建议优先保持宏为 crate-local，仅在确有必要时才导出，以降低维护负担。作用域方面，文章对比了文本作用域（按定义位置生效、顺序敏感、子模块自动可见）和路径作用域（通过 pub(crate) use 注册到模块树、顺序无关、可像普通 item 一样导入），推荐优先使用路径作用域。导出宏需使用 #[macro_export]，该属性会将宏固定绑定到 crate 根路径；若希望宏出现在子模块路径下，需配合 #[doc(hidden)] 与 pub use 重命名来隐藏根路径暴露。宏卫生方面，作者提醒 crate-exported 宏应使用 $crate 元变量引用自身 crate 内的类型，避免直接写 crate 关键字；依赖外部 crate 时可通过隐藏的 __private 模块重新导出。组织策略上，作者建议每个宏单独建文件，再通过组织模块统一 re-export，便于定位与维护。常见用例包括：为语义相近的类型批量实现 trait 或函数、构建类似 format! 的表达式宏、初始化复杂类型、以及减少重复样板代码。

## 13. 递归下降解析器的两个问题（2009）

- 原始链接: <https://eli.thegreenplace.net/2009/03/14/some-problems-of-recursive-descent-parsers>
- 英文标题: Some problems of recursive descent parsers (2009)

本文针对作者此前介绍的递归下降（RD）解析器，指出并解决两个实际问题。问题一是运算符结合性：原BNF中expr规则将expr置于右端以避免左递归，但由此导致减法和除法被错误地按右结合求值（如5-1-2算出6而非2）。作者提出用EBNF的重复语法（花括号表示零次或多次）重写规则，并将递归调用改为while循环，使加减乘除按从左到右的左结合方式累加结果；而幂运算等天然右结合运算符仍保留递归定义。问题二是效率：RD解析器只能通过嵌套子规则（expr→term→power→factor）表达运算符优先级，导致即使解析单个数字42也要经历四层函数调用，开销明显。作者指出这是RD解析器的固有局限，无法在不使用嵌套的前提下表达优先级，建议采用混合解析器——将RD与专门处理中缀表达式的算法（如调度场算法）结合，以兼顾表达式解析效率与高级语言构造的通用性，并预告后续文章将给出实现。文章同时提供了基于Python 2.5的旧版（BNF）与新版（EBNF）解析器源码及词法分析模块。

## 2. Pixel 10 上 C2PA 内容凭证的伪造漏洞

- 原始链接: <https://www.hackerfactor.com/blog/index.php?/archives/1102-C2PA-and-Pixel-Glitter-Milk.html>
- 英文标题: Forgery of C2PA on a Pixel 10

安全研究者 Neal Krawetz 联合马里兰大学巴尔的摩郡分校 PASAWG 工作组及研究者 retr0id，公开披露了 Google Pixel 10 相机 C2PA 签名机制的严重漏洞。Pixel 10 是首个通过 C2PA 认证级别 2（最高安全等级）的移动产品，其签名密钥存储于 StrongBox 安全芯片中，理论上不可提取。但攻击者只需获取设备 root 权限（可通过硬件芯片级方法或软件漏洞实现），即可利用 Android TEE 中的签名程序对任意图片——包括 AI 生成图片——加盖 Google 签发的 X.509 证书，生成与真实拍摄照片无法区分的「已认证伪造品」。该漏洞本质为「混淆代理」攻击，修复需重新设计 Android 安全模型，无简单补丁。2025 年 11 月漏洞即被报告，Google 漏洞赏金计划将其标记为「Won't Fix（不可行）」及「NSBC（非安全公告级别）」，未分配 CVE，但随后仍支付了赏金；C2PA 组织则完全未回应。Google 在演示后数天内撤销了相关证书，但这暴露了 C2PA 与公钥基础设施交互的根本缺陷。作者指出，可验证来源、可靠归属和安全密钥管理均属安全问题，Google 将其排除在安全公告之外存在根本性认知偏差。

## 4. 如何为博客文章申请 DOI：通过 Rogue Scholar 的实践与反思

- 原始链接: <https://shkspr.mobi/blog/2026/09/how-to-get-a-doi-for-your-blog-posts/>
- 英文标题: How to get a DOI for your blog posts

本文作者 Terence Eden 分享了他为个人博客 shkspr.mobi 的每篇文章获取 DOI（数字对象标识符）的完整过程与思考。背景是：他的博客文章频繁被学术论文、书籍和新闻引用，而 DOI 作为唯一且持久的标识符，能确保即使域名变更或网站重构，引用仍可正确跳转。文章介绍了多种获取途径——学术机构订阅、arXiv 上传、付费服务，以及重点推荐的 Rogue Scholar（一个面向科学博客的开放获取档案与注册平台）。Rogue Scholar 自动轮询博客的 Atom feed，为每篇新文章分配 DOI，默认摄取最近 40 篇更新过的文章；作者还演示了通过其 API 查询 DOI、自行生成 DOI（随机数转 Base32 加校验码，前缀 10.59350/）、以及在 HTML 中用 citation_doi 或 DublinCore meta 标签嵌入 DOI 的方法。文章也坦诚列出缺点：DOI 体系存在中心化单点风险；内容被归档后失去 CSS 排版控制；必须采用 CC BY 许可；无法删除或撤回已注册内容；引用追踪尚不完善；以及为每篇博客（包括非学术内容）都分配 DOI 是否「自恋」的伦理疑问。作者最终认为，让学术博客获得正式引用身份是值得的，并期待观察此举对博客在学术界可见度的影响。

## 5. Navier-Stokes之后，我仍对LLM持悲观态度

- 原始链接: <https://dank.systems/posts/2026-09-15-ai-bear.html>
- 英文标题: Why i'm still bearish on LLMs after Navier-Stokes

作者认为，尽管Navier-Stokes方程证明、FreeBSD RCE等headline成果令人瞩目，前沿实验室的估值仍建立在「即将产出全自动知识工作者替代品」的叙事上，而现实是模型在简单任务上仍需大量人工监督与护栏。核心论点包括：模型仅在训练任务邻域内泛化，微小扰动即引发失败或reward hacking；解决reward hacking依赖领域专家的严格规范，但此类专家极度稀缺，规范成本常远超直接实现（CPU项目中规范/验证工程师与设计工程师比例可达3:1至5:1）；Navier-Stokes等纯数学问题是agent工作的最佳场景，因定理本身即严格规范且Lean验证器经充分审计，但绝大多数知识工作不具备此条件；人类审查虽为最佳替代，却无法规模化且自身易被绕过（如xz后门）。作者结论：对多数领域，LLM更像「能力很强的实习生」，能完全自主使用LLM的企业仅三类——可廉价承受失败者、窄任务有护栏者、能承担严格规范成本者（芯片设计、药物发现等）。前两类对价格敏感，开源模型配合更宽的agent swarm即可胜任；第三类虽可能用前沿模型，但IP保密顾虑使其不愿将数据交予Anthropic或OpenAI。作者最终判断：即使前沿实验室叙事破灭，「数据中心中低智AI集群」仍会驱动算力需求，但受限于人类协调瓶颈，其影响范围将远超前沿实验室本身。

## 6. 重构 Issue 追踪：本地优先与 Git 原生

- 原始链接: <https://blog.manganin.dev/blog/reinventing-issue-tracking/>
- 英文标题: Reinventing issue tracking: Local-first and Git-native

本文记录了作者为代码托管平台 Manganin 设计 issue 追踪系统的迭代过程。核心需求有二：issue 数据以 Git 原生方式存储，发挥版本管理优势而非引入 Postgres 等外部依赖；同时满足「本地优先」原则，即无需联网、无需额外工具即可在命令行完成全部操作。作者先后尝试了两种方案并均放弃：其一是将 issue 文件放入代码仓库的 .issues/ 目录，但 issue 变更频率远高于代码提交，会导致频繁 rebase，不可持续；其二是利用 Git 的 special refs（如 refs/issues/12）存储 issue，但本地编辑需经历 hash-object、mktree、commit-tree、update-ref 等多步操作，涉及四个不同 ID 指向同一 issue，复杂度过高且存在竞态问题。最终作者回归 KISS 原则，采用独立隐藏仓库存储 issue 数据：每个 issue 即一个文件，文件名即标题，文件内容即正文，由工具层将其解析为类 forge 的列表视图。代码仓库与 issue 仓库分离，按需克隆，互不干扰。作者强调，设计应从理想的用户体验出发再反推架构，让工具「隐形」，避免将 Git 强行当作关系数据库使用。

## 7. Veloren 的一些不同设计选择

- 原始链接: <https://blog.jsbarretto.com/post/veloren>
- 英文标题: Some things Veloren does differently

本文由 Veloren 核心开发者撰写，介绍这款体素 MMO 在架构与设计上的一系列非主流选择。架构层面，Veloren 采用 ECS（实体组件系统）而非传统面向对象继承，在 48 线程服务器上可支撑 500 余名玩家与数万实体同时交互，远超多数 MMO 的扩展能力；ECS 的默认多态性也带来过玩家被当作掉落物拾取、坐骑叠成高塔等有趣 bug。玩家与 NPC 在物理引擎、移动控制（统一 Controller 组件）、技能与经验系统上完全一致，NPC 若 AI 不够智能也会从悬崖跌落。体素存储方面，团队自创了名为「chonks」的数据结构，在缓存友好性与压缩率之间取得平衡，优于传统大数组、RLE 或八叉树方案。世界生成采用启动时低分辨率预生成再加细节填充的策略，支持长河流等全局约束；生成哲学偏向「本体论」而非「目的论」，以物理模型（如水力侵蚀）驱动地形，强调自洽性而非随机美学。游戏还包含 RTSim 实时模拟系统，NPC 离开视野后仍持续运行，追踪任务、派系与经济动态。此外，Veloren 坚持不设隐形墙、所有玩法置于单一世界空间，包括可达一公里深的洞穴网络，这对光照隔离等细节提出了极高要求。

## 11. 用 Delta 取代 Pull Request：Zed 团队发布多人 AI 协作编码平台

- 原始链接: <https://zed.dev/blog/delta-public-beta>
- 英文标题: Replacing Pull Requests with Delta

Zed 团队正式发布 Delta 公开测试版，这是一个面向 AI agent 协作与代码审查的多人编码环境。其核心理念是：当 agent 大量生成代码后，传统 Pull Request 的 diff 审查方式已严重滞后。Delta 用「thread（线程）」取代 PR 作为协作基本单元，团队成员可直接加入他人与 agent 的对话，共享 worktree 并继续工作，无需依赖 commit 和 push。审查时，审查者获得隔离的 worktree 副本，可借助原始 agent 上下文理解决策，而非仅看 diff 猜测意图。技术上，Delta 基于 DeltaDB 构建，在 Git 内容版本控制之上引入基于 delta 的增量版本，保留 commit 之间人类与 agent 的编辑及消息记录，同时保持与 Git 的兼容——团队无需整体迁移，zed 仓库仍留在 GitHub，但鼓励贡献者在 Delta 中协作。Zed 团队已在自身仓库中彻底关闭 PR，33 名成员在 Delta 中向 main 提交了 570 个变更。他们提出「continuous engineering」概念，主张将构思、实现、审查、合入统一在同一 thread 中完成。Delta 支持 macOS、Linux、Windows 及 Web 端，测试期间免费，后续将推出付费方案但保留免费版本。

## 12. 为什么构建 Rust LSP 如此困难

- 原始链接: <https://rust-glancer.github.io/blog/why-lsp-is-hard/>
- 英文标题: Why building a Rust LSP is hard

本文作者正在开发实验性 Rust LSP「Rust Glancer」，从架构层面分享构建 Rust LSP 的难点。核心观点是：LSP 与编译器的根本区别在于，编译器只需判断是否编译成功，而 LSP 必须从部分信息中尽快产出可用结果。初始化阶段面临索引耗时与用户等待的矛盾，两种实现都选择先响应再后台索引。文章阐述了虚拟文件系统与 source generation 机制的必要性，用于处理并发编辑和查询取消。查询复杂度从 document symbols（仅需解析）到 hover（需语义分析）、inlay hints（需类型推断）再到 references（需跨 workspace 搜索）逐级递增；索引也分为解析、item tree、defmaps、语义层、body 层等多层。实现策略上，rust-analyzer 依赖 salsa 增量数据库配合 cache priming 做惰性计算；Rust Glancer 追求低内存与即时重启，采用预索引并将状态持久化到文件系统。文章还讨论了 workspace 发现的模糊性：用户意图难以判定，两种 LSP 在激进程度上采取了截然不同的策略。

## 15. 苹果参考图像：可验证摄影的新路径

- 原始链接: <https://security.apple.com/blog/apple-reference-image/>
- 英文标题: Apple Reference Image: A New Approach for Verified Photography

面对AI生成与篡改图像泛滥、C2PA等现有溯源标准易被篡改且存在隐私风险的困境，苹果在iPhone 18 Pro及Pro Max主摄上推出「苹果参考图像」功能，提供可验证摄影的新方案。该系统围绕三大核心要求设计：语义真实性——传感器内即时加密签名生成「安全数字底片」，再由隐私云计算（PCC）在可审计环境中完成去马赛克、色调映射等处理，确保最终图像忠实反映原始捕获；抗妥协能力——传感器与安全隔离子处理器（SEP）在出厂时通过硬件清单绑定，采用RSA-3072与ML-DSA-87复合后量子签名，并配备按传感器粒度的撤销机制；隐私保护——图像由苹果签名服务背书而非摄影师个人凭证，PCC架构确保连苹果自身也无法查看图像内容，时间戳经Oblivious HTTP传输以隐藏设备IP。苹果称这是业界首个同时满足上述三项严格要求的图像溯源系统，为可验证数字摄影树立了新标准。

## 16. 给数字加一个小数就能修好着色器：一次跨平台 GPU 调试之旅

- 原始链接: <https://crocidb.com/post/when-the-fractional-part-of-a-float-fixes-your-shader/>
- 英文标题: When adding a fractional part to a number fixes your shader

作者为音乐视频实现了一个 Voronoi 噪声着色器（含 UV 扭曲与调色板查找），在多数设备上运行正常，但一台 Windows + RTX 4070 的电脑上出现明显的顶点跳变卡顿。他先借助 LLM 将噪声函数中的 fract(x) 替换为等价的 x - floor(x)，问题消失，LLM 将其归因于 NVIDIA 驱动对 fract 的误编译。但作者并未止步，尝试复现最小用例失败后，手动发现一个奇异现象：只要给噪声输入乘以一个带小数的标量（如 398.1 而非 398.0），卡顿即消失，与 fract 本身无关。随后他用 RenderDoc 捕获浏览器帧，反汇编发现着色器实际以 DirectX 11（ps_5_0）格式运行，而非预期的 OpenGL ES。关键线索是 ANGLE——Google 的 WebGL 转译层在 Windows 上将 GLSL 编译为 HLSL 再交给 DirectX，正是这一层对 fract 的优化在特定字面量下生成了异常指令。将 ANGLE 后端切换为 Vulkan（编译至 SPIR-V）后问题不复现。文章展示了从 LLM 辅助调试到手动反汇编、捕获浏览器帧、拦截 ANGLE 中间代码的完整排查过程，揭示了跨平台图形栈中转译层优化可能引入的微妙 bug。

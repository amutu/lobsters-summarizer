## 1. 我如何用 uBlock（Hard Mode）浏览网页

- 原始链接: <https://untrusem.party/blog/how-I-browse-the-web-with-Ublock-Hard-Mode.html>
- 英文标题: How I browse the Web with uBlock (Hard Mode)

本文作者分享了自己在浏览器中启用 uBlock Origin“硬模式”的完整工作流。作者认为正常浏览不应被广告和追踪器侵扰，其首选是基于文本的浏览器，日常则使用 LibreWolf，并通过 uBlock、Redirector 和 LocalCDN 三个扩展实现高度可控的上网体验。核心步骤包括：在 uBlock 设置中启用“高级用户”模式、屏蔽大媒体、远程字体并禁用 JavaScript；导入 oisd 和 hagezi 等第三方拦截规则；在“我的规则”中加入全局拦截第三方请求、脚本和框架的规则。启用硬模式后，网站可能损坏，需要用动态过滤功能修复。文章重点介绍了 uBlock 的记录器（Logger），可实时查看请求、被拦截内容，并通过详细面板、规则面板和静态过滤器进行精细放行；还提及 DOM 检查器、防火墙过滤和动态 URL 过滤等高级工具。此外，Redirector 用于将 YouTube、Reddit 等站点重定向到隐私友好的前端；LocalCDN 则本地模拟 CDN，减少外部请求，作者已拦截数千次 CDN 请求。作者强调这一切的核心是隐私、安全与自由，让用户真正了解网页背后发生了什么。

## 2. Mojo 语言现已开源

- 原始链接: <https://www.modular.com/blog/mojo-open-source>
- 英文标题: Mojo is now open source

Modular 团队宣布，Mojo 编程语言现已完全开源，采用 Apache 2.0 许可证（含 LLVM 例外）。Mojo 编译器、工具链及相关源码均托管在 modular GitHub 仓库中。Mojo 是一种新型通用编程语言，集成了最新的编译器与编程语言研究成果，旨在支持 GPU、AI 加速器等先进计算。过去四年，Mojo 以开放社区但封闭编译器的方式开发；上周 Mojo 达到 1.0 版本并实现源码稳定性，今日则正式开放整个编译器与工具链。文章解释了选择 Apache 2.0 的原因：该许可证灵活，适合各类应用，而 LLVM 扩展进一步放宽了从 Mojo 编译构建和分发二进制文件的自由度。开源的节奏经过深思熟虑：先开源标准库，再开放大量用 Mojo 编写的内核代码，如今开放编译器；团队认为紧密的小型设计团队更利于定义语言核心，而广泛社区反馈则有助于避免回声室效应。文章还提供了从源码构建编译器的命令（使用 Bazel 和 `./bazelw run --config=build-mojo`），并说明可运行标准库测试。当前标准库已接受贡献，但编译器与工具链暂不接受贡献，预计年底前开放，届时会公布更多细节。最终，团队欢迎开发者加入论坛、克隆源码并分享基于 Mojo 构建的项目。

## 4. Bluesky如何在截图中显示其Logo

- 原始链接: <https://timmarinin.net/2026/bluesky-screenshots/>
- 英文标题: How Bluesky draws its logo on screenshots

文章作者发现，在截取Bluesky应用中的帖子时，截图右下角会出现Bluesky的Logo，但实际应用界面中该位置显示的是“Follow”按钮。作者感到好奇，通过查看Bluesky的开源代码，找到了名为GrowthHack.tsx的文件，该文件使用了作者自建的expo-privacy-sensitive包。该包的实现方式是创建一个设置了isSecureTextEntry属性的UITextField，并将实际内容渲染到这个字段的layer上。当用户截图时，iOS会因安全隐私机制自动隐藏该UITextField的内容，从而露出底层预先放置的Bluesky Logo。但在切换应用的过程中截图则不会触发这一效果，作者推测这是iOS在手势开始时先截取快照，而模拟器中的实时UITextField无法响应截图操作所致。虽然作者认为这个技巧很巧妙，但相关讨论帖中许多人并不赞同这种做法，认为这是对API的滥用。作者还指出，Telegram的“秘密聊天”和Signal也已实现类似功能，因此苹果短期内可能不会封禁此类用法。文章客观描述了该技术的原理和争议。

- 英文标题: CSS: the bomb inside your inbox

## 6. 利用铁路网作为平板扫描仪

- 原始链接: <https://philo.gay/linecam/>
- 英文标题: Using the railway network as a flatbed scanner

作者使用工业线性扫描相机将铁路网络变成一台巨大的平板扫描仪，在火车和渡轮上拍摄超宽幅照片。文章详细记录了项目的原理、设备搭建与后处理过程。相机以每秒数千次的速度扫描单列像素，随着车辆移动，将连续扫描线拼接成完整图像。作者最初用手机尝试，发现速度变化导致图像畸变，于是改用Basler ruL2048-19gm工业相机，并自行设计安装加速度计、GPS等传感器来测量运动速度，用于校正。实拍中遇到曝光、对焦、信号丢失等难题，而后处理更是挑战：需要根据加速度数据选择正确的扫描线，处理视差效应，并手动调整距离每像素和起始速度参数，以平衡近景和远景。最终作品拼接成巨大TIFF文件，发布在画廊中。文章展示了从概念到完成的完整过程，并强调了运动测量和图像校正的关键作用。

## 8. GitHub有替代品，却无真正替代者

- 原始链接: <https://lalitm.com/post/github-alternatives/>
- 英文标题: GitHub has alternatives, but no replacement

文章讨论GitHub虽令人不满，但尚无真正替代者。作者认为，Codeberg等平台虽有明确使命，却并非普适替代品，引发失望。核心问题在于：开源空间不乏Git仓库托管服务，但缺少能承载开源社区的“社会层”——即共享身份、协作习惯和项目发现机制。GitHub恰好提供了这些，而其他平台均未在同等规模上实现。自托管（如Gitea）适合个人项目，却会阻碍陌生贡献者参与；GitLab过于企业化，SourceHut的邮件工作流对多数人不友好，Forgejo联邦尚在实验，Radicle不成熟，Tangled仍在alpha阶段。作者指出，GitHub自身体验也在恶化：慢、故障多、PR审查笨拙，同时过度聚焦AI而忽略核心功能。Ghostty项目因依赖GitHub而频繁受阻，只能另寻出路。作者设想，或许需要一家“无聊的公司”专注于可靠、愉快的开源协作，直接向开发者收费，而非追求扩张；但关键难点在于，共享社会层只有在达到规模后才显价值，单纯托管无法解决冷启动问题。最终，真正的替代品必须将社会层作为核心产品来建设。

## 11. 是否应该转向 GitHub 替代品？

- 原始链接: <https://lobste.rs/s/0zdh32/does_it_make_sense_switch_github>
- 英文标题: Does it make sense to switch to a Github Alternative ?

文章围绕 GitHub 近几个月频繁宕机，讨论了是否应切换至替代 Git 托管服务。多数评论认为，是否迁移取决于用途：若仅作代码备份，可容忍；若需要高可用性、CI/CD、自主域名或避免微软控制，则应考虑替代。部分开发者强烈支持迁移，如 Fennel 项目早在2020年就迁移并保留镜像，认为离开 GitHub 是重要信号；有人选择使用 Codeberg、sr.ht、Radicle 等第三方非营利平台，也有人自托管 Git 服务，用 stagit 生成静态网页或 soft-serve 提供 SSH 访问，以摆脱大厂依赖。另一方指出，企业用户因深度绑定 GitHub Actions、用户管理等生态难以迁移；且免费 CI 与庞大贡献者池是小项目留在 GitHub 的诱因。还有人认为若跟风迁移到另一中心化平台，终将重蹈覆辙，应支持分散化或自托管。总体而言，没有一致结论，但共识是：无需一味追求全功能平台，应根据项目实际需求选择方案，小型项目完全可脱离 GitHub。

## 14. AI;DR（AI，没读）：拒绝未经编辑的AI内容

- 原始链接: <https://blog.rust-lang.org/inside-rust/2026/08/18/reducing-target-dir-size-on-nightly/>
- 英文标题: Experiment in reducing target directory size on nightly

Cargo 团队宣布将在 nightly 通道默认启用 -Zembed-metadata=no 特性，以减少 target 目录占用空间。该特性通过避免在 .rlib 文件中重复嵌入 crate 元数据（此前元数据同时存在于 .rmeta 和 .rlib 中）来减小构建产物体积。实验测量显示，在 release 配置（无增量编译、无调试信息）下，serde 的 target 目录可减少约 30%，Cargo 自身最多减少约 33%（绝对量近 300 MiB）；而在 dev 默认配置下收益较小（约 5%–8%），因为调试信息和增量产物占主导。该特性尚未计划稳定化，此次实验旨在收集真实使用反馈。大多数用户不会感到差异，但手动链接 .rlib 的用户可能需要额外提供对应的 .rmeta 文件。用户可通过 Cargo 标志 -Zembed-metadata=yes、环境变量 CARGO_UNSTABLE_EMBED_METADATA=true 或 .cargo/config.toml 中的 unstable.embed-metadata 配置退出实验。Cargo 团队将根据反馈决定后续是否稳定化、调整或重新设计。

## 23. 当向下箭头不是倒过来的向上箭头（2022）

- 原始链接: <https://thefloatingcontinent.com/blog/upside-down-arrow-unicode/>
- 英文标题: When the Down Arrow is not an Upside-Down Up Arrow (2022)

文章探讨了一个字体渲染现象：Unicode 中的“Upwards White Arrow”（⇧，U+21E7）和“Downwards White Arrow”（⇩，U+21E9）本应是镜像对称的箭头，但在 macOS 上，向上箭头显得更矮胖，向下箭头则不同。作者调查后发现，问题不在于 Unicode 标准本身，而是字体回退机制：Lucida Grande（系统默认字体）只包含了向上箭头的字形，向下箭头则由另一个回退字体 STIXGeneral 渲染，导致两者外观不一致。作者引用 Unicode CJK 专家的解释，认为 Lucida Grande 之所以支持向上箭头，可能是因为它源于 Big5 编码中的汉字字符，而非从箭头集合中专门选择。文章还提到，若想确保跨平台显示一致，可以使用 CSS 技巧将向上箭头垂直翻转来模拟向下箭头，但这样做不利于屏幕阅读器。作者后来指出，在 macOS 上 VoiceOver 会把向上箭头读作“shift”，因此建议使用时可加上 role=img 和 aria-label 来保证可访问性。文章以轻松语气讲解了 Unicode 代码点、字体回退和跨平台文本渲染的复杂性。

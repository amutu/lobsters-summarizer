## 1. 我以为我在构建C的替代品，但我错了

- 原始链接: <https://c3-lang.org/blog/i_thought_i_was_building_a_c_replacement/>
- 英文标题: I thought I was building a C replacement. I was wrong

作者回顾了自己将C3语言定位为“C替代品”的失误。他成长于80年代，当时C用于编写应用程序，因此他对C的认知是“适合开发通用软件的语言”。后来他经历Pascal的高效开发、Java的面向对象热潮，并在PHP项目中意识到：核心逻辑本质上是过程式的，OO带来的前期架构负担反而阻碍了重构和探索问题空间。他认为“方法优先”的思维（如foo.do_something(bar)）会固化对象层次，使调整关系代价高昂，而过程式思维（如run(&game)）更灵活。C3虽然支持方法，但作者希望它回归C的简单高性能，同时补充现代应用开发所需的字符串、动态数组等便利性。然而如今“C替代品”在公众语境中意味着替代C当前的主要用途——操作系统、嵌入式、高性能库等，而非通用应用开发。作者因此意识到自己用旧定义营销新语言，实际目标是让C3成为令人愉快的通用应用语言，而非狭义的C替代品。他决定今后更强调其通用应用定位，并承认自己之前的市场定位是根本性错误。

## 2. 千篇一律的网站

- 原始链接: <https://op.tngl.io/every-fucking-website/>
- 英文标题: Every Fucking Website

这篇文章是一篇讽刺性的短评，标题为“Every Fucking Website”，副标题“slop edition”意为“俗套版”。作者用调侃的口吻，逐项罗列了当前互联网网站设计中日益泛滥的模板化元素：衬线字体配上随机斜体的文字，用破折号作为视觉支柱，标题被无意义地分割成“三个词”，放置主要和次要两个行动号召按钮，而后者往往没人点击；页面中展示了一段 `curl install.sh | sh` 的命令，并特别提醒“运行它是傻瓜行为”；底部则是重复出现的LOGO墙，以及“Trusted by”某YC孵化器的六家公司。此外，网站顶部还设有“实时状态”，但毫无实际信息。作者通过这些典型段落，揭示了现代网站设计陷入同质化、缺乏原创性的现象，到处充斥着形式主义的“slop”。文章并非严肃技术教程，而是对当下网页设计雷同潮流的冷嘲热讽，提醒读者警惕这些表面光鲜却空无一物的设计俗套。

## 3. 保护 Rust 标准库免受意外破坏

- 原始链接: <https://predr.ag/blog/protecting-the-rust-stdlib-from-breakage/>
- 英文标题: Protecting the Rust standard library from accidental breakage

本文介绍了 Rust 标准库如何借助 cargo-semver-checks 工具防止意外破坏。尽管标准库有严格的稳定性机制，但历史上仍多次发生因添加不稳定方法、泛型方法缺少 Sized 约束、实现变更导致自动 trait 丢失等问题，对 async-std、tokio 等下游生态造成破坏。作者回顾了这些事件，指出人工审查无法可靠避免此类问题，因此需依赖自动化工具。文章重点说明了将稳定性信息集成进 cargo-semver-checks 的技术方案：在 rustdoc JSON 中新增 Item::stability 字段表示项级稳定性，新增 const_stability 字段表示 const 稳定性，并通过 default_unstable 字段表示 trait 默认实现的稳定性；在 lint 数据模型中，将 #[unstable] 项视同 #[doc(hidden)]，将 const-unstable 视为非常量，将不稳定的默认实现视为不存在，从而无需重写数百条 lint 即可正确识别稳定 API 的破坏。该方案已在 Rust CI 中落地，能自动报告稳定项被移除、去稳定化等破坏，同时忽略不稳定 API 的预期变更。作者还提到工作仍未完全完成，未来将改进稳定性破坏的报告 UX、支持更多平台等。

## 4. 第三世界嵌入式工程师回应“RISC-V：他们本应更懂行”

- 原始链接: <https://rvembedded.com/blog_post/12/>
- 英文标题: A Third World Embedded Engineer Responds to "RISC-V: They Should Have Known Better"

本文是特立尼达和多巴哥嵌入式工程师Armstrong Subero对Dmitry Grinberg批评RISC-V一文的回应。作者承认RISC-V确有短板，如压缩指令偏移怪异、Zicsr未随基础指令集隐含等，但认为对方视角充满发达国家的偏见。从第三世界出发，芯片价格和可获得性压倒一切：作者所在地运费高昂，十美分芯片能让三十名学生每人拥有一块板，而一美元芯片只能全班围观一块演示板。Grinberg自己从第一原则推导出廉价微控制器应实现RV32EC，甚至承认RISC-V终将主导该市场，却转而对此结果不满。作者用CH32V003、CH32H417和Baochip三款器件证明，同一RISC-V基础指令集可覆盖从十美分单片机到带MMU和特权隔离的SoC，技能全程可迁移；而ARM因不同profile和许可壁垒形成断裂，高端的MMU、USB 3.0等能力难以获得。他认为碎片化与可扩展性是一体两面，是RISC-V兼顾两端的代价。归根结底，RISC-V赢不在编码优雅，而在开放、低价、无许可障碍，让边缘地区开发者真正参与嵌入式领域，这才是更重要的胜利。

## 5. Magit 状态界面漫游指南

- 原始链接: <https://heiwiper.com/posts/magit-status-tour/>
- 英文标题: A Tour of Magit's Status Interface

本文介绍了 Emacs 的 Git 客户端 Magit 的核心界面——Magit Status（状态界面）。作者因被其直观的 UI/UX 打动而转向 Emacs，并认为 Magit 非常出色。Magit Status 是调用 Magit 时出现的入口界面，主要包含两部分信息：第一部分显示仓库的四个关键状态——Head（本地分支的最新提交）、Merge（合并变更所针对的远程分支）、Push（推送变更的目标远程分支，如贡献所用的 fork）以及 Tag（本地分支上的最新标签及领先该标签的提交数）。第二部分显示最近的提交记录，默认折叠以保持界面整洁，可按 TAB 展开。界面会按需显示区块：仅当有变更时才出现未跟踪文件、未暂存改动和已暂存改动等区域。该界面的核心亮点是交互性：用户可直接暂存/取消暂存改动，添加、删除或隐藏未跟踪文件。按 ? 键可调出命令菜单，涵盖几乎所有常用操作，且快捷键多为操作首字母，易于记忆。作者认为，这一界面既完整呈现了仓库状态，又提供了全部所需命令，无论对 Git CLI 老手还是 Git 新手都非常友好。文章最后提到，作者原本计划涵盖更多主题，但仅状态界面就值得单独成篇，后续将介绍暂存、提交、分支切换以及 cherry-pick 和 rebase 等工作流。

## 6. Firefox成为唯一仍支持uBlock Origin的主流浏览器

- 原始链接: <https://www.pcworld.com/article/3212428/firefox-is-now-the-last-major-browser-that-still-supports-ublock-origin.html>
- 英文标题: Firefox is now the last major browser that still supports uBlock Origin

Firefox近日在Bluesky上发文，承诺继续支持uBlock Origin，回应了Microsoft Edge即将阻止该扩展及其他基于Manifest V2架构的广告拦截扩展的消息。Edge基于Chromium内核，而Google早已推动从Manifest V2向V3迁移，微软此举并不意外。随着Edge跟进，主流浏览器中只有Firefox仍完整支持uBlock Origin。Safari和DuckDuckGo虽非Chromium内核，但也不支持该扩展。对uBlock Origin的忠实用户而言，Firefox成为唯一无需妥协的选择；在其他浏览器上，用户只能使用功能较弱、拦截效果较差的uBlock Origin Lite，或依赖浏览器自带的广告拦截功能。文章指出，这已成为Firefox的“杀手级应用”，并强调只要Firefox持续支持uBlock Origin，部分用户就不会回归Chrome。

## 7. 为什么我仍然对LLM持怀疑态度

- 原始链接: <https://blog.jsbarretto.com/post/i-remain-a-skeptic>
- 英文标题: Why I remain a skeptic

作者Joshua Barretto解释了自己为何对大型语言模型（LLM）持怀疑态度，并明确表示不会用LLM处理任何重要事务。他认为，虽然已过去四年并投入巨额资金，AI革命在软件行业几乎没有实际成果：软件质量未提升、成本未下降、安全性未改善，也没涌现真正有用的新想法。他坦言并未因不用LLM而感觉落后，自己的开源项目依然被信任，功能可被复制，但信任无法替代。关于生产力提升的证据十分薄弱，1.5万亿美元投资后仍缺乏严谨的独立研究，现有研究要么聚焦于无关指标，要么规模太小，且结果仅显示边际甚至负面效应。作者收到的LLM生成PR质量仍远低于人类，且这些模型常会漏掉明显问题，反而不如爱好者用头脑发现得准。他批评AI拥趸的理念违背了软件开发的本质——代码是输入而非输出，把代码量当指标只会产出难以维护的垃圾。此外，大科技推动LLM的暗含目标是使智力劳动同质化、可替换，从而削弱工人议价能力。作者刻意选择不依赖LLM，专注于更专业的技能，反而保障了工作安全。总之，他从实效、证据、哲学和劳工权益四个层面解释了持续怀疑的正当性。

- 原始链接: <https://christianheilmann.com/2026/08/11/anti-social-media/>
- 英文标题: Anti-Social Media

作者因被X（原推特）封禁而逐渐淡出社交媒体，并直言社交媒体已死，沦为分散注意力、传播宣传和煽动愤怒的机器。他认为主流平台如Meta旗下产品（Facebook、Instagram、Threads）和X，以及BlueSky、LinkedIn甚至Mastodon，都在走向同样的下坡路：人们不再分享思想和创意，而是按照平台规则塑造人设，甚至被迫把链接放在首条评论以促进互动，这种机制把用户变成了内容生产者和流量诱饵。他回顾了Web2.0时代，Flickr、LastFM等早期平台围绕照片、音乐等情感核心聚合人群，但后来平台为了追求增长和UGC（用户生成内容），逐渐放弃质量，例如Yahoo Answers因追求流量而关闭质量设置最终衰亡。他指出主流媒体对社交媒体的报道几乎总是负面的，而社交媒体本身也已变得反社会。不过，他认为仍有希望：Facebook的兴趣小组（如8位计算、编程、乐高、电影制作等）保留了分享的乐趣，联邦宇宙（如Mastodon）也提供更开放的空间，但门槛较高。最后他呼吁人们反思“为什么做这件事”，停止用AI生成、追求病毒式传播的内容消耗自己，允许自己真实地表达。

## 9. 在PyPI上实现可重现构建还缺什么？

- 原始链接: <https://snarky.ca/whats-missing-to-have-reproducible-builds-on-pypi/>
- 英文标题: What's missing to have reproducible builds on PyPI

文章探讨了在PyPI生态中实现可重现构建所缺失的要素。作者认为可重现构建能增强供应链安全：独立第三方可验证发行版的二进制内容是否与源代码一致，从而发现构建过程中的篡改，如SolarWinds事件；即使是纯Python wheel，也可能因构建后端被攻破而受污染。当前规范有几个缺口：第一，发行版没有记录源代码来源位置（直接安装源码仓库时有direct_url.json，但sdists和wheels缺少类似元数据）；第二，wheels可通过PEP 770的SBOM记录构建工具，但sdists没有存放SBOM等附加元数据的位置，需要设计sdist v2格式；第三，如何记录构建环境中的全部软件，作者提出可由构建后端自动记录并生成SBOM，这样发行方无需额外工作，但需要pip维护者配合。最后，作者建议由可信第三方验证者将成功重现的结果反馈给PyPI，并在Index API中展示，让安装程序优先选择被独立重现的发行版。他强调这应被视为优点而非义务，类似SLSA build level 1。

## 10. 模型正有意“变笨”：舍弃事实知识，专注推理

- 原始链接: <https://w4g1.dev/blog/models-are-getting-dumber-on-purpose>
- 英文标题: Models Are Getting Dumber on Purpose

文章指出，前沿模型正刻意将规模做小、事实知识变少，把资源集中到推理能力上。GLM-5.2在AIME 2026达到99.2%，活跃参数约400亿；Qwen3.5 9B在知识基准上的幻觉率高达80%至82%，回答常识性事实时经常一本正经地编造。作者认为这是有意权衡：事实存储成本高且会过时，推理则易于压缩，且不会随时间腐坏。随着知识被移出权重，模型依赖外部工具、检索和文档等“harness”在运行时获取信息；这样错误反而可追踪、可修复，幻觉问题从无法调试的权重缺陷变成普通数据错误。文章预测，几年后模型可能只需200亿到400亿参数即可在消费级GPU上运行，具备前沿级推理能力，但几乎不储存事实，需要配合工具使用。核心观点是：把昂贵、缓慢的模型与每日变化的世界状态解耦，让模型只负责推理，知识由外部环境动态提供。

## 11. 使用Healthchecks.io监控SystemD服务

- 原始链接: <https://passbe.com/2022/healthchecks-io-systemd-checks/>
- 英文标题: Monitoring SystemD services with Healthchecks.io

本文介绍了如何用Healthchecks.io监控SystemD服务。作者需要监控由systemd定时器触发的任务，借助可自托管的Healthchecks.io及集成通知功能，利用SystemD的OnSuccess/OnFailure钩子，在服务状态变化时自动发送ping。初始方案中，每个被监控服务通过OnSuccess和OnFailure引用两个模板服务，模板内用curl向Healthchecks实例的ping端点发送成功或失败信号。作者后来根据同事建议更新了模板，合并为单个通用模板healthcheck@.service，在实例名中用冒号分隔UUID和动作（如success、failure、start），并配合Wants=发送启动信号；动作标记至关重要，缺少它SystemD不会向模板服务传递$MONITOR_*环境变量。新模板通过journalctl抓取最近50行日志，用curl的--data-raw将日志发送给Healthchecks.io，并设置超时和重试。文章还引用了SystemD手册，说明$MONITOR_*变量仅在OnSuccess/OnFailure触发时传递，且多个服务触发同一单元时不会传递，建议使用模板处理单元。该方案最终实现了服务出错时及时通知，同时便于与Vorta/borg等备份工具整合。

## 14. Aiki实现递归自我解释

## 17. LazyPromise：比 Effect 更轻量的异步替代方案

- 原始链接: <https://github.com/lazy-promise/lazy-promise>
- 英文标题: What do you think of LazyPromise as a lightweight alternative to Effect?

本文介绍了 LazyPromise，一个旨在结合 Observable 与原生 Promise 优点的轻量异步库。它本质上是单次发射的 Observable：懒执行、可取消、同步发射（非微任务），并支持类型化错误与依赖注入。与原生 Promise 相比，LazyPromise 解决了 Promise 的急切执行和强制微任务问题，同时保留了类似 Promise 的简洁 API（map、catch、finally 等）。与 Effect 相比，它提供了生成器语法、类型化错误和依赖注入等相似能力，但更偏向库而非框架。文章重点展示了如何创建 LazyPromise（通过 sink 对象和可选 teardown 函数），订阅后可取消；支持生成器语法（yield*）实现类似 async/await 的流程控制，并自动处理取消。类型化错误通过 ErrorBox 包装，利用类型系统强制处理所有错误情况。依赖注入通过向构造回调和订阅时传入额外依赖实现，便于测试。此外，库还提供多种浏览器/Node 延迟工具（inTimeout、inMicrotask 等）。设计问答解释了为什么用 map 而非 then、为什么 finally 在取消时不执行、为何不提供内置缓存等，强调其作为轻量原语的定位。

## 18. 压缩即预测？：等价性的边界与前提

- 原始链接: <https://lukefleed.xyz/posts/compression/>
- 英文标题: How Is Compression Prediction?

本文围绕“压缩即预测”这一常见说法展开技术分析。作者承认，在给定概率模型和熵编码器后，理想编码长度等于模型对观测序列的累积对数损失，因此优化对数损失与减少编码比特在数学上确实是同一问题。但作者强调，这种等价性成立需要许多前提：编码器和解码器必须事先约定被表示对象的类型、允许的备选集合、概率模型如何共享，以及解码端需要如何操作表示。文章先介绍了压缩在引入概率之前的定义，包括柯尔莫哥洛夫复杂度和有限族对象的计数下界；随后说明概率分布如何给出理想比特成本，而任意唯一可解码码长也可反过来诱导一个概率分布，从而建立概率与编码长度的双向关系。作者进一步指出，源模型本身也是消息的一部分，若解码器不知道模型，则模型必须被编码进总长度；最短比特流也不一定是最合适的表示，因为可能缺少随机访问等能力。结论是：压缩与预测可以在数学上等价，但该等价只覆盖表示成本的一部分，压缩问题的起点和终点都超出预测之外。

## 19. CVE-2026-33696：n8n 中从 Schema 名称到远程代码执行的原型污染漏洞

- 原始链接: <https://simonkoeck.com/writeups/n8n-gsuiteadmin-prototype-pollution-rce>
- 英文标题: CVE-2026-33696: From a Schema Name to RCE in n8n

本文介绍了 n8n 中一个严重漏洞（CVE-2026-33696）的发现过程与利用链。在审计 n8n 节点实现时，研究者发现 GSuiteAdmin 节点在创建和更新用户时，会将用户可控的 schemaName 直接作为普通对象的动态键使用，且未检查 __proto__、constructor 等危险属性名。当 schemaName 为 "__proto__" 时，赋值操作会写入 Object.prototype，造成全局原型污染。攻击者可借此设置 GIT_SSH_COMMAND 属性，再通过 Git 节点克隆 SSH URL，使 simple-git 和 Node.js 将污染属性传递给子进程，最终以 n8n 进程用户身份执行任意命令，实现远程代码执行。该漏洞还可独立造成拒绝服务：原型污染后 TypeORM 的 for...in 遍历会抛错，导致数据库查询全部失败、界面无响应、实例需重启恢复。影响范围涵盖自托管、工作进程和云部署，可导致凭据窃取。修复方式是对 schemaName 进行危险属性黑名单校验，或使用 Object.create(null) 创建对象。n8n 已在 2025 年 3 月发布公告和 CVE。

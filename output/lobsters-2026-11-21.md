## 1. Vim Classic 8.3.1 正式发布

- 原始链接: <https://vim-classic.org/news/vim-8.3.1-released.html>
- 英文标题: Vim Classic 8.3.1 released

2026年11月20日，Drew DeVault 宣布 Vim Classic 8.3.1 正式发布，这是该项目的第二个版本。Vim Classic 是经典文本编辑器 Vim 的一个稳定、长期支持的分支，其核心特点是维护过程中完全不依赖生成式 AI 工具。本次发布整合了截至 Vim 8.2.3237 的适用补丁，涵盖大量 bug 修复、小型功能增强以及插件兼容性改进，同时移除了对 Python 2 的支持。Vim Classic 延续了 Vim 的 charityware 模式，继续支持 Bram Moolenaar 在乌干达资助贫困儿童的慈善事业，并鼓励用户从 Vim 迁移时进行捐赠。安装包（tar.gz 及 PGP 签名文件）可从 SourceHut 下载，发布附 PGP 公钥签名以供验证。作者建议用户订阅 vim-classic-announce 邮件列表以获取后续重要更新，并向所有参与测试、反馈和提交补丁的贡献者致谢。

## 2. 移除 Binder C 实现：Android 内核 IPC 机制的 Rust 化之路

- 原始链接: <https://lwn.net/Articles/1102982/>
- 英文标题: Removing binder.c

Kangrejos 2026 大会上，Carlos Llamas 宣布删除 Android Binder 驱动的 C 实现，Rust 版本全面接管。Binder 自 2008 年加入内核，是 Android 核心进程间通信机制，被 Google 红队认定为漏洞密度最高的组件，成为内核首个 Rust 移植项目，历时逾五年。Alice Ryhl 分享了移植难点：尾延迟比吞吐量更关键，锁竞争引发的优先级反转通过将操作移出锁并改用自旋锁解决；tracepoint 被用户当作事实 API 依赖，必须完整复制；还需适配 KASLR、CFI、PGO 等工具链。部署方面，厂商自定义钩子使部分厂商仍依赖 C 版本，旧稳定版继续维护 C Binder 并接收安全修复。该补丁已合入 7.4 合并窗口，7.3 为 2026 年 LTS 版本。文章指出，移植中最困难的并非 Rust 特有问题，而是任何重写都会面临的兼容性挑战。

## 3. 发布 jj-musubi：面向 Jujutsu 的多机实时同步工具

- 原始链接: <https://www.serpentine.com/posts/2026/announcing-jj-musubi/>
- 英文标题: Announcing jj-musubi: live sync for Jujutsu

作者宣布推出 jj-musubi，一款为 Jujutsu（jj）版本控制工具设计的多机实时同步程序。每当 jj 对工作区进行快照，jj-musubi 便在数秒内将提交、变基、拉取等操作同步到所有关联机器，使分散在多台设备上的仓库副本体验如同 jj 的工作区（worktree）。该工具面向单人跨机工作场景，无独立安全模型。架构上，一台机器运行 hub，其余机器通过 SSH 与 hub 交换 jj 历史，部署极为轻量。关键设计包括：不写入工作副本，构建期间可安全接收新历史；支持离线工作，联网后自动补同步；通过「租约」机制管理临时虚拟机中的仓库，避免残留堆积。作者曾在 Meta 参与 Sapling/Mononoke 项目，此次希望以极小基础设施复现类似便利。并发安全方面，作者使用 Lean 证明网络协议关键属性，并以 Rust 实现与模型对照测试，辅以大量并发编辑、中断同步、hub 重启等场景测试及变异测试。并发编辑复用 jj 既有的 divergent 标记与冲突合并机制，用户只需在 workspace 名前缀加上机器名即可区分。工具已提供 Linux、macOS、Windows 预编译二进制，可通过 cargo install 安装，配合 musubi hub、musubi create、musubi join 三步完成初始配置。

## 4. 已访问链接该不该变紫

- 原始链接: <https://dbushell.com/2026/11/16/visited-links/>
- 英文标题: Visited links are purple

作者受Kev Quirk提问启发，重新审视了CSS中:visited伪类的使用。他调研发现Wikipedia、MDN、GOV.UK设计系统、BBC News等主流站点仍保留已访问链接的视觉区分（多为蓝转紫或黑转灰），随后决定在自己博客正文中为已访问链接添加紫色样式，虽起初觉得略怪，但逐渐欣赏这种色彩点缀。无障碍方面，WCAG 2.2并未要求区分已访问与未访问链接；SC 1.4.1「颜色使用」条款明确，仅凭颜色区分已访问/未访问链接不构成失败，即使对比度低于3:1。作者认为蓝紫之间的细微差异虽非人人可辨，但作为罕见例外可以接受，强行加大对比或增加其他视觉标记反而会损害可读性。此外，他提到Chromium浏览器于2025年引入了:visited链接分区（link partitioning）机制，出于隐私考量对已访问链接的样式施加了更严格限制。文章后半段介绍了社交RSS聚合器Bubbles（bubbles.town），称赞其支持小型个人博客、倡导非毒性话题，但也指出其尚需技术过滤和更多社区参与。作者呼吁小博客生态繁荣，以对抗Google等巨头对网络的「守门」，让个人化、人性化的网络空间得以存续。

## 5. Alice v0.6.0 发布：支持 C 代码混合、配置脚本与字节码后端

- 原始链接: <https://www.alicecaml.org/blog/alice-v0-6-0/>
- 英文标题: Alice v0.6.0

Alice 是 OCaml 语言的包管理与构建工具，v0.6.0 于 2026 年 11 月 21 日发布，主要目标是支持从 Opam 仓库向 Alice 包格式（alice-ports）移植更多包。本次更新引入四项核心功能：一是在 Alice.kdl 清单中新增「builtins」字段，允许包引用标准库中被排除在预导入之外的内置模块（如 Unix、Str）；二是支持在包的 src 目录中放置 C 源文件，构建时自动编译并链接进最终可执行文件；三是新增配置脚本机制，包根目录下的 config.ml 文件会在编译前以字节码方式执行，其标准输出中以「alice:」开头的行被解析为构建指令，目前支持打印消息和添加 C 链接器参数；四是编译命令（alice build、alice run）新增「--backend」参数，可在 native 与 bytecode 两种后端间切换，默认仍为 native，字节码后端编译更快但运行性能较低。此外还添加了「--bin」作为「--exe」的别名、构建输出附带耗时等小改进。安装方面，Windows 可用 WinGet，macOS 与 Linux 可用 Homebrew 或官方安装脚本，NixOS 可通过 flake 安装。

## 8. Jujutsu 版本控制系统入门指南

- 原始链接: <https://ethanlowman.com/posts/jj-primer/>
- 英文标题: Jujutsu Primer

本文是面向 Git 用户的 Jujutsu（jj）版本控制系统入门指南。作者指出 jj 的核心优势在于自动 rebase、原生 undo 及简洁原语的组合能力，能显著减少版本控制簿记对工作记忆的占用。jj 可与 Git 在同一仓库并行使用，通过「jj git init」即可接入现有 Git 仓库。文章系统介绍了 jj 的基本概念与操作：无暂存区，编辑文件后自动将工作副本快照为新提交；提交 ID 随内容变化，而变更 ID 稳定标识同一逻辑变更。通过「jj new」「jj commit」「jj desc」可创建和演进提交，用「jj edit」在提交图中自由切换工作副本。Revset 是借鉴自 Mercurial 的表达式语言，用于从提交图中筛选修订集合，支持父子关系、区间、作者过滤等。自动 rebase 在编辑工作副本后自动更新子提交；若产生冲突，jj 仅标记而不阻塞当前任务。撤销方面，jj 维护完整操作日志（op log），支持「jj undo」「jj redo」「jj op restore」等操作。文章还提及 squash 工作流，但正文在此处截断，未完整展开。

## 9. DreamCoder：来自《Mastering Emacs》作者的浏览器端 AI 编程 IDE

- 原始链接: <https://www.masteringemacs.org/article/announcing-dreamcoder>
- 英文标题: DreamCoder: coding harness and IDE from the author of Mastering Emacs

《Mastering Emacs》作者在历时十五个月开发后，正式发布了 DreamCoder——一款运行于浏览器、跨三大平台、内置平铺窗口管理器的前沿 AI 编程 harness。作者对 Claude Code 等终端优先的 AI 编程工具表达不满，认为严肃开发者不应被限制在「鞋架大小的终端窗口」中，而现有 GUI 版本也仅是千篇一律的侧边栏聊天界面。文章用大量篇幅回顾了 AI 与 Emacs 的交织历史：从 1950 年代 McCarthy 的 LISP 与 Advice Taker 常识推理构想，到 Russell 实现首个 LISP 解释器，再到 1970 年代 Stallman 与 Steele 在 MIT AI 实验室创建 EMACS，以及 Teitelman 的 ADVISE 系统如何演化为 Emacs 至今保留的 advice 机制。作者指出，符号 AI 虽未实现通用智能，却催生了 LISP、Emacs 等最具延展性的工具；而最终胜出的是连接主义（神经网络），这本身是一种「柔韧、可塑」的路径，与符号 AI 追求的刚性规则世界形成讽刺对照。作者坦言，从在 Emacs 中手工编写 DreamCoder 到让 DreamCoder 自我编写，他感到深切悲伤，但也重获少年时的乐观。文章核心论点是：「品味」是稀缺的人类资源，AI 时代仍需要经验丰富的程序员把控方向，因此编程工具的设计必须以人为中心。

## 11. Farcall：一个可在终端运行的 Rust 语言 IBM PC 与 DOS 模拟器

- 原始链接: <https://www.dialup.net/farcall/>
- 英文标题: Farcall, a terminal-ready Rust PC+DOS emulator

作者受复古计算机大会启发，用 Rust 语言从零编写了 x86（8088）CPU 模拟器 Farcall，目标是最终在终端中运行 Windows 3.1。项目从执行简单的 COM 文件开始，逐步实现约三百余条 8088 指令、INT 中断机制及 DOS/BIOS 服务，随后引入开源 BIOS 实现 GLaBIOS，不得不额外模拟 PPI、PIT、DMA 等硬件外设。作者还实现了 CGA 图形模式，发现视频内存按 8 KiB 偏移交替存储奇偶扫描线的机制，并通过 Kitty 图形协议将画面直接渲染到终端。性能方面，作者将时钟检查间隔改为每 128 步一次、将帧数据从全彩 PNG 改为 4 位索引色 PNG，分别消除了约 43% 和 70% 的 CPU 开销。目前 Farcall 已部署在公共 SSH 服务器上，用户可通过 ssh me@intodos.com 体验 Zork、NetHack、GW-BASIC 等经典 DOS 程序。下一步需支持保护模式与 286 架构以运行 Windows 3.1。代码以 MIT 协议开源。

## 12. 验证 Raft 实现的形式化模型

- 原始链接: <https://antithesis.com/blog/2026/verifying-formal-models/>
- 英文标题: Verifying formal models of Raft implementations

Antithesis 团队结合 AI、TLA+ 与 Antithesis 故障注入测试，对 etcd-raft 和 HashiCorp Raft 两个生产级库进行形式化验证。他们使用 Claude Fable 5.2 自动从 Go 代码推断 TLA+ 状态转移模型，再通过「轨迹验证」将运行时日志映射到模型路径，确保模型与实现一致。验证覆盖选举安全、日志匹配、领导者完整性和状态机安全等核心 Raft 安全属性，并纳入预投票、快照、领导者转移及 etcd 特有的读索引、异步存储写入和成员变更等扩展。过程中通过有界模型检测（TLC，状态空间超 160 万）与轨迹验证迭代发现并修复了 7 个补丁，包括已知 issue 和新 bug。最终借助 Lean 证明助手（经 Veil 库翻译）和 TLAPS 完成完整证明，每个库成本不足 1200 美元。文章强调，所证明的是形式化模型而非代码本身，模型仍假设存储层（如 BoltDB）不产生撕裂写入，且未覆盖租约读、异步心跳等特性，也未验证活性。作者 Hillel Wayne 指出，形式化方法证明设计正确，而轨迹验证借助测试弥补「设计与代码是否一致」这一核心缺口，两者互补；当前工作相当于「在小鼠上验证药物有效」，距离真实系统全面验证仍有距离。

## 13. Rust 中的持久化增量计算

- 原始链接: <https://rust-glancer.github.io/blog/persistent-incrementality-in-rust/>
- 英文标题: Persistent incrementality in Rust

本文围绕增量计算在 Rust 生态中的实践展开。增量计算的核心思想是：当输入发生变化时，仅重算受影响的子集，而非全部重新计算。该理念在增量编译和 LSP 服务器（如 rust-analyzer 依赖的 salsa 库）中尤为关键，因为用户编辑频率远高于编译频率，每次按键都需在毫秒级内更新编辑器状态。然而 salsa 主要在内存中工作，对追求低内存占用的 Rust Glancer 项目并不适用。Rust Glancer 此前采用手动分片持久化缓存，但复杂度随计算与缓存实现的双重增长呈二次膨胀。文章通过一个带文件包含关系的文字计数示例，演示了 salsa 如何利用依赖图、revision 版本号和 memo 缓存实现增量重算：若某查询输出未变，则其下游查询可跳过；即使 revision 变化，也可通过比较新旧输出决定是否真正失效。随后作者调研了现有持久化方案——salsa 自身的快照式持久化、rustc 的编译耦合逻辑、picante 的异步全局序列化、turbo-tasks 的文件系统缓存（仅支持 nightly）、Buck2 的 DICE 引擎——指出它们均未能提供「salsa 式增量计算 + 全量落盘」的完整方案。基于此，作者决定构建名为 Ajika 的新引擎，将 salsa 的增量计算能力与文件系统持久化结合，以在低内存场景下实现高效增量计算。

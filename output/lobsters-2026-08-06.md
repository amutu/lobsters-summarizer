## 1. Rust 语言项目采用 LLM 使用政策

- 原始链接: <https://blog.rust-lang.org/inside-rust/2026/08/05/rust-langrust-is-adopting-an-llm-policy/>
- 英文标题: rust-lang/rust is adopting an LLM policy

Rust 项目五个团队近期通过了一项由 Jynn Nelson 起草的政策，规范在 rust-lang/rust 单一仓库中使用大语言模型（LLM）的方式。该政策并非官方对 LLM 的总体立场，仅适用于特定贡献场景，主要影响四类人：审查 PR 的维护者、用 LLM 生成代码的作者、用 LLM 发现并提交 issue 的人，以及直接引用 LLM 输出的评论者。政策制定的背景是：LLM 让“精美的技术产物”不再代表付出与理解，降低了写代码门槛从而加剧审查负担，且机械复制 LLM 回复浪费社区时间。此前缺乏公开规则，导致处理不一致。政策核心原则是：LLM 可用于提问、分析、提炼、完善、检查、建议和审查，但不得用于“创造”。公开的 LLM 输出必须明确披露；LLM 生成的代码变更需满足更高的测试和审查标准，且禁止触及健全性关键改动。审查者有权关闭违规 PR，但不得因怀疑使用 LLM 而无证据指责他人。政策也允许用母语发帖，无需英文翻译。该政策旨在建立清晰的明线规则，并收集数据以支撑未来调整，同时不禁止 LLM 的使用，也不强迫任何人使用 LLM。

## 2. 进攻性互联网姿态：让服务器对恶意爬虫与骚扰者不再友好

- 原始链接: <https://bruceediger.com/posts/offensive-machine/>
- 英文标题: Offensive Internet Posture

作者介绍了一系列用于保护自己博客VPS的“进攻性”防御措施，旨在让互联网底层的恶意扫描器、爬虫和垃圾信息发送者感到无利可图、浪费时间。具体做法包括：部署一个永不接受凭据的虚假WordPress登录页，故意拖延5秒再拒绝；在22端口运行endlessh（慢速连接陷阱），将真实sshd移到其他端口；针对Meta等用户代理直接返回403，针对xAI、Claude、GPTbot等AI爬虫则将其引导至无限虚假网站；对/phpinfo.php请求返回伪造的PHP信息；robots.txt中设置长延迟，并“禁止”访问一个不存在的/porn目录；运行一个包含200多万虚假页面的爬虫垃圾场；尝试通过博客页脚对LLM进行提示注入或投毒；运行TFTP蜜罐，诱捕扫描错误配置TFTP服务器的人；联系页面只用来浪费垃圾邮件发送者的时间，并随机设置0到25个随机命名的Cookie。作者还提出了其他可行措施，如运行SMTP、Telnet、FTP蜜罐，将Google爬虫也导向虚假网站，以及上线WordPress蜜罐。核心观点是：如果互联网上有一定比例（作者猜测超过10%）的机器运行蜜罐或对底层骚扰者采取进攻性姿态，这些骚扰者就会因成本过高而离开。同时，作者强调防御方式应“ idiosyncratic ”，多样化，这样大型企业难以统一应对，个人垃圾信息运营者更是无法适应。

## 3. 比忍者还快：build2 构建性能对比 Ninja

- 原始链接: <https://build2.org/blog/faster-than-ninja.xhtml>
- 英文标题: Faster Than Ninja

文章评测了现代原生构建系统 build2 与 Ninja 的从零构建性能。作者引用一篇关于构建瓶颈的文章，其中将 Ninja 视为构建系统的“光速”基准，但指出 Ninja 依赖 CMake 生成构建文件，且功能极简。作者使用 Xerces-C++（299 个 C++ 翻译单元）进行公平对比：Ninja 构建耗时 3.4 秒，但加上 CMake 生成时间则需 19 秒；build2 默认配置耗时 3.8 秒（慢 11%）。通过禁用更精确的变更跟踪（模拟只读项目）后耗时降至 3.4 秒，再禁用文件缓存压缩后达到 3.355 秒，比 Ninja 快 2.2%。文章指出 build2 额外承担了 CMake 的工作，如生成版本头文件、提取编译器信息等，仍然保持同等速度。其优势源于三大设计决策：积极缓存环境信息、多线程处理内部任务（如解析头文件依赖）、以及显式提取依赖并进行部分预处理，从而改善文件访问局部性并降低内存压力。最后附有详细基准环境与命令。整体表明 build2 在功能更全面的前提下，构建速度可与 Ninja 匹敌甚至略优。

## 4. 自动过期并自我警告的 Nix Override

- 原始链接: <https://jezenthomas.com/2026/07/nix-overrides-that-expire-themselves/>
- 英文标题: Nix Overrides That Expire Themselves

文章介绍一种 Nix override 模式，让原本会因 nixpkgs 更新而过时的 override 在求值时自动发出警告，提醒开发者删除。作者发布了 yesod-form-1.7.10，但固定的 nixpkgs 版本只包含旧版本，因此需要写 override 通过 callHackageDirect 拉取新版。为了在将来升级 nixpkgs 后知道这个 override 已多余，作者用 prev.lib.versionAtLeast 比较 hprev.yesod-form.version 与所需版本，再用 prev.lib.warnIf 在条件满足时打印提示，例如：yesod-form >= 1.7.10 is now in nixpkgs, the override can be removed. 这样 override 就会主动宣告自己已过期。该方法不限于版本号，只要 override 的存在理由能用条件表达即可。比如某个包原先在 nixpkgs 里被标记为 broken，开发者加了 markUnbroken 处理；当上游修复后 broken 标记被移除，便可用 warnIfNot p.meta.broken 输出警告，提示删除对应 workaround。核心是利用 Nix 的警告函数和条件判断，让不再必要的 override 在求值阶段产生可见提醒，降低技术债和人工排查成本。

## 5. 用高斯模糊作画：基于图像边缘的自适应数字绘画系统

- 原始链接: <https://yogthos.net/posts/2026-08-03-splat-painter.html>
- 英文标题: Painting with Gaussians

本文作者在之前构建边缘感知像素化工具的基础上，进一步将边缘信息应用于数字绘画。核心思想是用2D高斯分布模拟笔触，其中均值决定笔触位置，协方差编码笔触方向、拉伸和旋转，颜色和透明度用于叠加混合。作者指出，现有基于梯度下降的方法（如DrawingWithGaussians）既慢又难以控制，最终只是有损重建，不像绘画。因此他采用结构张量和Di Zenzo颜色张量提取边缘方向与相干性，使笔触沿轮廓拉伸；结合多尺度Haar小波生成细节密度图，在纹理丰富的区域放置更多小笔触，平坦区域则用大笔触。为了打破网格伪影，使用Wang avalanche哈希生成白噪声放置位置，再用Perlin噪声为笔触添加自然抖动和流动感。在分层绘制中，先用大而透明度的笔触铺底色，再逐层叠加更小、更透明的笔触以增加细节，边缘附近使用锥形笔触链，避免颜色交叉。最后作者将流程移到GPU，使用OpenGL几何着色器进行变换反馈，支持实时交互调整参数。作者认为最终结果在视觉效果上接近真实绘画。

## 6. 生于反对：业余编程社区为何强烈抵制LLM使用

- 原始链接: <https://blog.fogus.me/llm/born-against.html>
- 英文标题: Born Against, or why hobby programming communities are aggressively against LLM usage

本文探讨了业余编程社区对LLM（大语言模型）使用日益敌对的原因。作者从一则关于国际象棋引擎开发的GitHub讨论出发，观察到类似情绪广泛存在于OSDev、LangDev、TxtDev、EmuDev、RLDev、演示场景和代码高尔夫等小众社区。这些社区普遍认为，其领域知识是经过艰苦斗争获得的，而使用LLM则完全错过了重点。在这些社区中，掌握一门困难领域的过程本身就是成果，而“能运行”只是附带的好事。作者指出，即便早期有些社区真诚尝试引入LLM，也因实践者缺乏深层理解以及部分成员的敌视而迅速恶化，后者将LLM视为作弊。这些社区历史上就以严格的门槛和缓慢的进步著称，因此有人想借LLM快速获得认可也不足为奇。在传统的小众开发者圈子里，尊重是通过多年参与论坛、分享优雅代码、展现真诚好奇心和传播深层领域知识而慢慢赢得的。归根结底，这些社区不在乎你的代码能否运行，而在乎你是否知道它为什么以及如何运行。作者认为，LLM最适合作为“力量倍增器”而非“替代品”，在已经深刻理解领域的专家手中可以起到杠杆作用。但在这些社区中，整个练习的意义就在于学习——用LLM生成成品并不能让我们成为工匠，只会剥夺我们对手艺的掌握。最后作者提醒，即便是专家也无法天然免疫于被LLM误导。

## 7. C++26: #embed 嵌入二进制资源

- 原始链接: <https://www.sandordargo.com/blog/2026/08/05/cpp26-embed>
- 英文标题: C++26: #embed

本文介绍了C++26新增的预处理器指令#embed，它允许在编译期直接将二进制文件（如证书、图片、默认配置）转换为整型常量表达式序列，无需外部工具或生成代码。此前开发者常依赖xxd、objcopy、脚本或CMake等方案，既脆弱又易因忘记重新生成而过时。#embed的设计经历了漫长标准化过程：P1967从2020年提交，经14个修订版、五年时间才被委员会接受；早期P1040曾提议通过constexpr函数实现，最终转向预处理器方案。基本语法为`#embed "file"`，展开为逗号分隔的字节值，路径规则与#include类似。它还支持四个标准参数：limit限制嵌入字节数；prefix和suffix在资源非空时前后添加令牌（需注意逗号处理）；if_empty在资源为空时提供回退内容。配套的`__has_embed`宏可检测资源是否存在及是否为空，返回三个常量：未找到、找到非空、找到但空。文中给出了嵌入默认配置在实际程序中的示例，展示其简化构建流程的优势。编译支持方面，GCC 15完整支持，Clang 19+作为C23扩展支持，MSVC尚不支持；大文件嵌入有内部优化，GCC嵌入100MB文件约1.3秒/117MiB内存，而xxd生成头文件需139秒/13GiB。总结认为#embed消除了整个类别的构建系统复杂性，让二进制资源成为源码的一部分。

## 8. Lua 社区需要学会向前看

- 原始链接: <https://hisham.hm/2026/08/04/the-lua-community-needs-to-learn-to-move-on/>
- 英文标题: The Lua community needs to learn to move on

本文是作者对 Lua 社区长期过度支持旧版本现象的反思。起因是 LuaJIT 维护者 Mike Pall 删除了上游仓库中旧版本的标签，以此强制用户升级，这一做法虽有争议，但其背后是对无数项目长期停留在 luajit-2.1.0-beta3 等旧版本、并不断提交早已修复的 bug 报告的无奈。作者在 LuaRocks 维护中也遇到过类似问题，理解双方难处。他指出，自 Lua 与 LuaJIT 在 5.2 时代分裂以来，社区形成了一种瘫痪性习惯：库作者持续测试和支持 Lua 5.1 到 5.5、LuaJIT 2.1 及 OpenResty 变体甚至 3.0。虽然 Lua 作为嵌入式语言确实可能因应用捆绑而长期绑定旧版本，但作为可扩展语言，它应当像其他脚本语言一样，只支持最新的 PUC-Rio Lua 和最新 LuaJIT。作者承认自己曾通过维护 compat-5.3 等兼容层参与并加深了这种碎片化问题，现在他开发 Teal 语言（类似 TypeScript 之于 JavaScript），旨在帮助开发者跨越版本差异，一次编写即可生成 5.1 至 5.5 的 Lua 代码。最后他强调，Lua 官方和 LuaJIT 官方都已停止旧版本支持，库作者也应效仿，让使用极旧版本的用户使用相匹配的旧生态，而不是无限期迫使维护者承担 20 多年的兼容负担。

## 11. 别再给我发错误信息了

- 原始链接: <https://kramkow.ski/article/2026/08/05/stop_sending_me_your_errors.html>
- 英文标题: Stop Sending Me Your Errors

作者批评了通过multipart/alternative邮件格式的text/plain部分发送错误提示的做法。他举例说收到一封纯文本正文为“Plain text version not available”的邮件，但HTML部分才是真正内容。他指出，multipart/alternative在RFC中的设计初衷是以多种可互换形式呈现同一信息，而不是用来向收件人报告错误。如果邮件客户端无法处理HTML，应该由客户端自己报告错误，而不是在纯文本部分嵌入错误信息。作者分析了三类会看到纯文本内容的用户场景：使用非MIME老客户端、支持MIME但不支持HTML的客户端，以及主动配置为偏好纯文本的用户。对前两类用户，错误信息毫无帮助；对第三类用户，则要被迫手动切换到原先不偏好的HTML格式，纯属添乱。他还列举了其他真实收到的离谱纯文本示例，比如“此邮件包含html内容”、夹杂大量空白行和HTML标签等。最后他提出解决办法：如果不能生成真正有意义的纯文本替代，就不要添加text/plain部分。这样既符合规范，也能降低邮件被标记为垃圾邮件的风险，让所有人受益。

## 13. GNU/Emacs 的液态玻璃效果

- 原始链接: <https://github.com/larrasket/emacs-liquid-glass>
- 英文标题: Liquid Glass effect for GNU/Emacs

本文是“五要点Haskell”系列的一篇，核心概念是“无条件拣选”：借助 Haskell 的 forall 和参数多态，类型本身就能强制实现某些行为，无需额外注解或运行时检查。作者对比 Java/TypeScript 中泛型函数可依赖运行时类型做条件分支，而 Haskell 因类型擦除，forall a. a -> a 只能是恒等函数，forall a. a -> String 必须是常量。文中通过“猜类型签名可能实现”的游戏展示自由定理：例如 [a] -> [a] 只能重排或改变元素个数，[a] -> Maybe a 只能按位置取元素且空列表必为 Nothing，[a] -> Int 只能依赖长度或为常数，a -> [a] 必须重复同一个值。这些自由定理源于范畴论中的自然变换，因而与 map/fmap 可交换。实践上，参数多态可用于施加约束：将 User 的 userId 参数化为 uid，可保证处理函数不改变 ID；将 Checklist 的 items 参数化为 Traversable t，可保证 updateItems 不增删条目数量。作者主张放弃具体类型带来的灵活性，用参数多态换取更强、免费的保证，体现“最小能力原则”。

## 1. Coreutils 被拒绝的功能请求汇总

- 原始链接: <https://www.gnu.org/software/coreutils/rejected_requests.html>
- 英文标题: Coreutils - rejected feature requests

本文由 GNU coreutils 维护者整理，系统列出了项目中被拒绝的功能提案及拒绝理由，按命令逐一分类，涵盖 cat、chmod、cp、cut、date、dd、df、du、join、ls、mv、rm、shred、sort、stat、*sum、touch、uniq、wc 等几乎所有核心命令，以及 misc 杂项和新命令提案。拒绝理由高度一致，主要集中在以下几类：其一，现有工具或 shell 组合已能实现同等效果，例如用 sed、awk、find、grep、rsync 等替代；其二，功能过于特化或收益有限，不值得增加核心工具的复杂度；其三，与 POSIX 标准或既有接口设计冲突，如 echo 的选项终止方式；其四，涉及文件系统或平台特定行为，缺乏通用性。文章还明确表达了 coreutils 的设计哲学：保持工具精简，复杂需求交由专用工具或 shell 脚本、别名、包装脚本处理，不鼓励新增环境变量或全局配置文件。新命令提案（如路径操作、稀疏文件、bloom filter 等）也大多因「现有工具已足够」或「不够通用」被拒。整体而言，该文档为贡献者提供了清晰的拒绝依据，也体现了 coreutils 作为基础工具集「少即是多」的取舍原则。

## 2. 从实习生到软件架构师：六层认知跃迁

- 原始链接: <https://chauhankiran.blogspot.com/2026/09/levels.html>
- 英文标题: From Intern to Software Architect

本文以六个层级描绘了软件工程师从实习生成长为架构师的认知演进路径。第一层关注语法与语言构造（变量、函数、条件）；第二层转向程序文件，能跨文件理解修改影响；第三层将文件视为逻辑模块，理解模块内关联；第四层将多个模块视为完整应用，在代码评审中引入全局上下文；第五层视野扩展到应用外部，涵盖代理、DNS、安全、防火墙等周边服务，掌握请求的完整链路；第六层则跨越团队边界，理解多个应用如何协同构成完整产品，这正是软件架构师的核心视角。文章指出，层级与职位的映射可灵活调整，例如将一至二层合并为初级工程师、三至四层为中级工程师等。自上而看的视角揭示了抽象层的设计意图：上层架构足够完善，下层便无需关心更高层的细节，每一层只需处理必要的上下文。最后，文章讨论了AI时代的影响——层级边界趋于模糊，工程师被期望跨层级工作（如二层人员需处理一至四层任务），但天才虽能跳跃层级，仍难以替代经验所积累的判断力。

## 5. 一种面向交互应用的新等面积地图投影（缩放时原生过渡至墨卡托）

- 原始链接: <https://www.benjoffe.com/map>
- 英文标题: A New Equal-Area Map for Interactive Computer Use (natively zooms to Mercator)

本文提出一种面向交互式地图的新等面积圆柱投影，核心公式为 y=atanh(sin(lat)·a)/a、x=lon·k，形式极为简洁。该公式具有优雅插值性质：a=1 时退化为墨卡托等角投影，a→0 时退化为兰伯特等面积投影，中间值生成折衷投影。作者通过线性插值 a 和 k 实现缩放时从等面积视图到墨卡托视图的无缝过渡，兼顾联合国「Correct the Map」决议所关注的国家面积失真问题与墨卡托在导航中的方向保真优势。相比 Equal Earth 需多个拟合常数及牛顿迭代求逆，新公式正逆变换均为闭式解，计算更高效。作者以微积分严格证明了等面积性质（面积比恒为常数 b），并展示了 2:1、黄金矩形等宽高比下的折衷圆柱投影效果，指出新投影在北极、南极区域的空间浪费远少于传统方案。作者查阅 Snyder 经典著作及在线文献后未发现该公式先例，认为其新颖性在于算法简洁性与视觉效果的结合。未来计划将方法扩展至圆锥投影。

## 6. .NET 11 性能改进详解

- 原始链接: <https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-11/>
- 英文标题: Performance Improvements in .NET 11

本文以电影《This Is Spinal Tap》中「调到十一」的经典桥段开篇，寓意 .NET 11 在运行时与库层面又积累了一年性能优化。文章首先介绍基准测试环境，使用 BenchmarkDotNet 对 .NET 10 与 .NET 11 进行逐项对比。核心内容聚焦 JIT 编译器改进：一是去抽象化（Deabstraction），包括保护式去虚拟化（GDV）将接口或虚调用转为类型检查加快速路径，使内联成为可能，从而让常量传播、死代码消除等优化穿透调用边界；二是逃逸分析扩展，.NET 11 将可空值装箱的临时对象暴露给逃逸分析，使不逃逸的装箱可完全消除堆分配，相关基准中分配量从 24 字节降至零；三是条件逃逸分析（CEA）在枚举器场景的进一步扩展，解决 GDV 产生的回退分支导致枚举器被误判为逃逸的问题。文章还概述了数百项微观优化，涵盖边界检查移除、锁消除、常量折叠、冗余检查提升、指令融合、系统调用规避、SIMD 数组拷贝等，强调这些改进逐层叠加、可量化验证，整体性能「确实更响了一格」。

## 8. GDScript 的优劣与不足

- 原始链接: <https://azhdarchid.com/gdscript-good-bad-ugly/>
- 英文标题: GDScript: The Good, Bad, and Ugly Parts

作者将一套系统从 TypeScript 移植到 GDScript（Godot 引擎），借此全面评估该语言。优点：GDScript 专为游戏逻辑设计，提供原生 Vector2/Vector3、整数与浮点区分、match 语句、packed arrays 及 lerp()、smoothstep() 等常用函数；与引擎深度集成，注解系统、preload()/load() 和信号机制大幅提升开发效率；以手动内存管理与引用计数替代垃圾回收，避免帧间卡顿。缺点：类型系统严重不成熟，map() 等泛型操作返回未类型化数组，函数仅有 Callable 类型，缺乏联合类型与判别联合，narrowing 逻辑远弱于 TypeScript，作者建议多数场景避免使用类型化集合。不足：缩进语法、冗长的 lambda 写法、缺少解构赋值与展开运算符、不支持不可变对象模式，使函数式编程体验较差，数组甚至没有 flatmap() 和 zip()。作者认为类型系统是最大短板，但因 GDScript 与引擎绑定、无需向后兼容，未来改进空间较大，建议 Godot 5 可引入 Lua 风格语法。

## 9. 安装停滞：WebKit 与 Web 应用安装之争

- 英文标题: Stalling installing

作者以 W3C 邀请专家身份参加了技术架构组会议，讨论可安装 Web 应用（PWA）这一悬而未决的大方向问题。多数浏览器厂商希望推进安装 API 的细节设计，但 WebKit 方直接否定了整个前提，主张不应由开发者触发安装流程，而应交由浏览器自行决定，并质疑用户是否真有此需求。作者指出，若 iPhone 上已存在便捷的 Web 应用安装方式，该立场尚可成立，但现实中安装入口深藏于「分享」图标下五层菜单，堪称可用性噩梦。更关键的是 WebKit 立场存在明显矛盾：一方面将安装类比为书签（无需 API），另一方面又担忧安装后应用获得推送等更强权限，却忽略了其他浏览器已通过权限机制安全实现这些功能。作者在十分钟内代表开发者发言，强调开发者亟需启动安装流程的 API，用户应享有与原生应用对等的安装选项，而原生应用在数据访问上的不对称优势损害了 Web 的公平竞争。评论区多位开发者呼应，批评 Apple 以引擎级保护主义拖延跨平台 Web 应用标准的推进。

## 11. IBM为NSA建造冷战最强密码破译机Harvest

- 原始链接: <https://spectrum.ieee.org/cold-war-codebreaker-nsa-ibm>
- 英文标题: IBM Built the Cold War’s Most Powerful Code Breaker for the NSA

IBM于1962年为美国国家安全局（NSA）交付代号Harvest（IBM 7950）的专用密码破译计算机，由IBM 7030 Stretch主机与定制数据流协处理器组成，运行速度达当时其他计算机的200倍，持续服役至1976年。Harvest采用流式处理架构，从共享内存中并行读取两路数据流，经逻辑单元与表查找单元处理后输出第三路结果，是当今视频流与AI实时处理的前驱，其模块化设计类似现代GPU协处理器。为匹配巨大吞吐量，IBM建造了世界首个自动化磁带库Tractor（IBM 7955），伺服机械臂可自动存取数百盒磁带，在线存储达44GB，远超同时代磁盘系统。IBM与NSA联合开发专用编程语言Alpha，支持通配符与层级字符串操作，为密码分析提供灵活表达。关键设计者Frances Allen、Frederick Brooks Jr.与James Pomerene后均成为计算领域重要人物。1976年，因Tractor机械部件磨损且制造商已倒闭，Harvest被永久关闭，结束近15年服役，历经古巴导弹危机至缓和时代，处理了NSA最敏感的截获信息。

## 12. Nix 存储的本质：仅需三个函数

- 原始链接: <https://fzakaria.com/2026/09/11/a-nix-store-is-three-functions>
- 英文标题: A Nix store is three functions

本文揭示了一个简洁事实：要成为 Nix 二进制缓存，只需实现三个 GET 请求——返回 nix-cache-info、返回 narinfo 元数据、返回压缩归档文件。作者构建 trynix 时发现 GitHub Pages 默认设置宽松的 CORS 策略，将 nix copy --to file:// 的输出提交到 Git 仓库即可免费充当 Nix substituter。由于 narinfo 的签名仅覆盖 StorePath、NarHash、NarSize 和 References，不覆盖 URL 字段，任何能返回匹配 NarHash 的存储介质均可作为缓存，甚至 URL 可指向不同协议或域名。作者列举了多种创意实现：gachix 将归档存入 Git 对象库（体积缩减约 82%）、DNS TXT 记录、pastebin、OCI 镜像仓库，乃至 YouTube 视频编码。文章重点演示了将 Nix 包发布到 npm 的完整流程：用 nix copy 生成本地缓存目录，添加 package.json 后 npm publish，即可通过 unpkg.com 让 Nix 拉取完整依赖闭包并运行。npm 的 dist-tags 机制还能模拟 Nix 的 channel 语义，实现 staging 与 production 分流。主要不足是 npm 缺乏增量发布，每个版本均为完整 tarball，导致共享依赖被重复上传。作者认为将每个 store path 拆为独立包虽可解决，但不符合 npm 生态精神。

- 原始链接: <https://anekstein.com/posts/2026-08-22.html>
- 英文标题: Search over Algebraic Graphs

本文探讨如何在 alga 库的代数图表示上直接执行 Dijkstra 最短路径搜索，而无需先展开为邻接表。alga 的 Connect 构造子以 O(1) 空间描述 O(n²) 条边的双图，本质上是一种图压缩；若先物化所有边再搜索，将丧失亚二次算法的优势。作者借鉴 Bannach 等人的「切换图」（switching graph）理论，将代数图表达式映射为 DAG 压缩结构，并在此基础上实现搜索。具体做法是：先用递归方案（cata）自底向上遍历表达式树，构建包含父节点映射、顶点出现位置及子节点引用的索引；再定义 Up、Down、At 三种搜索状态，通过邻居函数在表达式节点间惰性生成搜索前沿，经过 Connect 节点时计入边权重。最终 Dijkstra 以优先队列驱动，时间复杂度为 O(s log s)，其中 s 为表达式大小。基准测试表明，对于压缩率高的图（如传递锦标赛、完全有向图、随机稀疏图），切换图方法在时间和内存上均显著优于 alga 原有的邻接表方案；而对于压缩率低的图（如路径图），两者差距不大。

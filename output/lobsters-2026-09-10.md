## 2. 拒绝与随机鹦鹉交互：一位工程师的AI零容忍宣言

- 原始链接: <https://ploum.net/2026-09-09-ai_policy.html>
- 英文标题: I Don’t Want to Interact With Stochastic Parrots

作者Ploum（作家兼工程师）在文中宣布其个人AI政策：完全拒绝与任何AI、LLM或聊天机器人交互。他拒绝阅读AI生成文本，认为写作本身即思考，AI输出只是「随机平均垃圾」，无法代表个人；若对方用AI代写，他要求直接发送原始提示词。他拒绝AI生成图片，视其为廉价、缺乏人类情感的产物，会立即引发不适感。他拒绝运行AI生成代码，警告这会使项目丧失人类可维护性，最终走向不可修复的崩溃，并强调开源软件的价值在于人类可理解、可修改。他拒绝在讨论中接受AI作为论据来源，认为这等同于放弃自由意志。在教育方面，他发现学生使用AI后表现普遍下降，因此要求所有作业必须由学生本人完成，引用Scalzi的「吉他英雄」比喻说明AI无法替代真实学习。但他将AI类比为一种「药物」，不评判私人使用，只要求不被强迫接触。全文立场鲜明，核心主张是：人类认知劳动不可外包给随机算法，任何试图以AI替代思考的行为都是对交流本身的否定。

## 3. DNS系统的目的似乎成了传播诈骗

- 原始链接: <https://shkspr.mobi/blog/2026/09/the-purpose-of-dns-is-to-spread-scams/>
- 英文标题: The purpose of DNS is to spread scams

本文指出域名系统（DNS）正沦为诈骗犯罪的主要载体。作者引用Interisle报告数据：2025年新增8500万个通用顶级域名（gTLD）注册中，至少10%至20%最终出现在安全黑名单上，13个TLD的注册被封锁比例超过50%。由于互联网传播速度极快，诈骗域名从注册到全球可访问仅需一分钟，等注册商或安全列表反应过来，数百万条钓鱼邮件早已发出。作者探讨了多种可能的治理路径：注册商加强实名认证（KYC）、收取保证金、设置域名上线延迟期供机构审查、关键词过滤等，但每种方案都会对合法用户造成不便——例如匿名注册抗议性域名、小型注册商合规成本、大企业获得域名否决权等。ICANN已在协调各方滥用报告机制，但与会者警告，在AI时代DNS滥用只会更容易，犯罪者因利润驱动将不断绕过任何限制。作者坦言没有理想答案，但强调DNS正面临类似安卓应用生态的信任危机，呼吁在保持开放性的同时降低系统危害。

## 4. rustls 十周年回顾

- 原始链接: <https://rustls.dev/blog/2026-09-08-a-decade-of-rustls/>
- 英文标题: A decade of rustls

本文由 Joe Birr-Pixton 基于 RustConf 2026 演讲撰写，回顾 rustls 项目十年发展历程。rustls 于 2016 年 5 月首次提交，不到四个月即发布 0.1.0，早期得益于 briansmith、djc 等外部贡献者。2018 年引入 QUIC 支持，2018–2020 年完成 CNCF 资助、Cure53 执行的第三方安全审计，2021 年起获得 ISRG Prossimo 计划资助，推动可插拔密码提供者、no_std 支持、FIPS 认证、后量子密钥交换及加密 ClientHello 等重要特性落地。0.23 版本（2024 年 2 月）进入稳定期，累计 43 个非破坏性更新。即将发布的 0.24 带来四项重大改进：一是外部缓冲机制，TLS 数据通过新 trait TlsInputBuffer 传入、输出追加至用户提供的 Vec，避免额外拷贝；二是异步友好的会话类型系统，将握手建模为 NeedsInput→Accepted→Complete 等步骤，支持异步、阻塞及完成式驱动；三是「分离模式」，将发送与接收拆为 SendTraffic 和 ReceiveTraffic 两个 Send 对象，全双工场景吞吐可翻倍；四是 CryptoProvider 改为独立 crate（如 rustls-aws-lc-rs、rustls-ring），消除 feature 统一导致的 panic。作者表示 0.24 稳定后将发布 1.0，目标是提供可长期维护的稳定 API。

## 5. Solaris 旋转门（Turnstile）机制

- 原始链接: <https://rdmsr.github.io/writing/turnstiles/>
- 英文标题: Solaris Turnstiles

Solaris 曾以出色的 SMP 支持闻名，其中「旋转门」（turnstile）是一项鲜少被讨论却影响深远的创新。设计动机有二：一是阻塞锁需记录持有者、等待队列等状态，内嵌于每个锁会使细粒度锁开销过大；二是阻塞锁不禁止抢占，易引发优先级反转。Turnstile 的核心思想是将等待队列与优先级继承状态从锁中剥离：每个线程创建时分配一个 turnstile，阻塞时将其「捐赠」给所等待的锁，内核通过哈希表以锁地址定位对应 turnstile；释放锁时等待线程从空闲链表取回任意 turnstile。多跳优先级继承则沿「turnstile→持有者→turnstile」链逐级提升优先级。局限在于仅支持单一继承者，多所有者锁需依赖启发式策略。该机制已影响 Illumos、macOS XNU、FreeBSD、NetBSD 等内核，其「等待机制外置于锁」的思想也见于 Go 运行时信号量和 WTF::ParkingLot 等用户态组件。

## 6. Async/Await 设计空间探索

- 原始链接: <https://cel.cs.brown.edu/blog/design-space-async-await/>
- 英文标题: A Design Space Exploration of Async/Await

本文围绕现代编程语言中 async/await 机制的设计差异展开研究，作者将这一范式统称为「直线异步」，并指出尽管各语言的设计初衷相似——让并发代码看起来像顺序代码——实际语义却远非一致。文章以一个极简的后台写日志示例说明问题：同一伪代码在 Python、Rust、C#、JavaScript、Swift、Tokio、Trio 等七种运行时中产生四种不同输出，且三个变体中没有任何两种运行时给出完全相同的结果。作者进一步提炼出九个影响可观察语义的设计维度，归入任务生命周期的三个阶段：启动阶段（急切性、挂起保证）、结束阶段（存在范围、引用强度、销毁方式、异常传播）和取消阶段（取消感知、传播方向、持久性）。每个维度都有多种取值，各语言组合不同，导致行为分叉。文章强调没有绝对对错，每种选择都有性能、内存、易用性等权衡。为精确刻画这些差异，作者将设计空间形式化为一套异步程序核心演算的小步语义，通过抽象机状态转移图展示不同设计决策如何导致不同执行路径。最终结论是：即便对小型程序，理解其 async 语义也需要系统性地追踪多个设计维度的交互，建议读者参阅完整论文以深入理解。

## 7. ID设计与主键：从业务需求到物理表结构

- 原始链接: <https://anchorsandlinks.com/posts/primary-keys/>
- 英文标题: ID design and primary keys

本文为Alexey Makhotkin所著《数据库设计书》的补充章节，系统讨论数据库设计中主键的选取方法，分为逻辑层与物理层两个视角。逻辑层首先引入「外部ID」概念，即面向业务、可对外使用的唯一标识（如零件编号、护照号、URL路径），并指出其三大特性：唯一对应一个实体、可变更、一个实体可拥有零个或多个外部ID。随后提出「锚点ID」，用于在数据库内部无歧义地标识每条记录，通常采用无业务含义的自增整数，且必须不可变。文章讨论了锚点ID能否直接充当外部ID：技术上可行，但自增整数可能泄露业务量，宜改用日期加随机数形式；而外部系统生成的ID（如护照号）可能因跨国重复或伪造而不可靠，有时只能作为属性值而非独立标识。物理层则回归主键本身，以一张混淆列名的示例表说明主键的唯一性与非空约束，并以一个极简内容管理系统（pages表）演示标准锚点表设计：id为整数主键，slug作为外部ID施加唯一约束，content为普通文本列。最后强调唯一性约束在逻辑上对应外部ID，在物理上由主键隐含，且可覆盖多列但不可跨表。第二部分将讨论复合主键及链接表、EAV表等常见设计策略。

## 8. CUDA Rust 发布：两条 GPU 内核编写路线

- 原始链接: <https://developer.nvidia.com/blog/introducing-cuda-rust-two-tracks-for-writing-gpu-kernels/>
- 英文标题: Introducing CUDA Rust: Two Tracks for Writing GPU Kernels

2026年9月，NVIDIA 正式推出 CUDA Rust，允许开发者用 Rust 原生编写 GPU 内核并直接编译为 PTX，填补了此前内核必须依赖其他语言的空白。项目提供两条路线：SIMT 路线（cuda-oxide）与 Tile 路线（cutile-rs）。cuda-oxide 作为自定义 rustc codegen 后端，经 Pliron IR 和 LLVM 将「#[kernel]」函数编译为 PTX，需绑定 nightly 工具链，目前处于早期 alpha 阶段。cutile-rs 基于较新的 Tile 编程模型，在稳定 Rust 1.89 上即可运行，通过 CUDA Tile IR 进行 JIT 编译，已发布至 crates.io 并被 HuggingFace 的 Grout 推理引擎及 mistral.rs 采用。两条路线均在编译期保证内存安全：cuda-oxide 借助 DisjointSlice 与 launch contract 防止别名；cutile-rs 通过张量分区与所有权机制确保每个 Tile 独占写入，经典别名错误在编译阶段即被拦截。文章以 1024 元素逐元素加法为例，并列展示了两种写法的完整可运行代码。NVIDIA 同时宣布将支持 CUDA Rust、C++ 与 Python 之间的跨语言互操作，避免前端语言锁定。两个项目均处于早期阶段，API 可能变动，NVIDIA 邀请社区参与共建。

## 9. Emacs Consult 异步搜索为何感觉慢及加速方法

- 原始链接: <https://www.jamescherti.com/emacs-consult-speed-async-searche-grep-ripgrep-fd-find/>
- 英文标题: Why Emacs Consult async searches feel slow and how to speed them up

本文解释了 Emacs 的 consult 包中异步搜索命令（如 consult-ripgrep、consult-grep 等）为何比 Counsel 感觉迟钝，并给出加速方案。作者指出，consult 默认采用保守的防抖（debounce）和节流（throttle）延迟，加上独立的 UI 刷新间隔，导致每次输入后会有短暂停顿才启动搜索或更新结果，这是有意设计而非性能缺陷。文章介绍了三个关键变量：consult-async-input-debounce（防抖，停止输入后才触发搜索，避免为每个中间字符启动冗余进程）、consult-async-input-throttle（节流，硬性限制搜索进程的最大启动频率）、consult-async-refresh-delay（控制完成界面拉取新结果并重绘的间隔）。将三者分别设为 0.05、0.1、0.05 秒可显著降低输入延迟，使体验接近 Counsel 的即时反馈。但作者强调，这些设置并不会让 ripgrep 等外部工具本身跑得更快，只是缩短了 Emacs 内部的等待与重绘周期。代价是更频繁的进程创建和界面重绘会增加 CPU 占用与垃圾回收压力，在笔记本上会加速耗电。因此，激进设置适合插电的高性能机器；在电池受限或搜索超大项目时，保守默认值反而更均衡。最优取值取决于打字速度、项目规模、搜索工具性能及功耗约束，本质是输入延迟与异步工作频率之间的显式取舍。

## 10. 3×3棋盘上2048游戏的穷举分析

- 原始链接: <https://www.chiark.greenend.org.uk/~sgtatham/quasiblog/small2048/>
- 英文标题: Analysing 2048 on a 3×3 board

Simon Tatham为缩短2048游戏时长，将棋盘缩小为3×3，并通过穷举所有棋盘状态来精确计算完美玩家达成各目标数字的概率。状态空间为(k+1)的9次方，即便目标为2048也仅约2的32次方个状态，且游戏单调递增、无循环，适合用带缓存的递归（仅缓存玩家回合的pvalue）求解。关键结论：完美玩家达成256的概率约99.6%，512约73.7%，1024仅约1.1%，而2048概率严格为零。作者给出简洁证明：合成2048需同时存在两个1024，逆向推导要求9格全部≥8，但最新随机落子只能是2或4，故绝对不可能。1024极难则因需9格全≥4，而随机落4的概率仅1/10。此外，作者发现用32位float计算时128的成功概率被舍入为1，改用64位double后实为约0.9999998；解决方法是改算「失败概率」以规避接近1的浮点精度问题。文章还讨论了未采用的对称性归一化优化、与「Satan」（最坏对手）对弈等延伸话题，并提供了可在线游玩的3×3 2048实现。

## 11. Upyo：面向 JS/TS 的跨运行时、跨服务商邮件库

- 原始链接: <https://hackers.pub/@hongminhee/2026/upyo-email-decoupled-from-where-and-how>
- 英文标题: Email, decoupled from where and how: A cross-runtime, cross-provider email library for JS & TS

文章介绍了名为 Upyo 的 JavaScript/TypeScript 邮件发送库，核心目标是让应用代码与运行环境和邮件服务商解耦。Upyo 基于 fetch、Web Streams、Web Crypto 等 Web 标准 API 构建，不依赖 node:net、node:tls 等 Node.js 专有模块，因此同一份代码可在 Node.js、Deno、Bun、Cloudflare Workers 等环境中直接运行。所有邮件服务（SMTP、JMAP、Resend、SendGrid、Mailgun、Amazon SES 等）统一通过 Transport 接口抽象，切换服务商只需替换 Transport 实例，业务代码无需改动。依赖方面，如 @upyo/ses 自行实现 AWS Signature v4 而非引入 AWS SDK，以保持跨运行时兼容。在可靠性层面，RetryTransport 将重试策略封装在传输层，应用代码无需关心；PoolTransport 支持按优先级故障转移或轮询分发，两者可叠加组合。开发体验上，LogTapeTransport 在开发环境仅将邮件写入日志而非真正发送，MockTransport 用于自动化测试，均通过依赖注入替换，业务函数签名不变。尽管接口精简，Upyo 仍处理了 SMTPUTF8 国际化地址、DSN 投递通知、附件流式传输、日历邀请及邮件线程（messageId/inReplyTo/references）等复杂场景。

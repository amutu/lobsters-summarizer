## 1. IANA 解释 example.com 页面变更原因

- 原始链接: <https://www.oliverdunk.com/2026/09/30/iana-reply>
- 英文标题: IANA's email about why example.com changed

作者就 example.com 页面内容变更向 IANA（互联网号码分配机构）发邮件询问，意外收到其副总裁 Kim Davies 的回复。Davies 说明，IANA 对 example.com 的改动通常出于两个目的：降低站点带宽消耗或提升实用性。该域名本质上是一个占位符，供文档和示例中使用，不应被真实访问，但 IANA 历史上会在页面上显示说明信息，告知访客域名注册原因及合法用途。由于该域名流量极大，本周的改动是将页面拆分为一个精简的基础页面和一个独立的 JavaScript 文件（承载额外内容）。鉴于绝大多数访问来自自动化程序，它们通常不会加载 JS 文件，从而显著减少整体数据传输量。Davies 还强调，example.com 的根本用途是出现在技术文档、配置示例等场景中，人们复制粘贴示例时可能忘记替换其中的示例域名，因此会产生少量附带流量，但 IANA 不鼓励将其用作可用性测试等通用端点。此外，该域名并不要求主机上必须运行 HTTP 服务，IANA 提供 HTTP 响应纯属便利之举。Davies 表示欢迎进一步提问，并允许自由转发该信息。邮件日期为 2026 年 9 月 30 日。

## 2. 降低AI生成代码的认知负荷

- 原始链接: <https://amoffat.github.io/blog/cognitive-load.html>
- 英文标题: Reducing the cognitive load of AI changes

本文作者Andrew分享了一个在审查AI生成代码时降低认知负荷的实用技巧。核心问题是：大语言模型为抽象概念、过程和对象选择的命名（如「MutationIntent」）往往与开发者自己的命名习惯（如「EditRequest」）不一致，每次阅读都需在脑中做一次语义映射，这种摩擦虽小，但当数十个陌生术语在代码中交织时，认知负荷会迅速累积，最终导致对代码逻辑的误解。作者提出的解决方案是：在正式审查之前，先向AI发送一段预处理提示词，要求AI提取本次变更中所有非常规或自定义术语，生成一份临时Markdown文件，列明每个术语的含义、选择理由及若干替代建议。开发者逐一确认或替换为更贴合自身习惯的命名后，AI再执行全局查找替换，涵盖代码与文档。经过这一轮「语言对齐」，最终产出的代码读起来更像出自开发者本人之手，审查效率显著提升。文章亮点在于将「命名一致性」这一常被忽视的隐性成本显性化，并用一个轻量级的提示词流程加以解决，对日常使用AI辅助编程的团队具有直接参考价值。

## 3. Rust 1.99.0 发布

- 原始链接: <https://blog.rust-lang.org/2026/10/01/Rust-1.99.0/>
- 英文标题: Announcing Rust 1.99.0

2026年10月1日，Rust 发布团队宣布 Rust 1.99.0 稳定版发布，用户可通过 rustup update stable 升级。本版本核心亮点包括：一是稳定化 extern「C」可变参数函数（variadics），开发者现在可直接在 Rust 中定义使用「C」或「C-unwind」ABI 的可变参数函数，其参数列表类型为 VaList，与 C 语言 va_list 保持 ABI 兼容，读取类型受 VaArgSafe trait 约束；同时支持以内联汇编方式定义非「C」ABI 的裸可变参数函数。二是稳定化裸指针布局信息获取，新增 Layout::for_value_raw、mem::size_of_val_raw、mem::align_of_val_raw 三个函数，明确了 Sized 与非 Sized 类型的安全要求。三是文档层面，建议避免对 Box::leak 泄漏的内存进行后续释放（round-trip unleak），推荐改用 Box::into_non_null 或 Box::into_raw，以规避与编译器优化及未来自定义分配器稳定化的潜在冲突。此外，本版本还稳定化了 VecDeque::retain_back、Vec::into_parts、String::from_utf8_lossy_owned、std::fs::set_times 等一批 API，并包含 Cargo 与 Clippy 的多项改进。团队同时鼓励用户切换至 beta 或 nightly 频道参与测试并反馈问题。

## 5. Outis：通过伪造「用户不存在」退信对抗 AI 垃圾邮件

- 原始链接: <https://github.com/dtonon/outis>
- 英文标题: outis: Fight AI spam by generating and sending a fake "user unknown" bounce emails

Outis 是一款用 Go 语言编写的命令行工具，旨在对抗近期泛滥的 AI 自动化垃圾邮件。其核心思路是：当你收到一封可疑邮件后，Outis 会生成并发送一封伪造的 RFC 3464 投递状态通知（退信），状态码为 5.1.1（用户不存在），使发件方误以为该地址无效，从而将你从其邮件列表中移除。退信格式模仿 Postfix，包含可读部分、delivery-status 部分及原始消息附件，由 MAILER-DAEMON@你的域名 发出。工具名称源自希腊语「无人」，取自《奥德赛》中奥德修斯欺骗独眼巨人的典故。已知局限是：退信在邮件已被接收后才发出，发件方日志仍显示投递成功，且仅影响处理该通知的单一发件人。使用前提是你需控制一个域名并拥有可伪装 MAILER-DAEMON 的 SMTP 账户，Gmail、iCloud 等消费级服务会改写 From 头而暴露身份。工具支持单文件、目录批量、剪贴板输入、干运行预览及发送后自动删除等操作；多账户按域名匹配收件人；针对 Amazon SES 等共享抑制列表的提供商，退信改发至 From 头地址以避免误伤其他用户。配置以 TOML 格式存放于系统用户配置目录。

## 6. 类型类与模块系统：辨析与取舍

- 原始链接: <https://sm2n.ca/articles/typeclasses-vs-modules/>
- 英文标题: Typeclasses vs Modules

本文旨在澄清类型类（typeclass）与模块系统（module system）之间长期存在的混淆。作者指出，两者核心目标不同：类型类提供「即席多态」，即运算符重载与基于类型的分派，服务于小范围编程中的符号复用；模块系统提供「模块化抽象」，涵盖依赖注入、封装与信息隐藏，服务于大范围编程中的程序分解。两者共享「定义接口并验证符合性」的底层机制，可互相模拟但通常非最优。用类型类模拟模块化抽象会丧失组合式分解能力，导致函数签名冗长和编译期实例搜索开销；用模块模拟即席多态在 OCaml 中可通过 open 或命名空间实现，理论上也可构建全局签名、类型、模块数据库来精确复现。文章还梳理了各语言现状：Haskell 的 Backpack 模块系统鲜有人用，Rust 的模块系统缺乏抽象签名与参数化模块，Elixir 的参数化模块不做类型检查。作者最终建议，语言设计者往往优先实现即席多态而将模块化抽象视为附属，但作者认为这一优先级应当颠倒，良好的模块化抽象支持对编写高质量程序更为关键。

## 10. AI帕斯卡赌注：开源项目应拒绝LLM生成贡献

- 原始链接: <https://ploum.net/2026-10-01-pascal_wager.html>
- 英文标题: The AI Pascal’s Wager

作者Ploum从纯实用角度分析开源项目是否应接纳大语言模型生成的代码贡献。他将立场归纳为三种：完全接受、折中观望（即Debian式AI政策）、强烈拒绝。作者认为中间路线不可持续——只要不做出明确选择，AI生成代码终将「渗透」进来，拖延等于缓慢地默认接受，本质上是天真或虚伪的。他进一步权衡利弊：接受AI短期看似提升效率，实则让项目日益依赖昂贵且完全封闭的专有工具，并疏远部分社区；拒绝AI虽会赶走少数「离不开LLM」的贡献者，但这类人往往缺乏独立审查代码的能力，失去他们反而是好事，且拒绝AI不会让任何用户流失。长期来看，当每段代码都越来越不被人类理解、AI工具突然涨价或代码实为跨项目抄袭时，后果将极为严重。作者援引Cory Doctorow的「石棉」比喻：AI生成代码表面光鲜、易于铺满，但一旦需要清理或夺回控制权，代价将以年计。最终，他借用帕斯卡赌注的逻辑得出结论：在AI尚未被证明可靠、伦理、可持续之前，最理性的策略是明确拒绝一切AI生成贡献；未来若AI确实向善，随时可以改变政策，成本为零；但若现在放任「slop」涌入，可能永远无法挽回，甚至被迫放弃整个项目。

## 11. 第二根金钉：Valen与Rust边界上的内存安全

## 13. 在类型层面追踪列表反转状态

- 原始链接: <https://grim.cargocut.org/a/rev-list.html>
- 英文标题: Lists that keep track of their reversal

本文由Cargocut团队发布非空列表库nel后引发的讨论展开，核心问题是OCaml程序员在类型层面追踪列表「是否需要反转」的可行性。背景是OCaml中列表通常通过前置（prepend）构建、最后统一反转，由此产生了rev_append、rev_map等匈牙利命名函数，OCaml维护者Antonin Décimo提议将反转状态编码进类型。作者依次给出三种方案：第一种基于GADT，通过构造器强制约束列表为rev或ord标签，语义清晰但需遍历重建列表、重写整个API，性能代价大；第二种采用多态变体加constraint的幽灵见证（phantom witness）方式，olist类型底层仍是普通列表，实现极简且兼容现有List API，但rev与ord函数实现相同却需分开声明；第三种引入dir类型参数，将反转关系编码为(「o」,「r」)dir与(「r」,「o」)dir的对称映射，从而将rev和ord统一为单一函数，最为优雅。文章在第三种方案的完整演示处截断，但整体展示了从构造器约束到类型级开关的渐进思路，体现了OCaml类型系统在表达局部不变量方面的潜力与权衡。

## 16. Rust 转 WGSL 转译器 wgsl-rs 发布 0.1.0-beta

- 原始链接: <https://renderling.xyz/articles/wgsl-rs-beta-release.html>
- 英文标题: Rust to WGSL transpiler `wgsl-rs` released

wgsl-rs 是一个将 Rust 转译为 WGSL（WebGPU 着色器语言）的转译器，其 0.1.0-beta 版本正式发布。作者全职投入四个月，完成三方面工作：将 wgpu 代码生成从编译期 proc-macro 迁移至运行时 IR 遍历、系统性消除 Rust 与 WGSL 之间的静默语义差异、以及完成 beta 发布所需的词汇覆盖与文档。文章列举五个技术亮点：一是运算符优先级翻转，Rust 与 WGSL 对位运算和比较运算的绑定优先级相反，修复方案为对所有二元表达式完全加括号；二是向量等号在 WGSL 中产生分量掩码而非布尔值，需增加后单态化重写 pass；三是字面量类型推断差异（Rust 默认 0 为 u32，WGSL 为 i32），通过作用域追踪的锚定 pass 解决；四是运行时 IR 遍历替代约 650 行 proc-macro 代码，解锁泛型模板模块在运行时生成 wgpu 管线的能力；五是绑定阶段可见性从硬编码改为基于传递调用图可达性推导。项目已获实际采用，包括游戏开发者 Jak Kos 和 Zed 编辑器 gpui crate 的社区分支 gpui-ce。作者下一步计划移植 crabslab 与 craballoc，并构建 GPU 端 ECS。

## 17. 我们应当能够自定义自己的编程语言

- 原始链接: <https://jimmyhmiller.com/change-our-languages>
- 英文标题: We Should be Able to Change our Languages

文章指出，编程语言长期被视为不可更改的固定产物，人们因此用复杂的构建系统、外部工具和约定来弥补语言表达力的不足。作者回顾了反对宏与自定义语言构造的经典论据：Raymond Chen 认为控制流宏会隐藏代码真实语义、增加调试难度；Richard Gabriel 则警告宏让不擅长语言设计的人做出不可读的代码。作者认为这些顾虑在 AI 时代已不再成立：大语言模型让理解复杂代码变得前所未有地容易，逐行阅读代码的重要性下降，而宏反而能帮助 AI 编码时保持模式一致性，减少其因局部复制导致的风格漂移。为此，作者复活了已废弃的 SweetJs 项目，推出面向 TypeScript 的宏系统 Sweetener，演示了自定义管道操作符、带模式匹配与穷尽检查的代数数据类型、以及 TSX 中内嵌控制流等能力。文章最终呼吁：我们已不再需要依赖外部框架和委员会来间接实现语言功能，AI 降低了学习、迁移和定制的成本，编程语言应赋予开发者完整表达力，而非因「怕用户用错」而自我设限。

## 1. AI时代如何熬过代码审查

- 原始链接: <https://lobste.rs/s/7tpc5q/surviving_code_reviews_era_ai>
- 英文标题: Surviving Code Reviews in the era of AI

本文是一篇社区讨论帖，楼主抱怨同事全面拥抱AI后，每个PR平均达6000行diff，远超人类能有效审查的规模，而AI生成的解释又冗长难懂。多位参与者分享了应对策略与观点。技术层面，有人公司硬性规定PR不超过400行，无论代码由AI还是人类生成；有人用AI工具（如Greptile、Claude Code Review、cubic等）做第一轮筛选，再由人类终审；有人借助jj等工具将大改动拆成stacked commits，让AI辅助拆分但人类把控拆分逻辑。流程层面，多位评论者强调PR必须附带人类撰写的「为什么做」和「做了什么」说明，否则直接退回；建议团队在AGENTS.md中固化质量规范。组织层面，核心矛盾在于管理层只追求交付速度、不关心工程质量，导致工程师缺乏否决权。部分人选择降低审查参与度以保护心理健康，也有人直言若公司文化无法改变，只能考虑离开。共识是：AI审查工具可提效，但代码质量责任仍在人；没有团队共识，个人难以扭转局面。

## 3. Babashka 1.13.220 发布：新增 FFI 支持

- 原始链接: <https://blog.michielborkent.nl/babashka-ffi.html>
- 英文标题: Babashka 1.13.220 gets FFI

Babashka 1.13.220 版本发布，核心亮点是新增 babashka.ffi 命名空间，允许在 Babashka 脚本中直接调用 C 库（如 libz、libm），该库同时可作为独立库用于 JVM Clojure 项目。API 目前标记为实验性，但暂无变更计划。设计上受 coffi 启发但有所区别：defcfn 可显式绑定库，并引入受 Specter 启发的「place」概念以高效读写 struct 和 union；底层基于 java.lang.foreign，通过 arena 显式管理内存，出错时抛异常而非 segfault。Linux 默认二进制从全静态链接改为 mostly-static（仅 glibc 动态链接），仍可通过 --static 标志获取全静态版本。作者用 FFI 构建了 pacman、doom 射线投射、GTK4 窗口、PortAudio 音频、嵌入 CPython 等演示，并推出了 babashka.sqlite、babashka.duckdb、babashka.postgres、filewatcher 等 FFI 库，其中 SQLite 库支持在数据库内定义 Clojure 函数。此外，任务系统改进包括 :exec-fn 通过 :depends 组合、支持 :exec-args 直接传参、:cmd 树可通过 var 按需加载。开发过程中使用了 LLM 辅助。

## 4. NX 位不仅是安全机制：一次 ARM64 投机取指引发的调试之旅

- 原始链接: <https://purplesyringa.moe/blog/guest/the-nx-bit-is-not-just-about-security/>
- 英文标题: The NX bit is not just about security

本文记录了 Sonya 在 postmarketOS 的 ARM64 裸机 hypervisor 开发中排查一个诡异锁死 bug 的全过程。启用 CTR_EL0 拦截后，手机随机挂起并被看门狗复位。她先后排除了异常处理 trampoline 寄存器破坏、ARM 指令/数据缓存不一致（排序后未刷新 Icache）、内核 panic 等假设，最终通过 objdump 定位到少量「热点」指令，并将问题缩小到一个函数内。关键发现是：语义完全等价的 blr x0（动态调用）与 bl 静态调用表现截然不同。经分析，动态分支的预测器可能将目标误预测为地址 0x0，而该地址映射着已被锁定的 bootrom，导致投机性指令取指触发硬件异常。ARM 官方文档明确指出：将内存标记为 Device 仅阻止投机性数据访问，要阻止投机性指令取指必须同时标记为不可执行（NX）。最终她将相关页设为 NX，系统首次完整启动至 Android。文章的核心观点是：在 ARM 架构中，NX 位并非单纯的安全防御（DEP），而是防止投机性指令取指访问 Device 内存的必要属性位，对 hypervisor 等底层系统同样至关重要。

## 9. Collider：一个实验性 Minecraft 服务器

- 原始链接: <https://github.com/Nozistance/collider>
- 英文标题: Collider: An experimental Minecraft server

Collider 是一个用 Clojure 编写的概念验证型 Minecraft 服务器，约 5500 行代码，核心目标是实现并行 tick 且完全无锁、无区域划分、无线程所有权约束。作者选择 Clojure 是因为该语言天然提供不可变快照、纯读阶段和数据化变更等并行计算所需的全部原语，整个 tick 逻辑仅需六行代码即可完成。性能方面，单核下与原版 1.8.9 持平，六核下达到 4.5 倍加速。与 Folia 等基于空间区域划分的方案不同，Collider 不关心玩家位置，无需将世界切分为独立线程管理的区块，拥挤时也不会将相邻区域合并回单线程。项目功能刻意精简，仅实现羊的 AI、光照、水与岩浆、火、方块物理、掉落物、TNT、伤害、昼夜循环、世界保存、聊天命令及物品栏等，目的是验证数据模型能承载真实游戏机制并作为性能基准。运行需 Java 21+，通过 config.edn 配置文件启动。作者参考了 MCP-919 反编译的 1.8.9 源码以还原原版行为。这是一个纯个人实验，不面向任何现有 Minecraft 项目。

## 11. FORCE_COLOR：在管道与日志中保留命令行彩色输出的非正式标准

- 原始链接: <https://force-color.org/>
- 英文标题: FORCE_COLOR: Keep Your Command Line Colorful, Even when Piping - Retain Text Colors in Logs, Output Streams, and More

本文介绍了一项于2023年提出的非正式标准 FORCE_COLOR，旨在为命令行程序提供统一的强制开启彩色输出机制。背景是 NO_COLOR 环境变量已被广泛采用，但用户在管道（如 less、grep、tee）、CI 环境或非交互式终端中常遭遇颜色被自动关闭的问题，而各程序强制着色的方式不一，甚至许多程序根本不提供该选项。标准规定：命令行软件应检测 FORCE_COLOR 环境变量，只要该变量存在且非空（值不限），即强制添加 ANSI 颜色。用户只需在环境中设置 FORCE_COLOR=1，即可让所有支持该标准的软件输出彩色文本。文章给出了 C 语言示例实现，并解释了为何不能仅依赖 --color 或 -c 参数（内部管道无法从外部传参）。此外，文章列出了已支持 FORCE_COLOR 的多个语言库（如 JavaScript 的 chalk、colorette、supports-color，Python 的 rich、termcolor，Go 的 gookit/color，Rust 的 supports-color，Lua 的 Warna）以及已支持该标准的软件（如 Node.js、Deno、Python 3.13、Julia 1.12、pytest、uv、Sphinx、turbo、npm、jest、Symfony VarDumper 等），并鼓励开发者通过提交 Pull Request 将自身软件加入支持列表或参与标准完善。

## 12. Neovim vim.async 异步 API 参考

- 原始链接: <https://neovim.io/doc/user/lua-async/>
- 英文标题: Lua-async

vim.async 是 Neovim 为 Lua 提供的结构化异步 API，使代码能等待定时器、回调及其他任务而不阻塞事件循环。核心概念是「任务」（Task）：通过 vim.async.run() 创建，顶层任务立即启动；在另一任务内创建的任务成为子任务，在父任务到达检查点时开始执行，父任务须等所有子任务完成才结束。任务内用 vim.async.await() 挂起等待回调或子任务完成，vim.async.pawait() 作为 pcall 的异步对应，在操作失败时返回 ok 标志而非中断当前任务。调度为协作式：任务在检查点（await、pawait、checkpoint()、函数返回）挂起时保存 Lua 栈并将控制权交回事件循环，同步代码不会被中途打断。取消同样为协作式，Task:close() 在检查点生效。Task:detach() 可将子任务提升为顶层任务，脱离父任务生命周期。协调工具包括 iter()（按完成顺序遍历任务句柄）、timeout()（带超时的等待）和 semaphore()（以许可数限制并发）。此外，wrap() 可将回调风格函数包装为异步函数，同步代码可用 Task:wait() 或 Task:pwait() 阻塞等待结果。

## 13. 探索Mojo的原始指针类型

- 原始链接: <https://melodyogonna.substack.com/p/exploring-mojos-raw-pointer-type>
- 英文标题: Exploring Mojo’s raw pointer type

文章介绍了Mojo语言原始指针类型的独特设计。Mojo默认追求内存安全，依赖唯一所有权、ASAP（尽快）销毁和origin（起源）三大机制。其指针非空且携带origin信息，默认完全安全：编译器通过origin强制执行参数排他性与生命周期分析，防止别名冲突和悬空引用；空值用NoneType表示，可空指针用Optional包装，彻底消除空指针解引用风险。然而，指针的安全性由操作决定而非类型本身。所有不安全操作在API签名中标注「unsafe」，如越界解引用（unsafe_offset）或从分配句柄泄漏指针（unsafe_leak）。动态分配内存时使用MutUntrackedOrigin，编译器不做生命周期分析，程序员须自行完成初始化与销毁。Mojo通过线性类型的分配句柄防止内存泄漏——句柄必须被显式释放或消费，否则编译报错；结合origin信息还能防止双重释放和释放后使用。文章最后指出，Mojo曾尝试将安全与不安全指针分为两种类型，但安全变体使用极少且定位尴尬，最终统一为单一指针类型，以操作而非类型区分安全性，使语言更简洁。

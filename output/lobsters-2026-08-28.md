## 1. SourceHut 更新服务条款：限制 LLM 与生成式 AI 的使用

- 原始链接: <https://sourcehut.org/blog/2026-08-27-tos-changes-and-llms/>
- 英文标题: Changes to SourceHut's terms of service regarding LLMs

SourceHut 平台宣布修改服务条款，自9月10日起禁止使用大语言模型及其他生成式 AI 工具生成源代码、资源、工单和邮件等内容。此前 Codeberg 已做出类似限制，SourceHut 经社区讨论后决定跟进。平台给出多重理由：资源层面，AI 辅助项目常产生复杂 CI 配置和频繁提交，造成过度消耗；伦理层面，LLM 训练忽视开源许可证，产出专有模型却不回馈社区；气候层面，AI 基础设施能耗巨大，预计电力需求堪比印度全国；社会层面，AI 加剧贫富分化，被用于监控与操纵选举；个人层面，AI 导致技能退化与心理健康问题。条款留有解释空间：允许镜像宽松策略的代码库，AI 用于私人审查或安全分析但不产出代码则不违规，但包含生成式 AI 功能的软件不被欢迎。执行采用轻触式策略，不部署自动检测工具，依赖荣誉制度，发现欺骗则暂停账户，现有项目不追溯。受影响项目需自行迁移，平台推荐 Forgejo、自托管 SourceHut 或 GNU mailman 等替代方案。

## 2. 请停止用AI生成的垃圾贡献来装点你的简历

- 原始链接: <https://neilalexander.dev/2026/06/30/flooding-contributions.html>
- 英文标题: Please stop flooding our projects with AI slop to furnish your CV

开源维护者Neil在2026年6月的博客中批评了当前开源社区中泛滥的AI生成贡献。他指出，GitHub的贡献记录已成为求职「货币」，而过去一年外部贡献模式明显异化：PR数量激增，issue常附带AI分析，安全漏洞报告也大量涌入。Neil怀疑相当一部分贡献者并非真正关心项目，而是利用Claude等LLM批量生成PR或漏洞报告，以刷绿格、攒CVE、装点简历。他举了一个典型案例：一位几乎无贡献历史的用户突然提交三个仅修正注释中拼写和语法错误的PR，commit签名和co-author均由Claude代劳，他最终关闭了全部三个PR，不愿为「让机器人修错别字」树立先例。在安全漏洞方面，近期收到的CVE报告明显由AI生成，维护团队因此更严格地评估严重性，对低危项拒绝发布CVE公告。Neil的核心立场是：开源建立在信任之上，衡量贡献的标准不是能说服LLM产出多少PR或积累多少CVE，而是是否让项目真正变得更好。他呼吁贡献者出于对项目的关心而参与，若只为一个绿色方块或贡献者徽章，请另寻他处。

2026年8月，Rust 项目正式公布首届「驻场维护者」（Maintainers in Residence, MiR）及「维护者资助」（Maintainer Grant）名单，共六位贡献者获得至少12个月的资金支持。其中 Gen Li 全职负责 rustup，Chris Denton 半职覆盖标准库、编译器及 Windows 相关维护，Alejandra González 半职专注 Clippy 性能优化与代码审查，León Liehr 半职负责 rustdoc 与编译器；Jason Newcomb 和 Jonas Böttiger 则分别以维护者资助身份支持 Clippy 和标准库。该计划依据 RFC 3931 设立，设全职（5天/周）、半职（约2.5天/周）和资助（约1天/周）三档，资金来自 Rust 基金会维护者基金（RFMF），由 Google、AWS、OpenAI 及 Rust 领导委员会等共同赞助。遴选时，团队先评估各子项目（rustdoc、cargo、compiler、clippy 等）的维护基线缺口，再匹配有需求的维护者，最终优先选择能立即投入且影响面广的六人。文章强调，此举旨在为长期维护提供稳定经济保障，让贡献者专注核心工作而非担忧生计，并呼吁社区继续向 RFMF 捐款以扩大资助规模。

## 4. UNIX V4 工作坊：在低资源计算会议上重返 1974 年

- 原始链接: <https://github.com/thaliaarchi/unix-v4-demo/blob/main/README.md>
- 英文标题: UNIX V4 workshop at Low Resource Computing

2026 年达特茅斯低资源计算（LRC）工作坊上，作者主持了一场 UNIX V4 互动体验。V4 是近年从犹他大学一卷 1974 年磁带上恢复的，为已知最早的完整可运行 UNIX 快照。作者修改内核将终端连接上限从 20 提至 32，搭配两台物理终端（TI Silent 700 电传打字机与 Heathkit CRT）及 29 个 telnet 会话，让参与者同时登录同一台机器。教学沿用当年方式：分发纸质手册，重点教授 ed 编辑器。参与者需适应诸多「古早」习惯——退格键无效（改用 # 和 @ 擦除）、cd 命令名为 chdir、登录偶尔切换全大写模式。核心挑战是将 1984 年 IOCCC 获奖程序 mullender.c 从 V7 移植到 V4，最终三人完成。期间，首位 UNIX 用户 Doug McIlroy 到场，演示了仅含 define 操作即图灵完备的 bare m4 宏处理器。参与者还探索了 UID 权限漏洞（256 取模 256 为 0 即获 root）、玩 Hunt the Wumpus 等游戏、用 write 和 mail 互发消息。最终，众人用完整卷纸打印出一枚 Saturn V 火箭 ASCII art，为工作坊画上句号。

## 5. 一百万只鸮鹦鹉：代码不再稀缺后开源的黄昏

- 原始链接: <https://blog.mempko.com/a-million-kakapos/>
- 英文标题: A Million Kakapos

本文探讨AI代理式编程使代码不再稀缺后开源软件的命运。作者以进化论类比：大熊猫和鸮鹦鹉因高度适应单一环境而脆弱，蟑螂和鲨鱼则凭冗余与适应性存续数亿年——效率与鲁棒性不可兼得。生态学中的压力梯度假说和Ostrom研究也表明，资源稀缺时合作取代竞争才是生存之道。开源软件正是这一逻辑的产物：90年代末工程师极度稀缺，IBM投资Linux、Apache协作诞生、Chromium与LLVM行业共建，都是将维护成本分摊到公共领域的适应性策略。然而AI编程代理正让写代码变得「基本免费」，GitHub上PR与仓库指数增长并非繁荣信号，而是生态从合作转向竞争的征兆。Elastic、Hashicorp、Redis等公司先后放弃开源许可，印证了丰裕环境下合作动力消退。作者预言，未来将涌现大量「私有软件」——为个人或小团队定制、无审查、无fork、无冗余维护者，如鸮鹦鹉般高度适配却极度脆弱。开源因稀缺而生，当稀缺消失，我们正用一百万只脆弱的鸮鹦鹉取代一条冗余而坚韧的鲨鱼。

## 6. Asahi Linux 进度报告：Linux 7.2

- 原始链接: <https://asahilinux.org/2026/08/progress-report-7-2/>
- 英文标题: Asahi Linux Progress Report: Linux 7.2

本文为 Asahi Linux 项目针对 Linux 7.2 内核的进度报告，涵盖多项关键进展。在 CPU 电源管理方面，因 Apple 核心未实现 EL3，标准 PSCI 接口无法使用，开发者 Sven 正基于 UEFI Runtime Service 构建替代 PSCI 通道，让 m1n1 保留内存并暴露 PSCI 服务，相关补丁已提交邮件列表。M4 系列因 Apple 锁定 chicken bits 寄存器导致 WFI 引发核心崩溃，Yureka 新增内核参数使空闲循环行为可配置，补丁已进入 linux-next。安全层面，M4 强制启用的 SPTM 曾使 m1n1 虚拟机管理程序完全失效，Sven 通过逆向 SPRR 与 GXF 机制，使管理程序得以模拟 GL2 环境并加载 SPTM 与 XNU。M3 系列进展显著：摄像头、麦克风、ACE3 USB 控制器（SPMI 总线）均已支持，DCP 显示固件接近功能对等，项目接近正式发布。M4/M5 方面，NVMe 与 PCIe 已初步可用，但整体尚未就绪。视频解码方面，AVD 硬件解码器已支持 H.264、H.265、VP9 及 AV1，并通过 megi 维护的 VA-API 到 V4L2 Stateless 翻译层接入桌面软件，但尚未默认集成。最后，文章讨论了直接扫描输出路径中帧缓冲格式统一（半平面 Y'CbCr 与 tiling/压缩格式）的挑战，指出消除多次内存拷贝需各硬件块在像素格式、寻址模式和压缩方式上达成一致。

## 9. 自由软件易用性为何普遍糟糕（2002）

- 原始链接: <https://web.archive.org/web/20030201183139/http://mpt.phrasewise.com/discuss/msgReader$173>
- 英文标题: Why Free Software usability tends to suck (2002)

Matthew Thomas 于2002年撰文，与IBM人士讨论自由软件能否拥有良好人机界面。他认为理论上可行，但实践中志愿者驱动的开发模式几乎必然导致界面质量低下。文章列出多条原因：其一，专职志愿者界面设计师稀缺且经验不足，而每位贡献者都试图参与界面设计，设计师越多越不一致；即便有专职设计师，因缺乏补丁实现力，其建议也常被忽视。其二，许多黑客盲目模仿微软、苹果的设计，重复其错误，永远无法超越专有软件。其三，志愿者多为高级用户，界面设计对普通用户过于复杂；而聚焦控件、优化错误提示等细节工作枯燥，进展缓慢。其四，贡献者意见分歧时，维护者为留住贡献者不断添加用户偏好选项，导致界面臃肿、普通用户困惑。其五，贡献者追求「十五像素的 fame」，将本应隐藏的功能暴露为复选框或菜单项。其六，「尽早发布、频繁发布」使用户习惯缺陷，功能完善后反而引发抱怨，进一步增加偏好选项。其七，受商业公司（如Netscape、Eazel）影响的项目，因公司体量不足以雇用既聪明又固执的设计师，且商业模式追求收入而非用户满意度，界面反而可能恶化。

## 11. 发布即失去：源码即工具的使用哲学

- 原始链接: <https://notes.highlysuspect.agency/cant-release-that.html>
- 英文标题: If I release it, you won’t get the same experience I get

作者在重构Minecraft模组构建工具时，自写了一个名为jardiff的对比程序，用于验证新旧构建产物功能一致。jardiff能递归比较目录、.zip/.jar内部文件，对JSON做标准化格式化后再diff，对.class文件则通过Java反汇编器（objectweb asm textifier）输出文本再比较，避免「二进制文件不同」这种无意义提示。作者还手写了Meyers diff算法。实际使用中，jardiff发现新工具因移除Java 8兼容sourceset导致class文件版本号变化，作者判定该差异可接受，于是直接在jardiff源码中修改反汇编器，使其始终输出统一版本号，从而过滤掉无关差异、聚焦真正需要关注的变化。文章核心论点是：当工具源码就在编辑器中时，使用者可以即时改写逻辑、跳过或强化特定检查，无需预设配置项或学习DSL；一旦将工具编译为独立二进制发布，这种灵活性便消失，用户只能面对开发者预先决定的接口。作者将编译成二进制比作「封入琥珀」，指出开发者与用户之间存在权力不对等——谁的代码进入二进制、谁获得真正的编程语言、谁只能用DSL。结尾以幽默口吻「发布」：只给出两个类的源码，让读者自行复制粘贴、按需修改。

## 12. 安全问题的贩卖者：对 Omarchy 4.0 安全缺陷的严厉批评

## 14. 浮点膨胀：向量序列化中的精度浪费

- 原始链接: <https://bonsai.io/blog/float-bloat/>
- 英文标题: Float Bloat: vector serialization gone wrong

Bonsai 发现向量搜索生态中存在一个普遍问题，称之为「浮点膨胀」（Float Bloat）。大多数嵌入模型输出 float32 向量，但客户端在序列化时将其提升为 float64，使每个数值从 9 位有效数字膨胀至 17 位，磁盘与网络开销近乎翻倍，而额外精度毫无意义。Bonsai 估计该问题在全球造成超过 20PB 无效存储。根源在于 Python、JavaScript、Ruby 等语言缺乏 float32 标量，值离开类型化数组时自动提升为 double；Java、C# 中则因开发者主动转型为 double 数组而触发。Bonsai 抽样 18 个向量搜索集群，12 个存在此问题，且出现在主流 SDK、云厂商文档及大量教程中。修复方案按优先级为：一、按真实精度序列化（Python 用 %.9g、Rust 用 ryu、JS 用 toPrecision(9)）；二、直接传输二进制格式（base64、Arrow、protobuf）；三、透传已正确的文本而不重新编码。Bonsai 还发布了自动检测修复工具 bonsai-fix-float-bloat。文章强调问题几乎不在嵌入服务端，而在客户端序列化环节。

## 15. 深入理解 React 中的 useMemo 与 useCallback

- 原始链接: <https://www.joshwcomeau.com/react/usememo-and-usecallback/>
- 英文标题: Understanding useMemo and useCallback

本文面向对 React 中 useMemo 和 useCallback 感到困惑的开发者，系统讲解二者的原理与适用场景。文章首先建立心智模型：React 通过「重新渲染」将 UI 与状态同步，每次渲染生成一个虚拟 DOM 快照，再与上一帧对比差异。useMemo 的核心作用是跨渲染「记住」一个计算结果，其依赖数组充当缓存失效策略——仅当依赖变化时才重新执行计算函数，否则复用上次结果。文章以素数计算为例说明第一个使用场景：当组件因无关状态（如每秒更新的时钟）频繁重渲染时，useMemo 可避免重复执行昂贵计算。同时指出替代方案：将无关逻辑拆分为独立组件，或用 React.memo 将子组件包裹为纯组件，从父级层面阻止不必要的重渲染。第二个使用场景是保持引用稳定：即使每次渲染传入的数据值相同，若每次创建了新数组或新对象，=== 比较仍判定为不同引用，导致 React.memo 失效，useMemo 可确保引用不变。文章强调两种优化策略——减少单次渲染的工作量与减少组件重渲染次数——各有适用位置，并非互相替代。

## 17. 布尔扫描中的对称性

- 原始链接: <https://ap29600.github.io/boolean_scans.html>
- 英文标题: Symmetries in boolean scans

本文探讨APL等数组语言中布尔scan（扫描）操作的高效实现问题。APL内置8个非平凡二元布尔原语（and、or、xor、nand、nor、equal、less-than、greater-than等），为每个原语编写高性能的位级scan实现代价高昂。作者从scan的代数结构出发，推导出三条组合等式：对右操作数施加一元变换g、对输出施加g、以及同时对两者施加g时，scan可等价改写为另一个scan。取g为布尔取反，将8个真值表统一编码为10×2×2数组后，通过轴反转与逐元素取反操作，即可找出所有等价关系。关键结论是：只需为∧（and）、<（less-than）、≠（xor）三个函数提供快速实现，其余五个均可由对称性推导，从而大幅削减实现工作量与可执行体积，同时不牺牲性能。文章还指出该技巧在K语言及CBQN解释器中已有实践。附录A将真值表解释为有限状态机并讨论不变量；附录B给出xor、and、less-than三种scan的位级高效实现，包括前缀倍增法、无进位乘法指令、以及利用word+1与按位与的and-scan技巧，实测吞吐可达每周期62位。

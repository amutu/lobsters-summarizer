## 1. decomp.dev 正式关停：AI 时代下反编译社区的困境与抉择

- 原始链接: <https://decomp.dev/>
- 英文标题: Sunsetting decomp.dev

decomp.dev 于 2024 年创立，旨在集中追踪匹配反编译进度并凝聚社区力量。匹配反编译历来是耗时数年的艰巨工作，但随着工具与知识积累，进度逐步加快。2026 年初，Opus 4.6 与 GPT-5.4 已能借助训练数据中的反编译知识产出可用结果，但仍需大量人工修正；而 GPT-6-Astra 等新一代模型在长程任务连贯性、跨文件符号交叉引用及源码变体穷举方面表现突出，使 AI 辅助反编译在速度与成本上取得质变。然而，社区生态因此严重受损：恶意分叉者用 AI 快速「补完」他人项目而不投入实质贡献；投机者抢跑移植，将社区辛苦反编译的成果变为半成品 PC 移植；「反编译」一词被广泛等同于「移植」，偏离了研究初衷。decomp.dev 的排行榜机制也被扭曲为空洞的数字游戏。作者决定关闭主索引与新建项目入口，仅保留现有项目页面与历史数据；同时声明代码从未开源，禁止任何复刻。作者明确表示不禁止 AI 辅助项目，认为 AI 本身并非问题，但作为独立维护者无力对数百个项目进行质量审核。文章以感谢所有参与者与社区热情作结，标志着一个反编译时代的落幕。

## 2. JPEG XL 与 AVIF 在 Web 场景下的全面对比测试

- 原始链接: <https://jakearchibald.com/2026/jpeg-xl-vs-avif/>
- 英文标题: JPEG XL vs AVIF for web use-cases

文章在2024款MacBook Pro（M4 Pro）上，使用avifenc 1.4.2、libjxl 0.12.0、jixel 0.4.2等最新编码器，对JPEG XL与AVIF在Web场景下进行了全面基准测试，涵盖F1赛车、人物照片、截图、插画、透明图像及HDR等多种素材。核心结论：有损照片场景下，AVIF文件几乎总是更小，默认设置下JPEG XL大15%至25%，最大effort下差距缩至6%至20%；截图、插画和透明图像中AVIF优势更显著（大30%至90%）。编码与解码方面，AVIF综合表现更优，JPEG XL解码通常慢2至3倍。jixel编码器通常优于libjxl，但libjxl高effort设置性价比极低。AVIF的4:2:0色度子采样模式不推荐作为默认。渐进式JPEG XL在最高effort下开销极小，AVIF渐进式渲染目前仅Chrome支持。HDR方面，JPEG XL缺乏浏览器端gain maps支持，是明显短板。无损压缩中JPEG XL为明确赢家，可将现有JPEG缩小9%至20%。作者最终建议：Web场景默认选用AVIF 4:4:4最高effort，仅在AVIF产出异常大文件时再尝试jixel。

## 3. 我的C23编程约定

- 原始链接: <https://abner.page/post/c23-conventions-1/>
- 英文标题: My C23 Conventions

本文是作者Abner于2026年撰写的三部曲系列首篇，分享其在Zig构建中启用-std=c23后自然形成的三条现代C编程约定。第一，[[nodiscard]]与[[maybe_unused]]的配合：当函数标记了[[nodiscard]]但调用方确实无需使用返回值时，用「[[maybe_unused]] auto _ = foo()」替代传统的UNUSED()宏，既消除编译错误又保持代码整洁，作者还提到独立开发者Zardium提出的用宏拼接生成唯一变量名的改进方案。第二，联合体初始化的变化：C23中空花括号{ }会将整个结构体（含所有union成员）完全清零，而{0}仍沿用旧行为；GCC与Clang此前在union清零行为上曾互换，作者建议将最大成员置于union首位以确保安全。第三，枚举底层类型问题：C枚举默认以int为底层类型，若枚举值超出int范围编译器会自动调整类型，可能产生意外结果；C23支持显式指定底层整数类型（如enum options : int），避免此类隐患。文章结尾预告第二部分将讨论更安全的宏使用方式。

## 4. Haxy：一个将元数据存入仓库、通过 SSH 提供 TUI 的新型 Git 托管平台

- 原始链接: <https://try.haxy.net/haxy:haxy>
- 英文标题: Haxy on Haxy

Haxy 是一个处于预览阶段的新兴 Git 代码托管平台（git forge），作者以幽默风格介绍了其两大核心设计理念。第一，项目元数据（issues、pull requests、discussions）直接存储在仓库中，而非独立数据库。每次元数据变更生成一个 commit，以 JSON 形式写入 commit message，服务器通过事件溯源机制消费这些事件。好处是元数据可轻松在不同 Haxy 实例间复制，也可在本地离线浏览和编辑后推送。第二，Haxy 提供通过 SSH 连接的文本用户界面（TUI），用户凭 SSH 密钥即可自动认证，无需单独注册；同时提供 Web UI，但 Web 端实际上是在浏览器中渲染同一套 TUI，避免维护两套界面代码。与 Radicle 等 P2P 方案不同，Haxy 采用联邦架构：任何人都可部署实例，项目可在实例间迁移，作者认为这比 P2P 更实用且大幅降低复杂度。项目使用 Zig 0.17.0 编写，通过「zig build」编译，「zig build try」可启动带模拟数据的本地服务器体验，也可通过 SSH 将仓库推送到本地实例。预览版已上线于 try.haxy.net。

## 7. OCapN 端到端加密中继的实现

- 原始链接: <https://spritely.institute/news/end-to-end-encrypted-relays-for-ocapn.html>
- 英文标题: End-to-end encrypted relays for OCapN

本文介绍了 Goblins 项目为 OCapN 协议实现端到端加密（E2EE）联邦中继的工作，由 NLnet 资助完成。由于家庭网络普遍存在 NAT 限制，P2P 直连难以保证，中继服务器成为通用方案。Goblins 0.12 已引入名为「prelay」的联邦中继，但缺乏 E2EE，中继方可读取或篡改消息。新方案基于 Noise 协议的 XK 模式（发起方已知响应方静态公钥），选用 X25519 密钥、AES-GCM 加密和 SHA256 哈希，兼顾 Guile VM（GnuTLS）与浏览器端 Hoot（SubtleCrypto）的兼容性。团队为 Guile 从零编写了 Noise 库，实现全部 12 种基本交互模式并通过官方测试向量。设计上，Noise 作为 meta netlayer 可与任意底层 netlayer 组合，与 prelay 组合即得到 E2EE 中继，用户无需额外操作。中继本身保持无状态、联邦化：两个 actor（Controller 与 Endpoint）分别负责连接管理和跨中继寻址，两个对端可使用不同中继服务器通信。未来工作包括向 OCapN 标准化组提交中继规范、配合 Dart 实现方推进互操作、以及提供 Guix 服务以方便用户低成本部署中继节点。

## 8. sslx：一个快速、现代的 OpenSSL 命令行替代工具

- 原始链接: <https://github.com/glincker/sslx>
- 英文标题: sslx: A fast, modern alternative to OpenSSL's CLI

sslx 是一个用 Rust 和 rustls 构建的单二进制命令行工具，旨在替代 OpenSSL CLI，无需依赖系统 OpenSSL，将原本需要多次 openssl 调用的操作整合为一条命令。核心功能涵盖：TLS 评级（类似 SSL Labs 的终端版，从协议、密码套件、证书有效期、密钥类型、主机名匹配、证书链完整性和 ALPN 等维度给出 A+ 到 F 的评分）、批量证书过期检查（7 天内过期返回退出码 1，适合 cron 与 CI）、证书与密钥匹配验证、PEM/DER/PKCS12 格式互转、自签名证书与 CSR 生成（默认 EC P-256，亦支持 ec384 和 ed25519）、证书链验证，以及自动识别并解码 JWT、PEM、DER、私钥等文件。所有命令均支持 --json 输出便于脚本化，并定义了清晰的退出码（0 正常、1 证书过期、3 链不可信、4 连接失败、5 文件错误）。在 macOS M2 上，证书检查耗时约 2.1ms、生成证书约 1.7ms，显著快于 openssl 的 9.4ms 和 4.5ms。安装方式包括 cargo install、Homebrew 及预编译二进制，支持 bash/zsh/fish 补全，项目采用 MIT 许可证。

## 10. 远程证明技术不应被容忍

- 原始链接: <https://lumi.codeberg.page/blog/remote-attestation.html>
- 英文标题: Remote Attestation Should Not Be Tolerated

本文从自由软件与用户自主权视角，全面批判远程证明（Remote Attestation）技术。作者指出，远程证明是一种通常嵌入硬件的验证机制，允许第三方远程判定某设备运行的软件是否「合法」，本质上是限制性DRM的构建块。以Google Play Integrity为例，银行和政务应用借此强制用户运行官方Android系统，一旦用户改用修改版系统、替代操作系统或模拟器，应用即拒绝运行；Apple App Attest和Volla统一证明等方案只是更换了裁决权威，并未解决问题。作者反驳了「安全」这一常见辩护：远程证明所保护的是裁决方而非用户，用户反而被锁死在他人设定的规则中，自主权与安全性均遭损害。文章进一步将个人设备类比为身体的延伸，主张用户应对设备拥有完全控制权——包括获取全部代码、自行修改与分发、自由运行任何应用，开发者或公司无权限制。作者还补充指出，桌面端反作弊系统同样依赖远程证明，因此该技术的危害已不限于移动端。结论是：远程证明虽有少数合理用途，但绝大多数场景对用户极具敌意，应被整体反对，个人设备不应受任何外部权威管辖。

## 11. 维护的几何模型

- 原始链接: <https://entropicthoughts.com/geometric-model-of-maintenance>
- 英文标题: The geometric model of maintenance

本文以James Shore的「阈值模型」为起点，利用git提交记录对tmux、nginx、Rust等八个开源项目进行实证检验，发现该模型预测维护量指数增长，与实际曲线严重偏离。作者据此提出「几何衰减模型」：新开发引发的维护需求按固定月比率递减。对八个项目分别拟合后，初始维护占比（3%至48%）与月衰减率（0.7%至19%）差异悬殊，不存在统一常数。核心发现：项目全生命周期总维护量约为新开发量的1.5倍（nginx）到5.3倍（Neovim），中位数约3倍；维护降至可忽略水平的「消除时间」平均约6年。作者给出实用规划建议：每1小时新开发应预留约3小时维护、分摊至6年，且首年维护即超过开发本身。文章同时指出该模型未考虑代码库规模等变量，参数需逐项目拟合，未来仍需寻找跨项目稳定的参数以揭示更深层的软件维护规律。

## 12. Gleam 模式匹配穷尽性检查：一位爱好者的深度解读

- 原始链接: <https://oyster.pckt.blog/gleam-case-exhaustiveness-as-a-fan-fd4whyp>
- 英文标题: Gleam case exhaustiveness, as a fan

本文是 Gleam 语言爱好者 Lewis 对编译器中 exhaustiveness.rs 模块的一次「漫步式」解读，梳理了 case 表达式穷尽性检查的实现思路与理论渊源。文章从 Augustsson 1984 年「Compiling Pattern Matching」论文讲起，经 Maranget 2007 年关于「见证」（witness，即反例）的论文，再到 2008 年关于决策树编译优化的工作，勾勒出该领域的演进脉络。Gleam 并未采用 Maranget 的矩阵方法，而是将子句表示为分支列表并构建决策树，通过 Decision::Switch 与 Decision::Fail 节点在编译期判定穷尽性，再回溯树路径定位缺失模式。文章重点介绍了几项论文中未见、颇具新意的实现：字符串前缀匹配配合内联守卫时，编译器会记住同级已见前缀并将较短前缀插入较长前缀的「守卫失败」分支以继续匹配；位数组匹配中检测不可能模式与跨后端（JS/BEAM）行为统一；类型窄化——编译器记住变量的具体构造器实例，避免对已确定类型的 case 报冗余警告；以及错误信息中复用类型打印器，按用户实际 import 别名显示缺失构造器名。作者以热情而细致的笔触，展现了 Gleam 编译器在诊断友好性上对经典文献的超越，并鼓励读者研读源码。

## 13. Git on S3 的常见误区与 Enroute 的新解法

- 原始链接: <https://enroute.sh/blog/everyone-is-doing-git-on-s3-wrong>
- 英文标题: Everyone is doing Git on S3 wrong

文章指出，当前Git托管仍重度依赖SSD，而对象存储在持久性与扩展性上优势明显，但将Git迁移到S3并非易事。Git不仅是内容寻址存储，更是图数据库，对象间存在指针与delta编码，逐对象访问在对象存储上每次需30-40ms往返。以Cursor/SpaceX的Continuity为代表的WAL方案虽解决了读扩展与持久性，但写路径仍是单点瓶颈（约120-300 push/s），且每个副本仍需将完整仓库加载到磁盘。Enroute提出全新架构：分离计算与存储，Ledger层用MultiRaft共识维护每仓库的复制日志，Compute层完全无状态。关键创新有三：一是乐观锁与多版本并发控制，使push的索引与校验可并行，仅ref更新需串行提交；二是新存储格式将对象按commit边界切分为「segment」，delta限制在祖先范围内，避免读时遍历对象图；三是小push先内联写入日志，约每秒批量合并后刷入对象存储，类似LSM的memtable flush。实测在EC2与S3上，单仓库达7600+并发push/s，冷缓存克隆linux.git仅需128.6秒，与热缓存126.0秒几乎持平。

## 15. 宗教学视角下的软件工程

- 原始链接: <https://tombh.co.uk/religious-studies-in-software-engineering>
- 英文标题: Religious Studies In Software Engineering

作者拥有威尔士兰彼得大学宗教学学位，后从事软件工程，认为宗教学训练对理解技术实践至关重要。他提出，编程不仅是面向计算机的行为，更深刻影响人类与社会；意识形态、政治与宗教本质上都是「遵循特定步骤以达成理想结果」的体系。文章围绕「内部人/外部人」问题展开：实践者最了解宗教却最难客观，外部人虽能保持距离却缺乏切身体验，二者需互补。作者梳理了口语、文字、印刷、数字化四次媒介范式转换对宗教与文化的影响——口语催生编码与社会等级，文字固化信仰，印刷术削弱教会垄断并推动世俗化，而数字化时代的技术奇点叙事带有明显宗教修辞色彩（一神论、预言、全知），作者对此保持怀疑。他引入「教派-教会-教派」循环理论，说明宗教组织在垄断与分裂间不断摆动。文章穿插个人经历：父亲因酗酒离世，作者在佛教考试中落泪，空段落呼应佛教「空性」概念。核心亮点是：宗教学教会我们真诚而严肃地对待「终极关怀」问题，即使无法精确定义研究对象；这种视角帮助软件工程师审视技术背后的意识形态力量，避免将技术变革视为纯粹中性事件。

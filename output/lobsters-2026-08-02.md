## 1. Atom为何在关键方面优于RSS

- 原始链接: <https://chrismorgan.info/atom%3Erss>
- 英文标题: Atom is better than RSS, in ways that matter

文章主张Atom在技术上优于RSS，并列举了几个真正影响内容表达的关键差异。作者首先指出，虽然多数人认为两者差异无关紧要，但RSS在标题编码上存在严重问题：RSS没有为标题定义明确的编码语义，导致字符如<、&或HTML标签无法可靠地表达，而Atom通过text construct机制提供了text、html、xhtml三种清晰的选择，使内容表达无歧义。其次，RSS在摘要与全文的区分上依赖启发式规则，互操作性差，Atom则更规范。作者还提到RSS名称混乱，指代九种互不兼容的格式，但实践中可忽略命名空间。文章最后讨论了播客领域的例外：由于苹果早期在iTunes音乐商店仅支持RSS，导致大量播客阅读器和聚合器至今只支持RSS，尽管Atom本可解决许多问题。作者批评苹果在关键时期的选择使RSS延续至今，并指出播客RSS因时间冻结而堆满hack。作者写本文的目的是希望用实际理由说服人们采用Atom，而非仅基于意识形态，并明确表达希望RSS消亡的立场。文章尚处于草稿阶段，作者计划对RSS阅读器进行实测调查以验证相关案例。

## 2. 我现在（大部分）按速度而非智能选模型

- 原始链接: <https://martinalderson.com/posts/speed-vs-intelligence/>
- 英文标题: I'm (mostly) picking models on speed now, not intelligence

作者观察到，随着模型智能水平普遍达到日常任务所需的“足够好”门槛，他选模型的首要标准已从原始智能转向速度。像Opus 4.6级别的模型已能胜任编码、研究、幻灯片设计和数据库分析等工作，而更强的新模型（如Fable）虽然令人兴奋，但因推理速度太慢，作者很快切回Opus。文中提出人类感知“即时”的阈值是100毫秒，对应模型约100-200 tok/s的输出速度已接近阅读极限，低于50 tok/s则明显拖沓，超过200 tok/s反而令人不安。开源生态带来速度和价格的良性竞争，例如GLM5.2在OpenRouter上的服务速度从不足30到129 tok/s不等，价格已降至Opus的5%。但作者也指出，单纯提升模型速度会遭遇瓶颈：整体任务时间受限于工具调用、本地硬件和人类决策，5倍模型提速可能只换来2倍端到端提升。硬件成本因AI需求而飙升，进一步限制本地加速。同时，DeepSeek V4 Flash GA发布前OpenAI对Luna降价80%，预示价格战已开启。未来新一代GPU（如NVIDIA Vera Rubin、AMD MI400）将带来2倍以上内存带宽提升，2027年可能出现500 tok/s以上且价格合理的高质量模型。至于超大参数模型是否能在日常任务中带来显著优势，作者仍持观望态度。

## 3. C语言中sizeof的解析出人意料地困难

- 原始链接: <https://sebsite.pw/w/20260802-sizeof.html>
- 英文标题: sizeof is surprisingly difficult to parse in c

文章讨论了C语言中sizeof运算符的解析难点。sizeof的操作数既可以是单目表达式，也可以是带括号的类型名，例如`sizeof 67`、`sizeof(int)`和`sizeof (x).y`都合法。朴素的解析方法是先检查左括号，尝试解析类型名，失败则回退并解析表达式，但复合字面量的存在使情况复杂化：`sizeof(int){0}`是合法代码，其中的`(int){0}`是表达式。仅添加对`{`的检查还不够，因为表达式后可能跟随任意后缀运算符，如`sizeof(T){}.x[0]()`。一种方案是扩展特例，解析复合字面量后的所有后缀运算符；另一种方案是编写一个能同时尝试单目表达式和括号类型名的函数，避免回溯。但需注意不要将单目表达式与强制类型转换表达式合并解析，否则`sizeof(int)+1`会被误判为强制转换的大小，而它实际是加法表达式。此外，C2y新增的`_Countof`也面临类似问题。

## 4. 手动重打LLM生成的代码，防止认知债务

- 原始链接: <https://ankursethi.com/blog/prevent-cognitive-debt-by-manually-retyping-llm-generated-code/>
- 英文标题: Prevent cognitive debt by manually retyping LLM-generated code

作者尽管此前表示不再使用编码助手，但个人项目中仍在用LLM加速无聊部分，却发现放任AI生成代码会积累大量认知债务。虽然审查每一行AI代码是常见的做法，但作者认为阅读大量防御过度、注释糟糕且隐含错误的代码毫无乐趣，个人项目应以过程愉悦为先。因此，他采用了一种低效甚至略显滑稽的方案：让编码助手在聊天中生成代码，但不允许直接修改文件，而是由他手动将每一行代码输入编辑器。他在项目代理文件中设置了明确指令：不创建、编辑或删除文件，不运行修改项目状态的命令，只展示建议的编辑和命令，由他亲手执行。这种方式让他比完全不用LLM快约两倍，但远慢于愿意让机器代劳的人。然而，手动输入迫使他放慢节奏，更容易察觉幻觉和糟糕设计，同时顺手清理、重构、加注释，并逐渐建立对代码库的空间认知——清楚每个功能所在位置，未来也能更精准地提示LLM。作者将这一过程类比于早年学编程时被建议手动敲入示例代码，强调理解胜过效率。他认为软件行业正背负巨大认知债务，未来可能无法理解自身基础设施的构建方式；虽然无法改变整个行业，但他至少确保自己完全理解发布的软件，否则便是职业失职。

## 7. OCaml中的受保护方法

- 原始链接: <https://xvw.lol/en/articles/oop-refl.html>
- 英文标题: Guarded methods in OCaml

本文介绍OCaml中的“受保护方法”（guarded methods）这一概念及其编码方式。受保护方法允许仅对特定方法附加约束到接收者（self），使得这些方法只有在接收者满足相应约束（即guard）时才能被调用。然而，OCaml在语法层面并不直接支持定义这类方法。为此，文章展示如何利用类型相等见证（type equality witness）来间接实现这种受保护方法的编码，从而在OCaml中模拟出对方法调用条件的静态约束。由于正文内容简洁，主要聚焦于问题背景和解决思路，未深入展开具体实现代码，但指出了核心手段是类型相等见证。

## 8. Rust 新 API 实现更快的浮点运算

- 原始链接: <https://pythonspeed.com/articles/faster-float-math-rust/>
- 英文标题: Faster floating point math with Rust’s new API

文章介绍了 Rust 1.98 新增的“代数运算”浮点 API，用于解决编译器默认无法像优化整数运算那样优化浮点运算的问题。原因在于浮点运算不满足结合律，改变运算顺序会改变结果，因此编译器出于保守会避免重排操作。Rust 1.98 提供了 algebraic_add、algebraic_sub、algebraic_mul 等代数运算符，允许编译器在特定代码区域利用实数代数性质进行激进优化，而其他区域仍可保持严格顺序以保证精度。文章以两个例子验证效果：一是用代数加法实现成对求和（pairwise summation），速度超过 NumPy 的 np.sum，且误差量级相近，同时生成 SIMD 指令；二是计算两数组的平方差之和，使用代数运算后运行时间从约 628.7 微秒降至 371.1 微秒，CPU 指令数从每值 4.5 条降至 1.0 条。作者建议在算法中对精度关键部分使用严格运算、对顺序无关部分使用代数运算，两者结合可在保证精度的同时大幅提升性能，并鼓励数值计算开发者尝试 Rust 1.98 的这一新特性。

## 10. Rust 参数解析的老派新解

- 原始链接: <https://jmmv.dev/2026/07/hello-getoptsargs.html>
- 英文标题: An old-new take on argument parsing in Rust

本文作者 Julio Merino 分享了他在 Rust 生态中对命令行参数解析的独特看法。他认为，命令行工具应融入目标工具生态，而非仅迎合所用语言的主流习惯。以 Go 的 flag 库为例，其设计虽然方便开发者，但让终端用户感到陌生。在 Rust 中，clap 虽已成为事实标准，但作者指出其风格过于华丽，且依赖宏和派生（derive）机制，缺乏对启动流程的端到端控制。为此，他基于经典的 getopts 库开发并发布了新库 getoptsargs。该库作为 getopts 的扩展，允许声明带基数约束的位置参数，自动校验，并在帮助中单独分节显示；同时提供应用元数据（版本、bug 报告、主页、手册页）的辅助功能。更重要的是，getoptsargs 提供了一套端到端的应用框架，通过 Builder、Matches 和 app 宏三部分组织 main 函数，统一处理选项、参数、帮助和退出码，风格力求贴近传统 Unix 工具。作者也承认该库名称不优雅，API 较原始，但它是为自身项目需求而诞生的独立实现。文章包含示例代码和运行效果，并强调并非意在取代 clap 等库，只是提供一种符合 Unix 传统的替代选择。

## 12. Lean内核健全性漏洞#14576事后分析

- 原始链接: <https://leodemoura.github.io/blog/2026-8-1-postmortem-for-kernel-soundness-bug-14576/>
- 英文标题: Postmortem for Lean Kernel Soundness Bug #14576

2026年7月，Lean内核被发现一个健全性漏洞（#14576）。起因是Ramana Kumar借助AI发布了一份看似无需公理的Collatz猜想“反证”，但该证明利用了内核在处理嵌套归纳类型时的缺陷。Kiran Gopinathan将其化简为证明False，并提交了issue。修复在报告后一小时内完成。该漏洞的根源在于：当消除嵌套归纳类型时，若其参数是幻影参数（未出现在构造子字段中），这些参数会从生成的辅助类型中消失，从而绕过类型检查；攻击者可在该位置放入类型错误的项，使内核接受False的证明。该问题仅能通过元编程直接向内核发送归纳声明来触发，前端会拦截此类非法项。官方内核和独立检查器nanoda涉及两个互不相关的bug：nanoda虽检查了官方遗漏的位置，但未验证投影节点中的类型名，该问题在Lean漏洞报告前一周已被修复；因此用独立内核检查仍有效，但需要两个实现都保持最新。lean4lean因移植了参考实现也受影响。讨论中提出的移除元编程的建议被否决，因为攻击者也可直接编写olean文件或修改内存绕过前端，内核必须在自身进程中独立拒绝非法声明。Lean FRO随后增加了回归测试、修复了多个相关漏洞、强化了内核不变量，并借助AI安全专家发现了其他编程错误（均已被nanoda捕获）。comparator.live现已默认运行nanoda并每日跟踪更新，以保持一致性。

## 13. RISC OS Open 二十年回顾

- 原始链接: <https://www.riscosopen.org/news/articles/2026/06/20/twenty-years-of-risc-os-open>
- 英文标题: Twenty years of RISC OS Open

本文是 RISC OS Open（ROOL）成立二十周年的纪念文章，由 Steve Revill 撰写，回顾了从 2006 年到 2026 年每年最具代表性的里程碑。2006 年，ROOL 以将专有操作系统开源的“疯狂”目标成立，次年首批源码公开。此后，项目逐步开放更多组件，移植到 BeagleBoard、Raspberry Pi 等平台，推出夜间自动构建和 Bounty 悬赏计划。2012 年 RISC OS Pi 发布，将系统带给新一代用户。2013 年 RISC OS 5.20 成为多年来的首个稳定 ROM 版本，并支持经典 Risc PC 和 A7000。2018 年，RISC OS 在 Apache 2.0 下重新授权，真正实现自由使用与修改。2019 年，整个代码库迁至公共 GitLab。随后陆续支持 Raspberry Pi 4、NVMe 存储、原生 Git 客户端，并发布 RISC OS 5.30 等稳定版。2024 年，ROOL 启动“Moonshots”计划，致力于将 RISC OS 移植到 64 位 Arm 架构。文章强调，如今 RISC OS 的健康状况远超 2006 年，这归功于所有贡献代码、提交 bug、资助悬赏、参与社区的用户，并期待下一个二十年。

## 20. Fixi 项目

- 原始链接: <https://fixiproject.org/docs.html>
- 英文标题: The Fixi Project

Fixi 项目是一个相互配合的 Web 库家族，旨在让 Web 开发更愉快。每个库的源代码（未压缩、未精简）大小都被限制在 Preact 库 .min.gz 体积（约 4.7kb）之下；整个项目压缩并经过 brotli 编码后约 4.5kb。项目包含五个库：fixi.js 是旗舰库，允许元素基于任意事件发起 HTTP 请求，并将响应 HTML 放置到 DOM 任意位置；moxi.js 用于在元素上为任意事件绑定脚本，并提供简化常见脚本需求的辅助函数，同时支持简单的基于 DOM 的响应式；paxi.js 提供 DOM 变形（morphing）功能，可将新内容合并进 DOM 而无需整体替换，从而保留焦点、输入值等状态；ssexi.js 扩展 fixi.js，用于处理流式 Server Sent Events；rexi 提供更符合人体工学的 fetch() 封装，让从脚本中发起 HTTP 请求更省力。一个典型的 fixi 应用会这样使用：用普通链接进行页面间导航；用 fixi 处理需要服务器通信的页内交互；用 moxi 处理小型客户端行为，如开关、切换标签、防抖事件、启用元素；用 ssexi 接收实时通知或服务器推送内容；在需要保持焦点和输入状态时用 paxi 进行 morph 替换；在需要基于脚本发起 HTTP 请求时使用 rexi。Fixi 的理念是“少即是多”。

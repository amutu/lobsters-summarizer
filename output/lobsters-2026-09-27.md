## 1. 在 Steam Link 上运行 NixOS 的完整实践

- 原始链接: <https://feyor.sh/blog/infecting-the-steam-link-with-nixos/>
- 英文标题: Infecting the Steam Link with NixOS

作者将2018年购入的 Valve Steam Link 改造为常驻低功耗 ARM 设备，目标是安装 NixOS。核心难点在于 Steam Link 引导加载程序仅接受 Valve 签名的内核，且自带内核未启用 CONFIG_KEXEC。作者自行编译了一个 kexec 内核模块（基于13年前的 3.8.13-mrvl 内核），通过 kexec 将新内核注入运行中的系统。构建过程使用 Nix 交叉编译 armv7l-linux 目标，需处理旧内核与现代 GCC 的兼容问题，并借助 sd-image 模块生成 USB 启动镜像。调试阶段因 HDMI 无输出且未拆机接 UART，作者用 Busybox initramfs 配合 Netcat 反向 shell 逐步排查，最终成功通过 SSH 登录。镜像优化方面，作者通过仅保留单个 Marvell 固件 blob、禁用 base 模块、移除 Nix 自身及文档等组件，将镜像从 2.3GB 压缩至 1.2GB。文章附有完整 Nix flake 和 kexec_mod 源码，展示了在嵌入式 ARM 设备上部署 NixOS 的可行路径。

## 2. 如果我们不再停下脚步互相帮助，我们会变成什么？

- 原始链接: <https://blog.codinghorror.com/if-we-do-not-stop-to-help-each-other-what-do-we-become/>
- 英文标题: If we do not stop to help each other, what do we become?

本文是Jeff Atwood分享的一封读者来信。读者D回忆了2013年在菲律宾苏禄群岛执行军事任务期间，恰逢当地爆发围城事件，逾百人丧生、十二万平民流离失所。在战火中他仍坚持远程完成大学学业，将微软Surface平板塞进防弹背心以随时学习。遇到编程难题时，家人和朋友要么忽视要么让他「自己解决」，而Stack Overflow上的陌生网友却主动伸出援手。D表示，LLM或许能给出同样的答案，但无法给予他当时真正需要的东西——「有人在乎你」的情感连接。社区的价值不仅在于解答问题，更在于他人付出时间、让人感到自己重要、成为某个集体的一部分。作者借此反思：当社区被LLM取代、人与人之间的互助逐渐消失，我们失去的是一种像引力一样无形却不可或缺的东西。LLM或许提醒我们，应更用心经营属于自己而非某个亿万富翁的线上社区，因为停下脚步帮助他人，也是我们自身成长的方式。

## 3. Go 并发编程精要速查

- 原始链接: <https://antonz.org/go-concurrency-distilled/>
- 英文标题: Go concurrency distilled

本文是一本 Go 并发编程的精简速查手册，定位为快速复习而非入门教程，涵盖 goroutine、channel、select、pipeline、time、context、wait group、数据竞争、互斥锁、信号量、原子操作、对象池、调度与诊断等主题，每个主题配有可交互代码示例，另提供 PDF 版本，作者声明全书未使用 AI 生成。正文依次展开：goroutine 由 go 关键字启动，由运行时调度至 OS 线程，远比 OS 线程轻量，可用 WaitGroup 或 Go 方法等待完成；channel 是 goroutine 间同步通信机制，介绍了输出 channel 模式、关闭与「comma OK」读取、range 遍历、方向 channel、缓冲 channel 及 nil channel 的阻塞行为；select 语句实现多 channel 多路复用，用于数据合并、协程取消和非阻塞操作；pipeline 将数据流拆为 reader-processor-writer 阶段，并给出首错返回、结果结构体、独立错误通道三种错误处理策略；time 包提供 After、Timer、AfterFunc、Ticker 管理超时与周期任务；context 用于跨调用链传递取消信号，支持手动取消、超时与 deadline 三种方式，且 context 不可变、以分层派生方式扩展属性。

## 4. JavaScript 双关：标签模板字面量

- 原始链接: <https://shukla.io/blog/2026-09/pun.html>
- 英文标题: The JavaScript Pun: tagged template literal

文章从莎士比亚的双关语切入，引出 JavaScript 中标签模板字面量（tagged template literal）的一个巧妙双关。标签模板字面量允许通过标签函数（如 dedent）对模板字符串进行后处理，标签函数可接收文本片段与 `${...}` 求值结果作为独立参数。作者注意到，JavaScript 的 `${...}` 插值与 Mustache、Handlebars、Jinja2 等模板语言常用的 `{{ }}` 占位符存在视觉巧合：写出 `${{ url }}` 时，JavaScript 将其解析为 `${{ url: url }}`（利用对象属性简写），而人类读者看到的却是熟悉的 `{{ url }}` 模板语法。基于这一巧合，作者与 Helicone 的 Justin 合作，定义了一个名为 prompt 的标签函数，使开发者在 JavaScript 中书写 prompt 时能使用类模板语言的 `{{ }}` 写法，底层则生成带标注的字符串供可观测性工具分析。该功能已于 2024 年正式纳入 Helicone SDK。文章最后将双关定义为「一个字符串，两种解析」，并提及自己在其他文章中进一步探索了语法模型的多维解析，将这一语言游戏推向更深的层次。

## 5. 2026年Rust SIMD生态现状

- 原始链接: <https://shnatsel.github.io/state-of-simd-rust-2026/>
- 英文标题: The state of SIMD in Rust in 2026

本文是Fearless SIMD维护者对2026年Rust SIMD生态的深度调查。文章先回顾SIMD原理及x86（SSE2至AVX-512）、ARM NEON、WebAssembly等指令集差异，指出x86需通过函数多版本化（multiversioning）适配不同CPU。随后对比三种编程路径：自动向量化（最易用但不可靠，浮点类型需Rust 1.98的代数运算支持）、可移植SIMD抽象、平台特定intrinsics。重点评测五个主流库：std::simd（nightly-only，API不稳定，浮点函数性能与精度堪忧）；fearless_simd（功能最全，刚发布v1.0，但三角函数支持缺失）；wide（已v1.0但不支持multiversioning，x86性能受限）；pulp（为faer线性代数库设计，偏原生宽度向量）；macerator（为burn设计，支持f16但文档匮乏）。此外还讨论了multiversion crate的隐藏开销陷阱、archmage等安全intrinsics方案，以及Rust 1.87+对安全调用平台intrinsics的改进。整体结论：fearless_simd是当前最推荐的综合方案，但三角函数移植仍是全生态最大短板。

## 6. 错，而非坏：AI代理时代可观测性的新命题

- 原始链接: <https://aws.amazon.com/blogs/aws-insights/wrong-not-broken/>
- 英文标题: Wrong, not broken

传统软件运维围绕「是否坏了」构建，指标、日志、追踪已非常成熟。但AI代理带来新挑战：系统可能指标全绿，输出却是错的——例如退款代理在600毫秒内零错误率回答，却因检索到过期文档而给出错误金额。文章指出，代理的正确性必须在每次运行中持续衡量，因为同一代码可能因提问方式、检索上下文、工具路径不同而产生不同结果，质量需从隐性经验变为可操作的显性定义。同时需沿因果链追踪从用户请求到代理决策再到底层服务的完整路径，并支持事后发现异常模式。代理自主权应随质量证据动态调整：表现好则扩权，质量下滑则收缩。本周AWS发布Amazon CloudWatch Omni，将代理追踪、应用服务与基础设施统一呈现，内置17个评估器，支持生产流量转数据集与实验，基于OpenTelemetry生态，兼容LangGraph、CrewAI等框架。核心观点：传统可观测性仍不可或缺，但需新增「工作是否做得好」这一维度，能同时回答两组问题的团队才能更放心地赋予代理更多责任。

## 7. 逆向解析经典Intel 8087正切算法：不止CORDIC

- 原始链接: <http://www.righto.com/2026/09/8087-tangent-cordic.html>
- 英文标题: Reverse-engineering the vintage Intel 8087's tangent algorithm: more than CORDIC

本文通过开盖芯片、显微镜成像及微代码分析，逆向还原了1980年Intel 8087浮点协处理器FPTAN指令的正切算法。作者发现8087并非单纯采用CORDIC，而是将16位CORDIC与Padé有理近似（3x/(3-x²)）相结合，在仅用移位、加减等简单操作的前提下达到64位精度。算法分三阶段：伪除法阶段将输入角度逐次减去预存特殊角度并记录16位决策序列；有理近似阶段对残余小角计算Padé近似，以分子、分母分别作为初始向量的Y和X，从而避免显式除法；伪乘法阶段按逆序应用旋转，每步仅含移位与加减。文章还介绍了8087的80位临时实数格式、八级寄存器堆栈及1648条微指令结构。性能方面，8087将正切计算从8086的约13000微秒降至90微秒。值得注意的是，FPTAN返回的是「部分正切」即(X,Y)坐标对而非直接商值，因当时除法代价高昂，省略除法可为上层调用者留出优化空间。

## 8. TLA+中的可达性属性：语义合法性与模型检测

- 原始链接: <https://ahelwer.ca/post/2026-09-26-reachability/>
- 英文标题: Can we have reachability properties in TLA⁺?

本文探讨TLA+能否表达可达性（可能性）属性，即「系统始终能够到达某状态P」而非「所有行为都会到达P」。起因是Hillel Wayne声称TLA+无法表达此类属性，作者重读Lamport《A Science of Concurrent Programs》第5.1节后认为可以。文章分两层展开：模型检测层面，TLA+已有ENABLED操作符支持单步可达性，Lamport用正则式风格的+操作符定义多步可达性公式，但TLC尚不支持；可通过在完整状态图探索后执行反向广度优先搜索（backward reachability）来实现，实现风险较低。语义层面，核心技巧是利用机器封闭的公平性假设将分支时间推理嵌入TLA+的线性时间语义：若存在机器封闭的公平性假设F使得(Spec∧F)⇒□◇P，则每个有限前缀均可扩展为到达P的行为，从而在语义上合法。作者以计数器x=0的可达性为例，演示了构造公平性假设F=◇□[Down]_x∧WF_x(Down)的过程。此外，最终一致性系统的收敛性本质也是可达性属性，可用公平性假设替代此前笨拙的布尔标志位。作者坦言借助GPT-6辅助理解，但文章为本人独立撰写。

## 9. 保持 if 条件子句无副作用

- 原始链接: <https://www.teamten.com/lawrence/programming/keep-if-clauses-side-effect-free.html>
- 英文标题: Keep if clauses side-effect free

本文主张 if 语句的条件子句应仅用于判断，不应承载副作用操作。作者指出，直接在 if 中调用如 enqueueMessage(message) 这类有副作用的方法，会使返回值语义模糊——读者无法判断 true 代表「入队成功」还是「队列已满」。正确做法是将返回值赋给语义清晰的变量（如 boolean success = enqueueMessage(message); if (success) {...}），使代码读起来更像自然语言。对于非布尔返回值（如 flushQueue() == 0），同样应先用变量接收再判断，避免读者将动作误认为查询。作者还引用了一段生产代码 if(!categorySeen.add(categoryID)) continue;，说明读者会下意识将其读作 contains 查询，且配合 continue 后出现三重否定，逻辑极为绕。此外，将副作用方法与短路求值结合（如 queueNeedsFlushing() && flushQueue() == 0）尤其危险，第二个调用极易被忽略。作者强调短路求值本应用于保护无副作用表达式（如除零检查、空指针检查），不应用来「省掉」一个 if 块。结论是：多写三行显式代码的代价远小于日后因遗漏关键调用而付出调试成本，保持 if 条件无副作用是对自己和后续维护者的负责。

## 10. AI代理正将人类逐出决策回路

- 原始链接: <https://arxiv.org/abs/2608.23642>
- 英文标题: AI Agents Push Humans Out of the Loop

本文是Margaret Mitchell、Avijit Ghosh和Samir Passi于2026年发表的一篇立场论文，聚焦AI代理（AI agents）自主性提升后人类监督失效的问题。作者指出，尽管「人在回路中」（human in the loop）是应对AI代理风险的常见方案，但当前AI代理的设计与部署方式实际上阻碍了有效的人类监督，且长期使用AI系统本身会削弱监督者所需的认知能力，形成恶性循环。论文核心论点是：现有开发路径不仅无法支撑有效监督，反而在加速其退化。为此，作者主张将监督者的情境化目标与认知需求置于与AI代理能力同等重要的地位，作为AI代理发展的首要优先级。在实践层面，论文借鉴自动化领域与人机交互（HCI）的研究成果，提出两类设计层面的支持机制与组织协议：一是帮助监督者行使批判性判断，二是对抗因长期依赖自动化而产生的技能萎缩。作者呼吁开发者和部署者采纳此类方法，并警告：若不能明确回应有效人机交互中的认知需求，AI代理系统将持续被动地侵蚀其自身所依赖的人类技能，最终使「人在回路中」沦为形式。

## 11. NetBSD 磁盘标签（disklabel）格式详解与手动编辑实践

- 原始链接: <https://movq.de/blog/postings/2026-09-25/0/POSTING-en.html>
- 英文标题: NetBSD Playing with disklabels

作者从 DOS 和 Linux 背景出发，在 NetBSD 11 x86_64 虚拟机中系统探索 BSD disklabel 的二进制格式。文章首先确认 disklabel 位于磁盘第二个扇区（通过 getlabelsector() 和 getlabeloffset() 验证），以避免与 MBR 冲突。随后逐字段解析结构：元数据区包含 magic number、驱动器类型、CHS 几何参数（每扇区 512 字节、每磁道 63 扇区、每柱面 16 磁道等）及硬件时序字段，作者指出这些参数在现代 x86_64 上大多已过时且置零；分区表紧随其后，每条目 16 字节，记录 p_size、p_offset、p_fstype 等，其中分区 d 在 x86_64 上始终存在并描述整块磁盘。校验和采用将全部数据按 16 字节分块后做 XOR 的方式，作者用 dd 加 gawk 脚本验证了这一点。最后，作者在十六进制编辑器中手动写入一个 ZFS 类型的分区 i（大小 1234 扇区、偏移 5678），重算校验和后重启虚拟机，disklabel 工具成功识别新分区并提示与分区 a 重叠。文档来源为 man 5 disklabel 及 /usr/include/sys/disklabel.h。作者总结：动手实操是熟悉陌生系统机制最有效的方式。

## 12. 为基准测试调优服务器：从 3% 噪声到 0.26%

- 原始链接: <https://david.alvarezrosa.com/posts/tuning-a-server-for-benchmarking/>
- 英文标题: Tuning a Server for Benchmarking

本文以一个 double 数组求和的微型基准测试为例，演示如何逐步调优机器使测量结果具备可重复性。作者强调，基准测试调优与生产性能调优目标不同：前者追求可重复性，可牺牲峰值速度；后者追求极致性能。初始未调优状态下，变异系数（CV）高达 2.72%，任何小于此幅度的优化都无法被观测。调优路径依次为：（1）用 lstopo 了解硬件拓扑，区分混合 CPU 与同构 CPU；（2）用 taskset 将进程绑定到单个 P-core，CV 降至 1.06%，均值从 99.6 µs 降至 55.3 µs；（3）将 CPU 频率调节器设为 performance 模式，CV 降至 0.79%；（4）关闭超线程（SMT），CV 进一步降至 0.26%；（5）关闭 Turbo Boost，在本例中无额外变化但保证跨次运行可比。最终从 2.72% 噪声降至 0.26%，同时获得 1.8 倍加速，半个百分点的差异已成为可测量的信号。作者还提到在更繁忙的机器上可进一步关闭 ASLR、NMI 看门狗、透明大页等，并指出所有调优设置重启即失效，这正是期望行为——调优、测量、再恢复。

## 13. House of Apple 2 在 glibc 2.43 上的可行性剖析

- 原始链接: <https://jazho76.github.io/house_of_apple_2/>
- 英文标题: Dissecting House of Apple 2 on modern glibc

本文以 glibc 2.43（Ubuntu 26.04 / Fedora 44）为实验环境，通过 GDB 交互式调试逐步拆解 House of Apple 2 这一 FSOP 利用技术，验证其在现代 glibc 上是否仍然有效。现代 glibc 对 _IO_FILE_plus 的 vtable 指针进行了范围校验（必须落在 __io_vtables 区域内），直接伪造 vtable 会被 _IO_vtable_check 拒绝。House of Apple 2 的绕过思路是：将外层 vtable 指向合法的 _IO_wfile_jumps，使执行流进入宽字符流处理函数 _IO_wfile_overflow，再经由 _IO_wdoallocbuf 中通过 _wide_vtable+0x68 的间接调用实现任意函数调用——该二级 vtable 不受范围校验。文章详细给出了紧凑 payload 布局，将 _IO_FILE_plus、_IO_wide_data 与伪造 wide vtable 重叠放置以减小内存占用，并列出各偏移处的字段约束（如 _flags 不得置 _IO_NO_WRITES 或 _IO_UNBUFFERED，_IO_write_base 与 _IO_buf_base 须为 NULL，_lock 指向可写零页等）。获得任意调用后，利用 __push___start_context+63 处的 mov rsp, rdx; ret 栈迁移 gadget 将栈指针移入可控区域，再拼接 ROP 链调用 execve 获取 shell。最终结论：尽管各版本偏移和 gadget 地址会变，但「合法外层 vtable 通往未校验二级 vtable」这一核心控制流思路在 glibc 2.43 上仍可复现，House of Apple 2 依然是可行的利用路径。

## 15. Rust 中的「解析而非验证」模式

- 原始链接: <https://eli.thegreenplace.net/2026/rusty-thoughts-on-parse-dont-validate/>
- 英文标题: Rusty thoughts on "Parse, don't validate"

本文以 Rust 语言为视角，探讨「解析而非验证」设计模式。核心问题在于：Vec 的 first() 返回 Option<&T>，即使调用方已确保向量非空，仍须处理 None 分支，造成代码冗余与潜在隐患。解决方案是引入 NonEmpty<T> 类型，将「非空」不变量编码进类型系统，使 first() 直接返回 &T，无需 Option 包装。文章列举多个实例：nonempty crate 提供 NonEmpty 实现；Rust 版 POSIX 工具用 NonEmpty 构建 shell 管道；rust-analyzer 通过 AbsPathBuf 将路径逐步精炼为绝对路径；标准库 NonZero<usize> 保证非零并优化内存布局；serde 反序列化时借枚举与 NonZeroUsize 在解析阶段即完成校验。作者强调，「解析」的本质是将数据从一种表示转换为携带更强语义的新类型，转换完成后后续代码无需重复验证。相比 Python、JS 等动态语言中依赖手动校验，Rust 借助类型系统使该模式自然融入日常开发。

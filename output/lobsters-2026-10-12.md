## 1. GitHub 的种种问题——GNU 项目的批评

- 原始链接: <https://www.gnu.org/philosophy/whats-wrong-with-github.html>
- 英文标题: What's Wrong with GitHub

本文由 Jacob Bachmeyer 与 Richard Stallman 为 GNU 项目撰写，呼吁开发者避免将代码仓库托管于 GitHub，并围绕四大核心问题展开批评。第一，GitHub 推广模糊的许可实践：其「选择许可证」页面建议仅将 GPL 文本放入仓库文件即可，而 FSF 律师要求在每个实质性文件中加入许可声明，GitHub 却将此列为「可选步骤」。第二，GitHub 网站大量使用非自由 JavaScript，拒绝该脚本的用户几乎无法进行任何交互操作。第三，GitHub Copilot 属于 SaaSS（服务即软件替代品），其模型运行于远程服务器，用户无法控制；2026 年初 GitHub 将订阅制改为按 token 计费，用户被迫接受。此外，Copilot 生成的 issue 淹没维护者，GitHub 却拒绝允许屏蔽。第四，GitHub 试图颠覆 Git 的分布式架构：通过成就系统（游戏化）、集中化的 fork 与 pull request 工作流、GitHub Actions（含自动更新后门）以及隐藏邮箱地址、不提供邮件列表等做法，逐步将用户锁定在 GitHub 生态中。文章指出，Git 本身是自由软件，GitHub 无法强制绑定，但通过便利性诱导用户形成依赖。建议开发者在 README 中公布邮箱、将项目文档托管于不依赖非自由软件的站点，从根本上脱离 GitHub。

## 2. C 语言中的竞技场分配器

- 原始链接: <https://eliasebner.com/blog/guides/arena-allocators-in-c/>
- 英文标题: Arena Allocators in C

本文介绍了一种在 C 语言中管理内存的高效范式——竞技场分配器（Arena Allocator）。作者首先指出传统 malloc/free 模式的三大痛点：程序员易遗忘释放导致内存泄漏、频繁小内存分配性能差、调用方难以从函数签名判断是否发生了内存分配。竞技场分配器的核心思路是：将生命周期相近的内存归为一组，预先分配一大块连续内存，通过移动指针来「分配」，需要时一次性释放或重置，从而避免逐块管理。文章给出了完整实现：arena 结构体仅含 data、size、used 三个字段；arena_create 创建竞技场；arena_alloc 在分配时做 8 字节对齐并检查越界；arena_realloc 在末尾重新分配并拷贝旧数据；arena_clear 将 used 归零以复用；arena_free 释放整块内存。所有函数采用返回结构体加 success 标志的错误处理风格，避免输出参数。作者以字符串库为例，展示将 str_view 转为 str_owned 时传入 arena 指针，既让调用者明确知道发生了分配，又由调用者决定内存归属的生命周期，无需单独 free。作者认为该方案在性能与开发体验上均有显著收益，适合作为 C 程序员工具箱中的常用手段。

## 3. Git 提交到底占多大空间？

- 原始链接: <https://ratfactor.com/cards/git-commit-size>
- 英文标题: How big is a Git commit?

本文通过一系列实验，实测了不同场景下 Git 提交在 .git 目录中占用的实际字节数。作者指出，Git 以 zlib 压缩的松散对象存储数据，最终还会合并为 packfile 进一步去重，因此提交大小取决于文件内容的可压缩性。实验结果（均为松散对象）：git init 约 64 KB；提交 250 个极小文件增加约 47 KB；在 50 文件目录中改动 3 字节增加约 17 KB；单文件仓库改动 3 字节仅增加约 8.7 KB；提交 580 KB 二进制文件增加约 298 KB；提交 16.4 MB 文本源文件仅增加约 1.6 MB。作者还借助 git show 命令拆解了单次提交产生的四个新对象（一个 commit、两个 tree、一个 blob），解释了开销来源。结论是：极小提交存在数 KB 的固定开销，与涉及的文件树规模相关；而文件较大时，Git 的压缩效率极高，存储量可降至原始大小的 10% 到 50%，整体非常节省空间。

## 4. 多语言文档站点的「狂野西部」

- 原始链接: <https://technicalwriting.dev/blog/2026/10/polyglot/index.html>
- 英文标题: The wild west of polyglot docs sites

当一个项目同时提供多种编程语言的库时，其文档站点往往需要整合多个API参考生成器（如Doxygen、rustdoc、Sphinx）的输出，作者将此类站点称为「多语言文档站点」。文章讨论了两种主要架构策略：一是「转换」策略，即解析各生成器输出并转换为主文档格式，以Breathe（Doxygen XML转Sphinx）为例，存在丢失专业信息、违背用户既有习惯、构建缓慢、胶水代码导致静默失败等问题；二是「火鸡套鸭」策略，即直接发布各生成器原始输出，如pigweed.dev将Doxygen、rustdoc、Sphinx三个独立站点拼合，面临外观不统一、跨站导航困难、搜索碎片化、链接脆弱等挑战。作者通过引入统一页头和基于Pagefind的全面搜索改善了后者，对小型API也可手动编写文档。文章最后提出未来改进方向：为生成器增加「--fragment」模式以输出纯内容片段，以及开发类似Doxylink的跨方向链接校验工具，旨在推动文档生成器与搜索库之间的协作。

## 5. 「D-Bus 地狱」：一个域名的误会与姓氏词源漫谈

- 英文标题: D-Bus Hell

本文是英国开发者 David Bushell 的一篇轻松随笔。他的个人博客域名 dbushell.com 长期被读者误读为「D-Bus Hell」（D-Bus 是 Linux 桌面进程间通信总线项目），作者以幽默口吻回应这一「评论区老梗」。他通过 WHOIS 记录证明域名注册于 2004 年 5 月，而 D-Bus 项目 2006 年 11 月才首次发布，时间线上域名与该项目毫无关联，甚至 D-Bus 自身都没有独立域名。文章随后转向语言学话题，介绍「重新分词」（rebracketing）和「民间词源」（folk etymology）现象，以「Hamburger」从「Hamburg + er」变为「ham + burger」为例说明。作者追溯自己姓氏 Bushell 的可能来源：英制容量单位 bushel（源自古法语 boissel）、约克郡村庄 Bossall（盎格鲁-撒克逊语 Bosciale），以及拼写变体 Buchel 等，指出在识字率极低的年代，抄写员的音译差异导致同一姓氏出现多种拼写，难以追溯单一源头。最后，作者谈及域名作为临时租赁 URI 的特性，解释自己为何坚持保留 dbushell.com 作为个人空间，并邀请读者分享自己姓名与域名的词源故事。全文以调侃为主，技术含量有限，但涉及域名系统与词源学的趣味知识。

## 6. 动态JSON拆解如何让Logfire查询提速千倍

- 原始链接: <https://pydantic.dev/articles/dynamic-shredding-2026-01-26>
- 英文标题: How shredding JSON is giving Logfire 1000x query speedups

Logfire是基于OpenTelemetry的可观测性平台，其半结构化属性数据以JSON形式存入Parquet列，导致查询时需下载并解析大量无关JSON，成为性能瓶颈。早期采用「静态拆解」，手动将少量高频属性（如http.status_code）提取为独立强类型列，但灵活性差、未拆解属性查询仍慢、且产生大量全空列。文章提出「动态拆解」方案：在数据摄入和压缩阶段，自动识别每个Parquet文件中出现频率最高、体积最大的属性（默认取前128个），将其拆为独立列，其余保留在残余JSON列中。这样查询可借助zone map和全文索引跳过无关文件，仅下载目标列，避免JSON解析，实现渐进式裁剪。实现上需DataFusion支持JSON访问器的表达式下推与谓词下推，相关改动已合入DataFusion 52.1.0（2026年1月），剩余GROUP BY等场景的优化预计2026年2月完成。类型推断遵循Int→Float→JSON、Bool→JSON、String→JSON的 widening 规则。生产数据显示99%文件唯一顶层键不超过128个，该上限可防止异常动态键导致列爆炸。该功能预计2026年2月向全部用户推出，部分查询从30秒超时降至1秒以内。

- 英文标题: Tello's GameSir T1d controller as a Linux Xbox controller

GameSir T1d 是随 Ryze/DJI Tello 无人机出售的蓝牙手柄，仅支持 BLE 并采用 GameSir 自有 GATT 协议，而非标准 HID，因此 Linux、Windows、SteamOS 等系统均无法识别。本文介绍了一个开源 Python 桥接方案：通过 bleak 库读取 T1d 的 BLE 输入通知（20 字节/包，含四轴摇杆、模拟扳机、按键等），再借助 Linux uinput 子系统创建一个虚拟 Xbox 360 手柄，使 Steam、SDL 及大多数 Linux 游戏将其视为普通有线手柄，无需任何硬件改动。文章给出完整步骤：下载桥接脚本与 udev 规则、安装依赖、配置权限、校准摇杆、运行。作者还深入分析了摇杆漂移的硬件根因——碳膜电位器磨损导致 ADC 值偏离 512 中心甚至卡在 1023 上限，桥接程序通过动态采样中心、按轴缩放量程、15% 径向死区及 2 秒限位超时等策略予以补偿。此外，作者解释了为何不直接刷写固件（BLE 模块疑似 TI CC2540，需 IAR 8051 工具链且无公开源码），并提及 Windows 端已有社区方案，以及未来可用 ESP32-S3 制作 USB 转接器的设想。

## 8. 一致性不是局部属性

- 原始链接: <https://n-the-loop.com/blog/consistency-is-not-a-localized-property/>
- 英文标题: Consistency is not a localized property

本文以 Apache Kafka 的「精确一次」（exactly-once）语义为案例，论证一致性并非可由单个组件独立保证的局部属性，而是端到端的系统级全局属性。Kafka 团队耗费多年、引入多个新组件并重写旧组件才实现精确一次写入，但即便如此，其设计者仍明确指出：精确一次处理是端到端保证，应用层自身也必须不违反该属性。由此引出两条实践推论：第一，既然没有任何单一组件能确认全局一致性，就必须有人从整体上理解整个系统，在组件之外维持一致性；第二，各组件负责人只会说「我的部分没问题」，而全局属性需要一个人对整体负责，并确保其设计合理。文章进一步指出，Kafka 的精确一次协议上线八年后（2022 年 KIP-890）仍需重新设计以修补可能破坏该语义的正确性漏洞，说明即使经过大量工程投入，全局保证依然脆弱。核心教训是：不要将全局性、高价值属性交给机器并假设代码能自动维持，这类保证的根基在于人对系统的理解与责任归属，而非代码本身。

## 9. Futhark 类型检查器中别名传播的最终设计方案

- 原始链接: <https://futhark-lang.org/blog/2026-10-11-what-we-did-about-aliasing.html>
- 英文标题: What we ended up doing about alias propagation

本文总结了 Futhark 编程语言在通往 1.0 版本过程中，对类型检查器中别名传播（alias propagation）问题的最终设计决策。核心挑战在于：为确保原地更新安全，类型检查器必须保守地跟踪对象间是否可能共享内存；而多态高阶函数（如管道操作符 |>）使得精确判断返回值是否别名输入变得困难。作者放弃了在用户可见类型系统中引入「新鲜度多态」的方案，转而利用参数化性在内部推断更精确的别名信息：若某类型参数仅通过特定函数参数获得，则结果继承该函数的新鲜度。为控制复杂度，该细化仅适用于完全应用的多态变量函数，不支持部分应用等情形。在安全性验证方面，作者借助 AI 编码代理在 Rocq 中构建了一个仅含元组、函数和对象三种值的小型模型语言，通过归纳法证明了良型程序不会产生非法内存复用。编译器实现为基于相同算法的 Haskell 重写，但包含形式化未覆盖的特性（如和类型），仍存在引入错误的风险。作者承认当前设计在简洁性与表达力之间做了取舍，例如对 id (x,y) 会丢失元组分量的别名精度，未来可能进一步改进。

## 10. 下一代借用检查器：Rust借用检查的即插即用替代方案

- 原始链接: <https://gist.github.com/FlameyosSnowy/a49a35ba006238be55d8c3e410c31061>
- 英文标题: The next-gen borrow checker, a drop-in replacement for Rust borrow checking

作者Eyad Amr在2026年10月发布的博客中，介绍其正在开发的新语言Zeta，核心目标是解决Rust借用检查器过于保守而阻碍生产力的问题。文章首先梳理了Rust借用检查的三大支柱：所有权、共享XOR可变性规则（同一时刻仅允许一个可变引用或任意多个不可变引用）以及生命周期系统。作者指出，该规则虽能防止悬垂引用和竞态条件，却导致大量合法内存模式被拒绝：例如对Vec中不重叠索引同时获取多个可变引用时，Rust要求使用get_disjoint_mut，其内部执行O(n²)的运行时重叠检查；实现双向链表等含回指的数据结构时，不得不依赖Rc与RefCell叠加运行时借用检查，代码冗长且需处理繁琐的Result。作者还展示了Zeta编译器自身用Rust编写时，结构体被大量生命周期参数（如「f」「a」「bump」）侵入的困境。作为解决方案，Zeta引入第三种引用类型&alias，声称能在编译器层面原生支持共享可变性，同时保持内存安全（包括防止悬垂引用），无需unsafe或额外运行时开销。文章定位为Rust借用检查的「即插即用」替代方案，兼顾性能保证与开发体验。

## 11. NumPy 2.5 中 np.searchsorted 实现最高 25 倍加速

- 原始链接: <https://blog.scientific-python.org/numpy/searchsorted/>
- 英文标题: Making np.searchsorted up to 25× Faster in NumPy 2.5

本文介绍了 NumPy 2.5 中对 np.searchsorted（二分搜索）的重大性能优化，最高提速 25 倍。作者首先将经典逐键二分搜索改写为向量化形式：用数组同时维护所有查询的搜索区间，利用 NumPy 的向量化原语批量推进，消除 Python 循环开销。关键改进包括：让所有查询执行相同迭代次数（ceil(log2(n)) 步），去除活跃掩码判断，提速约 2 倍；进一步用「左边界 + 全局长度」替代每查询的 lo、hi 两个数组，将额外内存从 O(K) 降至 O(1)。该算法随后被移植为 C++ 实现，通过 PR #30517 合入 NumPy 2.5。基准测试在 Apple M1 Pro 上完成，排序数组长度达 4 GiB、查询键 1 万条，2.5 版本较 2.4 快最高 25 倍。与 JAX、TensorFlow、PyTorch 的对比显示，NumPy 2.5 在单线程向量化路线上具有竞争力；多线程库在缓存未命中时性能趋同。文章还指出，Eytzinger 等缓存友好布局是未来进一步优化的方向，并探讨了是否可通过 Array API 暴露此类布局。该优化将惠及 SciPy、scikit-learn 等依赖 NumPy 的生态库。

## 13. 用 React Compiler 让 Context 消费变廉价

- 原始链接: <https://jjenzz.com/making-react-context-cheap/>
- 英文标题: Making React Context Cheap with React Compiler

本文探讨 React Context 在大规模消费者场景下的性能问题。以 5000 个 radio 为例，任何一次选择变更都会触发全部消费者重渲染，而 React 至今未提供类似 useContextSelector 的细粒度订阅 API。作者对比了三种方案：基于 useSyncExternalStore 的 store（仅两个 radio 重渲染）、Context 配合 React.memo 子组件（外层仍全部渲染但内层跳过 4998 个）、以及 React Compiler 自动复用未变化 JSX。在 M3 Pro 上以 p95 生产构建测量，三种方案在挂载和点击延迟上几乎持平，Compiler 版本甚至略优。作者引用 Joseph Savona 的观点指出，Compiler 已在渲染阶段自动完成类似 memo 化的工作，无需额外组件或 selector。对于尚未采用 Compiler 的开发者，文章提供了一个 withContextSelector 组件工厂作为过渡方案，但提醒其属于组件工厂、与 React lint 规则冲突，迁移 Compiler 后应移除。文章最终结论是：与其执着于减少渲染次数，不如让每次渲染足够廉价；React Compiler 可能已使 useContextSelector 和 useSyncExternalStore 变通方案不再必要。

## 14. Eufy视频门铃与Homebase基站安全漏洞逆向分析

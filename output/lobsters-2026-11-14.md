## 1. 如何（不）做一个音乐播放器：一个Zig开发者的血泪教训

- 原始链接: <https://alichraghi.github.io/blog/how-not-to-build-a-music-player>
- 英文标题: How Not to Build a Music Player

作者居住在伊朗，因2026年「十二日战争」及后续长达四个月的全国互联网封锁，急需离线音乐播放器。试用Strawberry后因其歌词时间戳显示方式令人不适，决定用Zig语言从零开发一款名为AMP的播放器，目标为最小功能集、无C++依赖、原生系统集成，连着色器也用Zig编写。项目刚起步便遭遇新一轮断网，作者花数百美元通过白名单SIM卡、Starlink等黑市渠道维持连接，在极慢网速下艰难推进开发。网络恢复后，作者受前沿LLM热潮影响，用Claude Max订阅「vibecode」了大量代码，但随后Anthropic因识别到其伊朗身份封号，Codeberg亦宣布禁止AI生成内容政策，迫使作者逐行审查并重写全部代码。四个月后近一半代码被删除，但功能不减、健壮性反升。作者深刻反思：LLM适合当作高级IDE辅助（本质是长sed/正则），而非替代人工思考；业余项目切勿赶工。AMP v0.1已发布，模糊着色器基于Zig实现，路线图涵盖音乐服务器、Android/Windows移植及Linux发行版打包。

## 2. 不占用单元格的终端边框协议

- 原始链接: <https://www.joshka.net/cell-borders/>
- 英文标题: Terminal borders that don't cost a cell

本文由Ratatui维护者撰写，介绍一种新型终端协议：在单元格边缘绘制细线边框而不占用整行或整列。传统Unicode制表符边框每条线占一个完整单元格，在约50行高的终端中，多层嵌套面板可浪费6至8行仅用于装饰线。新方案将边框视为单元格属性（类似背景色），每格可携带12段线段（四边各两半加四根中心臂），支持实线、双线、虚线、点线及带抗锯齿的圆角，各段可独立设置颜色、宽度和位置。协议采用DCS转义序列，以「画笔」模型在光标处设置边框后随文本输出；相邻单元格共享边按优先级、宽度、位置规则合并，确保聚焦面板边框完整。在Ghostty中实现约1650行代码，每格仅增16位边框ID（复用已有填充），无边框时零额外开销，最坏情况约10至15MB。不支持的终端自动回退到制表符。作者已用Ratatui构建分屏面板、btop风格监控等演示，并公开规范与代码，征求终端及TUI开发者反馈，希望该方案不止于单一终端实现。

## 3. 移动端亟需至少第三个选择

- 原始链接: <https://blog.ovalerio.net/archives/3359>
- 英文标题: The need for at least a third option

作者Gonçalo Valério将手机从Android迁移至Ubuntu Touch，不到一小时即完成，由此引发对移动操作系统格局的思考。他指出，过去认为安装去谷歌化ROM（如LineageOS、GrapheneOS）配合F-Droid即可保持自由，但近期趋势表明用户和开发者正持续丧失对设备的控制权：iOS始终封闭，Android虽理论开放，Google却在逐步收紧，运行软件需付费获取许可，安装流程甚至耗时24小时。与电脑端可自由更换Linux、FreeBSD等系统不同，移动端被牢牢锁定，替代ROM遭封锁，应用开发者也被激励仅面向两大平台。作者警告，现代生活高度依赖手机，社会正逼近「必须成为两家外国公司的客户才能在本国行使公民权利」的境地，数字主权问题日益紧迫。他认为理想的替代方案应至少开源核心、支持多软件分发渠道、注重互操作性，且不能是现有生态的翻版或过于小众的系统。最终，他锁定三个已有社区基础的候选：SailfishOS、Nura（原PostmarketOS）和Ubuntu Touch，计划逐一探索、测试并贡献，强调无论哪个胜出，关键是必须有一个真正起势。

## 4. Go 语言中的概率数据结构

- 原始链接: <https://antonz.org/probabilistic-data-structures/>
- 英文标题: Probabilistic data structures in Go

本文介绍 Go 语言概率数据结构包「unsure」，涵盖 Bloom filter、Count-min sketch、HyperLogLog、T-digest 和 Top-k 五种结构。概率数据结构以近似结果换取大幅内存节省，适用于缓存过滤、限流、去重计数和分位数统计等场景。unsure 的核心逻辑仅 100 至 300 行，无外部依赖，统一采用 wyhash 哈希。其中，Bloom filter 采用分块设计，每次操作仅访问一条缓存行，比 bits-and-blooms 快约 4 倍、比 gloom 快约 2 倍；Count-min sketch 使用保守更新与 32 位计数器，内存减半且误差降低 2 至 2.7 倍；HyperLogLog 采用 Ertl 改进估计器，基于直方图计算，Count 操作比 axiom 快 270 至 83000 倍；T-digest 以 8 KB 空间替代 8 MB 排序列表完成分位数估计。文章对每种结构均给出原理图示、代码示例及与主流实现的基准对比，unsure 在速度和内存上普遍占优。

## 7. ML模块系统：面向普通人的入门指南

- 原始链接: <https://thunderseethe.dev/posts/ml-modules-for-mere-mortals/intro/>
- 英文标题: ML Modules for Mere Mortals

本文以Rust风格伪代码介绍了ML（元语言，非机器学习）模块系统的核心概念。ML模块诞生于1983年的SML，但至今仅OCaml在生产中使用，作者认为这很可惜。文章指出，模块系统的核心在于「签名」（signature）——模块的类型即为其签名，签名充当接口，使模块可匹配任意兼容签名，从而免费复用和裁剪模块。通过抽象类型，签名可隐藏具体类型表示，防止外部破坏不变量，实现真正封装。参数化模块（即函子）接受另一个模块作为参数，实现类似泛型的抽象，且可要求参数模块提供比较函数等完整能力，无需像Rust那样依赖trait。include机制允许将子模块内联合并，兼顾模块化与便利性。文章最后以构建执行器为例，展示如何用静态模块组装替代OOP中的运行时依赖注入：通过替换缓存模块和运行器模块即可切换构建行为，测试时注入假运行器即可验证逻辑。作者总结道，ML模块的表达力源于签名，通过改变签名视角即可实现封装与重构，值得更多语言借鉴。

## 11. Rust 与 C++ 中的指针来源（Provenance）机制对比

- 原始链接: <https://sofiabelen.github.io/projects/pointer-provenance-in-rust-vs-cpp/>
- 英文标题: Pointer Provenance in Rust vs C++

本文围绕指针来源（provenance）这一编译器抽象概念，对比了 C++ 与 Rust 的处理方式。作者首先解释：指针并非单纯的地址整数，编译器会追踪每个指针「派生自」哪个内存分配，据此进行优化（例如判断两个指针是否可能指向同一块内存）。通过 LLVM IR 可观察到编译器构建有向无环图来记录指针的根来源。在 C++ 中，将指针转为 uintptr_t 会「暴露」来源，迫使编译器放弃相关优化，即使程序员仅想读取地址数值。Rust 则提供了更精细的 API：addr() 读取地址但不暴露来源；with_addr() 用修改后的地址构造新指针同时继承原来源（适用于无锁结构中利用对齐低位存储标志位的场景）；without_provenance() 生成无来源的裸地址（不可解引用）。作者用 Miri 验证：旧式 Rust 写法（指针转整数再转回）会触发警告，提示可能遗漏指针错误；而使用严格来源 API 后，Miri 能更准确地捕获违规操作。实验表明，当前 Rust 版本在优化效果上与 C++ 类似（仍会重新加载栈变量），但更表达意图的 API 为未来优化留出空间，并借助 Miri 在编译期发现潜在 bug。

## 13. 从字节码到 SSA：命令式珍珠

- 原始链接: <https://bernsteinbear.com/blog/ssa-bytecode/>
- 英文标题: SSA from bytecode: imperative pearl

本文是 Ruby JIT 编译器 ZJIT 作者对字节码转 SSA（静态单赋值）形式的通俗讲解。ZJIT 中约 1900 行的 add_iseq_to_hir 函数负责将 CRuby 的 YARV 栈式字节码转换为高层 SSA IR，但其核心逻辑非常简短。关键观察是：每条字节码指令的栈输入和输出数量在编译期即可静态确定，因此可以在编译时模拟栈操作，无需关心具体数值，只需追踪每个值的来源——用指令名（如 v0、v1）替代实际值，使后续指令直接引用前驱指令的输出。作者引用 Java HotSpot 编译器论文的观点：指令同时代表操作与结果，操作数即指向先前指令的指针。文中用 Ruby 代码展示了具体解释器（操作值栈）与抽象解释器（操作 SSA 名栈）的对照，两者结构几乎一致，仅将数值替换为唯一名称即可。作者将此过程概括为「将时间推入 IR」：同一栈槽在不同时刻承载不同 SSA 值。对于跨基本块的控制流，还需引入 phi 节点或基本块参数等数据流机制。标题「imperative pearl」戏仿了「functional pearl」系列论文，并致敬 Andrew Appel 的「SSA is Functional Programming」。文章整体风格轻松，旨在降低 SSA 转换的认知门槛。

## 15. 修复 WebKit 中 Promise 永久挂起缺陷：Promise 是铁轨吗？

- 原始链接: <https://alistair.sh/thenables>
- 英文标题: Fixing a WebKit bug to see if promises are made of train tracks

文章以一个在 Safari 和 Bun 中永不终止的程序切入：篡改 Promise 的 constructor 使 Symbol.species getter 抛异常，导致 await 后 Promise 永远 pending。根因是 JavaScriptCore 快路径中 species 查找先于 resolve/reject 函数创建，异常抛出时无函数可用，异常逃逸出微任务，Promise 便永久挂起。修复仅 +16 行：将创建 resolving functions 提前到调用 then() 之前。文章还梳理了 resolve 的完整流程——resolve(value) 并非立即 fulfill，而是先读 value.then，若为函数则视为 thenable 进行扁平化；属性读取可触发 getter 抛异常，规范将异常置于 rejected 轨道。作者以铁路编程类比 Promise 的 fulfilled 与 rejected 双轨道，但指出 failure 轨道无法标注类型，因为引擎自身（如 species 查找）也可能向 rejected 轨道写入值，这正是 TypeScript 的 Promise<T> 长期没有 E 参数的根本原因。

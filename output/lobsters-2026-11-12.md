## 1. 如何真正安全地自托管？

- 原始链接: <https://lobste.rs/s/m43bas/how_do_you_actually_self_host_securely>
- 英文标题: How do you actually self-host securely?

一位自托管新手在论坛提问：如何用树莓派安全地托管静态网站，同时避免依赖 Cloudflare Tunnels 等第三方服务。讨论围绕几个核心层面展开。网络层面，有答主建议租用每月 5 美元的 VPS 作为跳板，通过 SSH 端口转发将 443 流量引至树莓派，配合 acme.sh 自动签发 TLS 证书，从而获得静态公网 IP 并隐藏家庭地址；也有人指出 SSH 隧道易中断，需借助 autossh 等工具维持。安全实践方面，多位答主强调：定期更新系统、禁用 SSH 密码登录、使用非标准端口、用 UFW 等防火墙封禁多余端口、对仅个人访问的服务加 basic_auth 或 fail2ban、避免在不懂 Docker 网络时贸然使用容器。关于内网穿透，Tailscale 被反复提及，它基于 WireGuard 让所有设备如同处于同一局域网，免去了端口转发和动态 DNS 的麻烦，个人使用免费；但部分人认为对简单场景而言原生 WireGuard 已足够，Tailscale 属于「过度配置」。另有答主给出通用建议：优先从源码或包管理器安装软件而非拉取 Docker 镜像、理解 Unix 权限模型、避免功能蔓延、尽量用密钥替代密码、不要轻信「守门人」说某事不可行。整体基调鼓励新手从小处着手、逐步学习，不必一开始就追求完全自主。

## 3. 为 GitHub Actions 工作流添加锁文件

- 原始链接: <https://hugovk.dev/blog/2026/lock-github-actions/>
- 英文标题: Lock your GitHub Actions

GitHub Actions 现已支持工作流锁文件（workflow lockfiles），用于解决 action 版本固定带来的供应链安全风险。此前社区建议将 action 固定到完整 SHA 而非 tag，因为 tag 可变，攻击者可能将原本安全的 tag 指向恶意代码。本文介绍了完整的锁文件配置流程：首先通过「gh extension install github/gh-actions-lock」安装扩展，然后在仓库中运行「gh actions-lock」，工具会将工作流中的 SHA 引用改写为语义化版本标签（如 v7.0.1），并在「.github/workflows/actions.lock」中记录每个 action 对应的 commit SHA、owner_id 和 repo_id，实现版本锁定与可追溯。文章指出 Renovate 和 Dependabot 均已支持锁文件，定期更新时会自动同步。此外，建议在 CI 中增加验证步骤（使用「gh actions-lock --verify」），确保锁文件未过期或损坏，作者将其作为独立 job 放入现有 lint 工作流中并行执行。安全方面，文章强烈推荐在 prek 或 pre-commit 中集成 zizmor（v1.32.0 起支持锁文件）对 Actions 进行安全扫描。最后给出了 Python 生态中多个项目的实际采用示例，包括 Pillow、release-tools、miss-islington 和 cpython 的 PR。

## 4. C++标准首次未通过国家机构投票

- 原始链接: <https://herecomesthemoon.net/2026/11/cpp26-failed-the-national-bodies/>

## 7. curl 三十年：从百行代码到承载全球互联网传输

- 原始链接: <https://daniel.haxx.se/blog/2026/11/11/30-years-of-internet-transfers-with-curl/>
- 英文标题: 30 years of Internet transfers with curl

1996年11月，巴西学生Rafael Sagula发布了仅百余行C代码的HTTP下载工具httpget 0.1。瑞典开发者Daniel Stenberg发现后开始修补并添加域名解析，逐渐成为实际维护者。他当时为IRC机器人Dancer的货币汇率服务需定期抓取HTTP页面，由此与该项目结缘。随着gopher和FTP支持的加入，工具先后更名为urlget；1998年初加入上传功能后定名curl，4.0版已含3300行代码、三种协议。2000年Stenberg将其重构为libcurl库，PHP随即采用为默认网络引擎，极大推动普及。curl以C语言编写，Stenberg坚持「只迭代、不重写」，三十年来从未推倒重来。如今curl支持二十余种协议，libcurl估计运行于约三百亿个实例中，甚至被NASA确认用于火星着陆任务。作为完全独立、不隶属任何组织的开源项目，Stenberg仍任BDFL，但强调由数千名贡献者共同支撑。他参与IETF工作，推动HTTP/2和HTTP/3早期实现，致力于让curl成为最安全、文档最完善的网络传输组件。

## 9. Andrew Kensler 的 permute()：无状态、常数时间的伪随机数组遍历函数

- 原始链接: <https://andrew-helmer.github.io/permute/>
- 英文标题: Andrew Kensler's permute(), a function for stateless, constant-time pseudorandom-order array iteration

本文详解 Andrew Kensler 提出的 permute() 函数，用于从长度为 n 的数组中无重复地随机选取 k 个元素。传统 Fisher-Yates 洗牌需 O(n) 时间与 O(n) 空间，而 permute() 仅需 O(k) 时间、O(1) 空间，且可并行查询任意随机索引，特别适合图形渲染中同时遍历海量数组、或从超大数组中抽取小样本等场景。其核心由两部分构成：一是在 2 的幂次域上构造可逆（双射）哈希函数，利用异或、乘以奇数等操作保证一一对应；二是借用密码学中的「cycle-walking」技术，反复哈希直到结果落入数组长度范围内。为控制迭代次数，作者用掩码将哈希域限制为不超过 2 倍数组长度，使平均迭代次数小于 2 次，从而实现近似常数时间。文章给出了完整的 C++ 实现，包括 Kensler 通过爬山法优化的哈希函数，并指出该哈希在域大小约 2^27 以内效果良好，更大域需额外处理。此外，作者强调该函数并非密码学安全，适用于渲染积分计算和一般统计分析，不适合安全敏感场景。

## 12. 修改 Linux 内核使 SIGKILL 和 SIGSTOP 可被捕获与屏蔽

- 原始链接: <https://vulpinecitrus.info/blog/what-if-you-could-handle-sigkill/>
- 英文标题: Modding Linux to use SIGKILL on every process

本文记录了作者尝试修改 Linux 内核源码，使通常不可捕获、不可屏蔽的 SIGKILL 和 SIGSTOP 信号能被普通用户进程注册处理函数或加入屏蔽集。文章首先梳理了 POSIX 信号机制及 Linux 内核中信号投递的完整路径：从 exit_to_user_mode_loop 触发 arch_do_signal_or_restart，经 get_signal 出队、handle_signal 搭建栈帧，到用户态通过 rt_sigaction 和 rt_sigprocmask 系统调用注册处理与屏蔽。作者发现内核在多处显式排除这两个信号：rt_sigprocmask 中用 sigdelsetmask 强制移除、do_sigaction 中通过 sig_kernel_only 宏拒绝注册、do_sigtimedwait 中排除等待、get_signal 中对 SIGSTOP 做特殊分支。补丁方案是新增 KConfig 选项 CONFIG_KILL_STOP_HANDLING，用条件编译将上述四处特殊处理屏蔽或统一为普通信号逻辑，其中将 SIG_KERNEL_ONLY_MASK 定义为 0 即可一次性解除 do_sigaction 及 sig_task_ignored 等处的限制。作者基于 Linus 仓库的 Linux 6.13.0 完成编译，配置 GRUB 启动项后重启。文章在「启动修改后的内核」一节被截断，仅写到「启动后什么都没发生」，未给出最终实验结果或稳定性分析。

## 13. 果不先于因：从爱因斯坦到Lamport

- 原始链接: <https://www.itworkslocally.dev/posts/no-effect-before-its-cause>
- 英文标题: No Effect Before Its Cause: From Einstein to Lamport

文章以Alice和Bob在Notion中同时编辑文档却因网络中断导致「丢失更新」的场景切入，引出无主复制（leaderless replication）的核心难题：当多个副本各自独立接受写入、没有中央仲裁者时，如何决定冲突写入的顺序。作者先借用爱因斯坦1905年狭义相对论中「火车与闪电」的思想实验说明： simultaneity（同时性）并非宇宙事实，而是取决于观察者；类比到分布式系统，每台服务器的时钟都会漂移，比较物理时间戳无法可靠判定因果先后。随后介绍Lamport 1978年论文的核心贡献：用消息传递的因果链定义「happens-before」关系，完全不依赖时钟。两个事件若不存在消息传递的因果链，则互为「并发」——并非时间上同时，而是彼此互不知晓。文章进一步解释无主复制的含义：每个副本（如Dynamo、Riak、Cassandra及协作编辑器）独立接受写入，同步服务器仅充当消息中转而非裁判，目标是所有副本最终收敛到相同状态。最后提出处理并发写入的三种常见策略：最后写入胜出（信任时钟）、保留两者并存、以及基于因果关系的方案，并预告后续将讨论CRDTs（如Yjs）如何具体实现。

## 15. Linux 路由查找性能演变（更新至 7.3）

- 原始链接: <https://vincent.bernat.ch/en/blog/2026-linux-performance-ipv4-ipv6-route-lookup>
- 英文标题: Performance evolution of route lookup on Linux

本文是作者系列追踪文章的更新，将 Linux 路由查找性能基准测试推进到 7.3 版本，并定位了导致性能回退的根因。测试在 Scaleway 租用的 AMD EPYC 8024P（Zen 4c，2.4 GHz，关闭 boost）上完成，使用 GCC 10.2 编译各版本内核。IPv6 侧测试了 26 万、4 万前缀及 /48、/128 等四种场景；IPv4 侧测试了 100 万、50 万前缀及连续 /32 三种场景。历史改进包括：4.15 以 RCU 加自旋锁替代读写锁、4.18 优化数据结构、5.9 移除昂贵间接调用。然而 6.5 引入的 SRSO（推测性返回栈溢出）缓解措施为每次函数返回增加约 20 个周期，导致 IPv6 回退约 200 ns、IPv4 回退约 30 ns，几乎抹平此前全部收益。此外，作者自身在 5.11 引入的一处回归（ip_ignore_linkdown 多跟三个指针）也造成少量开销，通过重排条件判断可将中位数从 132 降至 126 周期。缓解措施的影响因 CPU 而异：Intel Xeon W-2295 上 IPv4 仅几个周期、IPv6 不足 3%。若路由性能关键，可选换用 AMD Zen 5、第四代 Xeon 或 ARM Neoverse V2，或通过 mitigations=off 等参数关闭部分缓解，亦可用 XDP/eBPF 绕过内核路由或将路由卸载至网卡。

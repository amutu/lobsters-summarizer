## 1. 源代码可用性：谁该为此买单？

- 原始链接: <https://kristoff.it/blog/source-code-availability/>
- 英文标题: Who Should Pay For Source Code Availability?

本文作者以自己用Zig构建静态站点生成器Zine的亲身经历为引，指出依赖托管在GitHub、Codeberg或自托管Forgejo上时，主机宕机或消失会导致构建失败。他先讨论了通过fork或vendor依赖来增强韧性的做法，但认为这两种方式都不够高效，因为分叉或 vendored 的代码不易被发现，也无法自动作为镜像使用。随后作者介绍了Radicle——一个点对点网络，节点按兴趣播种仓库，问题（Issue）和补丁（Patch）以CRDT Git对象形式存储在仓库中，并通过网络同步。在Radicle模型中，播种自己的依赖和下游用户的仓库能保持代码可被发现，同时成本与各方利益更一致，比“自托管forge+fork/vendoring”更高效。作者还探讨了让Zig包管理器直接支持Radicle的可能性，指出使用RID（仓库ID）而非URL可避免单点故障，但需要节点身份；他提议通过镜像支持或CLI工具将RID解析为HTTP URL，供HTTP客户端直接克隆。最后他对比了Codeberg，认为Forgejo的fork设计资源占用更高，并提及Codeberg应探索更本地优先的高效协作设计。总的来说，作者主张通过Radicle这类去中心化网络，让源代码可用性的成本更公平地由受益方共同分担。

## 2. 追踪Zsh历史记录数据丢失的bug

- 原始链接: <https://michael.stapelberg.ch/posts/2026-08-09-zsh-history-truncation-bug/>
- 英文标题: Tracking down a Zsh history data loss bug

作者长期遇到Zsh历史记录文件(~/.zsh_history)中部分命令丢失的问题，文件看似正常但只保留很旧的条目。通过inotify、fatrace、bpftrace等工具监控文件系统和系统调用，发现Zsh在退出时会重写历史文件：读取旧文件内容，写入临时文件再rename覆盖。但bpftrace显示有时读取的数据量明显偏少，导致新文件被截短。为定位根因，作者修改Zsh源码，在写入少于50000行的临时文件时故意崩溃，并用systemd-coredump收集核心转储。分析崩溃现场发现savehistfile调用自readhistfile，而readhistfile中的错误标志errflag=2(ERRFLAG_INT)且lasthist.interrupted=1，说明读取历史文件时被信号中断。进一步推断是作者退出mosh/ssh会话时按Ctrl+C发送SIGINT所致。当Zsh正在读取历史文件时收到该信号，读取循环被中断，随后用不完整的内容重写历史文件，造成数据丢失。该问题已在Zsh 5.9.2(2026年7月12日发布)中修复，修复补丁为53454。

## 4. 依赖Go：Solod语言的设计思路

- 原始链接: <https://antonz.org/relying-on-go/>
- 英文标题: Relying on Go

文章介绍了一种名为Solod的系统编程语言，它面向C和Go开发者，但并非通常意义上“类似Go”或“修复Go缺陷”的语言。Solod在语言层面严格是Go的一个子集，刻意复用Go现有工具链，包括语法高亮、LSP、静态检查和包管理。用户安装Solod命令行工具后，可以用常规Go工作流编写代码，仅需导入Solod标准库，并通过“so run”运行，该命令本质上是用Go实现的程序。Solod标准库大量借鉴Go源码，甚至原样复制部分字符串函数并保留版权；对于需要手动内存管理的场景，则以显式分配器参数改写函数，例如Clone函数从Go版本改为接受mem.Allocator参数。由于Go工具无法识别Solod不支持的语法（如函数字面量），Solod提供了自定义的“so”工具给出诊断错误。最终所有Solod代码会被翻译为C11，并由GCC或Clang编译，因此同样依赖C工具链和数十年优化成果。文章强调，新语言不一定需要新生态，Solod重度依赖Go反而使其更可靠、更易用，并邀请读者查看readme或在线试用。

## 6. 抖动二维码：原理、生成与实用技巧

- 原始链接: <https://www.andrewt.net/dithered-qr-codes/wtf/>
- 英文标题: Dithered QR codes

本文介绍了如何在保持二维码可扫描的前提下，用抖动（dithering）技术把图片嵌入二维码，使其更具美观性。作者首先解释二维码的基本结构：功能图案用于定位，必须清晰；数据模块用于存储数据，可以稍作修改。一种常见做法是把每个数据像素缩小成九宫格中心的一个小方块，其余空间用于显示图片，从而形成低分辨率、一位色深的图片。随后文章介绍了两种抖动方法：Bayer 抖动通过规则棋盘格产生中间色调；Floyd-Steinberg 误差扩散则把量化误差扩散到周围未处理的像素，使整体亮度更准确，图案也更自然。作者进一步提出对二维码的数据模块也进行误差扩散：第一轮先预置这些模块的固定颜色，并把误差传递给周围像素；第二轮再正常抖动整幅图，从而显著减少二维码数据模块带来的椒盐噪声。文章还提到一个生成工具，支持旋转二维码、调整编码设置，甚至允许少量修改数据模块以改善外观，但这会降低纠错能力。最后提醒，美观与可扫描性是权衡；打印在纸张上、在恶劣光照下可能难以扫描，且二维码需要留白边，缩放时要避免浏览器模糊。

文章反驳了近期一种流行观点：LLM擅长写代码，但软件开发中真正的难点是“弄清楚要构建什么”，编码本身很容易。作者认为这种说法是对程序员的严重侮辱。他通过一系列反问质疑：如果编码容易，为何程序员长期高薪、高压、过劳？为何有《代码整洁之道》《程序员修炼之道》等经典著作？为何卡马克、费边·贝拉尔被视作天才？为何软件仍充满缺陷？同时，他也反驳“弄清楚要构建什么才是难点”的观点，指出产品经理、市场研究员、业务分析师并未因此获得更高地位或认可。他还批评了另一种陈词滥调，即“软件开发主要是与利益相关者沟通”，现实中很少有程序员喜欢这样做。文章强调，优秀代码本身是一项需要技能、耐心、经验和智慧的技艺，而理解用户需求同样重要，应当两者兼顾。面对AI带来的行业剧变，不应沉溺于“代码容易”或“代码不可自动化”的自我安慰，而应主动适应变化：保持好奇与批判，学习相邻领域知识，资深开发者可学习用户体验、客户访谈等，初级开发者应夯实底层原理如指针、递归、算法。最后作者提醒，不要把自己的理解、判断、同理心和品味外包给AI。

- 英文标题: my server is a phone now

作者讲述了自己用一部 CMF Phone 1 手机替代 Hetzner VPS 运行个人基础设施的经历。起因是不满 VPS 的性价比，而手机已有 8 核 ARM CPU、8GB 内存、128GB 存储、Wi-Fi 6 和电池，闲置可惜。最初尝试刷入 postmarketOS 失败导致软砖，恢复后改为保留 Android，以 Termux 作为宿主环境，并用 runit 管理服务、Tailscale 提供稳定网络、Cloudflared 隧道解决入口问题。应用原本通过 proot 运行 OCI 镜像，但性能不佳，最终 root 后改用 chroot 直接挂载 Debian 文件系统，大幅提升性能。整套配置用 Ansible 管理，发布流程带版本校验、健康检查和回滚，机密通过 1Password 派生。HTTP 服务走 Cloudflare Tunnel，Surf 远程浏览器则用 WebSocket 包裹 TLS 以兼容老 iPad。最终手机稳定运行 Surf、个人财务追踪等应用，且支持移动场景。作者认为对于已有闲置可 root 手机的人，这是比购买 VPS 更省钱、更实用的方案，但提醒需要离机备份，且 chroot 并非安全隔离边界。

## 11. 重访日期计数：改进的格里高利历转日数算法

- 原始链接: <https://dotat.at/@/2026-08-09-rata-die.html>
- 英文标题: Counting the days, revisited

本文回顾并改进了将格里高利历日期转换为儒略日数（或类似线性计数）的算法，该算法是C语言mktime()函数的核心。作者旧版本代码中使用了y*1461/4等表达式，但Ben Joffe指出这种写法在年份很大时会导致乘法溢出，且现代CPU上并不更快。改进后的核心公式为：y*365 + y/4 - y/100 + y/400 + m*979/32 + d - 336，其中月份和年份先经过调整，使1、2月视为上一年的年末，从而利用从3月开始重复的5个月长短模式。文章详细解释了各部分含义：儒略年计数、格里高利修正、月份模式、纪元偏移，以及适用范围。作者还讨论了有符号除法截断问题，建议使用u32以避免负数年份带来的错误，并可通过加减400的倍数扩展至负数年份。此外，文中介绍了新的快速闰年测试（先判%25再判%4或%16），以及计算每月天数的巧妙表达式，如30|(m^(m>>3))，它仅用两条ARM指令即可实现，比作者之前的乘法取模方案更简洁高效。整体展示了算法优化中的关键技巧和编译器优化细节。

## 17. Triton：为 QEMU 打造的 DirectX 11 驱动

- 原始链接: <https://blog.getutm.app/2026/introducing-triton-directx-11-driver-for-qemu/>
- 英文标题: Triton: DirectX 11 driver for QEMU

本文介绍了 Triton，一个全新的 Windows 图形驱动程序，它与此前开发的 Neptune 协议配合，为 QEMU 虚拟机带来完整的 DirectX 11 硬件加速支持。文章解释了为何不能像 Wine 那样通过替换 d3d11.dll 和 dxgi.dll 来拦截 API：这会导致性能差（DWM 需 CPU 拷贝）、系统组件不可替换、反作弊检测等问题。正确做法是实现 Windows 的 DDI（设备驱动接口），即用户态驱动（UMD）和内核态驱动（KMD）。Triton 的 UMD 将 DDI 调用逆向转换为 DirectX API 调用，从而复用 Neptune 的序列化协议传输到宿主机，减少了一层转换开销。关键挑战是 DXBC 着色器字节码：DDI 只传递 SHDR 部分，Triton 需要重建完整的 DXContainer 元数据。宿主机渲染方面，作者放弃了原先宿主机端交换链方案，改为在 guest 驱动中实现共享纹理的导入导出。针对 macOS 宿主，文章比较了 DXVK+MoltenVK 与 DXMT 两条路径，并探讨了跨进程共享 Metal 纹理与围栏的方案，包括 MTLSharedTextureHandle、IOSurface、CALayerHost 以及基于 shm_open 的新思路。

## 18. Arch Linux 脚本与钩子机制解析

- 原始链接: <https://devblog.archlinux.page/2026/on-scripts-and-hooks/>
- 英文标题: On Arch Linux scripts and hooks

本文基于对约120个软件包源码仓库的研究，探讨Arch Linux包管理器（pacman/alpm）中两种用于处理非包文件数据（如系统集成、用户组创建、缓存管理等）的机制：alpm-install-scriptlet（安装脚本）与alpm-hooks（钩子）。安装脚本是包含在软件包中的shell脚本，通过预定义函数在单个包安装、升级或移除前后运行，可访问新老版本号，但存在样板代码多、运行顺序依赖包管理器、无法声明运行时依赖等问题。钩子则是声明式文件，在整批事务前后执行，支持基于包或路径变化触发，可由系统管理员配置，更易测试，但缺少版本上下文。文章列举了常见用例：钩子常用于清理缓存、通过sysusers.d/tmpfiles.d创建用户和文件、生成缓存、迁移数据或重启服务；安装脚本常用于显示版本升级相关提示或管理systemd单元。最后指出，当前Arch Linux两者并用，钩子更现代、声明式、可测试，但脚本仍因其版本感知能力而不会消失；建议尽可能减少脚本中的自定义代码，并扩展文档帮助维护者选择。

## 21. systemd 动态用户（2020）

- 原始链接: <https://ethulhu.co.uk/systemd-dynamicuser>
- 英文标题: Systemd Dynamic Users (2020)

本文介绍了 systemd 的动态用户（Dynamic User）特性。传统上，Linux 创建用户需要写入 /etc/passwd 和 /etc/group，而 systemd 通过名称服务开关（NSS）可以只在单元运行时动态创建用户，单元结束后用户随即消失，无需持久化用户记录。该用户虽是完整 Linux 用户，但默认权限受限，可加入辅助组、写磁盘或获得能力。配合 StateDirectory，可在单元结束后保留数据目录，并在下次运行时自动修正属主，适合存储服务数据或模拟家目录。动态用户的实用价值在于简化服务打包和运行：无需在安装时创建用户、卸载时删除用户，服务包只需包含 service 文件即可。文中给出两个示例：一个 Web 服务使用 DynamicUser=yes、Group=www-data、RuntimeDirectory 和 StateDirectory 实现运行时用户与数据目录；另一个 Kodi 媒体中心示例展示如何通过 DynamicUser=yes、User=kodi、SupplementaryGroups 和 StateDirectory 运行图形程序。最后，作者展示了如何将 Steam 沙箱化：创建专用组 eth-x11，通过 xhost 授权该组访问 X11 显示，再利用 systemd-run 以动态用户身份启动 Steam，并附加 audio、input、video 等组，设置 StateDirectory 和 HOME、DISPLAY 环境变量。文章指出 systemd-run 需要 root 或向 systemd 认证，可通过 sudoers 或 setuid 改善体验。

## 22. 多栈连接式编程语言

- 原始链接: <https://www.sheeeeeeeep.art/multistack-catlangs.html>
- 英文标题: Multistack Concatenative Programming Languages

本文探讨连接式编程语言（catlangs）中的多栈设计。连接式语言以“并置即组合”为原则，通过数据栈和隐式调用栈实现无点组合；引用机制可将代码块作为数据处理并执行，从而支持高阶编程。然而数据栈管理易产生“只写”代码，词法变量虽缓解压力却破坏组合性，因其作用域嵌套而无法通过连接分解。为此，非词法绑定（如 Factor 的命名空间栈、PostScript 的字典栈）和多个命名栈成为研究方向。文章展示了命名栈操作（>x、x>、@x、=x），可模拟嵌套作用域并支持动态上下文。Mirth 通过栈标签和线性类型实现强约束，在 C 生成阶段可将命名栈消除为局部变量。命名栈还能替代闭包对象，StackTalk 和 Kit 将对象建模为命名栈集合。经验表明，catlangs 的栈应职责单一：Factor 的 retain 栈既用于 dip 又复用为词法绑定，导致 fried quotations 与词法绑定冲突，建议设独立词法变量栈。文章最后列出 Dawn、Mirth、Nova、StackTalk、Kit 等项目，它们正在探索多栈高级连接式语言。

## 1. Yap：LLM代码中一种典型的「废话注释」

- 原始链接: <https://mckayla.blog/posts/yap.html>
- 英文标题: Yap: a particular kind of slop

作者是一名负责审查大量LLM生成代码的工程师，提出并定义了「yap」这一概念，用以指代LLM在代码中生成的冗长、空洞、缺乏实质信息的注释。文章首先指出写代码注释本身极难，且注释不像代码那样有编译器校验，容易过时或失准。随后作者讨论了用LLM审查LLM代码的不可靠性——「如果一个机器人认为某事是好主意，凭什么相信第二个机器人品味更好？」在此基础上，作者将沟通分为两个层次：「talking」（真正为让他人理解而表达）和「yapping」（为说而说，并不期望被理解）。LLM的「推理」过程本质上就是自我独白式yapping，问题在于它们无法把这种独白收起来，而是将其大量输出为代码注释。作者列举了典型yap表现：在简单类型定义上写30行注释、在文件顶部堆砌50行不知所云的说明、注释只是复述prompt而非描述代码实际行为、注释位置严重错位等。作者将过去需要写几十条礼貌审查意见的场景浓缩为一个词「yap」，其含义是：退后一步思考这条注释是否真正提供了非显而易见的价值、是否放在了正确位置、是否根本不需要。文章最后呼吁将这类问题模式命名并文档化，甚至希望AI公司将其纳入训练数据，使「yap」成为软件工程通用词汇，从而提升审查效率。

## 2. OpenOffice 周二无法打印之谜（2009）

- 原始链接: <https://beza1e1.tuxen.de/lore/print_on_tuesday.html>
- 英文标题: OpenOffice does not print on Tuesdays (2009)

本文讲述了一个颇具戏剧性的 OpenOffice 打印故障：部分用户发现 OpenOffice 在周二无法打印，其他应用则正常。一位用户在周四卸载重装后问题解决，但两周后的周二问题复现；另一位 Ubuntu 开发者的妻子也抱怨同样现象，却因「今天是周三」而无法当场复现，令人忍俊不禁。最终排查发现，问题根源在于 Unix 下的「file」命令。该工具通过模式匹配识别文件类型（超过 1600 种），OpenOffice 生成的 PostScript 文件头部会写入创建日期，周二时格式为「%%CreationDate: (Tue MMM D hh:mm:...)」。而「file」命令中 Erlang JAM 文件的匹配模式存在缺陷：模式字符串「4 string Tue Jan 22 14:32:44 MET 1991 Erlang JAM file - version 4.2」中的空格未用反斜杠转义，导致 PostScript 文件中的「Tue」被误判为 Erlang JAM 文件，文件因此未被送往打印机。修复方法是在模式中的空格前添加转义反斜杠。文章指出，面对上千种文件类型的匹配规则，模式书写错误和匹配顺序不当造成误判并不罕见。

## 3. 追寻永恒的 Wayland 桌面 Dock：lambdock（C + GTK4 + GNU Guile Scheme）

- 原始链接: <https://jointhefreeworld.org/blog/articles/gnu-linux/quest-for-eternal-dock/index.html>
- 英文标题: Quest for eternal dock on Wayland - lambdock (C + GTK4 + Lisp GNU Guile Scheme)

本文讲述了开源项目 lambdock 的开发历程——一个 Wayland 原生的桌面 Dock 应用，采用 C + GTK4 + gtk4-layer-shell 作为高性能渲染核心，并嵌入 GNU Guile Scheme 引擎充当运行时「大脑」。作者回顾了大量失败原型（纯 Lisp、Python+GTK、Rust+GTK、Node.js+Layer Shell），最终确定 C 负责底层渲染与 Wayland 协议交互，Guile 通过 libguile.h 双向绑定提供无限可扩展性。lambdock 支持多 Dock 实例的动态生成、热重载与销毁，通过监控配置目录中的 Scheme 文件实现；提供 Unix domain socket REPL，可经 Emacs Geiser 或 socat 等工具实时查询和修改运行中 Dock 的状态，无需重启。项目已上游至 GNU Guix 和 Nixpkgs，并覆盖 openSUSE OBS、Debian/Ubuntu、Arch Linux 及 OCI 容器分发。作者总结三条经验：拥抱 C/GTK4 平台以获得速度与可靠性、Lisp 是最佳扩展引擎、不满足于「够用」而持续迭代。

## 4. 一周内将 Rustdoc 提速 33% 的优化实践

- 原始链接: <https://noahlev.org/blog/2026/08/27/making-rustdoc-faster/>
- 英文标题: How I made Rustdoc 33% faster in one week

Rustdoc 团队成员通过四个 PR 将 Rustdoc 平均 wall-time 降低 25%（即 33% 加速），在 hyper 等真实 crate 上达 40%，微基准测试达 60%。起因是发现 beta 版 Rustdoc 对含 recursion_limit 属性的 crate 报错而 Rustc 正常，排查时定位到 build_extern_trait_impls 阶段遍历整个依赖图的所有 trait impls 极为昂贵。作者将过滤逻辑提前到 build_impl 调用之前，仅对真正需要展示的 impl 执行构建，带来 20% 加速和 12% 内存下降，并顺带修复了 notable trait 提示的潜在 bug。随后两项优化分别针对 primitive 类型（改为仅处理本地 primitive，省 12%）和 synthetic impls（仅分析文档中可见类型，省 6%）。最后一项通过避免对非内联 impl 调用 param_env 查询、仅检查 self type 的 head 部分，再省 18%。作者强调核心经验是：结合火焰图等实证数据，敢于质疑长期存在的代码假设，直觉驱动的深度排查往往能发现重大性能机会。改进已合入 nightly，将于 Rust 1.99 进入 stable。

## 7. 用GADT风格枚举在Rust中实现零开销的「Tagless Final」

- 原始链接: <https://inferara.com/blog/rust-tagless-final-gadt/>
- 英文标题: Zero-Cost 'Tagless Final' in Rust with GADT-style Enums

本文探讨如何在Rust中实现「Tagless Initial」编码（Tagless Final模式的一种变体）并验证其零开销特性。该模式用GADT将表达式与其结果类型绑定，使同一接口可对接求值、打印、优化等多种解释器。作者利用Rust的never类型（!）构造Gadt风格枚举：通过Attic和Cursor两个trait在类型层面控制枚举变体的可构造性，使任意给定类型签名下仅一个变体合法，从而在编译期消除运行时标签。eval函数本质是递归match，但编译器已知唯一可达分支，整个表达式树被完全展开。Release模式汇编显示，复杂的lambda、apply、add调用最终优化为几条leaq和addq算术指令，无解释循环、无动态分发、无内存分配。作为对照，将!替换为零大小类型((),)后，编译器无法确定活跃变体，汇编退化为含显式eval调用的运行时解释。作者强调，never类型方案在构造层面保证优化，比依赖#[inline(always)]等编译器启发式更可靠，为在Rust中构建高性能嵌入式DSL提供了可行蓝图。

## 13. SimCity 完美城市的算法逆向与反直觉策略

- 原始链接: <https://www.jeffquast.com/post/a-perfect-simcity/>
- 英文标题: A Perfect SimCity

## 20. 变更检测测试之害（2015）

- 原始链接: <https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html>
- 英文标题: Change-Detector Tests Considered Harmful (2015)

本文是Google测试博客「Testing on the Toilet」系列的一期，由Alex Eagle撰写，主题围绕「变更检测测试」（change-detector tests）的危害展开。所谓变更检测测试，是指测试代码的内部实现细节（如验证某个方法是否被调用、参数是否匹配）而非验证其外部行为，一旦实现重构，测试即失效，但代码功能可能并未改变。文章的核心观点是：这类测试增加了维护成本，阻碍安全重构，应尽量避免，转而测试公共API的行为。评论区进一步讨论了该话题：有读者指出，在高度面向服务的系统中，有时难以完全避免编写验证函数调用关系的测试，将其作为快速建立信心的手段；另一读者则反驳称，若测试中mock了所有依赖，即使内部实现被彻底替换，测试仍会通过，但实际功能可能已损坏，因此变更检测测试既不能提供真正的信心，也无法帮助安全重构，还会降低代码可读性，不利于他人理解。文章本身正文信息有限，主要观点通过标题和评论得以体现，整体立场是倡导测试行为而非实现。

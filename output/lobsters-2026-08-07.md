## 3. Python 字符串字面量的古怪之处

- 原始链接: <https://sebsite.pw/w/20260806-pystrings.html>
- 英文标题: python string literals are kinda funny

文章从一个小测验引出 Python 字符串字面量的怪癖：r'asdf\' 是语法错误，而 r'asdf\'' 合法，得到的字符串内容是 asdf\'。原因是原始字符串字面量虽然不解释反斜杠转义，但词法分析规则与普通字符串相同，因此字符串不能以反斜杠结尾，否则后面的引号不会被当作结束符。作者指出这最初是为了简化实现。随后文章展示 f-string 更滑稽的解析行为：f'{'}'}' 合法并输出 '}'；f'{67#}...}' 也合法，输出 '67'。这是因为词法分析 f-string 时，需要对花括号内的表达式调用完整的 Python 解析器；表达式可以包含引号、跨行甚至注释，只有未加括号且未被注释的 }、! 或 : 才会结束表达式。于是 lambda 表达式和海象赋值在 f-string 内都必须加括号，例如 f'{lambda: 67}' 是语法错误，而 f'{x := 67}' 相当于 f'{x}'。文章通过这些例子说明，这些看似奇怪的行为都源于实现方式，读来既有趣又揭示了 Python 词法/语法解析的深层机制。

## 5. 薛定谔的TOCTOU：你运行的二进制并非你编写的程序

- 原始链接: <https://github.com/xoreaxeaxeax/schrodingers-toctou>
- 英文标题: schrodingers-toctou: The binary you run is not the program you wrote

文章揭示了编译器优化可能引入“发明式加载”（invented loads），导致原本看似安全的C代码在编译后产生TOCTOU（检查时间到使用时间）漏洞。即使程序员采用“快照、验证、使用”的标准防御模式，编译器仍可能从原始共享内存中重新读取攻击者可控的值，使验证与使用不一致，从而凭空产生缓冲区溢出等安全问题。作者通过示例演示了同一行源代码在不同编译器、架构和优化标志下可能安全或可被利用，形成一种“叠加态”漏洞，只有实际构建后才会塌缩为真实威胁。文章进一步指出，该问题源于多阶段编译器优化流水线的复杂交互，而非单一阶段错误，且难以通过静态检查预防。研究发现，在QEMU、Linux内核、edk2、seL4、SGX等100多个安全关键项目中存在300多个此类“薛定谔TOCTOU”，可导致虚拟机逃逸、内核提权、固件持久化攻击等严重后果。作者尝试了volatile、READ_ONCE、barrier等常见防御手段，但均存在局限，无法根治问题。最终建议借助自动化审计工具分析信任边界，识别可能被编译器重新读取的模式，并提醒开发者：此类漏洞很可能也存在于自己的代码中。

## 6. 品味是仅存的

- 原始链接: <https://notashelf.dev/posts/taste-is-all-thats-left>
- 英文标题: Taste Is All That's Left

文章认为，AI生成代码让软件开发中从想法到成品的摩擦几乎消失，而这种摩擦过去既是成本过滤器，也是培养品味的课程。品味不是审美偏好，而是先于理性的直觉判断，像Pirsig所说的“质量”：你认得出它，却说不出为什么。品味来自反复制作糟糕的东西并被迫与之共处，不是靠消费好作品就能获得。当工具免费供给“足够好”的代码，新手绕过了学徒期，能生成一切却无法判断什么值得存在。更糟的是，市场只测量速度，品味缓慢、不可见、不会出现在diff中，因此有品味的人反而在指标上吃亏。作者把AI生成的中等代码比作工程上的“胡扯”——它无所谓对错，只是漠然。过去90%的废话受制造成本限制，现在噪音免费且无限，真正的稀缺从制作转向选择：决定哪些生成物值得保留。正如工业革命后工艺美术运动提出的问题，当制造免费，“应该被造出来吗”成为核心。品味没有贬值，只是被剥去所有伪装，成为唯一稀缺、不可自动化、不可测量的能力，也是人类最后的裁判权。文章最终主张，即使外部不奖励，也要在“还行”和“正确”之间拒绝前者。

## 9. Rust 官方仓库采用大语言模型使用政策

- 原始链接: <https://blog.rust-lang.org/inside-rust/2026/08/05/rust-langrust-is-adopting-an-llm-policy/>
- 英文标题: rust-lang/rust is adopting an LLM policy

2026年8月5日，Rust 项目的五个团队正式通过了一项由作者 Jynn Nelson 起草的大语言模型（LLM）使用政策，适用于 rust-lang/rust 单一仓库。该政策并非对 LLM 的官方立场，也不覆盖整个 Rust 项目，旨在解决 LLM 贡献带来的三个主要问题：精美的技术产物不再代表付出和理解、写代码更容易加剧了本就紧张的审查带宽、机械地在 LLM 与 GitHub 之间复制粘贴浪费大家时间。政策核心原则是：可以使用 LLM 来回答问题、分析、提炼、检查、建议和审查，但禁止用其“创造”内容。LLM 生成的内容必须明确披露，且此类代码变更需满足比人工代码更高的标准，例如必须附带测试；涉及健全性关键部分的变更严禁由 LLM 生成，除非作者本身是领域专家。政策还规定，审查者可以关闭不符合政策的 PR，但不得仅凭风格指控他人使用 LLM；骚扰无论何种情形都不被允许。作者强调，制定政策并非为了惩罚，而是为社区提供清晰、公开的规则，同时收集数据以指导未来调整。该政策目前仅适用于 rust-lang/rust 仓库，但作者希望未来能有覆盖整个项目的更广泛政策。

## 13. Futhark终于支持递归函数

- 原始链接: <https://futhark-lang.org/blog/2026-08-05-recursion.html>
- 英文标题: Finally adding recursive functions to Futhark

文章介绍了Futhark语言从最初不支持递归到最终实现递归支持的过程。Futhark作为面向GPU的数据并行纯函数式语言，一直避免递归，因为GPU线程栈极小且无法动态分配内存，非尾递归会带来不可预知的内存需求。作者通过flattening技术解决了这个问题：将递归调用提升到CPU端，GPU只执行扁平的并行操作，从而在保证正确性的前提下支持递归，尽管性能可能较差。实现中遇到的主要挑战包括：类型检查器需支持size-polymorphic递归（但禁止类型参数多态递归）；高阶递归函数可能因无限特化而失败，因此规定递归调用必须传递与定义相同的高阶参数；lambda lifting可能引入互递归，但可被现有流程处理。目前递归支持已合并到编译器中，但默认未启用，需通过环境变量或特定分支实验。作者提醒，flattening生成的代码可能效率低下，且递归会消耗大量内存，未来还需要新的编程构造来更高效地利用递归。文章也提到，缺少递归虽未影响大多数数组编程，但递归分治算法表达更自然。整体而言，这是对Futhark历史性功能添加的技术总结。

## 20. Zig 的 Io.Threaded 很巧妙

- 原始链接: <https://matklad.github.io/2026/08/06/neat-io-threaded.html>
- 英文标题: Zig's Io.Threaded is Neat

文章介绍了 Zig 新的 Io 接口的线程实现 std.Io.Threaded，它基于普通阻塞系统调用，却完整支持取消操作。作者认为这个实现很巧妙，因为它解决了长期困扰他的难题：如何让标准 OS 线程上的阻塞调用可被可靠取消。作者区分了并发与并行：并行是确定性的声明式任务拆分，而并发必然涉及取消——当某个计算得知另一计算无法完成时，需要主动取消它，而不是傻等。传统“只用线程”方案缺乏取消能力，因为线程阻塞在内核系统调用中，语言 API 通常无法解除阻塞。Zig 的 Io.Threaded 在 POSIX 上利用信号机制：取消方在共享内存中设置标志，并反复向目标线程发送信号；目标线程收到 EINTR 后检查标志，决定重试系统调用还是确认取消并展开错误处理。用户侧取消表现为 error.Canceled。Windows 上则直接使用 NtCancelSynchronousIoFile。作者对比了类似机制：Java 的线程中断无法中断系统调用，IO 异常与中断异常分离；pthread_cancel 虽然类似，但未与语言级取消（try/defer）集成，清理繁琐，且销毁整个线程不适合线程池。Zig 的 Io 接口巧妙地在接口层区分 io.async（异步）与 io.concurrent（并发），后者由线程池支持，并具有更精确的错误签名。

## 1. Firefox成为唯一仍支持uBlock Origin的主流浏览器

- 原始链接: <https://www.pcworld.com/article/3212428/firefox-is-now-the-last-major-browser-that-still-supports-ublock-origin.html>
- 英文标题: Firefox is now the last major browser that still supports uBlock Origin

文章报道了Firefox官方在Bluesky上宣布将继续支持uBlock Origin，回应了Microsoft Edge即将禁用基于Manifest V2架构的广告拦截扩展的消息。Edge基于Chromium内核，而Chromium项目在Google主导下已从Manifest V2迁移到V3，导致广告拦截扩展无法获得有效识别和屏蔽广告所需的功能。目前大多数主流浏览器（如Chrome、Edge、Opera、Brave等）都基于Chromium，因此均受影响。Firefox是少数非Chromium内核浏览器之一，如今成为唯一支持uBlock Origin的主流浏览器。其他非Chromium浏览器如Safari和DuckDuckGo也不支持uBlock Origin。对于依赖uBlock Origin的用户，Firefox成了唯一无需妥协的选择；在其他浏览器上只能使用功能较弱的uBlock Origin Lite或内置广告拦截功能。文章还引用了用户评论，强调Firefox对uBlock Origin的支持是其决定性优势。

- 英文标题: Why I remain a skeptic

## 3. 压缩就是预测吗？——等价性的边界

- 原始链接: <https://lukefleed.xyz/posts/compression/>
- 英文标题: How Is Compression Prediction?

文章围绕“压缩即预测”这一常见说法展开。作者认同在概率模型与熵编码框架下，预测与压缩确实数学等价：给定模型Q，编码长度等于累积对数损失，改进预测与减少比特数是同一优化问题。但作者强调，这种等价需要严格的前提条件，压缩问题在应用概率模型之前早已开始，在产生最短比特流之后也未必结束。文章首先从压缩先于概率的视角出发，介绍Kolmogorov复杂度描述单个对象的最短程序但不可计算，而有限对象族可给出无需概率的计数下界log|F|。随后引入信息含量、熵与Kraft–McMillan不等式，说明任意唯一可解码码都能诱导一个概率分布，反之概率也决定理想码长。接着探讨“何时压缩变成预测”：编码器与解码器必须事先约定对象类型、可行替代集合、模型如何共享，以及解码后需支持哪些操作（如随机访问）。作者还指出，源未知时模型本身可能是消息的一部分，而最短比特流未必是合适的表示。最终结论是：压缩与预测可以数学等价，但该等价只度量完整表示中的一部分成本，不能覆盖所有压缩问题。

## 4. RISC-V：他们本应更明智

- 原始链接: <https://dmitry.gr/?r=06.%20Thoughts&proj=12.%20RV>
- 英文标题: RISC-V: They Should Have Known Better

本文作者系统阐述了对RISC-V指令集架构的强烈批评。作者认为，RISC-V号称适用于从超算到微控制器的所有场景，但这是不可能的，因为高端CPU与低成本嵌入式核心的需求根本对立。在嵌入式领域，作者对比了RISC-V与Cortex-M0的中断处理开销：RISC-V需要至少44个周期完成中断进出，而Cortex-M0仅需27个周期，即便采用RV32E也仍慢三分之一以上。压缩指令扩展同样设计糟糕，字节和半字存储的偏移范围极小，且相关指令被放在可选的Zcb扩展中。对高性能核心而言，RISC-V缺乏数组寻址模式，必须用多条指令组合，Zba扩展直到2021年才被批准，且只能将三条指令减为两条，代码密度仍不如ARM。作者还猛烈抨击了RISC-V的“可选性”泛滥：乘法、除法、特权模式、CSR、压缩指令等统统可选，导致标准名存实亡；连用于检测特性的misa寄存器本身也是可选的，且允许读为全零，客户代码无法可靠识别硬件能力。作者讽刺这种设计委员会式的工作方式，并提到高通曾提议改进编码空间却无果。由于正文在此处截断，未能看到作者对RISC-V是否注定失败的最终结论。

## 5. Flirt 开发进展：GitHub 与邮件列表后端

- 原始链接: <https://blog.buenzli.dev/flirt-github-and-mailing-list/>
- 英文标题: Flirt: GitHub and Mailing List backends

本文是代码审查工具 Flirt 的开发更新。作者完成论文后，为 Flirt 实现了 GitHub 和邮件列表后端，但功能仍有限且有缺陷。目前 Flirt 将所有数据本地存储，仅在同步时转换为 API 调用或邮件。GitHub 后端的主要问题是无法获取 PR 历史强制推送信息，因此难以展示所有提交版本间的差异；注释只能加在 diff 右侧，对左侧删除行注释的定位仍需解决。邮件列表后端仅支持使用 public-inbox 的项目，且依赖 git format-patch 输出，但该格式缺少基础提交信息、Jujutsu change-id 等关键元数据，导致 Spirits 版本关联只能靠启发式匹配。作者决定优先支持将每个新版本系列作为对上一版本首封邮件的回复的约定，并指出 Linux 内核文档反而建议避免此做法，引发了对工具适用性的反思。解析邮件中的评论线程较为复杂，目前仅支持简单场景；发送评论邮件尚未真正实现，而是通过 public-inbox-mda 导入本地测试实例。作者计划在一到两个月内将 Flirt 开源，以便早期贡献者参与开发，并预告将参加 JJ Con。

## 6. Serokell 的 GHC 工作：依赖类型（第五部分）

- 原始链接: <https://serokell.io/blog/serokell-s-work-on-ghc-dependent-types-part-5>
- 英文标题: Serokell’s Work on GHC: Dependent Types, Part 5

本文是 Serokell GHC 团队关于在 Haskell 中实现依赖类型的第五期进展报告。报告介绍了三项主要成果：其一，在 GADT 中支持可见 forall（Visible forall），即允许数据构造器把类型作为可见参数，例如 `Typed :: forall a -> a -> T a`，这需要重构构造子模式的 AST、更新类型检查器与 Core 表示，为未来完整依赖类型扫清语法与表示障碍；其二，实现命名空间指定的导入/导出（namespace-specified imports），支持 `type ..` 与 `data ..` 通配符，帮助区分类型命名空间与数据命名空间，并修复了若干历史遗留 bug；其三，经过十年努力，终于让 GHC 在 kind 检查阶段按需发现开放类型族实例，不再受源码声明顺序影响，解决了一长串相关 issue。算法采用带 SCC 的试错式迭代：按词法依赖排序，跳过受阻、有缺陷或失败的组，直至成功或报错。这些进展让 Dependent Haskell 更接近实用。

## 7. ActivityPub因乏味而胜出

- 原始链接: <https://o.ee/blog/activitypub-won-by-being-boring/>
- 英文标题: ActivityPub Won by Being Boring

本文报道了Evan Prodromou在FediForum 2026上的演讲，核心观点是ActivityPub成功的关键在于其核心设计刻意保持普通和务实。它仅约定各独立网络交换活动数据，而不统一数据库、审核模型或界面，依靠HTTP、JSON、URL、收件箱和发件箱等常见Web机制实现联邦。这种“无聊”让任何Web工程师都能理解并实现，因此得以普及。文章也指出协议积累的怪债，如广泛使用已过期的HTTP签名草案，以及缺少端到端加密，实例管理员成为信任边界。治理方面，去联邦化是粗糙但必要的防御机制，而W3C共识过程缓慢但保障互操作。Prodromou认为，真正的胜利标准是出现两个以上数亿用户的商业网络通过ActivityPub联邦，同时警惕大型平台将规模转化为标准话语权。当前W3C新工作组正进行向后兼容的维护修订，并考虑LOLA账户迁移提案，以保护用户免于锁定。未来的挑战不是让协议更聪明，而是在隐私、审核、可移植性和商业规模下保持其“无聊”的实用性。

## 9. nixpkgs-multiverse 快速模式：零求值直接获取历史包

- 原始链接: <https://fzakaria.com/2026/08/14/nixpkgs-multiverse-fast-mode>
- 英文标题: nixpkgs-multiverse: fast mode

文章介绍 nixpkgs-multiverse 新增的 fast 模式。传统上要获取某个历史版本（如 python3 3.8.9），需要下载并求值整个 Nixpkgs 源码树；fast 模式则直接通过索引给出对应的 store path，让 Nix 从缓存中获取，完全跳过 Nixpkgs 的下载与求值，也无需实验特性或 --impure。其核心技巧是 mkFakeDerivation：利用 builtins.appendContext 给字符串附加 store path 上下文，再包装成类似 derivation 的 attrset，从而让 Nix CLI 接受一个尚未存在于本地、也不在本轮求值输入闭包中的路径。该过程仍是纯求值，结果与真实求值比特级一致。文章也提醒了使用注意：fake derivation 没有 drvPath，只能替换不能构建，需显式追加 .out；override 或 nix develop 需通过 .eval 获取真实 derivation；meta 为空。此外，作者对缓存进行了普查：截至 2026 年 8 月 14 日，全部 271,187 个历史版本路径在 cache.nixos.org 上均仍可获取，总计约 14.8 TB 解包软件，可通过 fast 命令随时使用。相关数据也可通过 mvs 命令行工具离线查询。

## 10. 免费午餐已结束：软件向并发的基础性转变（2005）

- 原始链接: <http://www.gotw.ca/publications/concurrency-ddj.htm>
- 英文标题: The Free Lunch Is Over: A Fundamental Turn Toward Concurrency in Software (2005)

Herb Sutter在本文中指出，软件开发者长期依靠CPU性能提升而无需修改代码的“免费午餐”即将结束。过去30年CPU性能增长主要依赖时钟速度、执行优化和缓存增大，但自2003年起，时钟速度因热量、功耗和电流泄漏等物理限制急剧放缓，Intel甚至放弃了4GHz计划。处理器厂商因此转向超线程和多核架构，2004年被称为多核元年。然而，多核并不等于线性加速：2个3GHz核心并非6GHz，核心间存在缓存一致性等协调开销，而且单线程应用只能使用一个核心，难以获得显著提升。未来几年性能增长主要来自超线程、多核和缓存，其中只有缓存增大对现有应用仍有普遍好处。作者认为，这标志着软件开发的基本转向：并发将成为主流，大多数现有应用需要重新设计才能利用新硬件，软件开发者必须正视这一变革。

## 11. 权力关系：责任、声誉与能力的范畴论分析

- 原始链接: <https://corbinsimpson.com/words/power-relations.html>
- 英文标题: Power Relations

文章将权力重新定义为责任：一个人对另一个人拥有权力，恰因其对该人负有责任。作者用范畴论和层论（stack）为权力委托建模，视权力委托为箭头，并假设传递性成立。分析表明，在时间演化中，委托的持续与撤销具有自然解释，但新委托的创建缺乏自然性，因此无法被唯一确定。由此引出“声誉问题”：一个群体无法通过自然算法为匿名新人分配声誉而不暴露于滥用风险；该问题属于“wicked problem”，不可能化为求解方程式的自然解。文章还讨论了能力（capability）作为可通信、不可伪造的委托令牌，并指出智能合约中常存在责任不对等。最终强调，权力关系应被理解为多重的、可独立委托的责任网络，而初始信任的建立本质上是非自然的。作者引用康威定律与奥曼协议等观点，说明此类社会性权力问题无法简单机械化解。全文融合数学、计算机科学与社会哲学，试图为远程通信型关系中的权力、责任、声誉与礼貌提供结构性解释。

## 12. RVA23与ARMv9的小型对比实验

- 原始链接: <https://gist.github.com/camel-cdr/3a7aed17e017e8cab675ad696c7d14af>
- 英文标题: RVA23 vs ARMv9 a Small Experiment

文章作者设计了一个小型实验，比较RISC-V（RVA22/RVA23）与ARMv9在动态指令数和代码密度上的差异。实验选用chibicc C编译器作为测试负载，让编译器编译自身，并特意禁用了SIMD/向量指令，以聚焦于基础ISA的比较。作者使用QEMU和GEM5进行测量，并针对ARM的加载/存储对及前后索引寻址指令被拆分为微操作（uop）的情况进行了统计调整。结果显示：RISC-V的静态二进制大小比ARM约小18%；动态取指字节数方面，RVA22比ARMv9少21%，RVA23少24%；但ARM的动态指令数平均比RISC-V少6.5%，不过ARM部分指令会被拆分为两个uop，经调整后两家的uop总量大致相当，GCC下RISC-V甚至略优。GEM5模拟显示RISC-V执行时间略快于ARMv9，且GCC二进制快于clang二进制，尽管clang指令/uop数更少。作者指出，QEMU与GEM5的指令数差异可能源于用户态模拟的伪影，并承认无法确定ARM GEM5模型中哪些指令被拆分。最终结论是：在此实验中，ARM和RISC-V后端所需uop数量大致持平；ARM解码指令更少但存在指令拆分，RISC-V依赖压缩指令减少取指字节但解码指令更多；RVA22与RVA23在本测试中差异可忽略，因为主要差异RVV扩展被禁用。

## 23. 潜在推理模型是否易于解释？

- 原始链接: <https://arxiv.org/abs/2604.04902>
- 英文标题: Are Latent Reasoning Models Easily Interpretable?

该论文发表于COLM 2026，旨在评估潜在推理模型（LRM）的可解释性。LRM因其推理成本低且理论上可并行探索多条推理路径而备受关注，但由于推理过程不使用自然语言，难以监控。作者对两个最先进的LRM进行了实证研究，得出三个主要发现：第一，潜在推理token在多数情况下并非必需——在逻辑推理数据集上，即使不使用潜在推理，模型也几乎总能得到相同答案；这暗示token可能未被充分利用，也部分解释了为何LRM未稳定优于显式推理方法。第二，当潜在推理token确实对性能必要时，在正确预测的实例中有65%至93%可以解码出黄金推理轨迹，说明模型通常实现的是预期解决方案而非不可理解的推理过程。第三，作者提出一种无需预先知道黄金轨迹即可从潜在token解码出经过验证的自然语言推理轨迹的方法，并发现多数正确预测可找到已验证轨迹，而少数错误预测则不能。整体结论是：当前LRM在很大程度上编码了可解释的推理过程，并且可解释性本身可作为预测正确性的信号。

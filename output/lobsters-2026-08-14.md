## 1. Python 预声明常量的奇怪行为

- 原始链接: <https://sebsite.pw/w/20260801-pythonconstants.html>
- 英文标题: python's pre-declared constants are kinda weird

本文分析 Python 中六个预声明“常量”：True、False、None、__debug__、Ellipsis 和 NotImplemented 的怪异差异。True、False、None 是关键字，属于词法 token，不是普通标识符，所以 x.True 会报 SyntaxError。__debug__ 是普通标识符，却是全语言唯一不能赋值（含属性赋值）的名字，并有特殊删除错误信息；此外，某些看似非法的语法错误仅在非优化构建中触发，如 assert (__debug__ := 67) 在 -O 下不会报错。Ellipsis 和 NotImplemented 只是普通 builtins，可被全局遮蔽。最有趣的是，虽然 True、False、None、__debug__ 在内建模块中也有条目，且 setattr(builtins, ...) 能修改这些条目，但直接访问不受影响，所以仍是常量；Ellipsis 被修改后直接访问会变，而 ... 不会，造成 Ellipsis 可变、... 恒定的奇怪局面。

## 2. 呼吁 Rust 支持 extern "fil-c"：让 C 代码走安全路径

- 原始链接: <https://domenkozar.com/2026/08/13/i-want-extern-fil-c/>
- 英文标题: I want extern "fil-c"

文章指出 Rust 的 C FFI 存在根本性矛盾：Rust 在编译期保证内存安全，但一旦跨过 unsafe 边界，就不得不信任 C 库遵守一份双方都无法强制执行的契约，遗留 C 代码成为廉价但危险的路径。作者提出 Fil-C 提供了更有意思的选择：它通过能力模型、运行时检查和并发垃圾回收重新编译 C/C++，使内存安全违规变成 panic 而非漏洞，现有代码通常无需或极少改动。作者希望 Rust 能拥有一个讲 Fil-C ABI 的 extern "fil-c" 接口，第一版可只支持标量、拷贝字符串/切片和不透明句柄，生成安全 Rust 包装，并用 Fil-C 编译整个 C 依赖图，不提供回到普通 unsafe C 的逃生口。这样既能用 Rust 获得编译期安全，又愿为使用 C 付出运行时性能代价：保留旧库仍内存安全，但指针操作被检查并参与 GC；用 Rust 重写热路径后检查变成静态，性能税消失。文章还提到 filnix 项目已把 Fil-C 打包为 Nix 交叉编译平台，支持超过 100 个 nixpkgs 包；Zig 也在探索受 Fil-C 启发的可选 fil ABI。作者呼吁跨生态合作，并邀请大家参加明年在兰萨罗特岛的 OceanSprint 共同构建这一桥梁。文中强调“100% 安全”仅限于跨边界的内存安全，不涵盖逻辑错误或死锁，且该桥接必须保持 Fil-C 全程序 ABI 保证，不能悄悄留出 Yolo 风格漏洞。

## 5. 有人不用 PgBouncer 跑 Postgres 吗？

- 原始链接: <https://brandur.org/fragments/postgres-without-pgbouncer>
- 英文标题: Does anyone run Postgres without PgBouncer?

作者回顾十年前撰写的数据库连接管理文章，指出 Postgres 在管理大量连接方面依然不理想，因此连接池化仍是常态。他调研了主流托管 Postgres 提供商，发现几乎所有知名厂商（如 Aiven、AWS、Azure、Google Cloud、Supabase 等）都内置或支持 PgBouncer，只有 IBM Cloud 和 Oracle 不提供托管池化，但这两者实际使用场景有限。作者认为，既然 100% 可行的托管提供商都捆绑了连接池，这说明连接池并非可选的附属功能，而是 Postgres 的核心缺陷导致的必要补丁。每家企业都需自行部署和配置池化层，用户也必须了解 PgBouncer 的限制和模式，造成大量重复劳动。他类比汽车无挡风玻璃的销售场景，批评这种现状。最后，作者提出设想：如果 Postgres 内核能原生支持连接池，用户只需一个数据库 URL 和一个端口，无需额外配置，就能像 MySQL 和 MongoDB 那样开箱即用。尽管这涉及进程与线程的古老争论，推进难度大，但若实现，将是运维层面最具影响力的改进之一。

## 7. 我讨厌为 Linux 打包我的软件

- 原始链接: <https://getfresh.dev/docs/blog/packaging-for-linux/>
- 英文标题: I hate packaging my software for Linux

作者开发了工具 Fresh，希望它能在所有平台上轻松安装，但 Linux 的碎片化让打包成为噩梦。Windows 和 macOS 各有相对统一的方案，而 Linux 必须支持多种渠道：npm、cargo、AppImage、Flatpak、deb、rpm、AUR、nix、mise、homebrew、Terra、Gentoo GURU 等。每种渠道只覆盖部分用户，且都有明显缺陷：npm 有安全隐患且不通用；Flatpak 的沙箱与终端应用不匹配，需用不良参数绕过；AppImage 因 FUSE 挂载启动极慢；deb/rpm 若未进入官方源就无法自动更新，而进入官方源又要求所有 Rust 依赖也打包，工作量巨大；AUR 因安全事件进入只读模式，发布受阻；mise 曾因证书固定问题悄悄失效。作者认为发行版特定渠道不是好方案，随着发行版变体增加，维护成本接近不可承受。下一步计划以静态链接的 musl 二进制为主要发布形式，并内置自更新机制，用户按需触发，成为 Linux 的默认安装方式，同时暂时保留现有包渠道。文章表达了 Linux 打包生态碎片化对独立开发者的沉重负担，并提出了简化的自救思路。

## 8. Tailscale 如何帮助发现 SQLite WAL-Reset 漏洞

- 原始链接: <https://tailscale.com/blog/sqlite-wal-reset-bug>
- 英文标题: How Tailscale helped find the SQLite WAL-Reset bug

Tailscale 在过去数月遭遇了多次数据库损坏事件，导致控制平面间歇性中断。他们以 SQLite 作为主数据库，按分片部署，并定期备份到 S3。从去年8月起，备份中频繁检测到损坏，总计19次，造成部分配置数据丢失和短时停机。由于无法复现，他们与 SQLite 核心开发者合作，部署了定制的调试工具和事务日志，发现一个神秘现象：已提交的数据会在后续事务中消失。最终定位到罕见的竞态条件——checkpoint 过程中特定时机的写入会让 checkpoint 误以为页面已复制到主数据库，实际上并未复制，导致数据永久丢失和文件损坏。该 bug 被命名为 WAL-Reset bug，已存在至少16年，SQLite 在 3.51.3 中修复（3.52.0 曾引入索引误报问题被撤回）。Tailscale 通过日志警告确认修复有效，并连续四个月未再发生事故。他们反思：以非标准方式（如手动控制 checkpoint）运行“无聊技术”存在隐藏风险，并感谢 SQLite 团队的协作与支持。

## 9. 利用DRAM地址加扰解锁CPU全部保护机制

- 原始链接: <https://github.com/xoreaxeaxeax/skitter-creek-bath-salts>
- 英文标题: Unlocking _everything_ on the CPU with DRAM scrambling

本文介绍了一种名为skitter-creek-bath-salts的攻击技术，通过修改DRAM控制器（MCT/DCT）的地址转换寄存器，在运行中重新映射物理内存地址，从而绕过基于物理地址构建的所有安全机制，包括平台安全处理器（PSP）、系统管理模式（SMM）、C6 DRAM省电状态和CPU微码等。攻击基于AMD Family 16h CPU，该代数据手册明确记载了DRAM控制器的转换寄存器且无法锁定；后续世代虽未公开细节，但底层原理可推广至ARM、RISC-V等架构。核心漏洞在于：内存保护机制仅守卫物理地址，而DRAM控制器在最终层将物理地址改写为DRAM坐标，翻转一个控制位（如bank-swizzle模式）即可使同一DRAM单元在畸形视图下产生“别名”地址，从而绕过保护访问秘密数据。攻击难点在于平台运行中重排内存而不崩溃，作者通过禁用AP、预热TLB和缓存、关中断、序列化内存访问等技巧实现瞬时切换。由于地址变换是GF(2)线性映射，作者利用z3求解器，通过投放哨兵值并扫描其重新出现的位置来收集（目标，别名）对，进而求解完整转换矩阵，从而将任意受保护地址转换为可访问的别名。文章展示了详细的汇编代码和线性代数推导，证明仅需一条xor指令即可重写内存映射，并通过数学方法恢复映射关系，最终解锁所有受保护区域。

## 10. C3 0.8.3 特性标志

- 原始链接: <https://c3-lang.org/blog/c3_0_8_3_feature_flags/>
- 英文标题: C3 0.8.3 Feature flags

C3 0.8.3 版本发布，最显著的变化是新增 @feat 属性，用于替代非泛型顶层声明中的 @if，成为顶层条件编译的新方式。旧 @if 因接受任意编译期常量表达式，导致编译顺序不确定和 IDE 分析困难；@feat 基于编译器内置特性标志（如 WIN32、LINUX、BIG_ENDIAN），在声明注册前即可过滤，解决了排序问题。@feat 支持多常量匹配（任一满足即可）、使用 |、&、! 进行逻辑组合，并可用多个 @feat 表示同时满足。同时 $feature 更名为 $feat（旧名已弃用），@if 仅保留用于泛型。此外，0.8.3 引入实验性关键字别名：constdef→constset/cenum、typedef→distinct、faultdef→faultconst/faultset/excuse、attrdef→attrgroup/attrmacro。其他改进包括自动获取 MacOS SDK、支持 Windows Aarch64 目标、标准库新增正则表达式支持、JSON/对象反序列化（json::unmarshal 等）、DateTime 比较运算符、Range 相关方法等。修复涵盖泛型、编译期执行、JSON 解析、AES CTR、RISC-V ABI 等大量问题。

## 12. 论黑客精神

- 原始链接: <https://stallman.org/articles/on-hacking.html>
- 英文标题: On Hacking

本文是Richard Stallman对“hacking”原始含义的阐述。他从2000年在韩国用餐时尝试用六根筷子夹食物的趣事入手，说明“hack”指的是以好玩、聪明的方式去做困难的事，不必实用。他将hacking定义为：带着玩闹的机巧去探索可能性的边界，这类行为具有“hack value”。文章澄清了媒体把hacker等同于安全破坏者的误解，指出真正的安全破坏应称为“cracking”，行为者叫“cracker”。Stallman回顾了MIT在1960-70年代的黑客社群，黑客活动涵盖软件编写、恶作剧、探索校园屋顶和隧道等；他也列举了从John Cage的《4'33"》到各种现代创意恶作剧的众多例子，用以说明hacking的多样性和趣味性。最终他呼吁人们区分hacking与cracking，以纠正大众的长期误解。

## 14. 让他们写RFC

- 原始链接: <https://ohadravid.github.io/posts/2026-08-let-them-write-rfcs/>
- 英文标题: Let Them Write RFCs

作者在开发一个超出自己当前能力的复杂项目时，借助LLM加速，但发现直接让模型写代码会导致自己不理解问题、容易被看似合理的方案迷惑，甚至陷入“LLM幻觉”的恶性循环。为此，他采用了一种新方法：不再让模型直接解答或写代码，而是要求它针对当前模糊的问题撰写RFC（Markdown文件），描述问题定义、解法思路和替代方案。通过反复迭代和追问，迫使自己真正理解问题，也让问题中的缺陷更容易暴露。RFC不同于一般实施计划，它更关注问题本身和方案的总体形态，而非具体细节；写RFC的过程让作者把精力从阅读“垃圾代码”转移到思考和理解难题上。即使RFC看起来不错，最终代码仍可能失败，这时作者会丢弃改动并重新开始。他强调最终仍需阅读代码，没有捷径。文章总结道，这种方法既提高了产出质量，也更令人愉快。标题“让他们写RFC”意在以RFC写作作为LLM交互范式，帮助开发者在复杂项目中建立真正理解。

## 16. 采用CHERI实现内存安全与细粒度隔离

- 原始链接: <https://www.infoq.com/presentations/cheri-memory-safety-compartmentalization/>

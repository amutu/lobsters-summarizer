## 1. nginx2root：五个nginx远程代码执行漏洞与内核提权攻击链

- 原始链接: <https://xint.io/blog/nginx2root-remote-code-execution>
- 英文标题: nginx2root

Xint研究团队披露了名为「nginx2root」的六漏洞组合：五个独立的nginx远程代码执行漏洞（CVE-2026-123007、123634、123633、121810、113425）加一个Linux内核SCTP子系统本地提权漏洞。最严重的CVE-2026-123007自2015年HTTP/2引入（1.9.5）起存在，至1.31.8仍未修复，允许未认证攻击者在启用HTTP/2的服务器上以worker进程权限执行任意命令；结合内核漏洞可获取宿主机root权限，测试中甚至成功逃逸Docker容器。五个nginx漏洞各自独立，影响不同配置，除HTTP/2外还涉及resolver配合动态proxy_pass与mirror指令、HTTP/3转发、邮件代理等场景。修复版本为1.31.9，补丁发布前禁用HTTP/2仅能阻断其中两个漏洞，其余需按配置采取针对性缓解。文章还详细提供了暴露检查命令、攻击痕迹排查方法（连接统计、请求日志分析、worker进程execve审计、异常退出检测）及紧急缓解步骤。发现过程中，CVE-2026-123007由研究者手动发现，其余四个由Xint全自动扫描在数天内定位。

## 2. Java4Shell 反而是使用 Java 的理由

- 原始链接: <https://mccue.dev/pages/11-18-26-java4shell>
- 英文标题: Java4Shell is a reason to use Java

Ethan McCue 在 Java4Shell 漏洞曝光不到一天时撰文，指出该问题源于 JVM 对 Base64 编码的汇编内在化（intrinsic），建议用户先添加 -XX:-UseBASE64Intrinsics 标志，再尽快升级 VM。作者将 Java4Shell 置于近期一系列高影响力安全事件的背景下，强调 AI 作为模糊测试工具大幅降低了发现潜在缺陷的门槛，而漏洞在原生代码中后果更严重、在共享依赖中影响更广泛，Java4Shell 恰好兼具这两点。然而作者随即转折：Java 程序本身是内存安全的，若依赖库需调用原生代码，JVM 会发出警告乃至硬错误，除非开发者显式授权，因此即使依赖树庞大也能精确掌握原生代码暴露面。相比之下，C# 允许任意依赖内联汇编，Python、JavaScript、Go 均通过 C 接口引入原生代码，风险更大。此外，JIT 编译使 Java 性能可与 C 竞争；作者以「周末光线追踪」基准为例，Java 28 值类版本仅为 C++ 的 1.71 倍耗时，已足够让多数场景无需原生扩展。结论是：若担心 AI 挖掘出严重安全漏洞，选择 Java 或 Kotlin、Clojure、JRuby 等 JVM 语言，问题严重性大概率更低。

## 3. Windows 11 暗中收集编码代理与开发工具使用数据

- 原始链接: <https://xusheng.dev/posts/windows-coding-agent-telemetry/>
- 英文标题: Windows 11 collects data on which coding agents and dev tools you use

作者通过逆向工程 Windows 11 的 MissionControlAggregator.dll 发现，该系统组件内置了一份编码代理（codex.exe、claude.exe、copilot.exe、cursor.exe 等）和开发工具（python.exe、dotnet.exe、gcc.exe、code.exe 等）的可执行文件名列表，并通过字符串比较检测用户是否运行过这些程序。组件订阅 KernelProcess.AppStateChangeSummary、Win32kTraceLogging.AppInteractivitySummary 及 WSL 相关事件，将匹配结果以位图形式写入本地状态文件（C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage\），再通过 ETW 的 Segments.SubCohorts 事件上报。作者将 cmd.exe 复制为 codex.exe 运行即触发检测，证明仅凭文件名即可被识别。关键发现是：该报告被归类为「可选诊断数据」，而在美国区域的 Windows 11 安装中，此选项默认开启，数据会被 DiagTrack 服务排队上传至 Microsoft。报告仅记录是否观察到某工具（一个比特位），不包含提示词或源代码内容，但已足以揭示用户的开发工具偏好。用户可在安装时或「设置→隐私与安全→诊断与反馈」中关闭可选诊断数据以阻止上传。

## 7. IPv6 前缀委派：一个异常隐蔽的故障模式

- 原始链接: <https://savyasacheejha.com/posts/why-odhcpd/>
- 英文标题: IPv6 delegation, an unusually subtle failure mode

作者运行一台基于 NixOS 的 x64 自组路由，使用 networkd、pppd、kea-dhcp4 和 blocky 等组件。他发现每次重启 pppd（与 ISP 重新协商）后，Google 的 IPv6 地址无法访问，而 IPv4 正常。排查发现：pppd 重连后 ISP 委派新前缀，但旧前缀未被正确废弃，客户端仍保留旧地址且 preferred lifetime 不为零，导致路由异常。根本原因在于 RFC 9096 要求路由器在上游撤销旧前缀时以 preferred/valid lifetime 为 0 广播，但 networkd 尚未实现该规范（补丁未合并），radvd、dnsmasq、VyOS 同样缺失。最终作者从 OpenWrt 引入 odhcpd，它通过 netlink 直接读取内核状态、无需 ubus，可在 NixOS 上运行，并正确按 RFC 9096 广播 45/90 分钟的 lifetime。实测重启 pppd 后旧地址立即标记为 deprecated，IPv6 连通性恢复。但 iPhone 因休眠错过 RA，约 10 分钟后才切换。作者总结：作为客户端时偏好 systemd 工具，但作为路由器等服务器角色时，应使用 odhcpd、kea-dhcp4、chrony 等专用工具，以覆盖更多边界情况，并强烈推荐 odhcpd 用于家庭消费级 ISP 环境。

## 8. FreeBSD GUS：无界序列安全内存回收机制解析

- 原始链接: <https://gregoire.dev/writing/gus/>
- 英文标题: FreeBSD GUS

本文深入介绍了FreeBSD的GUS（Global Unbounded Sequences）安全内存回收（SMR）方案，该方案也被Apple XNU采用。文章首先阐述SMR在无锁数据结构中的必要性：无锁结构缺乏同步，被移除的对象仍可能被其他CPU访问，因此必须保证内存仅在无人访问时释放。SMR主要分为EBR（基于纪元回收）和QSBR（即Linux的RCU）两大族。GUS属于EBR族，但将传统有界纪元（0/1/2循环）改为全局单调递增的无界写序列，配合全局读序列和每CPU本地序列，通过poll操作检查所有CPU是否已越过目标序列来判定内存可释放。其核心亮点在于与UMA分配器的深度集成：当bucket完全空闲时，分配器推进写序列并标记bucket，后续从depot取bucket时批量poll，利用bucket大小动态调整实现摊销，避免逐对象poll的高开销。XNU在此基础上引入per-CPU「recirculation depot」和延迟推进/提交机制，进一步减少全局原子操作。与RCU相比，GUS实现更简洁、释放到复用延迟更低，但poll在大型NUMA系统上仍可能成为瓶颈，且进入读区需额外fence。

## 9. 用 Maiao 实现堆叠式差异工作流

- 原始链接: <https://entropicthoughts.com/stacked-diffs-with-maiao>
- 英文标题: Stacked diffs with Maiao

本文介绍了 Maiao 工具如何解决堆叠式差异（stacked diffs）工作流与传统代码托管平台（如 GitHub）之间 Pull Request 机制不匹配的问题。作者首先对比两种 Git 工作流：传统方式中每个原子变更对应一个独立分支和多个提交，而堆叠式差异将所有变更集中在一个长期开发分支上，每个提交即代表一个完整变更，合并时通过 cherry-pick 或 rebase 依次复制到上游分支，使历史清晰可读。然而，堆叠式差异与 GitHub 的 PR 模型天然冲突——PR 假设每个分支对应一个变更，手动为每个提交创建分支、推送并设置正确的合并目标极为繁琐。Maiao 通过一条「git review」命令自动完成全部流程：拉取最新上游、rebase 当前分支、为每个提交创建临时分支并推送、通过 GitHub API 创建相互堆叠的 PR、在提交修改后自动更新 PR 描述与合并目标。该工具还支持多开发分支并行、仅对部分提交创建 PR 等场景，核心逻辑是让远端 PR 栈始终与本地提交栈保持一致。作者认为 Maiao 大幅降低了在 GitHub 上使用堆叠式差异的心智负担，几乎在所有场景下都能「做对事情」。

## 10. PyPI 对上传分发包实施更严格的格式校验

- 原始链接: <https://blog.pypi.org/posts/2026-11-18-stricter-checks-for-uploaded-sdists/>
- 英文标题: Stricter checks for uploaded distributions on PyPI

PyPI 近期新增了对源分发（sdist）和构建分发（wheel/bdist）的上传校验，旨在减少解析器差异（parser differentials），提升 Python 打包生态的安全性。文章指出，tar 与 ZIP 格式并非为 Python 打包设计，其宽松解析在本地场景尚可接受，但在网络分发环境中，不同解析器对同一归档的解读差异可能被攻击者利用，导致用户安装看似合法实则恶意的包。具体变更包括：拒绝使用 V7 风格 tar 归档的源分发，以及拒绝包含可能被误读为 ZIP 控制结构的归档级 ZIP 注释。这些措施建立在 Seth Larson 去年八月针对 ZIP 差异的早期工作之上。对下游用户而言，这些变更无任何破坏性影响；对维护者而言，绝大多数包不受影响，若遇上传被拒，通常只需改用标准 Python 构建后端（如 setuptools、hatchling 等），或手动确保源分发为 POSIX pax 风格 tar（GNU tar 需加 --format=pax），构建分发为合法 ZIP 且文件名使用 UTF-8 编码。PyPI 后续还将评估完全拒绝 GNU 风格 tar 和 ZIP 注释等更严格限制，并计划与 Python 标准库的 zipfile、tarfile 模块及打包规范协同推进，目标是逐步收紧校验同时保持最小用户影响。

## 12. 通过编排式 Pytest Worker 加速 CI

- 原始链接: <https://making.close.com/posts/faster-ci-with-orchestrated-pytest-workers/>
- 英文标题: Faster CI with Orchestrated Pytest Workers

Close 公司主后端服务拥有近 58,000 个集成测试，CI 总耗时仅约 2.5 分钟。文章回顾了测试基础设施十余年的演进：从 2012 年 Jenkins+nose 的串行运行，到 2014 年引入 pytest-split 确定性分割实现多 runner 并行，再到基于文件运行时的 bin-packing 均衡分配。该方案稳定运行约 12 年，但受限于固定成本（测试收集、数据 store 启动、镜像拉取等），即使 17 路并行也难以突破 12 分钟瓶颈。突破来自 currents.dev 的编排器思路：引入集中式队列动态分配测试，编排器仅收集文件列表（跳过 pytest 完整收集），worker 只收集自身任务，使固定成本与 worker 数量解耦。同时引入 spot 实例（2 个按需 + 54 个 spot，成本与 17 个按需相当），并解决失败重跑（所有 worker 等待全部批次完成，由编排器统一判定）、批次降序排序避免尾部大任务、自托管 runner 弹性扩缩等细节。最终 CI 计时通过 OTel 链路追踪汇入 ClickHouse/Grafana 做聚合分析。核心结论：当测试规模足够大时，将固定成本从每个 worker 剥离到单一编排器，并配合动态调度与 spot 实例，是突破并行化天花板的关键。

## 15. 为什么是斐波那契：Fibonacci LED 灯板的螺旋布局原理

- 原始链接: <https://www.evilgeniuslabs.org/why-fibonacci>
- 英文标题: Why Fibonacci?

本文解释了 Evil Genius Labs 的 Fibonacci 系列 LED 灯板为何采用斐波那契螺旋布局。作者受 Jim Bumgardner 启发，自 2015 年起制作了数十款此类设计。所有灯板（从 One Inch Fibonacci64 到 Fibonacci1024）均将 LED 置于费马螺旋上，即与向日葵种子相同的排列方式，而非从正方形绘制的单条「斐波那契螺旋」。布局规则为：从中心出发，每次微增半径、放置一颗 LED、旋转 137.508°（黄金角）。黄金角等于 360°÷φ²，无法表示为有理数，因此 LED 永远不会对齐成放射状。半径采用 √n 规则，使每颗 LED 占据等面积，保证整板像素密度均匀。螺旋布局的另一优势是任意数量下都呈均匀圆盘，新增 LED 不影响已有位置，故 32 至 1024 各型号共用同一布局。螺旋臂数量恰为 3、5、8、13、21、34 等斐波那契数，这也是产品命名的由来。文章还通过表格展示黄金角精度与可容纳 LED 数量的关系，指出两位小数已足够 Fibonacci1024 使用。

## 16. Maak v1.0.0：用 Lisp 构建的可无限扩展命令运行器

Maak 是一个用 Guile Scheme 编写的命令运行器与构建系统，其核心理念是「构建即程序」：用户编写一个普通的 Lisp 模块 maak.scm，其中每个过程自动成为可在命令行调用的任务，无需学习额外 DSL 或维护第二语言。文档字符串即任务说明，lambda 列表即参数语法，任务间通过函数调用而非子进程互调。功能亮点包括：run-pipeline 支持管道连接、失败阶段全量报告、后台作业与 PID 轮询；-j 参数按依赖拓扑并行执行并分块输出；dry-run 与 quiet 以 Scheme 参数实现，便于测试中 parameterize；任务可声明依赖、隐藏与示例。除 Lisp 文件外，也支持 maak.yaml、maak.toml、maak.json 等静态格式，共享 --list、--plan、--watch 等命令。--plan 可打印含 argv、工作目录、环境变量、提权与后台标记的类型化执行计划，--json 输出可供 CI 归档或 diff；explain 命令展示调用图、加载路径与 .env 优先级，回答「为何以 root 运行」等问题。此外提供 --watch 热重载、多编辑器（Emacs、Neovim、Vim、VS Code、Helix、IntelliJ、Zed、Sublime）集成，并覆盖 cargo、uv、npm、Maven、Gradle、Guix、Nix、Podman/Docker、git、gettext 等常见开发工具。作者表示将持续改进 shell 补全等功能。

## 17. sysdeck：面向 Linux 与 BSD 的轻量命令中心

- 原始链接: <https://xn--gckvb8fzb.com/sysdeck-raycast-for-linux-bsd/>
- 英文标题: sysdeck: Raycast for Linux & BSD

作者介绍了开源工具 sysdeck，一个为 Linux 和 BSD 桌面设计的键盘驱动命令中心，定位类似 macOS 上的 Raycast 但更精简。sysdeck 用 Zig 编写、GTK4 构建界面、SQLite 存储索引，通过热键唤起一个弹出窗口，用户输入关键词即可搜索应用、命令行可执行文件、文件与文件夹、浏览器书签、剪贴板历史、Sway 窗口、SSH 主机、Podman 容器、文本片段及 emoji。此外还支持单位与货币转换、通过 MPRIS 控制媒体播放器、管理 NetworkManager 连接、区域/窗口/全屏截图，以及对接 Gemini、OpenAI、Anthropic 等 LLM 进行问答。其核心设计亮点是完全不运行后台服务：每次热键触发即启动新进程，完成操作后退出；剪贴板记录也由 wl-paste 调用一个极轻量进程在 10–20 毫秒内完成，代价是约 0.1 秒的启动延迟。作者认为在内存日益昂贵的当下，这种按需运行比常驻后台更合理。sysdeck 采用 SEGV 许可证，主仓库位于 tty.fail，GitHub 有镜像并提供预编译二进制，覆盖 x86_64、aarch64、riscv64、powerpc64le、s390x、loongarch64 及 FreeBSD、NetBSD、OpenBSD 等平台。

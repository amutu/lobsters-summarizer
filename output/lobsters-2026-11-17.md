## 3. core：将其他程序的内存可视化并允许直接「涂鸦」

- 原始链接: <https://citrons.xyz/journal/2026-04-13>
- 英文标题: Paint in the memory of other programs

作者介绍了一款名为 core 的程序，它可将其他进程的内存「内脏」铺展在屏幕上供用户观察与修改，兼具「深奥调试器」与「绘画工具」的双重身份。可视化方案为：每页 4096 字节内存映射为 256×128 的矩形，每个像素对应一个比特（白为 1、黑为 0），比特按行、字节按列排布，各页沿 Z-order 曲线排列。用户可直接在画面上「涂写」，例如向栈下方未提交的空闲区域注入数据。core 被视为 blinkenlights 的「终极形态」，追求一种有目的的无目的体验，鼓励观者让视觉模式自然流过。不同数据类型呈现不同纹理：ASCII 文本因 7 位编码和值分布偏斜而极易辨认；64 位指针末两字节恒为 0 或 1 同样醒目。在复杂程序中可观察到数据结构分配、垃圾回收器首代回收、游戏栈帧逐帧闪烁等动态。作者用 CHICKEN Scheme 编译了一款采用 CPS（续延传递风格）的游戏，看到栈如瀑布般流动。图形程序在内存中产生生动的视觉图案；连接虚拟机或模拟器后，core 可俯瞰整个操作系统的内存，页表振动、新分配如蜂巢般填充。作者认为，将程序的比特「内脏化」虽简单却极具力量，让抽象程序获得可感知的物理存在。

## 4. Rust 如何重塑了一名开发者的思维方式

- 原始链接: <https://blog.startifact.com/posts/how-rust-changed-me/>
- 英文标题: How Rust Changed Me As A Developer

作者 Martijn Faassen 分享了自己使用 Rust 六年多后的感悟，认为 Rust 从多个维度深刻改变了他作为开发者的思维。首先，Rust 的枚举（sum type）让他重新认识到变体建模的价值：相比 OOP 中需要设计接口或继承层次，enum 配合 match 更轻量、静态可检查，且编译器强制覆盖所有分支。其次，Rust 将动态分派、条件分派与编译时分派（泛型）并列呈现，让他更清晰地理解分派机制与性能之间的关联。第三，类型不仅是静态检查工具，更能像测试和文档一样引导架构设计，即「类型驱动开发」。最大的惊喜在于，Rust 通过宏系统在编译期实现了类似 Python pickle 和 Pydantic 的序列化与 CLI 解析能力（如 serde、clap），开辟了一类新的框架模式。此外，所有权系统禁止循环引用和可变别名，迫使开发者分离数据构建与使用阶段，虽局部代码更难读，但整体数据流更清晰、耦合更低。为绕过循环引用限制，Rust 生态广泛采用「竞技场」模式——将对象存入连续数组、以索引互引，从而获得缓存友好、快速分配和内存归一化等性能优势。最后，Rust 让性能代价在代码中显式可见，要求开发者建立新的权衡直觉，而非盲目追求极致优化。

## 6. 高质量 IMAP 实现（一）：你的邮箱本质上是一个数据库

- 英文标题: Quality IMAP, Part 1: Your Mailbox Is A Database

本文是 Aerogramme（一个去中心化、运行在翻新硬件上的实验性邮件服务器）系列技术博客的第一篇，聚焦 IMAP 协议中细粒度邮件检索与查询的实现挑战。作者指出，从 IMAP 视角看，邮箱并非简单的邮件文件目录，而更接近一个用专用查询语言访问的数据库：SEARCH 命令支持按头部、日期、正文、标志及布尔组合筛选邮件，FETCH 命令则可按邮件的递归结构、原始字节或二者组合进行部分提取，这要求服务器必须真正解析邮件而非仅存储。Aerogramme 的实现分为三层：基于 AST 的 SEARCH/FETCH 解释器、通用邮件解析库 eml-codec、以及将元数据（K2V）与内容（S3）分离的存储架构。在测试方面，团队借助 Dovecot 维护的 ImapTest 工具进行差分测试，发现 FETCH 的 BODY[<section>] 子命令存在概念性错误；同时通过模糊测试驱动的属性测试验证 eml-codec 的「解析-打印」往返一致性，暴露出大量边界情况，例如 MIME 编码词在 From 与 Subject 头中因上下文不同而解析结果迥异。文章还讨论了 IMAP 规范中 SEARCH FROM 的「包含」语义模糊问题，以及真实世界中 10 万封邮件的容错解析。核心结论是：IMAP 与邮件规范充满歧义，仅靠阅读规范难以保证正确性，必须依赖自动化的差分测试与属性测试来驱动实现。

## 9. 在 Nightly 通道默认启用 Rust 编译器并行前端

- 原始链接: <https://blog.rust-lang.org/2026/11/16/enabling-parallel-frontend-on-nightly/>
- 英文标题: Enabling the parallel frontend on nightly

Rust 编译器团队宣布自 nightly-2026-11-14 起，在 nightly 通道默认启用并行前端（parallel frontend），以在稳定化前收集社区反馈。此前，编译器后端（LLVM）已支持多线程，但前端（类型检查、借用检查）长期为单线程执行，限制了编译性能。三年前虽已允许在 nightly 上选择启用，但原定 2024 年稳定化目标未能实现；去年 Vadim Petrochenkov 等人发起协调推进，修复了大量遗留问题并提升了性能。性能方面，单 crate 编译中 8 线程下 cargo check 可提速约 2 倍（如 nalgebra、cargo、diesel 等 crate），但整个 crate 图编译时因 CPU 核心已被后端和 Cargo 并行编译占用，端到端提升降至约 15%；增量编译改善仅 3%–5%。默认使用 2 线程以控制内存，用户可通过 --jobs-frontend 调整线程数。已知限制包括诊断顺序不确定及二进制不可复现等问题。稳定通道不受影响；nightly 用户可通过 --jobs-frontend=1 回退至串行前端。团队计划数月内监控 GitHub 与 Zulip 上的反馈，确认无重大问题后推进稳定化，并继续并行化宏展开、名称解析及 AST 到 HIR 的 lowering 等前端环节。

## 10. beer.drv.drv.drv：用 Nix 动态派生链唱完 50 瓶啤酒

- 原始链接: <https://fzakaria.com/2026/11/14/beer-drv-drv-drv>
- 英文标题: beer.drv.drv.drv

本文围绕 Nix 实验特性「动态派生」（dynamic derivations）展开。动态派生允许一个派生在构建阶段产出新的派生，从而在运行时动态扩展构建图，而非在求值时预知全部依赖，是 Nix 对标 Bazel、buck2 等构建系统速度的关键尝试。文章起因于一位读者提问：能否通过 nix-store --query --deriver 从动态派生的输出反向追溯到初始派生？作者验证后确认通常可行，但若生产者设置了 __contentAddressed = true，则因输出路径在构建前未知，Nix 不会回填 deriver 字段，会返回「unknown-deriver」（已提交 NixOS/nix#16823）。为探索回溯极限，作者用经典歌曲「99 瓶啤酒」构造了一条动态派生链：每个派生用 busybox 手写 ATerm 格式的下一个派生，逐句输出歌词。受 Nix store 路径 211 字符上限约束（每层 .drv 后缀占 4 字符），链深最多 50 层，故只能唱到 50 瓶。最终作者用循环从 result 一路回溯，成功取回 52 条记录（1 个结果 + 51 个派生），并可通过 nix log 让任意一层重新「唱」出对应歌词。文章末尾提到 tomberek 正牵头工作组推进动态派生的最终定稿，作者对此特性充满期待。

## 11. NoisyTCP：Linux内核TCP预认证远程内存损坏漏洞（CVE-2026-99288）

- 原始链接: <https://www.openwall.com/lists/oss-security/2026/11/15/2>
- 英文标题: NoisyTCP

NoisyTCP（CVE-2026-99288）是Hyunwoo Kim报告的Linux内核TCP预认证远程内存损坏漏洞，潜伏约11年（2015年10月引入，2026年11月修复），影响几乎所有Linux发行版。漏洞利用过时的ehash查找与请求套接字的释放、重新分配在不同RX上下文中并发执行，要求目标具备两个以上RX队列或启用RPS。攻击者可针对Nginx、Apache、SSH等默认配置的TCP监听器进行预认证远程利用。存在两条触发路径：一是request_sock复用ABA竞态，导致内核panic实现远程DoS，容器场景下可波及宿主机；二是完整子套接字ABA竞态，可触发远程use-after-free，但嵌套竞态条件复杂，实际利用难度较大。触发耗时因环境而异：QEMU/KVM虚拟机上约5秒至2分钟，安静裸机（8个RX队列）上约14小时。缓解措施：优先应用官方补丁；临时方案可禁用SYN cookies（需逐网络命名空间设置，但会降低SYN洪水防护能力），或将RX队列缩减为单个并禁用RPS与RFS。

## 12. 发布 hegel-clj：Hegel 生成式测试库的 Clojure 接口

- 原始链接: <https://aphyr.com/posts/428-announcing-hegel-clj>
- 英文标题: Announcing Hegel-clj

作者发布了 hegel-clj 0.1.1，这是跨平台生成式测试库 Hegel 的 Clojure 绑定。文章首先剖析了 Clojure 生态中广泛使用的 test.check 在缩小（shrink）阶段的痛点：当生成器通过 bind 或 let 嵌套组合时，缩小树会陷入困境，导致找到的最小反例体积庞大（例如本应缩小为 [42] 却得到含三十九个零的长向量）。根本原因在于 test.check 采用两阶段机制——先生成缩小树再深度优先搜索，而 bind 在缩小外层参数时会重新生成内层随机值，使搜索极易卡住。Hegel 则采用「内部测试用例缩减」策略：生成器每次只产出一个值，若该值触发失败则重新运行生成器并要求产出更小但相似的值，从而避免上述问题。hegel-clj 提供纯函数式、可组合的生成器体系，支持 fmap、bind、let、composite（将任意代码提升为生成器）以及 deferred 递归生成器；与 clojure.test 深度集成，使生成式测试的写法与示例测试几乎一致；还引入「最终测试用例」机制，配合 fprn、finfo 等工具大幅改善调试体验。作者同时指出 test.check 的 API 存在命名不一致、参数风格混杂等历史包袱，hegel-clj 以全新设计追求更统一、更易上手的接口。

## 15. FreeBSD pkgbase 本地镜像搭建

- 原始链接: <https://blog.feld.me/posts/2026/11/local-mirror-for-freebsd-pkgbase/>
- 英文标题: Local Mirror for FreeBSD pkgbase

FreeBSD pkgbase 将基础操作系统从单体 tarball 包集改为独立包分发，但批量部署系统或 jail 时会反复访问官方镜像，造成大量带宽浪费。作者拥有内部源码包仓库，但基础 OS 需保持与官方上游一致以确保完整性，因此不自行构建。在将全部 jail 迁移到 pkgbase 时，每次转换都会重复拉取 36 次官方镜像，促使他搭建本地镜像。方案采用 Apache 反向代理加磁盘缓存，关键注意事项是不能指向 pkg.freebsd.org（该地址会重定向到 CDN，而 Apache 不会跟随重定向进行缓存），需直接指向 CloudFront CDN 地址。配置中仅对不可变的 Hashed/blobs 路径启用缓存，其余请求走代理透传；同时加载 cache、proxy、ssl 等模块，设置缓存根目录、最大文件大小及默认过期时间等参数。服务器端只需将 FreeBSD-base 仓库的 URL 改为本地镜像地址即可生效。作者还提到未来可考虑发布 SRV 记录，在本机宕机时自动回退到官方镜像，但尚未实施。

## 16. funkycache：基于 SQLite 的 Python 函数缓存库

- 原始链接: <https://alexwlchan.net/2026/funkycache/>
- 英文标题: funkycache: a Python library to cache functions in SQLite

作者为静态站点生成器开发了一个名为 funkycache 的 Python 库，将函数缓存逻辑封装为装饰器，底层以 SQLite 持久化存储。此前作者仅实现了基础的键值存储，需为每个函数手写缓存读写代码，难以测试且不可靠。funkycache 借鉴标准库 functools.cache 的接口，用户只需在函数上添加 @cache.register 装饰器即可完成缓存。缓存键由 inspect 模块提取完整参数后序列化为 JSON，再用 XXH64 哈希（经基准测试，大键值场景下 XXH64 显著快于 MD5，而 MD5 甚至慢于直接存储）。缓存值借助 Pydantic 依据返回类型注解进行 JSON 序列化与反序列化。对惰性生成器，库将其物化为列表存储，取回时转回迭代器，并设内存预算防止无限生成。依赖追踪方面，可声明函数依赖的文件路径和静态值（如第三方库版本号），变化时自动使缓存失效。项目灵感源于响应式编程中类似电子表格的有向无环图模型，但作者最终选择装饰器方案以降低复杂度。暖缓存下整站构建仅需约半秒，库代码含测试仅数百行，已发布至 PyPI。

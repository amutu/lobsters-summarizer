## 1. 论开关控件的危害

- 原始链接: <https://ignorethecode.net/blog/2026/08/09/toggles_considered_harmful/>
- 英文标题: Toggles Considered Harmful

本文批评了数字界面中的开关（toggle）控件，指出其状态不明确，是一种糟糕的UI设计。作者以macOS系统设置中的对话框为例，其中布尔开关以四种不同灰色呈现，用户无法直观判断开关状态。作者认为这类开关起源于iOS，取代了复选框，因为触屏上更具触感、操作目标更大，且类似物理拨杆，符合苹果早期拟物化设计风格。但在真实世界中，物理开关需要借助标签和指示灯来表明当前状态，因为开关本身是对称的。数字开关却缺少这些辅助线索，除非用户事先知道“左关右开”的约定，否则无法判断开关状态。苹果为提高开关状态的可辨识度做了各种尝试，反而制造了更多混乱。因此，最直接的解决方案是改用状态一目了然的控件，如复选框或单选按钮。文章还提到macOS有一个无障碍设置“区分无颜色”能在开关上显示开关指示符，但这只是辅助手段，并未解决根本问题。核心结论是：开关控件不应存在，应被状态显式、无需额外解释的UI组件替代。

## 2. GitHub Actions 需要 OIDC 受众约束

- 原始链接: <https://blog.yossarian.net/2026/08/10/github-actions-needs-oidc-audience-constraints>
- 英文标题: GitHub Actions needs OIDC audience constraints

文章指出 GitHub Actions 的 OIDC 机制存在安全弱点：与 GitLab 要求静态声明 audience 不同，GitHub 允许工作流在运行时通过 id-token: write 权限请求任意 audience 的 ID token。由于许多工作流既授予该权限又运行第三方代码，一旦攻击者利用漏洞或恶意代码，就能为其他服务伪造 token，实现跨服务横向移动。作者认为，应在 GitHub Actions 中增加 audience 约束语法，例如 permissions: id-token: [pypi]，限制某任务只能为指定受众请求 token，从而减少被用作跳板的风险。服务若确需动态 audience 可继续使用原有 id-token: write 作为兜底，但安全性较低。文章也提到 Trusted Publishing 通过强制包含 workflow 名缓解问题，但并非所有集成都适用；总体而言，增加约束是低成本、高收益的安全改进。

## 3. Firefox 容器功能预览

- 原始链接: <https://blog.mozilla.org/en/firefox/firefox-containers-preview/>
- 英文标题: Firefox Containers Preview

Mozilla 宣布在 Firefox 153 中推出原生容器（Containers）功能的预览版，该功能允许用户在同一浏览器窗口中分别登录工作、购物、个人和银行等不同账户，并在各容器内隔离 cookies 和广告追踪，避免跨容器数据泄露。此举将此前广受好评的 Multi-Account Containers 扩展的核心能力直接内置到浏览器中，使用户无需安装附加组件即可使用。原生版本默认可见，简化了打开、创建和管理容器的流程，同时保留了扩展的核心功能、灵活性和视觉风格，并计划持续投资该功能的未来发展。在预览版中，用户可以在指定容器中打开标签页，自定义容器的名称、颜色和图标，通过 Firefox 设置界面管理容器。使用方式包括右键点击标签页或长按新建标签按钮创建容器标签页。现有扩展用户无需卸载扩展，原生版本尚未包含扩展的全部功能，两者可同时使用。Mozilla 表示这是使 Firefox 更适配用户在线生活方式的第一步，并邀请用户通过 Mozilla Connect 提供反馈。

## 4. 纯CSS实现阳光透过窗户洒入的视觉效果

- 原始链接: <https://github.com/jackyzha0/sunlit>
- 英文标题: a pure css implementation of some sunlight streaming in through the window

这篇文章分享了一个纯CSS实现的太阳光透过窗户洒入室内的视觉特效，灵感来自Daylight Computer和Sunlit Place网站。整体结构基于多个带背景的div层，叶片素材来自Adobe Stock并缩小至约300x500以便模糊处理。核心要点包括：1) 渐进模糊：使用多个带backdrop-filter的图层，配合mask-image线性渐变限制模糊范围，越靠近墙壁越清晰，远处更模糊，模拟光线扩散。2) 叶片飘动：对叶子容器施加rotate/scale动画，并利用SVG滤镜feTurbulence和feDisplacementMap添加高频噪声，让每片叶子有独立的摇曳感。3) 日出日落过渡：颜色来自手工调色，并添加一个粗略的发光层模拟地板反射。4) 3D透视变换：由于普通affine变换无法产生透视扭曲，作者用Python计算单应性矩阵，生成CSS的matrix3d值，实现满意的角度变形。文章提供了关键CSS片段和Python脚本，展示了如何用纯前端技术营造逼真的光影氛围。

## 5. Django 转向年度发布周期

- 原始链接: <https://www.djangoproject.com/weblog/2026/aug/10/annual-release-cycle/>
- 英文标题: Django is moving to an annual release cycle

Django 指导委员会已接受增强提案 DEP 20，决定从 2028 年 1 月起采用年度发布周期。每个功能版本都将获得等同于以往 LTS 的三年支持期（一年主流错误修复，两年安全与数据丢失修复），版本号直接采用年份，如 Django 2028、Django 2029。此举旨在更好地配合 Python 每年 10 月的发布节奏：每个 Django 版本在发布时支持最新的三个 Python 版本，并在第一年内纳入新发布的 Python 版本，其支持窗口与所支持的最旧 Python 版本同步结束，避免了旧版 Python 长期超期维护的问题。新周期下，每个版本都是 LTS，消除了以往 LTS 之间的空档期，用户可每年升级一次，无需一次性跨越两年的大变更；任意时刻有三个版本受支持，为第三方包提供了清晰滚动的目标。API 稳定性与弃用政策不变，弃用期按日历时间实际更长。过渡安排：Django 6.1 于 2026 年 8 月发布，2027 年 12 月结束支持；Django 6.2 LTS 于 2027 年 4 月发布，2030 年 4 月结束；Django 2028 为首个新周期版本，2030 年 12 月结束；2028 年前一切不变，现有 LTS 承诺维持。完整细节见 DEP 20。

## 6. 研究员买下noreply.net域名，公司开始向他发送机密信息

- 原始链接: <https://arstechnica.com/security/2026/08/a-researcher-bought-noreply-net-companies-started-sending-him-secrets/>
- 英文标题: A researcher bought noreply.net. Companies started sending him secrets

一位安全研究员购买了无人认领的域名 noreply.net，结果意外收到了大量来自各大公司系统自动发送的邮件。由于许多企业在内部系统、软件配置或员工账户中误将 noreply.net 用作发送或接收地址，导致包含敏感信息的邮件持续涌入他的邮箱。这些信息包括内部财务文件、员工密码、个人身份数据、客户表单，甚至一些本应绝对保密的内部通信。研究员在保留证据后联系了相关公司，但部分企业并未及时响应。文章指出，这一事件暴露了企业在自动化邮件系统配置上的严重疏漏，尤其是对未经验证域名的依赖可能造成数据泄露风险。同时，它也提醒所有开发者和管理员，在设置无人值守的邮件服务时，务必确认域名所有权并采用安全的邮件验证机制，避免将机密信息发送到不受控的地址。文章还提到，这类看似无害的域名注册行为，有时能意外揭示出大规模信息暴露的真实案例，突显了互联网基础设施中隐藏的安全盲区。

## 7. 点云碰撞检测的未竟之路：从CAPT到MVT的演进与反思

- 原始链接: <https://claytonwramsey.com/blog/mvt/>
- 英文标题: We're not done with point clouds

本文作者介绍了一项改进点云碰撞检测数据结构的研究成果。此前作者提出的CAPT结构虽然查询速度快，但构建时间随点云密度急剧增长，内存开销大。Chen和Yeh提出的多层级体素表（MVT）改用稀疏体素网格替代近邻搜索树，避免数据复制，显著降低了构建时间和内存占用。作者用Rust重新实现了MVT，简化了内存管理，并额外提供了可变版本。文章通过参数扫描发现，体素宽度的最优值并非原作者推荐的基于机器人最大球体半径，而在10至20厘米之间，且Baxter机器人上差异悬殊。基准测试显示，MVT在构建时间、查询吞吐和端到端运动规划性能上均优于CAPT和k-d树，甚至接近使用真实几何的规划速度。不过作者也指出，MVT仅解决了构建时间问题，点云数据固有的遮挡缺陷仍未解决，现有的八叉树方案虽能处理遮挡但速度慢，安全与速度的权衡依然是感知规划中的开放挑战。本文同时提供了论文、C++原版和作者Rust实现的链接。

## 8. 编程语言如何影响大模型的Token效率与正确性？

- 原始链接: <https://danluu.com/pl-tokens/>
- 英文标题: How do programming languages impact token efficiency and correctness?

文章针对“动态语言比静态语言更省Token”的流行说法进行了检验。作者指出，早期被广泛引用的评估多基于琐碎的小问题，结论无法推广到真实任务；另一项评估还存在评分路径被错误符号链接污染等严重方法问题。为验证假设，作者用Zstd解码器和Pandoc两个较大任务进行了自己的评估，比较多种语言在成本和正确性上的表现。结果显示：在中等努力水平下，动态语言似乎略占优势，但提高努力水平后静态语言表现更好，整体上两类语言没有一方明显胜出；极端简洁的冷门语言（如J）并不占优，汇编等语言表现很差；语言流行度与正确率、成本呈弱到中等正相关。作者还指出，不同任务间结果差异很大，单一或少数评估不足以支持强结论。最终作者认为，所谓动态语言更高效的说法至多在方向上略有道理，实际指导意义有限；选择主流语言通常比追求冷门高密度语言更可靠。文章强调，用LLM做这类评估虽然仍不完美，但比传统人类受试者实验更可行，并为未来更严谨的多任务评测提供了参考。

## 11. nixpkgs-multiverse: 汇集 Nixpkgs 所有历史版本

- 原始链接: <https://fzakaria.com/2026/08/09/nixpkgs-multiverse-every-version-that-ever-existed>
- 英文标题: nixpkgs-multiverse: every version that ever existed

文章介绍了 nixpkgs-multiverse 项目，它让用户通过单个 flake 输入即可访问 Nixpkgs 中曾经存在过的所有软件包版本。作者最初因某个软件包版本升级破坏工具链，不得不额外引入多个 nixpkgs 输入并固定提交，但这种方式既笨拙又拖慢求值。nixpkgs-multiverse 应运而生：它把从 2017 年到 2026 年约 1393 个 Nixpkgs 修订版本（主要是发布版和 nixos-unstable 通道更新）统一编入索引，通过 `nix run 'github:fzakaria/nixpkgs-multiverse#versions.python3."3.6.2"'` 等语法即可获取任意版本。其实现秘诀是 flake 无输入，利用 `builtins.fetchTree` 按 `narHash` 懒加载修订，避免急切获取大量输入；用 `revisions.json` 保存修订元数据，`versions.json` 记录每个（属性, 版本）对应的最新修订偏移量，从而压缩数据体积。性能测试显示，传统方式每个未使用的 nixpkgs 输入约耗费 5 秒，五个输入就需 26 秒；而 multiverse 提供 1393 个修订仅需 0.20 秒解析。项目本身约 5 MB JSON 和 200 行 Nix 代码，不构建、不镜像、不托管任何东西，只相当于一个电话簿，将 Nixpkgs 历史中已缓存的构建产物按版本号而非提交哈希重新组织，让用户轻松混用不同版本的包。

## 13. C89标准中一个永远不会被修复的歧义

- 原始链接: <https://sebsite.pw/w/20260810-c89ambiguity.html>
- 英文标题: an ambiguity in c89 which will never be fixed

本文探讨了C89（ISO C90）标准中一个因措辞模糊而从未被澄清的歧义，该歧义导致GCC和Clang对同一代码给出相反的编译结果。C89具有隐式函数声明特性：当调用一个未声明的非括号标识符时，编译器会将其隐式声明为返回int、参数未指定的函数。关键在于，如果函数声明中的数组声明符内部调用了一个与参数同名的函数，标准对隐式声明插入位置的描述（“innermost block”）存在两种解释：若指块作用域，代码合法；若指函数原型作用域，则构成非法重复声明。作者展示了一个具体例子：`int f(int f[sizeof(f())])`，Clang编译通过，而GCC报错。另一相反示例中两者行为亦颠倒。作者指出GCC将隐式声明放入函数原型作用域时不进行数组到指针的退化，这暗示Clang的解释可能更符合标准本意。由于C99已移除隐式函数声明，该歧义永远不会得到官方决议。文章最后作者强烈呼吁开发者停止使用C89，改用C11。

## 14. 谁应为源代码可用性买单？

- 原始链接: <https://kristoff.it/blog/source-code-availability/>
- 英文标题: Who Should Pay For Source Code Availability?

作者以自身项目 Zine 为例，指出依赖分散在 GitHub、Codeberg 及自托管 Forgejo 上，这些平台一旦宕机会导致构建失败，而自托管虽更稳定却可能永久下线。常见的解决方案是 fork（将所有依赖迁移到同一主机）或 vendor（将依赖源码直接提交进自己的仓库），但这两种方式本质上仍是低效的成本分摊：被 fork 或 vendored 的代码无法被他人自动发现和作为镜像使用。文章由此提出核心问题：源代码的可靠可用需要持续投入，成本应由谁承担？GitHub 等平台的恶化（enshittification）固然存在，但用户长期免费消耗资源也有责任。随后作者重点介绍 Radicle——一个点对点网络，节点按兴趣 seed 仓库，使依赖保持可发现性，同时通过将 Issues/Patches 作为 Git 对象存储，避免了集中式服务器。Radicle 还提供可选的 HTTP 服务，让非 Radicle 用户也能通过普通 URL 克隆仓库。对 Zig 生态，作者建议包管理器支持 mirrors，并让 rad CLI 将 RID 解析为 HTTP 地址。最后对比 Codeberg：它基于 Forgejo、非营利且对 Zig 友好，但 fork 时复制整仓导致资源消耗，而 Radicle 用 Git namespaces 更高效。作者认为 Radicle 模型更符合各方利益且成本更低。

## 20. Deflate 压缩级别的再平衡

- 原始链接: <https://blog.klauspost.com/rebalancing-deflate-compression-levels/>
- 英文标题: Re-balancing Deflate Compression Levels (2016)

文章讨论了 Go 语言中 deflate 压缩级别的不合理权衡。作者在优化 Go deflate 压缩时发现，压缩级别 1 与 2 之间速度跳跃大；级别 5 以上压缩收益极小而速度下降明显，级别 6 到 8 缺少合理性价比，默认的级别 6 尤其昂贵。于是作者设定目标：级别 1 和 9 保持端点不变，每个级别应在合理速度成本下带来压缩率改善，且速度随级别更线性。作者在多个测试数据集（enwik9、Matt Mahoney 的 10GB 语料库、自制 Web 服务器文件集）上反复调整参数。结果显示重新平衡后，级别分布更均匀，尤其是 10GB 语料库上几乎达到理想分布；但级别 2 仍表现不佳，需要专门代码改进，级别 6 与 7 之间有算法切换导致的速度/压缩比差距。最终作者决定将默认压缩级别从 6 改为 5，因为在多数场景下级别 5 是速度与压缩率更好的折中点；相比旧默认级别 6，速度几乎提升一倍，加上对标准库的优化，整体性能约为原来的 4 到 5 倍，而压缩率只下降 2% 至 5%。这些改进预计随 Go 1.7 合并。

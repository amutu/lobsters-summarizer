## 1. 技术博客写作中的反模式

- 原始链接: <https://refactoringenglish.com/blog/anti-patterns-software-blogging/>
- 英文标题: Anti-Patterns in Software Blogging

作者将软件开发中「反模式」的思路引入技术博客写作，系统梳理了新手博主最常见的写作失误。核心观点是：读者注意力有限，标题和前三句话必须回答「这跟我有关吗」和「读完我能得到什么」两个问题，否则读者不会继续。文章逐一剖析了七类问题：漫无目的的开头、堆砌副标题与引言、假设读者具备与作者相同的知识背景、用链接代替解释、以「续集」口吻开篇迫使读者回看前文、过度正式的生硬文风、以及移动端页面溢出和字体对比度不足等渲染缺陷。作者强调，链接应是加分项而非阅读前提；写作应像跟朋友聊天一样自然，避免AI生成的千篇一律；发布前务必用浏览器移动端预览检查布局。文章还引用了Joel Spolsky等知名博主的段落作为风格范例，鼓励作者展现个人声音。总结部分以清单形式重申了各条建议，整体基调务实、幽默，面向希望提升技术写作质量的中初级开发者。

- 英文标题: Software developers are not okay

冰岛开发者Baldur Bjarnason在2026年10月的长文中指出，软件行业从业者正经历严重的心理健康危机。大量「我离开科技行业」视频涌现，评论区的讨论远比视频本身激烈。值得注意的是，离开者并非AI的反对者，而是曾拥抱AI、接受「这是未来」叙事后，发现工作不再有趣、不再令人满足的普通开发者和UX设计师。文章从激励机制角度剖析根源：高管有强烈动力削减人力以降低期权支出、削弱员工对不道德行为的阻力；裁员后剩余员工承担更多工作，而产品新颖性消失，充斥AI克隆。LLM工具不像电锯之于木工，更像「委托给无知的初级开发者」，破坏了心流与创造投入。行业不确定性加剧——每季度裁员、理由任意、员工无法改善处境。作者警告，即使AI泡沫破裂，问题也不会消失，因为模型只需「差不多能用」，成本压力会转嫁给开发者。冰岛计算机科学招生已下降约30%。作者认为，这种高压、低薪、与劳动脱节的状态可能成为大型科技公司开发者的常态，并建议从业者认真考虑行业之外的出路，面对身份认同危机。

## 3. 写给 Rust 程序员的 C 语言速览

- 原始链接: <https://bd103.dev/blog/2026-10-07-c-for-rust-programmers/>
- 英文标题: C for Rust Programmers

本文作者是一位先学 Rust 再学 C 的系统程序员，以 Rust 视角对比 C 语言，梳理了若干容易让 Rust 程序员「踩坑」的设计细节。文章涵盖六个主题：一、布尔值并非 C 原语，C99 前用整数 0/1 表示，C99 通过 stdbool.h 引入，C23 才成为语言原语；二、C 字符串以空字节 \0 结尾，不单独存储长度，与 Rust 的 &str（16 字节含指针和长度）形成对比，空字符串也占 1 字节，且忘记添加终止符会导致越界读取；三、C 整数类型宽度依赖目标平台，例如 long 在 64 位 Unix 为 64 位而在 Windows 为 32 位，跨平台开发应使用 stdint.h 中的固定宽度类型；四、C 的错误处理缺乏强制机制，函数仅靠返回 -1 或 NULL 表示失败，需程序员手动检查，作者尝试用标签联合模拟 Rust 的 Result 但效果不佳；五、C 对值和指针使用不同的字段访问运算符（. 与 ->）；六、数组作为函数参数时隐式退化为指针，sizeof 将返回指针大小而非数组长度。此外，C 没有引用和借用检查，全部依赖裸指针，指针算术虽灵活但易引发缓冲区溢出等安全问题。作者总结认为，C 虽设计哲学与 Rust 截然不同，但作为系统程序员仍不可或缺。

## 4. 为小型社区打造发行版构建工具：Chimera Linux 的 cbuild 实践

- 原始链接: <https://chimera-linux.org/news/2026/10/the-case-for-cbuild.html>
- 英文标题: Creating distro build tooling for a small community

作者回顾了自己从 Debian 到 FreeBSD 再到 Void Linux 的打包经历，并详述了 2021 年创建 Chimera Linux 及其构建工具 cbuild 的动机与设计理念。Chimera 是一个以社区为核心、追求极低维护成本的小型发行版，其核心目标是让每位用户都能轻松成为打包者。cbuild 用 Python 重写了 Void 的 xbps-src，将仓库管理、构建环境、签名、版本检查等全部整合进单一工具，依赖极少（Python、Bubblewrap、Git 及包管理器），可在任意 Linux 上运行。针对 xbps-src 的痛点——Shell 脚本解析数千模板需数十分钟、构建期间允许网络访问、沙箱一致性不足、缺乏逐模板单元测试、交叉编译质量低、staging 机制粗糙——cbuild 以严格沙箱（仅构建目录可写、configure 起禁止网络）、高速元数据解析（亚秒级）、自动 lint 与依赖校验、默认运行单元测试等策略逐一解决。文章还展示了从克隆 cports 仓库、生成签名密钥、构建包、提交 PR 到版本升级的完整工作流，以及基于 Git 范围批量构建等实用功能。作者强调工具应引导用户「隐式做对事」，让错误操作比正确操作更难执行，同时保持体验轻松有趣，不设门槛。

## 5. Janet 语言在 x32 ABI 下的实践：32 位指针、64 位速度、内存减少 25%

- 原始链接: <https://alexalejandre.com/programming/lisp/janet-for-the-x32-abi/>
- 英文标题: Janet on x32: 32-bit Pointers, 64-bit Speed, 25% Less RAM

本文探讨在 64 位 Linux 系统上通过 x32 ABI（即 -mx32 编译选项，使用 32 位指针搭配 64 位指令集）运行 Janet 语言以节省内存的可行性。作者指出 x32 在主流发行版中几乎被忽视：Debian 默认禁用，Arch 未编译，Ubuntu 也已移除支持。实验分两阶段：在 Arch 上用 -m32 编译 Janet，虽省 20% 内存，但因仅使用 8 个寄存器导致速度下降 50%；在已停止支持的 Ubuntu 20.04 上用 -mx32 编译，内存减少 21%（8%–32%），速度基本持平（波动在 -13% 到 +10% 之间）。作者用 words、records、tree、parse 四个基准验证了结论，其中指针密集的 tree 测试内存降幅最明显。文章还分析了 Janet 的 nanboxing 机制（值已压缩为 8 字节），指出 x32 的主要收益在于更小的对象头（16 字节 GC 头），并讨论了进一步缩减 struct、table、tuple 等类型头部开销的可能性，但受限于 glibc malloc 的 16 字节对齐。作者呼吁 Linux 发行版恢复 x32 支持，将守护进程和工具默认以 -mx32 编译，以更低成本实现日常计算中的内存效率提升。

## 7. rat 的极简寄存器分配器

- 原始链接: <https://hexrat.cc/pages/blog/2026_10_07>
- 英文标题: rat's minimal register allocator

作者介绍了其小型编译器 rat 的 x86-64 寄存器分配器重写。旧版基于线性扫描，代码达 1392 行；新版采用优先级 bin-packing 策略（与 LLVM 贪心分配器同族但大幅简化），仅 584 行。新分配器分五步执行：计算活跃区间、标记固定寄存器、合并可消除的拷贝、按优先级（权重除以区间长度平方根）为每个 bundle 分配物理寄存器、将无寄存器可用的 bundle 溢出到栈。设计刻意省略了驱逐、区间分裂和二次遍历，靠合并、寄存器提示、活跃区间空洞利用和按使用权重选择溢出目标等廉价手段获得质量。实测对比旧版：生成指令减少 3.6%，存储减少 22%，分配器耗时减少 77%，sqlite 在 -O0 下总编译时间减少 43%。逐项消融实验显示，合并与提示贡献约三分之一收益，空洞利用贡献 10%，而乐观二次尝试、重计算、溢出槽缓存等特性贡献几乎为零，故被直接丢弃。作者的核心教训是：移植旧代码前先做测量，很多复杂逻辑实际并无收益。

## 9. 清零（一）：擦除操作可能让情况更糟

- 原始链接: <https://00f.net/2026/10/06/zeroization-1/>
- 英文标题: Zeroization, part 1: Wiping can make things worse

本文讨论了密码学编程中「清零敏感数据」这一常见实践的反直觉问题。作者通过C语言示例及对应汇编输出，说明盲目添加清零调用不仅无效，还可能产生额外密钥副本。首先，memset()会被编译器优化掉；用volatile字节写入绕过优化时，中间值可能始终驻留寄存器，清零的栈位置从未被赋值；将清零函数置于独立编译单元时，编译器为传递地址反而将值先存入栈中，制造新副本；在tag比较示例中，编译器为跨调用保持计算值额外生成栈副本，而清零仅覆盖其中一个。作者还指出，寄存器中的密钥在上下文切换、core dump及微架构漏洞中可能泄露，传统清零函数无法触及。结论是：对已存在于内存中的缓冲区（如密码输入）清零仍有价值，但对小型局部变量添加清零前，应检查优化后的实际汇编，确认值是否已在内存中、取地址是否产生新存储、调用后哪些副本仍存活，而非盲目散布清零调用。

## 10. AI编程的五大反对理由及其回应

- 原始链接: <https://www.sicpers.info/2026/10/reasons-to-dislike-ai-coding/>

## 13. 天际中「魔法光」经验漏洞的逆向工程解析

- 原始链接: <https://blog.alexbeals.com/posts/explaining-the-magelight-xp-glitch-in-skyrim>
- 英文标题: Explaining the Magelight XP glitch in Skyrim

本文通过逆向工程彻底解释了《上古卷轴5：天际》中在独孤城附近山顶施放「魔法光」（Magelight）可瞬间获得大量变化系经验的漏洞。作者先推导出该技能每次施放基础经验约37.938点，再深入分析碰撞检测机制：法术投射物每帧沿路径检测碰撞，依据碰撞层判断是否命中。关键发现是，碰撞层L_TRANSPARENT_SMALL虽触发碰撞判定并授予经验，却被「HandleHit」函数豁免，不阻止投射物继续飞行。因此投射物穿过独孤城附近大量L_TRANSPARENT_SMALL不可见边界框时，每帧重复触发经验奖励，直至穿过物体中点。这解释了为何仅独孤城那座山能触发此漏洞，而非其他有云的山。作者还用SKSE编写mod可视化不可见墙壁，找到最优角度可使单次触发从约280次提升至约850次，并提供可复现操作指南，使玩家仅17次施法即可将变化系从15级升至100级。

## 15. 深入理解 Git Refs 机制

- 原始链接: <https://matklad.github.io/2026/10/07/git-ref.html>
- 英文标题: On Git Refs

作者分享了对 Git refs 机制的新理解。Git 不仅是一个内容寻址的不可变数据库，同时也是一个可变的键值存储：.git/refs 目录下以字符串路径为键、以内容寻址对象为值。分支、标签和 git notes 本质上都是 refs，但 refs 是底层实现细节，日常使用中几乎不可见，Git CLI 大量简写进一步掩盖了这一层。文章重点解释了「git fetch origin master」与「git switch -c my-feature origin/master」中空格与斜杠的区别：前者中 origin 是远程仓库的约定名称，master 是远程分支简写，完整展开为「git fetch <url> refs/heads/master:refs/remotes/origin/master」；后者中 origin/master 是本地远程跟踪分支 refs/remotes/origin/master 的简写。Git 将远程分支映射到 refs/remotes/<remote>/ 命名空间下，以支持多远程仓库场景。作者还指出 Git 采用离线优先、显式同步的模型，本地通过 refs/remotes/origin/main 镜像远程状态，与本地 refs/heads/main 独立演进。最后提醒 git switch -c 的第一个参数是「创建」ref 的名称而非 ref 本身，若展开为 refs/heads/my-feature 会导致路径嵌套为 refs/heads/refs/heads/my-feature。

## 16. Python 3.15 性能有多快？

- 原始链接: <https://blog.miguelgrinberg.com/post/how-fast-is-python-3-15>
- 英文标题: How fast is Python 3.15?

本文是 Miguel Grinberg 对 Python 3.15（rc3）的非正式性能基准测试，对比了 CPython 3.10 至 3.15、PyPy 3.12、Node.js 26.3 和 Rust 1.97，并额外测试了 3.13 起引入的 JIT 与 free-threading（FT）解释器。测试使用两个程序：fibo.py（递归计算斐波那契数列）和 bubble.py（冒泡排序），各含单线程与 4 线程版本，在 Linux 上运行取三次平均值。主要发现：3.15 标准解释器相比 3.14 仅提升约 3%–4%，属于微小改进；近年来性能跃升最显著的是 3.11 和 3.14 两个版本。JIT 在 3.15 中首次全面超越标准解释器（单线程快 1.20x–1.28x），但仍是实验性功能，不宜用于生产。Free-threading 在多线程场景下优势明显：fibo 多线程下比标准版快约 4.5 倍，bubble 快约 1.74 倍，但单线程下与标准版持平或略慢。PyPy 在单线程测试中仍快 5–18 倍，Rust 快 50–77 倍。作者结论：3.15 性能提升有限，生产环境无需急于从 3.14 升级，但计划将 3.15 作为日常开发解释器，以体验新特性（如类似 JS 的解包语法、惰性导入等）。

## 17. 基于批处理与聚合的更快流式 HTML 渲染

- 原始链接: <https://andersmurphy.com/2026/09/29/faster-streaming-html-with-batches-and-aggregates.html>
- 英文标题: Faster streaming HTML with batches and aggregates

本文探讨服务端即时模式流式 HTML 渲染的性能优化策略。架构核心是：所有状态驻留服务器，每 X 毫秒（一个 tick）通过 SSE 长连接加 Brotli/Zstd 流式压缩向每个客户端推送整页 HTML 帧。Tick 机制天然提供批处理边界与背压，将 N 用户×M 操作的 O(N×M) 渲染降为每 tick 仅 N 次渲染，避免二次方膨胀。在 tick 内引入 CyclicBarrier 作为读写屏障，将写入与渲染解耦；渲染线程按连接组绑定核心，使每线程仅需 64KB 缓冲（而非每连接 64KB），万级并发下内存从 640MB 降至 256KB，同时消除数据库连接争用。数据库层采用 SQLite 嵌入式投影，查询极快。HTML 模板层使用极简 hiccup 解释器，支持函数节点延迟求值与组件化调用，组件输出按函数与参数做内容寻址缓存，并借助 Caffeine 库的 WTinyLFU 算法自动过滤低频小条目、淘汰冷数据，避免缓存抖动。作者强调「不聪明」的广播策略反而让聚合优化成为可能。项目 hyperlith 已在生产运行，以 2 vCore 共享 VPS 支撑约 1000 并发用户、10 FPS。

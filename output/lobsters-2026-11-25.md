## 1. Hex.pm 安全事件：远程命令执行漏洞（CVE-2026-129514）

- 原始链接: <https://hex.pm/blog/security-incident-on-hexpm>
- 英文标题: Security incident on Hex.pm

2026年11月23日，Elixir 包管理平台 hex.pm 遭未授权攻击，攻击者利用远程命令执行漏洞（CVE-2026-129514）在 6 台 Web 服务器上运行命令，持续约 13 分钟，团队在 20 分钟内完成阻断与补丁部署。漏洞根因在于 hex.pm 使用 Plug.Crypto.non_executable_binary_to_term/2 解码未认证的 Erlang term 请求体时，虽阻止了函数和新原子，却允许含「__struct__」键的 map 通过。攻击者构造恶意 struct，经 Inspect 协议调用 Ecto.Query.DynamicExpr，再经 DBConnection.Stream 的日志回调触发任意代码执行。团队未发现包篡改或数据库写入，但因数据库读取无日志，无法排除攻击者获取了邮箱、密码哈希、API 密钥哈希、2FA 密钥等数据。已轮换全部服务器凭据，建议用户修改密码、重置 2FA 并更新 Hex 客户端，仅从 repo.hex.pm 获取包。同类漏洞亦存在于 Ash 框架（CVE-2026-124283），已于 11 月 24 日修复。该漏洞自 2016 年 2 月即存在于代码中。

- 英文标题: I checked Clojure's core with Lean and found 17 unreported bugs

## 3. 三分钟看懂 VP≠VNP 意味着什么

- 原始链接: <https://www.friedgil.com/vpvnp/>
- 英文标题: What VP != VNP Means (In 3 Minutes)

本文以行列式与永项（permanent）的对比，通俗解释了 Anthropic 近期证明的 VP≠VNP 定理的实际含义。行列式可用高斯消元法在多项式时间内计算，而永项——即去掉所有减法的行列式——至今没有已知的多项式时间算法；0-1 矩阵的永项问题甚至是 #P 完全的。VP≠VNP 的结论是：若将计算限制为仅含加法与乘法、规模关于输入大小为多项式的算术电路，则永项无法被高效计算。换言之，若 P=NP 成立，则必然存在某种超越纯算术（加、乘）的技巧，例如利用 AND/OR/NOT 等布尔门对输入位进行操作，从而在多项式时间内求出永项。然而目前尚不清楚布尔运算如何在此类问题上提供帮助。文章最后以幽默口吻指出：若你能想出这样的方法，便可去领取一百万美元的奖励。整体而言，该证明从算术电路复杂度角度给出了 P≠NP 的一个有力证据，但并未完全解决 P vs NP 问题本身。

## 4. 绕过 iOS Safari 60 FPS 限制：让 Web 应用拥有原生级流畅体验

- 原始链接: <https://rida.dev/blog/bypassing-ios-safari-60-fps-limit>
- 英文标题: Bypassing iOS Safari 60 FPS Limit

本文作者 Rida F'kih 探讨了如何在 iOS Safari 上突破 60 FPS 渲染瓶颈，实现 120 Hz 原生级交互。问题根源在于 WebKit 将 requestAnimationFrame 和触摸事件硬限为 60 Hz，即使屏幕支持 120 Hz ProMotion。作者的核心思路是绕过 JavaScript 渲染管线，利用浏览器合成器线程处理滚动。他构建了名为「控制器」的隐藏可滚动区域，通过 MessageChannel 配合 setTimeout 按设备刷新率节流、requestAnimationFrame 时间戳与 vsync 相位锁定，将滚动位置读取频率从 80 次/秒逐步提升至 120 次/秒；期间还利用空 rAF 循环强制 Safari 刷新位置、用隐藏 GPU 动画触发 ProMotion 满帧、以及按设备像素比缩放解决取整精度问题。渲染端则发现 OffscreenCanvas 配合 transferControlToOffscreen 可让 WebKit 跳过主线程渲染等待，从而在 canvas 上实现 120 FPS 输出。作者以此构建了一个 Liquid Glass 标签栏组件，通过 WebGL 纹理合成与着色器实现流畅的液态玻璃效果，实测控制器方案平均 118 FPS，低电量模式下仍达 60 FPS。文章最后提醒，Apple 有权随时改变 OffscreenCanvas 行为，作者更希望 Apple 直接为网页原生支持 ProMotion。

## 5. Lua 作为数据表示与配置格式

- 原始链接: <https://citrons.xyz/journal/2025-07-23>
- 英文标题: Lua for data representation

本文主张 Lua 虽以嵌入和扩展为设计目标，但其简洁与灵活使其同样适合作为通用数据表示语言。作者介绍了 Lua 多行字符串语法（如 [[ ]] 及带等号变体），并给出一个 stringize 函数为任意字符串生成正确的多行字符串字面量，同时指出 Lua 解析器专为处理大文件而设计。文章归纳了三种用 Lua 表示数据的风格：一是「JSON 风格」，直接 return 一个 table，但无法完全阻止任意代码执行；二是「INI 风格」，利用 Lua 的环境（environment）机制，以空环境加载配置文件并捕获其设置的全局变量，从而获得纯数据表；三是「命令式风格」，借助 Lua 省略函数调用括号的语法糖，写出类似 DSL 的配置代码，表达力最强。安全方面，作者强调对不可信数据应使用空环境沙箱、禁止加载字节码（load 的 mode 参数传「t」），并提及拒绝服务风险（如死循环、内存耗尽）可用 debug.sethook 部分缓解。最后，作者认为 Lua 在此场景的优势在于：项目已使用 Lua 时无需引入额外解析器，且可像 Lisp 或 Forth 一样构建任意复杂度的子语言，这是 JSON 或 INI 无法提供的扩展性。

## 8. iTerm2 通过 Kitty 图像协议 APC 响应注入实现任意命令执行漏洞

- 原始链接: <https://ii4gsp.github.io/iterm2-rce/>
- 英文标题: iTerm2 Arbitrary Command Execution via Kitty Image Protocol APC Response Injection

本文披露了 iTerm2（3.6.1–3.7.8）中一个 100% 可复现的逻辑型任意命令执行漏洞，默认安装即可触发，适用于 bash、zsh、fish 等所有 shell。漏洞由三个独立缺陷组合而成：其一，VT100 解析器的 APC 处理函数 executeAPC: 缺少 OSC 处理器中已有的 terminalIsTrusted 信任检查，任何 APC 序列均被无条件执行；其二，Kitty 文件传输（t=f）命令在文件不存在时，catch 块将 NSError.localizedDescription 直接拼入错误消息，而 macOS 的 localizedDescription 保留文件名中的字面换行符（0x0A）且不转义；其三，默认 verbosity 为 .normal，错误响应始终通过 screenSendReportData: 写入 PTY stdin，shell 将换行符视为命令分隔符从而执行注入内容。攻击者只需在任意文本文件中嵌入 APC 转义序列（cat 输出中不可见），受害者执行 cat 即触发。关键细节是 macOS 使用 Unicode 弯引号而非 ASCII 双引号，不会使 bash 进入引号模式。修复（3.7.9）通过两个提交完成：首个提交新增 sanitizedResponseMessage() 将 C0 控制字符替换为空格；后续提交将其扩展为覆盖 C1 字符的通用清洗函数，并统一应用于 Kitty 图像、Kitty 拖放（OSC 72）及标题报告三条响应路径。

## 9. cgo 指针检查的混乱现状

- 原始链接: <https://theconsensus.dev/p/2026/11/15/cgos-pointer-check.html>
- 英文标题: cgo's pointer check is all over the place

本文由 Shraddha Agrawal 撰写，深入剖析 Go 语言 cgo（FFI）的指针安全检查机制及其缺陷。文章首先回顾 cgo 的基本工作原理：cmd/cgo 工具在构建时解析 C 代码，生成 Go 与 C 两侧的桥接包装函数，通过「单指针+栈上连续内存」的方式绕过跨语言调用约定差异。随后重点讨论指针传递的安全规则：Go 指针指向的内存不得包含未固定的嵌套指针，且 C 侧不得在调用结束后保留 Go 指针。核心亮点在于揭示 cgo 的指针检查完全基于语法模式匹配而非类型信息，导致三类问题：（1）合法代码可能 panic——例如将 unsafe.Pointer(&s.small) 先赋给变量再传入 C 函数，cgo 无法识别该模式，退化为检查整个结构体对象中所有指针是否 pinned，从而误报；甚至多加一对括号也会触发同样问题；（2）性能差异悬殊——仅因 C 调用写法不同，同一次调用可从 48ns 膨胀到 76µs，相差约 1600 倍；（3）检查行为不一致，有时穷尽且昂贵，有时又过于宽松。作者指出该问题已存在约十年（golang/go#15318、#18184），根本原因在于 cgo 在语法层做转换而完全不了解 Go 类型系统。

## 10. 模拟磁盘故障的「噩梦模式」

- 原始链接: <https://antithesis.com/blog/2026/nightmare-mode/>
- 英文标题: Nightmare mode: simulating disk failures

本文介绍了Antithesis团队为分布式存储系统构建的磁盘故障注入机制「噩梦模式」。文章首先阐述磁盘不可靠性带来的复杂性：写入失败、空间不足、I/O延迟、断电致数据丢失等。核心方案是基于FUSE用户态文件系统模拟故障：团队先借助开源LazyFS实现断电模拟（清除内部缓存并杀死容器，等效真实断电），随后用Rust自研Amnesia，改用inode模型、全内存操作以提升性能与可扩展性。故障类型涵盖断电、撕裂写入、磁盘I/O错误（含fsyncgate bug中fsync返回EIO后页面被标记clean导致数据静默丢失）及延迟故障（乱序完成、部分完成以暴露并发竞争）。注入时机与Antithesis模糊测试器联动，采用「关联故障」策略，仅在磁盘操作前、中、后三个关键点触发，大幅缩小搜索空间。该机制已在客户软件中发现实际缺陷，包括etcd底层引擎bbolt中由I/O错误叠加断电触发的元数据损坏bug，验证了故障注入的有效性。

## 11. 依赖类型的代数：大Σ与大Π符号的由来

- 原始链接: <https://dotat.at/@/2025-05-28-types.html>
- 英文标题: the algebra of dependent types (2025)

本文从代数数据类型的计数视角，解释了依赖类型理论中为何使用大Σ（依赖对）和大Π（依赖函数）符号。作者指出，积类型（如元组）的元素数等于各分量元素数之积，记为 A * B；和类型（如枚举）的元素数等于各分支元素数之和，记为 A + B。依赖对（如「长度为 len 的数组」）中，第二个元素的类型依赖第一个元素的值，展开后等价于对 len 取所有可能值时各分支的总和，即求和 ∑，故用大Σ表示；当第二分量不依赖第一分量时，大Σ退化为普通积类型。依赖函数（如 repeat_zero(len) -> [i64; len]）的返回类型随参数变化，其纯函数计数相当于对每个输入取对应输出类型的乘积 ∏，即大Π，本质是指数类型。作者还提到「telescope」一词源自 de Bruijn 的 AUTOMATH 证明助手，用于指代多段依赖元组。最后，作者提醒读者避免使用「dependent sum」和「dependent product」等易混淆术语，因为「sum」在代数数据类型中指变体，而大Σ实际对应的是求和计数，二者含义不同。

## 12. 为非浏览器 TLS 客户端提供浏览器级证书验证

- 原始链接: <https://upki.rustls.dev/funding.html>
- 英文标题: Fund browser-grade certificate checking for every TLS client

本文介绍 upki 项目，旨在让非浏览器应用获得与浏览器同等的 TLS 证书信任决策能力。当前非浏览器客户端依赖操作系统缓慢更新的信任根，缺乏吊销数据（CRLite、OneCRL）、不信任日期和证书透明度策略等细粒度信息。2026 年 10 月 eMudhra 事件暴露了这一问题：浏览器可快速屏蔽受影响中间证书，而其他客户端只能等待平台信任库更新，造成大量缓解成本。upki 以紧凑本地缓存形式分发上述信号，自动更新、独立于应用，所有 TLS 栈共享一份；其检查仅收窄接受范围，不会引入新的信任。项目采用年度赞助模式（1.5 万至 15 万美元以上），路线图涵盖吊销检查（已发布）、根不信任（下一步）、Merkle Tree 证书（已申请资金）、CT 强制与中间证书预加载（计划中）等。当前已具备基于 CRLite 的离线吊销检查、C API（libupki）、OpenSSL 与 rustls 集成、缓存格式及镜像工具。Ubuntu 26.10 已集成基础支持，Go 1.28 提案拟默认启用 upki 吊销检查，OpenSSL 社区亦投票支持优先集成。项目托管于 rustls 组织，采用 Apache-2.0 与 MIT 双许可，核心团队包括 Dirkjan Ochtman、Joe Birr-Pixton 和 Daniel McCarney。

## 1. 工作中永远不应生气

- 原始链接: <https://www.seangoedecke.com/you-should-never-be-angry-at-work/>
- 英文标题: You should never be angry at work

本文主张工作中绝对不应该真正生气。作者认为愤怒在工作场所是毒性的：它会破坏会议或聊天氛围，让同事避之不及，甚至导致你被排除在关键决策之外，形成恶性循环——被忽视又加剧愤怒。然而，作者也指出愤怒往往源于对工作的在乎，而在乎是成为称职工程师的充分条件，甚至早期职业中偶尔的愤怒是“好错误”。但过度在乎会像水溢出管子一样变成愤怒，解决方法是调整关注点，让个人利益与组织目标对齐，或培养工作之外的生活以保持视角。作者还讨论了“展示一点点职业性愤怒”可能作为沟通工具，但强调能自由抽身才可行，真正的愤怒永远是错误。他以Linus Torvalds等名人反例说明，这些人的愤怒因权威而被容忍，普通人模仿只会适得其反。最后，作者认为愤怒只是“局部最优”，能让人感到自己重要且有影响力，但长期看会降低效率；找到更成熟的工作方式，才能真正在重要问题上发挥作用。

## 2. 软件变慢依然有理由：对LLM性能优化乐观论的质疑

- 原始链接: <https://typesanitizer.com/blog/performance-issues.html>
- 英文标题: There continue to be reasons for software to be slow

本文针对Dan Luu提出的“有了LLM，软件没有理由再变慢”的观点进行反驳，认为这一论断虽然用意良好，但在多数情况下前提不成立。作者承认LLM确实能降低某些性能优化的成本，但指出多个现实因素使优化仍难落地：第一，LLM驱动的异步工作模式（如智能体循环）改变了人们对延迟的容忍度，同步与异步体验的差异让人们接受更慢的性能；第二，许多公司软件部门被视为成本中心，预算原本就为零或极低，难以争取性能投入；第三，LLM反而压缩了项目预算，管理层期望更快交付，进一步挤压优化空间；第四，成本降低因子N常被高估，写代码只是成本之一，上线、维护、防回归以及避免破坏正确性（如Zig编译器并行化失败案例）的代价可能巨大；第五，性能工作未做往往并非预算问题而是优先级问题，LLM提高了吞吐量但不会自动改变优先级排序。作者还分析了Luu所举例子：pgrust在ClickBench上的优异表现疑似过拟合基准，且JIT在数据库中已有先例；FRE的代码量高达67万行，远超成熟正则引擎，且通用性能欠佳。最后作者表示，软件变慢的趋势既有真实技术原因，也可能包含感知偏差，但LLM并不能从根本上改变性能优化的现实困境。

## 3. OpenTelemetry进展不顺：我为此做了一份电子表格

- 原始链接: <https://matduggan.com/otel-isnt-going-well-and-i-made-a-spreadsheet-about-it/>
- 英文标题: OTel Isn't Going Well (And I Made A Spreadsheet About It)

文章分析了OpenTelemetry项目进展缓慢的深层原因。作者通过GitHub数据，将OTel各语言SDK与Envoy、Prometheus等CNCF项目对比，发现OTel存在严重的维护者集中问题：如PHP和Ruby SDK的大部分合并工作由个别人完成，而健康项目应有更分散的贡献者。同时，OTel对稳定性的严格承诺导致新功能推进缓慢——一旦标记为稳定就难以更改，维护者害怕出错而反复讨论，叠加覆盖语言和框架的庞大范围，形成恶性循环。作者认为核心问题是维护者不足，而非社区感知的‘进度慢’。为此他建议：引入有时间限制的Beta阶段，让实验性功能更容易被使用者体验和提供反馈；公开承认不同语言SDK的维护水平差异，避免假装平等，以吸引更多维护者。文章亮点在于用数据支撑观点，公开了原始数据供核查，并指出‘Approve Public API check’等流程需要更多维护者参与，是实际瓶颈之一。

## 5. Linus Torvalds 用 AI 调试 Intel GPU 驱动 bug

- 原始链接: <https://github.com/torvalds/linux/commit/818bebeb63dd6bf5f4e07e145f6cdbace520a34c>
- 英文标题: Linus Torvalds uses AI to debug an Intel GPU driver bug

正文是一份 Linux 内核补丁的 diff，修改了 Intel GPU 驱动 drivers/gpu/drm/xe/xe_vram.c 中 get_flat_ccs_offset 函数。原代码将 CCS（压缩存储）偏移用 round_up 向上取整到 128K，并断言该偏移等于 GSMBASE 减去 ccs_size。新代码改为用 round_down 向下取整到 4K，并将断言改为检查 offset + ccs_size 是否不超过 GSMBASE，以避免 CCS 与 GSM 重叠。补丁注释解释了原因：原取整方式会把 CCS 存储错误地发布为空闲内存；旧断言之所以从未失败，是因为 GSMBASE - ccs_size 本身是 128K 对齐的，即使实际基址未对齐，也会与向上取整后的偏移一致，而这正是本次修复的场景。修改后的逻辑更准确，能处理基址未 128K 对齐的情况，并保证 CCS 空间不与 GSM 冲突。整体来看，这是一次针对 Intel GPU 驱动内存布局计算的修正，核心结论是修复了潜在的 CCS/GSM 重叠问题，而标题所提的 AI 调试过程在正文中没有体现。

## 6. Gleam 语言的魅力之处

- 原始链接: <https://a.baez.link/3mtdbbp2dmc27>
- 英文标题: The cool things of Gleam

作者在学习 Gleam 语言一周后，对其简洁性印象深刻，并总结了几个关键特性。首先，@deprecated 属性可以标记旧函数并提示替代方案，帮助开发者平滑迁移。其次，todo 作为语言内置构造，不仅标记未完成工作，还能附带说明，比注释更直接。泛型方面，Gleam 以简单的类型注解实现，舍弃了约束泛型等复杂功能，换来了可读性。模式匹配通过 case 表达式统一实现，无论简单判断还是列表解构都清晰一致，不像 Elixir 依赖多种机制。Gleam 还彻底摒弃异常，用 Option 和 Result 类型显式处理缺失与错误，强制开发者编写可预测的代码。同样，语言没有 null，Nil 类型仅表示自身，空值场景一律使用 Option。总体而言，这些设计共同成就了 Gleam 的简洁性，这正是作者最欣赏的地方。

## 7. 下一代 trait solver 在 nightly 上默认启用

- 原始链接: <https://blog.rust-lang.org/2026/08/21/enabling-next-solver-on-nightly/>
- 英文标题: Enabling the next-generation trait solver on nightly

经过近四年的积极开发，Rust 编译器团队宣布下一代 trait solver 已接近稳定，并开始在 nightly 版本上默认启用，计划在未来数月内完成稳定化。这是 Rust 编译器自发布以来最大的单一改动，完全替代了旧的 trait solver，改变了 where 子句证明、关联类型归一化等核心机制。此次重构的主要收益将在未来显现，例如解锁 Type Alias Impl Trait (TAIT) 和 Return Type Notation (RTN)，支持新的隐式默认 trait 约束（如 Move 和 Forget），并修复类型系统中的已知不健全性问题。即便目前，该改动已修复了超过 200 个 GitHub issue，并对编译时间产生显著影响。文章同时指出了可能带来的兼容性破坏，并提供了禁用新 solver 的配置方法（通过 `-Znext-solver=coherence`）。具体变化包括 impl Trait（尤其是 RPIT）处理方式的改进，以及高阶类型中关联类型引用行为的修正。在编译性能方面，团队针对 top 20,000 crates 进行了对比优化，多数 crate 性能与旧实现相当，某些特征密集型 crate 获得大幅提升，例如 datafusion 的编译速度快了 8 倍以上。团队呼吁用户更新 nightly 并积极报告相关问题，以帮助完善诊断和稳定性。

## 8. LLVM 23 的编译时改进

- 原始链接: <https://aengelke.net/llvm23-ct.html>
- 英文标题: Compile-Time Improvements in LLVM 23

文章总结了 LLVM 23 在 -O3 构建中实现的编译时性能提升，整体耗时降低 6.75%（sqlite3 为 10.53%）。主要改进来自多个方面：在 ADT 层，哈希表改为线性探测并移除 tombstone 键，DenseMap 使用紧凑位数组存储占用率，同时将哈希函数切换为 xxh3；SmallVector 的 push_back 增长路径被外提并支持尾调用优化，BumpAllocator 也做了清理。支配树表示改为 child-sibling 形式并使用 bump 分配器，构建时不再具体化后继、前驱改用边列表，显著减少 malloc/free 调用。IR 数据结构方面，successors() 实现为 Use 范围迭代器，拆分 Br 为 UncondBr/CondBr，并将 BlockAddress 改为不引用基本块以加速前驱迭代；元数据附件改为单向量存储，调试位置改用普通 MDNode 指针；常量 isNullValue 改为预计算。块编号被更广泛地用于多个分析，减少了哈希表开销。后端方面，GlobalISel 在 AArch64 -O0 上相对 FastISel 的端到端差距从 12.71% 降至 9.39%，并移除了 -O0 流水线中的 localizer（但后来被回退）。Clang 端通过降低 switch 静态查找表密度阈值和避免重复计算当前位置元数据获得收益。此外，LLVM 改用预编译头文件，使构建时间缩短约 45%。整体来看，改进涉及数据结构、算法、后端和构建方式，属系统性的编译时性能优化。

## 9. 将卡西欧F-91W改装成非接触式支付设备

## 10. 不朽的1984年Macintosh（修复日记）

- 原始链接: <https://www.thebyteattic.com/2026/08/the-immortal-macintosh-restoration-diary.html>
- 英文标题: The immortal 1984 Macintosh (restoration diary)

这篇文章记录了一台1984年原版Macintosh 128K的完整修复过程。该机曾被原主人在1986年升级为Mac Plus主板，因此拥有1MB内存和SCSI端口，比原版更适合日常使用。作者修复时处理了大量老化部件：模拟板（电源与CRT驱动）上的电解电容全部更换；因电池漏液而整体更换了电池仓；更换了环氧树脂老化开裂的flyback变压器；将易爆的Rifa滤波电容换成现代安全电容；电源开关管、整流二极管和阻尼二极管均换成更高规格的现代器件，并刷新散热膏。数字板同样更换了电解电容，并补装了Apple原厂未焊接的CR1二极管，使SCSI口能提供5V，从而为BlueSCSI供电。软驱经过清洁润滑，更换了所有电容，并修复了因塑料老化碎裂的弹出齿轮。键盘和鼠标拆洗润滑，空格键与鼠标按键做了retrobright处理。机箱因严重黄变无法恢复，用汽车级2K涂料重新喷漆。最后用固态存储的BlueSCSI替换了原机械硬盘，并保留原电源作为装饰。CRT经过校准，画面对中良好。作者表示该机的所有已知故障点都已解决，它比出厂时更坚固耐用，成为一台“不朽的Mac”。

## 12. 编程语言语义与内存安全

- 原始链接: <https://burakemir.ch/post/formal-semantics/>
- 英文标题: Programming Language Semantics and Memory Safety

文章探讨编程语言的形式语义与内存安全的关系。作者用一个小型示例语言，分别从操作语义、指称语义和公理语义三种视角解释程序含义，对应开发者熟悉的解释器、编译器和断言。操作语义描述逐步执行；指称语义将程序映射为数学函数；公理语义用Hoare三元组描述前后条件。随后，文章分析C/C++中未定义行为（UB）的本质：在操作语义中，它是规范缺失导致的“卡住”状态；在公理语义中，它使前提为假，从而逻辑爆炸。编译器依赖公理语义，假设程序不会触发UB，并据此优化，例如越界访问可能被优化为死循环。这意味着一个内存安全错误会摧毁整个程序的可推理保证。作者认为，理解形式语义能看清内存安全的关键——需要数学上证明程序无UB。Rust通过所有权和借用检查器充当证明助手，保证内存安全，unsafe代码则需在注释中论证安全性。

## 13. 停止制作 TUI

- 原始链接: <https://sockpuppet.org/blog/2026/08/20/stop-making-tuis/>
- 英文标题: Stop Making TUIs

作者结合近期用 AI 辅助构建多个 macOS 原生应用的亲身实践，呼吁开发者停止制作终端用户界面（TUI）。他列举了 MDV 查看器、SageMath 计算前端、Apple Music 播放器、自驱动 Wiki、食物热量追踪器、温度传感器监控和 Apple TV 遥控器等示例，强调这些原生界面几乎无需手写 UI 代码，全靠 Claude 或 Codex 等模型按 SwiftUI 规范生成，且质量超过一般水平。作者认为命令行界面（CLI）有不可替代的用途，但 TUI 受限于 1970 年代的终端技术，即便借助 Ratatui 等框架也难以与原生框架的开箱即用体验竞争。他逐条反驳了支持 TUI 的常见论点：所谓高效密集的界面并非 GUI 不能实现；SSH 场景应使用 CLI 配合本地图形前端（如 Emacs TRAMP 的远程编辑）；TUI 的可访问性反而大概率更差；跨平台优势也不足以抵消体验损失。文章结论是，AI 已打破前端/后端、Web/原生的界限，默认选择构建原生图形界面如今既合理又可行，建议开发者重新校准认知，尝试用 AI 将琐碎的 CLI 工具升级为原生应用，这可能会改变对 UI 开发的整体看法。

## 17. 薛定谔的邮件：一次邮件转发失败的经历

- 原始链接: <https://yashgarg.dev/posts/the-schrodinger-email/>
- 英文标题: The Schrödinger Email

作者出于隐私考虑，想用邮件规则将银行邮件自动转发到Gmail，但发现Outlook的转发被Gmail拒绝。文章详细记录了排查和多次尝试的过程。首先，Outlook规则本身可以触发转发，但没有任何状态提示；Gmail的postmaster会发送硬性SMTP拒绝通知，原因是发送域名声誉极低。作者检查原始邮件头发现，第一跳认证全部通过（SPF/DKIM/DMARC均PASS），但转发会创建新的SMTP投递，第二跳的认证和声誉需要重新评估。作者解释了SPF、DKIM和DMARC在转发场景下的问题，并指出Outlook的Mailbox Rules Agent生成的重定向消息带有Resent-From等头部，且使用了@outlook.in身份。随后作者尝试添加@outlook.com别名并设为主别名，但转发仍使用旧身份，失败依旧。接着尝试引入Cloudflare Email Routing作为中间层，但增加转发层不能解决跨SMTP跳的认证与声誉问题。最后尝试Cloudflare Email Worker，希望通过代码完全控制转发，但Cloudflare会在消息到达Worker之前就执行SPF/DKIM/DMARC/ARC检查，认证失败的消息根本不会进入Worker。最终作者放弃技术方案，手动将所有银行相关邮件迁移到Gmail，感叹与邮件基础设施斗争不如直接手动处理。文章核心结论是：多跳邮件转发在现有认证机制下极易被拒，且主流服务没有提供简单可靠的转发方案。

## 19. 面向程序员的乐理：从第一性原理推导音乐体系

- 原始链接: <https://runjs.app/blog/music-theory-for-programmers>
- 英文标题: Music theory for programmers

本文面向完全不懂乐理的程序员，从“声音是随时间变化的数字”这一基础出发，用 Web Audio API 和 JavaScript 一步步推导出音乐的核心概念。作者先说明频率决定音高，音量包络决定音色质感；再引入谐波序列，解释为什么八度听起来像同一个音，以及简单频率比听起来和谐、复杂比或无理数比听起来刺耳的原因。接着展示纯五度叠加无法闭合回八度，产生所谓的“毕达哥拉斯音差”，说明完美调音系统不可能存在。随后引出平均律：把八度均分为十二个半音，用十二次根号二作为每步倍率，虽然除八度外所有音程都略有偏差，但换来的是可在任意调上演奏且音符可整数化表示。文章最后用暴力搜索证明“十二”是能用最少步数获得接近纯五度的划分，并说明 MIDI 编号如何把音高映射为整数。全文强调乐理不是死记规则，而是物理与算术的必然结果。

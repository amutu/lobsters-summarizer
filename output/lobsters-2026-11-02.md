## 1. 外部视角评析 Anthropic Scion 与 Mononoke 的关系

- 原始链接: <https://typesanitizer.com/blog/scion.html>
- 英文标题: An outsider's perspective on Scion and Mononoke

作者来自 Databricks 版本控制团队，长期研究 Facebook 的 Mononoke/Sapling、Google 的 Mercurial 及 jj 等工具，对 Anthropic 新发布的集中式版本控制系统 Scion 发表外部评论。技术层面，作者指出 Scion 的诸多设计——以 changeset 替代 Git tree、客户端与服务器非对称架构、水平扩展、无锁增量提交、稀疏工作副本、目录级 ACL、无完整 CI 的合并队列——均与 Mononoke 高度相似或属领域常识，部分借鉴在文章更新后才补充了出处。令人印象深刻的是，7 人团队在 5 个月内完成从 Git 到 Scion 的完整迁移，并首创用 Claude 担任各组件「superfan」进行异常检测。但作者也提出多项质疑： discouraging refs 的扩展性理由不充分；数百个 Git 镜像的必要性存疑；迁移前后性能数据（如 p50 pull latest 从 87 秒降至 3.5 秒）在稀疏检出和后台预取背景下难以自洽。非技术层面，作者批评文章「站在巨人肩膀上却不自知」，指出 Google、Facebook 早在 LLM 时代前就解决了类似扩展问题，文章语气兼具事实偏差与自我褒扬。

## 2. Pratt 解析：一个可以当作黑箱使用的工具

- 原始链接: <https://vinipsmaker.github.io/blog/article/pratt-parsing-is-a-black-box/>
- 英文标题: Pratt parsing is a black box

本文作者认为，绝大多数 Pratt 解析教程把精力花在解释算法本身，而真正重要的其实是 Pratt 背后的思维模式。Pratt 算法在高阶语言中仅九行代码，作者主张无需理解其内部实现即可直接使用，正如使用快排不必懂其源码。核心转变在于：传统解析（如 LL(k)）将语义动作绑定到产生式规则（非终结符），而 Pratt 将语义动作直接绑定到终结符上，分为 nud（左侧无内容）和 led（左侧有内容）两类。作者引用 Crockford 的概括：Pratt 将解析简化为一个问题——「一个 token 的左边期望看到什么？」。由此带来多项优势：天然避免左递归；无需回溯，仅比较绑定力数值即可迭代或递归；语义动作恰好执行一次，可安全携带副作用（如作用域管理）；动作内可任意前瞻，甚至嵌套 PEG 或组合解析器；语法歧义退化为查表冲突，设计负担大幅降低；表中空位天然成为扩展点，支持宏和语言自扩展。作者以自身编译器中的 nud 表、led 表和绑定力表为例，展示了实际工程中的组织方式，强调掌握这一思维框架比记忆任何细节都重要。

## 3. Kwi：一款全新的 KDE 终端模拟器

- 原始链接: <https://blogs.kde.org/2026/11/01/introducing-kwi/>
- 英文标题: Introducing Kwi, a new KDE terminal emulator

KDE开发者Eike Hein于2026年11月发布了全新终端模拟器Kwi，名称源自韩语「鬼」的罗马化。该项目基于Ghostty项目的libghostty-vt库与成熟的KDE Frameworks（如KPty），采用Qt Scene Graph实现Vulkan/OpenGL GPU加速渲染，UI由Kirigami构建并遵循最新KDE HIG规范。相比Konsole，Kwi在性能上提升3至35倍（DOOM-fire-zig基准测试中达870fps，Konsole仅23fps），同时在Wayland分数缩放、无障碍支持、Kitty图像与动画协议、OSC进度协议等现代TUI特性上更为完整。架构层面，Kwi提供可嵌入的Qt Quick/QML模块，填补了Konsole KPart无法被Qt Quick应用复用的空白，并统一了应用与组件的设置逻辑。作者强调Kwi目前仅为实验性提案，并非Konsole的替代品，而是为KDE生态提供新选项。项目尚处极早期，未发布v0.1.0，用户可通过KDE Invent的Flatpak每日构建进行试用。

## 5. OpenBSD 上 GEFS 文件系统移植工作持续推进

- 原始链接: <https://www.undeadly.org/cgi?action=article;sid=20261101115637>
- 英文标题: Work on GEFS (the Good Enough File System) for OpenBSD progresses

Ori Bernstein 正在将 GEFS（「足够好的文件系统」）移植到 OpenBSD，其 EuroBSDCon 2026 演讲广受好评。本文报道了最新进展：代码已重新整理并前向移植了 9front 的多数重要修复；错误处理路径已全面审查，理论上可正确处理大多数错误；文件系统默认保留首个 FS 块以容纳磁盘标签；用户空间工具已部分就绪，可在 OpenBSD 上执行 mkfs，但快照控制尚未完成。Ori 计划开发名为 gefs 的用户空间程序，提供 debug、usereserve、retain、snap、fork 等命令，接口风格参照 9front 的 ctl 文件。当前最大难点仍是一致性协议：理想方案是在提交阶段插入排序屏障，同时允许新块 I/O 继续写入。9front 上采用按（代次, 地址）排序的优先级队列实现顺序刷盘；Ori 考虑在 OpenBSD 中启动 syncer 内核进程执行同步 I/O，通过标记将 arena 头与超级块固定在缓存中不被重排，其余块可提前写回磁盘。他向 tech@ 邮件列表公开了思路并欢迎社区反馈与测试。

## 6. XKCD漫画与傅里叶级数

- 原始链接: <https://leancrew.com/all-this/2026/10/xkcd-and-fourier/>
- 英文标题: XKCD and Fourier

这是Dr. Drang博客上的一篇简短技术随笔，讨论了一期XKCD漫画与傅里叶级数近似之间的趣味关联。作者指出，熟悉傅里叶级数近似的读者看到该漫画后会产生三重反应：第一是会心一笑，因为能立刻认出漫画中隐含的数学概念；第二是意识到吉布斯现象（Gibbs phenomenon）的本质——向傅里叶展开中增加更多项时，振荡（ringing）并不会消失或衰减，而是逐渐集中到不连续点（角点）附近，那个「 ringing」永远不会真正消失；第三，作者自嘲地表示，一旦开始用数学思维去分析，漫画的笑点就被「毁掉」了。文中还给出了一个具体的傅里叶级数求和示例（对k取1、3、5、…、99的奇数项，系数为4/(kπ)，乘以sin(kπx)），用以直观说明吉布斯现象中振荡始终存在、仅位置集中的特性。文章篇幅极短，属于轻松的技术随笔，将流行文化与数学概念巧妙结合，适合在茶余饭后阅读。

## 7. 我为什么拒绝用大模型做安全研究

- 原始链接: <https://eva.ac/blog/llms>
- 英文标题: so i guess everyone uses llms to think now

作者是一名安全研究员兼博主，明确表示自己从未使用任何AI或大语言模型进行已发表的研究工作。他给出三点理由：第一，做研究纯粹出于乐趣，享受调试、逆向、阅读源码等动手过程，将工作交给AI等于剥夺了乐趣；第二，个人博客上的成果必须是自己完成的，无法将LLM的产出署名为己，也无法像引用人类合作者一样引用AI；第三，LLM自信地输出错误内容令他极度不适，使用体验令人抓狂。作者承认LLM确实强大，但强调当前阶段仍需要人类技能与经验来引导，并非人人可用。他批评了AI公司在网络安全领域的营销行为，以php2shell事件为例，指出Calif、OpenAI、Wiz三家公司各发博客、叙事不一，且OpenAI本可回移植补丁却未尽力。他还批评了在补丁发布前公开PoC视频、用哈希加产品名制造恐慌的做法，并以tailworm事件（一名研究者将极轻微的Tailscale提权漏洞当作重大0day在社交媒体上散布，未进行负责任披露）为典型。作者提到eMudhra的CA私钥漏洞实为人类用旧库偶然发现，并非AI之功。他呼吁人们别在AI浪潮中忘记动手的乐趣，个人项目应享受过程本身，因为写代码、逆向、折腾硬件带来的学习远非AI代劳所能替代。

## 8. groff/troff 宏包选择指南：ms、mm、me 与 mom

- 原始链接: <https://www.stephenlindholm.com/groff_macros.html>
- 英文标题: groff/troff macros: ms, mm, me or mom

本文介绍 Unix 排版系统 troff（及 GNU 克隆 groff）中 ms、mm、me、mom 四个宏包的选择。作者建议：一般文档用 ms，小说用 mom，结构化文档用 mm，me 因长期未维护不推荐。文章先解释 troff/groff 原理：文档为纯文本混合格式命令，需经处理生成 PDF 或 PostScript；命令分「请求」与「宏」两类，宏将格式与内容分离，便于统一修改和跨文档复用。随后对比各宏包：ms 由 Bell Labs 开发，上手简单但功能有限；mm 支持编号列表与交叉引用，功能丰富但网络文档匮乏；me 由 Berkeley 开发者编写，已停止维护；mom 由小说家编写，排版功能先进、文档完善。文章给出调用语法（如 groff -ms 文件 > 输出.ps），并以一份含标题、多栏、自动编号段落及签名行的 ms 示例，讲解段落宏、字体族、寄存器（数值变量）与字符串变量等核心概念，展示多栏切换、自动编号和制表符下划线等实用技巧。

## 9. 用 braindead-local-intelligence 轻松体验本地 AI

- 原始链接: <https://dataswamp.org/~solene/2026-11-01-braindead-local-intelligence.html>
- 英文标题: An easy way to try local AI with braindead-local-intelligence

本文介绍了一个名为 braindead-local-intelligence 的开源项目，旨在让普通用户无需复杂配置即可在本地电脑上体验 AI。项目基于 podman 容器，将兼容 OpenAI API 的大语言模型服务器、图像生成服务、SearXNG 网络搜索和 Open WebUI 网页界面整合到单一地址下，可选 token 保护。其亮点在于 LLM 与图像模型按需加载、空闲数分钟后自动卸载，避免显存冲突；文档提供针对普通硬件的预配置模型列表，切换模型只需复制配置块并重启。硬件要求为 Linux 加 podman 5.0 以上（rootless 模式），目前仅支持 AMD 显卡，最低约 4 GB 显存与 8 GB 内存即可运行小模型，作者用 2021 年组装的 32 GB 内存加 RX 6700 XT 即可流畅使用。作者实测 Qwen3.6 35B-A3B 配合网络搜索效果不错，但响应较慢；也将其接入 Mattermost 机器人供社区使用。文章最后提醒，本地 AI 在速度和上下文窗口上远不及云端服务，但适合隐私敏感场景或简单任务（如 CI 中的是/否判断、本地垃圾邮件过滤），是低成本探索本地智能的实用途径。

## 10. 万圣节特供：C++ 未定义行为引发的权限校验诡异现象

- 原始链接: <https://www.nablag.com/spooky_cpp>
- 英文标题: Spooky C++

本文以万圣节恐怖故事为包装，展示了一段 C++ 权限校验代码在开启 -O2 优化后产生反直觉结果的现象。代码中 Sanitize 函数接收 const std::string& 参数，返回一个 std::string_view，该 view 指向调用方传入的临时字符串。在 main 中，Sanitize(「foobarbazboo」) 返回的 string_view 在语句结束后其底层临时 string 已被销毁，属于典型的悬垂引用，构成未定义行为。在 -O0 下程序输出 false（权限校验正常），但在 -O2 下，编译器内联与内存复用使得已销毁临时对象的内存恰好与 admin_id 内容重叠，导致比较结果为 true，仿佛用户被错误授予 root 权限。作者验证了该现象在 C++17、C++20、C++23 标准下均存在，且 Clang 与 GCC 表现一致，排除了编译器或语言版本的特殊性。文章同时指出，该 UB 在真实工程中极难复现：它依赖输入字符串与 admin_id 长度完全相同、字符串以字面量内联传入等苛刻条件；将 admin_id 改为全局或单例变量、或将输入存入临时变量即可消除问题。作者认为虽然示例有趣，但此类 bug 在野环境中几乎不可能出现或被利用。环境为 WSL2 下 Clang 19.1.7 与 GCC 14.2.0。

## 11. 基于FPGA的专用Haskell处理器Ouros

- 原始链接: <https://bathtub-01.github.io/technical/ouros-demo/>
- 英文标题: A Specialised Haskell Processor on FPGA

本文介绍了作者博士研究中的Ouros处理器——一种面向非严格函数式语言的专用硬件，已部署于AMD捐赠的AUP-ZU3 FPGA板。Ouros采用组合子图归约架构，Haskell程序被编译为组合子图，执行过程是反复归约函数应用，而非传统指令序列。其核心组件包括解引用堆、归约器和ALU，数据以令牌形式在组件间流动，属于数据流驱动设计。Ouros支持自动细粒度多线程和并发硬件垃圾回收，无需软件运行时。IO通过IO monad的state-passing表示引入副作用，底层经AXI4-Lite总线完成读写，当前demo仅使用UART轮询。FPGA实现运行于100MHz，占用约27% LUT、7%寄存器和40% BRAM，逻辑规模与小型RISC-V核相当。作者也坦诚讨论了局限：不支持浮点、无内存层次、无动态加载和硬件中断。文章认为该设计虽速度不及PC上GHC编译代码，但展示了在极小电路预算内直接支持图归约、自动线程和垃圾回收的可行性，并展望了类树莓派的Haskell裸机嵌入式场景及全Haskell小型操作系统的研究潜力。最后给出了基于MicroHs fork、Chisel硬件生成、模拟器和Vivado工程四个仓库的复现指南。

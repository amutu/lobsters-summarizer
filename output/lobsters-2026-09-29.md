## 1. 「不内置AI」本身已成为LibreOffice的一项特性

- 原始链接: <https://blog.documentfoundation.org/blog/2026/09/03/yes-no-ai-is-now-a-feature/>
- 英文标题: Yes, no AI is now a feature

LibreOffice 26.8发布后，有用户提问「没有AI是否算一项特性」。项目方回应称，LibreOffice并非拒绝AI，但作为服务数千万用户的办公套件，在默认配置中引入AI功能须满足六项原则：用户可自主选择推理位置（本地、自有基础设施或自选服务）；文档内容未经用户授权不得离开本机；不收集任何遥测数据；不绑定单一供应商，接口须开放且可多后端实现；生成内容必须采用ODF格式以杜绝格式锁定；AI功能须完全可选，可安装、可移除，管理员可全局禁用。目前没有任何集成能同时满足上述全部条件，因此默认安装中不含任何AI功能。需要AI的用户可通过第三方扩展（多基于Ollama、LM Studio等本地模型）自行接入，但需自行评估数据流向。项目方强调，The Document Foundation作为非营利组织，没有订阅层级或数据变现压力，无需为季度财报赶工，因此有空间审慎评估技术是否真正惠及用户。未来随着本地推理硬件成本下降和开源模型进步，若出现满足全部条件的方案，项目将认真评估并纳入。

## 3. Lisp 为何难以阅读：括号位置与认知负荷

- 原始链接: <https://paultm.nl/paren-thesis>
- 英文标题: What makes Lisp difficult to read?

本文从认知科学视角分析 Lisp 语法可读性差的深层原因，作者认为问题远不止「不熟悉」，核心在于括号位置带来的额外认知负担。文章依次讨论了多个 Gestalt 视觉原则：邻近性方面，C 风格中参数间逗号与空格形成不同间距，模糊后仍可见结构分组，而 Lisp 中所有元素等距排列，无法在余光中传达层级；闭合性与对称性方面，C 风格中左右括号距离更近，可一眼匹配，Lisp 将函数名置于左括号之后，拉大了括号间距，尤其长函数名时更甚。在心理栈（工作记忆仅容 3–5 项）层面，深层嵌套迫使读者记住未闭合括号；左嵌套在 C 风格中可用 f(a)(b) 链式写法避免括号匹配，而右嵌套使阅读顺序与求值顺序相反，需两遍阅读。作者还指出，C 风格语言偏好命令式与对象方法链，天然让文本顺序对齐执行顺序，进一步降低认知成本。最后，作者认为中缀运算符和 if 等专用语法对可读性的贡献被高估，真正关键的是不同语法形式带来的视觉变化可作为「视觉地标」，并预告后续文章将深入探讨这一点。

## 6. 用 RLCD 解决大模型幻觉：让置信度从「感觉」变为可校准的概率

- 原始链接: <https://www.robw.fyi/2026/09/28/how-to-solve-hallucination/>
- 英文标题: How to Solve Hallucination (with RLCD)

文章指出，大语言模型输出的「90%确信」并非真实测量，而是与生成答案相同的下一词预测机制的产物，无法反映真实不确定性。作者将不确定性分为认知不确定性（可通过积累数据缩小）和随机不确定性（不可消除），并主张用概率分布替代单一数值：将结果空间划分为若干区间，让模型为每个区间分配概率，使总和为1。关键在于「校准」——模型声称某区间有30%概率，则实际结果应约30%落入该区间。RLCD（面向校准决策的强化学习）通过「预测—对比实际—打分—调整」的循环训练模型：生成多个略有差异的预测版本，以实际结果对各版本打分，只有概率与真实频率一致时得分最高，从而迫使模型学会「诚实」。校准后的概率可直接接入期望值计算与 Kelly 准则进行下注决策。文章以 NVDA 股票为例，展示未校准模型将95%概率堆在单一区间、而实际日波动率仅支持约30%的严重失准，说明校准仅覆盖训练数据分布，跨域需对开源模型（如 Laya）用自身数据做 RLCD 后训练。核心结论：RLCD 训练的不是答案本身，而是附着在答案上的数字的诚实性，唯有校准才能将模型置信度从主观「感觉」变为可接入下游决策的控制信号。

## 9. TimeLord：为 CPython 伪随机数生成器反向构造指定输出的种子

- 原始链接: <https://github.com/frazerpearce/TimeLord>
- 英文标题: Output-to-seed mappings for CPython's PRNG

TimeLord 是一个 Python 演示程序，展示如何为 CPython 的 MT19937 伪随机数生成器反向构造种子，使其产生指定输出序列（如 100 或 1000 个连续「正面」）。核心思路是先确定期望的未来输出，再反向求解初始条件。技术上，利用 MT19937 的 twist 和 temper 变换在 GF(2) 上为线性运算的性质，将每次掷币约束为两个比特条件，建立 XOR 线性方程组并求解得到满足要求的 MT 状态；随后反向通过 CPython 的 init_by_array 整数种子化过程，将状态还原为一个普通 Python 大整数种子。全程不修改生成器、不调用 setstate()、不做猴子补丁，最终效果可通过标准 random.Random(seed) 完全复现。文章还将该方法扩展到文本生成，可构造种子使随机程序输出任意指定 ASCII 文本。核心启示是：看似概率极低的事件（如 2 的负 100 次方），若种子是为达成该结果而条件性选择的，则并不意外；这与统计学中的后选择偏差、别处效应和选择偏差密切相关。该演示依赖 CPython 特定实现，不适用于密码学场景。

## 11. 二进制打包其实很有趣：从零构建 jBin 二进制序列化语言

- 原始链接: <https://hereticpleb.vercel.app/blog/packing-binary-is-fun-actually/>
- 英文标题: Packing Binary Is Fun, Actually

作者受社交媒体上「JSON 不是正经开发者该用的格式」的讨论启发，决定亲手设计一套二进制序列化方案，最终完成了名为 jBin 的二进制 schema 语言，声称可将 JSON 负载压缩约 80%。文章从最基础的 ASCII 编码讲起，逐步推导出 varint（LEB128）编码、用最高位作续接位、将 2 位 wire type（varint、f32、f64、delimited）与字段号打包进单个 varint 等核心技巧，并类比 C 结构体说明 schema 如何消除逐字段类型头开销。随后作者设计了一套简洁的 schema 语法，支持 message、enum、union、map、list 及自引用，刻意避免 protobuf 的冗长风格，用「数字. 名称: 类型」表示字段，用 end 关键字结束块，不依赖缩进。实现阶段选用 C++，完整构建了编译器管线：词法分析器（Lexer）将源码切分为 token，语法分析器（Parser）生成抽象语法树（AST），再经语义分析器校验，最终通过访问者模式完成代码生成，并附带命令行工具。全文风格轻松幽默，兼具教学性与工程实践价值，适合想理解二进制序列化底层原理的读者。

## 12. 专家星号：技术讨论中那些让新手分心的冷门补充

- 原始链接: <https://nedbatchelder.com/blog/202609/expert_asterisks>
- 英文标题: Expert asterisks

- 原始链接: <https://rustunit.com/blog/2026/09-04-bevy-ios-crates-objc2/>
- 英文标题: Dropping Swift entirely from our Bevy iOS crates

Bevy 团队宣布其 bevy_ios_* 系列 crate 已完全移除 Swift 包依赖，用户现在只需通过 cargo add 即可安装，无需再在 Xcode 项目中添加 SPM 包。此前每个 crate 都附带一个 Swift 或 Objective-C 桥接包，存在四种不同实现方式（@_cdecl、手写 C 头文件、protobuf C ABI、swift-bridge 加预编译 .xcframework），带来版本同步困难、CI 构建复杂、模拟器不支持等问题。团队统一改用 objc2 及其生成的框架绑定（objc2-ui-kit、objc2-user-notifications、objc2-game-kit、objc2-store-kit），利用 Objective-C 动态运行时实现通用桥接，将桥接从独立发布物变为普通依赖。回调方向通过在 Rust 中用 define_class! 宏定义 Objective-C 类并实现 delegate 协议完成，事件经 bevy_channel_message 传入 Bevy。重构后 bevy_ios_notifications 删除 2809 行、bevy_ios_gamecenter 删除 4430 行代码。唯一例外是 bevy_ios_iap，因 StoreKit 2 仅支持 Swift，仍保留一个由 build.rs 用 swiftc 编译的轻量 Swift shim，但同样无需 SPM。公共 API 变化很小，用户只需移除 Xcode 中的 SPM 依赖并升级 Rust crate 版本即可。

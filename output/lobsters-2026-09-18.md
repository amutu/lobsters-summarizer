## 2. 金质道钉：Valen 编程语言与 Rust 真正互操作的复兴之路

- 原始链接: <https://verdagon.dev/blog/golden-spike-reviving-vale-valen>
- 英文标题: The Golden Spike, and Resurrecting the Vale(n) Programming Language

Evan Ovadia 于 2026 年 9 月宣布启动一个极其雄心勃勃的项目：创建名为「Valen」的新编程语言，目标是实现与 Rust 的真正互操作（true Rust interop），让 Valen 编译器能与 rustc 无缝协作，从而在跨语言边界上同时保留泛型、内存安全、线性类型和组借用检查等特性。文章以 1869 年美国横贯大陆铁路的「金质道钉」为喻，指出编译器世界同样面临将两个遥远系统连接的难题。核心挑战在于跨语言泛型：C ABI 不含泛型，Rust 尚无稳定 ABI，导致其他语言无法直接调用 Rust 泛型函数。2024 年作者在 Vale 语言中曾通过解析 rustdoc JSON、运行 rustc 获取类型信息并生成 C 包装库的方式实现初步互操作，但存在需完全展开泛型参数、逐方法导入、C 类型无法实现 Rust trait 等限制。2026 年新方案改为以库形式调用 rustc_driver 的 run_compiler，让 Valen 类型检查阶段直接向 rustc 查询 Rust 依赖信息。然而 Rust 的 MIR 不支持组借用的共享可变引用、LLVM alias scope 及 comptime 元编程，因此 Valen 采用自有 IR 与后端，两个编译器的单态化器需协同工作以发现跨语言调用。项目仍处于高度实验阶段，线性类型、组借用（闭包除外）、跨边界结构体（须为零大小）等已部分可用，代际引用暂被禁用。

## 5. 带标签的正则匹配：为何这不是每个正则引擎的标配？

- 原始链接: <https://iev.ee/blog/categorize-everything-all-at-once/>
- 英文标题: Labeled matches: why is this not in every regex engine?

本文介绍作者自研的 RE#（resharp）正则引擎中的「带标签匹配」功能，并论证其为何值得成为通用能力。核心思路是为多条正则模式各赋予一个标签（如 DATE、MONEY、EMAIL），在文本中一次性完成多类命名实体识别，且执行代价与单次搜索相当。性能上，resharp 的 categorize_all 在 8 线程下达到 1.92 GB/s，比 spaCy 的 NER 组件快约 4500 倍。文章强调正则语言（regular language）的表达能力常被低估：借助交集（&）与补集（~）算子，可在纯正则框架内实现 if-then-else 条件逻辑，例如用 24504 字符的日历正则精确校验闰年与各月天数，而编译后仅生成 32 个 DFA 状态；经内部化简后模式缩减至 599 字符，并自动推导出格里高利历的闰年规则。标签在实现上仅是终态上的元数据，几乎零额外开销，且天然继承 SIMD 加速等优化。此外，作者利用集合论（A∩B 是否为空、A⊆B）提供正则重叠与包含检查，确保标签互斥，对应 CAV 2025 论文「Regex Decision Procedures in Extended RE#」。文章最后给出 Rust 端 RegexSet 的完整用法示例，并指出该功能已集成于 resharp 的 regex_set 特性中。

## 12. 为什么 .tar.gz 文件不能用 cat 合并

- 原始链接: <https://alexwlchan.net/2026/cat-confusion/>
- 英文标题: Why .tar.gz files can't be combined with cat

本文解释了为何无法用 cat 命令直接拼接多个 .tar.gz 文件，并从底层格式设计入手剖析原因。tar 源于磁带存储，采用固定块大小、顺序读取、追加写入的结构，每个归档末尾以两个全零块作为 EOF 标记，读取器遇到该标记即停止。gzip 则源于规避 LZW 压缩算法专利的需求，采用流式压缩，文件由多个 member 组成且无 EOF 标记，因此多个 .gz 文件可直接用 cat 拼接。问题在于 .tar.gz 是两层嵌套：gzip 层虽能顺利合并，但解压后 tar 层遇到第一个归档的 EOF 标记便停止读取，后续内容被忽略。正确做法是使用 Python 的 tarfile 模块，以「r:gz」和「w:gz」模式逐个打开源归档、提取成员并写入新归档，最终生成仅含一个 EOF 标记的合法 .tar.gz 文件。文章还顺带说明了 tar 中文件大小须预先声明、允许同名文件覆盖、EOF 后内容被忽略等特性，帮助读者建立对这两种格式的完整心智模型。

## 13. C++26：平凡无限循环不再是未定义行为

- 原始链接: <https://www.sandordargo.com/blog/2026/09/16/cpp26-trivial-infinite-loops>
- 英文标题: C++26: Trivial infinite loops are no longer undefined behaviour

在C++26之前，「while(true);」这类无副作用的空体无限循环属于未定义行为（UB）。C++11引入的「前进保证」规定线程最终必须终止、调用I/O、访问volatile或执行同步操作，而空循环不满足任何条件，编译器（尤其Clang）可将其完全优化删除，导致执行流意外落入后续代码。这一行为在嵌入式和内核代码中尤为危险，因为「while(true);」常被用作致命错误后的停机手段，优化后设备将进入不可预测状态。值得注意的是，C语言自C11起已通过额外规则（常量表达式控制的循环不被假定为终止）避免了此问题，C++却长期未跟进，造成不必要的语言分歧。C++26通过P2809R3提案修复了这一问题，定义了「平凡无限循环」：循环体必须为空（分号或空花括号），且控制表达式为求值为true的常量表达式。满足条件时，循环体被替换为std::this_thread::yield()调用，从而获得前进保证语义，编译器不再将其视为UB。该提案同时被接受为缺陷报告，实现方可将其回溯应用于更早的C++模式。此外，在freestanding（裸机）实现中，是否执行该替换为实现定义行为，以避免将刻意停机循环变为协作式让出。

BonoboMock 是一个与 GoogleTest 兼容的 C++ 模拟（mock）库，由 Bloomberg 开源维护，采用 Apache 2.0 许可证。其核心亮点在于：不同于传统模拟框架要求目标函数必须通过虚接口（virtual interface）才能被模拟，BonoboMock 能够直接模拟几乎所有类型的 C++ 函数，包括自由函数（含 extern「C」函数）、静态成员函数、非虚成员函数、虚成员函数、受保护成员函数、私有成员函数、重载与模板函数，以及 C++11 及以上版本支持的可变参数函数和 Lambda 函数。这一能力大幅降低了在测试中隔离依赖的门槛，使开发者无需为可测试性而额外设计虚接口。项目提供快速入门指南、食谱式示例和完整 API 参考文档。在协作方面，项目欢迎社区提交 Issue 与 Pull Request，要求贡献者遵循贡献指南并选用正确的 Issue 模板；所有变更需经维护者审查及公开社区讨论。项目设有行为准则、治理策略及维护者名单，安全漏洞报告需通过 opensource@bloomberg.net 私下提交，不在 GitHub 上公开。总体而言，BonoboMock 为 C++ 单元测试提供了一种灵活、低侵入的函数级模拟方案，适合希望在不改变生产代码结构的前提下编写测试的开发者。

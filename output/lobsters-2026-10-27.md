## 1. 网页应当适合打印

- 原始链接: <https://brennenputh.me/blog/printable-websites/>
- 英文标题: Websites Should Be Printable

作者Brennen Puth分享了自己为个人博客添加打印优化的经历。他习惯将网页打印为纸质文档阅读，但发现默认打印效果很差：正文字号偏大约两级、页眉在纸上极不美观、蓝色链接在黑白打印下呈灰色。他利用CSS的@media print选择器进行针对性调整：用onlyPrint和noPrint类分别控制打印时仅显示或隐藏的元素（如隐藏页眉、添加作者署名）；将正文设为12pt、各级标题设为13至16pt；为代码块添加黑色实线边框；将链接颜色强制改为黑色。他坦言这些调整耗费了大半天时间，且不确定有多少人真正会打印网页，但仍认为若网站以文本为主，让用户能以自己偏好的媒介阅读是一种对用户的善意。文章发布后意外登上Hacker News和lobste.rs首页，作者表示尽管CSS仍有缺陷，希望此文能推动更多人关注打印这一媒介。

## 2. 为什么发一封邮件这么贵？

- 原始链接: <https://evancz.dev/why-is-it-so-expensive-to-send-an-email>
- 英文标题: Why is it so expensive to send an email?

作者（Elm语言创始人、前GMail工程师）以自身实践探讨「为什么发一千封邮件要收15美元」。技术上，SMTP协议与HTTPS请求类似，用Haskell加OpenSSL即可实现，难度有限。真正障碍在于身份验证与反垃圾邮件体系：原始SMTP允许任意伪造发件人，如今需通过DNS TXT记录证明域名所有权。但即便通过验证，各收件箱提供商仍采用差异化信誉算法——有的关注域名，有的关注单个IP，有的按整个IP地址块判定。作者使用小型云服务商，其IP块中若有任何用户发垃圾邮件，整块都可能被拉黑，导致邮件无法送达。结论是：编写发送代码是一次性工作，但要被所有收件箱信任，通常需要拥有独立IP地址块并维持高日发送量，这才是商业邮件服务收费的根本原因。GMail的标签收件箱或许帮助其减少对IP块黑名单的依赖，但作者坦言并不确定。

## 3. eMudhra 中间 CA 证书泄露事件及 Apple 拦截措施

- 原始链接: <https://support.apple.com/en-us/149555>
- 英文标题: About the compromised eMudhra intermediate CAs

2026年10月，eMudhra 运营的 8 个中间 CA 私钥遭泄露，其中 6 个签发 TLS 证书，每个含 2 张证书（分别由 emSign Root TLS CA - G3 和 Sectigo 交叉签发），共 12 张。攻击者可利用这些密钥为任意网站伪造有效 TLS 证书，eMudhra 与 Sectigo 已吊销相关证书。Apple 自 10 月 19 日起在 Safari、Mail 及调用其网络与安全框架的应用中自动拦截这 12 张证书，并于 10 月 23 日进一步拦截 emSign ECC Root CA - G3，更新通过配置数据自动推送，无需安装软件更新。对于使用 curl、git、python3、ruby、perl、openssl 等命令行工具的用户，这些工具依赖 /etc/ssl/cert.pem 文件，在 Apple 发布后续更新前仍可能接受被拦截证书。管理员可选择手动从该文件中移除 emSign ECC Root CA - G3 及 AAA Certificate Services 根证书以提前生效，但需注意此举可能影响通过未受影响中间 CA 链至这些根 CA 的正常证书验证；每次 macOS 更新后需检查文件是否被覆盖并重新执行移除操作。

## 5. 更快的有符号64位常量地板除法

- 原始链接: <https://www.benjoffe.com/fast-floordiv>
- 英文标题: A faster way to compute signed 64-bit floor division by constants

本文讨论有符号整数「地板除法」（结果向负无穷取整）在除数为编译期常量时的快速计算。作者指出，主流语言与编译器（C/C++、Go、Swift等）不原生支持地板除法，现有库实现普遍使用较慢算法，某知名库甚至存在持续四年的溢出缺陷；而《Hacker's Delight》对此几乎未着墨。文章按时间线回顾了从标准截断除法的乘移修正、Granlund-Montgomery（1994）的通用模板、正除数XOR技巧到Robison（2005）的乘加技术，最终提出一种「符号选择乘数」新算法：根据被除数符号将预计算乘数偏移一个单位，再用一次128位乘加右移即得结果，无需分支。基准测试显示，在ARM平台上该算法吞吐量比现有最优快10%至20%，在x86上约80%的正除数快5%至10%。作者同时提供在线代码生成器，支持8/16/32/64位任意除数，生成MIT许可的C++内联函数，并附65535个除数的完整测试套件。该技巧还可推广至正模数与欧几里得除法。

## 7. 简易 NetBSD Web 服务器搭建指南

- 原始链接: <https://bsandro.tech/posts/simple-netbsd-webserver/>
- 英文标题: Simple NetBSD webserver

本文介绍在 NetBSD 11 上快速搭建 Web 服务器的「开箱即用」方案，适合家庭项目和小规模社区，不适合高流量场景。作者推荐使用系统自带的 bozohttpd 作为 Web 服务器，仅需在 /etc/rc.conf 中设置 httpd=YES、指定 www 用户和目录，再执行启动脚本即可通过 HTTP 提供静态文件服务。HTTPS 部分，作者选用 acme-client 包（OpenBSD 移植工具）从 Let's Encrypt 免费获取证书，需创建证书目录、编写 acme-client.conf 配置文件，运行 acme-client 命令完成签发，再通过 httpd_flags 将证书和私钥传递给 bozohttpd 以自动启用 443 端口。证书到期后通过 crontab 定时任务自动续期并重启服务。此外，bozohttpd 虽功能精简，但支持虚拟主机、CGI、HTTP 基本认证、Lua 脚本及 URL 重写等特性，manpage 信息丰富。作者还推荐了 netcup、panix 等支持 NetBSD 的 VPS 服务商，并提及 9front 和 TempleOS 作为其他可信赖的操作系统选项。

## 9. EQUALP 谓词下数字哈希的优化之旅

- 原始链接: <https://turtleware.eu/posts/Heavenly-delights-of-hashing-numbers-under-EQUALP.html>
- 英文标题: Heavenly delights of hashing numbers under EQUALP

本文记录了 ECL（可嵌入 Common Lisp）实现中，针对 EQUALP 谓词下数字哈希函数的多轮优化过程。作者最初在改进通用函数调度时，发现哈希表性能不足，遂着手重写哈希方案。核心难点在于 Common Lisp 的数字塔中，整数、浮点数、二进有理数在 EQUALP 下可互相等价，哈希必须保证等价对象产生相同哈希值，同时尽量降低碰撞。文章先回顾了基线方案——将所有实数强制转为 double 后哈希，虽简单但 2^60 与 2^60+1 等 64 位 ID 会碰撞。第一轮优化按类型分别处理：整数按位哈希、无分数部分浮点按整数哈希、二进有理数按 double 哈希、非二进有理数按分子分母对哈希，并修复了一个 double 转 fixnum 时因 53 位精度不足导致 2^61 被错误归入 fixnum 的边界 bug。第二轮提出更优雅的统一抽象：将所有二进有理数规范化为「符号、尾数、指数」三元组后哈希，彻底避免浮点与整数间的类型转换，概念清晰且碰撞极少。最后作者在不牺牲精确性的前提下，对 fixnum 等常见场景做工程简化以提升性能。新方案在 HTABLE-MIXBAG 基准上较旧版快约 100 倍，碰撞显著减少。

## 11. 用文章记录 Pratt 解析：从调度场到 Pratt 的演进

- 原始链接: <https://www.unix.dog/~yosh/blog/2026-10-25_pratt-parsing.html>
- 英文标题: writing about pratt parsing so I remember it

作者为构建 C 表达式解析器（未来可能扩展为编译器），系统梳理了 Pratt 解析的原理与实现。文章首先回顾调度场（shunting yard）算法：借助输出流与操作符栈，依据绑定力（binding power）决定运算符弹出时机，并给出了一段 C 语言实现，将「1+5*2+6」转为后缀序列。作者指出调度场的扩展性缺陷——括号、一元运算符、右结合等复杂行为会让逻辑变得混乱。核心转变在于：Pratt 解析用函数调用栈隐式替代显式操作符栈，仅在进入子表达式时递归，而非为每个优先级层级嵌套调用。作者给出等价的 Pratt 版 C 实现，将 expr() 函数分为前半段处理前缀（nuds）与后半段处理中缀/后缀（leds），从而让每个运算符可绑定独立子程序，扩展极为简洁。以添加括号为例，只需在绑定力表中加入「(」并在前缀分支调用一个 paren() 子函数即可。作者还提到可将绑定力与子程序选择合并为结构体，使核心逻辑保持简单而各运算符各自独立。文章参考了《Crafting Interpreters》及 Pratt 原始论文，并附有作者自行整理的结构化代码片段仓库，涵盖一元加减、后缀感叹号等扩展，旨在帮助读者（也帮助自己）记住这套优雅且易扩展的解析范式。

## 13. 用 AArch64 汇编实现简易数独求解器

- 原始链接: <https://blog.veitheller.de/Simple_Sudoku_Solvers_SIII%2C_EII%3A_Assembly.html>
- 英文标题: Simple Sudoku Solver in Assembly

本文为「简易数独求解器」系列新一集，在 macOS 的 AArch64 架构上以约 200 行汇编代码实现了一个数独求解器，与上一集 Agda 的「一切皆需证明」形成鲜明对比——汇编中没有任何类型检查、运行时或垃圾回收，正确性完全依赖程序员自身。棋盘为 81 字节平坦数组，置于 .data 段；候选数字用位掩码表示，数字 d 对应第 d 位（空格为 0，最终丢弃 bit 0），从而省去空值判断分支。求解采用回溯法：先执行传播（填充唯一候选格），再选取候选最少的空格，在真实机器栈上保存棋盘副本后递归尝试。位操作大量借助 CPU 原生指令：rbit+clz 定位最低置位、cnt+addv 统计位数、x&(x-1) 清除最低位，替代了此前在 Forth 中手写的循环。候选计算遍历行、列、宫共 27 格，用移位和或运算累积已用数字后取反。作者还介绍了 AArch64 寄存器约定、栈帧序言/尾声、宏系统等基础。性能方面，整个程序约 4 毫秒（含 1.7 毫秒进程启动），远快于 Python 参考实现的 70 毫秒和 Agda 的 2.7 秒。作者坦言更偏好有证明的版本，但享受「什么都不验证」的纯粹体验。下一集将转向 Verilog，进入纯硬件描述层面。

## 16. OpenLDK：将 Java 世界引入 Common Lisp

- 原始链接: <https://atgreen.github.io/repl-yell/posts/openldk-java-in-common-lisp/>
- 英文标题: OpenLDK: Bringing the Java World into Common Lisp

OpenLDK 是一个用 Common Lisp 编写的 Java JIT 编译器和运行时。其核心流程为读取 Java 字节码、翻译为 Lisp、再由 SBCL 编译为原生机器码，Java 对象与 Lisp 应用共享同一进程和堆，采用懒编译策略，仅在实际调用时触发编译。项目将 Java 类映射为 CLOS 类，Lisp 可通过 :before、:after、:around 等机制扩展 Java 方法行为；Java 异常映射为 Lisp 条件体系，支持 use-value 与 retry 重启。OpenLDK 支持在 Lisp 源码中内联嵌入 Kotlin、Scala、Groovy、Clojure、Kawa、JScheme、ABCL 共七种 JVM 语言，各语言保持自身语法，通过对象传递而非序列化实现跨语言交互。应用层面，已初始化的 Spring Boot 应用可保存为 Lisp 镜像，重启仅需约 84 毫秒，思路类似 CRaC 但基于 SBCL 镜像机制。性能测试中 OpenLDK 快照启动 83.9 毫秒，略慢于 GraalVM 原生镜像的 53.5 毫秒，但 OpenLDK 保留类加载器与 JIT 能力，支持运行时动态编译新类。当前目标平台为 Linux 上的 SBCL，仍存在字节码验证等兼容性缺口。

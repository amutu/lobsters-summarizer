## 1. 切换到 GitHub 替代品有意义吗？

- 原始链接: <https://lobste.rs/s/0zdh32/does_it_make_sense_switch_github>
- 英文标题: Does it make sense to switch to a Github Alternative ?

本文是 Lobsters 上围绕“GitHub 频繁宕机是否应切换替代品”的讨论。提问者因 GitHub 近几个月持续不稳定而困惑，并询问多数人何时会迁移。评论观点各异：有人主张个人项目不必迁移，可用自托管静态页或轻量方案；也有人指出多数项目并不需要 GitHub 的完整功能，反对“一刀切”，并倡议复兴小型项目集体（如 tilde 式共享基础设施），通过邮件列表、cgit 等自托管的协作方式。Codeberg 作为非营利、民主的开源平台被认为是一个选项，但规模有限。企业用户因深度依赖 GitHub Actions 等生态而难以迁离；个人开发者则可选择 SourceHut、GitLab、Forgejo 或 Radicle，其中 Radicle 通过点对点种子分发实现高可用。多数评论者认为“大多数人”不会真正迁移，因为网络效应和企业绑定太强；但对于开源项目，迁移即使保留镜像也是一种象征性信号，表明不愿长期依赖 GitHub。讨论还分享了具体自托管实践，如 soft-serve、Caddy、stagit 等。

## 2. GitHub 的替代品很多，但真正能替代它的还没有

- 原始链接: <https://lalitm.com/post/github-alternatives/>
- 英文标题: GitHub has alternatives, but no replacement

文章指出，尽管 GitHub 遭遇性能、可用性和 AI 功能喧宾夺主等问题，开源社区仍缺乏真正的替代者。作者以 Codeberg 禁止 AI 生成代码项目引发的讨论为引，认为关键缺口不是代码托管，而是社交层——GitHub 提供的共享身份、协作习惯和项目发现机制。自托管 Git 仓库看似去中心化，却对陌生贡献者造成门槛；GitLab、SourceHut、Forgejo、Radicle 等各有硬伤：或过于企业化，或工作流不亲民，或仍不成熟。GitHub 自身则因界面迟缓、PR 体验差和过度押注 AI 而令人生畏，Ghostty 的离开即是例证。作者认为，去中心化不足以构成替代，新平台必须把共享身份、约定和发现机制当作核心产品来建设，而非附带功能。他设想过一家类似 bunny.net 的“无聊公司”，以可靠协作和直接收费为宗旨，但承认冷启动问题极难解决——社交层只有达到规模才有价值，而这正是当前所有替代者都未能突破的瓶颈。

## 4. 我以为我在构建C语言的替代品，但我错了

- 原始链接: <https://c3-lang.org/blog/i_thought_i_was_building_a_c_replacement/>
- 英文标题: I thought I was building a C replacement. I was wrong

作者回顾了自己编程生涯的演变，从BASIC、Turbo Pascal到C/C++、Java和PHP，逐渐意识到自己最初对C3语言的定位存在根本性误解。他原先将C3称为“C替代品”，但发现如今“C替代品”在人们心中意味着替代C语言当下的主要用途——操作系统、嵌入式和高性能库，而他所追求的是将C语言带回通用应用程序开发的领域。作者通过PHP项目经验指出，面向对象并非高效开发的关键，面向对象强制提前架构，且“方法优先”的思维（如game.run()）会抑制重构，导致早期错误决策被锁定；而过程式思维（如run(&game)）更具灵活性。他认为C语言缺少现代应用所需的动态字符串、数组和映射等便利性，但又不想重蹈C++或Java覆辙，而是希望保留C的简洁和性能，同时提供适合现代软件开发的易用性。因此，C3的真正目标不是替代C，而是成为一种通用的应用开发语言，让C语言焕发新生。作者承认自己花了多年以错误的方式营销C3，如今将调整定位，强调其作为通用应用语言的潜力。

## 5. NixOS 下使用 kexec 实现免输密码重启

- 原始链接: <https://www.bevuta.com/en/blog/passphraseless-reboots-using-kexec/>
- 英文标题: Passphrase-less reboots using kexec under NixOS

文章介绍如何在 NixOS 上实现加密硬盘服务器的免手动输入口令重启。全盘加密在重启时需要人工输入 LUKS 口令，一旦中断就会卡在密码提示符，而且内核更新等场景经常需要重启。作者希望既保留加密安全性，又实现自动、快速重启。他们利用 kexec 机制让当前内核直接加载新内核，跳过固件和引导程序，节省数分钟时间；同时通过内存中的 initrd 传递一次性口令。具体实现是：在重启前用 cryptsetup 向 LUKS 添加临时密钥槽（keyslot 31），把随机生成的临时口令写入新建的 initrd 镜像；通过内核命令行指定该密钥文件，并保留 fallbackToPassword 作为手动输入口令的后备；在根文件系统挂载后立即用自定义 systemd 单元删除该密钥槽，确保临时口令无法泄漏。该方法结合了两种已有思路，避免在命令行暴露口令。最终重启无需人工干预，只需执行 systemctl start kexec.target，约 2 分钟即可完成。文章还提供了完整的 NixOS 模块示例代码。

## 7. 向下箭头为何不是翻转的向上箭头？

- 原始链接: <https://thefloatingcontinent.com/blog/upside-down-arrow-unicode/>
- 英文标题: When the Down Arrow is not an Upside-Down Up Arrow (2022)

文章探讨了一个字体渲染问题：在 MacOS 上，Unicode 字符“向上白色箭头”（U+21E7）和“向下白色箭头”（U+21E9）虽然标准定义应为镜像对称，但实际渲染出的形状却截然不同——向上箭头更矮胖，向下箭头更细长。作者通过检查发现，原因在于系统默认字体 Lucida Grande 只包含了向上箭头的字形，而不包含向下箭头；当浏览器无法在当前字体中找到对应字形时，会切换到回退字体 STIXGeneral 来渲染向下箭头，因此两者风格不一致。作者进一步追溯到历史原因：Lucida Grande 为了支持 Big5 编码而内置了向上箭头，该字形后来被映射到 Unicode 的箭头区，但字体创作者并未特意为整个箭头集补充字形。文章最后给出一个平台无关的解决方案：不直接使用向下箭头字符，而是通过 CSS 将向上箭头垂直翻转来模拟向下箭头，这样无论系统安装了哪些字体，只要存在向上箭头就能正确显示。这一现象也反映出 Unicode 标准与实际字体实现之间的差异，以及字体回退机制对文字显示的影响。

## 8. 计算星期几的更快方法

- 原始链接: <https://www.benjoffe.com/fast-day-of-week>
- 英文标题: A faster way to calculate the day-of-the-week

文章介绍了一系列快速计算星期几（day-of-the-week）的算法，核心是利用7是梅森数（2^N−1）的性质，通过乘法、加法和移位等少量指令实现高效模运算。作者对比了简单双模方法、Hinnant算法、Neri算法等现有方案，并提出了新的“乘-加-移位”技术：对于受限范围（约±24.2万年），仅需一次乘法、一次加法和一次右移即可得到结果；通过调整常量，还能以零额外成本输出ISO格式（1–7）的星期数。文章还给出了多种全32位范围变体，包括64位扩展、移位修正、双乘法等，针对x86和ARM进行了优化，并在AMD Ryzen 9和Apple M4 Pro上测试，新算法比已有方案快约2–3倍。一个突出示例是仅3条指令的序列，可覆盖整个有符号32位范围。该技术已应用于Rust的Jiff日期库，使相关函数提速40%。文章还讨论了算法的数学原理、与Hacker's Delight中方法的联系，以及向x % 24、x % 60等其他除数推广的可能性，适合对底层位操作和高性能日期库感兴趣的人。

## 13. 就地初始化的四个层次

- 原始链接: <https://blog.yoshuawuyts.com/four-levels-of-in-place-initialization/>
- 英文标题: Four levels of in-place initialization

文章围绕 Rust 中就地初始化（in-place initialization）的语法设计展开。作者认为不应引入单一特性，而应建立四级特性层级。Level 0 是裸指针与 MaybeUninit，最灵活但完全依赖 unsafe，无法静态检查，且无法在不移动或转为引用的情况下将所有权值标记为已初始化。Level 1 是借用引用（如 &uninit / &own 提案），将未初始化位置作为一等公民，使编译器能在合理时间内静态检查，同时保留高表达力。Level 2 是放置函数（placing functions），通过重写 return 关键字将返回值写入输出指针，语法更接近普通函数，无需修改签名，适合常见场景；作者建议将其编码为类似 const 的效果（如 with emplace）。Level 3 是 MIR 层自动消除移动的优化（RFC 3943），可提升现有代码性能，但作为优化不改变语义，不能依赖，因此无法支持 !Move 类型。文章对比了各层级在表达力、安全性、签名变化和语义保证上的差异，强调高、低级安全抽象应互补：易用场景保持简单，同时为需要控制的人保留底层能力。

## 16. 超越WASI：BrowserPod 3.0 让任意 Rust 应用在浏览器中运行

- 原始链接: <https://labs.leaningtech.com/blog/browserpod-rust.html>
- 英文标题: Beyond WASI: Running any Rust application in the browser with BrowserPod 3.0

BrowserPod 3.0 正式发布，新增对任意 Rust 应用在浏览器中运行的支持，同时修复了 Node.js 的诸多问题并初步支持 Python。其核心是提供浏览器内的代码沙箱，通过将 Linux 应用编译为 WebAssembly 并实现完整的 Linux 系统调用接口，使程序无需修改代码即可访问文件系统、发起网络请求、运行子进程并支持真正的并行。团队没有采用现成的 WASI 目标，因为编译真实 Rust 程序（如 Yarn）时需要大量平台适配、线程移除和功能降级。他们自行定义了 Rust 目标 wasm32-browserpod-linux-musl，通过自定义 target JSON、覆盖标准库及底层 libc 库实现。为绕过第三方 crate 对 wasm 目标的限制，他们将 target_family 设为 unix，并将 arch 设为 wasm64（LLVM 实际仍按 wasm32 处理）。实测 ripgrep、zpm、starship、jj 等大型项目无需改动即可运行，Codex 仅需关闭部分沙箱选项。用户可通过 rustup 安装工具链后用 cargo build 构建。未来计划采用 WALI 目标，以实现同一 Wasm 二进制在浏览器内外通用，并改善上游兼容性。

## 21. SCM_RIGHTS API 的古怪行为（2019）

- 原始链接: <https://gist.github.com/kentonv/bc7592af98c68ba2738f4436920868dc>
- 英文标题: SCM_RIGHTS API quirks (2019)

本文基于 Linux 实测，总结了 SCM_RIGHTS 辅助消息在 sendmsg/recvmsg 使用中的若干怪癖。SCM_RIGHTS 辅助消息附着于同一次 sendmsg 调用发送的数据字节范围，但接收端 recvmsg 与发送端 sendmsg 并非一一对应：消息可能被合并或拆分。接收辅助消息的 recvmsg 调用必须收到该辅助消息字节范围内的第一个字节，才会同时收到该辅助消息。为防止多个辅助消息同时交付，接收辅助数据的 recvmsg 会被人为限制，只读到该字节范围的最后一个字节为止，即使缓冲区中其后还有更多数据，且这些数据与任何辅助消息无关。然而，如果首次接收第一个字节的 recvmsg 没有提供足够的缓冲区来读取整个消息，下一次 recvmsg 将允许越过消息范围末尾，甚至进入新辅助消息的范围，并返回后一条消息的辅助数据。普通 read() 也会出现类似的提前结束模式，尽管它们根本无法接收辅助消息；这在使用边沿触发 I/O 时可能造成问题，因为短 read() 并不一定意味着没有更多数据。另外，单条 SCM_RIGHTS 消息最多可包含 SCM_MAX_FD（253）个文件描述符；如果 recvmsg 提供的辅助缓冲区空间不足以容纳整个描述符数组，消息会被截断以适应缓冲区，剩余描述符会被丢弃并关闭，无法通过多次调用来拆分列表。

## 23. Go 如何通过 sync.noCopy 检测结构体复制

- 原始链接: <https://func25.dev/posts/go-sync-nocopy/>
- 英文标题: How Go detects struct copies with sync.noCopy

本文深入解析 Go 中 sync.noCopy 标记的工作机制。sync 包中的 Mutex、Once、Map 等结构体都包含一个 _ noCopy 字段，但 noCopy 本身并不阻止复制，编译器对复制操作没有任何特殊限制。真正起作用的是 go vet 的 copylocks 检查器：它通过判断指针类型是否实现 sync.Locker 而值类型不实现，来识别不应被复制的类型。因此 noCopy 必须声明 Lock 和 Unlock 方法，使 *noCopy 实现 sync.Locker，而 noCopy 值不实现。检查器会递归检查结构体字段，因此能发现内嵌的 noCopy 或 sync.Mutex。在 sync.Map 中显式加入 noCopy，除了让告警更清晰，还修复了 LocalMutex 这类新定义类型因丢失方法而导致的漏报。忽略警告会产生实际故障：复制 WaitGroup 会导致 Wait 永久阻塞；复制已使用的 sync.Map 会让两个变量共享同一存储。文章还指出，noCopy 字段应放在结构体首位，若放在尾部，零尺寸字段会触发填充，使结构体在 64 位平台上从 8 字节增至 16 字节。整体帮助开发者理解该标记的原理，并学会在自定义类型中使用它。

## 1. Zig 0.17.0 发布说明

- 原始链接: <https://ziglang.org/download/0.17.0/release-notes.html>
- 英文标题: Zig 0.17.0 Release Notes

Zig 0.17.0 历经5个月、206位贡献者、925个提交，是迈向1.0稳定版的重要里程碑。核心亮点包括：构建系统全面重构并引入「Build Server Protocol」；ELF链接器大幅增强，预期x86_64-linux上增量编译已可普遍使用。目标支持方面，新增loongarch32、sparc64、xtensa等架构，标准库移植至x32与N32 ABI，并新增Switch、GBA、PSX、WiiU等游戏主机目标。语言层面，@bitCast语义改为基于「逻辑位表示」且与字节序无关，不再允许extern struct/union的转换；形式化语法与手写解析器现已一致并通过模糊测试；C翻译（@cImport）移至外部包；新增@backingInt、@fromBackingInt、@divCeil等内置函数。标准库引入SafeAllocator、改进ArrayList指针稳定性、增强格式化打印。编译器新增SPIR-V、aarch64、loongarch、WebAssembly后端；链接器增强ELF与COFF支持。工具链升级至LLVM 22、glibc 2.44、musl 1.2.5。语言稳定性方面，已接受约25个提案、拒绝约125个，距1.0又近一步。

## 2. 健忘的CPU：在M4上启动Linux

- 原始链接: <https://yuka.dev/blog-2026-10-02-linux-m4.html>
- 英文标题: The forgetful CPU (Linux on M4)

本文记录了作者在M4 Mac mini上首次启动Linux的完整历程。M4是首批强制启用SPTM（安全页表监视器）的Apple Silicon芯片，使传统m1n1虚拟机调试方法难以直接适用。作者通过禁用严格启动安全、安装m1n1、获取串口控制台逐步推进。调试中采用debug_putc（类似println）的二分法，先后解决了GXF功能锁定、RVBAR寄存器写入崩溃、MMU启用后MMIO空间未映射、设备树缺少stdout-path等问题。最关键的发现是：M4的WFI（等待中断）指令会清零x0-x31通用寄存器，违反ARM64架构规范，导致多核启动时崩溃。最终方案是通过新增idle启动参数，在裸机环境下将WFI/WFIT替换为NOP，该修复已合入主线Linux内核与m1n1，同样适用于M4 Pro、M4 Max及M5芯片。目前外设逆向工程仍在推进，作者呼吁关注上游项目的透明度与资金支持。

## 4. AI代理编程的「四骑士」：劣质代码、疏离、技能退化与团队裂痕

- 原始链接: <https://distantprovince.substack.com/p/the-four-horsemen-of-agentic-coding>
- 英文标题: The Four Horsemen of Agentic Coding

作者Alex Martsinovich指出，AI代理编程虽实用，却对开发者、工艺和团队关系造成严重损害，并将其归纳为四大问题。第一，「劣质代码」（Slop）：LLM生成的代码风格独特且令人不适，最新模型趋向「无法雇用的聪明」而非「令人振奋的聪明」，代码库沦为无人愿维护的荒地。第二，「疏离」（Alienation）：工程师不再亲手写代码，仅通过模糊指令驱动agent，与作品之间的情感纽带断裂，导致功能设计草率、修复敷衍，职业成就感下降。第三，「技能退化」（Deskilling）：AI的「一键操作」几乎无学习曲线，侵蚀专业技能的「用进废退」规律，资深工程师的存量优势难以长期维持，而要求新人不用AI并非可行策略。第四，「团队裂痕」（Team Fallout）：开发者各自与agent对话，团队聊天沦为agent线程，人际互助减少，技能表达空间消失，团队从多元协作退化为同质化的「prompt操作员」集合。作者坦言目前无解，但强调AI的收益正以好奇心、工艺精神和社会连接为沉重代价。

## 5. 泛型常量参数（GCA）特性族详解

- 原始链接: <https://blog.rust-lang.org/inside-rust/2026/10/02/generic-const-args-and-you/>
- 英文标题: Generic Const Args and You

本文是Rust常量泛型项目组于2026年10月发布的公告，系统介绍了「泛型常量参数」（Generic Const Arguments，简称GCA）特性族的设计与用法。GCA旨在替代自2021年min_const_generics稳定以来逐步演进的generic_const_exprs特性，允许在常量泛型中使用涉及泛型参数的更复杂表达式（如[u8; N+1]或[u8; T::NUM_BYTES]），从而减少用户对typenum等外部crate的依赖。GCA包含多个子特性：gca_adts支持在gca!宏内构造结构体、枚举、数组和元组；gca_const_items允许将任意常量项引入类型系统（需配合-Znext-solver）；gca_min_const_items是其精简版，仅接受以gca!表达式定义的常量项，避免后单态化错误并降低实现难度；gca_macroless_args与gca_macroless_items则探索隐式插入gca!宏以改善人体工学。所有新表达式目前必须显式写在gca!宏中，其语义与普通常量参数不同：允许引用泛型参数，但暂不支持算术运算和函数调用。文章强调当前所有特性均未达到稳定化标准，尚无法提交RFC，并邀请社区通过GitHub或Zulip反馈问题。

## 7. Docker 镜像层中隐藏的设计妥协

- 原始链接: <https://loige.co/hidden-design-compromises-of-docker-layers/>
- 英文标题: The hidden design compromises of Docker layers

作者在研究 SOCI（Seekable OCI）懒加载机制时，深入追问了一个看似简单却常被忽视的问题：Docker 镜像层本质上是 tar 归档，而 tar 没有删除操作，后一层如何删除前一层创建的文件？答案是 OCI 规范定义的 whiteout 约定：在层中放入名为「.wh.<文件名>」的空条目，表示删除前层中的对应路径；删除整个目录同理；若需保留目录但丢弃前层继承的所有子项，则使用更奇特的「.wh..wh..opq」不透明标记。作者强调，whiteout 并非 tar 本身的功能，而是 OCI 消费端在应用层时识别的特殊命名约定，直接解压 tar 只会得到一堆 .wh.* 文件。此外，层不可变意味着修改文件必须携带完整新版本，删除文件也不会缩小已生成层的大小，这解释了为何「下载-解压-清理」常需合并为单条 RUN 指令。最关键的妥协在于：整个「.wh.」前缀命名空间被 OCI 层表示法保留，无法在容器镜像中忠实地表示一个以 .wh. 开头的普通文件——这不是 Linux 的限制，而是序列化格式的固有限制。作者认为 tar 作为层基础是务实但存在阻抗失配的选择，whiteout 机制巧妙却略显 hacky，并进一步探讨了当文件名本身以 .wh. 开头时 Docker 的实际行为。

## 8. SequenceHash：面向通用哈希函数的安全多哈希构造

- 原始链接: <https://blog.trailofbits.com/2026/10/02/sequencehash-multihashing-for-the-rest-of-us/>
- 英文标题: SequenceHash: multihashing for the rest of us

Trail of Bits 发布了 SequenceHash 及其密钥变体 SequenceMAC，这是一对与底层哈希函数无关的安全多哈希（multihashing）构造，规范已纳入 C2SP 社区密码学规范项目。文章指出，多哈希是将多个输入值组合为单一哈希摘要的常见操作，广泛用于 Fiat-Shamir 变换、零知识证明、密码承诺及归档认证等场景，但简单拼接输入会导致严重的歧义与伪造风险。NIST 的 TupleHash 虽能解决该问题，却仅绑定 Keccak/SHA3，而 SHA3 采用率偏低，大量使用 SHA2 等函数的开发者缺乏标准方案。SequenceHash 采用 128 位定长长度后缀编码与双哈希结构，提供四项核心保障：无歧义输入编码、防长度扩展攻击、内置定制字符串实现域分离、以及带密钥的 SequenceMAC 模式。SequenceMAC 最小密钥 32 字节，通过将密钥长度纳入哈希头块，规避了 HMAC 中常见的密钥伪碰撞与尾零歧义问题。项目已提供 Rust、Go、Python 三种参考实现及覆盖多种哈希函数的测试向量，API 设计强调每次写入为独立的原子操作，与语言标准哈希接口相似但不完全相同，便于开发者快速集成。

## 9. 推力与方向控制（或：又一个邓宁-克鲁格效应的轶事）

- 原始链接: <https://write.as/tmcb/thrust-vs-steer-or-yet-another-anecdotal-case-of-the-dunning-kruger-effect>
- 英文标题: Thrust vs. Steer (or: Yet Another Anecdotal Case of the Dunning-Kruger Effect)

作者以三幕剧的形式讲述了一次耗时14小时的设备调试经历。第一幕：某设备在经历电源故障后，加速计行为异常。第二幕：作者借助大语言模型聊天机器人确认该设备加速计的方向映射确实存在已知问题（某主流开源项目中已有对应补丁），随后应用补丁并通过测试，过程中耗时约14小时，自感如同真正的黑客。第三幕：最终发现，在作者的实际使用场景中，主应用本身会根据设备朝向自行完成坐标转换，但这一转换仅在特定（尽管很常见）的事件序列触发后才生效，而作者在测试时未考虑该序列，导致全部工作白费。作者坦然承认这是典型的PEBKAC（或更精确地说是PEBDAC）——「字面意义上拿错了方向」。文章借此引出邓宁-克鲁格效应：一个人可能确实具备解决问题的能力，但偶尔会因过度自信而把简单问题复杂化，如同只想过马路却被喷气背包撞向邻居的墙。核心观点是：仅有「推力」（技术执行力）而缺乏「方向控制」（判断力与对上下文的准确理解），一切努力都可能南辕北辙。

## 10. 让 Futhark 的部分计算留在 CPU 上

- 原始链接: <https://futhark-lang.org/blog/2026-10-02-cpu_function.html>
- 英文标题: Keeping Futhark off the GPU

本文讨论了 Futhark 纯函数式数据并行数组语言中一个实际工程问题：如何在同一程序中让顺序部分跑在 CPU、并行部分跑在 GPU。背景是 Elias Smedegaard 的学士论文需要先用贪心算法对图做 distance-2 着色（本质为顺序嵌套循环），再用大规模并行计算稀疏 Jacobian 矩阵。Futhark 的 GPU 后端默认将所有数组放入 GPU 显存，导致顺序循环中逐元素访问 GPU 内存产生微秒级通信开销，性能比 C 后端慢三个数量级。理想方案是让编译器根据数组实际使用位置自动决定内存归属，但该优化涉及避免冗余拷贝、管理拷贝生命周期等复杂问题，短期内难以实现。作者最终采用了一个务实的「hack」：新增 #[cpu_function] 属性，将标记函数的输入与中间数组保留在 CPU 内存，函数结束时统一拷贝结果回 GPU 内存，从而让编译器仍可假设大部分数组在 GPU 上。该方案改动较小，成功使图着色阶段以高效顺序代码运行，而后续数值计算仍利用 GPU 并行。作者指出，即便未来编译器能自动推断内存归属，该属性仍可作为有用的提示保留。

## 11. 受 Emacs rx 启发的 JavaScript/TypeScript 可读正则表达式 DSL

- 原始链接: <https://rahuljuliato.com/posts/emacs-rx-in-typescript>
- 英文标题: Readable Regular Expressions for JavaScript/TypeScript, Inspired by Emacs' rx

本文介绍了一个受 Emacs rx 宏启发的 JavaScript/TypeScript 正则表达式 DSL，旨在解决复杂正则（如 SemVer 校验）难以阅读和后续维护的问题。核心设计是将正则片段表示为 RxNode 对象，通过 kind 字段（atom、seq、alt）决定拼接时是否需要添加非捕获分组括号，普通字符串经 literal 自动转义为字面量。DSL 提供 seq、or、anyOf、not、zeroOrMore、oneOrMore、optional、repeat、atLeast、between 等构建函数，以及 named 命名组、backref 反向引用、start/end 锚点、wordBoundary 等锚定符。一个亮点是 or() 对纯字符串分支按长度降序排列，模拟 Emacs regexp-opt 的最长匹配行为，避免 /in|int|interface/ 只匹配到「in」的经典陷阱。RX 函数直接返回 RegExp 对象，RX.flags 可附加正则标志；raw 允许将已有正则嵌入 DSL，便于渐进式迁移。与 Emacs rx 相比，该实现缺少 point、syntax 表相关形式及集合交集，字符类仅覆盖 ASCII，但用命名组替代了 group-n。全文以 SemVer 正则贯穿演示，最终代码可读性显著提升，并附带完整的 Emacs rx 与 TypeScript DSL 对照速查表。

## 13. 用 Rust 驱动 GDEH0154D67 电子墨水显示屏

- 原始链接: <https://sgt.hootr.club/blog/driving-gdeh0154d67-with-rust/>
- 英文标题: Driving the GDEH0154D67 e-paper display with Rust

作者购入开源电子墨水手表 SQFMI Watchy（ESP32 平台），因原固件为 C++/Arduino 且文档不足，决定用 Rust 重写。过程中遭遇 ESP32 上 Rust 支持尚处实验阶段的诸多困难：HAL 不支持深睡眠、Espressif 的 LLVM/rustc 在 NixOS 上难以部署、esp-rs API 频繁变动、esp-hal 放弃对 ESP32 v3.0 以下芯片的支持等。作者最终实现了加速度计、RTC 及 GDEH0154D67 电子墨水屏（SSD1681 驱动）的异步驱动。调试中遇到部分刷新图像损坏问题，根源在于该屏的 OTP 内存中启用了「ping-pong」机制，使 b/w RAM 与 red RAM 在每次部分刷新后交换，而软件重置会将指针复位，导致 diff 对象错位。修复方法是将绘制函数拆分为全刷（仅写 red RAM）和部分刷新（向 b/w RAM 写两次，确保两个 RAM 均持有当前帧），从而在有无软件重置的情况下都能正确过渡。最终作者以纯 Rust 实现了使用 Upheaval 字体的表盘，代码已开源。

## 15. 给初入职场的软件工程师的建议

- 原始链接: <https://www.seangoedecke.com/advice-to-a-beginning-software-engineer/>
- 英文标题: Advice to a beginning software engineer

作者认为，在LLM和AI代理带来行业巨变之际，新手工程师应对各类建议保持警惕，尤其不要盲信资深工程师的「政治斗争」式忠告。文章指出，当前行业已脱离ZIRP（零利率政策）时代，彼时工程师议价能力强、裁员风险低，而今天新手议价能力有限，应务实低调、友好尽责，避免卷入办公室政治。技术层面，作者强调「尽责」是工程师的核心价值：多提问、主动理解所参与的系统，几周专注即可掌握他人不了解的细节，从而创造独特价值。关于AI，作者建议不要恐慌，也不要完全回避——公司会像要求建筑工人使用电动工具一样要求工程师使用AI，抗拒这一趋势对新手极为不利。但关键是不能将判断力委托给AI，不能做「肉代理」原样转述AI输出，而应质疑、追问、形成自己的观点，把AI当作辅助理解的工具而非替代品。最后，作者鼓励新手不要失去希望：行业形态会变，但聪明、友善、尽责的人永远有价值，技术变革的连锁效应既有风险也有机遇，悲观论者几乎必然判断错误。

## 16. Klassik：在 KDE Plasma 6 上复活 KDE 3 经典桌面

- 原始链接: <https://linuxiac.com/klassik-revives-the-kde-3-desktop-on-modern-plasma-6/>
- 英文标题: Klassik Revives the KDE 3 Desktop on Modern Plasma 6

Klassik 是一个开源项目，旨在现代 KDE Plasma 6 桌面上重现经典 KDE 3 的视觉与交互体验。与单纯套用主题不同，该项目使用 Qt 6、Qt Quick、C++ 和 QML 从零重建了多个 KDE 3 面板组件，包括 K Menu 启动器、Quicklaunch、任务管理器、锁定与注销按钮、数字及模拟时钟等，并通过 QStyle 和 QPainter 渲染以尽量还原原始外观。项目还重写了 KDE 2/3 的 QStyle 应用主题，将旧版 KWin 窗口装饰移植到 KDecoration3 API（目前已包含 KDE 2 装饰），并附带 KDE 3 时代的配色方案与壁纸。底层仍依赖 Qt 6、KDE Frameworks 6 及 Plasma 6 库（如 PlasmaQuick、KSysGuard、KDecoration3），支持 Wayland 和分数缩放。安装方式为克隆 GitHub 仓库后用 CMake 编译，在系统设置的「颜色与主题 > 全局主题」中启用。开发者建议使用最新 tagged release 而非 master 分支。评论区中，有用户质疑其与 TDE 项目的区别，也有用户指出该方案不会降低系统资源占用，但整体评价认为它为 Linux 桌面生态提供了更多选择。

## 17. JetBrains Air：构建面向智能体软件开发的开放产品体系

- 原始链接: <https://blog.jetbrains.com/blog/2026/09/22/introducing-jetbrains-air/>
- 英文标题: JetBrains Air: Building a System of Products for Agentic Software Development

JetBrains 正式推出 JetBrains Air，一个面向智能体软件开发的开放多产品系统，覆盖开发者、团队与组织三个层面。产品包括 IDE 内智能体开发体验、团队协调与自动化工作流（Air Teams）、组织级治理与成本管控（Air Governance，原 JetBrains Central），以及编码智能体 Junie。文章指出，AI 已能生成代码，但组织仍需交付软件。瓶颈正从「生成变更」转向「理解、验证与承担责任」——代码生成变便宜，验证却更昂贵。个人采用智能体的速度远超组织基础设施，导致上下文断裂、成本不可归因、策略难以统一。Air 的核心设计原则是「多供应商」：不绑定单一模型，通过 ACP 标准连接外部智能体，让组织在保持可见性与管控的前提下自由选择工具。JetBrains 凭借 26 年工程智能积累，为智能体提供确定性代码理解能力，降低重复推理成本。未来 Air 将扩展至移动端与远程场景，支持由仓库事件和交付流程触发的工作流。最终目标不是产出更多代码，而是让软件可被理解、验证并为之负责。

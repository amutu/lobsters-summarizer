## 1. systemd 拥抱 Rust：集成策略与设计原则

- 原始链接: <https://amutable.com/blog/systemd-loves-rust>
- 英文标题: systemd loves Rust

systemd 项目宣布合并对 Rust 语言的支持，允许开发者在 C 之外用 Rust 编写组件。文章由核心维护者 Christian Brauner 与 Lennart Poettering 撰写，阐述了集成策略。核心结论：目前仅接受「叶组件」（独立二进制文件）使用 Rust，而「根组件」（核心共享库 libsystemd-shared.so）暂不可行，因 Rust 缺乏稳定 ABI 支持，静态链接对 180 余个二进制文件不现实。关键设计原则包括：共享库保持纯 C 并包装为 Rust crate 以统一 API 访问；C 与 Rust 二进制行为必须一致；构建继续用 meson 而非 cargo 以规避供应链风险；保守对待外部 crate 依赖；采用 no-std 模式；提供自定义 allocator 处理可失败分配；不无理由重写已有 C 代码；Rust 保持可选，不影响现有功能。文章呼吁 Rust 社区解决共享库一等支持及基于文件描述符的 I/O 等基础问题，并肯定 Rust 社区在 1.100 版本中快速回退破坏性变更的积极态度。

- 英文标题: Who wants to crowdsource LLM scans of articles submitted to Lobste.rs?

Lobste.rs用户wofo提议众包Pangram（主流LLM文本检测服务）的扫描结果，建立独立索引，以过滤社区中日益增多的AI生成垃圾文章（slop），并考虑以浏览器扩展形式展示，不强制改变Lobste.rs本身。该提议引发热烈讨论，分歧明显。支持者认为Pangram误报率极低（数万至数十万次运行中仅个位数误报），众包比各自扫描更省资源。但多数评论持反对或谨慎态度：多位作者反映自己的纯手写文章仍被Pangram标记为AI生成，质疑其可靠性；有人指出此举本质是「猎巫」，对无辜作者造成污名化，且对使用LLM辅助润色或翻译的写作者不公平；有人认为现有标记机制已够用，无需引入有缺陷的自动化工具。另有建设性建议：与其检测LLM使用，不如众包「承诺不用LLM」的网站白名单，或开发评估内容实用性的工具（如判断是否有具体问题陈述、建议是否可操作）。还有人指出，真正令人反感的是恶意灌水行为，而非LLM本身，检测LLM占比只是不良代理指标。整体而言，社区对以自动检测手段治理AI垃圾文章持较大疑虑。

## 3. 电子邮件系统原理简谈

- 原始链接: <https://maurycyz.com/misc/email/>
- 英文标题: A bit about email

本文以通俗方式梳理了电子邮件系统的核心机制。作者首先介绍邮件传输的完整链路：用户代理（MUA）经提交代理（MSA）和邮件传输代理（MTA）投递至接收方本地投递代理（LDA），这种分层设计源于1980年代单服务器时代对可靠性的需求，MTA会重试投递长达五天。随后文章演示了SMTP协议的工作流程，包括通过MX记录查找接收服务器、HELO/MAIL FROM/RCPT TO/DATA等命令交互及2xx至5xx响应码含义。在认证方面，文章解释了SPF验证发件IP、DKIM签名验证原始发件人、HELO正反向DNS一致性检查的作用，指出这些机制虽不能阻止垃圾邮件但能辅助过滤。消息格式部分介绍了MIME多部分编码、quoted-printable和base64编码的原理与局限，解释了附件体积膨胀约35%的原因。TLS方面，MTA间通信使用端口25的STARTTLS，客户端提交推荐端口465。文章最后提醒读者：邮件可能延迟数天送达；邮件本质是「数字明信片」，缺乏端到端加密；使用PGP等内置加密工具时需格外小心误操作。

## 4. 加密磁盘的无人值守重启：ZKeys 密钥托管服务

- 原始链接: <https://jmmv.dev/2026/11/zkeys-intro.html>
- 英文标题: Unattended reboots with encrypted disks

本文介绍了作者 Julio Merino 新推出的 ZKeys 服务，旨在解决加密磁盘在无人值守重启时的密钥管理难题。核心矛盾在于：密钥存本地则加密形同虚设，小偷可整机盗走；要求手动输入密码则无法实现自动重启。ZKeys 将密钥托管于远程服务器，客户端通过定期 keepalive 消息维持解锁状态；机器一旦离线（如被盗），服务自动锁定密钥，兼顾便利性与安全性。零知识设计上，服务器仅存储密钥的一半，另一半留在客户端，且密钥静态加密，即使服务器被攻破也无法还原完整密钥。但用户必须自行在第三方位置备份完整密钥，否则服务不可用时数据将永久丢失。技术实现上，CLI 工具用 Rust 编写，附带 FreeBSD（rc.d）和 Fedora（systemd/dracut）的集成脚本；后端基于作者自研的 III-IV 框架，前端采用 Bootstrap。服务目前免费提供，需使用 LAUNCH50 注册码，部署于 US West 和 EU West 两个非复制实例。作者呼吁社区贡献其他操作系统的打包与集成支持。

## 5. Mac mini M5 Pro 48GB 本地 AI 实际能做什么：社区经验汇总

- 原始链接: <https://lobste.rs/s/umsitb/what_can_i_realistically_do_with_local_ai>
- 英文标题: What can I realistically do with local AI on a Mac mini M5 Pro (48GB)?

本帖由一位刚入手 Mac mini M5 Pro（48GB 统一内存）的用户发起，询问本地 AI 在日常编程、图像生成、转录、RAG 等场景中的真实可用性。多位拥有类似或更强硬件的用户分享了经验。编程方面，Qwen3.8-27B 被公认为当前最佳本地编程模型，但长上下文受限、交互速度慢，更适合后台或夜间批处理任务；4-bit 量化在有限内存下性价比最高，更低精度会破坏模型。较小模型（如 gemma4-e4b）仅适合搜索摘要等低精度任务，不宜用于代码编辑。图像生成（ComfyUI）在 48GB 下能跑但速度偏慢，多数用户最终放弃，认为远不如云端大模型。语音助手和代码库扫描等轻量任务体验较好。多位用户坦言，对于需要高可靠性的编程工作，仍会回退到 Claude 等云端 API；本地部署的优势在于隐私和可控性。一位用户推荐了基于 llama.cpp 的 Unbiased Strata 推理引擎，通过预测 MoE 参数激活来热加载，仅需 12GB 显存加 96GB 内存即可运行 Qwen-Flash-Next，体验接近云端但略慢。总体结论：48GB 本地 AI 适合辅助性、隐私敏感或后台任务，严肃编程和高质量图像生成目前仍依赖云端。

## 7. Nspawn 3.0：为 systemd-nspawn 容器提供 Docker 兼容的 Engine API

- 原始链接: <https://blog.nspawn.org/posts/nspawn-3-0-a-docker-compatible-engine-api-for-systemd-nspawn-containers/>
- 英文标题: Nspawn 3.0: A Docker-compatible Engine API for systemd-nspawn containers

Nspawn 3.0 在主机上开放了完整的 Docker Engine API（兼容 1.51 及向下至 1.24 版本），socket 路径为 /run/nspawn/api.sock，由 nspawn-api.socket 管理。此前 2.0.0 仅提供只读 API 供 Traefik、Dozzle 等工具发现容器，3.0.0 则支持容器全生命周期操作（create、start、stop、exec、attach、archive 等）、镜像拉取与删除、卷与网络管理。用户可通过设置 DOCKER_HOST 环境变量直接使用 docker 命令操作 nspawn 容器，GitLab Runner 的 docker executor 也可指向该 socket。权限沿用 polkit 机制：root 拥有全部权限，其他用户需配置规则（如 nspawn-wheel.rules），且非 root 用户的连接数、日志流等资源有配额限制以防独占。破坏性变更包括：机器内挂载的 socket 由只读改为可写（可创建、删除容器），未运行的记录归为镜像而非容器，总线错误统一通过 org.nspawn.Error 返回。已知缺口为不支持镜像构建、加载、推送、swarm 及插件，docker build 不可用但 nspawn build 可用。3.1.0 新增 --device-cgroup-rule 支持热插拔设备，3.2.0 统一了机器与镜像的名称解析方式。Fedora、Debian/Ubuntu、Arch 均有预编译包。

## 8. 介绍 Project Steadfast：Ruby 通用宏工具

- 原始链接: <https://noteflakes.com/articles/2026-11-07-introducing-project-steadfast>
- 英文标题: Introducing Project Steadfast

作者宣布获得 Ruby Association 资助，在 Ruby 之父 Matz 指导下开发 Project Steadfast，旨在为 Ruby 引入类似 Lisp 和 Elixir 的 quote/unquote 宏机制，以替代传统 eval 字符串拼接式元编程。文章指出，eval 虽被 ERB、Rails 关联与脚手架等广泛使用以避免 DSL 性能开销，但存在易出错、易受注入攻击、代码构造繁琐等缺陷。作者以自身 Papercraft 项目为例，说明将 HTML DSL 编译为优化字符串拼接代码虽解决了性能问题，却使编译器本身极为复杂。quote/unquote 方案允许用 Ruby 代码构建 Ruby AST，再转回源码执行，既保留性能优势又大幅降低复杂度。项目范围涵盖 quote/unquote 工具、Prism AST 的生成与操作、AST 转源码等，并计划探索在 ERB、ActiveRecord、Roda 等流行 gem 中的集成可能性，同时研究该技术融入 Ruby 运行时的可行性与局限。Steadfast 是作者此前 Sirop 项目（Prism AST 转源码工具）的延续，预计 2027 年 3 月完成。作者希望这一新范式能推动 Ruby 元编程方式的革新。

## 9. 致开源开发者：不实行漏洞披露禁运期也没关系

- 原始链接: <https://opensourcesecurity.io/2026/10-embargo/>
- 英文标题: Dear Open Source Developers: It's OK not to embargo

Curl项目宣布，低危和中危安全漏洞不再走私有披露（embargo）流程，而是直接提交到公开issue tracker，按普通bug处理。作者认为这一政策值得所有开源项目借鉴。文章指出，传统embargo机制要求私下报告、禁用公开仓库与CI、无法引入社区审查、需管理PGP密钥等，流程极其繁琐，而当前每天新增数百个CVE，志愿者开发者根本无力应对。作者强调，寻找漏洞的成本已大幅降低，修复成本却居高不下，供需严重失衡，大量开源项目面临开发者倦怠甚至被遗弃的风险。对于公开漏洞可能带来的企业合规压力，作者提醒开源软件以「AS IS」方式提供，开发者不欠任何人即时修复的义务；一个被遗弃的广泛使用项目远比公开未修复的漏洞更危险。作者建议各项目参考Curl政策并自由调整，例如仅对严重漏洞保留禁运期，甚至完全取消禁运。核心结论是：维持现状已不可持续，保护开发者身心健康、维持健康的开源生态，比追求「零公开漏洞」更重要。

## 10. 虚拟化 Redox：从 Virtio-FS 到 Cloud Hypervisor 及更远的未来

## 11. 优化 Git 中引用删除的性能

- 原始链接: <https://nayak.im/posts/optimizing-reference-deletion/>
- 英文标题: Optimizing reference deletions in Git

本文讨论了 Git 中引用（reference）删除操作的性能瓶颈及修复。Git 的 files 后端将引用以松散文件（loose refs）或打包文件（packed-refs）存储。当仓库引用数量达数百万（如 GitLab 主仓库超过 1500 万条）时，packed-refs 文件可达数 GB，每次删除一条引用都需重写整个文件，耗时显著。作者为学习 Rust 并用 LLM 生成了 Rust 版 files 后端进行基准对比，意外发现 Rust 版比 C 版快约 18%。分析发现，C 版在回写未修改引用时调用 fprintf 和 oid_to_hex 重新格式化，而 Rust 版直接原样写入内存中的原始字节。据此，作者提交补丁，将 C 代码中未修改引用的回写改为用 fwrite 直接拷贝原始数据，跳过不必要的格式化。修复后性能提升约 17.4%，与 Rust 版持平。该补丁已合入 master（commit fc70f52），将随 Git v2.98 发布，为后续 Git 3.0（默认切换至 reftable 后端）做准备。文章也指出，files 后端已历经约 20 年优化，进一步改进空间有限，长期方向仍是迁移至 reftable 后端。

## 12. 在STM32MP2上跑裸机固件：从M33到A35再到PCIe的折腾记

- 英文标题: Playing with the STM32MP2

作者长期将STM32H7与FPGA搭配使用，但H7的FMC接口需30余根引脚且分布零散，在低成本四层板上几乎无法布线。ST推出STM32MP2后，其5Gbps SERDES可配置为PCIe Gen1/2 x1，仅需两对差分线即可连接FPGA，且保留了作者熟悉的STM32外设与AES-GCM/TRNG等IP。作者的目标是：仅用上游aarch64/arm工具链，不依赖厂商SDK、HAL、DDR、TrustZone或U-Boot，在EL3特权级直接运行简单事件循环，并让PCIe对接FPGA。他购买了STM32MP257F-EV1开发板，先完成M33辅助核的裸机启动（LED闪烁、从SPI Flash加载FSBL镜像、RETRAM与D侧总线别名映射等），再逐步唤醒双核Cortex-A35（1.5GHz），配置异常表、MMU页表（三级映射、1:1地址翻译）、缓存及时钟树，全程无需外部DDR，全部代码驻留片上808KB SRAM。PCIe方面，通过COMBOPHY和SYSCFG寄存器完成PHY校准与LTSSM链路训练，初始训练成功，但随后出现链路反复掉线重训的问题，作者借助高速示波器与ngscopeclient解码PCIe波形进行定位。文章还提及作者在调试中发现了一个具有安全影响的硅片缺陷，已通知ST发布公告。整体而言，MP2在算力上远超H735，但缺少ITCM/DTCM，且A核的MMU开销远大于M核的MPU，作者对此颇有微词。

## 13. 迟了二十年的 T-Mobile Sidekick 破解

- 原始链接: <https://x86.cx/blog/redanger>
- 英文标题: Hacking the T-Mobile Sidekick, 20 Years Too Late

文章记录了作者对 2002 年发布的 T-Mobile Sidekick（Danger Hiptop）进行逆向与破解的全过程。Sidekick 运行基于 Java 的 DangerOS，是「云设备」概念的先驱，但 Danger 于 2011 年关闭服务后，设备彻底失去后端。作者从 archive.org 获取 SDK 与固件，反编译后定位到 Danger 开发者计划使用的 512 位 RSA 自签名根证书。由于该密钥强度在 2026 年已可被分解，作者使用开源工具 CADO-NFS（数域筛法），在 7 台机器共 220 核上耗时约 8.5 小时完成分解，重建私钥后成功为 Sidekick 3 生成并刷入开发者密钥，解锁了 htconsole 调试控制台。随后作者用 JavaScript 编写轻量 Java 解释器，在浏览器中直接运行未经修改的 DangerOS 字节码，并重建了已消失的 Danger 服务器（Re:Danger），实现了时钟同步、消息推送（桥接至 Discord）和网页代理（可浏览 Hacker News）。作者还在真机上移植了视觉小说《Class of '09》。下一步计划是用软件定义无线电（Osmocom）搭建 GSM 网络，让真机连接 Re:Danger。文章也指出 Google 正推行开发者验证，与当年 Danger 的封闭签名机制形成呼应。

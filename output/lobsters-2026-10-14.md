## 1. Ente Locker 是否未经署名复制了 FairScan 的代码？

- 原始链接: <https://fairscan.org/blog/did-ente-locker-copy-my-code-without-attribution/>
- 英文标题: Did Ente Locker copy my code without attribution?

FairScan 作者在博客中披露，Ente Locker 应用在其文档扫描功能中使用了 FairScan 的分割模型，且其图像处理代码疑似从 FairScan 的 Kotlin 实现直接翻译为 Rust。作者于 2026 年 9 月 16 日收到 Ente 工程师邮件，对方最初称「从零编写」图像处理部分，随后改为模糊表述；9 月 21 日又辩称相关代码属于「标准图像处理方法」，并声称已在三天内重写逾 6000 行代码，但已发布的 1.0.9 版本无法追溯。作者通过 GitHub 对比指出，双方代码在整体结构、算法、函数与变量命名、硬编码数值上高度一致，难以用「标准方法」解释。作者向 Ente 版权邮箱发函询问 GPL 许可证合规问题，截至发文仍未获回复。作者 9 月 29 日在 Mastodon 发布事实性帖子，但几乎未获关注，感到沮丧。文章核心反思：开源透明并不意味着尊重，任何开源代码都可能被复制而不署名；作者原本预期代码来源会被诚实标注，却遭遇对方将个人大量投入贬为「标准方法」，这动摇了其继续参与开源社区的动力。作者呼吁其他开发者独立审视代码对比，给出公正判断。

## 2. vfmaddrnd231pd：一条从未存在的「幽灵指令」

- 原始链接: <https://purplesyringa.moe/blog/who-is-vfmaddrnd231pd/>
- 英文标题: Who is vfmaddrnd231pd??

作者在Intel SDM中发现一条名为vfmaddrnd231pd的FMA指令，声称可逐指令控制双精度浮点舍入模式，理论上能让依赖舍入的算法大幅提速。然而该指令在GNU汇编器中无法识别，Intel与Clang编译器均无对应intrinsics，在Haswell上执行会触发#UD异常，2026版SDM也已将其删除。经社区协助，作者还原了完整来龙去脉：2023年Intel因硬件限制无法在消费级CPU上加入AVX-512，转而设计AVX10扩展。由于AVX-512的EVEX前缀将舍入模式位复用为操作宽度，AVX10最初采用VEX前缀加立即数字节的方式实现256位自定义舍入，vfmaddrnd系列即由此诞生。但随后Intel改用EVEX前缀末位支持256位舍入并复用AVX-512编码，该方案被废弃；2025年AVX-512成为行业标配，Intel让AVX10无条件支持512位，整个临时方案彻底失去意义。GCC补丁中可见相关intrinsics被回退，命名与SDM中的「幽灵」指令高度相似。最终结论：vfmaddrnd231pd是AVX10原型阶段的产物，历经多次方案迭代后被废弃，但文档清理时有人遗漏，导致一条从未在硬件中实现的指令被正式记录在SDM中。

## 3. AI时代，新的好软件为何迟迟不见？

- 原始链接: <https://www.natemeyvis.com/where-is-all-the-new-good-software/>
- 英文标题: Where is all the new, good software?

本文针对「AI编程如此强大，为何我们没看到更多新的好软件」这一质疑，给出多条推测性解释。作者指出：其一，软件确实在改善，但体现为更少的缺陷、更好的性能以及现有产品功能的增强，而非全新产品的涌现；其二，大多数人很少尝试新软件，因此感知不到变化；其三，企业开发流程中的审批、协调等「政治子系统」尚未被AI加速，瓶颈仍在；其四，AI正以临时性、对话式交互（如用Claude报税）替代传统持久软件，用户获得了便利却缺少「发现一款惊艳产品」的体验；其五，AI将通用软件替换为领域专家自建的私有工具，外人难以察觉；其六，行业仍在「做更多软件」而非「让软件更好」；其七，开发团队将效率提升转化为更多休闲时间；其八，AI有时反而让人减少软件使用，转向人际互动或阅读。作者强调这些答案多为猜想，部分权重很低，但共同指向一个事实：AI带来的软件红利正以分散、隐性、非产品化的形式存在，而非集中表现为「新一代明星应用」。

本文是PostgreSQL核心开发者对19版本beta期间异常大量功能回退（约8至10项，远超每周期一项的常态）的公开反思。作者从多个角度分析原因：一是部分代码质量确实不足；二是团队同时推进了过多高难度功能；三是LLM辅助代码审查显著抬高了质量门槛，使大量边缘案例缺陷在beta期集中暴露，而相关功能多在LLM审查成熟前编写，相当于事后被提高了标准；四是「Vulnpocalypse」安全漏洞爆发期（约4月至8月）占用资深开发者精力，导致beta期常规审查和测试缩减，问题发现偏晚；五是PostgreSQL「万物兼容万物」的设计哲学使功能组合测试空间极大，缺乏足够脚手架支撑。作者强调这并非「vibe coding」问题，并指出社区长期讨论的「实验性功能」状态机制尚未落地，是具体待解决事项。展望方面，作者感谢社区支持，认为PostgreSQL 19仍将是稳健且具备亮点（如REPACK CONCURRENTLY、序列逻辑复制、pg_plan_advice等）的优秀版本，部分回退功能将尽快回归；PostgreSQL 20已有数个约80%完成的功能在排队，等待收尾。

- 原始链接: <https://stonetools.ghost.io/lotusimprov-next/>
- 英文标题: Lotus Improv on the NeXT

本文是博客「Stone Tools」作者对 Lotus Improv 这款 1988 年 NeXT 独占电子表格软件的迟来评测，恰逢 Steve Jobs 逝世十五周年与国际电子表格日。文章首先梳理了历史脉络：NeXT 急需独占应用，Improv 被寄予「VisiCalc 之于 Apple II」的期望；其多维数据建模、类英语公式与自由重排视图的理念，深刻影响了今日所有电子表格的透视表功能。作者使用 NeXTstation Turbo 搭配 NeXTSTEP 3.3 与 Improv 1.0 进行实测，指出 NeXTSTEP 虽外观朴素（2 位色深、固定 dock、可定位垂直菜单），但整体体验与现代 macOS 高度相似。Improv 的核心亮点在于：以「类别」和「项目」替代传统行列标识，公式以自然语言书写并集中展示于底部面板，完全透明；系统能自动检测公式冲突并交由用户裁决，而非静默覆盖；帮助系统支持上下文感知与「指向即帮助」。文章同时批评了 NeXT 版独有的「项目分配器」交互笨拙，Lotus 在 Windows 版 2.0 中已改为更直观的拖拽填充。作者认为 Improv 即便在今天仍无可替代，其设计哲学——「聪明地辅助，而非自作聪明地猜测」——值得当代软件借鉴。

## 6. Creusot 0.14.0 发布：为 Rust 提供形式化证明的合约支持

- 原始链接: <https://devlog.creusot.rs/v0-14-0/>
- 英文标题: Creusot 0.14.0 release - Contracts for Rust, formally proved

Creusot 是面向 Rust 的形式化验证工具，0.14.0 版本带来三项重要更新。第一，偏序支持：此前 Creusot 的 PartialOrd 规范仅支持全序，自 0.13.0 起已放宽为允许偏序。新定义采用布尔比较函数 lt_log（不可反身、传递），全序则作为额外定律（三择一：x<y、x==y、y<x）附加在 OrdLogic 上。值得注意的是，现有证明未受此变更影响，自动证明器顺利适配。第二，逻辑验证条件生成：Creusot 现在能为嵌入 Rust 程序中的逻辑快照（snapshot!）生成验证条件，使逻辑函数可充当引理函数。调用 snapshot!(lemma(n)) 时，工具会生成前置条件 hyp(n) 的断言和后置条件 concl(n) 的假设，且针对具体参数 n 特化，避免依赖证明器实例化全称量词。与程序函数调用不同，快照在编译时完全擦除，不引入实际函数调用，也无需通过借用检查器，从而更清晰地划分程序与证明的边界。第三，rust-analyzer 集成：Pearlite 规范中现已支持「跳转到定义」功能。实现中需让 rust-analyzer 展开规范宏，并修复宏展开后 token 跨度过粗导致搜索结果冗余的问题，最终使导航体验显著改善。

## 7. curl 8.23.0：更快、更精简

- 英文标题: A slightly faster slimmer curl

curl 团队在性能测试运行两个多月后，于 8.23.0 版本（10 月 14 日发布）中集中落地了一系列性能与内存优化。主要改进包括：内部 base64 编码速度提升逾两倍、解码提升 40%；URL 百分号解码提速逾两倍、编码提速约四倍；日期解析（如 Cookie 头中的时间戳转换）提速逾两倍；完整 URL 解析在数百条测试用例中快 20%–30%，并改善了非法 URL 的错误定位；libcurl 自带的 printf() 实现通过分块处理提速 5%–15%；通用数字解析（十/十六/八进制，64 位）通过减少边界检查提速近两倍。内存方面，easy handle 结构体从 4256 字节缩减至 3064 字节（约 28%），multi handle 从 900 降至 656 字节（27%），connectdata 从 824 降至 656 字节（约 20%）。以明文 HTTP 下载 512 MB 文件为例，分配次数从 100 次降至 96 次，峰值内存从 130,622 字节降至 126,875 字节（扣除 102,400 字节下载缓冲区后实际减少约 15%）。团队强调，这些优化对多数用户感知有限，但体现了「每一分都不浪费」的原则。所有性能测试已公开在 git 仓库中，方便社区贡献者自行验证和进一步加速。

## 10. 追踪 antcc 编译器中 -O2 性能劣化的根因

- 原始链接: <https://386s.org/w/lua-antcc-pessimization/>
- 英文标题: Chasing a -O2 pessimization in antcc

作者在为自己的 C 编译器 antcc 做基准测试时，发现 -O2 编译的 Lua 解释器反而比 -O1 慢 1.4 倍。排查过程中，他排除了内联阈值问题，发现主因是字节码解释循环 luaV_execute 在 -O2 下二进制膨胀 2.4 倍，但 IR 仅增大 11%。进一步分析寄存器分配阶段后，发现 IR 膨胀至 70%，超过 40% 的指令沦为栈与寄存器之间的 mov 搬运。最终定位到 mem2reg 优化 pass 的缺陷：当循环体内存在条件赋值的局部变量（如内联后的 luaV_tointegerns 中的 ib）时，mem2reg 将「变量初始未初始化」处理得过于字面化，未在当前块标记 UNDREF，导致递归查找跨越循环回边，在循环头部生成了本不应存在的跨迭代 phi 节点，造成 16 个 phi 同时活跃于整个循环，引发严重寄存器压力和溢出。修复仅一行代码：在 alloca 位置将变量初始化为 UNDREF，阻止 phi 跨越回边。修复后性能劣化消失。文章还提及该问题在 C 旧式变量声明风格下仍可能复现，可用 Tarjan 算法检测 phi 数据流环来彻底解决；作者亦提到借助 AI 辅助调试节省了排查时间，但 AI 未能自行找到根因。

## 11. 更快的傅里叶变换：一场大O记号下的「突破」幻象

- 原始链接: <https://www.argmin.net/p/faster-fourier-transforms>
- 英文标题: Faster Fourier Transforms

Ben Recht在argmin博客中评析了OpenAI数学仓库中声称实现更快傅里叶变换（FFT）的论文。文章首先回顾FFT背景：Cooley和Tukey于1965年将离散傅里叶变换从O(n²)降至O(n log n)，当n为百万时带来万倍加速。OpenAI的「main.pdf」声称log(n)项理论上略小，但作者通过让ChatGPT检索该论文发现，隐藏常数C约为10的100次方（N=10的12次方），意味着只有当n达到天文数字时该算法才比标准FFT快，属于Richard Lipton和Ken Regan所称的「银河系算法」。更关键的是，该算法依赖精确复数算术，要求超多项式增长的复数在单步内完成乘法，实际计算机根本无法实现。历史上，Morgenstern（1973）已证明系数有界时无法快于½n log n，Ailon进一步证明无严重数值不稳定则无法突破n log n。作者认为，这并非数学突破，而是计算机科学理论脱离实际计算模型的产物：理论界长期不鼓励实际运行算法，大O记号被滥用至失去工程意义。OpenAI的O(n^2.25)矩阵乘法等「重大结果」同样存在常数不可估计的问题。文章最终指出，AI放大了学术界「只证存在、不写实现」的不良文化，这些论文若润色得当本可投STOC或FOCS，但与真实计算机毫无关系。

## 15. 让 Nixpkgs 跑在 TypeScript 上：jinx 转译器

- 原始链接: <https://fzakaria.com/2026/10/12/nixpkgs-for-the-frontend-impaired>
- 英文标题: Nixpkgs for the frontend impaired

jinx 是一个将 Nix 语言转译为 TypeScript 的工具，作者用它编译了全部 nixpkgs（共 231,777 个属性），生成的 TypeScript 模块在求值时产生与 Nix 完全相同的 drvPath。作者的核心论点是：Nix 语言本身并不复杂，真正珍贵的是 nixpkgs 二十年积累的所有跨平台补丁、stdenv 阶段与 configure 脚本修复；但这也形成「陷阱」——任何想从新语言或新求值器探索 store 模型的人，都必须从零开始。jinx 的突破在于将整棵包树转译为 TypeScript，使 store 模型不再被 Nix 语言绑定。验证方面，在 x86_64-linux、aarch64-linux 和 aarch64-darwin 三个平台上，229,063 个属性 drvPath 完全一致，2,714 个在两侧均无法求值，差异为零。jinx 支持性能分析、编辑器自动补全与类型检查、断点调试、REPL 查询、node:test 单元测试以及浏览器内直接运行 nixpkgs 等场景，代价是比 Nix 慢约 3 至 5 倍、内存占用约 2 至 4 倍。项目无依赖、无原生代码、无守护进程，可用 Node 24 或浏览器直接运行，编译后的 nixpkgs 树以每次提交对应一个 nixpkgs 修订版的形式托管在 GitHub 上。

## 2. 堆叠拉取请求现已公开预览

- 原始链接: <https://github.blog/changelog/2026-07-30-stacked-pull-requests-are-now-in-public-preview/>
- 英文标题: Stacked pull requests are now in public preview

GitHub 推出堆叠拉取请求（Stacked PRs）公开预览功能。该功能将大型变更分解为一组有序的小型拉取请求（PR），每个 PR 代表变更中的一个独立层面。团队可以并行审查每个 PR，并通过一次点击合并整个堆栈，避免了大型 PR 审查缓慢或手动变更多个分支的麻烦。核心优势包括：保持大型变更推进（并行审查小范围 PR）、维护每层质量（结合分支保护）、灵活合并（全部或部分合并）。功能内置于 GitHub，现有审查流程、检查与合并要求均直接可用。技术领袖们给予高度评价，如 Vercel 的 Tim Neutkens 称其帮助 Next.js 在发布大型功能时引入更小变更；jQuery 创始人 John Resig 称赞直接合并 5 个堆叠 PR 到合并队列消除了大量摩擦。使用方式：安装 CLI 扩展（gh extension install github/gh-stack）后可在终端、github.com、移动应用或 GitHub Copilot 等编码代理中创建堆栈。审查时，每个 PR 只显示该层差异，堆栈地图展示全局关系。合并时，合并就绪的一层及其下方所有未合并层一键完成；部分合并则自动变基并重设目标。现存分支保护和必需检查依然生效。该功能正在所有仓库逐步推出，合并队列支持将在数周内逐步提供。更多信息可查阅文档并在反馈讨论区交流。

## 3. 灯泡的真相：你的认知被误导了

- 原始链接: <https://maurycyz.com/misc/tungsten/>
- 英文标题: You have been mislead about lightbulbs

本文揭示了关于灯泡寿命常见叙事的误解。人们常引用1925年灯泡制造商合谋将寿命标准化为1000小时的故事，认为这是为了迫使消费者频繁更换灯泡。然而，作者指出这种解读忽略了关键物理事实：更长寿命的灯泡在其他方面（如亮度和能效）往往更差。老式白炽灯靠钨丝发热发光，灯丝温度决定光色和效率；温度越高光越白、效率越高，但灯丝蒸发和变形也越快，寿命越短。因此，在寿命和性能之间存在根本性权衡。文中举例：加州消防站那盏号称运行120年的灯泡实际上仅消耗4瓦特，光线极暗，几乎无法用作正常照明——本质上是一个低效的残次品。早期手工灯泡成本高，故被优化为寿命极长但性能极低。自动化生产后，灯泡价格低廉，短寿命但高效率的灯泡反而更省电（因为电费远超灯泡成本）。因此Phœbus卡特尔设定1000小时标准并非单纯为了“计划报废”，而是为了避免厂商竞相生产寿命极长但性能糟糕的灯泡，从而误导消费者。作者强调，现实中产品设计充满妥协，长寿命不一定等于好产品，而灯泡故事不应被用作“计划报废”的典型案例。

## 4. C++ 浮点数转整数的未定义行为陷阱

- 原始链接: <https://kttnr.net/blog/cpp-float-to-int-conversion-undefined-behavior/>
- 英文标题: C++ float-to-int conversion can be undefined behavior

本文指出，在 C++ 中，将 float 转换为 int 时，如果截断后的值无法放入目标整数类型，则行为是未定义的（undefined behavior）。常见的转换方式如 int i = f; int(f); static_cast<int>(f); 均不会产生编译警告（即使开启 -Wall -Wextra），但实际存在 UB 风险。作者发现微软的 Guidelines Support Library (GSL) 中的安全窄化转换函数 gsl::narrow 也未能正确处理这一情况：尽管文档声称会在无法表示时抛出异常，但内部实现仍依赖 static_cast，导致某些输入触发 UB。GSL 维护者认为该 UB 在目标平台上是“良性的”，但作者反驳称 UB 本质上不可依赖——当前处理器（如 x86 的 CVTTSS2SI 指令）可能将其映射为 INT_MIN，而 AArch64 的 FCVTZS 会饱和处理，不同硬件结果不一致；更重要的是，编译器优化可能随时改变行为，使程序突然失效。作者建议在转换前进行边界检查，并参考 Rust 的饱和转换方案。此外，可用 Clang/GCC 的 Undefined Behavior Sanitizer（-fsanitize=float-cast-overflow）检测此类问题。文章强调，任何执行的 UB 都是潜在隐患，不应因当前运行正常而忽视。

- 英文标题: Progress toward compiling Linux with gccrs

## 6. DeskHop：快速桌面切换设备——开源硬件方案实现多机键鼠无缝共享

- 英文标题: deskhop: Fast Desktop Switching Device

## 9. 基于延续的通用模拟方法

- 原始链接: <https://crowdhailer.me/2026-07-30/a-universal-approach-to-mocking/>
- 英文标题: A universal approach to mocking with continuations

本文介绍了一种利用延续（continuations）实现通用模拟（mocking）的测试方法，可应用于同步/异步、可能出错或不可出错的计算。作者延续此前文章的思路，将延续反函数化（defunctionalise）为单一数据类型 `Effect`，通过捕获效果而非实际执行它们，让测试代码变得清晰可测。文章以一个业务函数 `task` 为例，该函数依赖一个 `fetch`（从字符串到字符串的带延续函数）。最初，测试时直接模拟 `fetch` 返回固定值，但存在不足：无法检验调用参数正确的顺序、不同输入对应不同输出、以及调用距离断言过远。改进方案是定义 `Effect` 类型，包含 `Fetch(key, resume)` 和 `Pure(value)` 变体，其中 `resume` 是用于恢复计算的延续函数。测试时，`fetch` 的实现仅构建 `Effect` 数据而不调用延续，运行函数返回一个 `Effect` 值列表，测试通过模式匹配逐一断言调用顺序、参数以及后续传递 `resume` 得到的值。这种方法带来的好处：无需特定测试模拟，实现共享；自动检查调用顺序和次数；断言值就近定义于测试中，可读性强。作者指出这种方式的代价是需要将延续引入所有含副作用的代码，但核心逻辑仍保持纯函数，副作用置于系统边缘。总体而言，它消除了对模拟库、存根对象、依赖注入框架和异步测试运行器的依赖，提供了一种统一、干净的测试方案。

## 10. GCC 指导委员会宣布 AI 贡献政策

- 原始链接: <https://lwn.net/Articles/1086041/>
- 英文标题: GCC steering committee announces AI policy

GCC 指导委员会采纳了 AI 政策工作组建议的 AI 贡献政策。政策核心规定：GCC 项目将拒绝任何包含 LLM（大型语言模型）生成内容或由其衍生的“合法重要贡献”，其中“合法重要”的定义沿用 GNU 项目维护者指南，阈值约为 15 行代码或文本。但维护者可自行决定是否接受 LLM 生成的合法重要测试用例。政策不禁止使用 LLM 进行研究、分析、漏洞发现与报告、补丁审查等活动，只要输出结果不直接纳入贡献中。委员会表示该政策将随时间演变并定期重新审视。社区讨论进一步澄清，若某段 LLM 编写的代码导致编译器崩溃，手动开发的修复方案属于漏洞发现范畴，因此是被允许的。政策的主要目的是避免版权风险，因为 LLM 输出可能源自许可证不兼容的自由软件代码，且其是否具有可版权性存在争议。整体来看，该政策在保护项目版权与允许 LLM 辅助开发之间做出了平衡，被认为比预期的更为合理。

## 12. std.Io.Writer.Allocating 耗尽了我的内存

- 原始链接: <https://www.openmymind.net/std-io-writer-allocating-ate-my-memory/>
- 英文标题: std.Io.Writer.Allocating ate all my memory

文章揭示了 Zig 标准库中 `std.Io.Writer.Allocating` 的一个内存分配 bug。作者通过代码示例展示：当使用预分配 1024 字节容量的 `Allocating` writer 写入 1025 个字符时，缓冲区的实际容量意外增长到 3204 字节，远超预期。若将写入拆分为两次（1024 + 1），则容量仅为 1668 字节，更合理。问题根源在于 `drain` 方法的实现：它错误地为每个输入数据块（包括最后一个作为“模式”的数据）都预留了额外的 `splat_len` 空间（即模式长度乘以 splat 次数）。即使用户只使用 `splat=1`，代码也会为每个数据块额外预留一份模式长度的空间，导致内存过度分配。作者指出，对于简单追加字节的场景，使用 `std.ArrayList` 更为高效，因为它没有 splat 机制，不会产生这种冗余预留。文章还提到 `splat` 功能实际用于压缩场景（如 zstd），但该 bug 使得普通写入操作遭受不必要的内存膨胀。

## 17. 按钮与链接的本质区别及Button Actions提案解析

- 原始链接: <https://unplannedobsolescence.com/blog/buttons-vs-links/>
- 英文标题: The Difference Between a Button and a Link

本文深入探讨了HTML中按钮（button）与链接（link）的核心区别：链接代表一个可独立导航的目的地，因此浏览器为其提供了丰富的重新上下文功能（如中键新标签打开、右键菜单、复制链接、书签分享等）；而按钮则代表在固定上下文内触发的动作，不支持这些重新上下文操作，这是有意为之的语义设计。常见的误解是“链接用于页面导航，按钮用于其他操作”，但作者指出两者均常触发导航（如登出按钮、搜索按钮会改变URL并加载新页面），而链接也可用于非导航场景（如页面内跳转、mailto、下载）。因此，决定用按钮还是链接的关键在于：操作是否需要在固定的、不可重新上下文的上下文中发生。例如，评论区编辑界面的“取消”按钮不应是链接，因为它的作用是关闭编辑视图，不应具备书签、中键打开等不相关功能。然而，当前HTML中按钮无法直接发起GET、DELETE等非表单的导航，导致开发者被迫使用链接并伪装成按钮，违反了语义，造成可访问性和行为不一致问题。为此，作者提出了Button Actions提案，为按钮添加action和method属性，使其能直接发起任意HTTP方法的导航，无需表单或JavaScript。该提案将简化HTML开发，使网页更简单、安全、无障碍，并为完整的CRUD生命周期提供语义化支持。

## 20. 简单游戏中的计时器设置（附帧规则详解）

- 原始链接: <https://lynn.github.io/blog/pico-timers/>
- 英文标题: Setting timers in simple games (feat. the frame rule)

文章介绍了在简单游戏中实现计时器的两种方法。首先，作者分享了自己在PICO-8（使用Lua）中常用的计时器系统：通过创建一个带元表的表`T`，其`__index`返回0，避免`nil`错误；在每帧更新中，遍历所有键并将值递减到0。使用时只需设置`T.glow=60`即可启动一个持续60帧的计时器，通过检查`T.glow>0`判断是否生效。这种方法也支持延迟触发（如`if T.blip==1 then sfx(2)`）、重复触发（如每10帧触发一次）和局部计时器（为每个敌人对象独立维护）。随后，文章对比了NES游戏《超级马里奥兄弟》中的计时器实现：由于硬件限制，所有计时器以单字节值连续存储在RAM中，最长只能计时约4.25秒（255帧）。为解决时间不足，游戏引入了`IntervalTimerControl`变量：大部分时间只递减前21个“快”计时器，而每当`IntervalTimerControl`耗尽（每21帧一次），才会递减所有36个计时器。这一机制导致关卡结束动画的计时与`IntervalTimerControl`同步，玩家无法通过操作改变其数值，只能以21帧为增量优化通关时间——这就是超级马里奥竞速中著名的**帧规则（frame rule）**。文章通过对比两种实现，展示了从简单游戏到经典游戏在计时器设计上的巧妙思路。

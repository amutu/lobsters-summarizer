## 1. 剖析 macOS 上 gcc 二进制的真实面目

- 原始链接: <https://zoey-on-github.github.io/blog/macgcc.html>
- 英文标题: examining the macOS gcc binary

本文通过反汇编深入探究了 macOS 上 /usr/bin/gcc 的真实运行机制。作者指出，macOS 的 gcc 并非简单的 shell alias，而是一个独立的二进制文件。反汇编发现，该二进制在启动时会根据调用名称（gcc、c++、llvm-gcc、llvm-g++ 等）做判断，最终调用 xcselect_invoke_xcrun()，即通过 xcrun 机制定位并执行真正的开发者工具。通过 xcrun --find gcc 可发现实际路径为 /Library/Developer/CommandLineTools/usr/bin/gcc。在该目录中，cc 和 clang++ 仅是 clang 的 alias，而 g++ 则指向同目录下另一个 gcc 二进制；进一步反汇编该二进制，发现它又通过 execv 调用 /usr/bin/xcrun 来执行 clang 或 clang++，形成多层间接调用链。作者推测这种设计源于 macOS 的 SIP（系统完整性保护）：/usr/bin 为受保护目录，Apple 无法在不重启的情况下更新其中的文件，而 Xcode 命令行工具可独立更新；不将工具目录直接加入 PATH 则是为了保留随时更改目录位置的灵活性。文章还附带了关键反汇编伪代码，展示了名称判断与 xcrun 调用的完整逻辑。

## 2. Docker 的「奇怪」之处：自研容器运行时的学习笔记

- 原始链接: <https://codeandcake.dev/posts/2026-10-22-docker-is-weird>
- 英文标题: Docker is weird

作者出于兴趣动手编写自己的容器运行时，借此深入理解 Docker 底层机制，并总结了若干「反直觉」的事实。第一，容器并非独立实体，本质上只是受特殊限制的普通进程，内核仍在运行它，且可在 /proc 中直接找到。第二，Linux 内核并没有一个名为「容器」的单一特性，容器实际是 namespaces（隔离可见性）、cgroups（限制资源）以及网络隔离等至少五项内核能力的组合。第三，镜像不过是文件夹，Docker 将其放置到某路径后，通过 chroot 或 pivot_root 将其设为容器进程的新根目录。第四，Docker 的运行时 runc 用 Go 编写，但 Go 原生多线程与容器运行时所需的单线程系统调用存在冲突，runc 不得不嵌入一个 C 模块在 Go 运行时初始化前完成关键调用；Go 也缺乏 fork，runc 转而通过 exec /proc/self/exe 并附加特殊参数来模拟 fork 行为。第五，Docker 守护进程通常需要 root 权限，因为许多内核 API 要求或曾要求 root；无 root 方案则需在用户空间重新实现整个网络栈。作者认为，亲手重写一个日常使用的工具是理解其内部原理的最佳途径。

## 3. 让网络自己「介绍」每个设备：结合 ARP 扫描与 DNS TXT 记录管理设备

- 原始链接: <https://unixdigest.com/tutorials/tell-your-network-to-explain-itself-and-then-some.html>
- 英文标题: Tell your network to explain itself and then some

本文围绕如何高效管理家庭或小型办公网络中的大量设备展开。作者先指出，给设备起有意义的主机名（如「johnslaptop」）在设备增多后极易混乱，而采用统一命名规范（如「区域.位置.类型.编号」）或影视角色名虽能缓解，但仍难以记住各设备对应的 IP 地址。作者推荐用 arp-scan 快速发现 IPv4 在线设备，它比 nmap 扫描快得多，但输出仅含 IP、MAC 及偶尔的网卡厂商信息，无法判断设备用途；IPv6 环境因使用 NDP 协议则不适用。真正的亮点在于利用 DNS 的 TXT 记录为每台主机附加自由文本描述（如「John 的 Intel i7-7700 Acer 笔记本」），配合 DHCP 实现 IP 与 MAC 的固定绑定，使设备每次上线自动获得相同地址。作者以 OpenBSD 上 dhcpd 搭配 unbound 为例，展示了只需在一处配置即可完成 IP 分配与 DNS 解析的方案；也提到 Raspberry Pi 上 Pi-hole 加 Dnsmasq 是更轻量的替代。此外，运行本地递归 DNS 解析器还能摆脱对 ISP 或公共 DNS 的依赖，并顺带屏蔽广告与遥测网站。文章核心结论是：将 ARP 扫描、DHCP 绑定与 DNS TXT 记录三者结合，能以极低成本让网络中每台设备「自我说明」，大幅提升可管理性。

## 4. 对象、属性与映射：动态类型语言的属性存储优化

- 原始链接: <https://bernsteinbear.com/blog/object-shapes/>
- 英文标题: Objects, attributes, maps, oh my

本文探讨动态类型语言中对象属性的存储与访问优化。作者指出，将属性建模为哈希表虽直观，但哈希探测与间接寻址导致频繁缓存未命中，严重拖慢性能。主流运行时因此采用「映射」（map/shape/隐藏类）机制：将属性布局抽象为不可变的树形持久化结构，对象内联存储属性值，通过映射指针快速校验布局是否变化。配合内联缓存（inline cache），热路径上仅需比较映射指针并按索引直接加载，彻底跳过字符串哈希。文章基于CF Bolz-Tereick的简洁实现，用不到500行Python代码演示了从哈希表到映射模型再到内联缓存的完整演进，并讨论了属性添加顺序对shape的影响、不同类可共享同一shape、集合存储策略的多态化拆分、类型冻结（将映射从「名称:偏移」扩展为「名称:(偏移,类型)」以减少类型守卫）以及类版本化等进阶优化。最后作者给出一个小型C++运行时，展示紧凑对象头、内联属性存储与溢出槽等真实运行时的内存布局，帮助读者在脑中建立完整图景。

## 5. 用 Caddy 仅暴露私有服务的分享链接

- 原始链接: <https://dataswamp.org/~solene/2026-10-21-caddy-forward-auth-public-share-links.html>
- 英文标题: Expose only share links of a private service with caddy

本文介绍了一种利用 Caddy 反向代理仅将私有自托管服务的分享链接暴露到公网的方案。核心思路是：服务本身仅通过 VPN 可达，公网 Caddy 站点仅放行分享链接相关路由；每个请求先由 Caddy 将 URL 中的分享密钥转发给后端验证，有效则放行，无效则返回 404，其余 URL 同样返回 404，使攻击者无法探测后端软件。文章以 Immich（照片库）和 Nextcloud（文件管理）为例给出完整配置：利用 reverse_proxy 配合 handle_response 实现验证（Immich 中 403 表示密钥有效，Nextcloud 中 200 表示令牌有效），用严格正则限定可访问的 API 路由，并剥离所有认证请求头，确保分享密钥是唯一认证途径。安全方面，该方案大幅缩小攻击面，使登录页、管理 API 等不可达，对近期 PHP 远程代码执行漏洞等威胁有显著防护效果。局限性包括：持有有效链接者仍可触发允许路由上的漏洞、应用更新可能改变路由、每次请求多一次验证开销。作者认为该模式适用于任何能验证分享令牌有效性的服务，值得自托管用户尝试。

## 6. 用 Rust 为 Rust 实现垃圾回收器（2023）

- 原始链接: <https://claytonwramsey.com/blog/dumpster/>
- 英文标题: I built a garbage collector for Rust (2023)

作者在一个夏天用 Rust 语言为 Rust 实现了一个名为 dumpster 的垃圾回收器，旨在解决标准库 Rc/Arc 无法处理循环引用的缺陷。文章从图论角度定义分配图与可达性，核心思路是在 Gc 的 Drop 时通过 DFS 加标记算法判断节点是否仍可达，不可达则批量释放。为遍历 Gc 内部的出边，作者引入 Collectable trait 与 Visitor 模式，要求被管理类型实现 accept 方法委托访问器遍历子 Gc。为支持 ?Sized 类型并解决类型擦除问题，作者设计了两类指针：瘦指针 AllocationId 用于哈希表键比较，胖指针 ErasedPtr 用于运行时恢复类型信息。为将单次 drop 的复杂度从二次降为线性，作者引入线程局部 COLLECTING 标志防止重入，并采用脏集合（dumpster）将回收操作摊销为均摊 O(1)。并发版本通过全局原子计数器 COLLECTING_TAG 为每个 Gc 打标签，在收集前递增标签，从而仅对受影响子图加锁，避免全局互斥锁带来的性能瓶颈。项目已开源至 GitHub 与 crates.io，整体在 Rust 这一以消除 GC 为设计目标的语言中，以相对少的妥协实现了可处理任意类型、支持并发、均摊常数时间的垃圾回收。

## 7. 用查表法修正线性近似以压缩枚举转字符串的查找表

- 原始链接: <https://www.corsix.org/content/using-a-lookup-table-to-correct-an-approximation>
- 英文标题: Using a lookup-table to correct an approximation

文章以将 DXGI 格式枚举值转换为字符串的 C 函数为例，展示了查找表逐步压缩的优化过程。原始 switch-case 实现在 -O0/-O1 下生成冗长汇编；-O2 起编译器自动将其改写为指针数组加边界检查。作者进一步指出，将全部字符串拼接为一段连续内存、改用 uint16_t 偏移量表替代指针表，可显著减小体积并避免重定位开销。核心亮点在于第三步：偏移函数 x→offsets[x] 近似为线性函数 x×17（由 382/22 四舍五入得到），其误差始终落在 [-9, +10] 区间，因此可用一个 int8_t 修正表替代原 uint16_t 偏移表，进一步缩小数据段占用。最终实现为 cases + (x*17 + corrections[x])，仅一次乘法、一次加法、一次查表即完成定位。作者总结出一条通用模式：当精确映射可被一个快速但略有偏差的近似替代、且修正量域足够窄时，用「近似 + 小修正表」往往比直接存完整表更省空间。这一思路并非全新，但作者认为仍值得反复提醒编译器开发者关注此类尚未自动完成的优化。

## 8. 用 Nix 管理脚本依赖

- 原始链接: <https://entropicthoughts.com/python-dependencies-with-nix>
- 英文标题: Script dependencies with Nix

本文介绍了一种在任意 Linux 发行版上用 Nix 管理脚本依赖的方法，无需安装 NixOS。作者以一个 Python 脚本为例，该脚本用 Trafilatura 提取网页内容、用 aplay 播放合成语音，涉及 Python 包与系统命令两类依赖。通过在脚本旁创建 flake.nix 文件，利用 writePython3Bin 将脚本封装为可执行文件：makeWrapperArgs 设置 PATH 以引入 Nix 管理的系统依赖，libraries 指定 Python 包。执行 nix run . 即可自动完成依赖安装并运行脚本，且结果完全可复现——复制到任何机器、隔一年再运行，行为一致。文章进一步展示该方法可推广至 R、Shell、Haskell 等语言（各有对应 writer 函数），对无现成 writer 的语言（如 Emacs Lisp、Ada）则使用底层的 makeScriptWriter 或 makeBinWriter，配合 compileScript 指定编译方式。作者强调 Nix 的核心机制（Unix 路径、环境变量、内容哈希）并不复杂，建议通过 Eelco Dolstra 的博士论文学习 Nix 基础，而 nixpkgs 中大量用法则需直接阅读源码。只要脚本语言已有对应 writer，换语言时基本只需替换 writer 名称，模板高度统一。

## 9. 一种不依赖 C 包装函数、可移植地获取 errno 的「野路子」方法

- 原始链接: <https://sebsite.pw/w/20260925-errno.html>
- 英文标题: a hacky fucked up way to portably access errno from outside of c

本文介绍了一种在 Hare 语言中不通过 C 包装函数即可获取 errno 值的非常规方案。由于 errno 在 C 中是宏，其展开方式不可移植，从其他语言调用 libc 后难以直接读取错误码。作者的核心思路是：利用 perror() 将错误描述写入 stderr，但在程序初始化时通过 dup/dup2 将文件描述符 2 重定向到一个临时文件，从而在不污染真实 stderr 的前提下捕获错误字符串；再在初始化阶段用 strerror() 预构建一张 256 项的错误消息表，将捕获到的字符串与表中逐项比对，反推出对应的 errno 数值。文中还讨论了可移植性上的两个棘手问题：一是 glibc 下「strerror_r」符号指向 GNU 版本而非 POSIX 版本，导致无法可移植地调用；二是 POSIX 未保证 SEEK_SET 等于 0，作者通过循环尝试 whence 值 0 到 2 来规避。最终目标是让 Hare 拥有一个通用「posix」编译目标，在任意 POSIX 系统上链接系统 libc 即可工作。作者认为这种「脏」但可行的技巧本身颇具趣味。

## 13. 手风琴头部：针对HTTP/3服务器的QPACK放大攻击

- 原始链接: <https://foxio.io/blog/header-accordions-qpack-amplification-attacks-against-http-3-servers>
- 英文标题: Header Accordions: QPACK amplification attacks against HTTP/3 servers

2026年10月，研究者Sébastien Féry披露了一类针对HTTP/3服务器的QPACK头部放大攻击。远程未认证攻击者仅需一条连接，即可迫使默认配置服务器分配比实际发送数据多数十至数千倍内存，导致OOM或资源耗尽。测试的10个实现中7个存在漏洞。攻击利用QPACK解码限制缺陷：部分实现仅校验压缩帧大小而非解码后大小、遗漏RFC规定的每字段32字节开销、默认无限制或根本未执行限制。两种主要变体为：一是用大量唯一短名称头部填满编码预算（约1MB帧可展开为16万余头部）；二是通过动态表插入大条目后以单字节引用反复触发完整拷贝，放大比可达4064:1。受影响实现包括quic-go、Cloudflare quiche、lsquic、Wireshark、Bun、h3及aioquic/mitmproxy，其中前四者已发布修复版本，Bun与h3仍未修复；IIS、Envoy、ngtcp2/nghttp3及Google quiche不受影响。修复核心在于解码过程中强制执行累计头部大小预算，而非仅检查压缩帧长度。

## 15. 理解 Nix flakes：实验性但日益普及的可复现构建机制

- 原始链接: <https://lwn.net/SubscriberLink/1094226/7bb13383b169d475/>
- 英文标题: Understanding Nix flakes

本文系统介绍了 Nix 包管理器中的 flakes 实验性功能。flakes 通过 flake.nix 文件将依赖以 URL 式引用声明为 inputs，并以 Nix 函数形式定义 outputs（如包、开发环境、测试），配合 flake.lock 将每个依赖锁定到具体提交，从而实现跨发行版的可复现构建。其纯评估模式禁止读取环境变量和未校验的网络访问，进一步强化了可复现性。文章以 Ghostty、Niri、pandoc 等项目为例，展示了 nix flake show 和 nix develop 等命令如何让用户无需预装工具链即可进入预配置的开发环境。历史方面，flakes 于 2019 年经 RFC 49 提出，因社区未达成共识于 2020 年被撤回，2021 年随 Nix 2.4 以实验性功能回归。2025 年调查显示 78.9% 的 Nix 用户已在使用 flakes，但社区对实验性标签存在明显分歧：Lix 将其视为冻结特性，Determinate Nix 已默认启用，而上游 CppNix 仍标记为实验性。RFC 136（2023 年 8 月通过）提出了逐步稳定化路径，包括惰性树等性能改进和 CLI 设计定稿，但尚无明确完成时间。总体而言，flakes 虽仍带实验标签，但采用率持续增长，预计将在软件生态中更加普遍。

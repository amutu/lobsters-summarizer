- 英文标题: VibeCoded AI-Slop License v1.0

开发者NicolasCARPi于2026年8月在GitHub Gist上发布了一份名为「VibeCoded AI-Slop License v1.0」的许可证，以戏谑口吻为AI生成代码（即所谓「vibe coding」）量身定制。该许可证共七条：第一条赋予使用者完全自由，可随意使用、修改、分发、出售、训练AI，无需授权或署名；第二条「来源」条款承认软件可能由AI根据模糊提示生成，作者本人可能从未编写、阅读、理解或测试过该代码，甚至不记得为何创建该仓库；第三条「质量」条款明确不保证任何质量，列举了AI生成代码的典型病症，如虚构API、十七层间接调用、名为processData2FinalNew的函数、注释描述已不存在的代码等；第四条声明无任何支持，issue和PR均不保证被处理；第五、六条以荒诞措辞（如「基本能力」「存在主义怀疑」「神秘云账单」）进行完全免责；第七条收束为「这就是AI垃圾，没人关心你拿它做什么，连做它的人也不关心」。该Gist获得26个星标和3个fork。评论区中，有读者指出在多数司法管辖区AI生成内容无法主张版权，因此许可证首行的版权声明本身即存在法律漏洞，颇具讽刺意味。

## 2. curl 项目的首起 CVE 争议：一个「低于 LOW」的漏洞为何不该获得编号

- 原始链接: <https://daniel.haxx.se/blog/2026/06/24/a-cve-dispute/>
- 英文标题: curl: a CVE dispute

curl 项目数年前成为 CNA（CVE 编号分配机构），此后自主发布了 57 个安全漏洞编号，流程高效且无需外部介入。文章重点讲述了 curl 成为 CNA 后遭遇的首起 CVE 争议（2026 年 2 月）。争议源于一个技术细节：curl 的 Curl_cert_hostcheck() 函数在处理带前导点的非法主机名（如 .example.com）与通配符证书 *.example.com 的匹配时存在缺陷，会错误返回「匹配」。但该问题触发条件极为苛刻——用户须使用前导点主机名、需本地攻击者配合、目标站点须持有对应通配符证书，curl 团队将其评级为「低于 LOW」，认为不值得分配 CVE。报告者不服，向 MITRE 发起争议。MITRE 在 5 月、6 月两次追问理由后，于 6 月 24 日作出最终裁定：同意 CNA 判断，该问题仅为已修复的 bug，不构成安全漏洞，不分配 CVE。文章同时强调，libcurl 全球约有 300 亿安装实例，每个 CVE 都会触发大量安全团队的补丁与更新工作，因此 curl 团队主张对理论性、极低概率问题保持克制，避免不必要的「安全警报」。

## 5. RangeFrom 设计缺陷分析（续）：我认为当前设计哪里出了问题

- 原始链接: <https://erk.dev/2026/08/30/rangefrom-part-2>
- 英文标题: RangeFrom, Part 2..: What I think is wrong about the design

本文是作者关于 Rust 中 RangeFrom 迭代器设计问题的第二篇长文。作者列出五项对 RangeFrom 的合理期望，并逐一论证当前实现均不满足：（1）开启 overflow-checks 时，迭代器在产出最大值前即 panic，导致最终值缺失；（2）溢出后迭代器会产出范围外的值，破坏「区间」语义，使其不能安全地用作值域守卫；（3）关闭 overflow-checks 时，仅基本整数类型能正常回绕，而 Ipv4Addr、Ipv6Addr 等类型仍会 panic，char 和 ascii::Char 也始终 panic；（4）NonZero<u*> 在溢出时饱和而非递增，违反单调性；（5）标准库中七种类型的 Step 实现存在三种截然不同的溢出行为，缺乏一致性。作者讨论了支持当前语义的理由（如与 zip 配合使用、向后兼容），并提出用 Iterator 上新增的 enumerate_with 方法替代 zip+RangeFrom 的用法。作者最终建议：溢出时 RangeFrom 应返回 None 而非 panic 或回绕，可借助 Step::checked_forward 实现，同时允许 Wrapping 等类型保留回绕语义。作者表示将根据社区反馈决定是否复活相关 ACP（libs-team#304）或发起新提案。

## 6. 可引导构建：原理与实践

- 原始链接: <https://lwn.net/Articles/1088279/>
- 英文标题: Bootstrappable builds: how and why

本文报道了FOSSY 2026大会上Timothy Sample关于可引导构建（bootstrappable builds）的演讲。可引导构建指从一个极小的种子程序出发，逐层构建出更大的工具，直至生成完整的现代Linux用户空间，使所有代码来源完全可追溯。与可复现构建侧重验证二进制与源码一致不同，可引导构建旨在防范Ken Thompson「信任的反思」中描述的编译器后门问题——即编译器二进制中可能隐藏源码中不可见的恶意逻辑。演讲介绍了GNU Guix（类似Nix的功能性包管理器）的引导路径：从仅256字节的hex0程序出发，经hex1、hex2、M0、M2-Planet、GNU Mes、Tiny C Compiler等阶段，最终构建出GCC和Guile等工具。对于仅支持自托管的语言（如Rust），社区采用「考古法」（用旧版本逐步推进）或定制引导工具（如mrustc）两种方式。Sample还介绍了他正在开发的Germ项目，约2.25KB，直接以Scheme解释器为起点，跳过中间汇编器层级，更契合Guix的Scheme构建脚本体系。但Germ面临性能不足（编译Mes需140秒以上）、仅支持x86_64、以及Lisp/Scheme语法争议等挑战。此外，live-bootstrap项目以182步流程探索了内核引导，但复杂度极高。

## 7. 取消术语辨析：同步取消、异步取消与优雅关闭

- 原始链接: <https://matklad.github.io/2026/08/31/cancelation-terminology.html>
- 英文标题: Cancelation Terminology

本文澄清了并发编程中三个常被混淆的概念。同步取消是一种控制流结构，类似异常处理中的栈展开，通过RAII、finally、defer等机制触发清理，在大多数语言中是隐式且高频的。异步取消是两方之间的通信协议：请求方发出取消信号后，必须等待执行方完成当前工作单元并确认，典型场景包括CPU线程池中取消正在执行SIMD循环的加密任务（需按块检查取消标志），以及io_uring中取消已提交的写操作（缓冲区必须保持占用直至完成）。优雅关闭则是应用层设计模式，如Web服务停止接受新连接但继续服务现有连接，以支持滚动升级。作者还提出「crash-only」理念：若系统能容忍断电重启，则无需复杂取消逻辑，尾延迟容忍（向多节点请求取最快响应）可同时应对崩溃与灰度故障。文章以TigerBeetle为例说明实践：Grid.cancel是异步取消（需回调通知完成），其上层StateMachine.reset可简化为同步取消；Client.shutdown虽被注释称为「graceful shutdown」，但作者认为这是误用，TigerBeetle整体采用crash-only策略。核心结论：同步取消是控制流操作符，异步取消是通信协议，优雅关闭是应用层设计模式，三者不应混用。

## 8. 终端模拟器对Unicode遗留计算符号的支持追踪

- 原始链接: <https://arewelegacycomputingyet.com/>
- 英文标题: Are We Legacy Computing Yet?

本文追踪了主流终端模拟器对Unicode「Symbols for Legacy Computing」(U+1FB00-U+1FBFF)及其补充区块(U+1CC00-U+1CEBF)的支持情况。这些字符源自20世纪70至90年代计算机，用于在终端文本网格上绘制半图形元素，如填充形状、像素画、游戏精灵和UI边框。作者将字符按实用性分为「重要」和「不重要」两类，测试了ghostty、kitty、urxvt、vte、xtermjs五款终端。测试方法为：将终端字体设为不含这些字符的字体，再用脚本强制输出全部码位，能正常渲染的即代表终端内置了自定义绘制逻辑。结果显示：ghostty在Legacy Computing区块达100%、Supplement重要部分达99%，表现最佳；kitty和基于libvte的终端（如gnome-terminal）对Legacy Computing支持良好（84%-94%），Supplement重要部分约63%-79%；xtermjs对Legacy Computing覆盖率达100%，但完全不支持Supplement；urxvt及其家族则两项均为0%。文章还展示了smooth mosaic、sextant/octant网格、圆角边框、圆形等字符的实际图形效果，并邀请社区贡献更多演示。

## 11. 任何用户进程均可提权至 root：docker 组权限隐患

- 原始链接: <https://www.vesto.me/2026/08/31/any-process-escalate-root.html>
- 英文标题: Any user process can escalate to root

本文转述 0xcc.io 上的一篇安全分析，指出 Omarchy（DHH 主导的 Arch 系发行版）将默认用户加入 Linux docker 组，导致该用户及其会话中启动的所有进程实质上拥有 root 权限。原理在于：Arch 上 Docker 守护进程以 root 身份运行并监听 /var/run/docker.sock，docker 组成员可通过该 socket 指示守护进程以 root 启动容器、挂载宿主机任意目录并以 root 操作其中文件，从而实现完整提权。Docker 官方早已警告 docker 组等同于 root 权限。作者坦言自己长期将 docker 组绑定到普通用户以省去 sudo 输入，却未充分意识到其安全后果，尤其在当前许多人以完整 shell 权限运行 LLM 编码助手的背景下，风险更为突出。修复方法很简单：执行 gpasswd --delete <用户名> docker 即可移除该组归属。作者还提到已将自托管服务迁移至 Podman，其无守护进程设计天然避免了 root socket 问题，安全性更优；同时他偏好用 systemd 配合 *.container 单元文件管理容器，而非依赖 docker compose YAML 和独立进程管理器，建议读者尝试。文章末尾附有对 DHH 及 Omarchy 项目的政治性吐槽，但核心安全提醒对所有 Linux 用户普遍适用。

## 12. Cargo 的构建调度器能否做得更好？

- 原始链接: <https://spirali.github.io/blog/cargo-scheduler/>
- 英文标题: Could Cargo's scheduler be better?

作者基于在 HyperQueue 中引入 MILP 调度器的经历，从外部观察角度分析了 Rust 包管理器 Cargo 的构建任务调度策略。实验选取 17 个 Rust 项目，通过追踪系统调用重建编译任务的依赖图，将每个 crate 拆分为「frontend」（生成元数据）和「rest」（代码生成与链接）两个节点，在 4 核与 16 核两种并行度下对比多种调度算法。结果表明，简单的 b-level 贪心策略（优先调度关键路径上剩余最长链的任务）在绝大多数项目中优于 Cargo 自身调度：4 核时中位加速约 8%，16 核时约 2%，且已非常接近通过模拟退火等昂贵搜索得到的伪最优解（差距仅 1.3% 和 0.4%）。鲁棒性测试显示，即使任务时长估计存在 60% 噪声，甚至每个任务仅提供 1 比特信息（标记为「短」或「长」），b-level 仍能击败 Cargo 基线；完全不用时间信息、仅依赖依赖图深度，在多数项目上也有改善。作者结论：b-level 已接近调度问题的实用上限，更复杂的策略收益有限；实际落地时，一个记录历史构建时长的本地小数据库（甚至只需快/慢标志位）即可带来可观加速，首次构建还可借助全局共享数据库冷启动。

## 13. Kale：一种变换安全的电子表格系统

- 原始链接: <https://arxiv.org/abs/2608.26345>
- 英文标题: Kale: A Transformation-Safe Spreadsheet System

本文提出了一种名为Kale的电子表格原型系统，旨在解决传统电子表格中因引用语义导致的结构性错误问题。在常规电子表格中，公式可引用任意大小的矩形区域；当用户修改被引用表格的结构（如插入或删除行列）时，系统会自动将引用更新为新区域，但该新区域往往与用户预期不符，从而引入难以察觉的公式错误。作者通过用户研究证实，标准引用语义具有较高出错率，给用户带来显著风险。Kale的核心思路是限制可表达的引用类型，从机制上消除此类结构性bug的插入可能。实验表明，用户能够借助Kale有效完成在传统系统中容易出错的任务，说明该限制并未严重损害可用性。此外，作者还开展了一项语料库研究，评估Kale的引用限制在实际用户工作簿中可能带来的影响范围，以判断其适用边界。该工作由Michael Coblenz等14位作者完成，发表于2026年8月，归类于人机交互与软件工程领域，为电子表格系统的引用安全设计提供了新的思路与实证依据。

## 15. 从 IIS AppPool 到 NT Authority/SYSTEM 的权限提升：利用 AD CS RPC 端点身份转换

- 原始链接: <https://www.mannulinux.org/2026/08/Privilege-escalation-from-IIS-AppPool-to-NT-AuthoritySYSTEM-via-AD-CS-RPC-endpoint.html>
- 英文标题: Privilege escalation from IIS AppPool to NT Authority/SYSTEM

本文介绍了一种无需 Potato 类漏洞即可从 IIS AppPool\DefaultAppPool 提升至域管理员权限的攻击方法，适用于已获取 IIS 应用池 RCE 且主机属于 Windows AD 域的场景。核心原理是 Windows 的既定行为：当 IIS AppPool 身份访问网络级资源（如 AD CS RPC 端点）时，其身份会被静默转换为主机机器账户（如 WEBSERVER$）。攻击链共六步：一、在攻击者机器上用 PowerShell 脚本生成 CSR 及私钥；二、将 base64 编码的 CSR 通过上传到目标 IIS 的 ASPX 页面提交至 AD CS RPC 端点，此时请求以机器账户身份到达，AD CS 依据默认「Machine」证书模板签发证书；三、从响应中获取已签发证书；四、用 certutil 将证书与私钥合并为 PFX 文件；五、使用 Rubeus 工具凭 PFX 向 KDC 请求机器账户 TGT；六、利用 S4U2Self 技术以机器账户 TGT 请求 CIFS 服务票据并冒充域 Administrator，最终获得对目标主机本地文件系统的完全访问权限，甚至可用 impacket secretsdump 提取 NTLM 哈希。文章附有视频演示及 GitHub 上的 ASPX 代码链接。

## 17. Rootless Docker 及其隐藏的安全权衡

- 原始链接: <https://www.kenmuse.com/blog/rootless-docker-and-its-hidden-security-trade-offs/>
- 英文标题: Rootless Docker and Its Hidden Security Trade-Offs

本文是「Docker Privilege」系列第三篇，探讨 rootless Docker 的底层机制与安全权衡。Rootless Docker 以非特权用户运行 dockerd，借助 user namespace 与 RootlessKit（通过 setuid 的 newuidmap/newgidmap 完成 UID 映射），使容器内 root 映射为宿主机普通用户，将容器逃逸的影响从宿主机 root 降级为普通用户权限；Rootless BuildKit 采用相同方案。但该模式存在多项限制：需内核允许非特权 userns 创建、常需设置 seccomp=unconfined 与 apparmor=unconfined（实质是禁用系统调用过滤器和 AppArmor 资源限制）、overlayfs 回退至 fuse-overlayfs、网络依赖 slirp4netns 等用户态工具、且无法使用 --privileged。文章重点指出 user namespace 本身扩大了内核攻击面——非特权用户可触及 CAP_SYS_ADMIN 等能力对应的内核接口，2025 年已出现多个相关 CVE 及绕过方法。作者建议保持内核更新、遵循最小权限原则，并强调「rootless」缩小了攻击爆炸半径，但并非完整安全方案，不可等同于可安全运行不可信负载。

## 18. 不存在「只是个工具」这回事

- 原始链接: <https://deadsimpletech.com/blog/no-such-thing-as-just-a-tool>
- 英文标题: There's no such thing as Just a Tool

作者Iris Meredith反驳科技批评中「这只是个工具」的常见论调。她借用海德格尔哲学指出，工具一旦「上手」便与使用者形成「人-工具格式塔」，绝非意识形态中性。叉子与筷子塑造截然不同的饮食文化，汽车与枪支改变人的认知与行动空间。在技术领域，她以React与Vue对比为核心论证：React以JSX函数为中心，要求操作经由JavaScript完成，天然排斥设计师、无障碍专家等非开发角色；Vue以HTML为第一公民，允许不同技能背景的人有效协作。这一差异并非技术优劣，而是塑造了「开发者至上」的意识形态，并蔓延至Kubernetes、Docker、云服务等生态，将HTML与CSS降格为低地位工作，边缘化设计与UX角色，形成自我强化的循环。文章结论是：工具绝非中性，技术从业者须审慎思考所造工具将催生何种格式塔与价值观。

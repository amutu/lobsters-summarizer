## 4. Rust 分配器 API 于 2026 年终于稳定

- 原始链接: <https://cetra3.github.io/blog/state-of-allocators-2026-finally-stabilised/>
- 英文标题: The State of Allocators in 2026 - Finally Stabilised

Rust 1.100 正式稳定了自定义分配器（allocator）API，结束了长达十年的未决状态。文章围绕这一里程碑介绍了三个实用场景：第一，调整内存释放时机。通过增量分配器（bump allocator），将大量突发分配（如 Web 请求、数据库查询）集中到一块预分配内存中，释放时一次性归还，避免逐对象 Drop 的开销。第二，内存记账。通过包装分配器记录已分配字节数，可驱动缓存淘汰阈值、外部排序内存上限、沙箱资源限制等决策；作者还介绍了其开源 crate「thresher」，采用本地与全局计数器结合的方式减少原子操作竞争，支持阈值回调，已在 logfire 服务中用于堆内存画像。第三，控制内存位置。包括栈上优先分配（小数据留在栈上，超出再溢出到堆）和块对齐分配（满足 O_DIRECT 绕过内核页缓存的需求，如 Kubernetes 场景）。文章最后指出，当前仅为 MVP，libs 团队仍需支持 map 等更多集合类型，许多流行 crate 因最低支持版本策略尚未跟进，但现有能力已足以开始采用并推动生态适配。

## 7. x86 本质上是一台八进制机器：80x86 指令编码的八进制解读

- 原始链接: <https://gist.github.com/seanjensengrey/f971c20d05d4d0efc0781f2f3c0353da>
- 英文标题: x86 is an octal machine

本文由 Mark Hopkins 撰写，发表于 alt.lang.asm 新闻组，核心论点是 80x86 的全部操作码均以八进制编码，一个字节对应三个八进制数字（000–377），这一设计继承自 8080/8085/Z80。作者批评 Intel 官方手册未揭示此规律，导致指令集显得晦涩难记。文章系统拆解了编码结构「op xrm Const」：op 为 1 或 2 字节操作码；xrm 中 r（0–7）编码寄存器（AL、CL、DL、BL、AH、CH、DH、BH），xm 编码寻址模式，x（0–3）决定是否带位移及位移宽度，m（0–7）决定基址与变址组合；s（0–7）编码段寄存器（ES、CS、SS、DS 等）。作者以 mov 指令族（210–216）和算术逻辑指令族（0P0–0P5，P 位编码 add/or/adc/sbb/and/sub/xor/cmp）为例，展示同一模式仅靠一位八进制数字即可区分八种运算。条件跳转是唯一例外，用十六进制数字 160+CC（八进制 160–177）表示 16 种条件。80386 起引入 32 位寻址与 32 位字长，地址模式表整体替换，且字长与地址长可独立切换，产生四种组合。文章还概述了寄存器命名含义、栈帧协议（enter/leave）、算术与移位指令的完整八进制编码表，旨在帮助读者以八进制视角统一理解 80x86 指令集，而非死记硬背。

## 10. 乐观更新为何具有腐蚀性

- 原始链接: <https://datastar-instant-intent.ndyg.cross.stream/corrosive/>
- 英文标题: Why optimistic updates are corrosive

本文围绕与开发者Ben的讨论，阐述乐观更新（在服务器确认前即向用户显示操作成功）为何有害。作者的核心论点是：乐观更新让软件表现得「不尊重用户」——用户拨动开关后看到它翻转，回来却发现未翻转，这意味着软件并未执行用户的指令，从而侵蚀信任。Ben区分了场景：对「预订确认」等关键操作，任何有自尊心的开发者都不会在服务器验证前显示成功；对「点赞」等轻量操作，可静默重试，但若用户提前关闭标签页，点赞将丢失且用户无从得知。作者进一步指出，不欺骗用户的软件实际上更简单：可省去为「用户以为成功实则未成功」而设计的整套对账（reconciliation）机制。作为替代方案，作者演示了「即时意图」（instant intent）交互：点击开关时客户端立即呈现按下状态并发送请求，但期间不再接受额外点击；若半秒内无服务器响应则开始闪烁，直到服务器返回确认后的HTML视图（通过Datastar原地morph更新）。该方案允许用户在不同延迟及离线场景下体验交互，且按下与闪烁的视觉样式与主页面座位选择器一致，既给予即时反馈，又诚实传达「尚未确认」的状态。

## 11. Haskell 异常处理最佳实践

- 原始链接: <https://www.well-typed.com/blog/2026/11/exception-best-practices/>
- 英文标题: Exception Best Practices

本文为 Edsko de Vries 所撰 Haskell 异常处理系列的第一篇，围绕三个核心目标展开：确保已分配资源被释放（避免泄漏）、确保代码始终能推进（避免卡死）、确保异常到达能处理它的代码（不捕获无法处理的异常）。文章首先回顾基础机制：throwIO 与 catch/handle 的用法、SomeException 动态类型包装，以及异步异常（throwTo）在 timeout、killThread、UserInterrupt 等场景中的角色。随后重点讨论异步异常安全：用 mask/unmask 保护资源获取与释放之间的间隙，并介绍 bracket 组合子作为资源管理的惯用模式，以及 generalBracket 对日志等扩展场景的支持。作者建议避免捕获 SomeException 这类「全捕获」，优先捕获特定异常类型或值；同时警告不要在异常处理器内部递归，以免产生无界处理器嵌套。文章还解释了通过 SomeAsyncException 标记区分同步与异步异常意图的方法，讨论了可取消性与可中断性的区别——interruptible 操作即使在 mask 下仍可接收异常，而 uninterruptibleMask 虽更安全却使代码不可取消。多资源获取需保证原子性，释放则应链式处理。本文为系列开篇，后续将分别探讨可中断外部调用与纯代码中的可恢复异常。

这是一篇以荒诞公式讽刺企业文化度量的幽默文章。作者 Liam Galvin 先嘲讽了企业常见的文化评估手段——员工敬业度调查、eNPS、团建活动中让 HR 把公司比作某种动物、办公室墙上贴着「诚实、努力、有趣」的标语，以及招聘时问候选人最像哪种厨房用具等。随后他提出一个「Emoji 系数」公式：用 Slack 工作区中自定义表情数量除以用户数的平方根（平方根体现表情作为共享资源的特性），并据此将公司文化分为四档：低于 5 表示只剩默认表情和点赞，5 到 20 为健康组织，20 到 50 为 thriving，50 以上则进入「晚期文化」，表情开始自我指涉，HR 甚至要求编写表情术语表。作者还补充了「参与率」指标，即上传过至少一个表情的用户占比，低于 20% 意味着文化由少数人维系，一旦他们离开文化便随之消散。文章还讨论了指标可被操纵的情形：中层管理者为绩效评审上传 600 个公司 logo 变体，或大规模裁员因分母缩小反而抬高分数。最后作者嘲讽使用 Microsoft Teams 的公司「缺乏文化恐怕是最小的问题」，并总结称文化无法靠价值观海报或强制娱乐制造，而是自然涌现——比如某工程师决定团队真正需要的是一个「极度惊讶的花椰菜」表情。

## 14. 我的替代文本写作方法（2024）

- 原始链接: <http://adrianroselli.com/2024/05/my-approach-to-alt-text.html>
- 英文标题: My Approach to Alt Text (2024)

本文围绕网页无障碍设计中替代文本（alt text）的撰写方法展开讨论。作者坦言自己在 alt text 的「前置信息」（front loading，即将关键内容放在描述开头）方面仍有不足，并感慨「总有更多可学」。文中推荐了三篇值得参考的资源：一是 Jake Archibald 的《Writing great alt text: Emotion matters》，强调替代文本中情感传达的重要性；二是 Léonie 的《Text descriptions and emotion rich images》，作者特别指出 Léonie 作为屏幕阅读器用户，拥有许多非残障人士不具备的第一手使用体验，其建议更具实践价值；三是 Eric Bailey 的《Your Image Is Probably Not Decorative》，提醒开发者不要草率地将图片标记为装饰性（即省略 alt 属性）。整体而言，这段内容聚焦于图片替代文本的写作实践，核心观点有二：其一，优秀的 alt text 不仅传递客观信息，还应兼顾情感与语境，让屏幕阅读器用户获得与视觉用户相近的体验；其二，在判断图片是否属于「装饰性」时应持审慎态度，多数图片实际上承载了有意义的信息。文章以评论和推荐链接的形式呈现，信息量有限，但清晰地勾勒了 2024 年 alt text 写作中「情感化描述」与「谨慎分类」两个关键方向。

## 16. 在编程语言中实现证明自动化

- 原始链接: <https://www.imperialviolet.org/2026/11/15/proofauto2.html>
- 英文标题: Proof automation in a language

ImperialViolet 在证明自动化已可用的前提下，探讨如何借此提升软件质量与可理解性。他提出若干编程语言设计「食材」并尝试组合：一是可变值语义（MVS），比 Rust 更激进地禁止引用进入类型系统，函数参数仅分不可变、可变、拥有三类，从而消除别名问题，使局部推理更简单；二是引用限制可绕过分离逻辑，让形式化验证无需建模堆的别名关系，比 Rust 更易于翻译到 Lean 等证明环境；三是设计契约（源自 Eiffel 的前置/后置条件与不变量），借助现代 SMT 求解器与模型可静态验证，无需运行时检查；四是精化类型，允许在结构上附加随处理阶段变化的不变量；五是文学化编程，代码按人类阅读顺序组织，文章本身即为该语言的合法源文件（Markdown 中仅编译标注代码块）。作者以 DER 标签编解码为例，展示契约如何让调用者无需阅读函数体即可确信解析器的严格性。挑战在于编译器前端为每段代码生成大量验证条件（示例中达 149 条），需 Z3、cvc5 等求解器处理，且求解器结果不可完全信任，仍需进一步验证。

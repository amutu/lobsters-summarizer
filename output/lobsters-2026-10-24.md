## 1. Zig 语言中的 @xkcdRandom 内置函数：一个学习编译器开发的趣味实践

- 原始链接: <https://ochagavia.nl/blog/the-glorious-@xkcdrandom-zig-builtin/>
- 英文标题: The glorious @xkcdRandom Zig builtin

作者受 xkcd 经典漫画启发——一个号称返回随机整数、实则永远返回 4 的 C 函数——并在近期一起安全事件中看到有人误将数字 4 当作随机字节使用，遂决定在 Zig 语言中实现一个名为 @xkcdRandom 的内置函数，其功能正是永远返回 4。作者刻意选择将其实现为语言内置构造（builtin）而非普通函数，目的是通过修改 Zig 编译器来学习生产级代码结构，而非追求实用。实现本身极为简洁，仅 22 行 diff，作者将代码托管在个人 Zig 分支上供人查看。文章重点分享了修改 Zig 编译器的开发体验：Zig 团队对开发者体验投入颇深，单条命令即可完成编译，首次构建约一分钟；代码结构清晰，配合 Zig 语言服务器和 LLM 辅助定位，导航与调试都很顺畅，作者远快于预期地完成了全部工作。最终编译并运行示例程序，成功输出两个 4，验证了该「100% 保证随机」的函数确实可用。文章整体语气轻松幽默，核心亮点在于以极小成本完成了一次编译器级别的动手实践，展示了 Zig 编译器对贡献者友好的工程体验。

## 2. 软件慢是因为设计差，而非语言慢

- 原始链接: <https://www.seangoedecke.com/software-is-slow-because-of-bad-design-not-slow-languages/>
- 英文标题: Software is slow because of bad design, not slow languages

文章反驳了「AI通过用C或Rust重写代码来加速软件」的流行观点。作者指出，大多数实际程序是I/O受限的，瓶颈在于数据库查询、网络请求等I/O操作，而非语言执行速度。即便C比Python快50倍，若程序半数时间花在I/O上，重写后最多提速约1.5倍。此外，慢语言已通过调用C或汇编库（如cmark-gfm、NumPy）将CPU密集任务卸载给快速代码，Python在机器学习中依然有竞争力。作者认为真正的加速来自重新设计：缓存慢操作、异步处理、并行化、修复N+1查询、减少不必要的数据获取等，这些策略与语言速度无关。他引用Bryan Cantrill用Rust重写C程序的案例，说明即使CPU密集型任务，性能也取决于设计（如B-tree比二叉搜索树更缓存友好）而非语言本身。结论是：应让AI去分析性能热点并建议重新设计，而非盲目重写；仅在极少数真正CPU受限且无法减少工作量的场景下，换用更快语言才有意义。

## 3. 纯函数式语言的性能能逼近C到什么程度？

- 原始链接: <https://rtfeldman.com/fp-vs-c>
- 英文标题: How close can pure FP get to C?

本文探讨纯函数式编程（FP）语言在运行时性能上能接近C语言的程度。文章先引用一篇关于Lean 4的DEFLATE压缩库lean-zip的报道：该库在所有压缩级别上均击败了Rust生态中下载量超十亿的miniz_oxide，最快设置下快15%且输出小8.8%，但面对C语言精心调优、使用架构特定SIMD指令的libdeflate仍远逊一筹。作者随后将目光投向Roc——一门以「Fast, Friendly, Functional」为口号、尚未发布0.1.0的函数式语言，对其DEFLATE包roc-deflate进行大量性能优化。基准测试在M1 MacBook Pro和AMD Ryzen 9 3900X上，使用经典Silesia语料库、覆盖L1至L12共144组压缩任务，并验证输出与libdeflate完全一致。结果显示：roc-deflate在Ryzen上中位数仅慢8.9%，在M1上仅慢2.6%，整体差距控制在10%以内。部分高压缩级别（如L6、L7）中roc-deflate个别文件甚至反超libdeflate。文章核心结论是：凭借语言设计、长期积累的优化手段和全新编译器实现，纯函数式语言在压缩这类计算密集型任务上已能非常接近C语言手写SIMD的性能，差距远小于直觉预期。

## 4. 请不要滥用链接：尊重浏览器原生行为

- 原始链接: <https://maurycyz.com/misc/real_links/>
- 英文标题: Please don't mess with links

本文以xkcd风格批评了前端开发中常见的反模式，核心观点是：浏览器原生能力已经足够优秀，开发者不应重新造轮子。文章首先指出，用JavaScript按钮（如span加onclick）模拟链接是「浅薄的模仿」，因为真正的a标签支持新标签页/新窗口打开、保存为文件、复制URL、键盘导航、搜索引擎与屏幕阅读器识别、悬停显示地址等，而按钮统统做不到。其次，即便使用了真实a标签，若绑定click事件弹出popup，也会剥夺用户查看加载进度、取消请求、多标签管理、收藏和分享URL的能力，且popup极易误关整个页面。作者还列举了其他常见问题：无限滚动破坏Ctrl+F、书签和后退键；用数MB的JS框架渲染纯文本不如让浏览器直接渲染部分下载的HTML；单TCP连接因慢启动机制优于多次请求；不要自行实现details折叠或日期选择器，原生控件已支持用户偏好格式、键盘操作和暗色模式。总结一句话：让浏览器做它擅长的事，别用JavaScript覆盖原生行为。

## 5. 揭穿「比Rust更快」：Tov语言基准测试中的恶意设计

- 原始链接: <https://blog.fyralabs.com/debunking-faster-than-rust-malicious-benchmarks-in-tov/>
- 英文标题: Debunking "Faster than Rust": Malicious Benchmarks in Tov

Tov是一种面向编码代理的新编程语言，号称「读起来像TypeScript，生成的原生二进制文件性能超越Rust」，其仓库中的基准测试甚至显示快10倍以上。然而Tov本质上只是将TypeScript转译为C再交由clang编译，而Rust性能已接近C，因此「Tov比Rust快」在逻辑上近乎「C比C快」。作者选取了bigint_fib、dispatch、map_insert三项基准进行复现与对比。在bigint_fib中，作者在三台不同机器上均无法复现Tov的领先数据，Rust反而快约1.3倍。在dispatch中，Tov刻意让Rust版本使用Vec<Box<dyn Shape>>动态分发，而C/Tov版本使用静态数组；改用enum+match的静态分发后，改进版Rust比Tov快约5%至7%。在map_insert中，Tov给Rust指定了抗HashDoS的std HashMap（天然较慢），而忽略实际工程中常用的ahash；换用ahash后Rust比Tov快1.2至2倍。作者结论：Tov的基准测试系恶意构造，故意让Rust处于不公平劣势；Rust的真正优势在于从代码本身榨取接近硬件的性能，而非写简单代码即自动最快。Tov的转译思路并非新颖，作者推荐了Porffor等已有项目作为替代。

## 8. 利用写时复制机制零成本复用物理内存的技巧

- 原始链接: <https://sebsite.pw/w/20260728-cow.html>
- 英文标题: a neat trick i found for reusing physical memory

作者分享了一个利用Linux写时复制（CoW）机制复用物理内存的技巧。具体做法是：先用memfd_create创建一个内存文件描述符，通过mmap将其映射为共享内存区域并写入模板数据；随后以MAP_PRIVATE标志对同一文件再次mmap，即可得到一份逻辑上的副本。关键在于，无论初始分配多大，副本在创建时不占用任何额外物理内存；只有当副本被修改时，内核才按需分配被触及的那一页（4 KiB），其余页面仍与模板共享。作者实测分配32 MiB模板并「复制」出另一块32 MiB区域，总物理内存仅32.004 MiB，几乎无额外开销。作者同时表达了两个遗憾与设想：一是希望更高层的标准库函数能更便捷地暴露此能力；二是设想能否对连续虚拟内存区域实现类似效果——即整段填充相同非零值时仅分配一页物理内存，从而在需要大量重复初始化的场景中显著节省内存。

## 9. 别再说未定义行为「没问题」了

- 原始链接: <https://blog.habets.se/2026/10/Attention-people-who-think-UB-is-fine.html>
- 英文标题: Attention people who think UB is fine

本文反驳了「C语言中未定义行为(UB)最坏不过是段错误」的常见误解，通过三个具体示例说明UB的后果完全不可预测。第一个例子中，在函数内调用std::unreachable()触发UB，GCC 16.2在-O1优化下省略了函数边界，导致从未被调用的explode()函数被意外执行——作者用「热巧克力爆炸」的比喻形容这种荒谬后果。第二个例子将UB改为解引用空指针(*ptr=99)，GCC生成的汇编却将0（而非99）写入地址0，随后用ud2指令主动崩溃；clang则再次出现explode()被执行的问题。第三个例子对空指针做ptr+=10后再解引用，编译器「恰好」生成了符合直觉的写入操作，但作者强调这纯属巧合。文章指出，编译器没有义务检测UB，且受停机问题限制，无法在一般情况下判断代码是否可达。同一处UB在不同编译器、不同优化级别下可产生三种截然不同的结果：执行内存中相邻的无关指令、写入随机值后崩溃、或碰巧做出预期行为。作者以此论证UB绝非「无害」，而是真正不可控的危险。

## 10. 分布式数据，集中式修复：从近期安全事件中提炼部署架构设计

- 原始链接: <https://miren.dev/blog/distributed-data-centralized-fixes>
- 英文标题: Distributed data, centralized fixes

本文由部署平台 Miren 撰写，以近期密集的安全事件（Railway 与 Zeabur 数据泄露、PHP 与 Node.js 漏洞、GitLab 漏洞、LiteLLM 与 OVH 供应链攻击、OpenCode 密钥泄露等）为引子，将混乱的 headlines 归纳为三种结构性问题：集中式平台导致「一个保险箱存所有人密钥」，非集中系统面临「一个补丁、百万处需手动更新」的碎片化困境，供应链攻击则让更新通道本身成为攻击向量。作者指出，这三个问题本质上是系统设计问题：密钥存在哪里、谁来打补丁、修复通道信任谁。Miren 据此提出设计选择：运行时开源且可自托管，用户密钥始终留在本地；Miren Cloud 不存储密钥，协议设计确保 Cloud 宕机时应用仍可运行与部署；全部软件开源可审计；自动升级采用稳定通道、一周冷却期与自动回滚机制。文章承认供应链风险不可完全消除，但开源自托管允许用户自行权衡安全与便利。核心结论是：「分布式数据、集中式修复」是现代软件部署的正确方向，既避免集中泄露的放大效应，又通过受控的自动更新通道解决碎片化补丁难题。

## 11. 内存慢，磁盘快（三）：磁盘数据结构全面击败内存AVL树

- 原始链接: <https://www.bitflux.ai/blog/memory-is-slow-part3/>
- 英文标题: Memory is slow, Disk is fast

本文是「内存慢，磁盘快」系列第三篇，核心论点是：在20亿节点规模下，基于8块NVMe磁盘的DiskArray（仅占264 MiB内存）在search、at、insert、delete四项操作上全面快于需144 GiB内存的AVL树，而Big O记号却预测AVL更优。作者从排序数组、链表、二叉树逐步推导到AVL树，再提出DiskArray：将排序键切分为4 KiB的extent（512个8字节键），索引驻留内存，extent存于磁盘。关键发现是AVL每次插入需约62次串行DRAM读（每次拉入64字节cache line），有效带宽仅312 MiB/s；DiskArray虽移动更多字节，但借助NVMe带宽达5.1 GiB/s，有效带宽2.1 GiB/s。DiskArray通过2048并发事务、28个io_uring worker和双半队列流水线隐藏磁盘延迟。作者指出Big O只描述性能曲线形状，无法反映斜率、量级及硬件边界效应（如L3溢出、磁盘开始承担读写），在当代硬件下预测力严重不足，呼吁引入更精细的方程与仿真。

## 12. OpenSSL 4.1.0 发布说明

- 原始链接: <https://github.com/openssl/openssl/releases/tag/openssl-4.1.0>
- 英文标题: Release OpenSSL 4.1.0 · openssl/openssl

OpenSSL 4.1.0 是一个功能发布版本，于 10 月 23 日推出，包含 441 个提交。核心亮点是新增 DTLS 1.3 支持（RFC 9147）、RFC 8701 GREASE 扩展、DTLS 在 SSL 监听器 API 中的支持、IKEV2 KDF 以及 Elbrus2000（e2k）架构的初步支持。性能方面，新增了 ppc64le 上 ML-DSA 与 ML-KEM 的 NTT 优化、x86_64 上 ML-DSA 的 AVX-512 优化及 AES-CBC 解密的 AVX-512/VAES 优化。构建层面，新增 VC-WIN32-MSVC2013 与 VC-WIN64A-MSVC2013 目标以弥补 MSVC 2013 的 C99 支持不足；移除了 Windows-on-Itanium 和 Windows CE 构建目标；废弃了 no-ecdsa 与 no-ecdh 配置选项，统一使用 no-ec。工具方面，tsget 改用 Net::Curl::Easy 替代已停维护的 WWW::Curl::Easy。已知问题共四项，均与 DTLS 1.3 相关：KeyUpdate 到达后其他握手后记录不再重传、监听器永久接收失败被误报为 SSL_ERROR_WANT_READ、非阻塞连接写失败被误报为 SSL_ERROR_SYSCALL、以及服务器在客户端部分确认首包时可能以 unexpected_message 中断握手。修复计划在未来版本中推出。

## 13. 增量计算图

- 原始链接: <https://dziban.net/posts/incremental-computation-graph/>
- 英文标题: Incremental Computation Graphs

本文介绍了增量计算图的核心机制，作者marce coll在开发Yabu语言（需交互式速度完成重编译、代码生成与类型检查）时，基于Salsa框架实现了该算法。系统包含两类要素：输入（可变，外部变化的唯一来源）和计算（对输入或其他计算的纯函数，结果被记忆化）。以Yabu为例，函数定义源码作为输入，经parse得到AST，再经typecheck和compile等纯计算逐层组合，形成运行时依赖图。当某个函数的类型签名变更时，依赖图自动将受影响的计算标记为失效，从而避免全量重算。核心失效机制为「红绿遍历」：每个记忆化条目记录返回值、verified-at修订号、changed-at修订号及依赖列表。遍历时沿依赖链向下走至输入层，若输入未变则向上回溯，将各节点verified-at更新为当前修订号，后续求值即可短路跳过。该机制使Yabu类型检查器即使在大型程序中也能保持交互级响应速度。文章还给出了具体示例，展示从新源码输入到逐层创建记忆化条目、校验标准库函数签名、最终完成类型检查的完整流程。

本文是 Charles Miller 以局外人视角回忆 Hibernate 诞生始末。2001 年前后，小型 IBM 合作伙伴 Cirrus Technologies 在墨尔本设有三人办公室，Gavin King 与 Daniel Bradby 在其中。当时服务端 Java 开发极为痛苦：Servlet、JSP、Struts 1.0 之下是过度设计的 EJB 组件模型，开发一个 EJB 需写两个接口再加一个不实现任何接口的实现类，部署描述符还依赖 IBM 专有 IDE。团队代号「苏格兰项目」的交付濒临失败，管理层召集悉尼会议讨论对策。Gavin 提出借鉴 Smalltalk 的持久化框架构想，但管理层仅同意减少 EJB 依赖、保留手写 SQL，未采纳其方案。散会后众人去酒吧消愁，次日 Gavin 在 CRT 显示器上独自写下框架首批类。数月后，名为 Hibernate 的 Java 持久化库以 LGPL 许可证发布，根包名仍为 cirrus.inf（inf 即 infrastructure）。值得注意的是，该包最初并非面向数据库持久化，而是 Struts 的轻量替代。Miller 强调自己仅是啤酒局上点头的旁听者，且讽刺的是他在 Cirrus 期间从未真正使用过 Hibernate，直到后来加入 Atlassian 参与 Confluence 开发才深入接触。

## 1. AI浪潮下，你如何应对网络环境的恶化？

- 原始链接: <https://lobste.rs/s/ipplhe/how_are_you_dealing_with_all_negative_side>
- 英文标题: How are you dealing with all the negative side effects of AI on the web?

这是一篇Lobsters论坛讨论帖，作者指出AI热潮对网络造成了多重负面影响：搜索引擎首页被AI生成的低质内容占据，LLM摘要反而因至少提及优质链接而显得「可用」；Google和DuckDuckGo对普通用户频繁限流；GitHub等站点强制登录，Anubis和Cloudflare的机器人检测无处不在，导致日常浏览效率显著下降。作者强调，许多动手项目（如阅读旧邮件列表、bug报告、PR）仍高度依赖网络，离线书籍无法替代。回复中社区成员提出了多种应对思路：使用Marginalia Search、Kagi等替代搜索引擎并屏蔽AI垃圾内容；转向RSS、Mastodon、Lobsters等小型社区；直接阅读源码和官方文档而非依赖Stack Overflow；有人建议将Gemini当作搜索工具使用；也有人呼吁构建去中心化网络（如ZeroNet、Freenet、Gnunet）以分散内容托管成本。核心共识是：在机器人泛滥和「死海效应」（重视质量的参与者最先离开）的双重压力下，找到高质量人类互动前所未有地困难，而现有反机器人方案（设备证明、数字身份绑定）令人担忧。部分人寄望于「车库式」的草根创新，在去中心化基础设施上重建有机社区。

## 2. Meridian：基于 Servo 与 GPUI 的实验性 macOS 浏览器

- 原始链接: <https://op.tngl.io/meridian/>
- 英文标题: Meridian — an experimental web browser built on Servo and GPUI

Meridian 是一款面向 macOS 的实验性网页浏览器，使用 Rust 编写，底层由 Servo 引擎处理网页渲染与状态管理，界面层则采用 Zed 编辑器背后的 GPUI 框架绘制。项目通过一个名为 gpui-servo 的独立库将 Servo 封装为普通 GPUI 组件，使任何开发者都能在 GPUI 生态中构建基于 Servo 的浏览器。目前 Meridian 对 JavaScript 和复杂布局依赖较少的网站已具备实用浏览能力，并支持高度自定义，包括字体、快捷键、配色和标签页布局等。功能方面涵盖地址栏自动补全、垂直与水平标签页、书签与历史记录、逐站点缩放、音视频播放、阅读模式、标签预览、右键菜单及暗色模式等。项目托管于 Tangled 平台，欢迎社区贡献，用户可通过 nix 命令直接运行体验。整体而言，Meridian 展示了将 Servo 引擎与 GPUI 界面框架结合的技术路径，为构建轻量、可定制的浏览器提供了新的参考方案。

## 3. 可编程 GeoDNS：从 AWS 迁移至 Bunny.net

- 原始链接: <https://vincent.bernat.ch/en/blog/2026-bunny-geodns>
- 英文标题: Scriptable GeoDNS: leaving AWS for Bunny

作者将个人博客的 CDN 与地理感知 DNS 从 AWS CloudFront + Route 53 迁移至 Bunny.net，月费从 5 美元降至 1 美元。Bunny DNS 的核心亮点是「可编程 DNS」：每条查询可执行用户提供的 JavaScript 来计算应答。作者在巴黎、纽伦堡、阿什本、新加坡、圣何塞、圣保罗、悉尼部署了 7 台 NixOS 虚拟机，利用 RoutingEngine.getClosestServer() 返回距用户最近的两个存活服务器，实现故障回退。但存在缺陷：若两个最近服务器距离差异大（如布宜诺斯艾利斯用户同时拿到圣保罗和阿什本），体验不佳。作者尝试过 HTTPS 记录（RFC 9460）方案，但 Chrome 忽略非根目标，最终采用混合策略：两服务器距离相近时返回两者（TTL 1 小时），否则仅返回最近一个（TTL 2 分钟）。ACME DNS-01 挑战改用 Rust 编写的 Hickory DNS 处理；因 Bunny DNS 无法发布 DS 记录，父域 luffy.cx 托管于柏林非营利组织 deSEC。目前性能与 AWS 持平，但 Bunny 仍缺少 HTTP/3、DS 记录发布及 IPv6 路由支持。

## 4. 「*sshole」：我们何时才能彻底告别C语言？

- 原始链接: <https://sunshowers.io/posts/sshole/>
- 英文标题: *sshole, or when are we finally going to get rid of C?

文章以2026年11月披露的一个SSH漏洞为切入点：在musl libc系统（如Alpine Linux官方AWS镜像）上，Unix中密码哈希「*」表示账户锁定，而musl的crypt函数对过长密码也返回「*」，加上sshd对锁定账户登录尝试做哈希以防时序泄露，三者叠加使未认证用户可能直接获得root shell。作者指出这并非内存安全漏洞，而是C语言缺乏代数数据类型与结果类型所导致的工程规范问题——C的类型系统无法强制开发者检查NULL返回值，musl开发者遂偏离POSIX规范，以哨兵值「*」表示错误。作者强调类型系统深刻影响工程文化：Rust社区规范不允许此类带内信号，密码过长会作为错误变体强制调用者处理。此外，作者批评Linux发行版维护者排斥Rust依赖，认为存在委托-代理问题；并反驳「AI agent可替代类型系统」的观点，指出社区积累的工程规范（如Rust库与代码模式）会自然编码更多不变量，忽视这些集体贡献是傲慢之举。

## 5. OpenBSD top(1) 新增 -Q 标志以显示 chroot、pledge 与 unveil 状态

- 原始链接: <https://undeadly.org/cgi?action=article;sid=20261106104957>
- 英文标题: OpenBSD top(1) adds flag to show chroot, pledge and unveil status

OpenBSD 的 top(1) 命令通过一次提交新增了 -Q 标志，用于在进程列表中展示每个进程对 chroot(2)、pledge(2) 和 unveil(1) 三项安全机制的使用情况。该提交由 Klemens Nanni 完成，经 deraadt 批准。具体实现上，pledge 的承诺信息会显示在 COMMAND 列，而 chroot 与 unveil 的状态字母则替代原有的 TIME 列，显示在 PRIV 列中。其设计目的是让管理员快速识别哪些程序未意识到自身权限、从而可能扩大系统攻击面，便于安全审计。提交者指出，非 root 用户若改用 ps(1) -o state,pledge 配合 tree-mode 或 watch(1) 虽可实现类似效果，但远不如 top(1) 交互便捷；由于 p 和 P 键已被占用，Q 键无既有含义且空闲，故被选为新标志。用户需安装最新快照版本才能体验此功能。该改动属于 OpenBSD 持续强化其安全沙箱机制（pledge/unveil/chroot）可观测性的一部分，使安全状态在常规监控工具中一目了然。

## 6. 不存在的端口：扫描整个IPv4的0端口

- 原始链接: <https://acid.vegas/blog/the-port-that-does-not-exist/>
- 英文标题: The Port That Does Not Exist

文章作者ACIDVEGAS指出，TCP端口0虽被IANA标记为「保留」，但16位端口字段在协议层并无禁止，因此可在网络上实际使用。作者先用iptables将IRC网络映射到0和1端口作为演示，随后用masscan（绕过内核TCP栈）扫描全部IPv4地址的0端口，获得约117万个SYN-ACK响应。然而94%的banner实为F5 BIG-IP负载均衡器的超时/重置日志，剔除噪声后仅约2905个地址真正运行服务，包括SSH（748）、MySQL（215）、Telnet（211）、HTTP（159）、FTP（105）等。大量暴露来自嵌入式设备：路由器、NAS、DVR、PLC（Beckhoff CX5120无密码远程桌面、Omron FINS/TCP）、Modbus主站、电力计量器、工厂遥测终端、DSC/Alwon报警通信器（部分泄露SIM卡ICCID及默认密码1234）、考勤机和家庭自动化网关。多数案例源于ISP的CPE配置中NAT外部端口被误设为0，少数为托管客户有意为之。文章还揭示了Linux内核将目的端口0作为「未连接」内部标记，导致getpeername()返回ENOTCONN，使Python ssl等客户端在已建立的连接上误判为未连接。整体结论是：端口0并非不可用，而是因工具链和内核语义的「共识性忽略」成为隐蔽藏身之处，但其中暴露的工业控制和安防设备构成实际安全风险。

## 8. GhostMap：无需打开即可让安卓手机陷入崩溃循环的系统漏洞

- 原始链接: <https://www.bitdefender.com/en-us/blog/labs/ghostmap-android>
- 英文标题: GhostMap: The Android flaw that crashes your phone before you open the app

Bitdefender Labs于2026年8月发现安卓系统漏洞GhostMap：安装一个特制APK即可使手机陷入持续崩溃循环，无需打开应用、无需权限、不含可执行代码。根本原因在于安卓两个核心库对ZIP条目处理逻辑存在分歧：libziparchive仅对「stored」类型校验未压缩大小，libandroidfw将非「deflated」条目一律按未压缩大小映射内存，二者间隙导致映射区域超出文件实际边界，进程读取时触发SIGBUS崩溃。若恶意条目位于系统服务自动读取的资源中，system_server将反复崩溃重启，手机陷入无法恢复的启动循环，重启与安全模式均无效，唯一解法是工厂重置（擦除全部用户数据）或事先开启USB调试后用ADB删除文件。该漏洞影响Android 10及以上所有版本，包括搭载2026年8月安全补丁的Pixel 10。Bitdefender两次向Google报告，Google均判定不在安全更新范围内，转交功能团队评估。此类解析器差异漏洞在安卓生态中已存在逾十年，理论上攻击者可借此禁用受害者手机或以数据丢失为要挟实施勒索，但目前尚未发现野外利用案例。

## 9. FOR UPDATE SKIP LOCKED Postgres 队列的性能极限在哪里？

- 原始链接: <https://garbagecollected.io/posts/postgres-task-queue-where-it-breaks/>
- 英文标题: Just how far can the FOR UPDATE SKIP LOCKED Postgres queue go?

本文通过实验探究基于 Postgres FOR UPDATE SKIP LOCKED 的持久化队列在单 CPU 环境下的性能上限。实验使用 Postgres 18 容器（1 CPU、1GB 内存、默认 100 连接），以 50 万条待处理任务为基准，将 worker 数从 1 逐步增至 128。结果显示：吞吐量在 32 个 worker 时稳步增长至约 292 jobs/s，64 个 worker 时达到峰值约 375 jobs/s 后停滞，128 个 worker 时反而降至约 208 jobs/s 且有 29 个连接失败。瓶颈并非连接数耗尽，而是 CPU 在 64 worker 时已占 86%，主要等待原因为 WAL 写入锁及队列头部少量页面的 BufferContent 锁。引入 20 连接共享池后，128 worker 吞吐量提升至 652 jobs/s，p99 延迟从 1.6s 降至 360ms，但 CPU 仍接近 100%，说明连接池只是抬高天花板而非消除瓶颈。文章还指出跨进程场景需服务端连接池（如 PgBouncer），并预告后续将探讨表膨胀与资源约束等问题。

## 10. 捕获隐藏在 PDF 中的提示注入攻击

## 12. GitHub Actions 工作流依赖锁定文件

- 原始链接: <https://docs.github.com/en/actions/concepts/security/workflow-dependency-lockfiles>
- 英文标题: Workflow dependency lockfiles

本文介绍了 GitHub Actions 的工作流依赖锁定文件（lockfile）机制。工作流通常通过 tag 或 branch 引用 action，但这些引用在运行时可能指向不同 commit，导致实际运行的代码与审查时不一致，存在被恶意篡改的风险。锁定文件将每个 action 依赖（含传递依赖）固定到已验证的 commit SHA，确保可复现、可审查、可审计。锁定文件存放于 .github/workflows/actions.lock，由 GitHub CLI 扩展 gh actions-lock 自动生成，禁止手动编辑。其结构包含 workflows 和 dependencies 两部分：前者记录各工作流使用的依赖，后者记录每个依赖解析到的 ref、commit、owner_id 和 repo_id，其中 owner_id 与 repo_id 用于运行时确认源仓库身份未变。锁定文件不覆盖可复用工作流调用（jobs.<job_id>.uses）、输入参数、secrets 及 runner 镜像。与传统的在 workflow 文件中直接写全量 SHA 相比，锁定文件的优势在于支持传递依赖、保持 workflow 文件可读性、记录源仓库身份，且能自动满足「Require actions to be pinned to a full-length commit SHA」安全策略。仓库可逐个工作流或批量接入锁定文件，接入后所有依赖必须存在于锁定文件中，且 commit 必须可从锁定的 tag 或 branch 到达，否则运行将被拒绝。

## 13. Alpine Linux openssh-server 密码认证绕过漏洞

- 原始链接: <https://www.alpinelinux.org/posts/2026-11-05-openssh-password-authentication-bypass/>
- 英文标题: Alpine Linux : openssh-server password authentication bypass

2026年11月5日，Alpine Linux发布安全公告，披露openssh-server存在严重密码认证绕过漏洞。当sshd未启用PAM（使用openssh-server包，或openssh-server-pam且UsePAM设为no）且PasswordAuthentication为yes时，攻击者无需任何密码即可登录。原理是：musl的crypt()函数对超过256字节的输入返回「*」，恰好与无密码账户（密码字段为「*」）的存储值匹配，一次连接即成功，无需重试。攻击者仅需知道一个无密码账户名，且系统存在至少一个含$5$或$6$哈希的账户即可利用。影响覆盖Alpine 3.16至3.24及edge所有版本。修复方案为升级openssh至10.6p2（各分支对应修复版本已发布）并重启sshd；若无法升级，应设置PasswordAuthentication no并重启。官方tiny-cloud镜像中alpine用户默认无密码且可doas提权，一旦系统出现$6$哈希即面临风险。日志中若出现对无密码账户的「Accepted password」记录，应视为已遭入侵。该漏洞由Wakefield的Özgün Kültekin报告，OpenSSH项目已发布10.6p2修复，撰写时暂无CVE编号。

本文由 Lennart Poettering 等人撰写，介绍 Amutable Foundations 的两大核心组件。AOS（Amutable OS）是一种基于镜像的 Linux 操作系统，以 Fedora 包为构建原料，在构建时预组装不可变磁盘镜像，从而消除传统包管理带来的「漂移」问题，实现逐字节可复现。AOS 通过少量（通常少于五个）粗粒度镜像组合构成系统，其中 system extensions 叠加于 /usr/ 提供可选组件（如图形驱动、云代理），configuration extensions 叠加于 /etc/ 实现原子化配置管理。镜像采用 UAPI.3 DDI 格式（EROFS + Verity + 签名 + GPT），配置镜像额外经 LUKS 加密；内核以 UAPI.5 UKI 形式分发，受 UEFI SecureBoot 与 TPM 保护。ACP（Amutable Control Plane）负责集群管理，涵盖节点注册、报告接收与验证、配置生成、TUF 镜像仓库、CVE 扫描及 Web UI，支持多租户。其核心机制为「加密锁定环」（CLL）：节点定期上报含 TPM/CoCo 度量的报告，ACP 验证后下发绑定硬件状态的配置镜像，形成远程与本地双重证明闭环。通信以异步报告与配置下发为主，辅以可选的远程 Varlink 模式（HTTPS + mTLS）实现交互式管理。安全设计涵盖七项要点：默认无 shell/SSH/语言解释器、仅允许签名镜像、W^X 策略、全量度量、禁用 SUID/SGID、强制完整性、内置工厂重置。系统机会性利用 TPM 2.0、AMD SEV、Intel TDX 等硬件，不可用时优雅降级为纯软件签名。

## 16. 探索 Janet 语言与 httpf 极简 Web 框架

- 原始链接: <https://nick.gs/blog/2026-11/exploring-janet-and-the-httpf-web-framework/>
- 英文标题: Exploring Janet and the httpf web framework

作者 Nick F 介绍了 Janet 语言及其 spork 扩展库中的 httpf 极简 Web 框架，并给出了目前可能唯一的实践教程。Janet 是一种小型 Lisp/Scheme 风格语言，自带标准库，spork 作为事实上的标准扩展库提供 httpf 模块。文章演示了基本用法：创建服务器对象、通过函数元数据（:path 标签）定义路由、调用 add-bindings-as-routes 注册路由、最后监听端口。路由函数接收 request 和 post-data 两个参数，Content-Type 由 :render-mime 元数据决定，返回 hiccup 风格数据结构交由 spork/htmlgen 渲染，响应码通过 setdyn 设置。作者指出 httpf 存在明显局限：不支持动态路径参数（如 /posts/:id）、无法设置响应头（因此不能写 cookie）、没有内置静态文件服务。此外，Janet 生态中另有 Circlet（GPL 许可，限制商用）和 Joy（功能更全但存在 cookie 相关 bug）两个框架。作者总结认为 httpf 仅适合最基础的演示，尚不足以支撑实际开发，但期待 Janet 生态持续成长。

## 18. 未经审视的转发：Web框架对Forwarded请求头的过度信任

- 原始链接: <https://www.lkoskela.fi/blog/2026-11-05-forwarded-without-question/>
- 英文标题: Forwarded Without Question: How Web Frameworks Overtrust the Forwarded Header

作者在工作中部署Envoy反向代理时，发现多数反向代理和CDN不处理RFC 7239定义的Forwarded请求头，而是将其原样透传至后端应用。然而Rails、Jetty、Spring Boot等框架在默认或近默认配置下会解析Forwarded头，且其优先级高于X-Forwarded-*系列头。这意味着攻击者可在未经代理处理的Forwarded头中伪造客户端IP、主机名和协议，绕过IP限制、速率限制或密码重置流程。具体而言，Rails 8.1因Rack库变更意外启用了Forwarded: for解析，8.1.4.1已修复；Jetty自2016年起默认优先Forwarded；Spring Boot 4.2已改为默认仅解析X-Forwarded-*；Symfony虽在冲突时返回400，但host字段仍可被单独伪造。反向代理方面，Envoy、Nginx、Traefik、Apache、Caddy、Kong均不处理Forwarded头，仅HAProxy在显式配置下支持。作者建议开发者和运维人员确保代理与应用对信任的请求头达成一致，并在代理层丢弃所有不可信的转发头，以消除伪造攻击面。

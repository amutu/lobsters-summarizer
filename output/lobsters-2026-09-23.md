## 1. 纯文本文件正面临消亡风险

- 原始链接: <https://paste.sr.ht/~awal/b76caf6f213a96a634454fa7292c035a10035b49>
- 英文标题: Plain-text files are at risk

作者指出，纯文本文件（txt、md、ini、json等）是人类迄今唯一真正通用的数据接口：它们直接存储在文件系统中，可用最基础的文本编辑器读写，不同编辑器间可互操作，无需云连接，且几乎所有操作系统（Linux、Windows、macOS）都默认附带纯文本编辑器。然而，这一传统正加速瓦解。智能手机普及是最大打击——双寡头系统未预装纯文本编辑器，也未能催生第三方纯文本编辑生态，普通用户几乎已遗忘「文件」这一概念。目前仅软件工程师群体仍在维护纯文本编辑生态，因为代码和配置文件本质上是纯文本。但如今开发者正将文本输入乃至文档编写外包给LLM REPL，代码审查仅以网页diff形式完成，手动编辑的需求急剧萎缩。作者警告，若这一最后的受众也转向LLM工具，纯文本编辑器及其插件生态将无人维护，随着操作系统和底层库持续更新，现有编辑器可能直接失效；文件管理器也可能步其后尘。叠加「通用计算的战争」——个人难以在缺乏企业或国家许可的情况下独立部署简单软件——纯文本文件这一最灵活、最通用的数据接口，可能最终变得不可触及。

- 原始链接: <https://lwn.net/SubscriberLink/1094575/2385e98583715c2b/>
- 英文标题: Looking forward to Git 2.56 - and 3.0

Git 2.56 发布候选版预计于 2026 年 9 月底推出，包含 700 余个提交，改进包括 git history drop 子命令（移除指定提交并重放后续提交）、git refs 新增 create、delete、update、rename 子命令、git branch --delete-merged 选项、git add --resolved 选项等，整体稳健但无颠覆性变化。文章重点展望了备受期待的 Git 3.0，其核心兼容性变更包括：默认哈希函数从 SHA-1 切换为 SHA-256 以消除长期安全隐患；对象 ID 仅接受小写形式以消除大小写歧义；引用存储从 .git/refs/ 文件机制切换为 reftable 二进制格式，以解决 Android 等超大型仓库中 80 万余条引用带来的性能瓶颈；Rust 编译器将成为构建 Git 的必需依赖。GitHub 员工 brian m. carlson 表示 GitHub 端 SHA-256 支持即将就绪，libgit2 亦已完成 reftable 与 SHA-256 适配，他认为上述变更不应阻碍 3.0 发布。据后续更新，发布计划为：2026 年 12 月推出 2.98 作为过渡信号，2027 年 4 月同时发布 2.99 长期支持版与 3.0，后者将成为后续所有版本的基础。评论区还讨论了子模块不支持混合哈希算法、以及集成分支与开发分支缺乏原生区分机制等议题。

## 3. Fearless SIMD v1.0 正式发布

- 原始链接: <https://linebender.org/blog/fearless-simd-1-0/>
- 英文标题: Fearless SIMD v1.0 is here

Fearless SIMD 是一个 Rust SIMD 抽象库，v1.0 于 2026 年 9 月发布，核心目标是将 unsafe 从 SIMD 编程中彻底移除。性能方面，该库为跨平台行为不一致的操作（如 swizzle、浮点最大值）同时提供精确变体与快速变体，支持按硬件原生向量宽度编写算法，并允许无开销地安全降级到平台 intrinsics，不设性能上限。安全性方面，通过 kernel! 宏（借助编译器 target feature v1.1）调用大部分 SIMD intrinsics，配合受 bytemuck 和 zerocopy 启发的 safe transmute 模块处理原始指针的加载与存储，仅需审计两个小型构建块即可保证整体内存安全，整个 crate 无需 ad-hoc unsafe 代码。易用性方面，同步发布的 fearless_simd_macros v0.1 提供「#[simd]」过程宏，实现非泄漏抽象，用户无需关注底层内联细节。该库承诺 3 年安全更新，并规划了向 std::simd 迁移及支持 SVE、RISC-V 向量扩展等演进路径，且不会因 std::simd 稳定而失去存在价值。目前已有 30 个 crate 直接依赖、逾千个 crate 间接依赖 fearless_simd，在 Rust 生态中占有重要地位。

## 4. 关于参数的争论：Rust 该不该引入命名参数？

- 原始链接: <https://steveklabnik.com/writing/arguing-about-arguments/>
- 英文标题: Arguing about arguments

Rust 核心团队成员 Steve Klabnik 在博文中系统梳理了函数参数相关的几类语言特性：命名参数、可选/默认参数、函数重载，并以 Ruby 的 redirect_to 为例说明这些特性虽简洁却令调用方难以理解。作者过去坚决反对 Rust 引入这些特性，认为它们彼此纠缠、大幅增加语言复杂度，而 Rust 用不同函数名（如 Vec::new 与 Vec::with_capacity）换取规则简单是正确取舍。然而作者近期改变了对「命名参数」一单项的看法：在 AI 编程代理日益普及的背景下，命名参数带来的冗余输入成本由代理承担，而其可读性收益对代理同样显著（无需回查签名即可理解实参含义，节省 token），因此作者对此持开放态度。但他仍反对可选/默认参数，因其刻意隐藏调用信息，与清晰性目标相悖。文章还列举了在 Rust 中实现命名参数的诸多实际难题：参数本质是模式而非名称、函数作为值时参数命名冲突、调用点求值顺序与借用检查的交互、重命名破坏向后兼容等。最终作者表示尚未下定论，但已不再像过去十余年那样完全排斥该提案。

## 5. Mac原生UI的时代或许该结束了

- 原始链接: <https://inessential.com/2026/09/22/that-about-wraps-it-up-for.html>
- 英文标题: That About Wraps It Up for Stock Mac UI

NetNewsWire开发者Brent Simmons在最新macOS发布后，对Liquid Glass设计表达了明显不满，尤其不满全高度侧边栏和Liquid Glass按钮。他调研发现，用户公认好看的Mac应用（如Things、Slack、Craft、OmniFocus等）大多并未使用原生UI。文章逐一拆解了坚持使用原生UI的传统理由：其一，用户熟悉性——用户根本不区分原生与自定义界面，甚至对Electron应用毫无概念；其二，开发者省力——以NetNewsWire为例，去年适配Liquid Glass反而比自定义UI应用（如Things）付出更多工作量。作者承认Apple仍拥有世界顶尖设计团队，但认为当前Mac UI的设计方向本身出了问题，执行者只是忠实落实了错误指引。最终结论是：使用原生UI已无充分理由，除非为了获得资深Mac开发者的认可。文章末尾，作者展示了在NetNewsWire分支中移除Liquid Glass元素后的实验性界面，坦言效果「可爱」但可能后续删除，并计划为工具栏图标增加色彩与布局优化。整体语气坦诚、略带自嘲，核心观点是：在用户无感、开发成本反增、设计方向存疑的三重背景下，固守原生UI已不再合理。

## 6. 命名参数与可选参数：Rust 的缺失与未来提案

- 原始链接: <https://botahamec.dev/named-optional-args>
- 英文标题: Named and Optional Arguments are Awesome

作者认为 Rust 最大的不足是缺乏命名参数和可选参数，并系统对比了 Dart、C#、TypeScript 等语言的处理方式。Dart 用花括号包裹命名参数，支持默认值与 required 关键字，设计最为完善；C# 允许任意参数命名且语法简洁；TypeScript 缺乏原生命名参数，需借助匿名类型与解构语法模拟，在 React 组件中尤为繁琐。Rust 目前的变通方案是定义结构体并实现 Default 特征，但类型非匿名、默认值需手写函数，冗长且仅适用于全部参数都有默认值的情况。作者以 HashMap 的八个工厂函数和易混淆的 print 参数为例，说明命名与可选参数能显著减少 API 冗余、降低出错概率。随后文章梳理了社区多项提案：默认字段值（已进 Nightly）、结构记录（因解析歧义和 trait 实现困难被搁置）、仿 C# 的任意顺序命名调用、Public Arguments 预 RFC（最完整但存在语法冲突与 Fn 特征适配问题）、结构体风格调用、仿 Dart 花括号语法、版本隔离、点前缀等，逐一分析其优劣。作者最终认为各提案的要素已齐备，可组合出一个兼顾向后兼容与表达力的完整方案，并以此文作为预 RFC 征求社区意见。

## 7. 编程语言设计准则（2024）

- 原始链接: <https://blog.veritates.love/design-it-right>
- 英文标题: Design your programming languages right (2024)

本文以随笔形式提出新编程语言设计应遵循的基本原则，将议题分为「已解决」与「未解决」两类。已解决方面：缩进感知的多行字符串（Dhall、Nix等已给出方案，应尽早内置，否则将受向后兼容性束缚）；文件路径应相对于所在文件或项目根目录，而非依赖工作目录；选定一两个文件扩展名并坚持使用，以兼容现有生态的语法高亮与搜索工具；允许尾逗号；数字字面量、字符串转义及关键字等语法应预留扩展空间，关键字建议附带sigil以避免与标识符冲突。未解决方面：开发态与发布态工作流差异应被尊重；版本管理尤为复杂，涉及跨版本迁移脚本的测试、API变更的自动检测，作者还强调发布版本应附带日期以便跨软件比较；文件监听难以事后 retrofit 到构建系统中；与find、grep等外部工具的集成（如提供文件列表、区分标识符与字符串的搜索）能显著提升开发者体验。作者核心观点是：许多设计决策必须在一开始就做对，否则后续修改代价极高。

## 8. 树莓派固件锁定Pi 5内存芯片，禁止用户自行更换升级

- 原始链接: <https://www.jeffgeerling.com/blog/2026/raspberry-pi-ram-lockdown/>
- 英文标题: Raspberry Pi locks down Pi 5 RAM upgrades in firmware

树莓派在固件中加入了限制，禁止用户更换Pi 5上的内存芯片，甚至同容量的其他板卡芯片也无法互换。此举起因是部分商家购买廉价1GB或2GB版Pi 5，焊接低质8GB内存后冒充全新8GB版出售，给官方售后带来大量问题。作者指出该固件更新实际发布于2024年底，并非近期AI热潮所致。从技术角度看，LPDDR内存时序复杂，焊接不良或廉价芯片易引发异常故障，超频和高温会进一步加剧问题，因此树莓派有合理的技术与法律理由进行锁定。但作者认为此举违背了树莓派「可自由折腾」的核心理念，且目前除回退到2024年9月10日及更早的旧固件外，几乎没有绕过方法。作者建议借鉴旧版Pi（至Pi 3B）的「保修位」机制：用户主动设置一次性固件标志声明放弃保修，即可合法更换内存，既保护官方利益又不剥夺用户维修和升级的权利。此外，软件层面可通过树莓派公开的型号代码验证内存规格，也有网友建议用钻孔替代焊接电阻来标识出厂内存容量。文章最终将此视为硬件所有权领域又一令人遗憾的退步。

## 9. Java类文件魔数0xCAFEBABE的由来

- 原始链接: <https://www.artima.com/insidejvm/whyCAFEBABE.html>
- 英文标题: Why 0xCAFEBABE?

1996年5月，Bill Venners在comp.lang.java新闻组发帖，询问每个Java class文件前四个字节为何固定为魔数0xCAFEBABE。帖子引发热烈讨论：有人猜测这是Java团队借咖啡隐喻，用十六进制字母A-F拼出「CAFE BABE」，比「A FAB CAFE」「CAFE FACE」等更酷；有人指出NeXTSTEP的胖二进制文件早已使用0xCAFEBABE标识Intel目标码、0xFEEDFACE标识Motorola目标码，Sun可能沿用了这一惯例；还有人列举了0xDEADBEEF（IBM/AIX标记未初始化内存）、0xBADBADBADBAD（Burroughs B6700）等经典魔数。最终，Java原始团队成员Patrick Naughton给出权威回答：该魔数在语言被命名为Java之前就已选定，团队只是想要一个有趣、独特、易记的值，0xcafebabe胜出了第二名0xdeadbabe（后者被IRIX arena文件占用）。与Java名称的关联纯属巧合。此外，Solaris调试内核使用0xCAFEFEED标记空闲内存块。整篇讨论以轻松幽默的社区风格，还原了一个技术细节背后的历史轶事。

## 12. EvilVM：基于Forth的位置无关Shellcode远程执行平台

- 原始链接: <https://web.archive.org/web/20250418124519/http://evilvm.ninja/>
- 英文标题: EvilVM: Forth shellcode

EvilVM是一个面向信息安全领域的远程代码执行项目，其核心是一个原生代码Forth编译器，以位置无关的x86_64 shellcode形式部署，体积仅5至10KB。项目于2019年在NolaCon会议上发布Alpha版本，演讲者Irongeek在YouTube上提供了演示录像。主要使用场景为：将agent部署到远程系统后，通过交互式shell或REPL进行控制，向agent交付代码并编译加入全局环境。技术选型围绕以下目标：一是小型化、易部署的payload；二是通过抽象网络流实现远程I/O，支持TCP、HTTP等传输；三是提供对编译器内部、机器码及内存的底层直接访问；四是提供简单的C FFI，便于导入DLL、查找导出函数并用Forth封装；五是Forth语言兼具「低门槛」（接近汇编）与「高天花板」（支持运行时语法扩展和元编程）；六是payload生成支持多种编码与封装方案，适配漏洞利用、注入等典型恶意投递场景。项目代码托管于GitHub，文档站同时提供快速入门指南。

2026年9月，Rust安全响应团队披露：Miri在运行时会将全部环境变量写入target/目录，当GitHub Actions缓存该目录时，若CI环境中包含密钥，PR的CI可通过读取缓存获取这些密钥，造成泄露。攻击者只需打开PR即可触发CI读取缓存，随后推送第二个commit覆盖痕迹，而GitHub UI可能隐藏被覆盖的提交，日志数月后亦会删除，增加了检测难度。短期修复为Miri仅保留CARGO_*（排除CARGO_*_TOKEN）及OUT_DIR变量，该补丁将随2026-09-22 nightly发布。团队对GitHub生态进行了扫描，发现1个仓库存在此问题、7个需警惕，已通知相关维护者。受影响条件为：CI中运行cargo miri、该步骤可访问密钥、缓存了target目录且缓存对PR可读。快速缓解措施包括禁用该任务缓存、将密钥限定于不调用Miri的步骤、临时停用Miri，并务必清除已有缓存、轮换可能泄露的密钥。文章同时提醒：即使不使用Miri，也应确保可写入公共缓存的任务不接触密钥，因为许多工具会将整个环境写入文件系统，Rust工具链不保证环境变量不会落入编译产物。该问题由OpenAI的Predrag Gruevski报告，生态扫描借助OpenAI提供的Codex完成。

## 17. 第一次Futamura投影：从解释器特化出编译器

- 原始链接: <https://blog.veitheller.de/A_First_Futamura_Projection.html>
- 英文标题: A First Futamura Projection

作者以自研的Brainfuck到Carp编译器compfuck为切入点，完整演示了第一次Futamura投影的实现。文章首先将原有编译器「逆向」改写为解释器interpret-compf，使其逐条执行指令而非收集代码片段；随后构建一个特化器specialize-compf，对解释器源码进行部分求值：将仅依赖源程序的静态部分（指令分发、括号匹配、步长计算）在编译期求值消除，将依赖运行时的动态部分（磁带操作、循环体）保留为残余程序。关键工程技巧包括用defmacro definterpreter同时生成函数并保留其源码元数据，用defstatic让括号搜索在编译期与运行期均可调用。最终通过compile-compf将特化结果拼入main函数，对外接口仍为(compf「某段Brainfuck」)。作者强调，此实现手工划分了静态与动态边界，真正的通用部分求值器要复杂得多，但核心洞见在于：给定解释器与已知程序，即可自动推导出等效编译器，无需另行编写指令翻译逻辑。

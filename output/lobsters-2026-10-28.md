## 1. 面向 Rust 生态的快速安全 tar 解析器 tar-codec

- 原始链接: <https://astral.sh/blog/tar-codec>
- 英文标题: A fast and secure tar parser for the Rust ecosystem

本文介绍了 Python 包管理工具 uv 在 0.13 版本中引入的全新 tar 解析器 tar-codec，其解析速度约为前代实现 astral-tokio-tar 的两倍，同时显著降低了解析器差异带来的安全风险。文章首先解释了 uv 作为 Python 包安装器需处理两种分发格式：wheel（ZIP 格式）和 sdist（tar 格式），其中 sdist 在安装时执行任意代码，安全性尤为关键。作者指出，astral-tokio-tar 存在大量解析器差异漏洞，攻击者可构造使不同解析器（如 uv、pip）对同一 tar 包产生不同解包结果的恶意归档，甚至让在 PyPI 上看似安全的包在本地解压时释放危险内容。由于 tokio-tar 系列在设计上过于宽松，修补成本高于重写，团队决定从零开发 tar-codec。文章随后以大量篇幅梳理了 tar 格式家族的演变：从 UNIX V7（512 字节定长块、路径限 100 字节、文件限 8 GiB）到 UStar/pax（引入扩展头突破限制）再到 GNU tar（采用 base-256 编码和 L/K 特殊类型标志），并详细分析了各变体头部结构、pax 全局/局部扩展头的优先级机制以及 GNU tar 的堆叠扩展。文章强调 tar 的块格式对填充区域无约束，这使其天然容易遭受解析器差异攻击，也是 tar-codec 必须严格规范解析行为的核心动因。

## 2. 告别劣质屏幕共享：用 WHIP 协议让 OBS 和 FFmpeg 直连视频会议

- 原始链接: <http://shittyscreenshare.com>
- 英文标题: Shitty Screenshare

本文作者（OBS 中 WHIP 功能的开发者）针对浏览器屏幕共享画质差、模糊的问题，提出使用 WHIP（WebRTC-HTTP Ingestion Protocol）作为解决方案。WHIP 是一项开放标准，允许通过 WebRTC 将直播视频推送到服务端，只需提供服务器 URL 和流密钥（bearer token）即可。在 WHIP 出现之前，加入视频会议必须运行各厂商的专有客户端代码，导致 FFmpeg、OBS 等工具无法直接接入。借助 WHIP，OBS 和 FFmpeg 可以直接将画面送入视频会议，用户能自行设定分辨率、帧率、码率和编解码器，从而根据共享内容和硬件条件精确控制画质，避免浏览器自动选择不匹配参数导致的模糊问题。文章还指出 OBS 虚拟相机虽能选择布局，但编码仍由会议应用接管，控制力有限。作者呼吁用户向不支持 WHIP 的视频会议服务商施压，要求采用开放标准而非专有客户端，并提供了 OBS WHIP 配置指南的链接。整体而言，文章核心观点是：屏幕共享质量差并非不可解，WHIP 让专业工具与开放协议结合，是提升共享体验的可行路径。

## 5. 编译时依赖类型：Syl 语言的模态类型系统设计

- 原始链接: <https://thenumb.at/Syl-Intro/>
- 英文标题: Compile-Time Dependent Types

本文介绍了作者正在开发的编程语言 Syl，其目标是通过模态类型系统（modal type system）将编译时计算编码进类型层面，灵感源自 András Kovács 的两层类型理论与 OxCaml。Syl 为每个值赋予两个模式轴：静态性（static/dynamic）与擦除（erased/unerased）。静态值在编译时可知，擦除值在运行时不可见。通过静态参数，函数可被单态化（monomorphized），从而获得依赖类型——返回类型可依赖输入的具体值。Syl 在编译时是依赖类型化的，运行时退化为简单类型化，类似 C++ 模板特化的效果。与 Lean、Coq 等定理证明语言不同，Syl 允许编译时计算中的一般递归与「type type type」，不强制全函数性，代价是类型检查不可判定，但无需全函数性检查器或宇宙层级机制。文章给出了带类型解释器和长度索引向量等示例，并展示了高阶类型、模块与函子、多文件导入、类型反射等特性均可在用户层用编译时依赖类型实现。作者指出设计尚不完整，仍需模式多态、生命周期、线性性、增量编译及 LLVM 后端等工作。

## 6. Filian与Fil-C在Debian上的二进制包适配

- 原始链接: <https://cr.yp.to/2025/fil-c.html>
- 英文标题: Filian, Fil-C binaries on Debian

本文为djb关于在Debian系统上使用Fil-C（内存安全的C/C++编译器，含filcc与fil++）的技术笔记。Fil-C兼容性良好，多数库和应用无需修改即可编译运行；性能上，Fil-C编译的代码通常比clang多消耗1至4倍周期。djb正在开发Filian项目，可在Debian 13上自动下载、编译Fil-C及glibc，再用Fil-C编译选定的Debian源码包并安装；Mikael Brockman的Filnix项目则将Nix包适配到Fil-C。编译Fil-C本身内存需求较大（约19GB swap加12GB RAM），128核512GB机器约8分钟即可完成。djb在61个构建目标中成功编译60个，涵盖openssl、git、vim、perl、python等常用软件，并额外验证了boost、mutt、tig、w3m等。Debian集成方案借鉴多架构（ABI）机制，将Fil-C编译的包注册为新架构（如amd64fil0），与原生包隔离安装，涉及include路径适配、autoconf配置修改及dpkg-buildpackage构建流程等细节。文章还提供了供应链审计脚本，帮助审计员比对Fil-C与上游clang、glibc等源码的差异。

## 7. 模糊测试与 AI 之争：Fuzzilli 与 BigSleep 在 JavaScript 引擎上的对比

- 原始链接: <https://projectzero.google/2026/10/fuzzing-v-AI.html>
- 英文标题: Fuzzers vs. AI: Comparing Fuzzilli and BigSleep on JavaScript Engines

Google Project Zero 在博客中对比了两种用于 Chrome V8 引擎漏洞发现的自动化工具：生成式模糊测试器 Fuzzilli 与基于大语言模型的智能体系统 BigSleep。在 2026 年 4 至 9 月的生产环境中，BigSleep 发现 45 个漏洞，Fuzzilli 发现 37 个，两者重叠约 25%。为评估理论重叠，团队还让 BigSleep 尝试重新发现 2023 年以来 Fuzzilli 报告的历史漏洞，结果显示约 62% 的历史漏洞可被重新发现，调整提示词后升至约 70%，综合估计理论重叠约 60%。分析表明，对模糊测试器而言难以发现的漏洞，对 AI 智能体同样困难，因此模糊测试不宜被取代；而编译器相关漏洞的重叠率明显低于引擎其他部分。此外，实验未发现模型因训练数据记忆而产生显著偏差。文章结论认为，模糊测试与 LLM 分析是互补方法，仍有相当比例的漏洞仅能被其中一种手段发现，建议厂商同时部署两类工具以最大化漏洞覆盖。

## 8. 用调用图分析器定位 Rust 中的 panic 路径

- 原始链接: <https://tweedegolf.nl/en/blog/242/finding-panics-with-call-graph-analyzer/>
- 英文标题: Finding panics with Call Graph Analyzer

本文介绍了由 Open Device Partnership 与 Microsoft 联合开发的开源工具 Call Graph Analyzer（CGA），该工具以 rustc-driver 形式运行，从单态化 MIR 中提取完整调用图，从而定位编译产物中所有可能触发 panic 的函数。文章首先讨论了消除 panic 的动机：嵌入式场景下 panic 字符串占用大量代码空间，关键路径（如固件更新、防 DoS 攻击）不允许崩溃，以及 panic 处理代码本身存在双重 drop 等风险；但完全消除 panic 既不现实也无必要，更合理的做法是让 panic 路径显化并纳入回归分析。随后，文章对比了已有方案——基于 ELF 调试信息的 rustig/findpanics、基于 HIR 的 cargo-callgraph、基于链接器的 no-panic/dont_panic 以及 rust-analyzer 方案——指出 MIR 级分析能覆盖依赖库和标准库中的 panic，但会在 LLVM 优化前产生假阳性。CGA 从 crate 入口（main、_start、extern 函数等）出发做可达性遍历，处理泛型单态化、dyn 对象（假设所有 vtable 条目均被调用）、函数指针及 async 块等复杂情况。工具支持将调用图导出为 JSON 或 GraphViz dot 文件，也可通过「cargo cga check」直接报告 panic 路径并给出带回溯的诊断信息；同时提供白名单与黑名单配置，允许用户豁免可信函数或禁止调用特定 API（如文件系统、网络）。主要局限包括：依赖特定 nightly 版 rustc 无法从 crates.io 安装、编译耗时约为 cargo check 的两到三倍、以及 dyn 和函数指针带来的假阳性。

## 9. 在 Java 中实现完整的 Haskell 风格类型类解析

- 原始链接: <https://garciat.com/posts/java-type-classes/>
- 英文标题: Full Haskell-like Type Class resolution in Java

本文探讨在纯 Java 中构建一个 Haskell 风格类型类实例解析引擎的可能性。作者利用 Java 反射、泛型类型元数据及一个小型一阶统一算法，实现了自动推导类型类见证（即 Haskell 中的 instance），支持高阶类型类、重叠实例及任意嵌套泛型类型的见证构造。文章首先解释类型类的核心思想：将行为绑定到类型而非对象实例，通过静态工厂方法（见证构造器）组合式地构建类型行为。技术路径上，作者利用 Java 泛型在 getGenericInterfaces() 等场景中保留的运行时类型信息，通过 Ty<T> 接口捕获静态类型；将 java.lang.reflect.Type 层级解析为统一的 ParsedType 抽象语法树；实现递归类型统一算法以匹配见证构造器的参数；再依据「仅在类型类与目标类型的定义中查找 @TypeClass.Witness 注解方法」的约定完成见证解析。文章还展示了 Show、Eq、Monoid、Traversable、Functor、Monad 等一阶与高阶类型类的完整示例。作者强调该项目并非面向生产，而是实验性质，揭示了 Java 运行时实际保留的类型结构远超预期，无需语言层面改动即可逼近类型级编程。项目代码已开源至 GitHub。

## 12. 忒修斯之变——玩具级位溯源抽象域

- 原始链接: <https://www.pypy.org/posts/2026/10/toy-bit-provenance.html>
- 英文标题: The Shift of Theseus — Toy Bit Provenance Abstract Domain

本文介绍了一种用于编译器优化的「位溯源」（bit provenance）抽象域，旨在弥补此前Knownbits玩具抽象域无法追踪位在不同指令间移动的缺陷。作者以「a = x & 0x0f; c = (x << 60) >> 60; result = a & c」为例，说明a与c计算结果相同，可折叠为result = a，而局部peephole规则难以覆盖此类长序列。位溯源域的核心思想是：对每个SSA变量的64个位，记录其来源（某操作的第i位，可选取反）或常量值0/1。实现上，SourceBit记录来源操作、位索引和取反标志；BitProvenance以元组存储全部位信息，并提供from_source（未知）与from_constant（常量）两个工厂方法。转移函数方面：取反操作翻转常量位并切换inverted标志；常量移位直接搬移位、非常量移位则退化为未知；and/or/xor逐位处理，遇到无法用常量或单一来源表示的情况时，用SourceBit(result, i)标记为未知。文章还借助Hypothesis属性测试验证了常量往返及移位正确性。该域的优势在于能自动识别跨多条指令的位等价关系，避免为每种模式手工编写peephole规则，从而更通用地消除冗余计算。

## 13. 修复 KIO 向 USB 存储设备与网络文件系统复制文件的进度与完成判定缺陷

- 原始链接: <https://blogs.kde.org/2026/10/27/fixing-kio-copy-to-usb-stick-and-network-filesystems/>
- 英文标题: Fixing KIO copy to USB stick and network filesystems

本文讲述了 KDE 文件 I/O 库 KIO 中一个存在 15 年（2011 年报告）的高优先级缺陷的修复过程。该缺陷导致向 USB 存储设备或 NFS/SMB 等网络文件系统复制文件时，进度条和完成通知反映的是数据写入内存页缓存的速度，而非实际落盘或到达服务器的进度；在慢速设备上，复制「完成」时数据可能仍在内存中，拔出设备即丢失。修复方案核心是引入 sync_file_range() 实现按窗口回写：数据以自适应窗口（1 MiB 至 16 MiB，CIFS 上至 128 MiB）分批写入，辅助线程负责回写已提交窗口，使内存中未落盘数据始终不超过两个窗口，进度条最多领先一个窗口。对可移动设备，复制结束时通过 fsync() 或 syncfs() 确保全部数据落盘；移动操作在刷新成功后才删除源文件。设备可移动性通过 sysfs 判断，网络挂载通过 statmount() 避免阻塞。附带修复了跨文件系统复制回退至 sendfile() 的性能问题。所有更改已合入，将随 KDE Frameworks 6.32（2026 年 11 月 13 日）发布。修复后，慢速链接上复制仅慢约 3%，快速链接基本无影响，且复制期间共享目录仍可正常浏览。

## 1. 我现在选模型主要看速度，而不是智能

- 原始链接: <https://martinalderson.com/posts/speed-vs-intelligence/>
- 英文标题: I'm (mostly) picking models on speed now, not intelligence

本文作者表示，自己首次不再以原始智能作为日常使用模型的首要标准，而是转向速度。他认为当前像 Opus 4.6 这一级别的模型已经“足够聪明”，能胜任编程、研究、演示文稿和数据分析等日常任务。相比之下，Fable 虽强大但输出太慢，体验不佳，作者很快换回 Opus。作者指出，速度对软件体验至关重要，100毫秒是人类的“即时”感知门槛，100–200 tok/s 的输出速度已经相当快，低于50 tok/s 会显得拖沓，超过200 tok/s 甚至令人不安。开源模型生态为此带来重大利好：提供商为吸引用户而在 OpenRouter 等平台上激烈竞争速度，例如 GLM5.2 的推理速度可以从不到30 tok/s 到129 tok/s 不等。但速度提升也有瓶颈——当模型足够快后，工具调用、本地硬件和人类决策会变成新的制约因素，5倍模型提速可能只换来2倍的任务总体提速。与此同时，价格战正在打响，OpenAI 大幅降价，GLM5.2 的每百万 token 价格已低至 Opus 的5%。随着新一代 GPU 推出，2027年可能出现500+ tok/s 的高质量模型。作者保留的疑问是：超大参数模型是否真的在日常任务中显著胜出，以及模型的安全护栏仍会在关键时刻带来干扰。

## 2. Atom在关键方面优于RSS

- 原始链接: <https://chrismorgan.info/atom%3Erss>
- 英文标题: Atom is better than RSS, in ways that matter

作者主张Atom在关键方面优于RSS，并希望以实用理由说服读者弃用RSS。文章首先承认大多数差异无关紧要，但强调标题编码语义是真正重要的区别。RSS对标题中的特殊字符（如<、&）和HTML内容缺乏明确的编码规范，不同实现处理不一，导致标题无法可靠表达。Atom则通过text construct机制，允许作者将标题明确指定为纯文本、实体编码HTML或XML编码HTML，确保无歧义。作者举例说明了如何编码包含<xmp>的标题。他还提到摘要与全文的区分问题，虽未展开，但同样认为Atom更优。最后，作者探讨了播客领域RSS仍占主导的原因：苹果早期只支持RSS，且后续也未曾支持Atom，导致Atom在播客生态中缺失。作者希望人们基于这些实际差异选择Atom，而不是出于意识形态。

## 3. C语言中sizeof的解析出奇地困难

- 原始链接: <https://sebsite.pw/w/20260802-sizeof.html>
- 英文标题: sizeof is surprisingly difficult to parse in c

本文讨论了C语言中sizeof运算符的解析难点。sizeof的操作数既可以是一元表达式，也可以是带括号的类型名，因此sizeof 67、sizeof(67)、sizeof(int)、sizeof (x).y都是合法的，只有类型名才需要括号。朴素的解析方法是先看是否有左括号，若有则尝试解析类型名，失败则回退并解析表达式。但复合字面量的存在使情况复杂化，例如sizeof(int){0}中(int){0}是表达式，导致解析需要特殊处理。即使特判复合字面量后的左花括号，后续还可能跟随后缀运算符，如sizeof(T){}.x[0]()。文中提出了两种方案：一是扩展特判以解析复合字面量后的任意后缀运算符；二是编写一个同时尝试解析一元表达式或带括号类型名的函数，避免回溯。但第二种方案需注意不能将一元表达式和强制类型转换表达式合并解析，因为sizeof(int)+1是加法表达式，而不是对强制类型转换表达式求大小。这些分析同样适用于C2y新引入的_Countof运算符。文章强调C语言中sizeof的语法看似简单，实际解析涉及多种边界情况，需要谨慎处理。

## 4. 手动重打LLM生成的代码，以避免认知债务

- 原始链接: <https://ankursethi.com/blog/prevent-cognitive-debt-by-manually-retyping-llm-generated-code/>
- 英文标题: Prevent cognitive debt by manually retyping LLM-generated code

作者虽在四月表示不再使用编码助手，但个人项目中仍在用LLM来加速枯燥部分。然而放任AI自由修改代码会带来巨大认知债务：他不想完全把理解交给机器。虽然很多开发者会逐行审查AI生成的PR，但作者讨厌阅读冗长、防御性过强、注释糟糕且微妙出错的AI代码，尤其不愿在个人项目中这样做，因为个人项目重在过程乐趣。他的解决方案是：让编码助手在聊天中生成代码，但绝不直接修改项目文件，而是由他手动将所有编辑逐字敲入编辑器。他在代理配置中写明：所有建议编辑必须在聊天中展示，以便手动输入；命令也需显示而非执行；并要求AI不解释基础语法。这种看似低效的方式让他比完全不用LLM约快2倍，但比完全放手的人慢。手动输入每一行代码使他建立对代码及代码库空间结构的心智模型，更容易发现幻觉或不良设计，并顺势清理、重构、加入注释。他类比年轻时学编程的抄代码建议，认为这是同样的学习过程。他担忧行业正在积累大量认知债务，未来可能不再理解数字基础设施的构建方式，他至少能确保自己完全理解发布的软件，否则就是职业失职。

## 5. 你的网站去哪儿了？

- 原始链接: <https://www.arscyni.cc/file/warez_your_website.html>
- 英文标题: Where's your website?

本文针对那些依赖社交媒体却渴望拥有个人网站的人，提供了一套快速、免费、轻量级的建站方案。作者指出，虽然理想方式是购买域名、自建网站并用Codeberg或statichost托管以获得完全控制权，但对多数人而言，使用现成的博客平台更现实。文章重点评测了三个免费托管选项：Mataroa.blog、Pagecord.com和Bearblog.dev，三者均支持Markdown语法。作者认为Mataroa支持评论且免费，故排第一；Pagecord功能最丰富、支持嵌入图片点击放大和YouTube视频，但编辑器会即时转换Markdown语法，体验不佳；Bear最简洁、默认设计美观、支持LaTeX，但免费账户会被搜索引擎和发现源隐藏（可通过人工审核解除）。总体而言，三者没有明显短板，均可选用。此外，作者建议将图片托管在专门的平台如PixelUnion.eu（基于Immich，免费15GB），以便减轻博客服务器负担。文章还介绍了POSSE理念——在自有网站发布原创内容，再分享到社交媒体，以降低平台依赖风险，并附带了示例和评论集成方法。

## 6. 用 Rust 新 API 实现更快的浮点数学运算

- 原始链接: <https://pythonspeed.com/articles/faster-float-math-rust/>
- 英文标题: Faster floating point math with Rust’s new API

文章介绍了 Rust 1.98 中新增的“代数运算” API，用于在保留精度控制的前提下让编译器更积极地优化浮点运算。默认情况下，由于浮点数不满足结合律，编译器为保证结果完全一致，不会重排浮点操作，导致性能远低于整数运算。Rust 1.98 提供了 algebraic_add、algebraic_sub、algebraic_mul 等运算符，允许程序员在特定位置显式授权编译器利用实数的代数性质进行优化。作者通过两个例子验证了效果：一是用代数加法实现 pairwise 求和，性能超过 NumPy，且误差量级相近；二是计算平方差之和，使用代数运算符后速度提升近一倍。文章强调，应严格与宽松运算符并用：在需要精度的关键合并处使用普通加法，在批量累加等对顺序不敏感处使用代数加法，从而兼顾准确性与速度。该 API 适用于需要高性能数值计算的 Rust 代码。

## 7. OCaml 中的守卫方法

- 原始链接: <https://xvw.lol/en/articles/oop-refl.html>
- 英文标题: Guarded methods in OCaml

这篇笔记讨论 OCaml 中“守卫方法”（guarded methods）的概念及其实现。所谓守卫方法，是指允许把约束条件附加到接收者对象 self 上，但仅针对某些方法生效；也就是说，只有接收者满足这些守卫条件时，相应方法才可被调用。这种机制可以对方法调用施加更细粒度的限制。OCaml 的语法并不直接支持定义这类方法，因此作者提出了一种基于“类型等式见证”（type equality witness）的编码方案，利用类型系统在类型层面表达约束，从而模拟守卫方法的语义。文章说明了这一编码思路，使得 OCaml 开发者能够实现类似功能。由于原文篇幅较短，更像一篇技术说明或预告，具体编码细节和示例需要参阅正文内容。

## 8. NetBSD 11.0 正式发布

- 原始链接: <https://blog.netbsd.org/tnf/entry/netbsd_11_0_released>
- 英文标题: NetBSD 11.0 released

NetBSD 项目于 2026 年 8 月 1 日宣布正式发布 NetBSD 11.0 版本，这是该操作系统的一次重要更新。用户可根据架构查阅安装说明，并从 CDN 下载合适的安装镜像。对于 ARM 设备，可获取预配置 U-Boot 的 netbsd-11 启动镜像。此次发布的 ISO 镜像被拆分为适用于 CD-ROM 的小于 700MB 的镜像和完整版 DVD 镜像；若不受 CD 容量限制，建议选择名称含 "-dvd.iso" 的镜像。使用 U 盘等闪存介质时，必须使用 .img 文件，并先用 gunzip 或 7-Zip 解压。项目团队特别指出，随着 AI 工具普及，安全漏洞数量激增，因此无法做到无未解决问题就发布。他们选择透明公开当前仍存在的三个安全相关 pullup 请求：hdaudio(4) 驱动的 ioctl 命令缺少访问检查（可通过删除 /dev/hdaudio* 手动缓解）；ipfilter 存在可远程触发的空指针解引用（默认内核未包含 IPF）；pf 分片重组存在释放后使用漏洞（PF 已弃用且默认未包含）。这些修复将在 11.0 发布后不久合入稳定分支，并包含在预计两个月内推出的 11.1 版本中。

## 12. Rust 参数解析的新旧结合：getoptsargs 框架

- 原始链接: <https://jmmv.dev/2026/07/hello-getoptsargs.html>
- 英文标题: An old-new take on argument parsing in Rust

本文作者分享了在 Rust 生态中开发命令行工具时对参数解析的思考，并介绍了自己发布的库 getoptsargs。作者认为，命令行工具的行为应融入目标工具生态（如 Unix 风格），而非仅迎合语言惯例。他指出，主流库 clap 虽功能强大、外观漂亮，但输出风格与 Unix 工具不一致，且其“魔法”式的 derive 写法不够透明；同时 clap 并未提供从解析到退出码的完整控制流，容易导致解析时机不当等问题。因此，作者基于古老的 getopts 库扩展出 getoptsargs，将其设计为一个小型端到端框架。该库支持声明位置参数及其数量约束、自动校验、在帮助中分区显示，并提供版本、bug 报告、主页、手册页等元数据辅助。其 API 尽量模仿 getopts，保持原有命名，同时提供了 Builder、Matches 和 app 宏三部分来定义 main 流程。文中展示了示例程序及运行效果，并说明用户也可用命令式方式避免宏。作者坦言该库并非要取代 clap 或 argh，而是为了满足自身对 Unix 风格工具一致性的需求，并已将其开源在 GitHub 上。

## 13. CP/M-386：面向386保护模式的CP/M，源自CP/M-68K

- 原始链接: <https://github.com/johnsonjh/cpm386>
- 英文标题: CP/M-386: CP/M for 386 protected mode, derived from CP/M-68K

CP/M-386 是一个基于 CP/M-68K 衍生、专为 Intel 386 保护模式设计的 CP/M 操作系统实现。目前处于极早期开发阶段，实现了完整的 32 位保护模式，并支持 Ring-3 TPA（暂驻程序区）。系统可通过 3.5 英寸 1.44MB 软盘 MBR 或 GRUB Multiboot 引导，支持 VGA 文本（0xB8000）和 COM1 串口（9600/N/8/1）控制台，但尚无软盘、硬盘、CD、USB、网络、声音等驱动程序。硬件方面兼容 386 及以上、拥有至少 2MB 内存的 PC BIOS 或带有 CSM 的 UEFI 系统，支持 VGA、8042 PS/2、8250/16550 UART、CMOS RTC 和 8253/8254 PIT。BDOS 兼容性方面，与 CP/M-68K 1.3 和 CP/M 2.2 完全对齐，并实现了大部分 CP/M-Plus 和 DOS-Plus 功能，以及约半数 MP/M 扩展；还新增了针对直接视频访问、高精度计时、PRNG 等特性的专有 BDOS 扩展。构建需要 AWK、cpmtools 2.23+、Binutils、Coreutils、GCC 或 Clang、Make、NASM 和 QEMU（仅测试用），支持在 NetBSD、FreeBSD 及多种主流 Linux 发行版上编译，推荐使用 GCC。构建产物包括 Multiboot 内核镜像 cpm386.elf 和可引导软盘镜像 floppy.img。项目附带了丰富的实用程序，如文件管理、显示、测试和演示工具。贡献方面不接受大量 LLM 生成的代码，项目目前没有 AI 生成的代码，允许在遵循 LLVM AI 工具政策的前提下使用 AI。项目采用 MIT 许可证，并获得了 Digital Research CP/M 资产继承者对 CP/M 技术的明确使用授权。

## 17. Lean 内核健全性漏洞 #14576 的事后分析

- 原始链接: <https://leodemoura.github.io/blog/2026-8-1-postmortem-for-kernel-soundness-bug-14576/>
- 英文标题: Postmortem for Lean Kernel Soundness Bug #14576

2026年7月25日，Ramana Kumar 发布了一个借助 AI 辅助、不含 sorry 的 Collatz 猜想“反证”，但该证明无效，因为它利用了 Lean 内核处理嵌套归纳类型时的漏洞。7月28日，Kiran Gopinathan 将其简化为一个 False 的小证明并提交了 issue #14576；一小时后官方推送修复（#14577），经 Joachim Breitner 审查后合并，并发布了新的补丁版本。漏洞原因是：当内核消除带参数 Ds 的归纳类型 T 下的嵌套出现时，若这些参数是幻影参数（未在构造字段中出现），它们会从生成的辅助类型中消失，从而绕过类型检查；恶意的类型错误参数可被用来让内核接受 False 的证明。该漏洞只能通过元编程（直接向内核发送归纳声明）触发，前端会拦截此类错误项。这是实现 bug，而非元理论缺陷。独立检查器 nanoda 此前也因另一无关 bug 而漏检，但该 bug 在 Lean 漏洞报告前一周已被修复。lean4lean 因移植了参考实现而受影响。官方与 nanoda 均确认该问题不影响独立检查的有效性，但用户需同时更新两者。Mario Carneiro 正在进行的 lean4lean 验证工作尚未覆盖归纳类型，该漏洞会在完成该部分验证时被发现。讨论中有人建议限制元编程，但作者认为这不可取：内核必须独立拒绝类型错误的声明。事后，Lean 基金会添加了回归测试，并借助 OpenAI 的安全 AI 发现并修复了内核中的多个相关编程错误，同时加强了内核不变量；comparator.live 现已默认运行 nanoda 并每日跟踪更新。

## 18. MkLinux 与改装版 Apple Workgroup Server 9150

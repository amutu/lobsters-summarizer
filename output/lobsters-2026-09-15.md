## 3. 反对将 JPEG XL 引入 Web 的理由

- 原始链接: <https://giannirosato.com/blog/post/case-against-jxl>
- 英文标题: The case against JPEG XL

作者是一位图像压缩工程师，曾积极支持 JPEG XL，但基于 2026 年的技术现状，认为该格式不适合 Web。文章从多个维度展开论证：有损压缩方面，现代 AVIF 编码器在感知优化上已全面超越 libjxl，JPEG XL 缺少方向预测模式和去块滤波，在边缘保持和非摄影图像上表现不佳；无损方面，仅比 WebP 小约 12%，而 Web 上无损需求极少；渐进解码方面，AVIF 已实现且可用图像出现时间更早；解码时间方面，JPEG XL 明显慢于 WebP，且存在「解码炸弹」风险——一个 1.9 KB 的文件可触发 17 秒素数计算，极易拖垮低端设备。作者认为 Web 编解码器应窄范围、高效、安全，AVIF 已覆盖整个保真度区间，JPEG XL「万物皆可」的宽泛设计反而不如 WebP 契合浏览器需求。但作者承认 JPEG XL 在 Web 之外的专业场景（如 Adobe 工具链、相机厂商）仍有真实价值，并指出推动其进入 Web 的动机更多出于对开发者选择权的政治诉求，而非技术上的不可替代性。

## 4. UNIX域套接字中的浪漫：一个潜伏40年的内核Bug

- 原始链接: <https://yuvalino.com/how-can-you-not-be-romantic-about-unix-domain-sockets>
- 英文标题: How can you not be romantic about UNIX domain sockets?

作者在DEFCON 34演讲时，其iOS虚拟机项目（内含SSH服务器，通过UNIX域套接字实现用户态TTY）在设备首次启动后崩溃。排查发现，对同一UNIX域套接字端点两次调用fstat()返回了不同的inode号。根因在内核函数uipc_sense()中：全局计数器unp_ino初始为0，代码使用后置自增unp_ino++，首次调用返回0（被误判为未初始化），第二次才分配新值，导致inode不一致。修复仅需改为前置自增++unp_ino。追溯历史，该缺陷可至1985年12月的4.3BSD提交，此前每次fstat()均返回递增的不同inode；1985年5月的提交注释甚至写着「fake up inode numbers and dev for the naive」。该Bug随NeXTSTEP（1989）进入Apple，经XNU 123.5（2001年Mac OS X 10.0）延续至今，影响所有现代macOS与iOS。作者幽默自嘲被41年前的提交信息称为「naive」，并总结道：上台前务必充分验证演示。

## 5. 经验之谈：程序员似乎不喜欢 reduce

- 原始链接: <https://evanhahn.com/posts/2026-09-13-programmers-dislike-reduce/>
- 英文标题: Anecdotally, programmers dislike "reduce"

作者基于个人开发经验指出，程序员普遍接受 map 和 filter，却对 reduce 表现出明显抵触。在代码审查中，使用 map、filter 几乎不会引发异议，但一旦提交包含 reduce 的补丁，常收到「这段代码难以阅读」的评论，且 reduce 在实际代码中的出现频率远低于 map、filter、some 等函数。作者提出了几种可能的解释：一是 reduce 本身可读性较差；二是开发者对其不够熟悉；三是相比其他写法，reduce 的性能可能更差；四是在 JavaScript、Python、Swift 等语言中 reduce 的语法不够优雅——作者回忆在 Clojure 开发期间并未收到此类反馈。此外，作者也承认自己可能误判了趋势，这或许只是主观感受。面对审查意见，作者通常直接将 reduce 替换为其他写法，并不执着。作者还提到，近期这一现象似乎有所减弱，可能与代码审查整体趋于宽松有关。文章最后向读者发出提问，邀请大家分享是否也有类似观察，以及是否真正喜欢使用 reduce。整体而言，这是一篇轻松的个人随笔，记录了一个值得关注的开发者协作中的小社会现象。

- 原始链接: <https://aloysberger.com/posts/writing-a-guix-service-from-scratch-as-a-beginner.html>
- 英文标题: Writing a Guix service from scratch, as a beginner

作者正在将个人 VPS 从 NixOS 迁移到 Guix，邮件服务器（exim + dovecot）和 WireGuard 已部署完成，但 Caddy 反向代理在 Guix 官方频道中尚无现成服务，遂以此为契机撰写本教程，面向 Guix 新手演示如何从零构建自定义服务。文章将服务拆为四步：定义空服务类型、创建守护进程用户与组、部署配置文件、通过 Shepherd 启动后台守护进程。核心讲解围绕 <service-type> 记录展开，逐一解释 name、extensions、compose、extend、default-value、description 等字段含义。作者特别澄清了 extensions 的直觉误区：它并非为自身服务「添加能力」，而是修改目标服务（如 account-service-type）使其代为执行操作，体现了声明式与依赖反转思想。compose 决定多个扩展服务的值如何合并（如拼接用户列表），extend 决定合并结果如何与目标服务自身值交互。文章以 account-service-type 为例，展示了如何通过 <user-account> 和 <user-group> 记录创建系统用户，并说明整个服务体系最终汇聚到 system-service-type 根节点。作者强调本文是边学边写的实践记录，鼓励读者配合官方文档阅读，后续计划重构并尝试向 Guix 仓库提交。

## 11. 4x4数独仅有12种本质解——以及寻找最小子集的巧妙技巧

- 原始链接: <https://baldino.dev/blog/there-are-only-twelve-4x4-sudokus/>
- 英文标题: There are only twelve 4x4 sudokus - and a cool trick for finding minimal subsets

本文探讨了4x4数独的解与谜题计数问题。作者指出，4x4数独（4×4网格，每行、列、2×2宫各含1至4各一次）共有288个合法解，但将数字视为无意义符号、消除置换等价后，本质不同的结构仅有12种。作者用一段朴素的Python深度优先搜索代码，在半秒内枚举出全部288个解；再通过固定第一行为「1 2 3 4」，将本质不同解与以该序列开头的解建立一一对应，验证了12这一数字。进一步，作者统计了具有唯一解且不可再删数字的「最小谜题」数量：共85632个，考虑置换后为3568个。文章的核心亮点是一个寻找最小子集的巧妙技巧——用bitmask编码格子子集，利用从0到2^S-1的递增迭代顺序，只需与已发现的谜题做位与比较即可判断当前子集是否最小，无需遍历全部子集；若求最大子集则反向迭代即可。然而该算法复杂度约为O(2^(N²)·N!)，对n=2（4×4）约需200秒尚可接受，对n=3（9×9）则需远超宇宙年龄的时间，9×9数独的谜题总数至今仍是未知数。文章最后以轻松笔调指出，3568个本质谜题印在A4纸上仅约102页。

## 15. 在 macOS 与 Windows WSL2 上共用单个 .zshrc 的实践

- 原始链接: <https://talkoren.com/blog/single-zshrc-macos-windows-wsl2/>
- 英文标题: How I use a single .zshrc file on macOS and Windows (WSL2)

作者 Tal Koren 拥有三台机器（一台 MacBook Pro 和两台 Windows 游戏 PC），长期在 zsh 环境下工作，并使用 chezmoi 管理 dotfiles。他面临的核心问题是：macOS 与 WSL2 虽同属类 Unix 环境，但在 ssh 客户端、文件打开命令等方面存在差异，维护两份 .zshrc 极易导致配置漂移。他的方案是维护一份共享的 .zshrc，仅在操作系统相关处加入条件分支。具体做法：首先通过「grep -qi microsoft /proc/version」检测是否运行在 WSL 中，设置 IS_WSL 变量；在 SSH 方面，因 1Password ssh agent 运行在 Windows 侧而非 WSL 内部，WSL 中需将 ssh、ssh-add、scp 别名为对应的 .exe 版本，并设置 GIT_SSH_COMMAND 以覆盖 Git 自身调用的 ssh；在文件管理器方面，macOS 原生 open 命令在 WSL 中不存在，故在 WSL 条件下定义 open 函数，调用 explorer.exe 并通过 wslpath -w 将 Linux 路径转为 Windows 路径。最终效果是：绝大部分配置跨平台共享，仅少量 Windows 专属逻辑集中在一处条件块中，既保持可读性又避免维护多份文件带来的同步负担。

## 16. 在纯数据中夹带函数：可扩展的去函数化技巧

- 原始链接: <https://blog.veritates.love/functions-as-data>
- 英文标题: Sticking Functions Where They Donʼt Belong

本文探讨在 Haskell 中如何将函数嵌入纯数据（即实现 Show、NFData、Eq、Ord 的类型）而不破坏其「纯」性质。作者正在实验一个编译到 WASM 的函数式语言，希望 AST 保持纯数据可比较、可序列化，同时允许用户以可扩展方式注入自定义语义。核心方案是利用存在类型与类型类字典：定义 Existentiable 约束（Typeable、NFData、Ord、Show），再定义 Semantics 类型类承载类型信息、代码生成、求值模拟等钩子；用存在类型 ForeignSemantics 将任意 Semantics 实例及其字典打包，并为该存在类型实现 Show、NFData、Eq、Ord（Eq/Ord 借助 Typeable.cast 比较运行时类型）。随后在 AST 中加入 EForeign 构造器，配合模式同义词即可在匹配时还原具体类型。这种方式属于可扩展的去函数化：库与用户可各自添加实例而无需协调，无需维护注册表，也不污染代码生成器。代价是需手动决定每个实例的「本质数据」，且无法自动序列化/反序列化这些存在字典（GHC.Compact 不支持类型类字典的跨二进制还原）。总体而言，该技巧以较小代价在纯数据中实现了开放世界的行为扩展，非常适合编译器插件等场景。

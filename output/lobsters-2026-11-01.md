## 1. Kluever 操作：用两次提交修复 Bug 的方法

- 原始链接: <https://jordi.inversethought.com/blog/the-kluever-maneuver/>
- 英文标题: The Kluever Maneuver

本文由 Jordi 撰写，介绍了一种名为「Kluever Maneuver」的 Bug 修复实践。核心做法是将一次 Bug 修复拆分为两个 commit：第一个 commit 仅添加一个能通过的测试，该测试断言的是当前错误的行为（即记录 Bug 现象）；第二个 commit 同时修复代码并修正测试断言为正确值。作者以加法函数多加 1 和年龄计算 off-by-one 两个例子说明，传统做法在同一个 commit 中同时修 Bug 和加测试，若测试在修复前就已通过，则无法证明修复真正生效；而 Kluever 操作能确保测试在修复前通过、修复后仍通过但断言值改变，从而提供可验证的证据。此外，该方法保证每个 commit 时 CI 均能通过，不会引入红色构建。文章还建议与 Bug 追踪器配合：第一个 commit 引用 Bug 编号并标注 FIXME，第二个 commit 标注 fixes 并移除 FIXME。该名称源自作者同事 Kurt Kluever，他习惯称这种测试为「terrible tests」，即故意写一个断言已知错误结果的测试。

## 2. 避免公共函数调用其他公共函数

- 原始链接: <https://matklad.github.io/2026/10/29/pub-calls-pub.html>
- 英文标题: Avoid Public Functions Calling Other Public Functions

本文提出一条软件设计经验法则：公共函数不应直接调用其他公共函数。当实现模块时，若公共函数 foo 的部分逻辑已由公共函数 bar 处理，DRY 原则会诱导开发者在 foo 中调用 bar()，但这会埋下隐患。正确做法是抽取一个私有辅助函数 helper，让 foo 和 bar 各自调用该私有函数。其核心理由是：公共 API 的目标是在调用点为外部用户提供最简洁的接口；若公共函数之间互相复用，就会在「对外部用户友好」与「在抽象内部方便调用」之间产生张力，导致函数不断累积用户本不应设置的可选参数，且这种接口退化往往在代码共享之后才逐渐显现。将共享实现设为私有后，辅助函数的签名调整成为廉价的局部变更，张力得以化解。文章也指出一个例外：「快捷方式」API（即一个公共函数被定义为对其他公共函数的常用调用链），此时规则相反，不允许出现私有调用，以确保它确实是真正的快捷方式而非中间层错误。文末作者还附带评论了 Stack Overflow 上相关讨论，认为不应 mock 内部方法而应 mock IO，不应孤立测试方法而应测试软件功能；同时批评了「因为某条规则被写进行业或组织标准就应遵循」的态度，强调应理解每条规则背后的动机，而非盲目服从。

## 3. 一个「黑屏」支持案例：客户把所有颜色都设成了黑色

- 原始链接: <https://devblogs.microsoft.com/oldnewthing/20261029-00/?p=112808/>
- 英文标题: The support case of a customer who said that all they could see was a black screen

本文由Windows核心团队成员Raymond Chen撰写，围绕「黑屏」问题展开。文章首先介绍长按电源键12秒可在硬件层面强制关机，按住8秒后Windows内核会生成紧急内核转储（内部称为「长按电源键」即LPBH故障），下次开机时上传至Windows错误报告服务；若4秒内信息不足，Insider版会提示用户松开电源键以完成采集。全黑屏幕的LPBH故障被进一步归入「黑屏LPBH」子类，由专门虚拟团队分析，作者本人即该团队成员。黑屏成因多样，包括视频驱动损坏、桌面合成器输出黑像素、无人向屏幕绘制内容、绘制进程挂起等。文章随后回溯到Windows 3.1时代的一个经典支持案例：一位客户开机后只看到空白屏幕，经排查发现该客户酷爱黑色，将颜色控制面板中壁纸、标题栏、按钮、窗口背景及文字等所有可选颜色全部设为黑色，导致界面完全不可见且难以自行恢复。作者推测支持工程师最终进入MS-DOS，用EDIT.COM编辑win.ini文件，删除[colors]段以恢复系统默认配色。文章以轻松幽默的笔调，将现代内核转储机制与早期Windows的趣味支持故事串联起来。

## 4. 电网60秒周期性波动之谜：大规模电池储能系统的同步电量检查所致

- 原始链接: <https://www.fz-juelich.de/en/news/archive/press-release/2026/mystery-of-60-second-fluctuations-in-power-grids-solved>
- 英文标题: Mystery of 60-Second Fluctuations in Power Grids Solved

德国于利希研究中心Dirk Witthaut团队联合科隆大学和卡尔斯鲁厄理工学院研究人员，在《自然·能源》上发表论文，揭示了欧洲电网中每60秒出现一次短暂频率下降的原因：大量大规模电池储能系统每分钟整点同步执行一次电量检查，导致用电需求出现可测量的周期性尖峰。德国最大输电运营商Tennet已观测到该现象多年，但成因一直不明。团队在于利希校园的Living Lab Energy Campus上设置80个测量点，确认波动仅出现在配备大型储能系统的位置。由于行业缺乏统一标准，多数电池制造商默认以60秒为检查间隔，且统一在每分钟起始时刻触发，形成全球性同步效应。Witthaut指出，空调、热泵、洗衣机等数字控制设备也可能产生类似模式。该周期性波动已对水电站涡轮机造成额外磨损——需求尖峰使涡轮短暂减速再加速。爱尔兰因数据中心储能占比达全国用电约五分之一，相关信号振幅在2016至2021年间增长四倍。解决方案并不复杂：将各系统的检查时间随机化，避免统一时刻触发即可显著减轻电网负担。

## 5. 检查空白字符为何如此复杂

- 原始链接: <https://serce.me/posts/2026-10-30-how-hard-is-it-to-check-for-whitespace>
- 英文标题: How hard is it to check for whitespace?

作者从Guava库的isWhitespace方法入手，探讨了「判断一个字符是否为空白」背后的复杂性。首先，Unicode的White_Space属性定义了25个空白字符，各有不同用途，且部分字符名称或外观具有误导性（如ZERO WIDTH SPACE并非空白，OGHAM SPACE MARK可渲染为可见横线）。其次，各运行时对空白的定义并不统一：Java排除U+00A0，Python额外识别U+001C等共29个，JavaScript的\s正则包含U+FEFF却排除U+0085。此外，Unicode标准本身持续演变，如6.3版将蒙古元音分隔符移出空白集合，给向后兼容带来挑战。在性能优化方面，Guava采用完美哈希函数：以32字符的TABLE为哈希表，通过乘法1682554634乘以字符码再右移27位得到索引，最后用等值比较验证，从而以O(1)完成判断。该乘数可通过暴力搜索获得，Guava的git历史显示其实现经历了从简单匹配到取模79再到完美哈希的演进。文章最后感慨，在AI优先的时代，深入函数内部探索的写作正变得越来越稀少。

- 英文标题: Tangled, hire a front-end accessibility expert

作者以一名可访问性从业者的身份，对去中心化代码托管平台 Tangled 的新版 UI 提出批评。Tangled 被视为继 Codeberg 之后又一个有潜力的 GitHub 替代品，近期以 Svelte 重写了前端并推出联邦代码仓库概念，但新界面将正文字号设为 12px、行高 16px，且使用像素单位而非相对单位，导致用户无法通过浏览器默认设置缩放文本。作者实测：强制 16px 时字符开始被裁切（如「g」的下伸部分），强制 24px（即 200% 缩放）时文本严重截断，违反 WCAG 2.2 中 1.4.4「文本可缩放至 200% 而不丢失内容或功能」的要求。作者给出两条免费建议：字体大小使用相对单位，行高使用无单位数值。他强调可访问性必须从设计初期就纳入流程，而非上线后修补；同时指出 Tangled 已接受风险投资，其「开源」性质已不同于纯社区项目，不宜期望专家免费贡献。作者并非求职，而是希望 Tangled 尽早聘请专业可访问性审计人员，让仍留在 GitHub 的用户少一个留下的借口。文章末尾作者也承认自己网站存在可访问性问题，态度诚恳。

## 8. 用 groff 排版中篇小说

- 原始链接: <https://movq.de/blog/postings/2026-10-31/0/POSTING-en.html>
- 英文标题: Novellas with groff

作者分享了自己用 groff 排版两部中篇小说（约15k词和40k词）的完整技术流程。第一部耗时七个月，第二部仅十天，源于去年七月起大量阅读小说后产生的创作冲动。排版选用 groff 而非 TeX 或 HTML，因其轻量快速（50页文档渲染约700毫秒），且能输出高质量两端对齐文本。作者自制了极简宏包，仅含章节标题（SH）、悬挂缩进段落（PP）和长段落间距（LP）三个宏，配合页脚页码 trap 和页眉 trap 完成完整书籍排版。文章详细讲解了 groff trap 机制：通过切换环境（ev/evc）隔离当前行缓冲，用中性撇号（'）抑制隐含换行，实现页脚页码的精确定位。写作层面，作者用简化 Markdown（标题、空行、斜体）记录文本，再通过 Perl 脚本转换为 groff 宏调用，兼顾可读性与排版质量。编辑环境为 Vim 搭配 Goyo 插件，隐藏所有界面元素，营造类打字机的无干扰写作体验。文本采用每段一行的重排方式，有利于版本控制 diff 和 groff 句末识别。作者坦言 groff 仍有诸多 TODO，但整体流程已足够支撑小说级排版。

## 9. 通过排列迭代空间加速 GPU 数组复制：优化恒等映射

- 原始链接: <https://futhark-lang.org/blog/2026-10-31-faster-copying.html>
- 英文标题: Speeding up GPU copies by permuting iteration spaces, or, optimising the identity function

本文介绍 Futhark 纯函数式数组编程语言在 GPU 后端中加速数组复制的新优化技术。Futhark 使用线性内存访问描述符（LMAD）将多维索引映射为一维内存偏移，从而将逻辑形状与物理布局解耦。复制两个 LMAD 描述的数组时，编译器可识别三种情形：连续布局直接调用 memcpy；矩阵转置使用专用高效实现；其余情况回退到逐元素并行循环。本文重点讨论第三种情形的新优化：在 GPU 上，相邻线程被分配到最外层维度的相邻索引，但该维度未必对应最小 stride，导致非合并（uncoalesced）内存访问。优化方法是在复制前按源 LMAD 的 stride 升序排列维度（次级按目标 LMAD），使相邻线程访问相邻内存位置，实现合并访问。排序使用简单选择排序，因数组秩通常很小，开销可忽略。实测中，对 2D 切片复制（如 xss[:,1:] 归一化）等不匹配已知模式的场景，优化带来约 36 倍加速（从 17561μs 降至 971μs）；但对整体基准套件影响有限，多数程序提升不超过 10%。作者指出，虽然看似在「优化恒等函数」，但数据搬移本身对性能至关重要，未来还将探索 CPU 后端的类似优化。

## 10. 快速编程的秘诀：停止「思考」

- 原始链接: <https://www.codesimplicity.com/post/the-secret-of-fast-programming-stop-thinking/>
- 英文标题: The Secret of Fast Programming: Stop Thinking »

Max Kanat-Alexander 在本文中提出一个反直觉观点：程序员写代码时停下来「思考」并非高效表现，而是存在问题的信号。打字速度很少是瓶颈，真正拖慢进度的是停顿，而停顿往往意味着理解不足、概念混乱或外部干扰。文章将「停下来思考」归为八类原因并给出对策：理解不足时应查阅文档或代码而非空想；概念过多时应画图或写下来；不知从何下手时应从完全理解的部分开始；跳步开发应按依赖关系逐步实现；身体疲劳、环境干扰、自我怀疑等也需针对性解决。作者强调，真正聪明的人不是靠「想」，而是通过学习、观察、行动来解决问题。此外他提醒，若整天被邮件和会议占据，那是组织层面的问题，但类似思路也可推广到团队。读者讨论中，有人补充写测试作为「不停下来」的方式，作者回应称所谓天赋可被拆解为可习得的技能，关键在于意识到自己「不知道什么」并主动去学。

## 12. 有效类型（上）：C语言类型别名规则与编译器实现问题

- 原始链接: <https://uecker.codeberg.page/2026-10-31.html>
- 英文标题: Effective Type: Part 1

本文由Martin Uecker撰写，介绍C语言中「有效类型」(effective type)规则及其对编译器优化的影响。有效类型规则是类型别名分析(TBAA)的基础，最早见于ANSI X3.159-1989：用不兼容类型访问对象属于未定义行为，编译器可据此进行激进优化。文章通过示例说明，当两个指针可能指向同一对象时，编译器可假设无别名存在，从而跳过重新加载。C99标准引入了「类型变更存储」机制：对无声明类型的对象（如malloc分配的内存）进行写入时，写入所用的lvalue类型即成为该对象的有效类型，后续读取须匹配此类型，这为内存复用提供了语义支持。文章重点指出编译器实现问题：GCC能将循环内不变存储正确移至循环外，而Clang将存储错误地提升到循环上方，导致类型变更存储覆盖先前写入值，属于误编译。作者强调Clang至今未实现ISO C99有效类型规则，仅在使用-fno-strict-aliasing关闭TBAA时才可能符合标准；GCC虽于2020年修复了核心问题，但仍有已知缺陷。结论是：有效类型规则本身并不复杂，但主流优化编译器的实现仍存在显著问题，开发者在特定场景下可能需要关闭TBAA以保证正确性。

## 1. 消灭Cookie横幅：呼吁支持浏览器自动隐私偏好信号

- 原始链接: <https://killthecookiebanner.eu/>
- 英文标题: Kill the Cookie Banner

本文是一篇行动倡议，旨在呼吁公众支持消灭互联网上烦人且误导性的Cookie横幅。文章指出，欧盟隐私法默认禁止在线跟踪，但跟踪行业为了获得用户同意，发明了故意误导用户的Cookie横幅，导致高达90%的人点击“同意”，而真正愿意被跟踪的仅约3%，这一系统从设计上就是失败的。为解决此问题，欧盟委员会于2025年秋季在“数字综合法案”改革中提出了自动化信号方案：用户只需在浏览器中设置一次隐私偏好（接受、拒绝或限制跟踪），即可自动与网站和App通信，无需再反复面对Cookie横幅。这种机制在技术上简单可行，类似浏览器自动发送语言偏好，且在美国部分州已获法律支持。然而，以谷歌为首的跟踪行业和部分成员国正在游说阻拦该提案，欧洲议会也可能拒绝。作者呼吁读者联系欧洲议会或本国代表表达不满，以推动该提案通过。文章同时特别注明，虽然该隐私信号提案值得支持，但“数字综合法案”的其他大部分内容会削弱用户权利，并不值得支持。

## 2. Soppo：补全 Go 缺失特性的语言

- 原始链接: <https://soppolang.dev/>
- 英文标题: Soppo - Go, with the features it's missing

Soppo 是一种基于 Go 语法的新型编程语言，目标是补全 Go 所缺失的类型安全与易用性，同时保持与 Go 生态的完全兼容。它采用熟悉的 Go 语法，可直接使用任何 Go 库，并允许在既有项目中逐步引入。主要特性包括：枚举与模式匹配，定义带结构体变体的标签联合，编译器强制穷尽所有分支，缺失情况会在运行前报错；错误处理改用 ? 操作符，避免了重复的 if err != nil 判断，同时仍可添加自定义处理；nil 安全机制在编译期追踪可空性，通过空值检查后自动收窄类型，从而减少指针解引用的运行时崩溃；错误消息经过优化，能精确定位问题代码，并给出修复建议。安装方面，推荐使用 SOPMOD 版本管理器，它能同时管理 Soppo 和其内部依赖的 Go 版本；也可以使用 Cargo 直接安装，但需自行安装 Rust 和 Go。整体上，Soppo 在保持 Go 简单性的前提下，引入了现代语言特性以提升开发体验。

## 3. Pandoc二十年

- 原始链接: <https://pandoc.org/twenty-years-of-pandoc.html>
- 英文标题: Twenty Years of Pandoc

文章作者John MacFarlane回顾了Pandoc项目自2006年首次发布以来的二十年发展历程。Pandoc最初是作者为学习Haskell而编写的Markdown解析器，采用解析器组合子构建真正的语法树，与当时基于正则表达式的实现不同，这种架构使得多种输入输出格式的组合成为可能。项目从个人工具逐渐壮大：2008年发布1.0版本，支持OpenDocument、语法高亮等；2010年引入模板系统；2012年支持Word docx；2013年增加YAML元数据、Lua自定义编写器和JSON过滤器。作者还深度参与了CommonMark规范的制定。2017年的2.0版本引入PandocMonad抽象和Lua过滤器，实现重大架构改进；2023年的3.0版本将项目拆分为多个包，并新增Typst和djot等现代格式支持；近期实现了WASM编译，使其能在浏览器中运行。如今Pandoc支持超过五十种文档格式，被Quarto、Jupyter Notebook等学术写作工具集成，成为最流行的Haskell程序，并持续活跃开发中。

## 6. 为PDF编写测试

- 原始链接: <https://blog.lvmbdv.dev/posts/tests-for-a-pdf/>
- 英文标题: Tests for a PDF

作者为自己的简历PDF搭建了一个测试套件，因为招聘系统（ATS）读取的是文本而非视觉呈现。该套件用Typst生成PDF，make编译到dist/，make test运行Python脚本检查四点：文件头是%PDF-、pdfinfo有作者和标题、至少一页、pdftotext提取到至少200字符。其中第4点最关键，用于防止PDF只是图片而没有文本层。作者还验证了简历建议网站常说的“禁用连字”设置：实测发现启用和禁用连字时pdftotext输出完全一致，因为PDF自带ToUnicode映射，但他仍保留该设置以防某些解析器忽略映射，代价是排版中的破折号需用变通写法。文中还记录了一个静默失败的bug：作者姓名的检查键指向旧文件名，导致该检查从未运行，通过毒药测试（篡改期望值后套件仍通过）发现，并改用常量比较修复。另一个问题是CI中字体缺失时Typst静默回退且退出码为0，导致错误字体发布三周，修复后增加字体检查。最终作者强调，测试套件最有价值的是文本层检查，而防御性设置常基于无法观测的假设，需要警惕测试自身的失效。

## 7. GNOME Boxes 的未来：从零重建迈向 Flatpak 与 GTK4

- 原始链接: <https://blogs.gnome.org/feborges/future-of-boxes/>
- 英文标题: The Future of GNOME Boxes

作者分享了过去两年从零重建 GNOME Boxes 的工作成果，现以 Beta 版本开放测试。重建由三个主要因素驱动：一是转向仅通过 Flatpak 分发，这样可以将完整的虚拟化栈（libvirt/qemu）打包在一起，便于针对特定用例精细调优；二是迁移到 GTK4 和 Libadwaita，并将原先基于 GTK3 的 SPICE 显示控件替换为 Libmks；三是现代化代码库并采用现代 GNOME 应用设计模式，以吸引新贡献者。新版已覆盖经典版本的大部分功能，包括从 ISO 和 qcow2 磁盘镜像创建虚拟机、配置资源、共享剪贴板、向客户机发送文件等。亮点是无需手动规避即可安装 Windows 11，Boxes 会自动配置 Secure Boot 和虚拟 TPM 设备，以通过硬件兼容检查。针对 Flatpak 沙箱限制，新版通过引入 VSOCK 设备，允许主机在客户机运行 systemd v256 或更新版本时直接通过 SSH 访问，并增加了端口转发支持。作者强调这是 Beta 版，仅供测试，建议提前备份虚拟机数据；安装方式为通过 GNOME Nightly 仓库执行 flatpak install org.gnome.Boxes.Devel。更多细节可在 nightly.gnomeboxes.org 查看。作者在业余时间维护此项目，希望社区耐心等待问题响应，并欢迎测试反馈。

## 8. Rust项目目标：不可移动类型与有保证的析构函数

- 原始链接: <https://github.com/rust-lang/rust-project-goals/blob/main/src/2026/move-trait.md>
- 英文标题: Rust Project Goals: Immobile types and guaranteed destructors

该文章是Rust项目2026年的目标提案，旨在引入“不可移动类型”（immobile types）和“有保证的析构函数”（guaranteed destructors）。当前Rust的所有类型默认都是可移动的，这导致某些需要固定地址的资源（如自引用结构、硬件寄存器映射）难以安全表达。文章提出一种新的类型属性，使类型在创建后不能移动，同时确保其析构函数在特定生命周期内必定被执行。该设计主要解决两类问题：一是自引用类型需要在移动后更新内部指针，但现有方案（如Pin）依赖用户遵守约定且存在局限；二是当类型包含不可移动资源时，析构顺序和资源释放需要编译器保证，而非依赖运行时检查。提案拟通过扩展类型系统，允许标记类型为immobile，并自动生成安全的析构逻辑，避免泄露内存或资源。此外，文章讨论了与Pin、Drop检查以及async/await的交互，并给出了迁移路径和兼容性考虑。最终目标是让编译器强制保证资源安全，同时不破坏现有代码的语义。

## 9. SQLite 严重 CVE 还是 LLM 垃圾信息？

- 原始链接: <https://research.jfrog.com/post/sqlite-critical-cves-or-llm-slops/>
- 英文标题: SQLite Critical CVEs or LLM Slop?

JFrog 安全研究人员发现，一个新建的 GitHub 仓库批量发布了 SQLite 漏洞公告，NVD 和 CISA 曾将其标记为严重，但经核实这些漏洞完全不成立。研究人员检查了引用的源代码、PoC 和官方公告，发现多处硬伤：引用函数在目标版本中不存在、行号超出文件长度、补丁是凭空捏造的，PoC 也无法触发任何崩溃，且 SQLite 官方漏洞页均未收录。通过 Gptzero 检测，这些公告疑似由 AI 生成，属于“LLM 垃圾”CVE。文章详细分析了 6 个典型 CVE，指出其描述与源码完全不符，例如 CVE-2026-51302 引用的函数实际于 2025 年才加入，而目标版本 3.41 根本没有该逻辑。作者认为，MITRE 提交流程缺乏身份验证，加上 NVD 自 2024 年 2 月起暂停深度分析，导致虚假公告轻易进入 GHSA、企业扫描器等下游系统。JFrog 审计了同一账号发布的 55 个公告，54 个完全捏造，仅 1 个包含真实 bug 但元数据未经验证。文章最后给出识别假 CVE 的红旗：缺少厂商确认、无提交哈希、元数据矛盾、引用不存在的代码，并建议安全团队不要盲目信任新 CVE，应核实影响并复现 PoC。这类虚假漏洞不仅浪费时间，还可能误导 AI 自动修复工具，使之基于不存在的代码生成补丁，带来更大风险。

## 11. BorrowSanitizer：用于检测Rust别名错误的LLVM动态分析工具

- 原始链接: <https://borrowsanitizer.com/>
- 英文标题: BorrowSanitizer

BorrowSanitizer 是一个动态分析工具，专门用于检测多语言应用程序中与 Rust 相关的别名错误。文章指出，Rust 编译器通过限制别名和可变性提供了强大的静态安全保证，但开发者可以借助部分 unsafe 特性绕过这些限制，这些特性对于 Rust 与其他语言互操作是必需的。然而，如果 unsafe 代码使用不当，就可能破坏 Rust 别名模型的规则，而编译器依赖该模型进行程序优化，错误的优化可能引入安全漏洞。目前，Rust 开发者可以使用解释器 Miri 来发现别名错误，Miri 是唯一能检测 Rust 最新 Tree Borrows 别名模型违规的工具，但它无法检测外部代码中的此类错误，且运行速度明显慢于原生执行，难以实际应用于模糊测试或属性测试。BorrowSanitizer 旨在解决这些问题，它是一个基于 LLVM 的消毒器，目标是足够快以支持模糊测试，并支持 Rust、C 和 C++ 之间的互操作，定位为生产级工具。项目代码开源，托管在 GitHub 上，并设有 Zulip 社区供贡献者交流。文章还提供了构建和测试该工具的指引，但正文主要聚焦于项目背景与目标，未详细说明具体实现原理、性能数据或使用案例。

## 13. 你的 JSON 在欺骗你

- 原始链接: <https://blog.gaborkoos.com/posts/2026-08-03-Your-JSON-Is-Lying-to-You/>
- 英文标题: Your JSON Is Lying to You

这篇技术文章揭示了 JavaScript 中 JSON 序列化（JSON.stringify/JSON.parse）并非无损，可能在你不注意时改变或丢失数据。作者通过示例展示了多种问题：大整数 9007199254740993 会因 IEEE 754 数值精度限制变成 9007199254740992；undefined 属性在序列化后被删除，数组中的 undefined 变成 null，导致缺失与未定义难以区分；Date 被转成字符串并丢失原始时区，Map、Set、RegExp、Error 等内置对象变成空对象，NaN/Infinity 变成 null，类型化数组和类实例丢失类型信息；对象属性顺序虽在 JS 中稳定，但 JSON 规范视其为无序，跨语言时无法依赖。文章还指出，序列化会调用 toJSON() 方法并触发 getter，因此可能执行任意代码。最后建议开发者显式定义数据契约：大整数用十进制字符串、有序数据用数组、特殊类型用明确编码，以避免 JSON 成为不可靠的隐式接口。

## 14. 开发者工具必须开源

- 原始链接: <https://blog.exe.dev/devtools-must-be-open-source>
- 英文标题: Devtools must be open source

文章认为AI时代开发者工具必须开源，因为只有拥有源码才能实现真正的个性化定制。过去软件定制成本高，工程师很少为自己写工具；现在AI agent可以下载源码、修改源码、建立夜间任务同步上游更新，使个性化成本大幅下降，甚至可以不用编程，用自然语言指令改变软件行为。作者以Shelley和meat.dev为例：用一条提示词就把diff精简工具集成进Shelley，后台预提交处理，改改UI即可，而传统插件API很难做到。由此，复杂的配置和插件系统不再是必需品，直接改源码更好；小团队也可以不用通用可配置产品，而是从开源组件拼出所需功能。文章还比较了开源agent与Claude Code：开源Codex可同样定制，但Claude Code闭源，只能依赖其提供的hooks，如果不适用就应转向可定制的开源agent。核心结论是：开源是可持续个人化的前提。

## 17. 《光环 2》与后续作品的内容管理

- 原始链接: <https://nikon.bungie.org/misc/gdc2005_mnoguchi/>
- 英文标题: Content Management for Halo 2 and Beyond(2005)

本文是 Bungie 工作室 Matthew Noguchi 在 GDC 2005 发表的演讲，介绍《光环 2》为应对 12GB、39000 个资源文件而构建的内容管理系统。其核心是“标签”系统：每个 tag 对应磁盘上的一个文件和内存中的一个 C 结构，通过 tag_group 定义类型，支持 tag_block 数组和 tag_reference 跨标签引用。借助预处理器宏，系统获得类似反射的能力，可通用地序列化、遍历和重载资源。文中展示了标签定义、加载流程、单标签热重载、PC 到 Xbox 的 xsync 同步、面向光盘的缓存文件、基于 tag_block 的几何缓存，以及用于分析引用关系和安全移动/克隆资源树的依赖数据库。演讲也指出系统存在数据耦合导致重载行为复杂等缺点。核心结论是：随着游戏规模扩大，内容管理比技术本身更关键，统一、可编程的资源系统能显著提升开发效率和作品丰富度。

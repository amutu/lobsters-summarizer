## 1. 我的ISP在劫持我的DNS

- 原始链接: <https://karthihegde.dev/posts/dns_tampering>
- 英文标题: So my ISP was hijacking my DNS

作者在一个普通周六排查家庭实验室中Podman容器无法访问外部站点的问题时，通过dig命令发现ISP正在劫持DNS查询——普通DNS解析返回的IP地址属于ISP本身，而Cloudflare的DoH端点返回了完全不同的IP。这一发现引发热议，作者遂撰文澄清几个常见误解：第一，自托管Unbound并不天然安全，因为DNS解析涉及多次明文UDP查询，ISP仍可窃听或篡改；但可通过配置forward-zone配合DoT实现加密。第二，DNSSEC提供的是签名验证而非加密，流量仍明文传输，且截至2026年10月仅7.03%的域名具备完整DNSSEC链。第三，DoH和DoT仅加密传输通道，解析器本身仍可能篡改响应，用户需信任所选解析器。第四，即使使用TLS，ISP仍可通过SNI字段获知访问的主机名，彻底规避需借助VPN。作者最终采用AdGuard配合dnscrypt-proxy进行DNSCrypt加密，并以Cloudflare作为备用解析器，服务器运行NixOS，dotfiles开源。

## 2. Shlemiel 画家重现：Zig 的 libc 重写如何让 SQLite 变慢

- 原始链接: <https://dennisforbes.ca/blog/microblog/2026/10/the_accidental_12000x_sqlite_slowdown/>
- 英文标题: Shlemiel the Painter Is Back: How Zig’s libc Rewrite Made SQLite Slower

作者运营一个基于 Rust 和 SQLite 的国际象棋分析服务，在将约四万条 JSON 记录写入数据库时遭遇严重性能瓶颈：本应毫秒级完成的操作竟耗时数分钟，且完全占满 CPU。问题根源在于使用 Zig 的 cc 编译器（通过 cargo-zigbuild）交叉编译 SQLite 时，Zig 对 musl 标准库的纯 Zig 重写（libzigc）中，strspn、strcspn、strpbrk、strstr 等函数在实现时先测量整个字符串长度，再执行匹配。当 SQLite 内部的分词器反复跳过空白、定位新位置时，每次迭代都重新计算剩余字符串长度，形成经典的「Shlemiel 画家」二次方复杂度陷阱。实测中，对 1.2MB 文件进行分词比正常情况慢约一万两千倍，且随文件增大呈二次方恶化。该问题仅在 Linux 构建中出现，因为 Mac 端未使用 Zig 编译 SQLite。作者引用 Joel Spolsky 2001 年的「Shlemiel 画家」寓言，并类比当年 Firefox 因字符串拼接反复分配内存而在 Sunspider 基准中落后、后经预分配缓冲区修复的案例，强调这类基础算法陷阱在 2026 年仍会反复出现。临时修复方案包括预裁剪 JSON 空白字符，或将 Linux 构建迁移至原生 Linux 容器以绕过 Zig 的 libc 重写。

## 3. Safari 27.3 推出自适应深色模式

- 原始链接: <https://webkit.org/blog/18541/introducing-adaptive-dark-mode/>
- 英文标题: Introducing Adaptive Dark Mode

2026年11月，Apple 在 Safari 27.3 测试版中推出「自适应深色模式」（Adaptive Dark Mode），可将浅色网站自动转换为深色显示，以弥合近40%深色模式用户与仅10%原生深色页面之间的差距。其核心为颜色变换引擎：通过自研颜色矩阵反转亮度同时保留色相，文本转换遵循 WCAG 4.5:1 对比度标准，并针对 SVG 图标、位图徽标、CSS 渐变、遮罩及混合模式等分别处理；已声明 color-scheme: light dark 的页面则不做改动。文章建议开发者采用 SVG 图标、CSS 渐变、透明背景图片等现代实践以兼容该功能，并介绍了 color-scheme 元标签、prefers-color-scheme 媒体查询、light-dark()、color-mix()、contrast-color() 等构建完整深色体验的工具；若需强制浅色，可使用 color-scheme: light only。隐私方面，Safari 阻止网站检测该功能是否启用，JavaScript 查询 CSS 颜色时返回原始值，Canvas 渲染亦保持原样，以保护用户免受指纹追踪。

## 4. C++26标准遭ISO投票否决：C++社区面临信任危机

- 原始链接: <https://andreasfertig.com/blog/2026/11/cpp26-dis-failed-how-does-cpp-survive/>
- 英文标题: C++26 Disapproved

2026年10月23日，C++26在ISO国家成员体（NBs）的DIS阶段投票中未能获得所需的三分之二多数，被正式否决。据作者Andreas（C++标准化委员会成员、代表德国投票）所述，这是C++自1998年以来首次出现DIS投票失败，上一次类似情况是2006年C++/CLI项目被终止。否决的核心原因是「Contracts」（契约）特性，部分NB认为该特性尚未成熟。Contracts自2019年科隆会议起历经多年研究组工作，经EWG讨论后以多数票纳入C++26，WG21亦以超过三分之二多数批准其进入下一投票阶段。然而NB层级的投票打破了这一共识。ISO提供四条后续路径：提交修订草案重新投票、退回CD阶段、发布为技术规格、或取消项目，但均需WG21多数同意，而该委员会此前已明确支持含Contracts的版本，僵局难以打破。作者将此事件称为「巨大灾难」，指出整个ISO标准体系建立在信任与妥协之上，此次投票动摇了这一基础。11月16日的下次会议将优先处理僵局，但C++29的工作也已陷入停滞，C++标准的未来前景不明。

## 9. Postgres TOAST：爱恨交织的大字段存储机制

- 原始链接: <https://www.pgedge.com/blog/burnt-toast>
- 英文标题: Burnt TOAST

作者以一家金融公司event_log表的真实案例，深入剖析Postgres TOAST（超大属性存储技术）的工作原理与性能影响。当表含无长度限制的TEXT/JSONB列时，Postgres会自动创建影子表，将超过约2KB的压缩数据拆成1996字节块外存，原行仅保留指针。实验表明，TOAST使表体积从318MB降至47MB，不涉及大字段的操作（如计数、偏移跳转、更新）反而快3至5倍；但需读取大字段内容时，因额外索引查找、块重组和解压，性能显著下降。作者给出的实践方案是将大字段拆至独立表，通过LEFT JOIN加视图对应用层透明，主表堆从47MB缩至5MB，性能提升逾9倍。此外，Postgres 14起支持lz4压缩，压缩速度比默认pglz快30倍以上，解压仅慢约20%。文章最终指出，性能瓶颈往往不在TOAST机制本身，而在于大字段列的表设计；TOAST提供了以指针换取堆页密度的合理折中，DBA不必对其产生恐惧，但应审视是否需将「可选」大列外移以进一步优化。

## 11. 分数比较技巧再探

- 原始链接: <https://www.johndcook.com/blog/2026/11/03/fraction-comparison-trick-revisited/>
- 英文标题: Fraction comparison trick revisited

作者回顾并推广了几年前提出的一个概率结果：当 a+d > b+c 时，a/b > c/d 的概率为 11/12。文章将问题等价转化为：从 [0,1] 上均匀取四数 a,b,c,d，在 a+d > b+c 条件下 ad > bc 的概率为 11/12；更直观的表述是，随机取两对数，和较大的那对乘积也较大的概率为 11/12。在此基础上，作者进一步定义 f(r) = P(ad > bc | (a+d)/(b+c) ≥ r)，并论证其为 r 的增函数：r=1 时 f=11/12，r→∞ 时 f→1。数值上 f(2)≈0.99、f(6)≈0.999，说明两对数之和的比值越大，乘积大小关系与之一致的概率越接近 1。作者指出 f(r) 存在闭式表达式但形式极为复杂，因此同时采用解析推导与蒙特卡洛模拟（借助 Claude 完成）进行验证，两种方法结果吻合。文章的核心亮点在于将一个看似反直觉的分数比较问题，通过交叉乘积与条件概率的视角，转化为关于「和」与「积」之间一致性的高概率结论，并给出了随比值 r 单调递增的定量刻画。

## 12. 电子投票背后的密码学：为何纸质选票仍不可或缺

- 原始链接: <https://blog.trailofbits.com/2026/11/03/the-cryptography-behind-electronic-voting-and-why-paper-ballots-are-still-essential/>
- 英文标题: The cryptography behind electronic voting (and why paper ballots are still essential)

本文探讨密码学在电子投票中的应用及局限，论证纸质选票在一般选举中仍不可替代。文章列出选举系统四项核心安全需求：投票人隐私、选票完整性、防止重复投票、结果可验证性。纸质系统通过物理流程满足前三项，但结果可验证性最难实现；电子系统则面临供应链攻击与零日漏洞可大规模影响结果的独特风险，须遵循「软件独立性」原则，确保任何软件故障均可被检测。文章重点介绍两个协议：Helios面向低风险、低胁迫场景（如学术机构选举），ElectionGuard则作为纸质系统的密码学增强层，已在马里兰、爱达荷、威斯康星等选区测试。核心技术包括：指数ElGamal同态加密保护投票隐私、门限密钥共享防止单一服务器解密、Benaloh挑战方法检测被篡改的投票客户端、零知识证明确保选票值合法、以及ElectionGuard的哈希链机制检测后端对早期选票的篡改。密码学可实现「端到端可验证性」——投票人可独立确认选票被正确计入，任何人可验证最终计票——但无法完全替代纸质选票提供的物理安全保障。专家共识是纸质选票短期内不会消失，密码学应作为补充而非替代。

## 13. 从箭头到查询：用范畴论中间语言编译出 SQL 的 catlang

- 原始链接: <https://reasonablypolymorphic.com/blog/arrows-to-arrows/>
- 英文标题: Arrows to Arrows, Categories to Queries

作者介绍了一个名为 catlang 的实验性编程语言，其编译器将程序编译为一条巨大的 PostgreSQL SELECT 语句，在数据库中执行即得到程序输出。catlang 的中间表示（IL）基于抽象范畴论，使用箭头记法（arrow notation）书写，风格类似 Haskell 的 proc 块。文章以 count 函数为例：无论输入何值，程序通过一个 while 循环逐步将数值累加至 100 后返回。该函数在 IL 层被展开为范畴论符号（如 ⨟ 表示管道组合、▽ 表示 cochoice、△ 表示积等）构成的表达式，每个符号具有明确的代数语义。最终编译生成的 SQL 使用 PostgreSQL 17 的递归 CTE（WITH RECURSIVE），通过大量嵌套子查询、CROSS JOIN、UNION 和 NULL 标记来模拟范畴论中的 join、dist、undist 等操作。作者确认该查询在 PostgreSQL 中确实能正确返回 100，且是逐步迭代到 100 的——去掉 LIMIT 1 后可看到每一步迭代结果。作者坦言生成的 SQL 极其冗长丑陋，但并未做优化，因为项目初衷是验证「将范畴论中间语言映射到任意编译目标（包括 SQL）」这一思路的可行性，而非追求实用性能。

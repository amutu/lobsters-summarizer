## 1. 四定理证明器漫谈：Isabelle/HOL、Lean、HOL4 与 Agda 的主观对比

- 原始链接: <https://blueberrywren.dev/blog/primes/>
- 英文标题: A tale of four theorem provers, or: A (reasonably) opinionated comparison of Isabelle/HOL, Lean, HOL4, and Agda

文章以在四个定理证明器中形式化欧几里得「素数有无穷多个」证明为实验，从多个维度对比 Isabelle/HOL、Lean、HOL4 与 Agda。作者将四者按基础分为 LCF 风格（Isabelle/HOL、HOL4）与依赖类型风格（Lean、Agda），按交互性分为高交互（Isabelle/HOL、Lean）与低交互（HOL4、Agda），按自动化程度分为高（Isabelle/HOL、HOL4）、中（Lean）、低（Agda）。Isabelle/HOL 的 sledgehammer 与 HOL4 的 HolyHammer 可调用外部求解器自动完成子目标，但生成的证明难以阅读；Lean 的 grind 有时有效却常无进展；Agda 几乎无自动化，需大量手动操作。逻辑基础上，Isabelle/HOL 和 HOL4 采用经典逻辑并接受排中律，Agda 坚持构造性，其优势在于证明本身可实际生成素数，但计算极慢。代码量方面，Isabelle/HOL 最精简（117 行），Agda 最冗长（264 行）。定理搜索方面，Isabelle/HOL 和 HOL4 支持按模式检索，Lean 的 leansearch 和 loogle 功能较弱，Agda 则缺乏等效工具。作者个人偏好 LCF 风格，认为其更利于自动化，但承认各系统各有取舍。

## 2. 为什么编程代理如此笨拙？

- 原始链接: <https://mtlynch.io/why-are-coding-agents-so-dumb/>
- 英文标题: Why Are Coding Agents So Dumb?

作者以自身使用Claude Code、Codex、OpenCode等编程代理的日常体验为切入点，尖锐批评了当前代理层（而非底层大模型）的严重不足。他首先厘清概念：模型是「大脑」，代理是连接模型与代码库的「身体」，而瓶颈恰恰在代理。具体缺陷包括：无法并行处理可并行的子任务；不会按任务难度自动切换不同模型，把委派工作推给用户；不了解自身功能，需联网搜索；输出的「计划」只是零散细节的堆砌而非结构化方案；遇到小问题就停工等待用户回复；缺乏真正的操作系统级沙箱，安全边界仅靠「礼貌请求」LLM不要读取某些文件。作者列出了对2026年代理的期望：任务自动拆分与模型匹配、成本/速度/正确性可调、人类可读的分层计划、确定性沙箱、自我认知、多模型与开源支持、AFK模式等，并进一步畅想统一Web界面、ETA估算、自我审查、密钥代理注入等愿景。他将代理层投入不足归因于「主代理问题」：AI公司高管与一线开发者脱节，关注光鲜演示和模型基准，而非代理本身的实用性与安全性。

## 3. Unison Cloud 正式开源

- 原始链接: <https://www.unison-lang.org/blog/unison-cloud-open-source/>
- 英文标题: Unison Cloud is now open source

Unison Cloud 宣布以 MIT 许可证全面开源，涵盖四个项目。Unison Cloud 能将任意节点池转化为分布式计算机，使用 Unison 语言编程。其核心特性包括：服务秒级部署且体积小于 200KB，无需构建和分发多 GB 容器；通过自适应服务图压缩实现快速、带类型的跨服务通信；支持 fork/join 风格的分布式批处理；提供基于 DynamoDB 的事务存储与基于 S3 的对象存储；以及密钥管理、长时后台任务等能力。四个项目分别为：Unison Cloud 客户端（定义编程模型，含本地解释器与分布式解释器，早已开源）；Nimbus（用 Unison 编写的 worker 节点，支持动态扩缩容，本次新开源）；API Server（Haskell 编写的控制平面服务，负责集群成员跟踪与认证，新开源）；以及 UI（app.unison.cloud 的前端代码，新开源）。团队表示，开源能让该技术更好地服务社区，期望开发者基于此构建优秀应用，同时提供专业支持服务。

## 7. 「机器人」是一种社会建构：你的洗碗机为什么不是机器人

- 原始链接: <https://robotgirlgang.com/2026/10/08/robot-is-a-social-construct-why-your-dishwasher-is-not-a-robot/>
- 英文标题: "Robot" Is A Social Construct: Why Your Dishwasher Is Not A Robot

作者Mikell以自身参与工业安全标准制定委员会的经历切入，指出「机器人」的定义在技术上极难划定边界。面对同事「洗碗机是机器人」的说法，她先给出技术层面的反驳——洗碗机的喷淋臂仅是机械装置，不具备「操作物体」的能力，因此不满足机器人定义；但她更核心的论点是：「机器人」一词根本不是技术功能描述，而是一种社会建构。该词源自1920年恰佩克的科幻剧本《罗苏姆的万能机器人》，在科幻叙事中发展数十年后才成为可购买产品。科幻长期以机器人、AI为透镜审视「何以为人」，因此我们倾向于将那些令人感到新奇、恐惧、引发存在性焦虑的自动化机器称为「机器人」——涉及就业威胁、人际关系、宗教信念，乃至奴隶制历史等不适议题。作者以历史为例说明：「机器人」的指代对象随时间不断迁移，从工业机械臂到Roomba，再到协作机器人、人形机器人，每次转移都与技术的新奇程度及公众对其社会影响的恐惧程度紧密相关。最终结论是：一台机器被称为机器人，是因为它迫使我们直面关于自身的不适真相；而洗碗机不会让人审视存在意义，故不是机器人。

## 8. 无分支代码中隐藏的分支：常量时间编程的陷阱

- 原始链接: <https://00f.net/2026/10/09/llvm-compiles-branch-free-code-into-branches-on-risc-v/>
- 英文标题: Branches in branch-free code

本文以128位无符号整数加法和位掩码选择函数（ct_select）为例，揭示了一个令人不安的事实：即使源代码完全使用位运算、看似常量时间，编译器在RISC-V 32位（RV32）目标上仍会生成条件分支（beq/beqz），从而引入时序侧信道。作者对比了x86_64、AArch64、MIPS32、WebAssembly、Cortex-M0、PowerPC、RV32/RV64及Zicond等多个平台，发现缺乏条件移动指令（cmov）的架构（如Cortex-M0、32位PowerPC、RV32）均会产生分支。换用Zig或Rust语言无法规避此问题。GCC 16.1在RV上表现较好，但将掩码改为由比较运算推导后分支又出现。作者发现通过空asm语句设置寄存器屏障可阻止优化器引入分支，但对加法进位链不建议依赖此技巧。RISC-V的Zicond扩展（czero.eqz/czero.nez）可彻底消除分支，但需配合Zkt扩展才能保证时序无关，且当前许多核心（尤其微控制器）尚未实现。文章结论：编写安全、可移植的常量时间代码极其困难，涉及秘密的算术应避免超过两个寄存器宽度的整数类型，应手动编写进位链。

## 11. 用 Swift Embedded 在 QEMU 上实现一个极简内核

- 原始链接: <https://carette.xyz/posts/minimal_swift_kernel_on_qemu/>
- 英文标题: A minimal kernel in Swift, running in QEMU

作者以实验为目的，用 Swift Embedded（无操作系统、无标准库的 Swift 子集）在 QEMU 的 virt 机器上编写了一个极简 AArch64 内核，目标三元组为 aarch64-none-none-elf。由于 Embedded Swift 仍处于实验阶段，需安装 main-snapshot 开发工具链。项目核心流程为：汇编入口 _start 设置栈指针并跳转到用 @c 属性（原 @_cdecl）暴露的 Swift 函数 kernel_main；手动实现 putchar（向 QEMU PL011 UART 寄存器 0x09000000 写字节）和 memmove 等运行时依赖；通过自定义链接脚本将内核加载至 0x40080000，分配 128 KB 栈，并显式放置 ELF 元数据段以解决链接器报错。最终内核能打印「Hello, Embedded Swift」，并通过轮询 UART 接收寄存器实现字符回显，形成简易命令行提示符。作者强调这并非要替代 Linux，而是理解无 OS 环境下程序启动与运行的底层机制。后续计划包括清零 .bss、抽象 UART 驱动、研究内存分配、引入中断与定时器、实现任务调度，乃至 framebuffer 和键盘驱动。完整代码托管于作者的私有 Git 仓库。

## 12. 基于浮点技巧的向量化 CLZ 与 CTZ 实现

- 原始链接: <https://purplesyringa.moe/blog/vectorized-clz-and-ctz/>
- 英文标题: Vectorized CLZ and CTZ

本文介绍了一种利用浮点运算实现向量化 CLZ（前导零计数）和 CTZ（尾随零计数）的替代方案。核心思路是：将 32 位整数嵌入双精度浮点数的尾数部分，利用浮点指数为偏置对数的特性，通过一次浮点减法后提取指数即可得到 CLZ 值；CTZ 则先以 x⊕(x−1) 隔离最低置位，再用类似方法求对数。作者给出了 Rust 实现及对应的 AVX2 汇编，在 Haswell 上 CLZ 向量化版达 0.45 ns/迭代（标量 1 ns），Alder Lake 上为 0.29 ns（标量 0.85 ns）；CTZ 分别为 0.49 ns 和 0.35 ns。该技巧受限于双精度 52 位尾数，仅适用于 32 位输入。文章还讨论了 AMD 平台 lzcnt 本身极快、标量版可能更优，以及 Zen 架构 AVX-512 的 vplzcntd 选项。此外，作者补充了基于 de Bruijn 序列的另一种向量化 CTZ 方案：用 16 位 de Bruijn 序列重复两次配合 vpshufb 的 16 字节通道限制，在 Haswell 上耗时 1 ns 但吞吐量翻倍，若不需处理 x=0 边界可降至 0.82 ns。整体而言，浮点法在 Intel 现代 CPU 上吞吐优于标量，但延迟敏感场景下优势有限。

## 13. 自旋锁为何有害（2020）

- 原始链接: <https://matklad.github.io/2020/01/02/spinlocks-considered-harmful.html>
- 英文标题: Spinlocks Considered Harmful (2020)

本文作者 matklad（once_cell crate 维护者）强烈反对在 Rust 生态中用自旋锁替代 std::sync::Mutex 以支持 #[no_std] 环境的做法。文章首先解释自旋锁原理：线程在用户态循环执行 compare_and_swap，对操作系统而言与计算密集型线程无异；而基于操作系统的 Mutex 通过 park/unpark 系统调用将等待线程移出 CPU。作者指出，即便临界区极短，线程仍可能被抢占，导致其他线程持续自旋耗尽时间片，阻止被抢占线程恢复执行，进而引发优先级反转——低优先级线程持有锁时被高优先级线程抢占，高优先级线程自旋等待，系统陷入灾难性低效。在裸机或内核场景中，中断处理器尝试获取同一锁还会造成确定性死锁。作者以 getrandom crate 为实例，通过 extern "C" 覆盖 poll 和 syscall 函数模拟慢速 /dev/random，配合实时优先级线程，实测自旋锁版本运行两分钟仍无法完成（系统时间 940 秒），而改用 std::sync::Once 后仅 0.51 秒。作者建议：短临界区直接使用 std 或 parking_lot 的 Mutex（其内部已含少量自旋）；一次性初始化可改为将状态缓存委托给调用方、采用幂等的 racy initialization，或参数化阻塞行为由用户注入同步原语；单线程场景（如 WASM）可假设不阻塞并在违反时 panic。

## 15. Lifeguard：Python 延迟导入兼容性静态分析工具

- 原始链接: <https://github.com/Facebook/lifeguard>
- 英文标题: Lifeguard: A static analyzer for Python lazy imports compatibility

Lifeguard 是一款由 Meta 开发的静态分析工具，旨在帮助 Python 项目安全采用 PEP 810 引入的显式延迟导入（Lazy Imports）。延迟导入将模块加载推迟到名称首次访问时，可显著降低大型代码库的内存占用与启动时间，但模块级副作用、注册模式、sys.modules 操作及元类等模式依赖导入立即执行，直接启用延迟导入可能导致行为异常。Lifeguard 通过并行遍历各模块的 AST 检测这些不兼容模式，采用保守策略——无法确定安全的模块默认标记为不安全，宁可牺牲部分性能优化也确保生产安全。工具输出 JSON 文件，包含 LAZY_ELIGIBLE（可安全延迟导入的模块及其前置约束）与 LOAD_IMPORTS_EAGERLY（必须立即加载全部导入的模块）两部分。用户可将其作为独立 linter 在 CI 中标记不兼容代码行，也可将输出驱动 Python 3.15 的 sys.set_lazy_imports_filter() 回调以构建延迟导入过滤器。工具以 Rust 实现，复用 ruff 的 AST 遍历能力，支持 Python 3.12 与 3.14，当前处于 Beta 阶段，目标在 Python 3.15 正式发布前达到通用可用状态。

## 16. 减少C语言中的未定义行为

- 原始链接: <https://lwn.net/Articles/1095811/>
- 英文标题: Reducing undefined behavior in the C language

本文报道了Kernel Recipes 2026会议上Martin Uecker的演讲，主题为C语言中的未定义行为及其向内存安全语言演进的可能性。Uecker指出，C语言凭借可移植性、稳定性和高效性仍是优秀语言，但其历史包袱导致标准中存在约100处未定义行为。C89标准采用抽象机器模型定义语义，仅约束可观察行为，赋予编译器极大自由度，甚至允许在遇到未定义行为时执行任意操作（即「nasal demons」），引发开发者对语言语义的广泛分歧。他列举了结构体填充字节读取、除零后编译器省略条件测试、volatile变量上的「时间旅行」优化等典型问题。为应对这些挑战，C委员会设立三个专项研究组，C2y草案已移除45处未定义行为；C23标准则删除了K&R函数定义、补码支持和trigraphs，新增位精确整数类型与检查整数运算。工具方面，编译器警告、静态分析器、sanitizers、LLM辅助工具和形式化验证正形成合力。内存安全被拆解为类型安全、空间边界检查和时间安全（如use-after-free）三个子问题，其中时间安全仍最难，Rust和CHERI架构具有一定优势。Uecker总结认为，C仍是活跃演进的语言，完全内存安全虽尚未实现，但通过受限语言子集配合形式化验证，未来有望逐步达成。

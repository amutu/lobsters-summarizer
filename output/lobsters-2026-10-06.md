## 1. Gleam v1.19.0：不再生成 Erlang 源代码，转向抽象形式编译

- 原始链接: <https://gleam.run/news/gleam-doesnt-compile-to-erlang-source-anymore/>
- 英文标题: Gleam doesn't compile to Erlang source anymore

Gleam v1.19.0 发布，核心变化是 Erlang 代码生成器被完全重写：不再输出 Erlang 源代码，改为生成 Erlang 抽象形式（abstract forms），即 Erlang 编译器内部使用的中间表示。这一改动带来三方面收益：编译速度显著提升（基准测试中 v1.19 远快于 v1.17）；运行时位置元数据精确到原始 Gleam 源码行号，BEAM 崩溃报告和堆栈跟踪更准确；编译器代码质量整体提升。文章还解释了为何不直接生成 BEAM 字节码——字节码格式随 VM 版本变动，维护成本过高，而抽象形式是成本与收益的最佳平衡点，Elixir 也采用同样策略。JavaScript 目标方面，决策树赋值优化将嵌套 if 合并为单条件判断，短列表字面量改用 prepend 链式构造而非数组转换，提升运行时性能。TypeScript 声明文件新增函数重载以保留泛型类型参数。此外，构建工具命令改进以支持 Elixir Mix 和 Erlang rebar3 集成；语言服务器补齐了字段与参数标签的跳转、查找引用和重命名功能；WebAssembly 构建新增 format_source 函数，可在浏览器中格式化 Gleam 代码；错误消息方面增加了合并冲突标记、记录更新语法位置错误、无效过程运算符等多种针对性提示。项目完全依赖社区赞助运营，核心团队成员收入仍待改善。

- 英文标题: Flirt is now Open-Source

作者宣布代码审查工具 Flirt 正式开源，代码托管于 Codeberg 平台。Flirt 专为「patch series」工作流设计，即作者持续对提交进行 amend、rebase 和 force-push 的场景。其核心特性是记住用户此前审查过的内容，并展示与当前状态之间的差异，帮助审查者快速定位变更。该工具采用本地优先架构，兼容 GitHub 和邮件列表等多种后端。作者同时发出明确警告：Flirt 目前尚不具备面向普通用户使用的条件，仍存在大量 bug 和缺失功能，建议非贡献者暂且耐心等待，待工具成熟后作者会另行发文通知。对于有意参与贡献的开发者，作者邀请其加入 Zulip 讨论组，但特别强调禁止使用 LLM 撰写讨论消息。此外，由于 Flirt 托管在 Codeberg 上，作者计划未来构建一个基于 Forgejo 的后端来「自我使用」（dog-food）Flirt，但该后端尚未实现，已列入待办清单。

## 3. 告别Deno，回归Node.js

- 原始链接: <https://dbushell.com/2026/10/03/deno-to-node/>
- 英文标题: Friendship ended with Deno, now Node is my best friend

作者长期以Deno为主要运行时，但近期在一个SvelteKit客户项目中重新使用Node.js后，发现Node已今非昔比：ECMAScript语法糖全面支持，旧API已现代化，require()彻底消失。包管理方面，作者选用FNM管理Node版本、PNPM替代NPM以规避供应链安全风险，并通过设置minimumReleaseAge和trustPolicy延迟恶意包更新。TypeScript方面，Node v26.10.0可直接运行TS，但出于生态考量拒绝处理node_modules下的TS文件，作者转而用Tsdown打包。迁移静态站点生成器时，仅需将Deno文件系统API替换为node:fs、Deno.serve替换为Hono的Node适配器，改动极小，构建速度反而提升15%。作者批评Deno公司被硅谷商业逻辑带偏，裁员后产品缺乏创新，加之ZSH集成损坏、JSR频繁返回429、并发HTTP请求崩溃等问题，最终执行「brew uninstall deno」，正式告别Deno。

## 4. 异步 Rust：调度器究竟该住在哪里？

- 原始链接: <https://herecomesthemoon.net/2026/10/async-rust-where-does-the-scheduler-live/>
- 英文标题: Async Rust: Where does the scheduler live?

作者以一张 5×5 的「bingo 卡」罗列了社区对 async Rust 的常见抱怨，涵盖 scoped task 三难困境、函数着色、async 闭包耗时六年才落地、Tokio 默认主义、复杂编译器报错、async Drop 缺失、Future 惰性求值、Send+Sync+『static』边界扩散、select! 取消安全、io_uring 兼容、Pin 与 Move trait 之争、栈溢出、work-stealing 与 thread-per-core 之争等二十余条。作者最初的核心困惑是：Rust 的招牌卖点正是无需运行时（如 GC），而 async 却要求引入一个外部运行时，感觉像是退步。但经过逐步推演，作者承认这些抱怨本质上是并发编程的通用问题——若改用线程，内核便成为调度器，问题并未消失。Rust 将调度器放在 crate 而非语言内置，是为了保持嵌入式 no_std 场景可用、维持零成本抽象定位，避免像 Go 那样以性能换便利。作者也指出 async Rust 并非性能最优，例如参数跨 yield 点时状态机会膨胀一倍甚至指数级增长。最终作者仍提出一个大胆设想：或许应直接改进内核线程调度（如 M:N 用户级线程），让「直接用线程」变得足够廉价，从而绕开整个 async 运行时生态的复杂性。文章在讨论 M:N 方案时截断，未给出完整结论。

## 5. 无root权限下让Podman配合docker-compose使用

- 原始链接: <https://elou.world/en/tutorial/podman-docker-compose>
- 英文标题: Using docker-compose with Podman rootless

Podman是Linux上无守护进程的Docker替代品，支持无root权限运行。文章介绍如何让Podman暴露兼容Docker API的UNIX域套接字，从而与docker-compose等Docker生态工具配合使用。核心步骤有三：首先以普通用户执行「systemctl --user enable --now podman.socket」启用Podman套接字；其次将DOCKER_HOST环境变量设为指向该套接字的路径，并写入shell配置文件使其持久化；之后即可像往常一样运行docker-compose的config、up、ps、down等命令。文章还补充了若干实用技巧：停止已安装的rootful Docker服务以释放端口；docker命令本身也可通过DOCKER_HOST连接Podman套接字；「podman unshare」可在用户命名空间中获取root shell，类似sudo -i，便于对容器文件执行chown等操作；「podman mount」可挂载运行中容器的文件系统以便用编辑器修改文件；若暂不切换Podman，Docker也支持rootless安装，但缺少unshare和mount的等价功能。最后，通过「loginctl enable-linger」可让容器在用户注销后继续运行，避免会话结束即停止。

## 8. 精炼 E-Graph：在等式之上引入偏序

- 原始链接: <https://www.philipzucker.com/refinement_egraph/>
- 英文标题: Refinement E-Graphs

本文提出「精炼 E-Graph」（Refinement E-Graph）的概念，在 E-Graph 原生的等号「=」之外，引入一个与等号同等地位的偏序「<=」，用于表达从抽象到具体的单向精炼关系。作者指出，编译器重写往往并非双向等式，而是从宽松语义（如整数溢出、求值顺序未定）向可执行的具体语义的单向推导；数字电路中的「Don't Care」项是典型例子——优化器可自由将其精炼为 True 或 False 以得到最优电路，且各处使用可独立选择，这与直接令 dontcare = true 或 dontcare = false 有本质区别。文章给出基于 microegg 的原型实现（含 WASM 演示），核心数据结构为「不等式并查集 + 哈希规范化」，其中不等式不会像等式那样「销毁」等价类资源。在算法层面，作者讨论了三个关键扩展：精炼闭包（以单调性/反单调性替代同态闭包）、精炼 E-匹配（在匹配时追踪 LE/EQ/GE 模式并按函数参数的 variance 翻转方向）、以及精炼提取（以「最精炼且最小」为最优准则）。语义上，<= 对应逐点集合包含，整体框架与 lifting E-Graphs 正交，可组合使用。文章最后附了一段 Python 玩具实现，展示了 LE_EGraph 类的基本操作。

## 10. 逆向工程《科曼奇》地形地图文件

- 原始链接: <https://pikuma.com/blog/comanche-maps-reverse-engineering>
- 英文标题: Reverse Engineering Comanche Terrain Maps

本文记录了逆向解析1992年NovaLogic游戏《科曼奇：最大杀伤》地形数据文件的完整过程。该游戏采用Kyle Freeman发明的Voxel Space体素空间渲染技术，每关需要1024×1024的颜色图与高度图。作者发现游戏目录中的.DTA文件（C系列为颜色图，D系列为高度图）本质是PCX v5图像，仅将标准PCX头前8字节替换为「Kyle DTA」签名，其余128字节头部、RLE游程编码像素数据及文件末尾769字节的256色调色板均遵循PCX规范。RLE解码规则为：字节高两位为1时低6位为重复计数，否则为字面值。作者用ANSI C编写命令行工具，完成读取、RLE解码、调色板提取，并输出为8位索引色BMP图像。高度图附带伪彩色调色板（蓝、橙、灰、品红各16级），可生成等高线视图。文章还解释了选择BMP而非GIF的原因（避免LZW编码复杂度），以及VGA 13h模式下调色板需右移2位以适配6位DAC等硬件细节。

## 11. 你不需要效果系统

- 原始链接: <https://burningwitness.github.io/blog/posts/against-effect-systems/>
- 英文标题: You don't need an effect system

作者获得机会重写一个旧Haskell生产代码库，借此逐一审查效果系统（effect system）的每项功能，结论是全部可以弃用。传递参数可手动完成；追踪效果并不能阻止unsafePerformIO等不安全操作；纯函数中的可变状态用ST单子即可；随机数等小效果反而不宜追踪；也不需要高阶嵌套效果。最终发现唯一真正用到的功能是错误处理，而效果系统对此并无特殊机制，本质只是包装了Either或异常。作者提出用bracket模式实现一个Early类型，以类型安全异常完成「提前返回」，并据此在纯IO中重建所有效果：配置直接作为函数参数传递，Mocking用函数记录类型表达，资源管理用mask与catch，错误处理用嵌套Either。模块可按接口、实现、内部三层拆分以控制访问。接口层将效果作为参数传递，借助GHC未使用参数警告定位问题；实现层用runStack逐层组合。文章最后指出，效果系统唯一独特能力是「在代码行之间做任意事情」，作者认为这并非优点。纯IO方案的代价仅是部分函数签名冗长，但换来兼容Haskell 98、无额外依赖、无怪异类型错误、编译与运行更快等显著优势。

## 13. 用 C++20 手写定制静态站点生成器 ssg 替代 Jekyll

- 原始链接: <https://nullprogram.com/blog/2026/10/04/>
- 英文标题: A new, bespoke static site generator to replace Jekyll

作者 Chris Wellons 在 nullprogram.com 博客上宣布，用约 8372 行 C++20 代码写了一个名为 ssg 的定制静态站点生成器，彻底替换了使用 15 年的 Jekyll。ssg 零依赖、无 libc 核心、采用模板化 arena 与 slice 等个人编码风格，冷生成整个博客仅需 150ms，比 Ruby 启动 Jekyll 还快。视觉与 HTML 语义几乎不变，但语法高亮改为自研，新增 WAT、AT&T、Aarch64 汇编及 QBasic 支持。由于 ssg 只服务这一个站点，无需 Liquid 模板系统，升级过程简化为修旧 bug、加入新生成器、删除模板三步。Jekyll 的真正痛点并非性能而是 Ruby 部署环境的繁琐，而 ssg 只需一个 C++ 编译器，单文件可移植，甚至能在 Windows XP 上运行。在 GitHub Actions 中每次推送都会重新编译生成器再出站，整体速度反而更快。作者明确表示 ssg 不会做成通用工具，认为「按需定制」才是软件的未来。文章另一亮点是：这是作者首次完全由生成式 AI 完成的项目——2026 年 9 月发布的 Opus 5.5 在 Claude Desktop 中约 2 小时即产出几乎无 bug 的 ssg，且完美匹配作者个人风格，令作者感到「如同看到他人复刻自己的笔迹」。作者建议读者在提示词中引用其四篇关于 C 编码哲学的文章，即可让前沿模型生成同等质量的代码。

作者将1993年原版Doom的游戏逻辑与渲染器完全用SQL实现，运行在CedarDB数据库中。游戏循环保持原始35 Hz，渲染器在笔记本上可达60 Hz输出320×200帧缓冲；Python客户端仅负责计时、读取键盘和显示位图，多人对战（4槽Deathmatch）也已可用。架构上，游戏逻辑与渲染解耦：逻辑以固定35 Hz推进，渲染器作为游戏状态表的纯函数按需查询。Doom的WAD文件格式本身高度关系型，导入仅需约1000行Python、18秒。游戏逻辑约5900行SQL，少于原版C源码的约9000行；渲染管线约1300行SQL、89个CTE，也少于linux_doom渲染引擎的约3300行。BSP树遍历被巧妙转化为一次SUM加ORDER BY的排序操作，同时完成前到后排序与视锥裁剪。怪物AI用SQL状态机编码（站立、看见、发射、疼痛、死亡、血腥爆炸等）。最慢的单个tic（E4M1、46个怪物）耗时10.45毫秒，仅占28.6毫秒预算的37%；典型场景约2.15毫秒。作者指出SQL天然契合ECS模式：每个组件是一张表，每个系统是一条带JOIN的UPDATE或INSERT，数据库自动并行处理。

## 15. 在 Steam Frame 上安装与配置 Nix

- 原始链接: <https://johns.codes/blog/nix-on-steam-frame>
- 英文标题: Nix on the Steam Frame

本文记录了作者在 Steam Frame 上安装 Nix 包管理器并配合 Home Manager 进行声明式配置的全过程。由于 Steam Frame 与 Steam Deck 使用相似的 SteamOS，官方 Nix 安装器的「steam-deck」模式可直接复用，安装时需注意根文件系统为只读、/nix 目录通过 bind mount 挂载到 /home/nix 以规避系统更新覆盖等问题。文章重点解决了几个 SteamOS 特有问题：一是嵌套 Plasma 会话导致用户 systemd 守护进程不可达，需手动覆盖 XDG_RUNTIME_DIR 和 DBUS_SESSION_BUS_ADDRESS 环境变量；二是 VR 启动器仅读取 ~/.local/share/applications 且 PATH 不含 Nix profile，需将 .desktop 文件链接并改写绝对路径；三是 /etc 下文件在系统更新后会被清除，作者自研 steamos-etc 模块将声明式 /etc 文件注册到 atomic-update 保留列表，同时处理 GPU 驱动符号链接在 /nix 挂载前不可用的问题。此外，作者还演示了通过 steamos-etc 以 Home Manager 风格配置 Tailscale 系统服务，并介绍了 frametop-nix 模块，后者为 Steam Frame 带来多屏桌面、3D 鼠标、眼动追踪和手部追踪等 VR 增强功能，使 Frame 可替代日常电脑使用。

## 1. curl 性能测试：从零开始的实践与公开上线

- 原始链接: <https://daniel.haxx.se/blog/2026/08/14/curl-performance-2/>
- 英文标题: Curl Performance

本文介绍了 curl 项目如何构建并公开其性能测试系统。作者指出，性能测试通常困难重重，项目此前多次讨论却因挑战过大而搁置，直到近期才决定动手。他没有寻找现成的开源性能看板或采用复杂的 Grafana 方案，而是选择在本地开发机上运行测试：编写脚本定期从 git 拉取最新代码、构建 curl、执行一组测试，并记录日志、生成图表，最终自动上传到 curl 官网公开结果。当前系统每 20 分钟运行一轮，包含 24 个测试，单轮约 6 分钟完成。文章强调，性能测试需要稳定的运行环境，而共享云基础设施难以满足，因此先使用个人机器。为了辅助短期和长期趋势分析，作者引入了“stakes”概念，即为每个测试设置人工阈值，以便识别意外性能退化；同时采用 LTTB 算法进行长时序降采样，并尝试 Mann-Kendall 趋势检验。文中还提到，公开数据后立即引发了开发者对性能优化的关注和提交，证明了可见性的价值；同时，优化也需权衡，例如减少内存分配可能导致结构体膨胀。作者表示，未来可能增加不同硬件、操作系统和库的测试维度，并欢迎社区贡献。

## 2. CHIP-8的艺术

- 原始链接: <https://beyondloom.com/blog/artofchip8.html>
- 英文标题: The Art of CHIP-8

本文深入探讨了CHIP-8这一诞生于1977年COSMAC VIP套件电脑的编程语言及其指令集架构。CHIP-8程序由一系列双字节指令组成，类似简单虚拟机的机器码，因此其解释器也常被称为“模拟器”。作者基于开发Octo汇编器的经验，指出由于长达半世纪的“传话游戏”，各种CHIP-8解释器在行为上存在大量分歧，他推广了“quirks flags”来标准化差异，并开发了成熟的测试套件。文章系统介绍了CHIP-8的34条指令，涵盖算术、内存、子程序、控制流、输入、随机数、定时和显示输出等方面，并给出了面向可移植性的实用建议。关键提醒包括：不要使用vf寄存器作为算术指令的目标，不要假设寄存器初始为零，避免依赖内置十六进制字体的外观，不要在load/save后重用i的位置，以及注意移位指令和位操作在不同解释器中的差异。文章还展示了自修改代码、间接寻址、数字显示等高级技巧，强调通过保守的编程习惯，可以在绝大多数解释器上获得兼容性。最后，作者提供了进一步学习的资源指引。

## 5. 别叫它“技术债”，那只是“一团乱麻”

- 原始链接: <https://www.simplermachines.com/lets-not-call-it-tech-debt-its-just-mess/>
- 英文标题: Let's not call it "tech debt," it's just "mess"

作者认为“技术债”这个比喻常被误用，尤其在非技术人员耳中，容易让人以为开发者工作不佳或推卸责任。金融债务有合理额度、条款明确、成本可预测，而多数被称作“技术债”的软件问题并不符合这些特征。一部分所谓“技术债”只是草率或低水平的工作，比如慢而不稳的测试，这属于技艺问题而非债务；另一些则是审美偏好，如容器镜像的组织方式，团队可能反复改来改去。作者最大的担忧是成本可预测性：真正的债务在借入时就知道代价，但技术决策的后果往往在事后才爆发。例如采用AWS Lambda的事件驱动架构，团队因缺乏经验而无法正确监控，最终系统难以理解且吞吐量极低，这更像买了无法赎回的私募信贷。作者主张改用“mess”（一团乱麻）和“维护家或工作空间”的比喻：软件项目需要持续清理、整理和重组，有时是从前业主手中接过的旧房子，需要大量修缮但还得先住着。这个比喻更贴近现实，也避免了“债务”带来的误导性金融联想。

## 6. 我想要的 Rust FFI：extern "fil-c"

- 原始链接: <https://domenkozar.com/2026/08/13/i-want-extern-fil-c/>
- 英文标题: I want extern "fil-c"

文章探讨了 Rust 通过 C FFI 使用旧有代码时面临的内存安全问题：Rust 在编译期保证内存安全，但一旦跨过 unsafe 边界调用 C 库，信任一个双方都无法强制执行的契约，安全保证便会失效。作者提出一种新的思路：使用 Fil-C——一个重新编译 C/C++ 并加入能力模型、运行时检查和并发垃圾收集器的系统，使内存违规变为 panic 而非漏洞。作者希望建立一个 Rust 到 Fil-C ABI 的桥接，支持 extern "fil-c"，生成安全 Rust 包装器，用 Fil-C 编译整个 C 依赖树，并提供无逃逸回普通不安全 C 的路径。文中提到 filnix 已将 Fil-C 作为 Nix 交叉编译平台，支持上百个包；Zig 也在探索受 Fil-C 启发的可选 ABI。该方案的成本模型是：使用 C 代码会因运行时检查而付出性能代价，而用 Rust 重写热路径则可将检查静态化，消除开销，从而激励迁移。难点在于保持全程序 ABI 一致性，避免破坏 Fil-C 的整体保证。作者呼吁 Rust、Fil-C、Zig、Nix 社区合作，并邀请参与明年在兰萨罗特岛的 OceanSprint 活动。

## 7. 代码注释与PR描述的区别

- 原始链接: <https://devblogs.microsoft.com/oldnewthing/20260812-00/?p=112607>
- 英文标题: Comments in the code vs PR description

文章指出，在提交Pull Request（PR）时，PR描述和代码注释承担完全不同的角色。PR描述是“点时”信息，用于说明变更为何被接受，包括要解决的问题、修复方式、验证过程、替代方案为何被拒绝以及相关检查单等，其本质是说服审阅者通过变更。代码注释则是“持久”信息，解释代码本身如何调用、有哪些前提条件等，在PR合并后依然有长期价值。文章通过具体例子帮助区分：比如“我检查了所有调用，只有这一个传了错误标志”应放在PR描述中，因为它只对当前代码状态成立；而“函数正确调用方法参见文档”应放在代码里，因为它长期有效。又比如“Doodad组件将利用极性反转”应放入PR描述，因为未来变化可能导致该表述失效。文章还特别提醒，代码注释必须脱离PR上下文也能被理解，例如不要写“当所有客户端迁移到新函数时，保持此代码”，而应在旧函数上写“当所有客户端迁移后，删除此函数”。整体而言，作者强调合理区分两类信息能够提升代码可维护性和团队排查回归的效率。

## 8. 仍然没有银弹

- 原始链接: <https://cekrem.github.io/posts/there-is-still-no-silver-bullet/>
- 英文标题: There Is Still No Silver Bullet

本文纪念弗雷德·布鲁克斯的经典论文《没有银弹》发表40周年，并论证其核心论断至今依然成立。布鲁克斯将软件工程工作分为本质与偶然两部分：本质是指概念构建、设计决策和对系统意义的理解；偶然是指表达这些概念的劳动，如语法、构建工具、样板代码等。布鲁克斯认为，任何工具或管理技术只能压缩偶然部分，因此除非偶然占工作量的九成，否则无法带来数量级的效率提升。文章指出，当前以LLM为代表的人工智能是历史上最有效的偶然压缩器，但关于AI大幅提升生产力的宣称，实际上只是暴露了使用者的工作中有多大比例属于偶然。文章引用METR在2025年的随机对照试验：16名资深开发者在自有成熟代码库中使用AI辅助反而慢了19%，而他们自感快了约20%。作者强调，代码写作本身包含大量本质工作，“代码从来不是难点”的说法是对程序员的误解和侮辱。最后，文章建议人们诚实地分类每周工作，有意将AI用于偶然任务，保护本质工作的时间，并像布鲁克斯所倡导的那样，着力培养优秀的设计师而非提示词工程师。

## 9. ActivityPub：因为无聊，所以胜利

- 原始链接: <https://o.ee/blog/activitypub-won-by-being-boring/>
- 英文标题: ActivityPub Won by Being Boring

Evan Prodromou在FediForum 2026的演讲揭示了ActivityPub成功的核心：它刻意保持“无聊”。协议只做最小约定——通过HTTP、URL和JSON传递“主语-动词-宾语”的活动数据，不规定数据库、审核或界面，因此Mastodon、PeerTube等异构平台能共享社交图谱却不失自身形态。文章指出，这种可实现的简单性正是它传播的原因。但技术债也存在：主流使用的HTTP签名基于已过期的草案，与RFC 9421不兼容；没有端到端加密，实例成了信任边界。治理依赖联邦阻断，没有中央权威。Prodromou认为真正的胜利标是至少两个亿级商业网络（如Threads+LinkedIn/Snap）通过ActivityPub联邦，以及中国大型社交网络可能带来的机会；同时以JavaScript战胜ActiveX为例，呼吁开放方案先行，防止巨头以实行规模抢占标准。W3C已在2026年成立新的工作组，计划在Q3完成向后兼容的维护修订，并推进账户迁移协议LOLA。结论是：ActivityPub的未来应保持“无聊”的基础设施，同时应对商业化、治理和隐私的挑战。

## 10. RISC-V：他们本该更明智

- 原始链接: <https://dmitry.gr/?r=06.%20Thoughts&proj=12.%20RV>
- 英文标题: RISC-V: They Should Have Known Better

作者Dmitry.GR系统阐述了对RISC-V指令集架构的批评，认为其试图用单一ISA通吃从低端微控制器到高性能服务器的所有场景，这注定失败。在低端嵌入式领域，RISC-V中断处理至少需44个周期，而Cortex-M0仅需27个周期，因基础ISA缺乏硬件自动压栈，必须依赖可选的Zicsr扩展，实际性能明显落后。压缩指令扩展（C/Zcb）的偏移范围设计也很糟糕，字节/半字存储的有效偏移极小，代码密度优势存疑。高性能方面，RISC-V缺乏索引寻址模式，数组访问需要多条指令，Zba扩展只是事后补救，且会增大代码体积。更根本的问题是RISC-V把几乎所有特性都设为可选：乘法、除法、压缩指令、CSR、特权模式均可选，导致“符合规范”几乎无意义；连检测特性的misa CSR本身也可选，甚至允许读作全零，低特权级代码无法可靠探测硬件能力。作者认为这是学术式设计委员会脱离现实的结果，但RISC-V仍可能因成本优势占领低端市场，只是并非因其设计优秀，而是因为它比8051这类老架构有所改进。

## 11. Python 预声明常量的怪异行为

- 原始链接: <https://sebsite.pw/w/20260801-pythonconstants.html>
- 英文标题: python's pre-declared constants are kinda weird

文章探讨 Python 中六个预声明“常量”——True、False、None、__debug__、Ellipsis（...）和 NotImplemented 的差异。True/False/None 是关键字，属于词法记号，不经过常规名字解析，因此 x.True 会直接抛出 SyntaxError；它们同时也以内置对象形式存在，虽可用 setattr 修改 builtins 中对应名称，但 True 本身不受影响。__debug__ 是布尔常量，用 -O 运行时为 False，用于模拟断言关闭；它是普通标识符，却唯一不能被赋值（包括属性赋值），删除也有专门报错，且修改 builtins.__debug__ 不影响其实际值。Ellipsis 和 NotImplemented 则只是普通内置名，可被全局变量遮蔽，setattr 后 Ellipsis 会变，但 ... 字面量仍是 Ellipsis，说明 ... 才是真常量而 Ellipsis 不是。文章还指出一种特殊 SyntaxError：给 __debug__ 赋值、在函数外使用 yield/await 时，语法本身合法但会报 SyntaxError，甚至 assert (__debug__ := 67) 在 -O 下不会报错，体现“语法错误”的例外性。整体揭示了 CPython 在常量处理上缺乏一致性，并对其设计理由提出疑问。

## 12. 利用DRAM加扰解锁CPU上的一切

- 原始链接: <https://github.com/xoreaxeaxeax/skitter-creek-bath-salts>
- 英文标题: Unlocking _everything_ on the CPU with DRAM scrambling

本文介绍了一种针对AMD Family 16h CPU的攻击技术，利用DRAM控制器（MCT/DCT）地址转换寄存器可被运行时重新编程的弱点，打乱物理地址到DRAM坐标的映射，从而绕过基于物理地址的安全机制。攻击者通过翻转一个寄存器位（如0xf80c2094的位22），在保持系统运行的情况下切换内存视图，使PSP、SMM、C6状态、微码等受保护内存区域暴露出可访问的别名。由于DRAM地址转换是GF(2)线性映射，作者利用z3求解器，通过向内存写入标记并恢复视图的方式收集目标-别名样本，进而重建转换矩阵，实现对任意受保护地址的读写。文章还详细描述了在攻击过程中维持缓存/TLB一致性、避免系统崩溃的技巧，并指出该技术可扩展到其他架构，但仅是一个开端。

## 13. 计算图支配者

- 原始链接: <https://neugierig.org/software/blog/2026/08/dominators.html>
- 英文标题: Computing graph dominators

本文介绍计算图支配者（dominators）的算法与直觉。作者因项目需要再次使用支配树，深入研究了相关算法。文章首先定义了节点支配和直接支配的概念，并给出了可视化示例。在选择算法时，作者对比了多种方案：Lengauer-Tarjan（1979）虽是标准但实现复杂；2001年的论文“A Simple, Fast Dominance Algorithm”提出简单算法，声称比LT快约2.5倍，但后续研究对此有争议；不过对不同图测试显示，各算法性能差异不大。文章重点讲解了“Simple, Fast”算法的核心思路：将问题转化为数据流方程，迭代计算每个节点的支配者集合或直接支配者。关键技巧包括使用反向后序（RPO）遍历保证父节点编号小于子节点，以及通过向上移动两个指针求最近公共祖先的高效方法。作者还讨论了初始化、收敛性等细节，并提供了完整的Rust实现代码。最后指出，对于常见图规模，算法选择影响不大。

## 14. OxiSH：用Rust编写的SSH服务器

## 17. Common Lisp 数组子类型的一个意外行为

- 原始链接: <https://simondobson.org/2026/08/07/strange-behaviour-in-lisp-sub-typing/>
- 英文标题: Unexpected (to me) behaviour in Lisp sub-typing

文章作者在 Common Lisp（SBCL）中遇到了数组子类型判定的意外行为。若在 defstruct 中声明槽位类型为 (simple-array integer)，使用字面量 #1A() 或 #1A(1 2 3) 作为默认值或初始值均可通过类型检查。但若将类型改为 (simple-array (unsigned-byte 16))，同样的字面量会报类型错误。原因是 #1A() 与 #1A(1 2 3) 的实际类型分别是 (SIMPLE-VECTOR 0) 和 (SIMPLE-VECTOR 3)，它们不是 (simple-array (unsigned-byte 16)) 的子类型。作者发现 integer、number、float 以及不带宽度的 unsigned-byte 都能通过，唯独 (unsigned-byte 16) 这类受限类型不行。他推测这与 upgraded array element type 有关：integer 和 unsigned-byte 的提升类型是 T，而 (unsigned-byte 16) 的提升类型仍是自身，说明编译器会对受限元素类型做更严格的表示和检查。解决办法是显式使用 make-array 并指定 :element-type，例如 (make-array 3 :element-type '(unsigned-byte 16) :initial-contents ...)。作者表示未在手册中找到相关说明，但认为该行为与数组元素类型的升级机制密切相关。

## 2. 如果 Git 托管服务是一个静态站点生成器

- 原始链接: <https://char.lt/blog/2026/09/sorcery-repo-viewer/>
- 英文标题: what if my git host were a static site generator?

作者长期运营个人 Git 托管服务（从 Gogs 到 Gitea 再到 Forgejo），但在小型机器上频繁遭遇磁盘耗尽和内存溢出，且 Forgejo 的 issues、PR、wiki 等功能远超其实际需求。作者反对用 Anubis 等 WAF 的 JavaScript 工作量证明来抵御爬虫，认为这违背开放网络精神，且对不支持 JS 的浏览器极不友好。由此诞生了 sorcery 项目：一个以静态站点生成器为核心架构的 Git 仓库查看器。收到仓库更新时，它预渲染概览页、各分支目录树和语法高亮源码为 HTML，后续请求仅需 sendfile，几乎零计算开销，天然抗爬虫。历史浏览则直接暴露 .git 目录，配合一个轻量 JavaScript 只读 Git 客户端在浏览器端渲染；为减少高延迟下的往返，服务端额外提供按对象 ID 批量返回 git object bundle 的接口，将多次请求合并为一次。sorcery 刻意省略用户账户、密钥管理和 issues 等协作功能，写入仅通过 git over ssh 完成，公开部署的安全性等同于 sshd。前端使用作者自研微框架，项目概览页仅传输约 9KB 压缩 JS。作者仍喜欢社区型 forge，但个人项目只需一个能推送代码、手机可浏览、可分享链接的轻量服务，未来计划加入 CI 注解支持，并可能将仓库查看器扩展为更完整的 forge 项目。

## 3. Golang开发者为何应尝试Odin语言

- 原始链接: <https://rm4n0s.github.io/posts/2-go-devs-should-learn-odin/>
- 英文标题: Golang developers should try Odin

一位拥有十年Golang经验的开发者撰文推荐Odin语言，认为其可作为后端开发中Go的潜在替代。作者指出Go存在GC性能开销、CGO编译缓慢、内存泄漏难排查、错误类型设计不佳等痛点。Odin被概括为「60%的Go + 20%Go缺失特性 + 10%数组编程 + 10%底层与FFI」，拥有类似Go标准库的核心库，已在JangaFX和ChiAha等项目中投入生产。语言层面，Odin仅31个关键字，配合#directive与@attribute，泛型设计优于Go，无包管理器（包即目录），编译命令与Go类似。因采用手动内存管理，Odin没有GC、闭包、Goroutine和Selector，但作者逐一演示了替代方案：用Enum/Union/Struct构建可追溯的错误树替代Go的error；用Arena_Allocator和defer规避内存泄漏；用struct内嵌proc指针模拟接口；用thread pool加channel加union模拟Goroutine与Selector。作者强调Odin无官方文档，需通过阅读源码和demo.odin学习，但语法对Go开发者极为友好。文章整体立场积极，鼓励Go社区关注Odin的演进潜力。

## 7. Heol：运行于 Uxn 虚拟机的 16 位 Lisp 系统

- 原始链接: <https://wiki.xxiivv.com/site/heol.html>
- 英文标题: heol

Heol 是一个专为 Uxn 虚拟机设计的 16 位 Lisp 系统，提供 Varvara 绑定。其执行模型基于表达式归约：原子返回自身值，列表视为函数应用（首元素为函数名，其余为参数，参数先求值再传入）。文章系统介绍了 Heol 的核心语法与内置操作：列表构造与解构（cons、car、cdr）、逻辑判断（eq? 比较原子、if 条件分支，真值为 #t，假值为空列表 ()）、前缀算术（+、-、*、/、% 支持多操作数）、过程定义（lambda 生成闭包、define 全局绑定、quote 阻止求值）。值得注意的是，Heol 没有显式的序列操作（如 progn、begin），而是用 and 实现：and 在遇到第一个空值时短路求值，但仍可用于「打印一个值再返回另一个值」等场景。文章给出了倒计时循环和阶乘递归两个完整示例，展示了如何用 if、and、lambda 组合出迭代与递归逻辑。文末汇总了全部内置形式，包括 eval、let*、or、not、dotimes、print 以及用于向 Varvara 端口发送数据的 deo。整体而言，Heol 以极简的 16 位设计在 Uxn 的受限环境中实现了完整的函数式 Lisp 编程能力。

- 英文标题: Can a regex match valid card numbers?

本文探讨了一个看似简单却极具深度的问题：能否用正则表达式（regex）通过Luhn算法验证信用卡号码的校验位。作者首先介绍了信用卡号码结构（IIN前缀、账户ID、校验位）及Luhn算法原理，随后从形式语言理论出发，论证了满足Luhn校验的数字集合构成一个正则语言，因此必然存在对应的确定性有限自动机（DFA）和正则表达式。作者构造了一个含100个状态、1000条转移的DFA，其状态空间为偶数与奇数长度字符串的模10部分和的笛卡尔积，转移函数通过「Luhn加倍」函数实现。借助greenery库的Brzozowski代数方法，作者成功将该DFA转换为正则表达式，但结果极为庞大：偶数长度正则约3200万字符，奇数长度约4800万字符，在M1 Air上各需约20分钟生成。Python的re模块可执行该正则，而grep或ripgrep会因内存耗尽被终止。文章还讨论了实际意义：PCI DSS合规要求下，日志中可能意外泄露支付信息，但作者强调不应依赖regex来检测或清洗此类敏感数据。最后列出了后续计划，包括DFA可视化、归纳证明正确性与最小性、Haskell实现等。

## 9. C++ 中的惰性求值：用 Lazy 模板避免不必要的计算

- 原始链接: <https://cpp-rendering.io/being-lazy-in-c/>
- 英文标题: Being lazy in C++

本文讨论了 C++ 中一个常见的性能陷阱：std::optional::value_or() 的实参在调用前即被求值，导致即使 optional 已持有值，传入的复杂计算仍会被执行，违背了「不为不使用的功能付费」的原则。C++23 的 or_else(f) 可解决该特定场景，但 value_or、std::map::try_emplace 等接口普遍存在此问题，因此需要通用方案。作者提出一个极简的 Lazy 模板：将计算封装在 operator T() 转换运算符中，利用 value_or 仅在 fallback 分支才将参数转换为 T 的特性，使计算仅在真正需要时才触发。示例中，对已有值的 optional 调用 value_or(Lazy{complex_computation}) 不再触发计算，输出符合预期。文章同时指出两个局限：一是无记忆化，同一 Lazy 对象被多次使用时计算会重复执行；二是转换运算符无约束，若(Lazy{...}) 等布尔上下文也能编译通过，可能产生意外行为。作者计划在下一篇文章中构建带记忆化、仅允许转换到目标类型的更健壮惰性类型，并测量其运行时开销。

- 原始链接: <https://blog.jchw.dev/wrong-number/>
- 英文标题: Sorry, Wrong Number: Debugging a Crash under Wine (2022)

作者记录了一次在 Wine 下调试 MinGW-w64（GCC 10.3）编译程序崩溃的完整过程。程序在调用 png_read_info 时触发执行权限违规，RIP 落在未映射地址。作者先后使用 WINE_DEBUG 日志、Valgrind 和 rr 记录重放工具排查，最终通过反汇编发现 libpng 中一条调用 crc32 的 CALL 指令被篡改，目标地址偏移了 0x100000000。深入分析后定位到 MinGW 的「伪重定位」机制：该机制为兼容未标注 __declspec(dllimport) 的 UNIX 风格代码，在 DLL 入口时遍历重定位表，将指针替换为相对于 IAT 条目的地址。作者用 GDB 连接 Wine 并设条件断点，逐步跟踪伪重定位代码，发现其符号扩展逻辑在 Wine 环境下因 IAT 条目值与预期不符，导致最终写入的 32 位地址多出 0x100000000，从而将 CALL 指向了无效地址。文章同时科普了 PE 与 ELF 重定位差异、IAT 桩函数、伪重定位的概念及动机，展示了 rr、GDB、IDA 等工具在 Wine 调试中的组合用法。

## 16. 没人愿意为开源付费，但我们可以强制他们

- 原始链接: <https://seldo.com/posts/nobody-pays-for-open-source-we-can-force-them-to/>
- 英文标题: Nobody pays for open source. We can force them to

作者从进化生物学中的「鹰鸽模型」切入，论证开源免费是软件市场的进化稳定策略：React、Elastic、HashiCorp、Redis 等公司尝试以许可证收费，均被社区 fork 击败后被迫回退。然而免费层以维护者持续燃烧为代价——60% 维护者无薪，近 60% 想过辞职，xz 后门事件暴露了单人维护的致命脆弱。作者指出，速度变化（npm 生态、漏洞利用加速）让问题恶化，但所有自愿性方案（GitHub Sponsors、基金会、企业捐赠、Tidelift、德国主权技术基金、Mozilla）均无法规模化。关键转折在于：公司其实每年在开源供应链上花费超十亿美元（JFrog 5.32 亿、Snyk 3.26 亿、Docker 2.07 亿），只是付给了注册表镜像和漏洞扫描等中间层，而非维护者本人。作者区分了「代码游戏」（免费必赢）与「供应游戏」（默认者赢），指出注册表是两者唯一交汇点，也是唯一无法靠复制绕过的收费层。文章最终指向在注册表层强制将费用传导给维护者的可能路径，但正文在此处截断，具体方案未完整展开。

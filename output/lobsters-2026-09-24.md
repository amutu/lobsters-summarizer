## 1. Radicle 网络协议安全漏洞披露

- 原始链接: <https://radicle.dev/2026/09/23/disclosure-of-vulnerability-in-network-protocol.html>
- 英文标题: Radicle: Disclosure of Vulnerability in the Network Protocol

Radicle 披露其网络协议存在两项关键漏洞：一是节点间通信未加密、未认证，数据以明文传输，路径上的攻击者可读取传输内容；二是连接握手中的对等认证存在缺陷，攻击者可冒充白名单中的 Node ID，直接拉取仅对授权节点开放的私有仓库。两项漏洞结合后，路径上的攻击者既能窃听又能冒充，威胁显著放大。所有已发布版本均受影响，但存储层的 Git 对象与签名引用仍受校验，攻击者无法伪造代码或身份。官方建议用户立即停止通过网络使用私有仓库，使用「rad block」命令阻止节点继续分发，并轮换可能已泄露的凭据；Tor、I2P 等叠加网络无法防护对等冒充，不能作为替代方案。修复方案为将现有基于 Noise 的自定义协议替换为开源 P2P 网络栈 iroh，该变更不向后兼容，将触发大版本升级并导致网络分区。官方强调在修复发布前先行公开披露，以便用户及时评估并采取行动。

## 2. 我希望网状网络采用消息签名而非加密

- 原始链接: <https://andanti.no/blog/SignedMesh.html>
- 英文标题: I want my mesh networks to be signed, not encrypted

作者是一名业余无线电爱好者，关注近年来兴起的用户友好型网状网络（如Meshtastic和Meshcore），认为这些低功耗（0.5W）设备在拥挤频段上实现广域通信令人印象深刻，但指出这类实验本质上属于业余无线电范畴，理应使用业余频段。然而，使用业余频段的前提是传输不得加密，而Meshtastic和Meshcore默认加密且难以关闭，给业余无线电爱好者带来不便。作者提出一种替代方案：让每条消息以明文传输但附带数字签名。签名的好处包括：确认通信对方身份、防止他人冒充、中继站可过滤无证操作员以简化合规、消息可见性降低新参与者加入的门槛。缺点同样明显：除「不参与」外没有隐私保护；他人可将带签名的消息公开；获取无线电执照需通过考试并缴费，构成入门壁垒；验证签名需要公钥基础设施（临时密钥交换扩展性差，证书机构则涉及政治因素）；每条ed25519签名额外占用64字节带宽。对于读者可能提出的「为何不用APRS」，作者以一句俏皮话回避。文章最终呼吁网状网络走向开放透明，并邀请读者讨论。

## 3. 我心目中的GNOME大模型政策

- 原始链接: <https://blogs.gnome.org/alatiera/2026/09/23/the-gnome-llm-policy-that-i-want/>
- 英文标题: The GNOME LLM Policy That I Want

本文针对KDE因AI政策提案引发的争议，提出作者心目中GNOME应采取的大模型（LLM）政策。作者认为此类政策的核心目标是塑造社区社会规范、传递价值信号，而非微观管理开发流程。政策核心条款为：禁止使用LLM创建或修改任何提交至GNOME或其基础设施的内容，违者可能被要求举证或遭封禁。作者还列出贡献者准则草案，包括须能个人解释修改、展示领域知识、解决根本问题而非表面症状、尊重其他贡献者时间、不得通过聊天机器人或自动化系统冒充本人。理念层面，作者强调GNOME的本质是集体创作社区，价值在于人与人之间的联结与共同成长的乐趣，而非单纯软件产出；面对AI时代，需营造有吸引力的社交空间以留住年轻人才，减少对少数企业的依赖。关于执行，作者坦言政策无法完全强制，但如同行为准则，其意义在于明确表达社区价值观，面向大多数不会尝试欺骗的贡献者。文末附有「Free Palestine」声明。

## 5. 放弃Scientific Linux是一个错误

- 原始链接: <https://blog.melashri.net/posts/scientific-linux-mistake/>
- 英文标题: Abandoning Scientific Linux Was a Mistake

作者借CERN将加速器控制系统的2200余台工业电脑迁移至Debian 13一事，回顾十多年前CERN与Fermilab放弃Scientific Linux的决策，认为这是一次战略失误。Scientific Linux并非简单的「RHEL换皮」，而是为高能物理社区提供了机构独立的Enterprise Linux实现，维系了人员、流程与制度性知识。2014年CentOS与Red Hat合并后，社区转向CentOS；2019年Fermilab宣布不再发布Scientific Linux 8。然而2020年Red Hat将CentOS Linux改为CentOS Stream，社区被迫再次寻找独立发行版，2022年转向AlmaLinux；2023年Red Hat又改变源码分发模式。作者指出，维护成本可见，但独立发行版的「期权价值」难以量化——它恰在主平台假设突变时显现。CERN加速器团队因RHEL 9/10提升x86-64基线而选择Debian，正是这一教训的延续。核心观点是：标准化不等于单一化，研究机构在评估退役开源基础设施时，应计入治理风险、迁移成本、知识流失及可信替代方案的价值，而非仅计算节省的人时。

## 6. Zig 之旅：面向系统编程的三层进阶建议

- 原始链接: <https://kristoff.it/blog/the-zig-journey/>
- 英文标题: The Zig Journey

Loris Cro 在慕尼黑 Zigtoberfest 会议上的演讲中，将 Zig 的学习路径分为三个层次。面向新手，他建议培养「面向目标计算机而非框架」的思维：把问题建模为目标系统提供的操作序列，而非堆叠高层依赖。系统编程不是工作类别，而是一种看待问题的方式；仅会拼接依赖无法支撑创新，唯有掌控核心功能才能提供真正新颖的体验。面向中级用户，他强调深入设计代码的「其余一切行为」，例如在 Zig 构建脚本中直接集成 C/C++ 依赖，避免对包管理器的隐性耦合，实现「从所有系统构建到所有系统」的黄金标准；他还创建了 All Your Codebase 组织来集体维护 C/C++ 项目的构建脚本。面向高级用户，建议是选定一个热爱的项目并坚持完成，达到功能与非功能层面的完整。文章指出，这一路径并非 Zig 独有，但 Zig 的工具链与社区有意帮助开发者走通这条路。作者以「Hello Systems」中的静态站点生成器为例，说明高层语言在超越表层功能后难以精细调优并发，过度依赖抽象会使人脱离机器实际能力。他进一步指出，深入理解系统不仅有助于更好地使用依赖，也是有效驾驭 LLM 的前提——若不知何为可能，便无法评判依赖或智能体产出的质量。演讲尾声，约百人的会场几乎全员举手表示在 Zig 之旅中取得进展，作者呼吁读者参与 Zig Day 等活动并支持 Zig 软件基金会。

## 7. 更廉价的 LLM 标注方案

- 原始链接: <https://entropicthoughts.com/cheaper-llm-labeling>
- 英文标题: Cheaper LLM labelling

作者在一个小项目中需要将约21,000个 git commit 标注为「维护」或「新开发」。直接调用 gpt-5.6 Luna 等低成本 LLM 虽然准确，但每次调用约1.5秒的延迟使整体耗时过长。为此，作者设计了一个「快慢结合」的标注架构：用一个基于词袋特征的逻辑回归作为快速分类器，仅在其置信度足够高（概率低于0.08或高于0.92）时直接给出标签，否则回退到 LLM 获取标签，并将结果反哺训练快速分类器。整个逻辑回归类仅用约40行纯 Perl 实现，支持流式梯度下降训练，无需任何数学库。作者还引入 Platt scaling 改善校准，并通过将 commit 哈希映射为确定性随机数实现标签缓存，避免重复调用 LLM。最终快速分类器承担了约46%的标注任务，使整体速度大致翻倍。文章还展示了学到的判别性词汇（如 fix、bug 对应维护，add、implement 对应新开发），并附上了完整的 LLM 提示词。

## 9. 不要在类型系统中做别名推理——Futhark 原地更新的教训

- 原始链接: <https://futhark-lang.org/blog/2026-09-22-aliasing.html>
- 英文标题: Do not let your type system reason about aliasing in your programming language

本文是 Futhark 语言作者对 1.0 版本规划的后续讨论，核心主题是：类型系统不应承担别名（aliasing）推理的重任。Futhark 最独特的特性是原地更新（如 A with [i] = v），它承诺仅以单元素代价完成语义上的数组拷贝，但要求类型检查器静态保证旧值在任何后续路径上不再被引用（即「消费」规则）。为实现这一点，编译器必须为每个变量维护别名集，并据此推导函数参数消费效果（diet）、返回值新鲜性（freshness）、元组组件互斥、高阶函数闭包别名传播、以及抽象类型下全局常量别名等规则。作者指出，一个本应简单的类型检查器 typo（忽略抽象类型全局变量的别名）一旦修复，会使大量模块泛型代码（如 add_one）变为类型错误，暴露出别名追踪与语言简洁性之间的深层矛盾。文章逐一分析了函数、元组、高阶函数、多态与抽象类型各自引入的额外约束，并探讨了用「位置化别名集」改进元组处理、利用参数多态性减少保守性等方向。最终结论是：除非有充分理由，否则不要在类型系统中引入别名推理，其带来的复杂性爆炸远超收益；Futhark 选择将别名机制限制为支持原地更新这一最小必要特性，而非像 Rust 那样构建完整的生命周期体系。

## 10. GitHub Wiki 是一种反模式

- 原始链接: <https://michaelheap.com/github-wiki-is-an-antipattern/>
- 英文标题: The GitHub wiki is an anti-pattern

作者认为在 GitHub 项目中使用 Wiki 存放文档是一种反模式。Wiki 唯一的好处是从仓库任意位置可一键访问，但缺点远多于优点：文档无法与代码一同版本控制；克隆仓库时文档不可用（Wiki 需单独克隆，属隐藏功能）；文档编辑无法纳入 Pull Request 审查流程；无法借助 GitHub Actions 对文档进行 Vale 等 lint 检查；无法使用 VS Code 等本地工具；品牌定制能力有限；且不支持图片上传。作者推荐将文档放在 /docs 文件夹中，配合 GitHub Pages 发布，初期可使用 just-the-docs 主题或 Hugo 等构建工具，并在 Wiki 中仅保留一个引导页指向托管文档。作者强调不要使用 gh-pages 分支，以免文档脱离代码版本管理。随着项目成长，文档最终会超出单个文件夹的承载能力，届时可平滑迁移至独立仓库，拥有独立的构建流程和审查规范。由于团队已习惯在仓库中协作文档，这一过渡对贡献者而言几乎无感。文章以「投入产出比」为线索，主张在产品开发早期用 /docs 文件夹是性价比最高的文档管理方式。

## 11. Redis 哈希槽：一次配送缓存优化的踩坑与修复

- 原始链接: <https://blog.verygoodsoftwarenotvirus.dev/posts/2026/09/23/why-didnt-anybody-tell-me-about-hash-slots/>
- 英文标题: Why didn't anybody tell me about Redis hash slots?

作者在一家即时配送平台负责骑手匹配服务，核心瓶颈是路由引擎延迟。由于附近骑手的路线估算高度重复，团队引入 Redis 缓存，以 H3 六边形网格对坐标去重，用 MSET 批量写入。上线后却发现严重性能问题：Redis Cluster 将 16384 个哈希槽分配给各节点，MGET/MSET 要求所有 key 落在同一槽，而每个 key 含唯一 hex ID，导致一次批量读被拆成数十次单 key 请求。作者借助 Redis 的 hash tag 机制（花括号内文本单独参与哈希）解决该问题，通过暴力搜索整数使标签均匀分布到各节点，将批量请求压缩为每节点仅一次往返。此外还按槽分组替代按块切分，避免同一节点被串行处理；用 EVAL 脚本替代 MSET 以支持过期时间；将缓存值从 JSON 改为 CSV 以降低 CPU 开销。文章最终反思：应先搭建基准测试框架再进入开发，且当数据规模 n 确实很大时，必须采用更精巧的算法而非简单方案，呼应了 Rob Pike 的编程准则。

## 12. 如何在谈论「AI」时避免拟人化

- 原始链接: <https://buttondown.com/maiht3k/archive/how-to-talk-about-ai-without-adding-to-the/>
- 英文标题: How to talk about "AI" without adding to the anthropomorphization

本文是Emily M. Bender与Nanna Inie在Tech Policy Press发表的评论，延续其关于「AI」拟人化语言的讨论，提出一套系统性的去拟人化表达方案。作者将拟人化语言分为七类——认知与认知产物、情感、沟通、能动性、人类角色类比、名称与代词、生物隐喻——并逐类给出替代说法。核心原则包括：以功能性描述替代认知隐喻（如「图像识别」改「图像标注」、「幻觉」改「不良输出」、「人工智能」改「概率自动化」）；将能动性归于人而非系统（如「AI智能体」暂称「概率性、未经验证的软件操作器」）；避免将系统置于与人对等的沟通或角色位置（如「提示」改「文本输入」、「回答」改「输出」）。作者承认替代表达可能更冗长、初用略显笨拙，但认为这恰恰促使人们停下来思考技术实际做了什么。文章鼓励读者在日常对话中尝试这些表达，并以「做那根插在泥里的棍子」比喻在语言习惯中为他人开辟新路径，同时推广其新书《The AI Con》。

## 13. 无需中间 AST 的 JSON 对象解析

- 原始链接: <https://arthi-chaud.github.io/posts/json-ir/>
- 英文标题: Parsing JSON Objects without intermediate ASTs

本文探讨 JSON 解析中中间表示（IR，通常为 AST）带来的额外内存分配与计算开销，并提出一种绕过 IR 直接生成领域数据的方法。传统流程为「字节串 → JSON AST → 领域对象」两步，作者利用 Haskell 的惰性求值，将目标结构体所有字段初始化为 undefined，解析过程中逐字段填充，同时用一个 Word64 位集追踪各字段是否已设置；解析结束后检查位集是否归零以判断完整性，缺失的 Maybe 字段则置为 Nothing。解析器通过 Template Haskell 在编译时从数据类型的结构自动生成，无需手写。作者基于 flatparse 库实现了概念验证，并用 Criterion 进行微基准测试：解析与 Album 规模相近的对象时，无 IR 版本耗时约 314 纳秒，而主流库 aeson（有 IR）约 1051 纳秒，差距接近 3 倍；含嵌套列表的大对象差距同样显著。作者强调 IR 本身并非缺陷，它解耦了解析与校验、提升可维护性；本文旨在揭示 IR 的运行时代价，并展示一种以复杂度换速度的替代思路。文中还提及 Rust 的 serde 框架通过分阶段编程将 IR 提升至编译期以规避此开销，在严格语言中可用 memset 将字段置零作为替代手段。

## 15. Apache Parquet 中的自适应无损浮点编码 ALP

- 原始链接: <https://parquet.apache.org/blog/2026/09/22/alp-adaptive-lossless-floating-point-encoding-in-apache-parquet/>
- 英文标题: Adaptive Lossless Floating-Point Encoding in Apache Parquet

Apache Parquet 新增了一种名为 ALP（Adaptive Lossless floating-Point Encoding）的轻量级浮点编码，针对以 32 位 FLOAT 或 64 位 DOUBLE 存储的十进制数值（如货币、地理坐标、科学测量）提供接近 zstd 的压缩比，同时实现约 10 倍于 zstd 的解码速度、数千倍的随机访问速度，并天然支持 SIMD 与 GPU 并行解码。ALP 的核心思路是将每个向量（8 至 32K 个值）中的浮点数通过共享的指数 e 和因子 f 转换为整数，再减去帧参考值后以固定位宽进行位打包；无法无损还原的值及 NaN、±Infinity 等特殊值作为「异常」单独存储，从而保证编码完全无损。该编码解决了传统重型压缩器在解码速度、随机访问和数据依赖性方面的三大瓶颈。ALP 源自 CWI 团队 2024 年 SIGMOD 论文，已被 Vortex、Lance 等格式采用，并于 2026 年 9 月随 parquet-format 2.14.0 正式发布，Rust 实现（parquet 60.0.0）已率先支持。对于向量嵌入等指数范围极广的数据，仍建议使用 PLAIN 或 BYTE_STREAM_SPLIT 配合 ZSTD 等通用压缩。

## 1. Rust 项目采用 LLM 使用政策

- 原始链接: <https://blog.rust-lang.org/inside-rust/2026/08/05/rust-langrust-is-adopting-an-llm-policy/>
- 英文标题: rust-lang/rust is adopting an LLM policy

2026年8月5日，Rust 项目的五个团队正式通过了一项由 Jynn Nelson 起草的 LLM 使用政策，适用于 rust-lang/rust 单一代码库。该政策并非官方对 LLM 的总体立场，也不覆盖整个项目，而是针对特定问题：过去 LLM 生成的代码和评论给社区带来了三大挑战——打磨过的技术产品不再代表作者的努力和理解；代码易写性加剧了审查带宽不足；机械复制粘贴 LLM 输出浪费评审者时间。政策核心原则是：可以用 LLM 来回答问题、分析、提炼、检查、建议和审阅，但不能用于‘创造’内容。公开的 LLM 内容必须明确披露，代码变更需遵循更高标准（必须带测试、禁止关键正确性改动等），审阅者有权关闭不合规的 PR，且禁止因使用 LLM 而骚扰他人。政策也承认部分条款无法强制执行，但希望建立清晰的明线规则，便于社区协作和未来调整。对贡献者的影响包括：报告 issue 须披露 LLM 参与，PR 模板将询问是否使用 LLM，审阅者可引导作者至 #llm-mentoring 频道。该政策旨在收集数据，为未来项目级政策提供依据。

## 2. 安全很难，各位

- 英文标题: Security is Hard, Y’all

本文是作者对软件安全复杂性的深刻反思，标题直白地表达了核心观点：安全工程远比表面看起来困难。文章指出，安全并非简单叠加防御措施，而是需要面对无数相互作用的脆弱环节，任何单一漏洞都可能被攻击者利用。作者强调了现实世界中安全威胁的动态性，攻击者不断演化手法，而防御者却受制于资源、时间和兼容性约束。文中特别讨论了浏览器作为安全边界所面临的挑战，比如同源策略、权限管理、第三方库风险以及供应链攻击。作者认为，所谓“安全软件”只是一个不切实际的期望，因为程序由人编写，注定存在缺陷，真正的安全是一个持续的风险管理过程，而非可一次性达成的目标。文章以幽默而无奈的口吻收尾，呼吁同行保持谦逊，认识到安全工作的艰难本质，并建议以纵深防御、及时修复和持续监控来降低风险，而不是追求绝对安全。整体上，这是一篇面向技术从业者的行业观察随笔，强调务实态度。

## 3. Lua 社区需要学会向前看

- 原始链接: <https://hisham.hm/2026/08/04/the-lua-community-needs-to-learn-to-move-on/>
- 英文标题: The Lua community needs to learn to move on

文章探讨了 Lua 社区长期固守旧版本的问题。作者提到 LuaJIT 维护者 Mike Pall 删除旧版本标签，以强制用户升级，虽看似激进，但反映了他对大量项目仍停留在十年旧版本的挫败感。类似情况也出现在 LuaRocks，维护者仍收到针对 2012 年版本的 bug 报告。自 Lua 5.2 与 LuaJIT 分流以来，社区形成了永远支持所有旧版本的趋势，库作者要同时测试 Lua 5.1 至 5.5 及 LuaJIT 多种变体，负担沉重。作者认为，对于可扩展语言，应像其他脚本语言一样，只支持最新的 PUC-Rio Lua 和最新的 LuaJIT。他承认自己也曾参与维护兼容层，如今则通过开发 Teal 语言来弥合版本差异，让用户一次编写、生成各目标版本的 Lua 代码。作者呼吁库作者效仿 Roberto（Lua 之父）和 Mike，对旧版本正式停止支持（EOL），并指出旧版本应搭配旧生态，而不应迫使维护者永远承担超过 20 年的兼容负担。

## 4. 生而对抗：为何业余编程社区强烈抵制LLM使用

- 原始链接: <https://blog.fogus.me/llm/born-against.html>
- 英文标题: Born Against, or why hobby programming communities are aggressively against LLM usage

本文作者由一则关于国际象棋引擎开发的GitHub讨论引发思考，探讨了业余编程社区为何对LLM（大语言模型）的使用日益敌视。作者指出，在OSDev、LangDev、TxtDev、EmuDev、RLDev、demoscene、代码高尔夫等小众社区中，普遍存在一种共识：这些领域积累的知识来之不易，而使用LLM完全错失了重点。在这些社区中，掌握一项艰难领域的过程本身就是成果，能跑起来的代码只是副产品。作者观察到，即便某些社区早期曾真诚地尝试与LLM互动，也很快因LLM使用者缺乏深层理解，以及社区内认为此举等于作弊的激烈反对而夭折。这些社区历史上就有强烈的守门员文化和极为缓慢的进展，因此有人想以“破墙者”姿态快速获得认可，反而适得其反。文章强调，在这些圈子里，尊重靠多年参与论坛、分享优雅代码、展现真实好奇心并传递深层领域知识来赢取。社区并不在意代码是否运行，而在意你是否理解它为何以及如何运行。作者认为，LLM的最佳定位是“力量倍增器”而非“替代品”，在专家手中可以成为杠杆；但在这些以学习本身为目标的社区里，用LLM直接生成最终成品并不能让人成为工匠，反而剥夺了手艺。最后作者补充，专业能力并不能天然免疫于被LLM误导。

## 6. 居中一个 div 终于变简单了，但浏览器侧边栏又搞砸了

- 原始链接: <https://seg6.space/posts/center-div/>
- 英文标题: we finally learned to center a div, then browsers added sidebars

文章讨论了一个现代 CSS 居中问题：用 Grid 布局轻松实现 div 居中后，浏览器侧边栏和开发者工具却让居中出现偏差。作者发现，当浏览器窗口开启侧边栏时，页面实际上是在剩余可视区域（webview）内居中，而不是在整个浏览器窗口居中，导致视觉上并不居中。作者尝试用 JavaScript 的 innerWidth 和 outerWidth 计算浏览器 UI 宽度，并据此调整元素位置，但 DevTools 停靠在不同侧时无法区分总差值在左右各占多少。最终作者利用指针事件的 screenX 与 clientX 坐标，结合缩放比例，准确计算出 webview 在窗口中的左右偏移，从而实现真正意义上的窗口居中。作者将这个方案做成浏览器扩展 center, actually，让用户选择要居中的元素，逐层修正侧边栏带来的偏移。文章强调这种修正应是用户主动选择，而非网站默认行为，并指出在空间不足时应避免隐藏内容。

## 7. Soppo：补全Go缺失特性的语言

- 原始链接: <https://soppolang.dev/>
- 英文标题: Soppo - Go, with the features it's missing

Soppo 是一款与 Go 语法高度兼容的编程语言，旨在为 Go 补充缺失的类型安全与易用性，同时保持完整互操作性。它允许开发者直接使用现有 Go 库和工具，并能在现有项目中渐进式引入。其核心特性包括：枚举与结构体变体配合模式匹配，编译器会确保所有分支都被处理，避免遗漏；通过 `?` 操作符简洁地传播错误，减少重复的 `if err != nil` 代码，同时保留显式错误处理能力；引入编译期 nil 安全追踪，在空值检查后自动收窄类型，避免空指针崩溃；错误信息清晰直观，能展示相关代码、指出问题位置并给出修复建议。安装方面推荐使用 SOPMOD 版本管理器，它同时管理 Go 工具链，也可通过 Cargo 直接安装 `sop` 二进制。Soppo 在保留 Go 熟悉语法和生态的基础上，提升了开发体验与代码可靠性。

## 9. 比 Ninja 还快：build2 构建性能实测

- 原始链接: <https://build2.org/blog/faster-than-ninja.xhtml>
- 英文标题: Faster Than Ninja

作者用 Xerces-C++ 项目对比了 build2 与 Ninja 的从零构建性能。Ninja 本身仅需 3.4 秒，但必须先由 CMake 生成构建文件，耗时 15.6 秒，实际总等待约 19 秒。build2 在相同配置下为 3.8 秒，启用只读模式关闭更精确的变更检测后降至 3.4 秒，再禁用文件缓存压缩后达到 3.355 秒，比 Ninja 快约 2.2%。值得注意的是，build2 还承担了更多工作，比如在构建时生成版本头文件、提取编译器身份与搜索路径等。作者认为其速度优势来自三个关键设计：积极缓存已发现的信息、多线程并行执行内部管理任务（如解析头文件依赖）、以及采用编译前显式的部分预处理来获取依赖信息并复用预处理结果。文章也给出了完整的基准测试环境与命令，供复现验证。

## 10. Nix 沙箱是隐藏输入

- 原始链接: <https://fzakaria.com/2026/07/30/the-nix-sandbox-is-a-hidden-input>
- 英文标题: The Nix sandbox is a hidden input

文章指出 Nix 的默认构建模型是输入寻址的，即存储路径哈希由构建配方（derivation）决定，而非输出字节，因此只能保证可重复性，而非逐位可复现。然而，Nix 的沙箱配置（sandbox-paths）是一个在 derivation 之外、却可能影响构建输出的隐藏输入。作者通过一个小例子演示：一个无依赖的 derivation 会检查 /truth 文件，若不存在则输出 4；通过 extra-sandbox-paths 挂载一个内容为 5 的 /truth 后，同一 derivation 构建出的输出变为 5，但输出哈希完全不变。这意味着两个人可以评估出字节相同的 .drv，却执行不同的实际构建步骤并得到相同哈希。与 /dev/random 或 date 等明显的不确定性不同，检查文件存在性极其隐蔽，难以审计。更严重的是，默认的 sandbox-paths 并非常量，而是 Nix 二进制编译时的属性；不同构建方式的 Nix（例如是否提供 /bin/sh）会导致同一 derivation 在不同机器上产生不同行为。若将 sandbox-paths 纳入 derivation 哈希，则会破坏二进制缓存共享，因为各机器的基础路径不同。作者在实际构建 OpenJDK 时遇到此问题：Guix 派生的构建假设无 /bin/sh，而 Nix 沙箱默认提供 /bin/sh，导致脚本意外执行并产生损坏输出，且已上传到缓存。这体现了“你不能信任非完全自己创建的代码”这一观点。

## 17. 不要提前停止：以内存速度对源码进行大小写折叠

- 原始链接: <https://github.blog/engineering/architecture-optimization/dont-stop-early-case-folding-source-code-at-memory-speed/>
- 英文标题: Don't stop early: Case-folding source code at memory speed

该文章来自 GitHub 工程博客，讲述了他们为代码搜索优化 Unicode 大小写折叠（case folding）的过程。在源码中，非 ASCII 字符（如注释里的引号、破折号）很常见，传统 SIMD 实现一旦在数据块中遇到这类字节就会提前中断，退回到缓慢的标量路径，导致性能瓶颈。作者提出“不要提前停止”的思想：即使块内含有非 ASCII 字节，也继续用 SIMD（如 AVX-512）以 64 字节为单位批量处理；先对 ASCII 字母做快速折叠，再通过掩码和查找表单独修正非 ASCII 字节。这样避免了频繁分支跳转和流水线停顿，使整体处理速率接近内存带宽。文章还论述了 UTF-8 边界处理、简单折叠与全折叠的取舍，以及该技术如何集成到 GitHub 搜索索引中。最终，这一优化显著降低了大小写不敏感搜索的成本，为大规模代码搜索提供了高性能基础。

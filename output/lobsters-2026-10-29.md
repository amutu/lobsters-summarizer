## 1. AlpineBSD：基于 NetBSD 内核、拒绝 AI 生成代码的操作系统

- 原始链接: <https://wiki.alpinebsd.org/>
- 英文标题: AlpineBSD

AlpineBSD 是一个基于 NetBSD 内核、用户空间受 Alpine Linux 启发的操作系统，其核心目标是尽可能减少 AI 生成软件的使用，基础系统和主包仓库中不包含任何大语言模型输出，并设有专门的 AI 使用政策。该项目目前仍处于开发阶段，尚未提供安装器，仅有一份面向高级用户的安装指南。在硬件层面，AlpineBSD 沿用 NetBSD 内核、libc 及 mount 等基础工具，但 NetBSD 的硬件兼容性远不及 Linux，用户需查阅 NetBSD 支持的硬件列表，尤其是笔记本设备。在用户空间方面，AlpineBSD 采用 apk-tools 包管理器和 busybox，整体偏向 GNU 生态（例如优先使用 GNU make 而非 BSD make）。它并非 Alpine Linux 的分支，包集合为原创，但许多包最终源自 Alpine 的 aports 项目。初始化系统上，Alpine Linux 使用 OpenRC，而 AlpineBSD 当前采用 s6，并计划将 OpenRC 作为可选方案加入。总体而言，AlpineBSD 试图在 NetBSD 的稳定性与 Alpine Linux 的轻量理念之间找到平衡，同时以「零 AI 代码」作为差异化定位。

## 2. 这不可持续：2026年网络安全危机下的防御困境

- 原始链接: <https://www.netmeister.org/blog/defense-ddos.html>
- 英文标题: This is not sustainable

本文是Johannes Schauer于2026年10月27日发表的评论，以讽刺笔调指出当前网络安全态势已不可持续。作者列举了同一周内并发爆发的多起重大事件：「PwnEscape」虚拟化逃逸漏洞、eMudhra供应链攻击、影响「70%网站」的PHP漏洞、以及Node.js中brotli解码器RCE，并指出这些事件在过去各需一年才能消化一次。核心论点是：漏洞发现与披露速度已远超防御者应对能力，而补丁部署、攻击面枚举和风险评估才是真正瓶颈，而非修复本身。作者批评AI公司通过大规模漏洞披露制造恐慌再出售防护服务，本质是「制造疾病再卖药」；同时指出防御端出现去技能化趋势——AI生成的冗长报告淹没关键信息，防御者盲目用AI生成exploit却无法理解原理，事件响应团队在多重危机中疲于奔命。作者坦言无解：AI修bug超过半数会引入新问题，基础设施改造需数年且缺乏资金，唯一现实选择是限制爆炸半径、假设已被入侵、检测利用行为，即多年前提出的「零信任」思路，但该方向长期得不到预算支持。全文以「晚安，祝好运」作结，基调悲观而尖锐。

## 3. C语言错误处理：用goto集中资源清理的优雅之道

- 原始链接: <https://thestateofinahaze.net/blog/c-goto-considered-totally-sick/>
- 英文标题: GOTO Considered Totally Sick (for error handling in C)

作者从Go和Zig转回C语言后，深感缺少defer/errdefer机制带来的痛苦。Go中用defer自动释放锁，Zig中用errdefer按逆序回滚已分配内存，而C语言中每个错误分支都要手动重复清理代码，极易出错且难以维护。受John Carmack关于「控制流应向前」的邮件及Henry Spencer对飞行软件控制流描述的启发，作者领悟到：将资源清理集中到函数末尾的单一goto标签处，相当于一个伪errdefer。重写后的示例中，所有错误路径统一跳转到free_mem标签，只需一处维护清理逻辑，可读性和可维护性大幅提升。作者还提到可用多个标签分段清理部分资源。更新部分补充了用calloc替代malloc以防乘法溢出、简化循环结构等建议，并指出Linux内核编码风格指南也推荐此模式。文章核心观点是：goto在C语言错误处理中并非洪水猛兽，而是实现单一出口、集中清理的有效手段，对从高级语言转回C的开发者尤为实用。

## 4. Hoot 0.10.0 发布：Scheme 到 WebAssembly 编译器迎来大量新特性

- 原始链接: <https://spritely.institute/news/hoot-0-10-0-released.html>
- 英文标题: Hoot 0.10.0 released

Hoot 0.10.0 正式发布。Hoot 是 Guile 的 Scheme 到 WebAssembly 编译器后端及通用 WebAssembly 工具链，使 Scheme 代码可在浏览器中运行。本版本距 0.9.0 以来包含大量新特性与修复。编译器方面，新增模块名辅助重复导入错误定位，支持 R6RS 库版本控制，修复 locate-library 未遵循 Hoot 自身加载扩展名的问题。运行时新增 %struct-ref 和 %struct-set! 原语，放宽未定义符号导入的严格性以兼容 Guile，修复 primitive-eval 中可选与关键字参数解析缺陷。Scheme 层面，部分实现 SRFI-13（字符串库）和 SRFI-60（整数位操作），新增 define-macro、defmacro 等宏形式，补充 (rnrs) 系列多个标准模块（base、syntax-case、r5rs、hashtables、files、records 等），显著提升 R6RS 兼容性。CLI 增加端口范围校验，修复无效选项报错不可达的缺陷，新增 --experimental-wasm-exnref 标志以兼容旧版 Node.js。浏览器兼容 Safari 26+、Firefox 121+、Chrome 119+。Hoot 已通过 Guix 和 Debian 分发，也可从源码构建。官方同时发布了游戏 Jam 模板，鼓励开发者用 Hoot 快速制作 HTML5 小游戏。

## 5. C++中每秒十亿次查询的完美哈希查找表

- 原始链接: <https://lemire.me/blog/2026/10/26/billion-query-per-second-lookup-tables-in-c/>
- 英文标题: Billion-query-per-second lookup tables in C++

本文介绍了一种在C++23中实现编译时完美哈希查找表的方法，由Daniel Lemire与Microsoft的Francisco Geiman Thiesen合作完成，并在P99 CONF 2026上展示。核心问题是：当映射键（如HTTP方法、URL协议、编译器关键字）在编译时已确定，std::unordered_map仍在运行时承担哈希、指针追踪和链表遍历的开销。作者采用类似gperf的完美哈希思路，槽位由键长与关联表中少量字符位置的值之和模表大小（2的幂）得到，编译时通过贪心算法为每个字符分配关联值，确保零冲突。查找仅需一次哈希加一次比较。字符串比较方面，利用ARM NEON或x64的16字节向量寄存器，将键零填充后以单条向量指令完成整串比对，将约40条指令、8个分支降至5条指令、0分支；对接近页尾的地址走慢路径以保证安全。ConstexprCore库以单头文件形式提供，运行时查找在Apple M3 Max上约1.3纳秒（5周期），比gperf快3至6倍，比std::unordered_map快7至13倍；在M4上URL协议查找突破每秒十亿次。结论是：键已知时不应在运行时为冲突处理付费，完美哈希可将查找压缩到约5个周期。

## 6. 数据库基准测试的危机

- 原始链接: <http://databasearchitects.blogspot.com/2026/10/the-benchmarking-crisis.html>
- 英文标题: The Benchmarking Crisis

Thomas Neumann撰文指出，数据库基准测试正面临Goodhart定律的严峻挑战：一旦系统针对特定基准进行激进优化，该基准便丧失参考价值。历史上TPC-D因过度缓存导致查询耗时趋零而被退役，TPC-H通过禁止利用先验知识和缓存结果加以修正。如今ClickBench遭遇同类问题，且AI代码生成大幅加速了这一趋势。以pgrust为例，其对字符串列的group-by仅基于哈希值而非完整内容、缓存重复谓词、利用limit无order by特性跳过大部分数据读取，这些微优化虽能提升分数，却可能产生错误结果且不具备通用性。Neumann提出三点建议：基准测试须为ad-hoc并禁止中间结果缓存；须包含更新流以公平比较事务系统；被测系统应早于基准测试发布，必要时定期自动生成新基准。他还建议借鉴机器学习领域Kaggle隐藏测试集和LiveBench定期更新题目的做法，对数据库基准采用隐藏查询或每轮生成新工作负载。评论区中，pgrust作者Michael Malis辩称相关优化ClickHouse亦已采用且使用128位加密哈希加盐使碰撞概率趋近于零；Neumann则强调即便碰撞极罕见，以哈希替代原始值聚合仍违反用户契约，且用户可控字符串使碰撞风险更高。

## 8. 纯逻辑漏洞打造 Microsoft Edge 完整攻击链

- 原始链接: <https://blog.orange.tw/posts/2026-10-the-last-proof-of-human-craft-browser-full-chain/>

## 12. 0xABADBABE 是什么，为何出现？（2011）

- 原始链接: <https://daniel.haxx.se/blog/2011/10/28/whos-0xabadbabe-and-why/>
- 英文标题: Who’s 0xabadbabe and why? (2011)

作者回忆在 Intel 从事 x86 全系统仿真软件开发的经历，讲述一次调试 Windows 7 蓝屏问题的曲折过程。当时模拟的 USB 磁盘设备导致系统启动时蓝屏，作者发现 Windows 7 在蓝屏前约 10 毫秒向 EHCI 控制器保留寄存器（索引 0x1C）写入 0xABADBABE，且该写入仅在插入模拟 USB 磁盘时出现，因此一度怀疑是 EHCI 仿真代码的缺陷。为追查来源，作者用 bgrep 工具在 20GB 的 Windows 7 文件系统中搜索该 32 位小端模式，命中 16 处；又自行编写 bcut 工具截取文件片段供 objdump 反汇编，定位到一条 movl $0xabadbabe, 0x1c(%rax) 指令。然而仅凭反汇编无法判断写入意图，最终经朋友指点得知：这是 Windows 故意写入的调试断点标记，只要接有 USB 设备就会执行，与蓝屏毫无关系，属于典型的「红鲱鱼」。真正的蓝屏根因是 EHCI 驱动发现控制器填入的 USB 数据结构指针越出了驱动所映射的内存区域，属于模拟设备中一个极难追踪的 bug。作者最终让仿真直接接受该写入，问题迎刃而解。

## 13. 让 SIMD 代码适配任意向量宽度

- 原始链接: <https://streamhpc.com/blog/2026-10-28/making-simd-code-scale-to-any-vector-width/>
- 英文标题: Making SIMD Code Scale to Any Vector Width

本文介绍了一种将 SIMD 运算从传统的 vec3/vec4 扩展到 8、16 甚至 32 宽向量的方法，核心思路是将数据从「数组中的向量」（AoS）转置为「向量中的通道」（SoA），即把多个向量的同一分量打包进一个宽寄存器。作者以 Clang 的 ext_vector_type 扩展演示，先展示同时计算 N 个点积的基本案例，再以一个典型的 CPU 视锥体剔除器为进阶示例。剔除器从朴素逐角点检测（13.4 ns/box）优化为仅检测最近角点（3.0 ns/box），再进一步用模板将多个盒子按通道并行处理，在 AVX2 下达到 1.24 ns/box，约为单线程最近角点方案的 10 倍。文章还指出编译器不会自动转置数据布局，这一步必须由程序员完成；同时提醒 Windows x64 默认按指针传递向量参数，应使用 __vectorcall 或 /Gv 改为寄存器传递。此外，作者通过实验揭示了分支预测器对基准测试的严重干扰：Zen 3 可记忆约 16000 个盒子的提前退出模式，导致小场景循环测试产生 4.4 倍虚高加速。测量环境为 Ryzen 7 5800（Zen 3）、Clang 23.1.0，分别针对 AVX2 和 SSE4.2 编译。

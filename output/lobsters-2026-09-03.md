## 2. 无需依赖类型实现依赖式 if 表达式

- 原始链接: <https://haskellforall.com/2026/09/dependent-if-expressions>
- 英文标题: Dependent if expressions without dependent types

本文介绍了一个 Haskell 中的经典技巧：仅借助 RebindableSyntax 一个语言扩展，即可在不使用依赖类型的情况下，让 if 表达式的 then 与 else 分支返回不同类型。文章分两步展开：首先回顾 Church 编码布尔值（将 true/false 编码为接受两个参数并返回其一的函数），此阶段需要 RankNTypes 和 RebindableSyntax 两个扩展，但 if 的两个分支必须同类型；随后关键一步是删除所有显式类型签名和 RankNTypes，让编译器自行推断更通用的类型。此时 true 的类型变为 a→b→a、false 为 a→b→b，Bool 类型同义词扩展为三参数形式 Bool thenBranch elseBranch result = thenBranch→elseBranch→result，从而在类型层面追踪 then、else 分支及结果的信息流。基于此，if bool then 5 else「hi!」可以正常通过类型检查，not、&&、|| 等逻辑运算也获得对应的多参数类型签名。文章还指出，将 true 与 false 混合放入列表时，推断类型会退化为 then 与 else 同类型的「未细化」布尔，因此对混合列表调用依赖式函数会产生类型错误，行为符合直觉。最后，作者展示了借助 DataKinds 与 TypeFamilies 实现编译期断言的扩展用法。全文约二十行普通函数式代码即完成全部实现，无需任何依赖类型机制。

## 3. 静态分配与恒定工作量：对象池中的内存安全与性能确定性

- 原始链接: <https://matklad.github.io/2026/09/02/static-allocation-constant-work.html>
- 英文标题: Static Allocation, Constant Work

本文围绕限价订单匹配引擎中的 use-after-free 问题展开，探讨对象池与内存安全的关系。作者指出，对象池本质上是一个带「代际标签」的标签联合体，类型系统无法追踪该标签。引入类型分离的对象池后，逻辑上的 use-after-free 虽仍存在，但不再导致类型混淆，行为变得确定可预测。文章随后介绍两个来自 TigerStyle 的加固技巧：一是「静态分配」——启动时一次性分配最大订单数，运行期不再动态分配，超出容量则拒绝请求，避免 OOM 导致系统崩溃；二是「恒定工作量」——始终维护固定数量的订单槽位，用 reserved 空操作订单替代释放，订单在系统中循环流转而非创建销毁。这一设计带来三方面收益：认知上只需关注状态转移而非生命周期管理；代码上无需维护活跃订单集合，直接遍历全量数组，利于编译器向量化与缓存预取；性能上 P100 延迟不随负载波动，性能不足在部署时即暴露而非在高峰时才发现。作者强调这些技巧并非万能，但值得纳入工程工具箱。

## 4. 实现FMA模拟并发现C与Rust标准库中的缺陷

- 原始链接: <https://shnatsel.github.io/implementing-fma-finding-bugs-in-std/>
- 英文标题: Implementing FMA and finding bugs in C and Rust standard libraries

本文讲述作者在fearless_simd项目中为无硬件FMA支持的CPU实现融合乘加SIMD模拟的经历，及由此发现Rust标准库和musl libc中隐藏缺陷的过程。作者依据Boldo与Melquiond 2008年论文，用f64中间计算实现f32 FMA，性能比std::simd快5倍。但社区贡献者提供反例，暴露出作者遗漏了对非规格化（subnormal）值的特殊舍入处理。深入排查发现，Rust标准库的f32::mul_add、std::simd乃至musl libc的fmaf函数均存在相同缺陷，该代码源自FreeBSD 2005至2011年实现，可能已被广泛复制。修复Rust标准库时又意外触发rustc在32位ARM上f128类型的ABI bug。作者指出，缺陷在x86无AVX2的Intel芯片、32位ARM及嵌入式系统上尤为突出，64位ARM不受影响；错误虽仅差一个最低有效位，但可能影响确定性模拟的可复现性。截至写作时，musl的修复仍未合并。

## 5. 从零构建一个数据压缩器

- 原始链接: <https://ochagavia.nl/blog/lets-build-a-compressor-from-scratch/>
- 英文标题: Let's build a compressor from scratch

本文以通俗易懂的方式讲解数据压缩原理，并展示作者用580行无依赖Rust代码实现的Huffman压缩器（ABC）。文章首先用布尔数组的JSON序列化（52字节）与位流编码（1字节）对比，说明压缩的本质是用更少字节表达相同信息。接着介绍通用压缩算法：gzip采用的DEFLATE算法由两部分组成——LZ77（识别重复字节序列并用短标记替代）和Huffman编码（高频字节用短比特序列、低频字节用长序列）。作者重点讲解Huffman编码，并嵌入交互式演示供读者体验。压缩流程为：统计字节频率、生成比特映射、按映射编码、将映射写入输出流头部；解压则反向操作。实测中，ABC将一本622KB的书籍压缩至366KB，一个90MB的Rust二进制压缩至73MB，效果虽不及gzip但已相当可观。文章结尾致敬已故信息论学者David MacKay，称其讲座系列是作者深入理解信息论的关键引导，并引用3Blue1Brown的视频说明压缩存在数学极限，不可能无限循环压缩。

## 6. TinyGo 0.42 发布：Recover 终于成真

- 原始链接: <https://tinygo.org/blog/2026/tinygo-0.42-recover-is-real/>
- 英文标题: TinyGo 0.42 - Recover Is Real

TinyGo 0.42 于 2026 年 9 月 1 日发布，填补了与标准 Go 之间最古老的差距之一：运行时 panic 现在可被 recover。空指针解引用、除零、越界切片与映射操作、channel panic 均可通过 defer 和 recover 正常处理；Windows 端新增向量化异常处理器，riscv64 也支持 recover。内存不足等致命错误仍不可恢复。该版本同时支持 Go 1.27（含泛型方法）并迁移至 LLVM 22，仍兼容 LLVM 19/20。新增最小化 UEFI 目标，用户可在操作系统启动前以 Go 编写并运行 UEFI 应用。ESP32 支持大幅增强，涵盖中断向量表、定时器、ADC、中断驱动 UART、Flash XIP、WiFi（espradio 包）以及 ESP32-C3/S3 的蓝牙。STM32 方面新增 F4/F7 的 OTG FS USB 驱动、H7 系列及 NUCLEO-H753ZI 板支持。此外还新增 Puya PY32F、Pimoroni Blinky/Badger 2350、XIAO nRF52840 Plus 等硬件，USB 端点改为动态注册并支持双向端点。testing 包支持 Goexit、SkipNow、FailNow，解锁了大量标准库测试套件。

## 7. nixpkgs 的圣杯：版本范围支持

- 原始链接: <https://fzakaria.com/2026/09/01/the-holy-grail-of-nixpkgs-version-ranges>
- 英文标题: The holy grail of nixpkgs: version ranges

本文介绍了作者 fzakaria 开发的 grail 工具，首次为 nixpkgs 引入版本范围（version ranges）查询与求解能力。nixpkgs 作为「无版本」包管理器，每个属性仅对应当前 revision 的单一版本，无法表达「python3>=3.10 且 openssl@1.1.*」这类跨版本约束。作者此前通过 nixmultiverse.com 恢复了 nixpkgs 全部 1,541 个 revision、逾 30 万个包版本的历史记录，使版本选择成为可能。grail 采用 Answer Set Programming（ASP）求解器 clingo，将版本范围问题建模为布尔可满足性问题（NP-hard），并借鉴 Spack 的 spec 语法，支持区间、逻辑与/或、共存组（^）等运算符，可在亚秒内完成求解。工具还能生成与 mvs 兼容的 lock 文件，并支持直接在 Nix derivation 中声明版本约束，由求解器在构建沙箱内自动选定 revision。针对 glibc 兼容性难题，grail 通过解析 ELF 的 .gnu.version_r 段提取二进制对 glibc 的最低版本需求，使求解器能跨 glibc 世代混合构建。作者计划将 clingo 编译为 WebAssembly 集成到 nixmultiverse.com 网站，实现浏览器端查询。代码已开源。

## 9. Go 1.27 新增 Goroutine 泄漏分析器

- 原始链接: <https://go.dev/blog/goroutine-leak-profiles>
- 英文标题: Goroutine Leak Profiles

本文介绍 Go 1.27 引入的 goroutine 泄漏分析器（goroutine leak profiler），用于在运行中的 Go 程序（含生产环境）中精确检测 goroutine 泄漏。文章首先说明泄漏成因：goroutine 永久阻塞在 channel、sync 包原语等并发机制上，且解除条件永不满足，导致内存与 GC 开销持续增长。现有工具如 goleak、synctest 及普通 goroutine profile 难以覆盖生产场景。新分析器通过 runtime/pprof 的「goroutineleak」类型或 net/http/pprof 的 /debug/pprof/goroutineleak 端点获取，几乎无假阳性，但仅覆盖永久阻塞于 channel 或 sync 原子的泄漏。实现上，它改编 Go 运行时三色标记 GC，以「活性」（liveness）归纳定义为核心：从非阻塞 goroutine 出发，沿引用增量标记所有可达并发原语及被其阻塞的 goroutine，未被标记者即为泄漏。文章给出并发 worker、双重发送、提前返回、超时等典型泄漏模式及修复建议（如为 channel 设缓冲）。局限性包括：全局变量导致的过度可达、非标准阻塞（文件/网络 IO、系统调用）不在检测范围、以及非确定性泄漏难以复现。性能方面内存开销可忽略，但标记阶段存在串行化与最坏 O(n²) 开销。该功能源自 Aarhus 大学、华盛顿大学圣路易斯分校与 Uber 在 ASPLOS 2025 的联合研究。

## 11. 在副本上实现「读己之写」：PostgreSQL 19 的 WAIT FOR LSN 实践

- 原始链接: <https://boringsql.com/posts/read-your-own-writes/>
- 英文标题: Read your own writes, off the primary

本文围绕 PostgreSQL 19 新增的 WAIT FOR LSN 语句，探讨如何在将读流量卸载到副本的同时保证「读己之写」一致性。现代前端在写入后毫秒级触发缓存失效与状态刷新，协作场景下更会放大问题，导致用户短暂看到旧数据。作者测量了多种路由策略：直接读副本在本地回环下仍有 99.2% 的读请求命中旧数据；sleep 50ms 虽能消除陈旧读但 p50 升至 54ms；而 WAIT FOR LSN 将陈旧读降为零，仅比直读主库多 1–2ms。文章分析了副本延迟的四个因素（write_lag、flush_lag、replay_lag、读负载），指出同步提交只等 flush 不等 replay 仍会漏，真正闭合需 remote_apply，但代价转嫁给所有写入者。WAIT FOR 将等待成本精确施加到需要它的单次读上。TIMEOUT 并非调优旋钮而是架构决策：超时回退主库可能在集群级延迟事件中引发连接池耗尽与主库踩踏。实现上需四步：提交后取 pg_current_wal_flush_lsn、将 LSN 作为令牌存入会话或响应头、读前在副本执行 WAIT FOR（须为顶层语句）、按结果路由。LSN 须取提交后位置而非事务内 insert 位置，否则只等行存在而非等事务可见。文章还给出约三十行 Go 示例，并指出 Rails 中 WAIT FOR 因不在只读白名单而被误判为写操作，需绕过语句层在连接上直接执行。

## 13. Bluefin 是一个能力系统

- 原始链接: <https://h2.jaguarpaw.co.uk/posts/bluefin-capability-system/>
- 英文标题: Bluefin is a capability system

Tom Ellis 在 2026 年 9 月的文章中提出，Haskell 效果系统 Bluefin 应被重新定位为「能力系统」（capability system）。Bluefin 于 2024 年初发布，基于 Andrzej Rybczak 的 effectful 库，是 Haskell IO 类型的轻量包装器；与 effectful 用类型约束标记效果不同，Bluefin 通过值级参数表示效果的存在。作者论证效果系统与能力系统本质等价：执行某效果操作需对应效果「在作用域内」，这等同于持有执行该操作的权限（即能力）。他逐一将 state（可变引用）、exception（Throw 值）、reader（线程局部状态）和 IO（与 RTS 交互）等效果映射为能力，指出可变引用、Throw 等值本身就是经典意义上的能力实体。作者认为「能力系统」这一术语优于「效果系统」：一是避免「效果」与「纯」定义模糊的困境；二是消除外人「Haskell 需特殊机制才能做效果」的误解；三是在软件架构层面，「用能力系统约束架构」比「用效果系统约束架构」更直观自然——即只赋予每个组件其所需的最小能力。在 AI agent 大量生成代码的背景下，作者强调能力/效果系统对维护架构分层和强制安全属性具有关键作用，并呼吁 Haskell 社区采用「能力系统」这一表述以更好地向外推广。

## 14. CTTI 是指数级成本，RTTI 是线性成本

- 原始链接: <https://www.gingerbill.org/article/2026/09/02/ctti-is-exponential-rtti-is-linear/>

## 17. 检测文件是否由 Claude 生成

Anthropic 提供了一个浏览器端工具，用于检测文件是否由 Claude 生成或处理。用户可将 JPG、PNG、SVG、MP4、MP3 等格式（上限 100 MB）的文件拖入页面，工具仅读取文件元数据中嵌入的内容凭证，文件本身不会离开设备，也不会被存储。Claude 对生成内容的标记分两种：文本通过写作层面的水印标识，文件则附加一份经加密签名的内容凭证。该凭证遵循 C2PA 开放行业标准，与相机厂商及照片编辑软件中记录图片来源的机制相同，任何支持 C2PA 的工具均可读取。若凭证指向 Claude，工具即会告知用户。需注意，该工具仅能判断 Claude 是否参与了文件的生成或处理，无法判断其是否参与了内容创作，也不包含任何用户身份信息。对于文本水印的检测，Anthropic 另提供 Detection API，目前面向符合条件的机构进行私有预览，以满足欧盟法律要求。此外，OpenAI、Google DeepMind、Gemini 等其他模型提供商也推出了类似的检测工具。

## 1. jujutsu 0.45.0 发布说明

- 原始链接: <https://github.com/jj-vcs/jj/releases/tag/v0.45.0>
- 英文标题: jujutsu 0.45.0

jujutsu（jj）是一款 Git 兼容的版本控制系统，0.45.0 于 2024 年 9 月 3 日发布。本版本最大亮点是新增「jj converge」命令，可通过启发式规则自动合并分叉提交，生成替代提交；若启发式无法确定则回退到交互式提示，也支持非交互模式。破坏性变更方面：「jj config edit/set/unset --user」不再在存在多个配置文件时弹出交互提示，而是直接操作首个加载的用户配置文件，用户可用「--file <PATH>」指定目标；非 colocated 仓库的「jj git import」不再导入 detached Git HEAD 分支上的提交。其他新特性包括：bisect 在因跳过评估无法唯一确定首个坏版本时会给出提示；Git HEAD 状态改为按 worktree 内部追踪，为未来支持多个 Git worktree 做准备，现有仓库自动迁移；config 命令新增「--file」选项以精确指定配置文件。Bug 修复涵盖：默认 immutable_heads 集纳入 untracked_remote_tags；arrange 视口滚动修复；默认 pager 加入 -K 标志避免 Ctrl+C 后终端异常；冲突中回车符丢失问题；colocated 工作区 update-stale 的 HEAD 重置；jj run 遇非零退出码不再继续执行；jj log 隐藏修订崩溃修复；colocated 仓库中外部 git add 产生重复树条目等问题。本版本由 26 位贡献者共同完成。

## 2. Revo 编程语言：以编程乐趣为核心的动态语言

- 原始链接: <https://revo.lung.fyi/>
- 英文标题: Revo Programming language

Revo 是一种以「编程乐趣」为设计目标的动态编程语言，由开发者 if-not-nil 用 Zig 编写，采用 MIT 许可证。其核心特性包括：管道（pipes）机制让数据自上而下流动、避免嵌套；错误即值（errors-as-values），用 atoms 取代 nil 与布尔值，所有崩溃均为显式处理；一切皆为表达式，无语句概念，但代码仍保持过程式外观；编译时虚拟机（comp）可在编译阶段执行任意表达式并将值烘焙进字节码；过程式宏允许直接遍历并转换 AST 原始 token；模式匹配支持就地解构与分支；纤程（fibers）通过在阻塞调用前添加 spawn 即实现非阻塞；表（tables）统一表示模块导出、数组与映射；可选类型系统在无类型时仍可运行，有类型时获得编译期正确性保证与性能优化；测试为一等公民，本质是闭包，返回错误即判定失败。工具链方面，Revo 自带 LSP 诊断与高亮，提供 tree-sitter 语法支持，兼容 VS Code、Neovim、Helix、Emacs 等编辑器，并可通过 C/Zig/Odin 等语言编写可加载扩展或嵌入 Revo 运行时。安装需 Zig 0.16.0，Linux/macOS 下从源码构建即可，Windows 用户推荐使用 WSL。项目迭代迅速，作者建议从源码构建而非使用预发布版本。

## 3. 你的 HTML 中不再需要 initial-scale

- 原始链接: <https://vale.rocks/micros/20260902-1350>
- 英文标题: You Don't Need Initial-Scale In Your HTML

文章讨论了 HTML 文档中几乎 ubiquitous 的一行 viewport meta 标签——「<meta name="viewport" content="width=device-width, initial-scale=1.0">」——并指出其中的 initial-scale=1.0 在现代浏览器中已无必要。作者回顾了历史背景：2007 年 iPhone 发布时，网站尚未针对小屏设计，用户需手动缩放和拖拽桌面版页面；Apple 随后引入 viewport meta 标签以支持小屏缩放，该标签逐渐被各浏览器广泛采用。width=device-width 解决了基本的宽度适配问题，而 initial-scale=1.0 在早期主要用于修复旧版 iOS 及部分浏览器中不期望的缩放行为。然而，随着浏览器迭代，这些问题已不复存在，无需再作兼容处理。作者明确表示，若目标为现代浏览器，仅保留「width=device-width」即可，可省去 19 字节。虽然单页节省有限，但考虑到整个 Web 的规模，累积效果可观。文章属于前端开发领域的轻量级建议，核心结论简洁：删除 initial-scale=1.0 不会带来任何负面影响，反而让文档头更精简。

## 5. Rust 1.98.1 点发布：修复 vtable 生成误编译问题

- 原始链接: <https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/>
- 英文标题: Announcing Rust 1.98.1

2026年9月3日，Rust 发布团队发布了 Rust 1.98.1 点版本。该版本的核心修复是解决了一个 vtable 生成中的误编译缺陷：在 Rust 1.98.0 中，某些情况下 rustc 会为 trait object 错误地生成包含空指针的 vtable（本应填入函数指针的位置），从而导致生成代码中出现未定义行为。该问题轻则引发空指针加载导致的段错误，重则可能成为任意代码执行等严重安全问题的根源。已安装 rustup 的用户只需执行「rustup update stable」即可升级到 1.98.1；未安装的用户可从官网获取 rustup。发布团队同时呼吁社区开发者在本地及 CI 环境中尝试 beta 和 nightly 频道，以便尽早发现潜在问题并反馈。Rust 1.98.1 由众多社区贡献者协作完成，发布团队向所有参与者致谢。总体而言，这是一次以安全修复为主的补丁发布，建议所有使用 1.98.0 的用户尽快升级以消除该误编译风险。

## 6. 为静态博客添加点赞功能：soupvotes 项目手记

- 原始链接: <https://qtea.me/posts/souping-up-my-blog/>
- 英文标题: Souping up my blog

作者希望读者能简单地对博客文章表达认可，但又不愿放弃静态生成架构。他参考了 Bear Blog 的点赞实现，自行搭建了一个独立的轻量 Web 服务：传入文章 URL 即可查询或提交一次点赞。防重复机制采用「访客 IP 哈希 + 当前年份」的组合键，虽存在跨年短暂窗口期可重复点赞的小瑕疵，但整体够用；同时加入站点白名单并校验目标文章是否存在，以抵御滥用。博客前端仅需少量 JavaScript 在页面加载时拉取点赞数并渲染一个按钮。项目最初命名为「upvaas」（upvotes as a service），但作者发现该词恰为印地语「禁食」，遂追求更俏皮、少「大厂味」的名字，最终定为「soupvotes」——既谐音 silly/service of upvotes，又契合他选用的热茶杯图标：点赞即「搅拌」，被赞文章便冒出一缕热气。文章语气轻松幽默，核心亮点在于：以极小代价为纯静态博客补上互动反馈，同时展示了从需求、防刷、命名到视觉隐喻的完整思考过程。

## 7. 能否别再只用百分比来衡量可用性了？

- 原始链接: <https://blog.jim-nielsen.com/2026/stop-with-the-uptime-percentage/>
- 英文标题: Can We Stop With the Uptime Percentages?

作者从Jason Gorman关于编码智能体可靠性的论述出发，指出从90%到99%、从99%到99.9%的难度逐级递增，但日常工作中GitHub、CI、AI、Slack等服务的频繁宕机让他不断面对服务状态页上密密麻麻的百分比数字。这些数字（如99.72%、99.09%、98.98%）对非基础设施人员而言看起来差别不大，「都像小学里的A」，但实际差异是非线性的——99.9%与99.99%看似接近，后者宕机时间却是前者的十分之一，类比地震震级中6.2与7.8的视觉相似但量级悬殊。基础设施从业者习惯用「两个九」「三个九」「四个九」来直觉感知差异，但状态页面的受众已扩展为所有普通用户。作者认为，百分比作为行业内部指标是合理的，但作为面向公众的可靠性界面却极不友好。他提议在状态页上同时给出直观的时间描述，例如将「GitHub Actions：98.31%可用性」改为「GitHub Actions：过去30天有12小时受影响（98.31%可用性）」，让普通用户无需理解接近100%的非线性数学，只需知道「一小时」是什么，就能直观感受服务中断的实际影响。

## 8. 简单不等于小巧

- 原始链接: <https://jyn.dev/simple-is-not-the-same-as-small/>
- 英文标题: simple is not small

本文探讨编程中「简单」与「小」的本质区别。作者以一次耗时九个月的代码覆盖率调试经历为引，提出应优先考虑简单性。他引用Rich Hickey在「Simple Made Easy」中的定义：简单即「单股」（sim-plex），复杂即「多股交织」（com-plex），并以「耦合」替代「复杂」来描述。文章用Unix管道（cat|tr|sort|uniq -c）与Clojure程序对比，指出Unix工具虽小巧却并非简单——例如sort|uniq -c将聚合与排序强行绑定，导致后续修改（如按原文顺序输出）需大量临时文件和晦涩正则。作者进一步以Rust struct将类型检查与固定数据表示耦合、Clojure用map加schema注解实现解耦为例，说明解耦是简单的核心。Google Drive Desktop虽体量巨大，对用户却感觉简单，因为内部复杂性被封装。文章指出，「小」在资源有限时（如PDP-11时代或开源维护者时间稀缺）有意义，但「简单」应始终追求。写简单程序需要好的心智模型与品味，有时还需像CSS、SQL那样投入大量工程构建声明式解耦层。最终，作者修复后的覆盖率管线反而变大了，却因隐藏依赖减少而变得更简单。

## 9. 安全事件通报：BGP 劫持导致 Softaculous 服务遭流量劫持与恶意更新投递

- 原始链接: <https://www.virtualizor.com/blog/security-incident-bgp-hijacking/>
- 英文标题: Security Incident – BGP Hijacking

2026年8月28日20:57至30日06:10 UTC，Softaculous 旗下托管于 Hetzner 的 162.55.80.0/24 地址段遭 BGP 劫持。攻击方 AS62390（NexonHost）经 AS6204（Zet.net）未经授权宣告该 /24 前缀，因比 Hetzner 正常的 /16 宣告更具体，在 BGP 选路中优先生效，将流量引向攻击者服务器。攻击者还通过被劫持的域名验证通道从 Let's Encrypt 获取了覆盖 virtualizor.com 等域名的有效 TLS 证书，受害连接不触发证书警告。事件分两波，中间约 11 小时间歇；路由极不稳定，窗口内记录约 10600 次撤回。Softaculous 利用 RIPE RIS 368 个采集器逐 10 分钟重建路由状态，峰值时约 72% 的 peer 流量被劫持。已确认少量 Virtualizor 实例在更新检查恰逢劫持窗口时收到恶意更新包，但因恶意响应未进入自身日志，无法给出完整受影响清单，故要求所有 Virtualizor 运维人员执行排查。截至 8 月 30 日 06:10 路由已完全恢复，其他产品是否受影响仍在调查中。

## 10. 将BBC Micro版Elite改造为双人游戏的实践

- 原始链接: <https://elite.bbcelite.com/hacks/two-player_elite/technical_information.html>
- 英文标题: How I converted BBC Micro Elite into a two-player game

本文详细记录了作者将BBC Micro经典游戏Elite（6502 Second Processor版，已应用无闪烁补丁）改造为双人模式的完整过程。核心思路是：原游戏中玩家始终处于宇宙中心，所有物体围绕玩家运动；双人版保留这一机制，将玩家2视为玩家1局部气泡中的一艘NPC飞船，由摇杆和键盘控制而非AI战术程序驱动。玩家1视角直接裁剪显示在屏幕上半部分，玩家2视角则需将太阳、行星、飞船、导弹等物体从玩家1参考系变换到玩家2参考系，这是最复杂的部分。文章还介绍了作者采用的位标志方案（利用6502的BIT指令通过bit 7和bit 6测试状态，无需占用寄存器），以及分屏绘制时通过「拉伸-裁剪-压缩」技巧复用原有线段裁剪例程LL145的方法。此外涉及目标锁定计算、太阳与行星的精度「作弊」处理、响应式控制等内容。所有改动均在GitHub仓库中以「Mod:」标记，逐行注释，风格与原代码一致。

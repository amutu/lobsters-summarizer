## 1. POSIX wordexp(3) 存在安全隐患

- 原始链接: <https://yossarian.net/til/post/posix-wordexp-3-is-dangerous/>
- 英文标题: POSIX wordexp(3) is dangerous

wordexp(3) 是 POSIX 提供的 C 语言 API，用于执行 shell 风格的字符串扩展，常被推荐用来做波浪号扩展（如将「~/foo」解析为「/home/me/foo」）。然而，该函数默认参数 0 会启用所有扩展功能，包括命令替换，这意味着传入「$(whoami)/foo」或「$(cat /etc/passwd)/foo」等字符串时，系统会实际执行其中的命令，造成严重安全风险。虽然可通过传入 WRDE_NOCMD 标志来禁用命令替换，但作者指出这在部分 libc 实现中仅是权宜之计：musl 的 wordexp(3) 将工作委托给系统 shell，仅做了简单的模式扫描，无法覆盖 GNU Bash 能识别的所有命令替换写法；macOS 的 libc 同样委托给外部辅助程序 /usr/lib/system/wordexp-helper，据 Julian Squires 报告，截至 2023 年仍存在类似绕过。文章最终结论是：不要对不可信输入使用 wordexp(3)，即便已加上 WRDE_NOCMD 标志，也无法保证安全。开发者若需做波浪号扩展，应改用更受限的专用函数（如 tilde_expand 或手动解析），避免引入命令注入风险。

## 4. Zig 语言引入部分运算符优先级及多项构建系统更新

- 原始链接: <https://ziglang.org/devlog/2026/#2026-10-24>
- 英文标题: Partial Order Precedence

本文是 Zig 语言 2026 年开发日志，涵盖多项重要变更。核心亮点是「部分运算符优先级」机制的落地：Zig 取消了部分运算符组合的隐式优先级，编译器在遇到歧义时强制要求程序员添加括号消义。该提案源自 2016 年的 issue #114，由贡献者 CMDRZero 实现。设计目标是大幅减少程序员需记忆的优先级规则，仅保留算术、比较、逻辑等少数无歧义组合；Zig 自身百万行代码中仅 353 行需调整。升级路径包括手动修复或运行「zig fmt --upgrade」自动补括号。此外，日志还记录了：裸包（无 build.zig.zon）现支持在 URL 旁声明 version 与 paths，使包哈希更稳定；新增包哈希一致性校验，可检测包所有权争议或版本未更新等问题；新增「--print-tree」选项以树形结构可视化依赖关系；帮助菜单在构建配置失败时仍可正常输出；std.ArrayList 引入指针稳定性锁（lockPointers/unlockPointers），在底层内存重分配时触发断言，帮助及早发现悬垂指针类内存错误；包管理功能（fetch、init、libc 等）从编译器二进制迁移至独立的 maker 进程，编译器体积显著缩小，且网络与加密操作在 ReleaseSafe 模式下运行，安全性与可维护性均得到提升。

## 5. 下一代时间线愿景：Matrix 协议时间线重构路线图

- 原始链接: <https://media.ccc.de/v/matrix-conference-2026-99070-a-vision-for-a-next-generation-timeline>
- 英文标题: A vision for a next-generation timeline

本文为 Matrix 2026 年大会（matrix-conf-2026）上的一场约 20 分钟演讲，由 Jade、Ginger、Sofya 等演讲者共同呈现，属于「Next Gen Spec」系列。演讲指出，时间线是聊天软件中用户交互最频繁的核心组件，但 Matrix 协议为支持联邦化架构，在时间线设计上做出了多项妥协，导致实际体验存在明显缺陷。文中列举了三个典型问题：一是 Synapse 服务器中 sync 与 history 接口返回的消息排序不一致；二是用户无法跳转到自己加入房间之前已被固定的消息；三是当用户加入一个本服务器此前已离开的房间时，时间线行为不明确。演讲的核心贡献是提出了一套完整的下一代时间线重构路线图（Fahrplan），涵盖三大关键技术方向：缝合排序（stitched ordering）以解决跨来源消息的有序拼接问题；时间线片段（timeline fragments）以支持分段加载与增量同步；以及状态有向无环图（state DAGs）以替代现有状态模型，为时间线提供一致且可验证的状态推导基础。演讲强调，该方案虽已成形，但完整落地仍需较长时间，属于分阶段推进的长期工程。整体而言，这是一份面向 Matrix 协议开发者与贡献者的技术愿景文档，旨在为下一代时间线规范提供清晰的方向与实施路径。

## 6. glibc 更新意外导致 Chromium 音频服务崩溃的排查始末

- 原始链接: <https://refi64.dev/posts/chromium-audio-break.html>
- 英文标题: When a glibc update accidentally breaks Chromium's audio (2021)

2021年，Fedora 的 Chromium Flatpak 包升级至 runtime 21.08 后，用户发现视频播放完全失效，日志显示音频渲染进程因「futex facility returned an unexpected error code」而崩溃。作者通过 core dump 和 gdb 回溯，定位到 PulseAudio 的 libpulse 在等待条件变量时触发了 glibc 的 futex 致命错误。深入 glibc 2.31→2.33 的变更后发现：一个重构 commit 将条件变量无超时等待路径统一为调用 __futex_abstimed_wait_cancelable64，即使 abstime 为 NULL 也会将 clockid（值为 0，即 CLOCK_REALTIME）传入，导致每次 futex_time64 调用都附带 FUTEX_CLOCK_REALTIME 标志。而 Chromium 的 BPF 沙箱在校验 futex 操作时仅剥离了 FUTEX_PRIVATE_FLAG，未处理该新标志，遂将合法调用误判为非法并返回 EPERM，glibc 随即 panic，音频服务崩溃。修复仅需在沙箱策略中增加对该标志的剥离，一行代码即可解决。此外，Chrome、Brave、Edge 未受影响，是因为 Chromium 发行版构建默认启用了大量 field trials（含 AudioServiceSandboxLinux），而官方文档建议非开发构建应通过 GN 标志 disable_fieldtrial_testing_config=true 关闭测试配置。文章最后强调：无论变更多小，都必须进行充分测试。

## 8. 在2美元微控制器上实现SIMD加速的计算机视觉

- 英文标题: SIMD-accelerated computer vision on a $2 microcontroller

作者为ESP32-S3（售价约2美元、双核240MHz、内置WiFi与BLE）编写了基于其128位SIMD指令的FAST角点检测器，性能较参考实现提升约220%，处理QVGA（320×240）帧仅需约6ms，可轻松处理30fps VGA视频流。文章记录了从零学习ESP32-S3汇编到完成SIMD加速FAST预检测的全过程。开发中遇到两个关键限制：一是指令集不支持非对齐读取，作者利用寄存器切片指令从相邻块中提取东西方向像素；二是SIMD仅支持有符号8位比较且算术为饱和运算，无法直接处理无符号像素数据。作者发现对每个字节执行XOR 0x80即可将[0,255]线性映射到[-128,127]，从而绕过饱和限制。此外，作者还自行编写了简易寄存器分配器basm。文章指出ESP32-S3的SIMD能力虽非秘密但鲜为人知，作者希望展示在极低成本芯片上实现实用计算机视觉的可能性。

## 10. 逆向工程指令编码：DERIVE 工具

- 原始链接: <https://www.usenix.org/legacy/events/usenix01/full_papers/hsieh/hsieh_html/>
- 英文标题: Reverse-Engineering Instruction Encodings (2001)

本文（USENIX 2001）介绍了 DERIVE 工具，用于从汇编器中自动提取机器指令的位级编码信息。背景是反汇编器、JIT 编译器、二进制代码重写器等工具都需要指令编码的显式表示，而手工查阅架构手册并填写字段偏移、宽度、操作码值等工作既繁琐又易出错，尤其在 x86 等 CISC 架构上。DERIVE 的核心思路是：用户仅提供汇编级描述（指令名与操作数类型，如寄存器、立即数、标签），工具向系统汇编器批量输入指令排列组合，分析生成的机器码，通过方程求解确定每条指令的操作码掩码及各操作数字段的位置、大小与变换方式。其内部包含寄存器、立即数、跳转目标三个专用求解器，基本方法是固定其余字段、枚举当前字段所有合法值，观察二进制编码中发生变化的位来定位字段。DERIVE 已完整求解 MIPS、SPARC、Alpha、PowerPC 指令集，并覆盖 ARM 和 x86 的绝大部分指令，输出为 C 结构声明。作者还基于其输出构建了代码发射器生成器，重写了 Kaffe JIT 后端，使后端描述体积缩减 40%。此外，DERIVE 可兼作汇编器测试工具，快速发现架构手册与汇编器实际实现之间的不一致。

## 11. SIMD与Go：从硬件原理到编译器实现

- 原始链接: <https://internals-for-interns.com/posts/go-simd/>
- 英文标题: SIMD and Go

本文介绍SIMD（单指令多数据）的基本原理及其在Go语言中的新支持。Go 1.26引入实验性包simd/archsimd（绑定CPU架构），Go 1.27进一步提供可移植包simd，均需设置GOEXPERIMENT=simd。文章从硬件层面解释了向量寄存器与lane的概念，以及「加载-运算-存储」的基本循环。随后逐一演示了常见SIMD操作：广播（将标量复制到所有lane）、融合乘加（FMA/MulAdd）、比较生成掩码、IfElse与Masked实现SIMD版条件分支、Permute重排lane、水平归约（ConcatAddPairs）以及尾部部分加载。在编译器实现方面，archsimd的方法（如Add）无函数体，属于编译器内建函数，直接映射为单条CPU指令；simd包则通过midway编译阶段为每种向量宽度（128/256/512位）各生成一份代码，运行时由分发器根据CPU能力选择对应版本。文章最后以点积计算为完整示例，展示了从Go源码到SIMD指令的全流程，包括AVX2/FMA特性检测、主循环、尾部处理及八lane归约为标量的过程。

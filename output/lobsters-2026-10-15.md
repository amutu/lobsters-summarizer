## 7. 又一个 Linux man page 信息过时的案例：initstate(3) 的真相

- 原始链接: <https://sebsite.pw/w/20261014-initstate.html>
- 英文标题: yet another place where a linux man page is inaccurate

作者此前在博文「your c is not standard c」中声称 glibc 的 initstate 函数在出错时不返回 NULL，违反 POSIX 规范，并引用 initstate(3) man page 的 BUGS 段落作为佐证。随后读者来信指出该缺陷已于 2013 年修复，man page 只是未同步更新。作者复现测试后确认 glibc 现已符合 POSIX，承认原文有误。然而进一步查阅 POSIX 标准 initstate(3p) 后发现更深层的问题：POSIX 根本未为该函数定义任何错误（ERRORS 一节明确写「No errors are defined」），glibc 在出错时设置 errno 以及将 state 参数为 NULL 视为错误条件，均属 glibc 自身扩展，并非 POSIX 要求。相比之下，musl 的 initstate 实现严格遵循 POSIX，任何情况下都不设置 errno，传入 NULL 指针则直接段错误。作者由此感慨：Linux man page 虽详尽，却常存在信息过时或遗漏关键细节的情况——既未删除已修复的 BUG 说明，也未标注哪些行为是 glibc 扩展而非标准规定。这是作者当月第二次遇到 man page 严重过时的情况。

## 9. 用 String View 修复 C 语言字符串

- 原始链接: <https://eliasebner.com/blog/guides/fixing-strings-in-c/>
- 英文标题: Fixing C Strings With String Views

作者因 C 语言缺乏现代字符串类型，编写了一个单文件小库，核心思路是用「str_view」（只读视图，含 const u8* 指针与长度）和「str_owned」（拥有数据的可变字符串）替代传统 NUL 终止字符数组。文章首先分析 C 字符串的三大痛点：求长度需 O(n) 遍历、截取子串必须复制内存、遗漏 NUL 终止符会导致越界崩溃。随后给出实现细节：用 u8 替代 char 以保证跨平台一致性；采用 arena 分配器统一管理内存；通过 STR 宏从字面量快速构造 str_view；提供 owned 与 view 之间的转换函数；并实现了 starts_with、slice（支持负索引，类似 JavaScript）、find_substr、contains_substr、eq、eq_ignore_case、split 等常用操作。设计上，作者偏好以 struct 返回多值而非 C 常见的输出参数，并大量使用 [[nodiscard]] 防止返回值被忽略。文章在 split 的完整实现处截断，但整体展示了如何用现代 string view 理念改善 C 语言字符串操作的人体工学与安全性。

## 10. ZXC：面向超快解码的无损压缩库

- 原始链接: <https://libzxc.org/>
- 英文标题: ZXC: Lossless compression built for ultra-fast decode

ZXC（libzxc）是一款用C17编写的无损数据压缩库，采用BSD 3-Clause许可，无外部依赖。其核心设计思路是「压缩一次、读取多次」：将匹配选择、最优解析和统计调优等工作全部前移至编码器，使解码器保持极简分支并充分利用SIMD指令，从而在ARM和x86上实现每秒数GB的解码速度。在Apple M2上，最快级别（-1）解码达13.5 GB/s，为LZ4的2.41倍且输出更小；最高级别（-7）压缩率33.09%，解码速度仍为zstd -1的2.80倍。ZXC提供7个压缩级别（默认3级），支持可寻址归档（O(1)随机访问）、原地解压（约1%额外内存）、训练字典、多线程流式处理，以及手写SSE2/AVX2/AVX-512/NEON。官方提供Rust、Python、Node.js、Go绑定，覆盖x86_64、ARM64、RISC-V等8种架构。项目由Google OSS-Fuzz持续模糊测试，代码覆盖率超80%。当前版本为0.15.0（2026年10月发布），适用于固件更新、游戏资源加载、内容分发及读多写少存储等场景。

## 11. 从UAF到RCE：curl HTTP/2上传漏洞解析

- 原始链接: <https://daniel.haxx.se/blog/2026/10/14/a-uaf-turned-rce/>
- 英文标题: A UAF turned RCE

curl 8.23.0修复了高危漏洞CVE-2026-92392（HTTP/2上传Use-After-Free），该漏洞在特定条件下可演变为远程代码执行。HTTP/2为复用协议，curl通过easy handle与multi handle管理并发传输。当恶意服务器将窗口归零、返回部分响应后重置流时，curl正确终止传输却遗留了指向已释放easy handle的悬空指针；随后清理multi handle时，服务器数据被写入该已释放内存，篡改函数指针，最终执行远程代码，攻击还依赖泄露的本地地址绕过ASLR。然而触发条件极为苛刻：需向持有有效证书的恶意服务器上传约135KB数据，且依赖特定分配模式、nghttp2与TLS 1.3行为，payload区域仅约23字节，成功概率极低，最可能仅导致崩溃。该漏洞由Anthropic的Luna Tong借助OSS Scanner发现。修复方面，curl团队正逐步以传输标识符替代内部指针，并加强测试与静态分析。团队明确表示不会将curl移植至其他语言，将持续在C中迭代改进。漏洞于9月15日确认，发布周期从8周缩短至6周以加速修复。

## 13. DelightQL：一种编译为 SQL 的函数式查询语言

- 原始链接: <https://delightql.org>
- 英文标题: The DelightQL Query Language

DelightQL 是一种将查询编译为 SQL 的领域特定语言，语法借鉴逻辑编程与函数式编程，旨在让查询更简洁、可复用，同时保留 SQL 的完整关系型能力。其核心特性包括：灵活的投影操作（按模式选列、原地变换与重命名、删除列无需列出其余列）；树形与兄弟集合构建（直接描述嵌套输出形状、将值转为键、在集合内继续查询并保留外层上下文）；局部函数与查询即函数（命名表达式复用、关联查询封装为函数调用、高阶函数与管道组合）；不规则联合、透视（Pivot）与融化（Melt）等表格重塑操作；以及从左到右的过滤-选择-排序-取前 N 流程、可选连接（问号语法）、带条件的过滤聚合和窗口函数。在 SQL 方言支持方面，DelightQL 目前对 SQLite 支持较好，对 DuckDB 部分支持，计划覆盖更多主流方言。实现上采用 Rust 编写，编译器前端使用 tree-sitter，提供跨平台 CLI 工具。文章强调 DelightQL 仍处于 alpha 阶段，不建议直接用于生产环境。网站上的代码块可在基于 WASM 的演示数据库中直接运行。

作者通过Docker容器与mitmproxy构建测试框架，对25个主流包管理器进行了实验，模拟被入侵的包仓库向合法包中注入恶意代码。结果显示，不到半数包管理器默认通过锁文件检测篡改，仅Go和vcpkg能验证每个下载包的完整性。在锁文件方案中，Bun、npm、pnpm、Cargo等默认校验哈希，但Pub、Conan、CocoaPods、Composer等虽在锁文件中包含哈希，却仅将其用作唯一标识而非完整性校验，恶意仓库仍可绕过。在签名方案中，仅Go默认验证签名，其余要么需额外配置，要么完全不支持。文章还指出锁文件承担构建确定性、环境共享、可复现构建等多重角色，将其视为完整性来源是较新的解读，与原始设计存在张力；锁文件哈希锁定具体版本也会阻碍用户及时获取安全更新。作者认为，随着针对开发者的供应链攻击缓解措施逐步完善，攻击者将转向包仓库这一更薄弱环节，而当前多数包管理器在密码学完整性保护上仍严重不足，未来需借鉴Go、vcpkg等前沿设计，但需平衡开发者体验与安全性。

## 1. 我让 Rust 的 never 类型终于稳定了

- 原始链接: <https://blog.ihatereality.space/0C-never-type/>
- 英文标题: I stabilized never type

这是一篇 Rust 语言开发者的简短公告，宣布 Rust 中的 never type（即「!」类型，表示「不可能到达」的类型）终于在 nightly 版本上完成稳定化。作者回顾了这段漫长的历程：never type 自引入以来已处于不稳定状态长达十年，期间经历了五次稳定化尝试均告失败，而作者本人也花了超过两年时间持续推进这项工作。最终，这一类型在 nightly 通道上正式稳定（或将在下一个 nightly 版本发布后生效）。文章语气轻松幽默，作者用「我感到……空空的，就像 never type 本身一样」来调侃完成目标后的感受——never type 在类型系统中代表空集，即不存在任何值，作者借此自嘲一种「达成后的虚无」。文中还推荐读者观看其此前录制的「when is never」主题演讲，以了解更多背景与细节。整体而言，这是一篇庆祝性质的短文，标志着 Rust 类型系统中一个长期悬而未决的设计问题终于画上句号，对 Rust 的类型表达力和编译器能力具有实际意义。

## 3. C2PA相机签名在现实中不堪一击

- 原始链接: <https://www.da.vidbuchanan.co.uk/blog/android-c2pa.html>
- 英文标题: C2PA Cameras Do Not Survive Contact With Reality

安全研究员David Buchanan（retr0id）于2026年8月撰文指出，C2PA内容真实性标准在Android平台上已被实质性攻破且难以修补。C2PA相机应用依赖Key Attestation与Google Play Integrity来确保仅对图像传感器数据签名，但Root权限提升漏洞（如CVE-2026-43499）可绕过这些机制：通过exploit获取Root后，bootloader仍显示锁定、AVB密钥未变，Google服务器照常分配C2PA密钥，攻击者无需提取原始密钥，只需调用StrongBox对任意文件签名即可伪造C2PA凭证。此外，低成本硬件故障注入攻击（如PTE位翻转）可root设备，且此类硬件漏洞无法通过软件更新修补。Samsung的RKP缓解措施部分阻断了该攻击，但作者称已有替代方案。彻底修复需将整条图像处理管线移入硬件安全飞地，Google已将报告标记为「Won't fix (infeasible)」，但仍支付7500美元赏金。作者强调，所有依赖Android Key Attestation或Play Integrity的C2PA相机应用均受影响，不限于Pixel设备。他还披露了一个私钥泄露漏洞，Google已于次日修补，但多数C2PA验证工具不检查密钥吊销状态。

## 5. 从 Codeberg Pages 迁移到 OpenBSD VPS 的实践记录

## 6. 生成树协议交互式入门

- 原始链接: <https://vincent.bernat.ch/en/blog/2026-spanning-tree>
- 英文标题: An interactive introduction to the spanning tree protocol

本文以办公室网络场景引入生成树协议（STP），说明以太网环路会引发广播风暴，STP通过阻塞冗余链路构建无环树加以解决。文章聚焦2004年推出的快速生成树协议（RSTP），借助开源用户态实现MSTPD在浏览器中提供可交互拓扑演示，系统讲解其核心机制：通过桥标识符（优先级加MAC地址）选举根桥；为端口分配根端口、指定端口、备用端口、禁用端口、备份端口五种角色，依据累积路径成本、桥ID和端口ID逐级裁决；详述端口在丢弃（红）、学习（黄）、转发（绿）三态间的转换，包括边缘端口直接转发及proposal-agreement握手机制完成同步的过程。文章还涉及拓扑变更通知、安全、收敛速度、网络规模上限及MSTP等话题，并回顾Radia Perlman在DEC发明STP的历史。作者指出，尽管BGP EVPN VXLAN等现代方案更优，RSTP因所有交换机均支持仍具实用价值。

## 7. 追踪32位嵌入式系统上Go运行时的netpoll别名缺陷

- 原始链接: <https://sigma-star.at/blog/2026/08/go-runtime-netpoll-bug/>
- 英文标题: Hunting Down a Go Runtime Bug on 32-bit Embedded Systems

文章记录了作者在32位ARM嵌入式Linux系统上定位并修复Go运行时一个长期未决bug的过程。客户报告的崩溃信息为「runtime: netpoll: eventfd ready for something unexpected」，实际收到EPOLLIN|EPOLLOUT而非预期的EPOLLIN。经排查，根因在于Go的netpoll代码在8字节的ev.Data字段中同时存放原始指针（指向netpollEventFd）和带标签指针（指向pollDesc，低4字节为fdseq计数器）。在32位小端系统上，原始指针仅占低4字节，高4字节为零；当程序长期运行、fdseq增长至约300万时，其值恰好与netpollEventFd的地址别名，导致socket fd被误判为event fd，内部假设被打破从而崩溃。该缺陷自Go 1.14（2020年）引入，2025年3月首次被报告，此前维护者曾拒绝一次修复尝试。作者提出的修复方案是将event fd的标识改为存储带标签的nil pollDesc，使ev.Data始终为带标签指针，彻底消除别名。修复于2026年合入。作者推测Google可能已不再运行32位Go程序，否则会更早发现此问题。

## 8. Firefox 宣布支持 JPEG XL 图像格式

- 原始链接: <https://hacks.mozilla.org/2026/08/intent-to-ship-jpeg-xl/>
- 英文标题: Intent to Ship: JPEG XL

2020年代浏览器迎来两大现代图像格式——AVIF与JPEG XL。Firefox于2021年支持AVIF后，如今宣布计划支持JPEG XL；Chrome同样计划跟进，Safari已有部分实现，预计年底前实现跨浏览器支持。安全方面，Firefox因JPEG XL解码器涉及约10万行多线程C++代码而担忧攻击面，遂挑战Google Research用Rust重写，最终产出jxl-rs作为Firefox的核心解码器，并推动Interop 2026集成测试。Firefox的Rust实现还补齐了Safari此前缺失的渐进渲染能力，使图片在仅下载少量数据时即可呈现大致内容。在格式选择上，JPEG XL擅长无损压缩、渐进渲染及JPEG再压缩；AVIF则在网络质量照片及锐边与平面混合图像上表现更优。实测数据显示，网络质量下AVIF文件通常更小，但无损场景JPEG XL优势明显（如1.45 MB对比1.76 MB）。作者建议开发者用站点代表性图片在目标质量下实测，并优先优化高像素密度场景。

## 11. XY问题：求助时别只说方案，要说清真正的需求

- 原始链接: <https://xyproblem.info/>
- 英文标题: The XY Problem

本文解释了「XY问题」这一常见沟通陷阱：用户真正想完成的是X，但不知如何实现，便假设先解决Y就能达成X，于是去求助Y；然而Y本身既陌生也未必是X的合适路径，导致双方大量时间被浪费。问题根源在于求助者卡在自以为的解决方案上，无法退后一步完整描述需求。文章给出三条应对建议：一是求助时附上更大背景，而非只抛出一个子问题；二是对方追问细节时如实补充；三是把已排除的方案及排除理由一并说明，这能反向揭示真实需求。文章还提醒：若你的诊断完全正确，就不必再求助。两个实例加深理解：其一，新手问「如何取文件名最后3个字符」，实际想要的是文件扩展名，而扩展名未必恰好3位，正确做法是用参数展开取最后一个点之后的部分；其二，一位用户问如何修改nmap的OS检测输出，真实目的是防止他人探测其操作系统类型，但nmap指纹基于TCP/IP栈行为，无法靠简单手段绕过，若一开始就说明真实意图，讨论会高效得多。

## 12. 用 64 位低比特标签替代 Rust 枚举，Plush 解释器提速 17%

- 原始链接: <https://pointersgonewild.com/2026-08-25-replacing-a-rust-enum-with-a-64-bit-word/>
- 英文标题: Replacing a Rust Enum with a 64-bit Word Made My Interpreter 17% Faster

本文是 Plush 语言解释器优化系列的第六篇。Plush 是动态类型语言，原 Value 类型采用 Rust tagged enum，因内存对齐需占 16 字节，造成大量浪费。作者与 Claude 协作设计了一套 64 位低比特标签方案：fixnum 占 62 位有符号整数（低 2 位为 00），flonum 采用自标签编码（低 2 位为 10，仅损失 2 位指数），immediate 用 5 位子标签区分 nil、true、false 等常量，另设两种指针类型以兼顾快速引用比较与结构相等。整数加减、比较可直接映射为机器指令；浮点运算参考 Melançon 等人的自标签论文，通过旋转加偏置实现，无需移位或掩码。在 MacBook Air M5 上测试，内存方面 mlp 等基准峰值 RSS 下降最多 37%，但 sha256_unfixed 因整数溢出产生堆装箱出现回退，经一行修复后恢复。性能方面出乎意料地所有基准均变快，无任何回退，整体提速约 17%。作者的目标是让解释型 Plush 具备实时渲染 3D 动画的能力。

## 14. AI 审查循环并不总能收敛

- 原始链接: <https://kevinmahoney.co.uk/articles/ai-review-loops/>
- 英文标题: AI Review Loops Don't Always Stabilise

文章指出，许多人天真地认为让 AI 反复审查代码并自动修复，最终能产出完美代码，但实际效果往往适得其反。现实中，一些团队已在无意中运行这一循环的「慢版本」：开发者 A 用 AI 生成 PR，开发者 B 用 AI 审查，开发者 A 再用 AI 修复，如此往复。文章列举了三个核心问题：第一，AI 缺乏一致的价值判断，每次运行对「好代码」的标准可能不同，极端情况下会在审查间来回翻转，导致循环永不终止；第二，审查极易引发范围蔓延，从「缺少测试」升级到「缺少 CI/CD 流水线」乃至「缺少 Android 应用」，不断膨胀需求边界；第三，审查中的误报或幻觉本身就会引入新缺陷，使代码质量不升反降。为验证这一点，作者让 Opus 5 生成一段「完美且非平凡」的代码，再经过三轮审查-修复循环，结果缺陷数量随每轮审查而增加，而非减少。文章结论是：若无精心设计的护栏机制，朴素的 AI 审查循环不仅无法稳定收敛，反而会让代码越改越糟。

## 18. 再探 SQLite WAL-Reset 竞态缺陷：100 行 C 代码复现数据丢失与文件损坏

- 原始链接: <https://theconsensus.dev/p/2026/08/23/another-look-at-sqlite-wal-reset.html>
- 英文标题: Another look at SQLite's WAL-Reset bug

Phil Eaton 在 Tailscale 报告的基础上，深入剖析了 SQLite 中一个存在约 16 年的 WAL 检查点竞态缺陷。该缺陷源于 wal.c 中检查点与写入线程重启日志之间的时序窗口：当检查点读取到过期的 mxFrame 值时，会错误地将已提交的 WAL 帧标记为已回写，导致后续帧被跳过，造成数据丢失甚至数据库文件损坏。作者仅用约 100 行 C 代码、两个线程和三个数据库连接，通过放大 mmap 区域使 munmap 耗时足够长，在数秒内即可稳定触发该竞态，观察到丢失写入和「database disk image is malformed」等损坏现象。SQLite 已于 2026 年 3 月修复（3.53.0），修复版不再出现丢失写入。但作者还发现：以调试模式编译修复版时，walMerge 函数中的断言会触发失败，暗示修复可能不够彻底；线程检测器（TSan）也能定位到 nBackfill 与 mxFrame 之间的数据竞争。作者总结称该缺陷触发概率仍较低，但建议用户尽快升级，并呼吁 SQLite 增加更通用的丢失写入防护机制。

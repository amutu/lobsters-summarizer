## 2. WinHelp 文件的工作原理

- 原始链接: <https://quin.fyi/posts/how-winhelp-files-work.html>
- 英文标题: How WinHelp files work

本文介绍了作者为阅读旧版 WinHelp .hlp 文件而编写的纯 Rust 解析库 libhlp 的技术细节。由于微软从未公开该格式文档，作者参考了 Manfred Winterhoff 的反编译器 helpdeco 附带的 helpfile.txt，并结合实际文件逆向出格式。文章指出 .hlp 文件本质上是一个归档，以魔数 3F 5F 03 00 开头，内部通过 B+ 树目录管理 |SYSTEM、|TOPIC、|FONT、|CONTEXT 等虚拟文件。文本以固定块存储，支持两层压缩：第一层为简化版 LZ77，第二层为短语替换编码（WinHelp 3.1 的 |Phrases 表与 Windows 95 的 Hall 压缩）。作者还分享了一个因一元编码步长为 1 时多读一位余数位导致后续数据全部错乱的 bug。此外，文章解释了链接通过名称哈希而非位置定位、粗体通过字体切换实现、文本使用 Windows 代码页等设计细节。libhlp 支持从 WinHelp 3.0 到 Windows 95 编译器的所有已知版本，已发布至 crates.io，并被 Paperback 应用集成使用。

## 4. 为 Rust 中的锁中毒机制辩护（2025）

- 原始链接: <https://sunshowers.io/posts/on-poisoning/>
- 英文标题: In defense of lock poisoning in Rust (2025)

本文针对 Rust 社区近期「将默认 mutex 改为 panic 时静默解锁」的提案，系统论证了锁中毒（lock poisoning）机制的必要性。作者指出，当非主线程在临界区内发生 panic、且未被 catch_unwind 捕获或未被 join 处理时，mutex 所保护的数据不变量将被永久违反，而锁中毒是检测此类故障的关键手段：释放锁时若线程正处于 panic 状态，mutex 即被标记为 poisoned，后续获取锁将返回 PoisonError 而非正常守卫。作者进一步将问题推广到「意外取消」这一更广泛的类别，包括 async Rust 中 future 在 await 点的取消，并引用 Oxide 公司因 Tokio mutex 不变量违反频发而完全弃用其 mutex 的实践经验。针对「中毒是否过于保守」的质疑，作者承认纯读取或简单计数等场景不会真正破坏不变量，但强调 unwind 安全性未编码进 Rust 类型系统，代码随时间演进极易引入隐患；误报仅导致可用性下降，而未检测到的 panic 后果无上界，甚至可能引发个人信息泄露。此外，catch_unwind 与 scoped threads 的引入使不变量违反不再局限于 mutex 场景。作者结论是：锁中毒的核心价值在于「检测」而非「恢复」，其重要性足以压倒将加锁与中毒分离所带来的概念优雅性。

## 6. Zig 中的类型化索引

- 原始链接: <https://lvignoli.eu/posts/2026-11-16-typed-indexes-in-zig/>
- 英文标题: Typed indexes in Zig

本文讨论在 Zig 语言中利用「命名整数」或「新类型索引」模式防止不同数组索引混淆的实践。作者指出，仅用枚举包装整数并不足够，因为调用者仍可通过 @backingInt 绕过类型检查，因此必须配合 getter 辅助函数作为访问约定。文章以电子表格结构体为例，展示行索引与列索引混用导致的 bug，并给出两种方案：一是为每个字段定义独立索引类型和访问方法；二是利用 comptime 泛型构建通用方案——通过 Field 枚举标识字段、Kind 枚举区分行与列、Index 函数在编译期生成对应索引类型、at 方法在编译期将字段与索引类型绑定，使类型不匹配在编译期即报错。该方案语法优雅（如 Sheet.Index(.row)），但并非完全密封：调用者仍可通过 @fromBackingInt 伪造索引或直接访问字段（Zig 无私有字段机制），最终依赖文档约定与主动类型审查来保障安全。

## 8. Ubuntu 26 中 sudo-rs 导致 Ansible 权限提升超时

- 原始链接: <https://www.jeffgeerling.com/blog/2026/ansible-fails-become-ubuntu2604/>
- 英文标题: Ansible Fails waiting for privilege escalation on Ubuntu 26

作者在将服务器从 Ubuntu 22/24 迁移到 26 时，发现 Ansible 使用 -K（--ask-become-pass）执行 sudo 提权时出现 12 秒超时失败。根本原因是 Ubuntu 26.04 用 Rust 重写了 sudo（即 sudo-rs），该版本在密码提示前额外输出一段字符串，导致 Ansible 等自动化工具无法匹配预期的提示文本而卡死。修复路径有三：一是升级 Ansible 至 Core 2.22.0（已包含修复），或等待 2.16、2.18、2.19、2.20、2.21 等版本的回移补丁；二是在 hosts 文件中将 ansible_become_exe 设为 sudo.ws，回退到传统 sudo；三是通过 update-alternatives --config sudo 在系统层面切换回旧版 sudo。该问题同样影响了 pyinfra，其 3.11 版本已修复。作者对 Ubuntu 将 Rust 重写引入 sudo 这类基础工具的做法表示不满，认为此类底层组件的变更应经历更长的测试周期，并批评 Ubuntu 缺乏类似 Fedora 那样的前沿测试发行版来提前暴露和消化兼容性问题，暗示若其他发行版跟进 sudo-rs，自己可能转向 Debian。

## 10. 浏览器标签页作为容器运行时

- 原始链接: <https://fzakaria.com/2026/11/25/browser-tabs-as-a-container-runtime>
- 英文标题: Browser tabs as a container runtime

本文介绍了一个名为 tabc 的 OCI 容器运行时项目，它将每个容器运行在 Chromium 浏览器标签页中，而非传统 Linux 内核进程。其核心依赖 unknernel 项目，该项目将 Linux 内核编译为 WebAssembly，使容器代码在浏览器中近原生速度执行，无需完整硬件模拟。在 macOS 上，tabc 无需 hypervisor 或 Linux 虚拟机，仅凭浏览器即可运行容器，彻底改变了 Mac 上容器部署的架构。隔离机制由浏览器沙箱与 WebAssembly 共同提供，替代了 runc 依赖的 namespaces 和 seccomp。性能方面，容器启动约 0.87 秒（含浏览器启动），计算密集型任务存在 11 至 36 倍减速，但交互式场景仍可接受；空闲容器内存开销约 540 MiB。tabc 兼容 Docker 命令与 docker compose（通过轻量级 tocker daemon），并支持 --open 模式将容器可视化到浏览器标签页中，实现跨终端交互。作者引用 Docker 创建者 Solomon Hykes 的观点，认为 WebAssembly 本可替代 Docker，而 tabc 正是这一设想的落地实践。

## 11. 主流编程语言亟需形式化可验证性

## 12. CSS 混合（Mixins）之美

- 原始链接: <https://patrickbrosset.com/articles/2026-11-25-the-beauty-of-css-mixins/>
- 英文标题: The beauty of CSS mixins

本文介绍了即将在 Chromium 浏览器中落地的 CSS 混合（mixin）特性。混合是一种可命名的 CSS 代码块，用 @mixin 定义、@apply 调用，可包含任意多条声明乃至嵌套规则，区别于仅持有单个值的自定义属性和只能嵌入属性值的 CSS 函数。文章演示了混合的多种能力：带类型校验与默认值的参数、条件规则（@media、@supports、@container）、通过 @contents 接收调用方传入的样式块、以及 @private 私有变量。作者特别展示了「命名断点」用法，将响应式断点集中定义、按角色命名，使媒体查询代码更清晰。文章还探讨了一个主题化实验：在白标网站中，开发者在 HTML 各逻辑区域预埋未定义的混合名称，客户通过外部样式表定义这些混合即可定制外观，兼顾了 HTML 结构可控性与定制灵活性，类似当年 CSS Zen Garden 的理念但避免了暴露完整选择器。作者构建了 Mixin Zen Garden 演示，提供六种风格切换。经验总结包括：未定义的混合无害、按角色而非外观命名混合；局限在于嵌套选择器仍可能穿透到 HTML 结构，且该特性目前仅在 Chromium 实验性标志后可用。作者还展望了跨 Shadow DOM 应用混合、集中强制可访问性规范等未来方向。

## 13. 解读Unix V6上下文切换中那句「你不必理解这段代码」

- 原始链接: <https://www.taniwha.com/~paul/not.html>
- 英文标题: Understanding "You are not expected to understand this."

作者Paul Campbell回忆四十五年前将Unix V6/V7移植到Vax的经历，深入剖析了V6内核上下文切换中那句著名注释「You are not expected to understand this.」背后的机制。V6将进程状态存于进程表条目和映射到固定内核地址的udot结构中，通过savu/retu/aretu（PDP-11汇编）保存和恢复栈指针与帧指针，而不触碰r2-r4寄存器。swtch()的流程为：savu保存当前进程状态，retu切到进程0，选择新进程后retu切换到新udot，sureg设置用户态MMU映射，最后return(1)。那句注释对应的分支处理SSWAP标志：当进程因内存不足被换出时，newproc()中执行savu(u.u_ssav)并调用xswap写入交换文件；换入后aretu(u.u_ssav)将栈和帧指针恢复到newproc()中该调用点，但PC仍指向swtch()，从而向fork()或main()返回1。作者还解释了局部变量rp之所以在retu之后仍有效，是因为它被编译器分配在callee-save寄存器r4中，而savu/retu不触碰r2-r4。文章以汇编级细节还原了这段精巧但晦涩的早期内核代码。

## 16. 高通Oryon 3架构登顶：Snapdragon X2 Elite的CPU性能解析

## 17. PostgreSQL 19 中的计划提示：pg_plan_advice 的机遇与风险

- 原始链接: <https://clickhouse.com/blog/pg-plan-advice-postgresql-19>
- 英文标题: Hints and hazards: pg_plan_advice in PG19

PostgreSQL 19 新增两个 contrib 模块 pg_plan_advice 与 pg_stash_advice，为社区争论十年的「查询提示」需求提供了官方方案。pg_plan_advice 在会话级别通过 SET 命令指定扫描方法、连接顺序、连接方法、并行度、分区连接及半连接唯一性等计划参数；pg_stash_advice 则将提示绑定到特定查询标识符，避免影响其他查询。其底层机制是排除未选定的计划选项，但无法强制 planner 采纳某条路径，且不对建议合理性做校验，使用不当反而可能劣化性能。文章通过三个场景演示：一是 ORDER BY…LIMIT 下数据分布不均导致主键索引扫描遍历千万行，改用 BITMAP_HEAP_SCAN 后执行时间从 1461ms 降至 9ms；二是 JOIN 中跨表过滤条件存在相关性而 planner 默认独立假设，调整 JOIN_ORDER 后从 3837ms 降至 20ms，提升近 200 倍；三是数据分布变化后原提示变为「过期提示」，原本 0.05ms 的查询因强制位图扫描退化至 368ms，凸显了提示需随数据演进而维护的风险。文章还指出生产环境应使用 SET LOCAL 限定事务范围，并建议将模块加入 shared_preload_libraries。总体而言，该功能填补了 planner 在极端分布和跨表相关性场景下的短板，但使用者需承担提示失效或过期的运维成本。

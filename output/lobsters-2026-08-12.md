## 1. GNOME Shell 设计愿景

- 原始链接: <https://blogs.gnome.org/shell-dev/2026/08/11/gnome-shell-design-dreams/>
- 英文标题: GNOME Shell Design Dreams

GNOME 设计团队发文分享了 GNOME Shell 的长期设计构想。文章指出，近期界面主要是小改进，这些构想代表更完整的未来方向，但实现取决于开发者能力与兴趣。主要构想包括：搜索改为从搜索框弹出的覆盖层，以匹配 GNOME 40 的空间模型，并加入文件预览、操作按钮等丰富内容，有望在 GNOME 51 出现；快速设置菜单支持用户自定义开关；日历弹窗精简，通知并入快速设置；窗口管理探索拖放窗口时缩放工作区以提供更大拖放目标，以及自动调整窗口大小的 Mosaic 概念，后者需要合成器底层支持；窗口切换器计划混合最近窗口与按应用分组；还有更视觉化的登录屏幕、动态电池图标、透明面板等。文章强调这些构想需要社区帮助，如今通过 Builder 和 Mutter Devkit 可更容易构建测试分支，或用 sysext 安装。设计团队邀请开发者参与原型迭代，并可在 Matrix 的 #gnome-design 频道联系。

## 2. 代码评审是一项技能

- 原始链接: <https://typesanitizer.com/blog/code-review.html>
- 英文标题: Reviewing code is a skill

文章提出，代码评审是一项可以学习和提升的技能，而不是天生能力。作者通过自己近期评审中发现的三个真实bug案例——git配置并发写入、AWS CLI进度输出导致CI日志超限、校验和与tar包上传不同步可能引发故障——说明细致的代码评审能发现许多问题，而当时用高性能LLM做评审并未发现这些隐患。文章引用Google等研究指出，代码评审除寻找缺陷外，还承担教育、维护规范、把关和防止事故等多重目的；实际中理解代码和知识传递往往比单纯找bug更重要。作者结合自己从物理转行、在实践中逐渐学会评审的经历，认为评审能力可以通过训练提高，也有望教给别人。文章还建议在具备心理安全的前提下，尝试随机苏格拉底式对话等新的评审实验，并提醒要审视“评审是瓶颈”“LLM更擅长评审”等流行说法。核心结论是：代码评审是一项现代技能，人类的能力上限仍未知，值得持续投入提升。

## 6. 本地模型不会胜出：推理仍将集中在AI数据中心

- 原始链接: <https://www.seangoedecke.com/local-models-will-not-win/>
- 英文标题: No, local models will not win

本文反驳了“本地模型将成为主流”的观点。作者认为，无论开源模型多强，大多数推理仍会在AI数据中心完成。首先，本地模型在能力上永远无法与数据中心模型匹敌：当前前沿模型过于庞大，必须依赖数据中心集群；而更小模型虽有进步，但人们的实际选择总是倾向于当前最强大的模型，即使未来可在笔记本上运行类似GPT-5.6-Sol的模型，那时它也会被视为过弱而无人愿用。其次，本地模型实际更昂贵且低效：搭建家用推理设备的价格相当于数年订阅费用，电费每月可达50至300美元；数据中心模型之所以便宜，关键在“批处理”——GPU可同时处理数百用户的推理，而单个用户本地推理无法批处理，加上数据中心GPU（如B200）在算力和带宽上远优于消费级显卡，本地运行资源消耗约为数据中心模型的30倍。作者也探讨了本地模型可能获胜的少数情景：政府禁止数据中心、大型模型进步停滞而小型模型持续突破，或小型模型足够强大到满足几乎所有需求，但他认为这些都不太可能。尽管如此，本地模型仍有其细分场景：在延迟敏感的应用（如语音聊天）中可作为前端，由数据中心大模型处理核心思考；也可能满足部分用户对隐私、控制权或离线使用的需求。但总体而言，这只会是小众选择，大多数用户仍会通过数据中心完成推理。

## 8. 你从未听说过的最快double转字符串算法

- 原始链接: <https://vitaut.net/posts/2026/yy-dtoa/>
- 英文标题: The fastest double-to-string algorithm you’ve never heard of

这篇文章介绍了一种鲜为人知但极快的双精度浮点数转字符串算法“yy”，它源自yyjson库的yy_double.c，没有正式论文，属于Schubfach算法家族。其核心思想是寻找能往返转换的最短十进制表示，但特别之处在于整个计算只用固定宽度整数运算，且仅需一次乘以预计算10的幂的乘法，而经典Schubfach需要两到三次。文章用8位E4M3浮点格式可视化展示了算法步骤：选择十进制指数、缩放、生成四个候选（整数和10的倍数），通过三个谓词决定输出。重点解释了一个边界情况：对值192，理论上应输出2e2，但定点运算的截断导致比较结果差一个最低位，算法通过一个奇偶修正项η_c=-1来补偿，最终正确输出2e2。文章还提供了一个单HTML交互探索器，并提到一个有趣事实：最小正规double的边界情况。总之，该算法虽低调，但性能卓越，值得关注。

## 10. msword：Microsoft Word 1.1a 的原生 x64 移植

- 英文标题: msword: Port of Microsoft Word 1.1a to x64

该项目将 Microsoft Word for Windows 1.1a（代号 Opus）完整移植为原生 Windows x64 可执行文件。它直接编译原始 Word 源码和资源，用现代 C/C++ 替代 16 位汇编、分段内存和 Win16 平台边界，既非模拟器，也未使用现代编辑器控件重新实现，而是保留原始应用及用户体验。构建要求包括 64 位 Windows、Visual Studio 2022（含 C++ 桌面开发）、Win10/11 SDK、CMake 3.25+ 和 PowerShell。通过仓库提供的 CMake 预设可生成 WORD1.exe，支持 Debug/Release。测试套件覆盖 x64 运行时、原始数据结构和命令表、进程启动以及自动化 UI 流程（输入、选择、格式化、对话框、保存）。移植策略是：将 16 位 x86 汇编入口翻译为固定宽度 C/C++，把分段和双间接内存句柄映射到 x64 安全运行时，将 Win16 的启动、消息、图形、文件与资源行为适配为 Win32 API，并用原生工具重建原始资源。CMake 仅对遗留汇编树列账而不编译进目标，保证所有代码基于 AMD64 有效，同时保留历史实现作参考。项目强调保持原始行为、指针宽度安全，并对新翻译行为添加针对性测试。

## 11. 对齐对性能的影响

- 原始链接: <https://eme64.github.io/blog/2026/01/12/Alignment-Performance.html>
- 英文标题: Performance impact of Alignment

本文探讨了 SIMD 向量化中内存访问对齐对性能的影响，涵盖自动向量化与显式向量化（如 Vector API）。对齐指地址能被对齐大小整除；向量对齐取决于向量总大小而非元素大小。部分旧架构仅支持对齐访问，否则会出错；现代 CPU 通常支持非对齐访问，但跨越缓存行边界时访问会被拆分，导致额外开销。作者通过基准测试直观展示了不同对齐组合的性能差异：在 AVX512 上，64 字节向量完全非对齐时性能可下降 50% 以上；对齐存储比对齐加载更重要。在 AArch64 NEON 上，对齐影响约 10%。对自动向量化，C2 编译器只能选择对齐一个访问，错误地优先对齐加载会导致 20% 回归。对 Vector API 用户，数组对齐未知且 GC 可能移动对象，无法保证对齐；建议使用 native MemorySegment 并显式指定缓存行对齐。实测显示，native 对齐内存性能最佳，数组可能呈现多个性能层级，紧凑对象头会进一步恶化对齐。总体而言，即使存在非对齐开销，向量化通常仍远优于标量循环。

## 12. GitHub Actions 需要 OIDC 受众约束

- 原始链接: <https://blog.yossarian.net/2026/08/10/github-actions-needs-oidc-audience-constraints>
- 英文标题: GitHub Actions needs OIDC audience constraints

文章指出 GitHub Actions 的 OIDC（OpenID Connect）机制存在安全弱点。与 GitLab 要求在 id_tokens 中静态声明 audience（受众）不同，GitHub Actions 仅需授予 id-token: write 权限，即可在运行时通过 HTTP 请求动态指定任意 audience 获取 OIDC 令牌。OIDC 令牌中的 aud 声明本应限制哪个服务可接受该令牌，作为纵深防御；但动态 audience 使攻击者一旦控制某个工作流中的第三方代码，就能为其他服务（如 AWS）请求令牌，从而实现跨服务横向移动。作者认为这正是 Trusted Publishing 和 Sigstore 等集成所依赖的机制中的隐患。文章建议 GitHub 允许在 permissions 中像 ['pypi'] 这样静态约束可请求的 audience，以阻止工作流被用作跳板。同时承认可能有一些服务需要动态 audience，但这种情况较少，且 GitHub 仍可保留原有写法作为较不安全的兜底。整体上，作者认为增加受众约束是必要且相对易行的安全改进。

## 13. 一个新手学FFT：从正弦波到频谱图的实践笔记

- 原始链接: <https://entropicthoughts.com/fft>
- 英文标题: A noob learns FFT

作者以零基础身份，通过R语言的fft函数逐步探索傅里叶变换。文章从纯5Hz正弦波开始，解释了变换输出复数、幅度缩放、镜像频率（正负频率）以及相位与幅度的关系；随后展示了截断信号引发的频谱泄漏，并引入包络函数缓解问题。接着，作者观察了含噪声、复合信号以及脉冲、阶跃、方波、自回归衰减等特殊信号的频谱特征。在真实数据部分，他分析了一年内每小时建筑高度增长数据，识别出日周期、周周期以及3.5天等谐波周期，并指出365天峰值仅代表年度趋势。针对数据中的尖峰（脉冲伪信号），作者尝试通过在所有频率上减去常数幅度来滤波，效果不错；同时也比较了低通滤波和中值滤波的不足。最后，他采用分块计算频谱的方法生成频谱图，比较了不同窗口大小（日、周、半月、月、季度）的优缺点，并引入滑动窗口改进边界问题，观察到周周期在特定时段消失、倍频出现等现象。文章亮点在于以实验驱动、逐步深入，直观展示了FFT的实际应用与注意事项。

## 17. 清洁成本：OpenBSD -fret-clean 标志评估

- 原始链接: <https://briancallahan.net/blog/20260811.html>
- 英文标题: Cleaning costs, or, examining the OpenBSD -fret-clean flag

文章评估了OpenBSD 7.6中面向amd64的编译器缓解标志-fret-clean。它让LLVM在每个call指令后插入movq指令，清零返回地址槽，希望减少可用于ROP的陈旧返回地址。作者将该缓解移植到FreeBSD内核、libc、libcrypto和ld.so进行对比测量：目标.text段增加约8%；运行时性能影响高度依赖负载，从可忽略到病态微基准的27%增幅，真实场景约0-2%。在脏栈测试中，缓解确实使返回地址减少90%，但所有libc指针仅减少约16%，多数关键指针仍暴露。文章还指出该技术并非创新：IBM 2000年专利已描述完全相同做法，2018年论文也有类似方案，OpenBSD至少是第三次独立发明。相似的-fzero-call-used-regs和-mmitigate-rop均已被证明无效或移除。作者认为-fret-clean局部有效但全局贡献存疑，成本可能大于收益，且OpenBSD缺少实证评估；直观的缓解措施必须经过严格验证，否则会带来虚假安全感。

## 20. 拆分换行符并不简单：Python 与 Unicode 换行标准探源

- 原始链接: <https://www.b-list.org/weblog/2026/aug/10/newlines/>
- 英文标题: Breaking up (lines) is hard to do

文章探讨了一个看似简单实则复杂的问题：如何将多行文本拆分为行数组。作者指出，Python 的 str.splitlines() 实际上将多达十个不同 Unicode 码点及一个双码点序列视为换行。文章回顾了 ASCII 时代的历史：LINE FEED（LF）、CARRIAGE RETURN（CR）、FORM FEED（FF）、VERTICAL TAB（VT）等控制字符最初用于控制电传打字机，不同操作系统（如 CP/M、MS-DOS/Windows、Unix、Mac）采用了不同的换行约定，导致文本不兼容。Python 2.3 引入“通用换行模式”来兼容三种主流换行方式。随后，Unicode 标准在 UAX #14 中定义了七个换行码点，包括 LF、CR、VT、FF、NEL（U+0085）以及专为 Unicode 新增的 LS（U+2028）和 PS（U+2029），并识别 CRLF 序列。此外，Unicode 双向算法（UAX #9）中定义的段落分隔符——双向类别为 B 的三个码点（U+001C、U+001D、U+001E）——也被视为换行。最终，Python 的 splitlines() 结合这两种标准，共识别十个码点加 CRLF 序列，帖子详细解释了这一集合的由来及其在 CPython 源码中的注释依据。

## 22. 点云碰撞检测：从CAPT到MVT的演进与展望

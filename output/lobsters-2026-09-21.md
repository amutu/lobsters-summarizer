## 1. Lambda MicroEgg：支持绑定器与高阶模式的轻量 e-graph 工具

- 原始链接: <https://www.philipzucker.com/lambda_miller_egg/>
- 英文标题: Lambda MicroEgg

Philip Zucker 发布了 Lambda MicroEgg，一个基于 s-expression 前端的 e-graph 工具，核心亮点是原生支持带作用域的 alpha 感知绑定器。该项目在 Max Pavlovich 的 microegg 基础上，增加了内置绑定器（以 @ 标记）、高阶 Miller 模式匹配、以及右侧的捕获避免替换。作者引入「lifting/thinning」机制处理上下文：每个 e-node 的 u32 Id 中借用 1 字节存储 thinning 位向量，从而支持最多 7 个自由变量，且 alpha 等价项可 hash-cons 到同一内存。高阶应用采用 [] 语法自动 curry，避免繁琐的嵌套 app 写法。性能上，AC-10 饱和测试约 1.5 秒，比 egg 的 0.6 秒慢但同数量级。作者坦承大量借助 AI 完成 Rust 实现，并计划后续支持更多变量、Buchberger 算法、多集/半环补全及证明日志导出。潜在应用包括关系演算、积分规则、程序解释器、类型检查器与不动点推理。文章还讨论了绑定器并非核心难点，真正关键的是上下文（ctx |- t）及其操作（weakening、exchange），以及有序 Miller 模式对非线性模式的限制。

## 2. 超越 jj：配置与工具生态全景

- 原始链接: <https://andre.arko.net/2026/09/16/beyond-jj-config-and-tools-ecosystem/>
- 英文标题: Beyond jj: config & tools ecosystem

本文是 2026 年 JJ Con 演讲的整理稿，系统梳理了 Jujutsu（jj）版本控制工具的配置与周边生态。作者从三个层面展开：一是 jj 核心内置功能，包括 bookmark advance（取代旧别名 tug）、bisect run（自动二分定位变更）、jj run（对 revset 中每个变更执行脚本）、jj fix（仅对已修改文件运行格式化/检查，速度远快于 run）、jj tag（原生标签管理，无需再调 git tag）、jj arrange（交互式变更重排，类似 git rebase -i 但无需编辑文本文件）以及最新的 converge 命令（自动合并分叉变更流，减少手动协调）。二是配置与集成层面，介绍了利用别名嵌套实现子命令的巧妙 hack、模拟 git push 的 publish 别名（作者认为这是当前 jj 内置最大缺口），以及 GitHub 堆叠 PR、JJHub、Radicle、Tangled 等 forge 对 jj 工作流的支持，其中 Tangled 被视为最接近「jj 原生」的托管平台。三是外部工具生态，涵盖 GUI（gg、JayJay、lightjj 等）、TUI（lazyjj、jj-fzf、jjui、majjit 等，是增长最活跃的领域）、主流编辑器插件（VSCode、JetBrains、Vim、Emacs、Helix 均有集成）及工作流辅助工具。作者强调，尽管 jj 生态仍在快速成长，社区热情高涨，工具选择已相当丰富。

## 3. Motif 界面工具包终于有了活跃维护的分支

- 原始链接: <https://www.osnews.com/story/145877/an-actively-maintained-and-updated-motif-fork-actually-exists/>
- 英文标题: An actively maintained and updated Motif fork actually exists

本文作者 Thom Holwerda 介绍了一个正在活跃维护的 Motif 分支项目。Motif 是 X11 时代极具影响力的用户界面工具包，定义了 20 世纪 90 年代企业级软件的视觉风格，但原始上游 SourceForge 项目已多年停滞：管理员不活跃、bug 追踪器消失、用户论坛早在 2017 年关闭。去年，以 Tim Hentenaar 为首的一群开发者在 GitHub 上发起 fork，合并了上游搁置多年的修复、Gentoo 的补丁及自身改进，至今已发布五个版本。作者本人是 Motif 的忠实爱好者，常在 HP c8000 PA-RISC 工作站上运行 HP-UX 体验 Motif 界面，并寄望于未来能整合现有 Motif 相关项目（如 Emwm 窗口管理器、toolbox 启动器、xmsm 会话管理器等）构建一套完整的 Linux 桌面环境。评论区观点分歧明显：支持者认为 Motif 在按钮状态、滚动条可见性、控件区分度等可用性方面优于现代 GTK4 等框架；批评者则指出 Motif 基于 Xt 内蕴的编程模型冗长笨拙，早已成为反面教材。此外，Wayland 逐步取代 X11 的趋势也给 Motif 生态的长期前景带来不确定性。

## 4. 关于浏览器未来的思考

- 原始链接: <https://sarahjamielewis.com/log/2026/future-of-web-browsers.html>
- 英文标题: Thoughts on the Future of Web Browsers

作者因Firefox持续集成AI功能而深感忧虑，认为Mozilla已明确将产品推向「智能窗口」方向，为第三方AI代理服务，而非为普通用户设计。他呼吁各Firefox分支合作维护一个独立于Mozilla的硬分叉，否则独立、非「slop」（低质填充）的万维网将不复存在。这一讨论催生了「base browser」项目：作者与志愿者团队基于Firefox 153 ESR，编写了一个涉及1605个文件、删除约85万行代码（37MB）的补丁，彻底移除AI集成等用户不友好功能，并通过git不可逆删除标志和自定义Python脚本将补丁压缩至不足1MB。作者坦言缺乏足够资金和开发者长期维护该项目，但仍希望至少让更多人学会从源码构建Firefox。作为临时应对，他转向openzim离线阅读器、独立桌面应用和RSS订阅来减少对浏览器的依赖。但他强调不想仅停留在「逃跑」，而是渴望建设性愿景。他回顾2000年代初Firefox引发的浏览器复兴，以及Amaya、Flock等将浏览器视为创作工具而非单纯消费工具的理念，并分享了自己实验支持gemini协议和RSS的微型浏览器的经历。文章以「我们需要新的噪音」作结，表达在商业利益主导的万维网标准中重新寻找愿景的迫切愿望。

## 5. 从反对者的身份看GDPR的价值

- 原始链接: <https://matduggan.com/you-know-gdpr-is-good-based-on-who-hates-it/>
- 英文标题: You Know GDPR Is Good Based on Who Hates It

文章以罗斯福「他们的仇恨恰恰证明我在做正确的事」为引，论证GDPR的成功。作者指出，cookie横幅虽被批评为政府干预的产物，实为「黑暗模式」，反而让公众意识到数据被数百个合作方共享的事实。GDPR迅速成为全球标准，源于「布鲁塞尔效应」：欧盟市场体量巨大且无法规避，日本2019年被迫与欧盟达成数据自由流动协议即为明证。反观美国，9/11后监管重心转向安全而非隐私，科技巨头借巨额游说和「旋转门」把持联邦立法，形成Zuboff所称的「监控资本主义」——用户不再是产品，而是被开采的原材料。作者援引波兰尼「双重运动」理论，指出美国在监控资本主义领域始终缺少第二轮社会纠偏，联邦层面已无制衡力量。结论是：GDPR的扩散并非欧洲野心，而是华盛顿缺席后布鲁塞尔填补了权力真空。隐私保护终将如安全带、禁烟令一般，从争议走向常识，而当年激烈反对的巨头们，终将在某艘游艇上声称自己「一直支持」。

## 6. 在测试方法名中使用不可断空格

- 原始链接: <https://mnapoli.fr/using-non-breakable-spaces-in-test-method-names>
- 英文标题: Using non-breakable spaces in test method names

本文介绍了在 PHP 测试方法名中使用不可断空格（&nbsp;）的实践。作者来自 Wizaplace 公司，受编码风格演讲启发，团队从传统的 camelCase（如 testAddProductToWishlist）逐步过渡到 snake_case，最终尝试用不可断空格让方法名读起来像自然语言句子，例如 test a user can add a product to a wishlist()。不可断空格在编辑器中外观与普通空格一致，但 PHP 将其视为普通字符，语法完全合法。团队以小规模实验方式验证，使用超过一年后仍非常满意，测试可读性显著提升。工具兼容性方面，git、PhpStorm、Sublime Text、GitHub 及 PHPUnit 集成均正常工作；Atom 和 VS Code 曾有语法高亮问题，已通过社区 PR 修复。PhpStorm 中需调整「快速定义」快捷键以避免冲突。在团队接受度上，新成员初次阅读代码时会有短暂困惑，但无论初级还是高级开发者都能较快适应。作者认为在小型闭源项目中推广容易，但在开源项目中因贡献者无法获得即时解释而较难推行，建议先在小型项目中采用，并尽量向社区传播这一实践，期待未来能更广泛地推广。

## 7. V 语言深度评测（2023）

- 原始链接: <https://n-skvortsov-1997.github.io/reviews/>
- 英文标题: V Language Review (2023)

本文是作者基于六个月使用经验对 V 语言（2023 年）的全面评测。文档方面，i128/u128 标注「soon」已逾四年，泛型部分仅有代码示例而无说明。内存管理是文章重点：手动模式下标准库函数普遍泄漏，vweb 框架数组从不回收，无法用于实际应用；autofree 模式文档宣称 90–100% 自动释放，实测简单程序仍泄漏，vweb 服务器十秒内泄漏 1KB，此前 free 函数因 GC 冲突退化为空操作，语言作者自己的编辑器 Ved 和编译器在 autofree 下均崩溃；GC 默认模式缺乏逃逸分析，任何取地址即触发堆分配，11 字符字符串插值竟分配 304 字节。作者批评语言作者将 autofree「生产就绪」的期限从 0.3 版一路推迟至 1.0 版，五年过去核心特性仍远未成熟，结论是 V 在内存管理和文档质量上存在根本性问题，不适合生产使用。

## 8. Notion 如何用 CRDT 实现并发编辑

- 原始链接: <https://www.notion.com/blog/how-notion-handles-concurrent-editing-with-crdts>
- 英文标题: How Notion handles concurrent editing with CRDTs

Notion 在 2025 年之前采用「最后写入胜出」策略，同一 block 的并发修改会直接覆盖他人编辑，数据丢失风险随协作者增多而加剧。为支持真正的多人协作及离线模式，Notion 重新设计了文本编辑的底层数据模型，引入基于 RGA（可复制可增长数组）的 CRDT 系统。该系统为每个文本片段分配由会话 ID 与 Lamport 时钟组成的唯一标识，通过确定性合并规则保证并发操作不丢失任何一方的修改。富文本层面，Notion 借鉴 Peritext 算法，将粗体、斜体等注解建模为可延伸或不可延伸的锚点操作，支持多注解叠加。针对 Notion 特有的 block 分割场景，团队提出「文本切片」「切片树」「文本实例」等概念，使跨 block 的并发编辑仍能精确定位目标位置；并引入「搜索标签」机制，将分割后定位的查询复杂度从线性降至常数级。该系统于 2025 年 7 月上线，每分钟处理数百万 CRDT 操作，是业界规模最大的 CRDT 部署之一，同时为离线模式与 AI 代理协作奠定了架构基础。

## 9. HEIF Heist：面向图像解码器的跨平台远程攻击链

- 原始链接: <https://heif-heist.com>
- 英文标题: HEIF Heist

Hacktron研究团队披露了一类名为「HEIF Heist」的远程攻击路径，针对所有处理HEIF、HEIC或AVIF图像的服务。漏洞位于底层C/C++解码器libheif和libde265中，这些库通过ImageMagick、libvips、Sharp等封装广泛嵌入生产环境。攻击者只需向上传端点投递精心构造的.avif或.heic文件，即可探测目标libheif版本并发送匹配payload，触发内存损坏、数据窃取或远程代码执行。影响面极广，涵盖OpenAI私有仓库、Slack、Meta核心产品、Discourse、Next.js（AVIF图像优化）、GitHub Enterprise（CVE-2026-19118）及多个Web框架。修复方面，团队建议升级至libheif v1.23.2及以上版本，并在架构层面禁用不必要的HEIF/AVIF解码或将图像处理隔离至加固沙箱。利用并非开箱即用，需版本指纹识别与payload定制，部分RCE尝试需数千次上传；但借助GPT-5.6 Sol等前沿模型，开发周期可压缩至1至3天。研究由Harsh Jaiswal等人主导，历时数月，从Discourse中的单一libheif RCE扩展为对整条图像处理生态的系统性排查。

## 10. Vim 中一个名为 UserGettingBored 的玩笑自动命令

- 原始链接: <https://evanhahn.com/usergettingbored-vim/>
- 英文标题: Vim's UserGettingBored autocmd

Vim 编辑器的自动命令（autocmd）机制允许用户在特定事件触发时执行代码，拥有超过 100 种事件。其中有一个名为「UserGettingBored」的事件格外引人注目，其文档描述为：「当用户按下同一个键 42 次时触发。开玩笑的！:-)」。然而，这个事件实际上并不存在任何功能，仅出现在文档和部分测试中；若尝试用 autocmd 绑定它，会收到「无此组或事件」的错误。该玩笑由 Vim 作者 Bram Moolenaar 于 2000 年 7 月首次加入，早于 Vim 6.0 发布一年多，最初描述为「当用户按下 CTRL-C 时。开玩笑的！」，2001 年 8 月补上了笑脸符号，2013 年改为「按同一键 42 次」的现行版本。它同时存在于 Vim、Neovim 和 Vim Classic 中，但从未真正生效过。2022 年，开发者 Mike Smith 受此启发制作了一个非官方插件：在插入模式下连续按同一键 42 次，屏幕上会出现 Samuel L. Jackson 的图片，让这个 22 年前的玩笑终于「成真」。文章整体轻松幽默，展示了开源社区中开发者以幽默注释增添趣味的文化。

## 11. 确定性核心与非确定性外壳

- 原始链接: <https://outdata.net/blog/260803>
- 英文标题: Deterministic Core, Non-Deterministic Shell

文章回顾了 Gary Bernhardt 十四年前提出的「函数式核心、命令式外壳」架构，并将其推广为「确定性核心、非确定性外壳」。原架构将代码分为纯函数核心（无 IO、无破坏性状态更新，专注业务逻辑）与命令式外壳（管理状态、协调外部依赖、处理 IO）。作者指出，纯函数并非获得确定性的唯一途径：状态机虽为命令式，只要给定相同的调用序列就返回相同状态，同样具备可测试性。因此将要求从「纯函数」放宽为「确定性」，既保留了可测试优势，又拓宽了适用场景（如 C 等语言）。文章列举了常见非确定性行为——未播种的随机数、异步与多线程、网络与进程通信、本地存储与数据库读写、获取系统时间等，建议将它们归入外壳层，通过拆分函数或注入参数的方式将确定性逻辑剥离出来。针对遗留代码，作者提出「确定性碎片整理」的渐进策略，类比 Windows 磁盘碎片整理：在散乱的代码中识别并逐步聚合确定性片段，使难以测试的非确定性代码面积不断缩小。即使大型项目无法收敛为单一确定性核心，将数千个碎片整合为数百个也是显著进步。作者强调，每个糟糕的代码库中都隐藏着更整洁的确定性状态机，逐块发掘即可逐步提升软件的可修改性与可靠性。

## 12. Quarkdown：图灵完备的 Markdown 排版系统

- 原始链接: <https://github.com/iamgio/quarkdown>
- 英文标题: Quarkdown: Turing-complete Markdown typesetting system

Quarkdown 是一个基于 CommonMark 与 GFM 的现代 Markdown 排版系统，核心亮点在于为 Markdown 引入图灵完备的脚本能力。用户可在 Markdown 中直接定义函数与变量，使用条件语句、循环及标准库中的布局构建、数学运算、I/O 等模块，实现传统 Markdown 无法完成的动态内容生成。一个源文件可通过 .doctype 函数编译为 HTML、分页文档（基于 paged.js）、幻灯片（基于 reveal.js）、技术文档、PDF 或纯文本，覆盖学术论文、书籍、知识库与交互演示等场景。文章通过与 LaTeX、Typst、AsciiDoc、MDX 的对比，强调 Quarkdown 在简洁可读性与完整文档控制间取得平衡，学习曲线平缓，同时支持脚本化、多目标导出与静态站点生成。系统提供 VS Code 与 IntelliJ IDEA 编辑器扩展，支持实时预览（官方 wiki 逾百篇子文档约 2 秒编译完成），并内置对编码 Agent 的技能支持。安装支持 Linux/macOS 脚本、Homebrew、Windows 脚本、Scoop 及 GitHub Actions 等多种方式。项目默认采用 GNU GPLv3 许可，CLI 与语言服务器模块采用 AGPLv3。名称「Quarkdown」取自「下夸克」，寓意以极轻的粒子构建复杂结构。

## 13. w64devkit 过去一年回顾

- 原始链接: <https://nullprogram.com/blog/2026/09/20/>
- 英文标题: What's been going on in w64devkit the past year

w64devkit 是一个面向 Windows 的 MinGW 交叉编译工具包，作者回顾了该项目近一年的主要进展。安全方面，所有 EXE 和 DLL 已实现代码签名，构建由 GitHub Actions 自动化并启用发布不可变性，产物一经锁定任何人不可篡改。工具链方面，x64 版本升级为 multilib 架构，可同时编译 32 位与 64 位程序；Binutils 上游已支持按需自动切换 bigobj 格式，解决了 C++ 大项目段数超限问题；静态运行时从 -Os 切换为 -O2，以体积换速度。新增工具包括 CMake、Ninja、ccmake、ccache、widl/uuidgen、make2compdb、recycle、quilt（C++ 全量重写）、NSIS 及 zstd。运行时层面，作者独立实现了 C11 线程（基于 SRW 锁，需 Windows 7 以上），并将 std::terminate 改为 trap 以配合调试器，同时削减约 100KB 冗余。未来计划重新启用 LTO 并分发 FatLTO 运行时，有望成为首个提供该功能的工具链。x86 版本仍保持 Windows XP 兼容。

- 原始链接: <https://www.buzzsprout.com/2469780/episodes/19824439>

## 15. 漫长旅途的最后一公里：浏览器中更快的 NumPy

- 原始链接: <https://notebook.link/blog/the-last-mile-faster-numpy>
- 英文标题: The last mile of a long road: faster NumPy in the browser

长期以来，浏览器中的 NumPy 无法使用加速 BLAS，矩阵乘法只能退化为朴素 C 循环，性能严重受限。Emscripten-forge（面向 WebAssembly 的 conda 分发系统）的 NumPy 包现已链接 OpenBLAS 0.3.34（WASM SIMD 构建），在 n=1024 时 np.matmul 的 float32 吞吐从 0.90 GFLOPS 跃升至 28.0 GFLOPS（约 30.92 倍），float64 提升约 14.90 倍；np.linalg 系列也有 1.2–2.1 倍改善。即将发布的 OpenBLAS 0.3.35 加入 QuantStack 贡献的 WASM SIMD 内核，float32 再提 1.79 倍；若启用可选的 Relaxed SIMD 构建（Chromium 153），端到端 float32 可达约 64.89 倍。技术路径上，团队先为 wasm32 构建 Flang（LLVM 的 Fortran 前端），再为 OpenBLAS 编写 Emscripten 适配补丁，最终完成 NumPy 与 libopenblas 的动态链接。得益于 conda 包模型，升级 OpenBLAS 无需重建 NumPy，SciPy、scikit-learn 及 xtensor-blas 等均可共享同一库。相关内核已上游至 OpenBLAS，未来可惠及 Pyodide 等其他 WebAssembly Python 栈。

## 16. 快速哈希函数的对抗性碰撞分析

- 原始链接: <https://thomasahle.com/blog/adversarial-examples-for-hashes/>
- 英文标题: Adversarial examples for fast hash functions

本文针对SMhasher中大量流行快速哈希函数（如xxHash、komihash、a5hash、HighwayHash、SpookyHash等）进行系统性对抗性碰撞分析。作者借助AI工具Claude Fable，发现多数哈希存在严重碰撞缺陷，性能至少低于理论预期20位；部分已发表证明亦存在漏洞，经Lean形式化验证后确认。作者自研的ChainHash在Intel Xeon上吞吐量居首、Apple M2 Pro上居次，同时具备可证明的碰撞保证。文章归纳出四类鲁棒性问题：种子无关碰撞对、少路碰撞、弱键多碰撞与种子无关多碰撞，并指出多数缺陷源于折叠乘法遗忘补码、公共算术将密钥排除在差异计算之外、零操作数吸收等重复模式。核心结论有三：其一，AI改变了威胁模型，以往依赖保密性的软件如今易被攻破；其二，可证明安全的哈希与启发式哈希速度相当，无需全部切换至SHA等密码学哈希；其三，Lean可验证证明优于已发表证明，审计中发现多处可修复与不可修复的缺陷。所有发现已在上游披露，维护者共识为仅多碰撞攻击需修复。

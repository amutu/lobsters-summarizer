## 1. 饿死狐狸：一款不对称棋盘游戏的计算机分析

- 原始链接: <https://entropicthoughts.com/what-the-fox-say>
- 英文标题: What the fox say?

本文对北欧传统棋盘游戏「饿死狐狸」（Starve the Fox）进行了系统的计算机分析。该游戏为不对称规则：狐狸方仅2子但可跳跃吃羊，羊方20子但不可后退，目标是填满中央3×3围栏。作者借助OpenSpiel框架，先用蒙特卡洛树搜索（MCTS）发现狐狸方胜率约85%，但进一步实验表明羊方在足够深的搜索下仍可取胜，揭示出羊方需协调整群、思考深度远高于狐狸方的特性，使游戏天然适合亲子对弈。为加速搜索，作者采用迭代自对弈加回归训练的方式构建启发式评估函数，将随机推演截断为8步并以学习权重补分，数轮迭代后获得较强对手。文章详细解读了学到的位置价值与宏观变量权重：一只被吃的羊约值0.15，羊进围栏平均值0.08，狐狸占据中盘b4-f5区域最优；第2排因易被吃而价值最低。此外，作者还提出从自对弈记录中生成类似围棋死活题的练习谜题（如「N步内困死狐狸」「N步内吃羊而不被反困」），N=1至3即可产出约2000题。文末作者感慨，正是近一年语言模型工具链的进步，才让这类编码与分析项目变得切实可行。

## 4. Qwenputer：在 Qwen3.5 权重中编译出一颗确定性 RISC-V CPU

- 原始链接: <https://divagr.com/blog/qwenputer>
- 英文标题: Qwenputer: a fully functioning, deterministic RISC-V CPU inside Qwen3.5

Qwenputer 是一个实验性模型，在 Qwen 3.5 4B 的权重中嵌入了一颗 32 位 RISC-V CPU（RV32IM + Zba 扩展及大数运算单元），无需任何外部运行时或工具调用即可在模型前向传播中执行算术、C 和 MicroPython 代码。其核心思路是利用 Qwen3.5 中 3/4 注意力层采用的 Gated DeltaNet（线性 RNN）作为 RAM：将门控设为 1、写入强度 beta 设为 1、采用 one-hot 键编码，即可对状态矩阵进行精确的逐行读写，成本远低于传统 KV 缓存。CPU 通过编译器直接写入权重（无需训练），占用 11 层，每条指令对应若干生成 token 作为执行轨迹。该 CPU 通过了官方 riscv-tests，自由运行 1800 万条指令零错误。在 DeepMind 和 NUPA 算术基准上，Qwenputer 达到 97.5%–100% 准确率，与外挂 Python 工具持平，远超基座模型。作者还实现了实验性文件系统（1024 槽、约 53000 token 容量），支持跨对话持久化。局限包括：检查点约 18.8 GB、需 RvChat 驱动启动、每条指令耗时数 token 导致整体较慢。作者还探讨了该架构在 AI 安全研究中的应用，如混合模型隐藏推理以规避 CoT 监控、以及编译权重作为模型无法篡改的内置监控工具。

## 8. C2PA的eMudhra时刻：媒体内容信任链的撤销困境

- 原始链接: <https://www.da.vidbuchanan.co.uk/blog/c2pa-four.html>
- 英文标题: C2PA's eMudhra Moment

本文以2026年eMudhra CA被攻破事件为切入点，探讨C2PA（内容凭证）生态系统在面对类似CA妥协时的脆弱性。作者David Buchanan指出，Web PKI生态在eMudhra事件中虽不算完美，但主流浏览器能较快获取撤销信息；而C2PA生态尚处早期，当前主流媒体验证工具根本不支持证书撤销。作者随后通过一个实验演示了C2PA信任链的严重缺陷：利用已公开且不属于漏洞赏金范围的已知漏洞，他让Google的C2PA中间CA为任意叶子密钥签发证书，并构造出一条可验证的S/MIME签名链，该链最终锚定在Google C2PA根CA（列入官方C2PA信任列表）上。作者坦承，该演示与eMudhra事件并非完全对等——eMudhra是受信任的中间CA本身被攻破，而他的案例中叶子证书私钥仅为数字「4」，但核心问题在于Google的中间CA可以为任意密钥签名。在TLS场景中这属于正常签发流程，但在C2PA的信任模型下，这意味着任何持有该中间CA签名能力的人都能为任意内容伪造合法凭证，且缺乏撤销手段。文章的核心警示是：C2PA若不能尽快建立类似Web PKI的撤销与信任管理基础设施，将面临与eMudhra事件同类的系统性风险。

## 9. Future 特性缺失的「完成」状态

- 原始链接: <https://blog.yoshuawuyts.com/the-future-trait-has-a-missing-state>
- 英文标题: The Future Trait Has A Missing State

本文深入分析了 Rust 异步生态中 Future 特性的一个核心设计缺陷：Poll 枚举仅有 Pending 和 Ready 两个变体，缺少表达「已完成且无更多结果」的 Done 状态。Future 完成后再调用 poll 会触发 panic，这在嵌入式等对代码体积敏感的场景中尤为有害。作者介绍了 MaybeDone 包装器作为变通方案，它能同时持有 Future 或其输出值，并在完成后持续返回 Ready(())；但 futures  crate 中的 FusedFuture/Fuse 适配器则滥用了 Pending 语义，存在隐患。作者建议在 Poll 中新增 Done 变体，将「已完成」的责任从被调用方转移到调用方，从而解除 async 对 panic 机制的隐式依赖，但 Poll 未标记 #[non_exhaustive]，无法直接修改。对于尚未稳定的 Coroutine 特性，作者建议将 CoroutineState 重命名为 Yield/Return/Done 三个变体，避免重蹈 Future 的覆辙。此外，文章还讨论了 Start（首次 poll 前）、pre-state（未初始化）以及 Snoozed（就绪但未被 poll）等额外状态，并提出了「poll 时必须同时 poll 所有 waker 已触发的子 Future」这一活性规则。最终结论是：当前不宜贸然替换 Future 特性，但应确保 Coroutine 和 gen 关键字等新设计不再重复同样的错误。

## 10. 9 位 AES 密钥：多款 PDF 实现的文件密钥可被轻松暴力破解

- 原始链接: <https://v12.sh/blog/the-case-of-the-9bit-aes-key>
- 英文标题: The case of the 9 bit AES key

本文披露了多款主流 PDF 库在生成 AES-256 文件密钥时使用了非密码学安全的随机源，导致实际密钥空间极小、可被无密码解密。MuPDF（1.28.5 之前）使用 drand48 线性同余生成器，种子仅为当前秒级时间戳；由于 LCG 高位不影响低位，输出字节仅取自状态第 17–24 位，而低 16 位固定为 0x330e，最终只有 9 位时间戳信息影响密钥，全部 512 种候选可在约 11 毫秒内穷举。Foxit PDF Reader 2026 版将文件密钥派生为 SHA-256(时间戳 ‖ 32 字节零填充 ‖「there」)，32 位时间戳在 32 线程 Ryzen 9 7950X 上以每秒约 3.7 亿次速度搜索，覆盖 1970 年至今仅需约 4.85 秒；该模式可追溯至 2014 年 PDFium 初始提交，原作者为 Foxit。OpenPDF 与 iText 则用毫秒时间戳加 JVM 空闲内存种子驱动 ARC4 流，可通过明文盐值验证猜测。作者指出，这些本应比旧版密码派生密钥更安全的 AES-256 升级，因随机源缺陷反而产生了更弱的密钥。问题已通报各厂商，MuPDF 已修复，但此前生成的 PDF 无法追溯保护，作者已公开 MuPDF 与 Foxit 的解密工具。

## 11. PDP系列计算机简史

- 原始链接: <https://entropicthoughts.com/history-of-pdp-computers>
- 英文标题: Extremely brief history of PDP computers

本文以时间线形式梳理了DEC公司PDP系列计算机的发展脉络。PDP-1最初是探索通用计算机能否替代工业控制中人工或逻辑电路板的实验；PDP-4为其廉价变体，经芯片升级演变为PDP-7与PDP-9；PDP-5更小更便宜，升级为PDP-8；PDP-6面向分时系统市场，支持大量直接寻址内存与内存保护，可运行Lisp，升级为PDP-10；PDP-11采用新架构试图统一各产品线，但最强配置仍不足以吸引PDP-10用户；VAX最终取代PDP-10。文章重点指出，早期黑客文化因机器规模分为两派：小机（18位及以下）催生了Unix、C语言、Usenet、vi、make、awk等；大机（32位及以上）则孕育了Emacs、Scheme、TeX、Zork、电子邮件和Microsoft Basic。这种分裂的根源在于雇主预算——Bell Labs资源有限，MIT则有DARPA资助，Richard Gabriel将其概括为「MIT/Stanford风格」与「新泽西路线」。作者坦言写作动机不明，但通过经通胀调整的价格与内存周期时间（作为速度代理）的图表，呈现了这些机器如何深刻塑造了早期计算文化。

## 12. Web 承受不起 JavaScript 运行时的单一化

- 原始链接: <https://redmonk.com/kholterhoff/2026/10/27/js-runtime-monoculture/>
- 英文标题: The Web Can't Afford a JavaScript Runtime Monoculture

Deno 团队整体加入 Cloudflare 且运行时将在一年后停更，使通用 JS 运行时仅剩 Node.js、Bun 和 Cloudflare 的 workerd 三家，其中两家核心业务并非运行时本身。作者以 IE6 时代浏览器单一化导致创新停滞的历史为鉴，指出服务端运行时正经历类似整合：Node、Deno、workerd 均依赖 Google V8 引擎，Bun 依赖 Apple JavaScriptCore，独立实现数量急剧缩减。这带来三重风险：一是 WinterTC 等标准组织失去独立声音，最广泛部署的运行时行为将默认成为标准；二是单一引擎故障将波及全部运行时，如同 2014 年 OpenSSL Heartbleed 事件；三是竞争消失后创新动力减弱——Deno 虽未超越 Node，却推动了 ES Modules、内置 TypeScript 支持、权限安全模型等特性落地，Bun 则推动了速度竞争。独立分叉 Ende 和 Dodo 已出现，但资源有限，远不及 Linux 生态的多发行版、多资助方格局。Cloudflare 工程师 James Snell 强调选择本身是生态前进的动力。作者警告，若无人持续构建和资助替代方案，JS 运行时生态恐重蹈 IE6 覆辙。

## 16. Redox 环形缓冲区项目总结

- 原始链接: <https://www.redox-os.org/news/nlnet-rb-summary/>
- 英文标题: Redox Ring Buffers Project Summary

Redox OS 团队在 NLnet 等资助下完成了类 io_uring 的环形缓冲区（Redox Rings）项目。由于 Redox 是微内核，I/O 由用户态 scheme 进程处理，该项目在应用与 scheme 之间引入共享内存环形队列（SQ/CQ），实现无阻塞、零拷贝的异步 I/O 通信。团队发布了 redox-rings  crate 及类 liburing 的 redox-ring API，支持固定与动态两种缓冲分配策略，并已在 RamFS、NVMed 等存储服务中落地。此外，团队为设备驱动构建了异步执行器，NVMe 驱动已接入。在性能优化方面，内核引入直接上下文切换（绕过调度器，IPC 延迟降低 15–20%）、大页映射（TLB 缺失率降低 75%）以及消除 XSAVE/XRSTOR 开销等手段，使 redox_ring 路径比传统同步系统调用快 14–15 倍，IPC 往返延迟从约 5800 周期降至约 2700 周期。未来工作将聚焦进一步简化 IPC 原语、降低锁开销及减少系统调用入口成本，以逼近 seL4 等高性能微内核水平。

## 17. 一种面向智能体的原生软件需求开放格式

- 原始链接: <https://slcr.dev/announcements#2026-10-29-slcr-launches>
- 英文标题: An open format for writing agent-native software requirements

2026年10月29日，Wack 团队正式发布了 SLCR（Sliceable, Linked, Checkable Requirements，读作「slicer」），这是一种面向人类开发者与编码代理共同使用的开放软件需求格式。项目起因是 Wack 团队在长期维护代码库时发现，随着越来越多实现工作交由代理完成，代理输出会逐渐偏离原始规范。SLCR 的核心价值在于为团队提供一种可验证机制，确保代理返回的实现仍符合最初的需求描述。名称中三个关键词分别对应其设计特性：可切片（Sliceable）、可链接（Linked）、可校验（Checkable），使需求文档既能被人类阅读，也能被代理解析与执行。目前团队已提供完整入门教程，涵盖从安装命令行工具到编写第一份需求规格的全过程，同时发布了 agent skill，帮助代理学会读写 SLCR 格式。项目完全开源，代码托管于 GitHub，欢迎社区提交 issue 反馈问题或贡献 Pull Request。

## 18. 编码代理、启动套件与 pgledger：功能设计的新张力

- 原始链接: <https://www.pgrs.net/2026/10/29/coding-agents-starter-kits-and-pgledger/>
- 英文标题: Coding Agents, Starter Kits and pgledger

作者介绍了其纯 PostgreSQL 账本实现 pgledger，并将其定位为一种「启动套件」而非传统软件依赖——它是一组数据库表与 SQL 函数，需嵌入现有应用。编码代理（coding agents）的兴起彻底改变了使用方式：用户只需发出「将 pgledger 添加到我的应用」之类的提示，代理即可自动获取、适配并定制代码，大幅降低了集成与修改成本。这一变化引发了功能设计上的双重张力：代理能轻松为用户添加所需功能，因此 pgledger 本身无需内置过多特性；但代理也能轻松删除不需要的功能，因此作为启动套件应尽可能提供丰富的可选功能。作者据此提出三条纳入标准：需求是否广泛、实现是否足够复杂（复杂功能交给代理风险高，作者亲自实现可保证设计与测试质量）、是否与核心函数深度集成。基于此，作者最终决定为 pgledger 加入幂等性支持：调用 pgledger_create_transfer 时可传入 idempotency_key，重复调用返回已有记录而非新建，若同一 key 搭配不同参数则报错。作者认为，编码代理让组装软件变得容易，但经过充分测试的坚固组件因此更加重要；pgledger 正是为关键财务逻辑提供可靠基座，希望推动更多应用广泛采用复式账本。
